# 바이브코딩을 위한 RAG 벤치마크 (4/6): VectorDB 선택 기준

이 글은 바이브코딩을 위한 RAG 벤치마크 시리즈의 4번째 글입니다.

VectorDB 비교는 브랜드 비교가 아니라 같은 벡터와 같은 질의를 서로 다른 인덱스 구조에 넣어 보는 실험입니다. Flat 인덱스는 완전 정확도를 주지만 코퍼스가 커지면 느려집니다. IVF는 빠르지만 recall이 약간 낮아집니다. 이 트레이드오프를 직접 측정해야 운영 조건에 맞는 선택이 가능합니다.

바이브코딩에서 이 개념이 중요한 이유는 단순합니다. AI에게 VectorDB 비교 코드를 요청할 때 인덱스 타입, recall, latency를 함께 측정하도록 명시하지 않으면, 기능 목록 비교에 머물고 실제 운영 조건에서의 차이를 확인할 수 없기 때문입니다.

> VectorDB 선택은 브랜드 이름을 고르는 일이 아닙니다. 같은 임베딩 벡터가 서로 다른 인덱스 구조 안에서 어떻게 동작하는지 측정하는 실험입니다.

---

## 이 글에서 다룰 문제

- VectorDB는 기능 목록이 아니라 어떤 운영 조건으로 비교해야 할까요?
- 같은 임베딩과 corpus에서 VectorDB만 바꿔 보려면 무엇을 고정해야 할까요?
- Flat, IVF, HNSW 인덱스는 어떤 트레이드오프를 가질까요?
- 자주 하는 실수와 그 해결책은 무엇일까요?
- 이 개념을 실무에 적용하는 방법은 무엇일까요?

VectorDB 선택 기준을 이해하면 AI에게 "동일한 벡터로 두 인덱스 타입의 recall과 latency를 비교하는 코드"를 정확하게 요청할 수 있습니다. 이것이 바이브코딩 시대에 이 개념을 배우는 이유입니다.

## Before / After

**Before — AI에게 컨텍스트 없이 질문:**

```
Q: "가장 좋은 VectorDB 추천해줘"
→ 기능 목록 비교표만 생성
→ 실제 데이터에서의 recall과 latency 측정 없음
→ 운영 복잡도와 비용 비교 없음
```

**After — 개념을 이해하고 구체적으로 질문:**

```
Q: "동일한 200개 문서 벡터와 20개 쿼리로
    FAISS Flat과 IVF100 인덱스를 비교해줘.
    Recall@5, 검색 latency, 메모리 사용량을 측정하고
    결과 표로 출력해줘"
→ 실측 기반 트레이드오프 확인
→ 운영 조건에 맞는 선택 근거 확보
```

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| 브랜드 리뷰만 보고 선택 | 실제 데이터셋에서 성능이 다를 수 있음 | 실제 corpus로 직접 측정 |
| Flat 인덱스가 항상 최선이라고 생각 | 코퍼스가 커지면 latency가 선형 증가 | 코퍼스 크기에 따른 ANN 인덱스 고려 |
| recall과 latency를 따로 봄 | 둘의 트레이드오프가 핵심 | 항상 쌍으로 측정 |
| 필터링 요구사항 미고려 | 메타데이터 필터가 필요하면 지원 여부 확인 필수 | 운영 요구사항을 먼저 정의 |
| 인덱스 재구축 비용 무시 | 대규모 업데이트 시 시간/비용 폭증 | 증분 업데이트 지원 여부 확인 |

## AI 협업 팁

VectorDB 비교 관련 효과적인 AI 프롬프트 패턴:

1. **인덱스 비교 요청**: "FAISS Flat과 IVF 인덱스로 동일한 쿼리를 검색해서 Recall@5와 latency를 비교하는 코드 작성해줘"
2. **코퍼스 크기 실험 요청**: "코퍼스가 1000, 10000, 100000일 때 각 인덱스의 검색 시간을 측정하는 스케일링 실험 코드 작성해줘"
3. **운영 체크리스트 요청**: "내 RAG 시스템에서 VectorDB를 선택할 때 확인해야 할 요구사항 목록을 만들어줘"

예시 프롬프트:
> "동일한 임베딩 벡터로 FAISS IndexFlatL2와 IndexIVFFlat(nlist=100)을 비교해줘. Recall@5, p50/p95 latency, 메모리 사용량을 측정하고 결과를 표로 출력해줘."

## 운영 체크리스트

- [ ] 비교할 두 인덱스에 동일한 벡터를 사용했는가?
- [ ] Recall@k와 latency를 함께 측정했는가?
- [ ] 메타데이터 필터링 요구사항을 사전에 정의했는가?
- [ ] 코퍼스 규모 변화에 따른 latency 스케일링을 확인했는가?
- [ ] 인덱스 재구축 빈도와 비용을 고려했는가?

## 처음 질문으로 돌아가기

VectorDB 선택 기준을 배운 지금, AI에게 이 주제로 더 정확한 질문을 할 수 있게 되었습니다. 실측 기반 비교를 요청하는 사람과 그렇지 않은 사람이 AI에게 받는 선택 근거의 신뢰도는 크게 다릅니다.

## 정리

VectorDB 선택 기준은 바이브코딩을 위한 RAG 벤치마크에서 실측 기반 의사결정의 핵심입니다. 브랜드 비교가 아닌 동일 조건에서의 recall-latency 트레이드오프를 이해했습니다. 다음 글에서는 검색과 생성을 하나의 흐름으로 묶는 종단 간 평가를 다룹니다.
