# 바이브코딩을 위한 RAG 벤치마크 (3/6): 임베딩 모델 비교

이 글은 바이브코딩을 위한 RAG 벤치마크 시리즈의 3번째 글입니다.

임베딩 모델은 RAG 품질의 출발점입니다. 그런데 많은 팀이 MTEB 리더보드를 보고 빠르게 결정을 내립니다. 이 접근에는 두 가지 함정이 있습니다. 첫째, 공개 벤치마크는 일반 도메인 평균이라 사내 특정 도메인에서는 순위가 뒤집힐 수 있습니다. 둘째, 품질이 조금 좋아지는 대신 임베딩 지연 시간이 크게 늘어나면 사용자 경험이 악화될 수 있습니다.

바이브코딩에서 이 개념이 중요한 이유는 단순합니다. AI에게 임베딩 비교 코드를 요청할 때 "코퍼스, 질문, top-k를 고정하고 모델만 교체"라는 조건을 명시하지 않으면, 공정한 비교가 아닌 코드가 생성되기 때문입니다.

> 임베딩 모델 비교는 어느 모델이 더 똑똑한가를 고르는 작업이 아닙니다. 같은 검색 파이프라인 안에서 관련 문서를 더 앞순위에 배치하는 모델이 무엇인가를 확인하는 작업입니다.

---

## 이 글에서 다룰 문제

- 임베딩 모델을 리더보드 점수만 보고 고르면 왜 위험할까요?
- 공정한 비교를 위해 어떤 조건을 반드시 고정해야 할까요?
- 품질이 좋아져도 latency나 비용이 커지면 어떻게 판단해야 할까요?
- 자주 하는 실수와 그 해결책은 무엇일까요?
- 이 개념을 실무에 적용하는 방법은 무엇일까요?

임베딩 비교 방법을 이해하면 AI에게 "같은 corpus와 query로 두 모델을 공정하게 비교하는 코드"를 정확하게 요청할 수 있습니다. 이것이 바이브코딩 시대에 이 개념을 배우는 이유입니다.

## Before / After

**Before — AI에게 컨텍스트 없이 질문:**

```
Q: "임베딩 모델 A와 B를 비교하는 코드 작성해줘"
→ 서로 다른 코퍼스로 비교하는 불공정한 설계
→ latency 측정 없어 속도 비용 무시
→ 도메인 특화 여부 확인 없음
```

**After — 개념을 이해하고 구체적으로 질문:**

```
Q: "동일한 corpus, query, top-k=5로
    model_A와 model_B의 Precision@5, MRR, 임베딩 latency를
    비교하는 코드를 작성해줘.
    corpus는 한 번만 임베딩하고 결과를 캐시해줘"
→ 공정한 단일 변수 비교
→ 품질과 속도 트레이드오프 가시화
```

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| 코퍼스가 달라도 비교 | 모델 차이인지 데이터 차이인지 알 수 없음 | 동일한 corpus로 두 모델 모두 재임베딩 |
| MTEB 점수만 보고 선택 | 도메인 미스매치로 실제 성능 역전 가능 | 실제 도메인 데이터로 직접 측정 |
| latency 측정 없음 | 품질 개선이 속도 손해를 동반해도 모름 | 문서당, 배치당 임베딩 시간 기록 |
| 단일 모델 결과만 보고 결정 | 비교 없이 "좋다"는 판단 | 최소 두 모델을 같은 조건으로 비교 |
| 재임베딩 비용 미고려 | 코퍼스 변경 시마다 발생하는 비용 무시 | 임베딩 캐시 전략 함께 고려 |

## AI 협업 팁

임베딩 비교 관련 효과적인 AI 프롬프트 패턴:

1. **공정 비교 요청**: "같은 corpus와 query로 두 임베딩 모델을 비교하고 Precision@5, MRR, latency를 출력하는 코드 작성해줘"
2. **캐시 전략 요청**: "corpus 임베딩 결과를 .npy로 저장하고 재사용하는 캐시 레이어를 추가해줘"
3. **트레이드오프 시각화 요청**: "품질 지표와 latency를 scatter plot으로 비교하는 코드 작성해줘"

예시 프롬프트:
> "동일한 20개 쿼리와 200개 문서 corpus로 sentence-transformers의 두 모델을 비교해줘. Precision@5, MRR, 쿼리당 latency를 측정하고 결과 표로 출력해줘. corpus 임베딩은 캐시 사용."

## 운영 체크리스트

- [ ] 비교할 두 모델이 동일한 corpus와 query로 평가됐는가?
- [ ] MTEB 점수가 아닌 실제 도메인 데이터로 직접 측정했는가?
- [ ] 임베딩 latency도 품질 지표와 함께 기록했는가?
- [ ] corpus 재임베딩 비용을 고려한 캐시 전략이 있는가?
- [ ] 다음 글에서 동일한 방법론으로 VectorDB를 비교할 수 있는가?

## 처음 질문으로 돌아가기

임베딩 모델 비교를 배운 지금, AI에게 이 주제로 더 정확한 질문을 할 수 있게 되었습니다. 비교 조건을 명시한 사람과 그렇지 않은 사람이 AI에게 받는 비교 코드의 공정성은 크게 다릅니다.

## 정리

임베딩 모델 비교는 바이브코딩을 위한 RAG 벤치마크에서 검색 품질의 출발점입니다. 동일 조건 고정, latency 측정, 도메인 특화 검증의 중요성을 이해했습니다. 다음 글에서는 동일한 방법론으로 VectorDB 선택 기준을 다룹니다.
