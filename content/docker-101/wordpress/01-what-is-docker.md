# 바이브코딩을 위한 Docker 기초 (1/10): Docker란 무엇인가?

이 글은 바이브코딩을 위한 Docker 기초 시리즈의 1번째 글입니다.

AI에게 "Docker 설정 만들어줘"라고 부탁하면 순식간에 그럴듯한 명령어들이 쏟아집니다. `docker run`, `docker build`, `docker push`... 그런데 막상 터미널에 붙여 넣었을 때 오류가 나면 어디서부터 봐야 할지 막막해집니다. "이미지가 없다"는 오류인지, "포트가 충돌한다"는 오류인지, 아니면 Docker 자체가 실행 중이지 않은 건지조차 구분이 안 될 때가 있습니다.

바이브코딩의 핵심은 AI가 생성한 코드를 그냥 실행하는 것이 아니라, 결과를 읽고 수정할 수 있는 능력에 있습니다. Docker도 마찬가지입니다. AI가 만든 Dockerfile이나 명령어를 올바르게 사용하려면, Docker가 무엇을 해 주는 도구인지, 이미지와 컨테이너가 어떻게 다른지 정도는 알아야 합니다. 전문가가 될 필요는 없습니다. 하지만 AI 결과물을 판단하고 고칠 수 있는 최소한의 맥락은 필요합니다.

Docker의 본질은 편의성이 아니라 재현성입니다. "내 노트북에서는 됐는데 왜 서버에서는 안 되지?"라는 질문을 없애는 도구입니다. 이미지라는 실행 가능한 패키지를 만들어 두면, 누가 어디서 실행하든 같은 동작이 나옵니다. AI가 만든 환경 설정도 결국 이 원칙 위에 있습니다.

> Docker의 본질은 편의성이 아니라 재현성입니다. '누가·어디서 실행하든 같은 이미지를 기준으로 같은 동작이 나온다'는 한 약속이, 개발자 노트북과 서버 사이의 미묘한 차이로 생기는 디버깅 시간을 줄입니다.

## 이 글에서 다룰 문제
- Docker는 정확히 무엇을 해 주는 도구일까요?
- 컨테이너와 가상머신은 무엇이 다를까요?
- image, container, registry는 어떤 관계로 이해해야 할까요?
- AI가 `docker run` 명령을 만들어 줄 때 어떤 부분을 직접 확인해야 할까요?
- 바이브코딩할 때 Docker에서 가장 자주 겪는 오류는 무엇일까요?

## Docker가 해결하는 문제

환경 차이는 입문자만 힘들게 하는 문제가 아닙니다. 숙련된 팀도 같은 문제로 시간을 잃습니다. 로컬에서는 되는데 CI에서만 실패하고, 어떤 개발자 노트북에서는 되는데 다른 노트북에서는 라이브러리 버전이 달라 오류가 나는 장면은 너무 흔합니다. 이런 문제는 개인 역량보다 시스템 설계의 문제에 가깝습니다.

Docker는 코드만 공유하는 것이 아니라 실행 환경까지 함께 공유하게 만들기 때문에 중요합니다. 팀이 "어떻게 실행해야 하는가"를 위키 문서나 입소문이 아니라 이미지와 명령으로 표준화할 수 있습니다.

핵심 용어를 한 번만 정리해 두겠습니다.

- **Image**: 코드, 라이브러리, 런타임을 포함한 실행 가능한 패키지입니다.
- **Container**: 이미지를 실제로 실행한 인스턴스입니다.
- **Registry**: 이미지를 저장하고 배포하는 저장소입니다. Docker Hub, GHCR 등이 있습니다.
- **Daemon**: 컨테이너를 생성하고 관리하는 백그라운드 프로세스입니다.

## Before / After

**Before**: "제 노트북에서는 돌아갑니다." 새 팀원 환경 구성에 반나절이 걸립니다.

**After**: `docker run myapp` 한 줄로 같은 환경을 바로 실행합니다.

이 변화가 중요한 이유는 설치 시간이 짧아져서가 아닙니다. 팀이 같은 문제를 같은 방식으로 재현할 수 있게 되기 때문입니다. 재현성이 생기면 디버깅이 쉬워지고, 디버깅이 쉬워지면 배포 속도와 운영 안정성도 함께 올라갑니다.

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| AI가 만든 명령을 그대로 실행하다 포트 오류 | `-p 8080:80`에서 앞이 호스트, 뒤가 컨테이너 포트인데 뒤집어 쓰는 경우 | 포트 매핑 방향을 직접 확인 |
| `latest` 태그를 운영에 그대로 사용 | 어느 날 조용히 다른 버전으로 바뀔 수 있음 | 명시적 버전 태그 사용 |
| Docker가 켜져 있는지 확인 안 함 | Docker Desktop이 꺼진 채로 명령 실행하면 `Cannot connect to the Docker daemon` 오류 | `docker info`로 먼저 확인 |
| 컨테이너를 종료 후 정리 안 함 | 멈춘 컨테이너가 쌓여 디스크와 포트를 차지 | `docker rm` 또는 `--rm` 옵션 사용 |
| root 실행을 당연하게 여김 | 보안 사고 시 권한이 과도함 | Dockerfile에 `USER` 지정 |

## AI에게 Docker 관련 요청하는 팁

AI에게 Docker 설정을 요청할 때 맥락을 구체적으로 주면 훨씬 나은 결과가 나옵니다.

- "Python 3.12 기반으로 FastAPI 앱을 실행하는 Dockerfile 만들어줘"처럼 언어와 버전을 명시하세요.
- "non-root 사용자로 실행하게 해줘"처럼 운영 요구사항도 함께 넣으세요.
- AI가 만든 명령에 `-p` 옵션이 있다면 앞 숫자가 내 컴퓨터 포트, 뒷 숫자가 컨테이너 포트라는 것을 기억하세요.
- `docker run` 뒤에 이미지 이름이 없거나 없는 이미지 이름이 들어 있다면 먼저 `docker build`가 필요합니다.

## 운영 체크리스트

- [ ] `docker info`로 Docker가 실행 중임을 확인합니다
- [ ] `docker run hello-world`가 정상 동작합니다
- [ ] image와 container의 차이를 설명할 수 있습니다
- [ ] 포트 매핑 `-p 호스트:컨테이너`의 방향을 이해했습니다
- [ ] 실행한 컨테이너를 정리할 수 있습니다

## 처음 질문으로 돌아가기

AI가 만든 Docker 명령이 실패했을 때 당황하지 않으려면 한 가지만 기억하면 됩니다. Docker는 이미지(정적 패키지)와 컨테이너(실행 인스턴스)를 분리합니다. 이미지가 없으면 빌드가 먼저고, 컨테이너가 안 떠 있으면 포트도 의미가 없습니다. 이 두 가지 구분이 오류 메시지를 읽는 출발점입니다.

## 정리

Docker는 실행 환경을 이미지라는 산출물로 묶어 재현성을 만드는 도구입니다. 바이브코딩 맥락에서 Docker를 사용할 때 가장 중요한 감각은, AI가 만든 명령을 그대로 붙여 넣기 전에 이미지가 있는지, 포트 매핑이 맞는지, Docker가 실행 중인지를 잠깐 확인하는 습관입니다. 다음 글에서는 이미지와 컨테이너의 관계를 더 깊게 봅니다.
