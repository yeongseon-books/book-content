# 바이브코딩을 위한 자료구조 기초 (1/10): 자료구조란 무엇인가?

이 글은 바이브코딩을 위한 자료구조 기초 시리즈의 1번째 글입니다.

AI에게 "사용자 100만 명 중 특정 ID 찾는 코드 짜줘"라고 하면 바로 코드가 나옵니다. 그런데 막상 실행해보니 서버가 느려지고 있습니다. 로그를 보면 쿼리 하나에 수백 밀리초가 걸립니다. AI가 리스트를 루프로 돌리는 코드를 줬기 때문입니다. 해시맵으로 바꾸면 수십 배 빨라지는데, 왜 AI는 그걸 선택하지 않았을까요?

바이브코딩은 빠르게 동작하는 코드를 만들어줍니다. 하지만 "동작하는 코드"와 "빠른 코드"는 다릅니다. 그 차이를 만드는 것이 바로 자료구조 선택입니다. AI에게 더 나은 질문을 하려면, 코드가 왜 느린지 판단하려면, 리뷰에서 병목을 잡으려면 자료구조의 기본 어휘가 필요합니다.

바이브코딩 환경에서 자료구조 지식은 코드를 직접 외워서 짜기 위한 것이 아닙니다. AI가 내놓는 코드의 성능을 판단하고, 더 나은 구조를 요청하고, 운영에서 문제가 생겼을 때 원인을 찾는 데 필요한 판단력입니다.

> 자료구조를 모르는 바이브코더는 AI가 짠 코드가 왜 느린지 절대 알 수 없습니다.

---

## 이 글에서 다룰 문제
- 자료구조와 추상 자료형(ADT)은 어떻게 다를까요?
- 같은 데이터를 다루는데도 왜 구조 선택에 따라 성능이 크게 달라질까요?
- 입력 크기가 커질수록 자료구조 선택이 어떤 식으로 비용 차이를 만들까요?
- AI에게 자료구조와 관련한 요청을 어떻게 해야 더 좋은 코드를 받을 수 있을까요?
- 바이브코딩에서 초보자가 자주 놓치는 자료구조 관련 포인트는 무엇일까요?

## 핵심 개념: ADT vs 자료구조

ADT(추상 자료형)는 "무엇을 할 수 있는가"를 정의합니다. 자료구조는 "어떻게 메모리에 저장하는가"를 결정합니다. 같은 ADT도 자료구조 구현에 따라 성능이 완전히 달라집니다.

```text
ADT: List (삽입, 삭제, 조회가 가능한 순서 있는 컬렉션)
  구현 1: 배열 기반 → 인덱스 조회 O(1), 중간 삽입 O(n)
  구현 2: 연결 리스트 기반 → 인덱스 조회 O(n), 앞 삽입 O(1)
```

AI가 코드를 줄 때 "리스트를 써야 하나, 딕셔너리를 써야 하나"라고만 물으면 AI는 적당한 선택을 합니다. 하지만 "이 기능의 핵심 연산이 키 기반 조회인지, 순서 유지인지, 앞뒤 삽입인지"를 먼저 파악하면 훨씬 구체적인 요청이 가능합니다.

## Before / After

**Before — AI가 준 코드 그대로 사용:**

```python
users = [{"id": i, "name": f"user{i}"} for i in range(10_000_000)]

def find_user(target_id: int):
    for user in users:
        if user["id"] == target_id:
            return user
    return None
# 평균 500만 번 비교
```

**After — 자료구조를 이해하고 AI에게 재요청:**

```python
# "키 기반 조회가 핵심이니 dict로 구현해줘"라고 요청
users = {i: {"id": i, "name": f"user{i}"} for i in range(10_000_000)}

def find_user(target_id: int):
    return users.get(target_id)
# 평균 한 번 비교
```

겉보기에는 둘 다 같은 기능이지만, 데이터가 커질수록 차이는 수백 배가 됩니다.

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| AI 코드를 그냥 실행하고 느리면 AI 탓 | 자료구조 선택 문제를 발견 못 함 | 핫패스의 연산 종류를 파악하고 재요청 |
| "더 빠르게 해줘"라고만 요청 | AI가 알고리즘만 바꾸고 구조는 그대로 둠 | "해시맵으로 바꿔줘", "정렬 유지가 필요해" 등 구체적으로 요청 |
| 작은 데이터로 테스트하고 배포 | 성장률 차이를 데이터가 작을 때 못 봄 | 예상 최대 입력 크기로도 테스트 |
| 리스트와 딕셔너리만 씀 | 힙, deque 등 더 적합한 구조를 놓침 | 연산 패턴에 따라 적합한 구조 물어보기 |
| ADT와 구현을 같은 것으로 봄 | "스택은 배열이다"처럼 단정 | ADT는 인터페이스, 구현은 별개 |

## AI에게 자료구조 관련 질문하는 팁

1. **연산을 먼저 정의하세요.** "이 기능의 핵심 연산은 키로 빠르게 찾는 것입니다. 어떤 자료구조가 맞나요?"
2. **입력 규모를 알려주세요.** "데이터가 최대 100만 건일 때 효율적인 구조로 짜줘."
3. **성능 요구사항을 포함하세요.** "삽입보다 조회가 훨씬 많은 시나리오에서 최적화해줘."
4. **AI 선택에 의문을 가져도 됩니다.** "왜 여기서 리스트를 썼어? 해시맵이 더 빠르지 않아?"
5. **Big-O를 물어보세요.** "이 코드의 조회 시간 복잡도가 뭐야? 더 빠른 방법은?"

## 운영 체크리스트
- [ ] 자료구조와 ADT의 차이를 설명할 수 있습니다
- [ ] AI가 준 코드에서 어떤 자료구조를 선택했는지 파악합니다
- [ ] 핵심 연산(조회/삽입/삭제/순회)이 무엇인지 먼저 정의합니다
- [ ] 시간 복잡도 개념(O(1), O(n), O(log n))을 기본적으로 이해합니다
- [ ] 데이터 규모를 고려해서 AI에게 요청합니다
- [ ] 작은 데이터와 큰 데이터 모두 테스트합니다

## 처음 질문으로 돌아가기

AI가 리스트를 줬을 때 해시맵이 더 적합한 이유를 알 수 있게 됐나요? 핵심은 간단합니다. 리스트 조회는 앞에서부터 훑는 O(n)이고, 해시맵 조회는 키로 바로 뛰어가는 O(1)입니다. 데이터가 100만 건이면 평균 50만 번 vs 1번 비교입니다. 이 판단을 할 수 있으면 AI에게 더 나은 코드를 요청할 수 있고, 운영 장애도 빨리 진단할 수 있습니다.

## 정리

자료구조는 데이터를 메모리에 어떻게 저장하고 어떤 연산을 효율적으로 지원할지 결정합니다. 바이브코딩에서 이 개념이 중요한 이유는 AI가 항상 최적의 자료구조를 선택하지는 않기 때문입니다. 연산 패턴을 파악하고 AI에게 명확하게 요청하는 것, 그리고 AI 코드의 성능을 판단하는 것이 자료구조 기초의 실용적 목표입니다.
