# 바이브코딩을 위한 자료구조 기초 (10/10): 자료구조 선택 기준

이 글은 바이브코딩을 위한 자료구조 기초 시리즈의 10번째 글입니다.

시리즈의 마지막 글입니다. 지금까지 9개의 자료구조를 살펴봤습니다. 이제 진짜 질문이 남습니다. "새로운 기능을 만들 때 AI에게 어떤 자료구조를 요청해야 할까요?"

새로운 프로젝트를 시작했습니다. AI에게 "실시간 알림 시스템 만들어줘, 사용자별로 알림을 쌓고 읽지 않은 것부터 보여줘"라고 했습니다. AI가 코드를 줬는데, 알림을 리스트로 관리하고 매번 정렬합니다. 동작은 합니다. 그런데 사용자가 늘고 알림이 쌓이자 느려지기 시작합니다.

이 시점에서 "더 빠르게 해줘"라고만 하면 AI는 알고리즘을 조금 바꾸는 데 그칩니다. 하지만 핵심 문제는 자료구조 선택입니다. 이 시리즈에서 배운 내용을 바탕으로 올바른 질문을 하는 방법을 정리합니다.

> 자료구조 선택 = 워크로드 분석 + 트레이드오프 이해 + 측정입니다. 세 가지 중 하나라도 빠지면 틀린 선택을 하게 됩니다.

## 이 글에서 다룰 문제
- 새로운 문제를 만났을 때 자료구조 선택은 무엇부터 생각해야 할까요?
- 워크로드를 정의하는 다섯 가지 질문은 무엇일까요?
- 각 자료구조가 어떤 연산 패턴에 맞는지 한눈에 정리할 수 있나요?
- AI에게 자료구조 선택을 요청하는 올바른 방법은 무엇인가요?
- 잘못된 자료구조 선택을 운영 중에 발견했을 때 어떻게 접근할까요?

## 핵심 개념: 워크로드 분석 5가지 질문

자료구조를 선택하기 전에 이 다섯 가지를 먼저 정의하세요.

```text
1. 핵심 연산은 무엇인가?
   → 조회 / 삽입 / 삭제 / 순회 / 최솟값 추출 등

2. 입력은 얼마나 큰가?
   → 100? 1만? 100만? 1억? 규모에 따라 O(n)과 O(log n)의 차이가 결정적

3. 어떤 연산이 가장 자주 일어나는가?
   → 쓰기보다 읽기가 100배 많다면 읽기 최적화

4. 순서/정렬이 중요한가?
   → 정렬 유지 필요 → BST/SortedList, 순서 무관 → 해시 테이블

5. 메모리 제약이 있는가?
   → 포인터 오버헤드(연결 리스트), 버킷 오버헤드(해시 테이블) 고려
```

## 자료구조 선택 지도

| 상황 | 선택 | 이유 |
|------|------|------|
| 키로 빠르게 찾기 | dict / set | O(1) 해시 조회 |
| 순서대로 처리 (FIFO) | deque | O(1) 양 끝 연산 |
| 최근 처리 (LIFO, 재귀) | list (스택) | O(1) 끝 연산 |
| 우선순위 처리 | heapq | O(log n) 삽입/삭제 |
| 정렬 유지 + 동적 삽입 | SortedList | O(log n) 삽입+검색 |
| 범위 쿼리 | SortedList / DB 인덱스 | BST 계열 범위 탐색 |
| 계층 구조 | 트리 노드 | 자연스러운 재귀 표현 |
| 임의 관계 | 그래프 (인접 리스트) | 정점+간선 일반 표현 |
| 인덱스 접근 + 순회 | list | 연속 메모리, O(1) 인덱스 |
| 양 끝 삽입/삭제 | deque | 연결 리스트 기반 O(1) |

## Before / After

**Before — "더 빠르게 해줘"만 요청:**

```python
# AI가 준 코드: 매번 정렬
notifications = []
def add(priority, msg):
    notifications.append((priority, msg))
    notifications.sort()   # O(n log n)

def get_next():
    return notifications.pop(0)   # O(n)
```

**After — 워크로드 분석 후 구체적 요청:**

```python
# "우선순위가 높은 알림을 먼저 꺼내는 게 핵심이야, heapq로 구현해줘"
import heapq

notifications = []
def add(priority, msg):
    heapq.heappush(notifications, (-priority, msg))   # O(log n), 최대 힙

def get_next():
    return heapq.heappop(notifications)               # O(log n)
```

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| "더 빠르게 해줘"만 요청 | AI가 알고리즘만 바꾸고 구조는 그대로 | 핵심 연산과 자료구조를 명시해서 요청 |
| 익숙한 구조(list/dict)만 사용 | deque, heapq, SortedList를 놓침 | 연산 패턴에 따라 적합한 구조 물어보기 |
| 작은 테스트 데이터로만 검증 | 성장률 차이를 놓침 | 예상 최대 입력 규모로 테스트 |
| 이론 복잡도만 보고 결정 | 상수 항, 캐시 효과 무시 | 실제 벤치마크도 확인 |
| 측정 없이 최적화 | 병목이 아닌 곳을 최적화 | 프로파일러로 실제 병목 먼저 확인 |

## AI에게 자료구조 관련 질문하는 팁

1. **핵심 연산을 먼저 말하세요.** "이 기능의 핵심은 [연산]이야. 어떤 자료구조가 맞아?"
2. **규모를 알려주세요.** "데이터가 최대 [N]건이야. 이 규모에서 효율적인 구조로 구현해줘."
3. **AI 선택의 이유를 물어보세요.** "왜 여기서 [구조]를 선택했어? 다른 선택지는?"
4. **성능 특성을 확인하세요.** "이 코드의 핵심 연산 시간 복잡도가 뭐야? 더 좋은 방법 있어?"
5. **병목이 발생하면 AI에게 분석 요청하세요.** "이 부분이 느린 것 같아. 자료구조 문제일까? 어떻게 바꾸면 좋아?"

## 운영 체크리스트

- [ ] 예상 데이터 규모를 AI 요청에 포함합니다
- [ ] AI가 선택한 자료구조가 핵심 연산에 적합한지 확인합니다
- [ ] 루프 안의 sort(), insert(0), `x in list` 패턴을 발견하고 개선을 요청합니다
- [ ] 실제 데이터 규모로 테스트하는 습관을 가집니다
- [ ] 이론 복잡도와 실측 벤치마크를 함께 봅니다

## 처음 질문으로 돌아가기

알림 시스템에서 올바른 질문은 "핵심 연산이 무엇인가?"였습니다. 답은 "우선순위가 높은 알림을 빠르게 꺼내는 것"입니다. 이 연산 패턴에는 heapq가 맞습니다. "더 빠르게"가 아니라 "우선순위 처리의 핵심 연산은 최솟값/최댓값 꺼내기야, heapq로 구현해줘"라고 요청하면 처음부터 올바른 코드를 받을 수 있습니다.

## 정리

자료구조 선택은 데이터의 모양이 아니라 연산의 빈도와 패턴에서 출발합니다. 바이브코딩에서 이 원칙은 더욱 중요합니다. AI는 동작하는 코드를 주지만 최적의 자료구조를 항상 선택하지는 않습니다. 워크로드를 분석하고 핵심 연산을 명시해서 요청하는 것, AI 코드에서 성능 함정을 발견하는 것, 실제 규모로 테스트하는 것이 이 시리즈에서 전달하고 싶었던 핵심입니다.

이 시리즈를 읽고 나서 AI 코드를 볼 때 "이 자료구조가 이 연산에 맞는가?"라는 질문이 자연스럽게 떠오른다면 목표를 달성한 것입니다.
