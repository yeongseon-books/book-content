# 바이브코딩을 위한 자료구조 기초 (2/10): 배열과 동적 배열

이 글은 바이브코딩을 위한 자료구조 기초 시리즈의 2번째 글입니다.

AI에게 "로그 데이터를 수집해서 분석하는 코드 짜줘"라고 했더니 이런 코드가 나왔습니다.

```python
result = []
for log in stream:
    result = result + [parse(log)]
```

처음에는 잘 돌아가는 것 같았습니다. 그런데 로그가 10만 건을 넘어가자 처리 속도가 급격히 느려졌습니다. 메모리 사용량도 이상하게 높습니다. 무슨 문제일까요?

바이브코딩에서 리스트를 다룰 때 가장 흔한 함정은 `+` 연산자로 리스트를 합치는 것입니다. `result = result + [new_item]`은 매 반복마다 전체 리스트를 새로 복사하기 때문에, 10만 번 반복하면 O(n²) 복사가 발생합니다. AI가 이 코드를 주는 이유는 동작 자체는 맞기 때문입니다. 하지만 성능이 왜 나쁜지, 어떻게 고쳐야 하는지를 이해하려면 동적 배열의 내부 원리가 필요합니다.

> 배열을 깊이 이해하지 못하면 AI가 준 리스트 코드의 성능을 판단할 수 없습니다.

---

## 이 글에서 다룰 문제
- 배열이 왜 인덱스 접근에서 O(1)인지 메모리 구조로 이해할 수 있나요?
- 동적 배열(파이썬 list)은 크기가 부족할 때 어떻게 늘어날까요?
- `append`와 `+`의 성능 차이는 왜 그렇게 클까요?
- 앞쪽 삽입이 왜 비싼지, 언제 deque를 써야 할지 알 수 있나요?
- AI에게 배열 관련 코드를 어떻게 요청하면 더 효율적인 코드를 받을 수 있을까요?

## 핵심 개념: 연속 메모리와 doubling 전략

배열은 같은 크기의 원소를 메모리에 연속으로 배치합니다. `arr[2]`를 찾으려면 `시작 주소 + 2 × 원소 크기`만 계산하면 되므로 어디를 찾든 O(1)입니다.

동적 배열은 공간이 부족해지면 보통 두 배 큰 블록을 새로 할당하고 기존 값을 복사합니다. 이 doubling 전략 덕분에 재할당은 가끔만 일어나고, `append`의 평균 비용은 O(1)로 유지됩니다.

```text
size=3, capacity=4: [10][20][30][ ]
append(40)        → [10][20][30][40]    capacity 가득 참
append(50)        → 새 블록(capacity=8) → [10][20][30][40][50][ ][ ][ ]
```

## Before / After

**Before — AI가 + 연산자로 리스트를 합침:**

```python
result = []
for i in range(1_000_000):
    result = result + [i]   # 매번 전체 복사: O(n²) 전체
```

**After — append로 올바르게 작성:**

```python
result = []
for i in range(1_000_000):
    result.append(i)        # 분할 상환 O(1): O(n) 전체
```

겉보기에 비슷하지만 100만 원소에서 수백 배 이상 차이가 납니다.

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| `result = result + [item]`로 반복 확장 | 매 반복마다 전체 복사 → O(n²) | `result.append(item)` 사용 |
| `list.insert(0, item)`으로 앞에 계속 삽입 | 매번 O(n) 이동 | `collections.deque`의 `appendleft` 사용 |
| capacity와 size를 혼동 | 메모리 예측 실패 | size=사용량, capacity=확보량으로 구분 |
| 큰 슬라이스를 반복 생성 | 메모리와 시간 낭비 | 가능하면 슬라이스 대신 인덱스 사용 |
| 정렬된 리스트를 선형 탐색 | O(log n) 기회를 버림 | `bisect` 모듈 검토 |

## AI에게 자료구조 관련 질문하는 팁

1. **연산 방향을 알려주세요.** "끝에 추가하는 작업이 대부분이야" vs "앞뒤 양쪽에서 추가/제거해"
2. **최종 크기를 안다면 미리 말해주세요.** "결과가 정확히 N개야, 미리 공간 확보해줘"
3. **슬라이스 의도를 설명하세요.** "이 부분 원본은 안 바꾸고 복사본만 써" vs "인덱스로 직접 접근해도 돼"
4. **느린 코드의 패턴을 물어보세요.** "이 루프에서 리스트 연산 중 O(n²)이 될 수 있는 부분 있어?"
5. **numpy가 필요한지 물어보세요.** "수치 계산이 많은데 일반 list보다 더 빠른 방법 있어?"

## 운영 체크리스트
- [ ] 배열 인덱싱이 왜 O(1)인지 메모리 배치로 설명할 수 있습니다
- [ ] `append`와 `+` 연산자의 성능 차이를 이해했습니다
- [ ] doubling 전략이 분할 상환 비용에 어떤 영향을 주는지 알고 있습니다
- [ ] 앞쪽 삽입이 왜 비싼지, deque가 언제 유리한지 알고 있습니다
- [ ] AI 코드에서 O(n²) 리스트 패턴을 발견할 수 있습니다
- [ ] 캐시 친화성이 반복 성능에 미치는 영향을 이해했습니다

## 처음 질문으로 돌아가기

`result = result + [parse(log)]`가 왜 느린지 이제 답할 수 있습니다. `+` 연산자는 매 반복마다 기존 리스트 전체를 새 메모리에 복사하기 때문에 O(n) 복사가 n번 → 전체 O(n²)가 됩니다. `append`로 바꾸면 동적 배열의 doubling 전략 덕분에 분할 상환 O(1)이 되어 전체 O(n)으로 줄어듭니다. AI에게 "리스트 누적은 + 대신 append로" 라고 명시하면 처음부터 올바른 코드를 받을 수 있습니다.

## 정리

배열은 연속 메모리에 원소를 저장하므로 인덱스 접근이 O(1)이고 캐시 친화적입니다. 동적 배열은 capacity가 부족할 때 doubling으로 확장하여 append의 분할 상환 비용을 O(1)로 유지합니다. 바이브코딩에서 중요한 것은 이 원리를 바탕으로 AI가 준 리스트 코드에서 성능 함정을 발견하고, 더 구체적인 요청을 하는 능력입니다.
