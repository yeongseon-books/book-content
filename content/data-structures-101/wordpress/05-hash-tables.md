# 바이브코딩을 위한 자료구조 기초 (5/10): 해시 테이블

이 글은 바이브코딩을 위한 자료구조 기초 시리즈의 5번째 글입니다.

사용자 세션 관리 기능을 만들고 있습니다. AI에게 "로그인한 사용자 목록을 관리하고 빠르게 확인하는 코드 짜줘"라고 했습니다. AI가 이렇게 줬습니다.

```python
logged_in_users = []

def login(user_id):
    logged_in_users.append(user_id)

def is_logged_in(user_id):
    return user_id in logged_in_users   # O(n) 선형 탐색
```

동시 접속자가 1000명일 때는 괜찮았습니다. 그런데 10만 명이 넘어가자 `is_logged_in` 호출마다 수십 밀리초가 걸리기 시작했습니다. API 응답 시간이 눈에 띄게 느려졌습니다.

AI에게 "dict나 set으로 바꿔줘"라고 하면 즉시 고칠 수 있습니다. 그런데 왜 그게 더 빠른지, 언제 이런 패턴이 문제가 되는지를 알아야 AI 코드를 능숙하게 리뷰할 수 있습니다. 해시 테이블이 그 답입니다.

> dict가 없으면 알고리즘 문제의 절반이 갑자기 훨씬 어려워집니다. 바이브코딩에서도 마찬가지입니다.

---

## 이 글에서 다룰 문제
- 해시 테이블이 왜 평균 O(1)으로 조회할 수 있는지 원리를 이해할 수 있나요?
- 충돌은 무엇이고 어떻게 처리되나요?
- `in` 연산자가 list에서는 O(n), set/dict에서는 O(1)인 이유는 무엇인가요?
- AI 코드에서 list를 dict/set으로 바꿔야 할 패턴을 어떻게 발견할까요?
- 해시 테이블의 한계(최악 O(n), 정렬 불가)는 언제 문제가 될까요?

## 핵심 개념: key → hash → index

해시 테이블은 키를 해시 함수로 정수로 바꾸고, 그 정수를 배열의 인덱스로 사용합니다. 그래서 키를 알면 메모리 위치를 바로 계산할 수 있어 O(1) 조회가 가능합니다.

```text
"alice" → hash() → 38291... → % 8 → 3번 버킷에 저장
"bob"   → hash() → 92847... → % 8 → 7번 버킷에 저장

조회: "alice"인지 확인 → 3번 버킷만 확인 → O(1)
```

두 키가 같은 버킷으로 가면 충돌이 발생합니다. 파이썬의 dict는 이를 내부적으로 처리합니다. 해시 함수가 나쁘거나 키 분포가 편향되면 최악 O(n)이 될 수 있습니다.

## Before / After

**Before — AI가 list에서 in으로 멤버십 확인:**

```python
logged_in = []
logged_in.append("alice")

if "alice" in logged_in:   # O(n): 처음부터 끝까지 탐색
    pass
```

**After — set으로 멤버십 확인:**

```python
logged_in = set()
logged_in.add("alice")

if "alice" in logged_in:   # O(1): 해시로 즉시 확인
    pass
```

10만 명 동시 접속자라면 한 번 확인에 O(1) vs O(n)의 차이가 됩니다.

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| 멤버십 확인에 list 사용 | `x in list`는 O(n) | set이나 dict 사용 |
| 가변 객체를 dict 키로 사용 | TypeError 또는 키 유실 | tuple, frozenset 같은 불변 타입 사용 |
| dict와 OrderedDict를 혼동 | Python 3.7+ dict는 삽입 순서 보장 | 목적에 따라 명시적으로 선택 |
| `__hash__`만 정의하고 `__eq__` 빠뜨림 | 동등성 판단이 깨짐 | 두 메서드를 항상 함께 정의 |
| dict가 항상 O(1)이라고 가정 | 해시 품질에 따라 최악 O(n) | 신뢰할 수 없는 키 입력은 주의 |

## AI에게 자료구조 관련 질문하는 팁

1. **`in` 연산 빈도를 알려주세요.** "이 목록에서 특정 값이 있는지 자주 확인해야 해" → set 요청
2. **키-값 매핑이면 dict를 명시하세요.** "ID로 사용자 정보를 빠르게 찾아야 해" → dict 요청
3. **중복 제거가 필요하면.** "중복 없이 저장하고 존재 여부만 빠르게 확인해" → set
4. **키가 가변 객체인 경우 확인하세요.** "이 dict 키가 나중에 변경될 수 있어?" → tuple이나 frozenset으로 변환
5. **충돌 가능성 있는 입력을 알려주세요.** "외부에서 받은 값이 키야, 해시 충돌 공격 방어 필요해?"

- [ ] 부하율과 리해싱이 성능에 미치는 영향을 이해했습니다
- [ ] 해시 테이블의 한계(정렬 불가, 최악 O(n))를 알고 있습니다

## 처음 질문으로 돌아가기

세션 관리에서 `user_id in logged_in_users`가 왜 느려졌는지 이제 명확합니다. list에서 `in`은 앞에서부터 하나씩 비교하는 O(n) 탐색입니다. 10만 명이면 최악 10만 번 비교입니다. `set`으로 바꾸면 `in`이 해시 기반 O(1)이 됩니다. AI에게 처음부터 "로그인 여부 확인이 핵심이야, set이나 dict로 구현해줘"라고 하면 이 문제를 처음부터 피할 수 있습니다.

## 정리

해시 테이블은 키를 해시 함수로 인덱스로 변환해 평균 O(1) 조회를 제공합니다. 파이썬의 dict와 set이 이 구조입니다. 바이브코딩에서 가장 중요한 활용은 AI가 list로 멤버십을 확인하는 코드를 줬을 때 set/dict로 교체를 요청하는 것입니다. 연산 패턴이 "키로 빠르게 찾는 것"이라면 해시 테이블이 기본 선택입니다.
