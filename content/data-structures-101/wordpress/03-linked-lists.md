# 바이브코딩을 위한 자료구조 기초 (3/10): 연결 리스트

이 글은 바이브코딩을 위한 자료구조 기초 시리즈의 3번째 글입니다.

실시간 채팅 기능을 만들고 있습니다. AI에게 "메시지 큐를 만들어줘, 새 메시지는 앞에 추가하고 오래된 건 뒤에서 제거해"라고 했더니 이런 코드가 나왔습니다.

```python
messages = []
def add_message(msg):
    messages.insert(0, msg)   # 앞에 삽입

def remove_oldest():
    return messages.pop()     # 뒤에서 제거
```

100개 메시지에서는 잘 돌아갑니다. 그런데 동시 접속자가 늘어 메시지가 수만 건이 되자 `insert(0, ...)` 호출마다 서버가 잠시 멈추는 현상이 생겼습니다. 왜 이런 일이 일어났을까요?

배열에서 앞쪽 삽입은 기존 원소를 전부 한 칸씩 뒤로 밀어야 합니다. 10만 개 원소가 있으면 10만 번 이동이 일어납니다. 이것이 연결 리스트가 필요한 이유입니다. 연결 리스트는 노드끼리 포인터로 연결되어 있어, 양 끝 삽입과 삭제가 O(1)입니다.

> 배열이 위치로 데이터를 묶는다면, 연결 리스트는 관계로 데이터를 묶습니다. 양 끝 삽입/삭제가 핵심이라면 연결 리스트 계열이 맞습니다.

---

## 이 글에서 다룰 문제
- 단일 연결 리스트와 이중 연결 리스트는 구조적으로 무엇이 다를까요?
- 연결 리스트는 왜 양 끝 삽입에 강하고 인덱스 접근에는 약할까요?
- 파이썬의 `deque`는 어떤 상황에서 list보다 훨씬 적합할까요?
- AI가 list를 쓴 코드에서 연결 리스트가 더 적합한 경우를 어떻게 알아챌까요?
- 연결 리스트의 캐시 친화성이 낮다는 것이 실무에서 어떤 의미일까요?

## 핵심 개념: 노드와 포인터

연결 리스트는 각 원소(노드)가 값과 다음 노드의 참조를 함께 가집니다. 메모리에 연속으로 저장되지 않아도 되기 때문에, 노드를 추가하거나 제거할 때 인접 노드의 포인터만 바꾸면 됩니다.

```text
[10 | →] → [20 | →] → [30 | None]
  ↑
 head

앞에 40 삽입:
[40 | →] → [10 | →] → [20 | →] → [30 | None]
  ↑ (head 포인터만 변경, 기존 원소 이동 없음)
```

이중 연결 리스트는 `prev`와 `next` 포인터를 모두 가져 양방향 순회가 가능합니다. 파이썬의 `collections.deque`가 이 계열입니다.

## Before / After

**Before — list의 insert(0)으로 앞에 삽입:**

```python
messages = []
for i in range(100_000):
    messages.insert(0, i)   # 매번 O(n) 이동 → 전체 O(n²)
```

**After — deque의 appendleft로 앞에 삽입:**

```python
from collections import deque

messages = deque()
for i in range(100_000):
    messages.appendleft(i)  # O(1) → 전체 O(n)
```

같은 기능이지만 deque 버전이 수십 배 이상 빠릅니다.

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| 양 끝 삽입/삭제에 list 사용 | 앞쪽 연산이 매번 O(n) | `collections.deque` 사용 |
| deque에 인덱스로 자주 접근 | deque 중간 접근은 O(n) | 중간 접근이 많으면 list 유지 |
| AI 코드의 insert(0) 패턴을 그냥 통과 | 데이터가 커지면 병목 | 앞쪽 삽입이 많은지 확인하고 deque 요청 |
| 배열처럼 인덱스로 계속 접근 | 연결 리스트 계열은 O(n) 순회 | 임의 접근이 많으면 list가 더 적합 |
| head 갱신을 빠뜨린 구현 | 리스트 전체를 잃어버림 | AI 구현 코드의 포인터 갱신 꼼꼼히 확인 |

## AI에게 자료구조 관련 질문하는 팁

1. **접근 패턴을 명확히 하세요.** "앞뒤에서 추가/제거만 해, 중간 인덱스 접근은 없어" → deque 요청
2. **양방향 여부를 알려주세요.** "이전/다음 항목 모두 이동해야 해" → 이중 연결 리스트 계열
3. **insert(0) 패턴을 발견하면 질문하세요.** "이 insert(0)이 많이 호출되는데 더 빠른 방법 있어?"
4. **LRU 캐시 같은 패턴을 요청할 때.** "최근 사용 순서를 유지하면서 빠르게 제거/추가해야 해"
5. **순회 vs 접근을 구분하세요.** "처음부터 끝까지 순서대로 처리해" vs "특정 인덱스 항목만 빠르게 찾아"

## 운영 체크리스트
- [ ] 단일/이중 연결 리스트의 구조 차이를 설명할 수 있습니다
- [ ] list.insert(0)이 O(n)인 이유를 이해했습니다
- [ ] deque가 적합한 상황과 list가 더 나은 상황을 구분할 수 있습니다
- [ ] AI 코드에서 앞쪽 삽입 패턴을 발견하고 개선을 요청할 수 있습니다
- [ ] sentinel 노드가 코드 복잡도를 줄이는 이유를 이해했습니다
- [ ] 연결 리스트의 캐시 친화성이 낮다는 트레이드오프를 알고 있습니다

## 처음 질문으로 돌아가기

채팅 메시지 큐에서 `insert(0, msg)`가 왜 느려졌는지 이제 답할 수 있습니다. 배열 앞쪽 삽입은 기존 원소를 전부 이동시켜야 하므로 O(n)이고, 메시지가 쌓일수록 비용이 선형으로 늘어납니다. `collections.deque`의 `appendleft`로 바꾸면 O(1)로 해결됩니다. AI에게 처음부터 "양 끝 삽입/삭제가 많아, deque로 구현해줘"라고 하면 이 문제를 피할 수 있습니다.

## 정리

연결 리스트는 포인터로 이어진 노드 구조로, 양 끝 삽입/삭제가 O(1)입니다. 대신 임의 접근은 O(n)이고 캐시 친화성도 배열보다 낮습니다. 바이브코딩에서 핵심은 AI가 list를 쓴 코드에서 앞쪽 삽입 패턴을 발견하면 deque 사용을 요청하는 것입니다. 연산 패턴이 양 끝 중심이라면 연결 리스트 계열이 훨씬 적합합니다.
