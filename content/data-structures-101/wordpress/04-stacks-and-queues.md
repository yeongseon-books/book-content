# 바이브코딩을 위한 자료구조 기초 (4/10): 스택과 큐

이 글은 바이브코딩을 위한 자료구조 기초 시리즈의 4번째 글입니다.

작업 처리 시스템을 만들면서 AI에게 "요청이 들어오는 순서대로 처리하는 작업 큐 만들어줘"라고 했습니다. AI가 이런 코드를 줬습니다.

```python
queue = []
queue.append("task-1")
queue.append("task-2")

def process_next():
    return queue.pop(0)   # 첫 번째 항목 꺼내기
```

작업이 10개일 때는 전혀 문제가 없었습니다. 그런데 큐에 작업이 수천 개 쌓이자 `pop(0)` 호출마다 처리 지연이 눈에 띄게 늘어났습니다. `pop(0)`은 O(n) 연산이기 때문입니다. 매번 남은 원소를 전부 한 칸씩 앞으로 당겨야 합니다.

파이썬에서 list는 스택에는 완벽하지만 큐에는 잘못된 선택입니다. 이 차이를 이해하면 AI에게 처음부터 올바른 코드를 요청할 수 있습니다.

> 스택을 모르면 재귀 디버깅이 어렵고, 큐를 모르면 비동기 시스템 설계가 어렵습니다.

## 이 글에서 다룰 문제
- 스택의 LIFO와 큐의 FIFO는 실제로 어떤 상황에서 각각 필요할까요?
- 파이썬에서 큐를 list로 구현하면 안 되는 이유는 무엇인가요?
- BFS와 DFS의 차이가 자료구조 선택 하나라는 것을 이해할 수 있나요?
- AI가 준 큐 코드에서 성능 문제를 어떻게 발견할까요?
- 스택과 큐가 실무 시스템에서 어떻게 사용되는지 알 수 있나요?

## 핵심 개념: LIFO와 FIFO

스택은 마지막에 넣은 것을 먼저 꺼냅니다(LIFO). 큐는 먼저 넣은 것을 먼저 꺼냅니다(FIFO). 이 단순한 규칙이 완전히 다른 시스템을 만들어냅니다.

```text
스택 (LIFO)        큐 (FIFO)
push → [C]         enqueue →  [A B C D]  → dequeue
       [B]                    ↑               ↑
       [A]                   front           back
        ↑
       pop
```

파이썬에서:
- 스택 → `list` (`append` / `pop`)
- 큐 → `collections.deque` (`append` / `popleft`)

list의 `pop(0)`은 O(n)이지만 deque의 `popleft()`는 O(1)입니다.

## Before / After

**Before — list로 큐 구현 (느림):**

```python
queue = []
queue.append("A")
queue.append("B")
front = queue.pop(0)   # O(n): 모든 원소가 앞으로 이동
```

**After — deque로 큐 구현 (빠름):**

```python
from collections import deque

queue = deque()
queue.append("A")
queue.append("B")
front = queue.popleft()   # O(1)
```

큐가 길어질수록 차이는 기하급수적으로 벌어집니다.

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| `list.pop(0)`으로 큐 구현 | O(n) 연산이 반복됨 | `collections.deque`의 `popleft` 사용 |
| 빈 컨테이너에서 pop | IndexError 발생 | 길이 확인이나 예외 처리 추가 |
| 재귀 깊이 한계 무시 | RecursionError 위험 | 명시적 스택으로 변환 |
| BFS에서 visited를 늦게 표시 | 중복 방문 또는 무한 루프 | enqueue 시점에 즉시 표시 |
| 우선순위 큐를 일반 큐처럼 사용 | 처리 순서가 틀어짐 | 힙(heapq) 사용 |

## AI에게 자료구조 관련 질문하는 팁

1. **순서 규칙을 명확히 하세요.** "먼저 들어온 것 먼저 처리해" → deque 큐 / "나중에 들어온 것 먼저 처리해" → list 스택
2. **pop(0) 패턴을 발견하면 지적하세요.** "여기 pop(0)이 많이 호출될 것 같은데 deque로 바꿔줘"
3. **BFS/DFS를 요청할 때.** "너비 우선으로 탐색해줘" → 큐 기반 / "깊이 우선으로 탐색해줘" → 스택 기반
4. **우선순위가 있으면 말해주세요.** "중요도가 높은 작업을 먼저 처리해야 해" → heapq (다음 편에서 다룸)
5. **재귀 깊이 걱정되면 말해주세요.** "입력이 매우 깊어질 수 있어, 재귀 대신 반복으로 바꿔줘"

## 운영 체크리스트
- [ ] LIFO와 FIFO의 의미와 사용 상황을 설명할 수 있습니다
- [ ] 파이썬에서 큐를 list로 구현하면 안 되는 이유를 알고 있습니다
- [ ] AI 코드에서 `pop(0)` 패턴을 발견하고 개선을 요청할 수 있습니다
- [ ] BFS는 큐, DFS는 스택이라는 연결을 이해했습니다
- [ ] deque가 스택과 큐 양쪽을 지원한다는 것을 알고 있습니다
- [ ] 메시지 큐 시스템이 FIFO 원리 위에 있다는 것을 이해했습니다

## 처음 질문으로 돌아가기

작업 큐에서 `pop(0)`이 왜 느려졌는지 이제 명확합니다. list에서 첫 번째 원소를 꺼내면 나머지 원소를 전부 앞으로 이동시켜야 합니다. 큐에 1000개 작업이 있으면 `pop(0)` 한 번에 999번 이동이 일어납니다. `collections.deque`로 바꾸면 `popleft()`가 O(1)로 즉시 처리됩니다. AI에게 "작업 큐는 deque로, popleft로 꺼내줘"라고 처음부터 명시하면 이 문제가 사라집니다.

## 정리

스택은 LIFO로 함수 호출/파싱/DFS를 지원하고, 큐는 FIFO로 BFS/스케줄링/메시징을 지원합니다. 파이썬에서는 스택은 list, 큐는 `collections.deque`가 올바른 선택입니다. 바이브코딩에서 `pop(0)` 패턴을 발견하면 deque 사용을 요청하는 습관이 중요합니다. 차이는 "어느 끝에서 꺼내는가" 하나지만, 그 하나가 시스템 성능을 완전히 바꿉니다.
