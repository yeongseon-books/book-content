# 바이브코딩을 위한 API 설계 기초 (1/10): API란 무엇인가?

이 글은 바이브코딩을 위한 API 설계 기초 시리즈의 1번째 글입니다.

"AI한테 REST API 만들어달라고 하면 되지 않나요?"라는 말을 자주 듣습니다. 맞습니다. ChatGPT나 Claude에게 "사용자 목록을 반환하는 API 엔드포인트 만들어줘"라고 하면 코드가 나옵니다. 그런데 그 API를 팀에 공개했더니, 프론트엔드 개발자가 "에러가 날 때 응답 형태가 뭐예요?", "null이 올 수도 있나요?"를 묻기 시작합니다. 문서도 없고, 규칙도 없고, 클라이언트마다 다른 방어 코드를 추가하다 보면 어느 순간 API를 바꾸고 싶어도 아무것도 건드릴 수 없는 상태가 됩니다.

AI가 잘못 짠 걸까요? 아닙니다. AI는 동작하는 코드를 줬습니다. 문제는 API가 단순한 함수 묶음이 아니라 **오래 유지해야 하는 외부 계약**이라는 점입니다. 이 계약의 원칙을 모르면, AI에게 아무리 좋은 코드를 받아도 운영 단계에서 무너집니다.

> AI에게 좋은 API를 받으려면, 먼저 좋은 API가 무엇인지 알아야 합니다.

---

## 이 글에서 다룰 문제
- API는 정확히 무엇이며, 왜 시스템의 외부 계약이라고 부를까요?
- 라이브러리 API와 웹 API는 무엇이 같고 무엇이 다를까요?
- 좋은 API라고 부르려면 어떤 조건을 갖춰야 할까요?
- 이 개념을 실무에서 잘못 적용하면 어떤 문제가 생길까요?
- 바이브코딩할 때 API 설계 지식 없이 AI 코드를 쓰면 어떤 일이 일어날까요?

API는 경계(boundary), 계약(contract), 안정성(stability) 세 가지를 동시에 담고 있습니다. 이 세 개념이 선명하게 보여야 AI가 만들어준 코드가 "동작하는 코드"인지, "오래 쓸 수 있는 계약"인지 판단할 수 있습니다.

## Before / After

**Before — AI가 생성한 "동작하는" API (계약이 없음):**

```python
# 클라이언트가 서버 내부 구조에 직접 의존
data = open("/var/db/users.json").read()
# 서버가 저장 경로를 바꾸면 이 코드는 즉시 깨짐
```

**After — AI에게 계약을 명시하고 받은 API:**

```python
# 프롬프트: "GET /users 엔드포인트를 만들어줘. 성공 시 200 + JSON 배열, 실패 시 에러 형태도 정의해줘"
import requests

response = requests.get("https://api.example.com/users")
assert response.status_code == 200
users = response.json()  # 계약: 항상 배열. DB가 바뀌어도 이 코드는 그대로 동작
```

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| 계약 정의 없이 API 생성 | 클라이언트마다 다른 가정을 붙임 | AI에게 입력/출력/에러 형태를 함께 요청 |
| 에러 응답을 빠뜨림 | 실패 케이스를 나중에 발견 | "실패하면 어떤 형태로 돌려줄지도 정의해줘" 추가 |
| 상태 코드를 모두 200으로 | 모니터링 도구가 에러를 감지 못함 | "HTTP 표준 상태 코드를 사용해줘" 명시 |
| 내부 구조를 그대로 노출 | DB 변경이 API 변경을 강제 | "내부 모델과 응답 스키마를 분리해줘" 요청 |
| 버전 없이 배포 | 수정 한 번에 모든 클라이언트 영향 | API 설계 시 버전 전략 포함 요청 |

## AI에게 API 관련 질문하는 팁

바이브코딩에서 API 설계 프롬프트를 잘 쓰려면 네 가지를 포함하면 됩니다.

1. **리소스 명시**: "사용자(User) 리소스에 대해"
2. **성공/실패 응답 형태 요청**: "성공 응답과 에러 응답 형태 모두 정의해줘"
3. **계약 질문 추가**: "이 API의 클라이언트가 알아야 할 것은 뭐야?"
4. **표준 준수 요청**: "HTTP 표준과 REST 원칙을 따라줘"

예시 프롬프트:
> "GET /users/{id} 엔드포인트를 만들어줘. 성공 시 200 + 사용자 JSON, 없을 때 404 + 에러 메시지, 인증 없을 때 401을 반환하게 해줘. 에러 응답 형태는 전체에서 일관되게 유지해줘."

이렇게 하면 AI는 상태 코드, 응답 스키마, 에러 계약을 모두 갖춘 코드를 제안합니다.

## 운영 체크리스트
- [ ] 이 API의 입력과 출력 형태가 문서화되어 있는가?
- [ ] 에러 응답 형태가 모든 엔드포인트에서 일관적인가?
- [ ] 상태 코드가 HTTP 표준 의미대로 쓰이고 있는가?
- [ ] 내부 DB 스키마가 그대로 노출되고 있지 않은가?
- [ ] API를 바꿀 때 기존 클라이언트가 영향받는지 판단할 수 있는가?
- [ ] AI가 만든 API에 계약(Contract)이 존재하는지 확인했는가?

## 처음 질문으로 돌아가기

AI가 만들어준 API 코드를 그대로 쓰다가 "왜 갑자기 안 되지?"라는 상황을 만났을 때, 우리는 "AI가 잘못했다"고 말하는 대신 "이 API에 계약이 있는가? 에러 형태는 일관적인가?"라고 물을 수 있어야 합니다. 그 판단력을 갖추는 것이 이 시리즈의 목표입니다.

API는 경계, 계약, 안정성입니다. AI 코드를 검토할 때도, 프롬프트를 쓸 때도, 운영 장애를 디버깅할 때도 이 세 가지 질문이 출발점입니다.

## 정리

API는 단순한 URL 묶음이 아니라 오래 유지해야 하는 외부 계약입니다. AI는 동작하는 코드를 만들지만, 그 코드가 좋은 계약을 담고 있는지는 여러분이 판단해야 합니다. 입력/출력/에러 형태를 명시하고, HTTP 표준을 따르고, 내부 구현을 숨기면 AI와의 협업 품질이 달라집니다.

다음 글에서는 REST의 기본 원칙을 다룹니다. 리소스 중심 설계가 무엇인지, 그리고 AI에게 "REST API 만들어줘"라고 말할 때 그 REST가 실제로 무엇을 의미하는지 살펴봅니다.
