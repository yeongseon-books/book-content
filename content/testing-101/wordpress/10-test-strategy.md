# 바이브코딩을 위한 테스팅 기초 (10/10): 테스트 전략 세우기

이 글은 **바이브코딩을 위한 테스팅 기초** 시리즈의 마지막 글입니다. AI와 함께 빠르게 개발하는 바이브코딩 팀에 맞는 현실적인 테스트 전략을 정리합니다.

---

AI로 코드를 빠르게 만들 수 있게 됐다고 해서 테스트가 줄어드는 것이 아닙니다. 오히려 AI가 더 많은 코드를 더 자주 바꾸기 때문에 테스트가 더 중요해집니다. 문제는 바이브코딩 팀이 AI 속도에 맞춰 테스트를 어디에 얼마나 써야 하는지 전략 없이 접근하면 CI가 30분씩 걸리고 플래키 테스트가 늘어나 개발 속도가 오히려 떨어진다는 것입니다.

좋은 전략은 AI 코드의 위험을 올바른 계층에서 잡고, 빠른 피드백을 유지하면서, 팀 습관으로 굳히는 것입니다.

> 테스트 전략은 AI 코드의 위험을 올바른 계층에서 잡는 의식적인 선택입니다.

## 이 글에서 다룰 문제

- 바이브코딩 팀의 테스트 피라미드는 왜 분포가 중요할까요?
- AI 코드 특성에 맞게 단위, 통합, E2E 계층에 어떤 비율로 투자해야 할까요?
- AI가 자주 바꾸는 코드에서 핵심 경로를 어떻게 보호할까요?
- 바이브코딩 팀이 빠르게 채택할 수 있는 테스트 운영 습관은 무엇일까요?
- AI와 함께 테스트 전략을 유지하는 방법은 무엇일까요?

AI 코드는 빠르게 늘어납니다. 전략 없이 테스트를 추가하면 느리고 깨지기 쉬운 테스트 묶음이 됩니다. 분포를 잘 잡으면 AI 코드의 핵심 위험을 빠르게 잡으면서 CI 시간도 짧게 유지할 수 있습니다.

## 한눈에 보는 구조

테스트 피라미드는 AI 코드 검증에서도 그대로 적용됩니다. 아래층일수록 빠르고 많아야 하고, 위층일수록 비싸고 적어야 합니다.

- **테스트 피라미드**: 단위 테스트는 많고, 통합 테스트는 그보다 적고, E2E 테스트는 더 적게 두는 분포 모델입니다.
- **ROI**: AI 코드 테스트에 투자한 비용 대비 잡는 버그 수입니다.
- **핵심 경로(critical path)**: AI가 건드리면 안 되는 결제, 로그인 같은 핵심 흐름입니다.
- **플래키 예산(flaky budget)**: 허용 가능한 불안정 비율을 수치로 정한 기준입니다.

## 바이브코딩 팀에 맞는 테스트 분포

| 계층 | 비율 | 역할 | AI 코드에서의 가치 |
|---|---|---|---|
| 단위 테스트 | 70% | AI가 만든 함수 로직 즉시 검증 | 빠른 피드백, AI 경계값 감시 |
| 통합 테스트 | 20% | AI 코드가 시스템에 연결되는지 | DB 스키마 불일치, API 계약 위반 감지 |
| E2E 테스트 | 10% | 핵심 사용자 흐름 최종 확인 | AI가 프론트/백엔드를 따로 만들 때 연결 확인 |

## 바꾸기 전과 후

**바꾸기 전 — AI 코드에 전략 없이 테스트 추가**

```text
- 모든 AI 함수에 단위 테스트
- 모든 AI 화면에 E2E 테스트
- CI 40분, PR 처리 속도 정체
- AI가 빠르게 만드는 속도를 테스트가 오히려 막음
```

**바꾼 뒤 — 위험 기반으로 분배**

```text
- 핵심 도메인 단위 테스트 1,400개 (AI 경계값 집중)
- 통합 테스트 400개 (DB, 외부 API 경계)
- E2E 20개 (결제, 로그인 핵심 경로만)
- CI 7분 이내
```

## 다섯 단계로 바이브코딩 팀 전략 만들기

### 1단계 — AI 코드의 현재 분포 측정하기

```bash
pytest --collect-only -q | wc -l    # 전체 테스트 수
ls tests/unit | wc -l
ls tests/integration | wc -l
ls tests/e2e | wc -l
```

### 2단계 — AI가 건드리면 안 되는 핵심 경로 정의하기

```text
바이브코딩 팀의 핵심 경로 예시:
- Login / Logout
- Payment (결제)
- Sign-up (회원가입)
- 핵심 비즈니스 로직 (할인 계산, 권한 판정)
```

### 3단계 — AI 코드 변경 시 자동 회귀 감시 설정

```yaml
# PR 템플릿에 추가
- [ ] AI가 수정한 기능의 회귀 테스트가 통과하는가?
- [ ] 새 기능에 단위 테스트를 추가했는가?
- [ ] 핵심 경로 E2E 테스트가 통과하는가?
```

### 4단계 — AI와 함께 테스트 전략 유지하기

```text
AI 프롬프트 원칙:
"이 PR에서 기존 테스트를 깨뜨리지 않으면서 기능을 추가해 줘"
"이 코드의 단위 테스트를 만들어 줘 (경계값 포함)"
"회귀 테스트가 모두 통과하는지 확인해 줘"
```

### 5단계 — 분기마다 AI 코드 테스트 부채 가지치기

```bash
# 6개월 동안 한 번도 가치 있게 실패하지 않은 E2E 재검토
# AI가 과잉 생성한 중복 테스트 정리
# 플래키 테스트 목록 리뷰 및 수정
```

## 바이브코딩 팀 테스트 예산 배분

**2,000개 테스트 기준 바이브코딩 팀 예산**

| 계층 | 개수 | 비율 | 총 실행 시간 | AI 코드 감시 역할 |
|---|---|---|---|---|
| 단위 테스트 | 1,400 | 70% | 14초 | AI 함수 로직, 경계값, 예외 처리 |
| 통합 테스트 | 400 | 20% | 40초 | AI 코드의 DB 연동, API 계약 |
| E2E 테스트 | 200 | 10% | 400초 | AI 풀스택 코드의 핵심 흐름 |
| **합계** | **2,000** | **100%** | **7분 30초** | — |

## AI 코드 테스트의 특수한 고려사항

바이브코딩 팀에서 일반 팀과 다른 테스트 전략 포인트입니다.

```text
1. AI는 경계값을 자주 빠뜨린다
   → 단위 테스트에서 경계값 케이스를 명시적으로 추가

2. AI는 리팩토링 시 예외 처리를 제거하기도 한다
   → 회귀 테스트로 예외 처리를 코드로 잠근다

3. AI가 프론트/백을 따로 만들면 연결 지점에서 버그가 생긴다
   → E2E 테스트로 핵심 사용자 흐름을 검증

4. AI가 생성한 Mock 과잉 테스트는 리팩토링에 약하다
   → Fake와 Stub 기반 결과 검증을 기본으로

5. AI는 이전 수정의 맥락을 모른다
   → 회귀 테스트를 CI에 포함해 AI 수정 시 자동 감시
```

## 자주 하는 실수

가장 흔한 실수는 AI가 생성한 모든 코드에 같은 강도로 테스트를 요구하는 일입니다. 핵심 결제 로직과 단순한 유틸리티 함수는 같은 커버리지 기준이 필요하지 않습니다.

둘째, AI가 빠르게 E2E 테스트를 생성하도록 두는 문제입니다. E2E는 가장 비싸고 느립니다. 핵심 경로 20개 이내를 유지하세요.

셋째, AI가 생성한 Mock 과잉 테스트를 그대로 두는 경우입니다. AI가 리팩토링할 때마다 Mock 테스트가 먼저 깨져 개발 속도를 낮춥니다.

## 바이브코딩 팀 테스트 전략 문서화

```markdown
# 바이브코딩 팀 Testing Strategy

## 1. 목표 분포
- Unit: 70% (AI 함수 로직, 경계값)
- Integration: 20% (DB, API 경계)
- E2E: 10% (핵심 사용자 흐름 최대 20개)

## 2. AI 코드 검증 원칙
- AI에게 코드 요청 시 테스트도 함께 요청
- AI가 생성한 테스트의 단언문 반드시 검토
- 회귀 테스트는 AI 수정 요청 시 함께 제공

## 3. 품질 지표
- CI time: < 10분 (PR)
- Flaky rate: < 5%
- Coverage: 핵심 도메인 90%+

## 4. 팀 습관
- PR 머지 전 테스트 통과 필수
- 버그 수정 PR에 회귀 테스트 포함
- 분기마다 플래키 테스트 리뷰
```

## 운영 체크리스트

- [ ] 팀의 테스트 분포를 알고 있습니다.
- [ ] AI가 건드리면 안 되는 핵심 경로가 E2E로 보호됩니다.
- [ ] PR 머지 전 CI 통과가 필수로 설정됩니다.
- [ ] AI에게 코드 요청 시 테스트도 함께 요청합니다.
- [ ] 분기마다 플래키 테스트를 검토합니다.

## 처음 질문으로 돌아가기

- **바이브코딩 팀의 테스트 피라미드는 왜 분포가 중요할까요?**
  AI가 빠르게 코드를 만들 수록 테스트도 빠르게 늘어납니다. 분포 없이 늘리면 CI가 느려져 AI의 생산성 이점을 테스트가 상쇄합니다.

- **AI 코드에서 핵심 경로를 어떻게 보호할까요?**
  결제, 로그인 같은 핵심 흐름을 E2E로, 비즈니스 로직을 단위 테스트로, 연동 경계를 통합 테스트로 계층화합니다.

- **AI와 함께 테스트 전략을 유지하는 방법은?**
  AI에게 코드 요청 시 "기존 테스트를 깨뜨리지 않으면서"를 명시하고, 회귀 테스트를 함께 제공하며, CI를 통해 자동으로 검증합니다.

## 정리

바이브코딩 팀에서 테스트 전략은 AI의 속도와 코드 품질을 동시에 유지하는 균형점입니다. 단위 테스트를 두껍게, E2E는 핵심만, CI는 자동으로 — 이 세 가지가 함께 작동할 때 AI 코드가 프로덕션에서 터지지 않습니다.

시리즈를 마치며: 바이브코딩은 강력합니다. 하지만 AI가 만든 코드를 테스트 없이 배포하는 것은 눈을 감고 운전하는 것과 같습니다. 이 시리즈에서 배운 테스팅 기초가 여러분의 바이브코딩을 더 안전하고 빠르게 만들기를 바랍니다.
