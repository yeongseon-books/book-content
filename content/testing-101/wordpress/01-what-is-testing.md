# 바이브코딩을 위한 테스팅 기초 (1/10): 테스트란 무엇인가?

이 글은 **바이브코딩을 위한 테스팅 기초** 시리즈의 첫 번째 글입니다. AI와 함께 코드를 만드는 바이브코딩 환경에서 테스트가 왜 더 중요한지, 그리고 자동 테스트를 어떻게 시작하는지 처음부터 설명합니다.

---

AI에게 코드를 시키면 빠릅니다. 함수 하나, 기능 하나, 때로는 모듈 전체를 몇 분 만에 만들어 줍니다. 문제는 그 코드가 실제로 맞는지 확인하는 일입니다.

AI가 만든 코드는 겉보기에 그럴듯합니다. 컴파일이 되고, 실행도 됩니다. 그런데 "잘 되네"라고 생각하고 배포했다가 프로덕션에서 터지는 일이 바이브코딩 팀에서 반복됩니다. AI는 코드를 만들지만 그 코드가 비즈니스 맥락에서 올바른지는 사람이 확인해야 합니다. 그 확인을 코드로 남기는 것이 테스트입니다.

> 테스트의 본질은 한 번의 확인이 아니라, 같은 검증을 여러 번 재현할 수 있는 자동화된 절차입니다.

## 이 글에서 다룰 문제

- 테스트는 정확히 무엇을 검증하는 코드일까요?
- 수동 확인과 자동 테스트는 무엇이 다를까요?
- 단위 테스트, 통합 테스트, E2E 테스트는 어떻게 구분할까요?
- 바이브코딩 환경에서 테스트 없이 배포하면 어떤 일이 생길까요?
- AI가 만든 코드를 테스트할 때 초보자가 가장 자주 놓치는 포인트는 무엇일까요?

AI가 만든 코드에 테스트가 없으면 모든 수정이 추측에 가까워집니다. AI에게 회원가입 코드를 고쳐 달라고 했더니 결제가 깨지고, 결제를 고쳤더니 로그인이 깨지는 일이 반복됩니다. 문제는 버그가 생긴다는 사실만이 아닙니다. 팀이 AI 코드를 믿지 못하게 된다는 점이 더 큽니다.

자동 테스트는 AI 코드를 검증하는 안전망입니다. AI가 코드를 바꿀 때마다 테스트를 돌려 기존 동작이 유지되는지 확인할 수 있습니다. 그래서 바이브코딩 팀일수록 테스트가 더 중요합니다.

## 한눈에 보는 구조

가장 단순한 흐름입니다. 프로덕션 코드가 있고, 그 코드를 검증하는 테스트 코드가 있습니다. 테스트 러너는 테스트를 모아서 실행하고, 통과 여부와 실패 위치를 알려 줍니다.

```text
┌─────────────────┐     ┌──────────────────┐     ┌────────────────┐
│ Production Code │ ←── │   Test Code      │ ←── │  Test Runner   │
│  (src/)         │     │  (tests/)        │     │  (pytest)      │
└─────────────────┘     └──────────────────┘     └────────────────┘
                                                         │
                                                         ▼
                                                  ┌────────────────┐
                                                  │  결과 리포트    │
                                                  │  Pass / Fail   │
                                                  └────────────────┘
```

테스트도 코드입니다. 기대하는 동작을 실행 가능한 형태로 남긴 것입니다. 버전 관리가 되고, PR에서 리뷰할 수 있고, CI에서 자동 실행할 수 있습니다.

| 용어 | 의미 | 예시 |
|------|------|------|
| 테스트 | 기대하는 동작을 코드로 표현한 검증 절차 | `assert add(2, 3) == 5` |
| 단언문(assertion) | 실제 값이 기대와 맞는지 확인하는 표현 | `assert result == expected` |
| 테스트 러너 | 테스트를 수집하고 실행하는 도구 | pytest, unittest, Jest |
| 픽스처(fixture) | 테스트에서 재사용할 데이터나 상태 | DB 연결, 임시 파일, 테스트 사용자 |
| 커버리지(coverage) | 테스트가 프로덕션 코드를 어디까지 실행했는지 보여 주는 지표 | line coverage 85% |
| SUT(System Under Test) | 현재 테스트 대상이 되는 코드 단위 | 함수, 클래스, 모듈 |

## 바이브코딩 관점: AI 코드의 함정

바이브코딩에서 가장 위험한 순간은 AI가 코드를 만들어 줄 때가 아니라, 그 코드를 확인 없이 배포할 때입니다.

**AI 코드가 터지는 대표 패턴**

```text
시나리오 1: AI가 할인 계산 함수를 만들었다
→ 로컬에서 몇 가지 케이스 확인 → "잘 되네"
→ 배포 후 특정 할인율에서 음수 가격 발생
→ 고객 민원 폭주

시나리오 2: AI에게 기존 함수를 리팩토링 요청
→ 코드가 더 깔끔해짐 → PR 머지
→ 엣지 케이스에서 예외가 사라져 버그 조용히 발생
→ 3주 뒤 발견
```

테스트가 있었다면 두 시나리오 모두 배포 전에 잡혔습니다.

## 바꾸기 전과 후

**바꾸기 전 — AI 코드를 수동 확인 후 배포**

```text
1. AI에게 함수 작성 요청
2. 로컬에서 몇 번 실행해서 "잘 되네"
3. PR을 머지한다
4. 배포 후 엣지 케이스에서 터진다
```

**바꾼 뒤 — AI 코드에 테스트를 붙이고 배포**

```bash
$ pytest
collected 142 items
.................................... 142 passed in 3.4s
```

AI가 만든 코드가 맞는지 테스트가 확인해 줍니다. 다음 주에도, 반년 뒤에도, AI에게 다시 수정을 요청했을 때도 테스트는 계속 돌아갑니다.

| 비교 항목 | 수동 확인 | 자동 테스트 |
|-----------|-----------|-------------|
| 반복 비용 | 매번 사람이 시간 투입 | 한 번 작성, 무한 반복 |
| 범위 | 기억에 의존, 빠뜨림 발생 | 정의된 시나리오 전부 실행 |
| 피드백 속도 | 분~시간 | 초~분 |
| AI 재수정 후 검증 | 다시 수동 확인 | `pytest` 한 줄로 재검증 |
| 회귀 감지 | 우연히 발견 | 즉시 실패 |

## 다섯 단계로 첫 자동 테스트 만들기

### 1단계 — 검증할 함수 준비

```python
# src/calc.py
def add(a: int, b: int) -> int:
    return a + b
```

### 2단계 — 테스트 파일 작성

```python
# tests/test_calc.py
from src.calc import add

def test_add_positive_numbers():
    assert add(2, 3) == 5

def test_add_with_zero():
    assert add(0, 7) == 7
```

### 3단계 — 실행

```bash
pip install pytest
pytest -v
```

### 4단계 — 일부러 깨뜨려 보기 (바이브코딩 핵심 습관)

```python
def add(a: int, b: int) -> int:
    return a - b   # AI가 잘못 만든 코드 시뮬레이션
```

```bash
pytest -v
# FAILED tests/test_calc.py::test_add_positive_numbers - assert -1 == 5
```

### 5단계 — AI에게 수정 요청 후 다시 검증

AI에게 코드를 고쳐 달라고 한 뒤 `pytest`를 다시 실행합니다. 모든 테스트가 초록색으로 돌아오면 AI가 올바르게 수정했다는 확신을 얻습니다.

## AI 실수를 잡는 테스트 작성 팁

```python
# 나쁜 예: 실패 시 "AssertionError" 한 줄만 나옴
def test_bad():
    assert process(data)

# 좋은 예: 실패 시 기대값과 실제값이 모두 보임
def test_good():
    result = process(data)
    assert result.status == "completed", f"Expected completed, got {result.status}"
```

AI 코드 테스트에서는 실패 메시지가 특히 중요합니다. 무엇이 틀렸는지 명확하게 보여야 AI에게 정확한 수정 요청을 할 수 있습니다.

## 테스트의 세 가지 레벨

```text
                ┌───────────┐
               /  E2E Test   \         ← 적고, 느리고, 비싸다
              /───────────────\
             / Integration Test\       ← 중간
            /───────────────────\
           /     Unit Test       \     ← 많고, 빠르고, 싸다
          └─────────────────────────┘
```

| 레벨 | 범위 | 속도 | 바이브코딩에서의 역할 |
|------|------|------|----------------------|
| Unit | 함수 하나, 클래스 하나 | ms 단위 | AI가 만든 로직 즉시 검증 |
| Integration | 모듈 간 경계 (DB, API, 큐) | 초 단위 | AI 코드가 시스템에 잘 연결되는지 |
| E2E | 사용자 시나리오 전체 | 분 단위 | 배포 전 핵심 흐름 최종 확인 |

## 자주 하는 실수

첫 번째 실수는 AI가 만든 코드를 한 번 실행해 보고 테스트가 끝났다고 생각하는 경우입니다. 한 번 확인은 그 순간에만 유효합니다. AI에게 다음 번에 그 코드를 수정하면 다시 깨질 수 있습니다.

두 번째 실수는 테스트를 나중에 쓰면 된다고 미루는 경우입니다. AI와 함께 코드를 만들 때 테스트를 같이 요청하는 것이 훨씬 효율적입니다. "이 함수를 만들어 줘"가 아니라 "이 함수와 pytest 테스트를 함께 만들어 줘"라고 요청하세요.

세 번째 실수는 테스트가 초록색이면 안전하다고 믿는 경우입니다. 테스트는 작성한 시나리오만 검증합니다. AI가 예상치 못한 엣지 케이스를 만들어도 테스트가 없으면 잡히지 않습니다.

## AI에게 테스트 요청하는 방법

바이브코딩에서 AI를 테스팅에 활용하는 실용적인 방법입니다.

```text
좋은 프롬프트 예시:
"apply_discount(price, percent) 함수를 만들어 줘.
그리고 pytest 테스트도 함께 작성해 줘.
경계값(0%, 100%, 음수 퍼센트)을 포함해서."

피해야 할 패턴:
"코드 만들어 줘" → 테스트 없음
"테스트도 만들어 줘" → 표면적인 테스트만 나올 수 있음
```

AI가 만든 테스트도 반드시 검토해야 합니다. AI는 단언문 없이 코드만 실행하는 테스트를 만들기도 합니다.

## 운영 체크리스트

- [ ] `pytest`를 한 번 설치하고 실행해 봤습니다.
- [ ] AI가 만든 코드에 테스트를 하나 이상 붙여 봤습니다.
- [ ] 코드를 일부러 깨뜨린 뒤 실패 메시지를 읽어 봤습니다.
- [ ] AI에게 테스트 작성을 함께 요청해 봤습니다.

## 처음 질문으로 돌아가기

- **테스트는 정확히 무엇을 검증하는 코드일까요?**
  기대하는 동작을 실행 가능한 형태로 남긴 코드입니다. `assert add(2, 3) == 5`처럼 입력과 기대 출력을 명시합니다.

- **수동 확인과 자동 테스트는 무엇이 다를까요?**
  수동 확인은 그 순간에만 유효합니다. 자동 테스트는 AI가 코드를 수정할 때마다 같은 검증을 반복합니다.

- **단위 테스트, 통합 테스트, E2E 테스트는 어떻게 구분할까요?**
  범위와 속도가 다릅니다. 단위 테스트는 함수 하나를 밀리초로 검증하고, E2E는 전체 사용자 흐름을 분 단위로 검증합니다.

- **바이브코딩 환경에서 테스트 없이 배포하면 어떤 일이 생길까요?**
  AI가 만든 코드의 엣지 케이스가 프로덕션에서 처음 발견됩니다. 발견 비용은 개발 중 발견 비용의 수십 배입니다.

## 정리

테스트는 AI가 만든 코드를 믿을 수 있게 만드는 장치입니다. AI는 빠르게 코드를 만들지만, 그 코드가 프로덕션에서 안전한지는 테스트가 보장합니다. 다음 글에서는 가장 작고 빠른 테스트인 단위 테스트를 자세히 보겠습니다.
