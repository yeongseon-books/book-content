# 바이브코딩을 위한 Observability 기초 (8/10): SLI와 SLO

이 글은 "바이브코딩을 위한 Observability 기초" 시리즈의 8번째 글입니다.

---

바이브코딩에서 AI는 메트릭과 대시보드를 빠르게 만들어 줍니다. 그런데 "서비스가 안정적인가"라는 질문은 의외로 자주 감정 싸움이 됩니다. 어떤 팀은 충분히 괜찮다고 말하고, 어떤 팀은 이미 위험하다고 말합니다. 서로 다른 감각만 들고 있으면 배포와 기능 추가, 안정화 우선순위가 계속 흔들립니다.

SLI(서비스 수준 지표)와 SLO(서비스 수준 목표)는 이 문제를 숫자로 바꿉니다. "이번 달 가용성이 99.87%라 목표를 밑돌았다"처럼 같은 문장을 함께 보게 되면 배포를 멈출지, 기능 개발을 늦출지, 안정화에 시간을 더 쓸지 판단이 쉬워집니다.

SLO는 엔지니어링과 비즈니스가 공통 언어를 갖게 해 줍니다. 오류 예산(error budget)은 기능 개발과 안정화의 균형점 역할을 합니다. 오류 예산이 넉넉하면 빠르게 배포하고, 빠르게 소진되면 안정화에 집중합니다.

SLI 정의, SLO 설정, 오류 예산, 소진 속도 경보를 중심으로 정리합니다.

> **핵심 인사이트:** 99.9% SLO는 30일 동안 43.2분의 다운타임을 허용합니다. 이것이 오류 예산입니다. 예산이 넉넉하면 배포를 빠르게 할 수 있고, 빠르게 소진되면 안정화에 집중해야 합니다. 이 숫자가 없으면 "얼마나 안정적이어야 하는가"는 항상 감정 싸움이 됩니다.

## 이 글에서 다룰 문제

- SLI는 무엇을 어떻게 측정할까요?
- SLO는 어떤 약속을 만들까요?
- 오류 예산은 왜 기능 개발과 안정화의 균형점이 될까요?
- 소진 속도(burn rate) 경보는 어떻게 설정할까요?
- AI가 만든 모니터링 코드에서 SLO 관점으로 확인할 것은 무엇인가요?

## SLI/SLO 핵심 패턴

```promql
# Availability SLI: 성공 요청 / 전체 요청
sli_good = sum(rate(http_requests_total{status!~"5.."}[5m]))
sli_total = sum(rate(http_requests_total[5m]))
# SLI = sli_good / sli_total

# SLO: 30일 99.9% 가용성
# → 허용 다운타임: 30 * 24 * 60 * 0.001 = 43.2분/월

# 오류 예산 소진량
1 - (sli_good / sli_total)  # 현재 실패율
```

```yaml
# 소진 속도 경보: 빠른 사고 + 느린 잠식 동시 탐지
- alert: FastBurn
  expr: >
    error_rate_5m > 14.4 * 0.001
    and error_rate_1h > 14.4 * 0.001
  for: 2m
  labels: { severity: page }
  annotations:
    summary: "오류 예산 빠르게 소진 중 - 14.4배 속도"

# 월간 SLO 보고 예시
# - Availability: 99.92% (target 99.9% → PASS)
# - Latency p95: 320ms (target <= 500ms → PASS)
# - 오류 예산 소진: 38%
```

## 변경 전후 비교

**Before: 감각 기반 논의**
```text
- "느리다" vs "괜찮다" 의견 충돌
- 배포를 멈춰야 하는지 감으로 결정
- "충분히 안정적"의 기준이 사람마다 다름
- 기능 개발 vs 안정화 우선순위 결정 어려움
```

**After: 숫자 기반 논의**
```text
- "이번 달 99.92%, 목표 99.9% → 통과"로 공통 언어
- 오류 예산 소진율로 배포 속도 결정
- 소진 속도 경보로 느린 잠식도 조기 탐지
- 월간 보고로 기능/안정화 우선순위 설득력 확보
```

## 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 방법 |
|------|-------------|-----------|
| SLO를 100%로 설정 | 어떤 배포도 리스크가 됨, 혁신 불가 | 99.9% 또는 비즈니스에 맞는 수준 |
| 지연 시간을 평균으로 측정 | 느린 사용자가 안 보임 | p95, p99 퍼센타일 사용 |
| 오류 예산 없이 SLO만 | 예산 개념이 없으면 배포 속도 결정 불가 | SLO에서 오류 예산 계산 필수 |
| 임계값 경보만, 소진 속도 없음 | 느리게 나빠지는 상황 탐지 못함 | 소진 속도 경보 추가 |
| 내부 메트릭만 측정 | 사용자 체감 성능과 다를 수 있음 | 사용자 요청 기반 SLI 사용 |

## AI 활용 팁

```
# AI에게 이렇게 요청하세요:
"웹 API 서비스의 SLI/SLO 체계를 만들어줘.
가용성 SLI (5xx 제외 성공률),
지연 시간 SLI (p95),
SLO: 가용성 99.9%, 지연 p95 500ms,
오류 예산 계산, 소진 속도 Prometheus 경보 포함"

# AI 결과물 검증 체크포인트:
# - SLI가 5xx 제외 성공률인가? (사용자 관점)
# - 지연 시간이 평균이 아닌 p95/p99인가?
# - 오류 예산이 SLO에서 명확히 계산되어 있는가?
# - 소진 속도 경보 (fast burn + slow burn)가 있는가?
# - SLO가 100%로 설정되지 않았는가?
```

## 운영 체크리스트

- [ ] 주요 사용자 여정에 SLI가 정의되어 있다
- [ ] SLO가 수치로 명시되어 있다 (예: 가용성 99.9%, 지연 p95 500ms)
- [ ] 오류 예산이 계산되어 있다 (월 허용 분)
- [ ] 소진 속도 경보가 설정되어 있다 (빠른 소진 + 느린 소진)
- [ ] 월간 SLO 보고가 있고 팀과 공유된다

## 처음 질문으로 돌아가기

- **SLI와 SLO의 차이는?** SLI는 측정값(실제 가용성 99.92%)이고, SLO는 목표값(가용성 99.9%)입니다. SLO를 SLI가 넘었는지로 안정성을 판단합니다.
- **오류 예산이란?** SLO에서 허용하는 실패량입니다. 99.9% SLO면 0.1%의 실패를 허용합니다. 30일 기준 약 43분입니다. 이 예산이 빠르게 소진되면 배포를 멈추고 안정화에 집중합니다.
- **소진 속도 경보가 필요한 이유는?** 임계값 경보만으로는 "서서히 나빠지는" 상황을 탐지하지 못합니다. 5분과 1시간 구간을 함께 보는 소진 속도 경보가 빠른 사고와 느린 잠식을 동시에 잡습니다.

## 정리

바이브코딩에서 AI가 만들어 준 모니터링 코드에 SLI/SLO 관점을 추가하세요. 사용자 관점 SLI, 오류 예산 계산, 소진 속도 경보를 반드시 확인하세요. "서비스가 안정적인가"를 숫자로 말할 수 있어야 기능 개발과 안정화의 균형을 잡을 수 있습니다. 다음 글에서는 비용과 카디널리티를 다룹니다.
