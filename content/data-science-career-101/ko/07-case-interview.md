# Data Science Career 101 (7/10): 케이스 인터뷰

케이스 인터뷰는 많은 지원자에게 가장 추상적으로 느껴지는 단계입니다. SQL처럼 정답 형태가 명확하지도 않고, 머신러닝처럼 알고리즘 이름을 기준으로 준비할 수도 없기 때문입니다. 그래서 질문을 들으면 곧바로 아이디어를 던지다가 구조 없이 끝나는 경우가 많습니다.

하지만 면접관이 보고 싶은 것은 아이디어의 양이 아니라 사고의 질입니다. 문제를 어떻게 명확히 하고, 어떤 지표를 중심에 둘지 정하고, 어떤 가설을 세운 뒤, 어떤 데이터로 검증하고, 마지막에 어떤 결정을 내릴지까지 보여 줘야 답변이 단단해집니다.

이 글은 Data Science Career 101 시리즈의 일곱 번째 글입니다.

![Data Science Career 101 7장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/data-science-career-101/07/07-01-concept-at-a-glance.ko.png)
*Data Science Career 101 7장 흐름 개요*

> 케이스 인터뷰에서 가장 중요한 것은 정답 찾기가 아니라 "명확화 → 지표 → 가설 → 데이터 → 결정" 순서를 일관되게 보여 주는 것입니다.

## 이 글에서 다룰 문제

- 케이스 인터뷰가 실제로 무엇을 평가하는가
- 문제를 들었을 때 왜 먼저 명확화 질문을 해야 하는가
- 북극성 지표와 보조 지표를 어떻게 고르는가
- 면접에서 자주 나오는 케이스 유형과 답변 구조는 무엇인가
- 팀 구조와 협업 맥락을 케이스 답변에 어떻게 연결하는가

## 케이스 인터뷰가 평가하는 것

빅테크와 데이터 중심 스타트업의 PM, 분석가, 사이언티스트 면접에서 케이스 스타일 질문의 비중은 높습니다. 실제 업무가 늘 애매한 문제를 구조화하는 과정이기 때문입니다.

면접관이 보는 핵심:
- 모호한 문제를 명확한 질문으로 전환하는가
- 지표를 구체적으로 정의하고 트레이드오프를 인식하는가
- 서로 다른 성격의 가설을 병렬로 세우는가
- 마지막에 실행 가능한 결론을 내리는가

**역량 수준별 케이스 답변 차이:**

| 역량 수준 | 동일 질문에 대한 답변 패턴 | 면접관 판단 |
| --- | --- | --- |
| 입문 | "리텐션을 높이기 위해 푸시 알림을 강화하겠습니다" | 지표 정의 없음, 가설 검증 계획 없음 |
| 중급 | "리텐션을 7일 기준으로 정의하고, 유입 채널별로 분해해 보겠습니다" | 지표 정의 있으나 가설과 결정 약함 |
| 실무 수준 | 명확화 → 지표 → 가설(3가지) → 데이터 → 결정 순서를 일관되게 보여 줌 | 사고 구조가 명확하고 실행 가능한 결론이 있음 |

## 다섯 단계 프레임

### 1단계 — 명확화 (Clarify)

```text
"DAU가 떨어졌습니다" → "어느 세그먼트에서, 어느 기간 동안, 얼마나?"
```

명확화 질문은 시간을 버는 장치가 아니라 잘못된 문제를 푸는 일을 막는 장치입니다.

**필수 명확화 항목:**
- 기간: 하루인가, 주간인가, 월간 추세인가
- 세그먼트: 전체인가, 특정 플랫폼/지역/코호트인가
- 기준 지표: 어떤 지표가 얼마나 움직였는가
- 최근 변경: 제품 출시, 마케팅 캠페인, 데이터 파이프라인 변경이 있었는가

**명확화 질문 예시 3개:**

1. "DAU 하락이 특정 플랫폼 (iOS/Android/Web 중 하나)에서 집중되고 있는지, 전체적으로 고르게 나타나는지 확인할 수 있을까요?"
2. "지난주와 비교해 최근 배포 일정이나 마케팅 캠페인 변경이 있었습니까?"
3. "이 수치가 일시적인 현상인지, 최소 2-3주 이상 지속되는 추세인지 파악할 수 있는 데이터가 있습니까?"

**명확화를 건너뛰면 생기는 문제:**

명확화 없이 바로 답변을 시작하면 두 가지 위험이 있습니다. 첫째, 잘못된 문제를 푸는 데 5분을 쓸 수 있습니다. 면접관이 "저는 iOS만 하락했다고 했는데요"라고 돌아오면 처음부터 다시 시작해야 합니다. 둘째, 면접관에게 "이 사람은 실무에서도 질문 없이 바로 분석을 시작하겠구나"라는 인상을 줍니다. 명확화는 신중함의 표시입니다.

### 2단계 — 지표 설계 (Metric)

```text
북극성 지표 1개 + 보조 지표 2개
```

지표가 없으면 대화는 금방 추상적으로 흩어집니다.

**지표 선택 예시 (구독 서비스의 경우):**

| 지표 유형 | 지표명 | 측정 방향 |
| --- | --- | --- |
| 북극성 | 월간 활성 구독자 (MAS) | 상승 |
| 보조 (선행) | 7일 리텐션 | 상승 |
| 가드레일 | 구독 취소율 | 하락 유지 |

가드레일 지표는 북극성을 높이는 과정에서 무너지면 안 되는 지표입니다. 이것을 먼저 정의하면 답변의 완성도가 올라갑니다.

**도메인별 북극성 지표 예시:**

| 서비스 유형 | 북극성 지표 | 보조 지표 | 가드레일 |
| --- | --- | --- | --- |
| 구독 서비스 | 월간 활성 구독자 | 7일 리텐션, 업그레이드율 | 구독 취소율 |
| 커머스 | 주문당 수익 | 재구매율, 장바구니 전환율 | 반품율, 고객 불만 건수 |
| SaaS | 주간 활성 팀 수 | 기능 채택률, NPS | 해지율, 지원 티켓 수 |
| 소셜 미디어 | 일간 콘텐츠 소비 시간 | 팔로우 증가율, 댓글 수 | 스팸 신고율 |

**지표 정의의 함정 — "리텐션"의 다양한 정의:**

| 정의 방식 | 측정 내용 | 주의 사항 |
| --- | --- | --- |
| N일 리텐션 | 가입 후 정확히 N일째에 활성 | 단일 날짜 기준, 노이즈 큼 |
| 롤링 N일 리텐션 | 가입 후 N일 이내 최소 1회 활성 | 더 안정적, 집계 단위 중요 |
| 주간 리텐션 | 이전 주 활성 중 이번 주에도 활성 | 서비스 주기에 맞게 선택 |

면접에서 "리텐션이 하락했습니다"라는 질문을 받으면 반드시 "어떤 정의의 리텐션인가요?"를 명확화 질문에 포함해야 합니다.

### 3단계 — 가설 수립 (Hypothesis)

```text
- 제품 가설: 최근 UI 변경이 온보딩 이탈을 유발했다
- 외부 가설: 경쟁사 프로모션으로 유입 감소
- 데이터 가설: 로깅 오류로 이벤트 누락
```

가설은 하나만 두면 위험합니다. 서로 다른 성격의 가설(제품, 외부, 데이터)을 함께 세워야 탐색 범위가 균형을 잡습니다. 면접에서 가설을 세 가지 카테고리로 분류하는 것 자체가 구조적 사고 신호입니다.

**가설 카테고리별 탐색 방법:**

| 가설 카테고리 | 탐색 방법 | 필요한 데이터 |
| --- | --- | --- |
| 제품 가설 | 출시 일자와 지표 변화 시점 비교 | 배포 로그, 제품 변경 이력 |
| 외부 가설 | 경쟁사 동향, 시장 데이터, SNS 언급 | 앱스토어 리뷰, 검색 트렌드 |
| 데이터 가설 | 파이프라인 로그, 이벤트 발송 수 | 이벤트 로그, 파이프라인 상태 |

**가설 우선순위 정하기:**

가설을 세운 후 바로 데이터를 보는 것이 아니라 "어떤 가설을 먼저 검증해야 하는가"를 판단해야 합니다. 데이터 가설을 먼저 확인하는 이유는 데이터 자체가 잘못됐다면 나머지 분석이 의미 없기 때문입니다. 이 순서를 말하는 것 자체가 실무 경험을 보여 줍니다.

### 4단계 — 데이터 계획 (Data)

```text
- 어떤 쿼리로 어떤 비교를 할 것인가
- 실험(A/B)이 가능한가, 관찰만 가능한가
```

"데이터를 보겠습니다"로는 약합니다. 어떤 비교를 할지, 어떤 로그를 볼지, 실험이 가능한지까지 말해야 실행 계획처럼 들립니다.

**구체적 답변 예시:**
- "유입 채널별 7일 리텐션을 전주 대비 비교하겠습니다"
- "데이터 파이프라인 로그에서 이벤트 누락 여부를 먼저 확인하겠습니다"
- "A/B 테스트가 가능하다면 새 온보딩 플로우를 10% 트래픽에 실험하겠습니다"

**데이터 계획의 실현 가능성 체크:**

면접에서 데이터 계획을 말할 때 "이 데이터가 실제로 존재하는가"도 고려해야 합니다. 예를 들어 "경쟁사 데이터를 분석하겠습니다"는 보통 실현 불가능합니다. 대신 "앱스토어 리뷰에서 경쟁사 관련 키워드를 분석하겠습니다"처럼 실제 접근 가능한 데이터로 말해야 합니다.

### 5단계 — 결정 제안 (Decision)

```text
추천 액션 1-2개 + 리스크 1개 + 후속 측정 방법
```

케이스 답변은 결론이 있어야 끝납니다. 추천 액션과 리스크, 후속 측정이 함께 나와야 실제 의사결정 제안이 됩니다.

**예시:**
"온보딩 3단계 이탈이 원인이라면 단계 간소화 실험을 2주 진행하겠습니다. 단, 가드레일로 유료 전환율을 모니터링해 2% 이상 하락 시 중단하겠습니다. 실험 후 7일 리텐션 개선 여부를 주 지표로 평가하겠습니다."

**결정 제안 구조 템플릿:**

```text
[상황 요약]: [원인 가설] 이 [지표]에 영향을 미쳤습니다.
[추천 액션]: [구체적 변경]을 [기간] 동안 진행하겠습니다.
[성공 기준]: [북극성 지표]가 [X%] 이상 개선되면 성공으로 판단합니다.
[가드레일]: [가드레일 지표]가 [임계값] 이하로 유지되어야 합니다.
[다음 단계]: [측정 기간] 후 결과를 검토하고 [후속 결정]을 내리겠습니다.
```

## 실제 케이스 분해 예시

### 케이스 A: "DAU가 20% 하락했습니다"

**명확화:** "어느 플랫폼에서 언제부터입니까? 최근 배포나 캠페인 변경이 있었습니까?"

**지표:** 북극성 = DAU, 보조 = 세션 수, 가드레일 = 앱 크래시율

**가설:**
1. 제품: 최근 업데이트에서 로그인 버그 발생
2. 외부: 경쟁사 신규 앱 출시로 이탈 증가
3. 데이터: 이벤트 로깅 파이프라인 오류

**데이터 계획:**
- 플랫폼별 DAU 분해 (iOS vs Android vs Web)
- 업데이트 날짜 전후 비교
- 앱스토어 1-2점 리뷰 급증 여부 확인

**결정:** "iOS 17.1 업데이트와 DAU 하락 시점이 일치하고 크래시율이 증가했습니다. 긴급 핫픽스 배포를 권고하고, 24시간 후 DAU 회복 여부를 모니터링하겠습니다."

### 케이스 B: "구독 취소율이 올랐습니다"

**명확화:** "어느 구독 플랜에서입니까? 신규 가입자인지 장기 사용자인지입니까? 취소 후 설문 응답이 있습니까?"

**지표:** 북극성 = 월간 구독 유지율, 보조 = 취소 이유 분포, 가드레일 = 신규 유입

**가설:**
1. 제품: 핵심 기능 제거 또는 가격 인상 공지
2. 외부: 경쟁사 무료 플랜 출시
3. 데이터: 구독 상태 집계 오류

**결정:** "취소 이유 중 '가격 불만'이 60%라면 연간 결제 할인 안내 푸시를 A/B 테스트하겠습니다. 단기 할인이 장기 LTV를 훼손하는지 가드레일로 함께 측정하겠습니다."

### 케이스 C: "신기능 출시 2주 후 성과를 평가해 주세요"

**명확화:** "이 기능의 목표가 기존 사용자 참여도 향상인지, 신규 유입 증가인지 확인하겠습니다. 기능을 활성화한 사용자와 그렇지 않은 사용자가 구분되어 있습니까?"

**지표:** 북극성 = 기능 채택률 (7일 내 2회 이상 사용), 보조 = 기능 사용 후 세션 길이, 가드레일 = 전체 DAU

**가설:**
1. 제품: 기능이 핵심 사용자층에게 유용해 채택률이 높음
2. 외부: 기능 관련 마케팅 캠페인 효과로 일시적 상승
3. 데이터: 기능 사용 이벤트 로깅이 일부 플랫폼에서 누락

**데이터 계획:**
- 기능 활성화 사용자 vs 비활성화 사용자의 7일 리텐션 비교
- 기능 사용 빈도 분포 (헤비 유저 vs 일회성 사용자)
- 기능 사용 전후 세션 깊이 변화

**결정:** "채택률이 15% 이상이고 기능 사용자의 7일 리텐션이 비사용자보다 12% 높다면 성공적인 출시로 판단합니다. 기능을 인지하지 못한 사용자에게 onboarding 가이드를 노출하는 추가 실험을 제안하겠습니다."

### 케이스 D: "결제 전환율이 2주째 하락 중입니다"

**명확화:** "결제 전환율의 분모가 상품 상세 페이지 조회인가요, 장바구니 담기인가요? iOS와 Android 모두 같은 패턴인가요? 결제 방식 변경이 있었나요?"

**지표:** 북극성 = 결제 전환율(결제완료/상품상세조회), 보조 = 각 퍼널 단계별 이탈률, 가드레일 = 앱 오류 로그 수

**가설:**
1. 제품: 결제 페이지 UI 개편으로 사용성 저하
2. 외부: 특정 결제 수단 오류 발생 (PG사 이슈)
3. 데이터: 결제 완료 이벤트 로깅 오류로 과소 집계

**데이터 계획:**
- 단계별 이탈 퍼널: 상품 상세 → 장바구니 → 결제 정보 입력 → 결제 완료
- 결제 수단별 성공/실패율 비교
- 2주 전 대비 단계별 이탈률 변화 비교

**결정:** "장바구니에서 결제 정보 입력 단계 이탈이 집중되어 있고, 신용카드 실패율이 3배 증가했습니다. PG사 장애 이력을 확인하고, 대체 결제 수단 우선 노출 A/B 테스트를 즉시 진행하겠습니다."

## 채용 공고 기반 모의 케이스

공고에 자주 등장하는 문구를 케이스 질문으로 바꾸는 연습이 효과적입니다.

| 공고 문장 | 모의 케이스 질문 | 필수 답변 요소 |
| --- | --- | --- |
| "리텐션 개선을 위한 데이터 분석" | "월간 리텐션이 하락했을 때 무엇부터 확인하겠습니까?" | 세그먼트 분해, 코호트 기준, 이벤트 정의 |
| "신규 기능 성과 측정" | "출시 2주 후 성과를 어떻게 판단하겠습니까?" | 북극성 + 가드레일 + 기간 설정 |
| "마케팅 효율 최적화" | "CAC가 상승했을 때 어떤 가설을 세우겠습니까?" | 채널별 가설, 실험 가능성, 의사결정 조건 |
| "사용자 경험 데이터 분석" | "체류 시간이 증가했는데 결제 전환율은 하락했습니다. 왜 그럴까요?" | 트레이드오프 분석, 콘텐츠 vs 구매 여정 분리 |

## 자주 하는 실수

| 실수 유형 | 구체적 사례 | 개선 방향 |
| --- | --- | --- |
| 질문 듣자마자 바로 답함 | 명확화 없이 아이디어부터 쏟아냄 | 30초 명확화 질문 2-3개를 먼저 습관화 |
| 지표 정의 없이 진행 | "리텐션이 떨어졌으니..."라고 말하는데 리텐션 정의가 없음 | 지표 분자/분모를 먼저 합의 |
| 가설 하나만 세움 | "아마 제품 버그일 것입니다"로 끝냄 | 제품/외부/데이터 세 카테고리 가설 병렬 제시 |
| 데이터 계획이 추상적 | "데이터를 확인하겠습니다"로만 말함 | 어떤 테이블, 어떤 기간, 어떤 비교를 구체적으로 설명 |
| 결론 없이 끝남 | 분석을 나열하다가 시간이 끝남 | 마지막에 반드시 "저는 A를 권고합니다. 이유는..."으로 마무리 |
| 가드레일 지표 없음 | 북극성만 말하고 무너지면 안 되는 지표를 빠뜨림 | 추천 액션의 부작용을 측정할 가드레일 지표를 항상 포함 |

## 협업 맥락과 케이스 연결

케이스 인터뷰에서는 개인 분석 역량뿐 아니라 팀 안에서 이 문제를 어떻게 풀 수 있는지도 봅니다.

| 팀 구조 | 케이스 답변 포인트 |
| --- | --- |
| 중앙집중형 데이터 조직 | "요청 우선순위를 어떻게 정렬하겠습니까?" |
| 임베디드형 (제품팀 내) | "제품 회의에서 데이터 기반 결정을 어떻게 이끌겠습니까?" |
| 하이브리드형 | "공통 지표 정의와 팀별 실험 속도를 어떻게 균형 잡겠습니까?" |

면접에서 "협업"을 말할 때 추상적으로 "소통을 잘합니다"라고 답하면 약합니다. 대신 "중앙팀과 제품팀의 지표 정의가 어긋날 수 있어 먼저 metric spec을 합의하겠습니다"처럼 구조 기반으로 답해야 신뢰가 생깁니다.

**협업 시나리오별 구체적 답변 예시:**

상황: "분석 결과를 PM에게 설명해야 하는데, PM은 통계에 익숙하지 않습니다."

약한 답변: "쉽게 설명하겠습니다."

강한 답변: "p-value나 신뢰구간 대신 'A 방식을 쓴 사용자 10명 중 6명이 7일 내 재방문했고, B 방식은 4명이었습니다. 이 차이가 우연일 확률이 5% 이하입니다'처럼 구체적인 숫자와 행동으로 설명합니다. 그리고 '그래서 A 방식을 모든 사용자에게 적용하면 월 리텐션이 X% 개선될 것으로 예상합니다'처럼 의사결정 형태로 마무리합니다."

## 케이스 인터뷰 준비 루틴

케이스 인터뷰는 반복 연습 없이는 개선이 어렵습니다. 아래 루틴을 2-3주 반복하면 답변 구조가 자동화됩니다.

| 주차 | 연습 방법 | 목표 |
| --- | --- | --- |
| 1주차 | 채용 공고 문장을 케이스 질문으로 변환해 혼자 답변 | 5단계 프레임 익히기 |
| 2주차 | 타이머 10분 + 녹음 후 자기 평가 | 논리 흐름과 시간 배분 점검 |
| 3주차 | 동료 또는 스터디 파트너와 모의 면접 | 면접관의 질문에 실시간 대응 연습 |
| 인터뷰 전날 | 자주 나오는 케이스 3가지 (DAU 하락, 취소율 증가, 신기능 평가)를 빠르게 복습 | 패턴 상기 |

**혼자 연습할 때 자기 평가 체크리스트:**

답변을 녹음하고 다음 항목을 확인합니다.

- [ ] 명확화 질문을 2개 이상 했는가
- [ ] 지표를 분자/분모로 명확히 정의했는가
- [ ] 가설을 세 가지 카테고리로 나눠 제시했는가
- [ ] 데이터 계획에서 구체적인 비교 방법을 말했는가
- [ ] 가드레일 지표를 포함한 결정 제안으로 마무리했는가
- [ ] 10분 내에 완료했는가

## 처음 질문으로 돌아가기

- **케이스 인터뷰가 실제로 무엇을 평가하는가**
  - 모호한 문제를 구조화하는 능력, 지표 정의, 다양한 가설 수립, 실행 가능한 결론을 내리는 능력을 평가합니다. 아이디어의 양보다 사고의 일관성이 중요합니다.
- **문제를 들었을 때 왜 먼저 명확화 질문을 해야 하는가**
  - 잘못 정의된 문제를 풀면 아무리 정교한 분석도 의미가 없습니다. 명확화 질문으로 범위와 기준을 합의하면 이후 모든 단계가 더 효율적이 됩니다.
- **북극성 지표와 보조 지표를 어떻게 고르는가**
  - 북극성은 제품의 핵심 가치를 나타내는 하나의 지표이고, 보조 지표는 이를 세분화해 원인을 찾는 도구입니다. 가드레일 지표는 북극성 개선 과정에서 무너지면 안 되는 한계선입니다.
- **면접에서 자주 나오는 케이스 유형과 답변 구조는 무엇인가**
  - DAU 하락 진단, 전환율 이슈, 기능 성과 측정, 취소율 증가가 대표 유형입니다. 명확화 → 지표 → 가설 → 데이터 → 결정 순서를 지키면 됩니다.
- **팀 구조와 협업 맥락을 케이스 답변에 어떻게 연결하는가**
  - 같은 분석이라도 팀 구조에 따라 실행 가능성이 다릅니다. 중앙집중형과 임베디드형에서 우선순위 정렬 방식이 다르다는 점을 답변에 반영하면 설득력이 높아집니다.

## 연습 문제

1. 아래 케이스 중 하나를 골라 10분 안에 5단계 답변을 작성해 보세요.
   - "이커머스 앱의 일평균 주문 건수가 지난 3일간 15% 하락했습니다."
   - "구독 서비스의 월간 취소율이 전분기 대비 2%p 증가했습니다."
   - "새로운 검색 기능을 출시한 뒤 검색 클릭률이 상승했지만 구매 전환율은 변화가 없습니다."

2. 작성한 답변을 녹음하고, 자기 평가 체크리스트로 평가해 보세요. 가장 약한 단계는 어디인가요?

3. 가드레일 지표를 포함하지 않은 기존 답변을 하나 골라 가드레일 지표를 추가해 다시 작성해 보세요.

4. "명확화 질문을 너무 많이 하는 것"의 위험성과 "너무 적게 하는 것"의 위험성을 각각 한 문장으로 설명해 보세요.

5. 자신이 지원하려는 회사의 서비스에서 케이스 문제를 직접 만들어 보세요. (예: "이 앱의 핵심 지표는 무엇이고, 그것이 10% 하락했다면 어떻게 접근하겠는가?")

## 면접 당일 케이스 답변 실전 팁

준비가 잘 된 지원자도 당일에 실수하는 패턴이 있습니다.

**패턴 1 — 문제를 듣자마자 분석부터 시작**
"그 전에 먼저 몇 가지 여쭤봐도 될까요?"라고 묻는 것을 면접관은 오히려 높이 평가합니다. 2-3개의 명확화 질문이 분석의 방향을 바꿉니다.

**패턴 2 — 모든 가설을 같은 중요도로 나열**
가설을 제시할 때 "가장 가능성이 높다고 생각하는 것부터 말씀드리겠습니다"라고 우선순위를 앞에 두세요. 순서 있는 가설이 순서 없는 가설보다 훨씬 설득력 있습니다.

**패턴 3 — 결론 없이 분석만 길게**
시간이 부족하면 "지금까지 논의를 바탕으로 결론을 먼저 드리겠습니다"라고 전환하세요. 분석이 아무리 좋아도 결론 없이 끝나면 불완전한 답변입니다.

**패턴 4 — 불확실성을 숨기는 답변**
모르는 데이터가 있을 때 "이 데이터가 있다면 확인하겠지만 현재는 가정으로 진행하겠습니다"라고 명시하는 것이 더 신뢰감을 줍니다.

## 운영 체크리스트

- [ ] 명확화 질문 세 가지를 준비했다
- [ ] 북극성 지표와 가드레일 지표를 구분할 수 있다
- [ ] 서로 다른 성격의 가설 세 가지를 세울 수 있다
- [ ] 추천 액션과 후속 측정 계획까지 말할 수 있다
- [ ] 채용 공고 기반 모의 케이스를 최소 3개 연습했다
- [ ] DAU 하락, 취소율 증가, 신기능 평가 세 시나리오를 완성했다
- [ ] 10분 내에 5단계 프레임을 완주하는 연습을 했다
- [ ] 자기 평가 체크리스트로 녹음 답변을 평가해 봤다
- [ ] 면접 당일 실수 패턴 4가지를 인지하고 있다

## 정리

케이스 인터뷰는 숫자를 많이 아는 사람보다, 애매한 상황을 구조화할 줄 아는 사람에게 유리합니다. 문제를 명확히 하고, 지표를 정하고, 가설과 데이터 계획을 세운 뒤, 마지막에 결정을 내려야 답변이 완성됩니다. 이 다섯 단계를 반복 연습하면 낯선 도메인에서도 안정적으로 답변할 수 있습니다. 가드레일 지표까지 정의하는 습관을 만들면 "이 사람은 부작용도 생각한다"는 인상을 남길 수 있습니다.

다음 글에서는 첫 데이터 직무에 들어간 뒤 90일 동안 무엇을 먼저 해야 하는지 봅니다.
