# Data Science Career 101 (6/10): ML 인터뷰

머신러닝 인터뷰를 처음 준비할 때는 보통 모델 이름과 알고리즘 개념부터 외우기 시작합니다. Random Forest, XGBoost, Logistic Regression, Precision, Recall 같은 키워드는 익숙해지지만, 막상 면접에서 "이 문제에서는 왜 이 지표를 보겠는가?"라는 질문이 나오면 답변이 급격히 얕아지기 쉽습니다.

실무 인터뷰는 모델 암기보다 판단 구조를 더 많이 봅니다. 어떤 문제를 풀고 있는지, 데이터 누수나 드리프트 같은 운영 함정을 알고 있는지, 그리고 모델을 서비스 안에서 어떻게 모니터링할지를 연결해 말할 수 있어야 깊이가 드러납니다.

이 글은 Data Science Career 101 시리즈의 여섯 번째 글입니다.

![Data Science Career 101 6장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/data-science-career-101/06/06-01-concept-at-a-glance.ko.png)
*Data Science Career 101 6장 흐름 개요*

> ML 인터뷰에서 가장 중요한 것은 모델 이름이 아니라 "문제 → 지표 → 모델 → 운영" 흐름을 하나로 연결해 말하는 능력입니다.

## 이 글에서 다룰 문제

- ML 인터뷰가 실제로 어떤 영역을 평가하는가
- 모델 선택을 설명할 때 무엇을 먼저 말해야 하는가
- 평가 지표를 문제 정의와 함께 봐야 하는 이유는 무엇인가
- 데이터 누수, 불균형, 드리프트 같은 운영 함정에 어떻게 답하는가
- 도메인별로 ML 접근이 어떻게 달라지는가

## ML 인터뷰의 평가 영역

ML 인터뷰는 크게 네 영역으로 나뉩니다.

| 영역 | 핵심 질문 | 예시 질문 |
| --- | --- | --- |
| 기초 개념 | 알고리즘 원리, bias-variance 이해 | "오버피팅을 어떻게 줄이겠습니까?" |
| 모델 선택 | 문제 유형에 맞는 판단 근거 | "왜 트리 계열이 아니라 선형 모델을 골랐는가?" |
| 평가 지표 | 지표 선택 이유와 트레이드오프 | "Precision과 Recall 중 무엇을 우선하겠습니까?" |
| 운영/배포 | 누수, 드리프트, 재학습 계획 | "배포 후 성능이 떨어지면 어떻게 대응하겠습니까?" |

입문 단계에서는 기초 개념과 지표에 집중하는 경우가 많지만, 시니어급 면접에서는 운영 관점이 더 큰 비중을 차지합니다.

## 기초 개념 핵심 정리

**bias-variance tradeoff:**

```text
High Bias (과소적합): 모델이 너무 단순해서 학습 데이터도 잘 못 맞춤
High Variance (과적합): 학습 데이터는 잘 맞추지만 새 데이터에는 약함
목표: 검증 세트 성능이 최대인 지점 찾기
```

**한 줄 설명 연습:**
- 오버피팅: "학습 데이터를 너무 외워서 새 데이터에는 일반화가 안 되는 상태입니다"
- 드리프트: "모델 학습 시점과 서빙 시점의 데이터 분포가 달라지는 현상입니다"
- 데이터 누수: "학습 시 미래 정보가 피처에 섞여 실제 환경에서 성능이 과대 추정되는 문제입니다"

## 모델 선택 논리

면접에서 "어떤 모델을 쓰겠습니까?"라는 질문에 모델 이름만 답하면 약합니다. 판단 기준을 먼저 말해야 합니다.

**모델 선택 순서:**

```text
1) 문제 유형: 분류인가 회귀인가 순위 예측인가
2) 데이터 크기: 소규모 정형 데이터인가 대규모 비정형인가
3) 해석 가능성: 모델 결과를 설명해야 하는가 (금융/의료)
4) 지연 요구사항: 실시간 응답이 필요한가 배치 처리인가
5) 기준선 먼저: 단순 모델로 기준선을 설정한 뒤 복잡도를 높임
```

**실제 답변 예시:**

"이탈 예측 문제라면 먼저 로지스틱 회귀로 기준선을 만들고, 피처 중요도가 해석 가능한 형태를 확인한 뒤, XGBoost로 성능을 개선하는 순서를 택하겠습니다. 금융 리스크 심사에 쓰일 경우 감사 가능성이 필요해서 트리 계열보다 선형 모델이 더 적합할 수 있습니다."

## 평가 지표 선택 근거

```python
# 지표 선택은 문제 비용 구조에서 시작합니다
from sklearn.metrics import precision_score, recall_score, roc_auc_score, average_precision_score

# 불균형 데이터에서는 PR-AUC가 ROC-AUC보다 더 신뢰할 수 있습니다
```

**지표 선택 기준표:**

| 문제 상황 | 우선 지표 | 이유 |
| --- | --- | --- |
| 사기 거래 탐지 | Recall (재현율) | 미탐(FN) 비용이 매우 큼 |
| 스팸 메일 필터 | Precision (정밀도) | 오탐(FP)으로 정상 메일 차단 시 피해 큼 |
| 의료 진단 보조 | Recall + 안전 절차 | 미탐이 생명 위험으로 이어질 수 있음 |
| 추천 시스템 | NDCG, Precision@K | 상위 K개 추천 품질이 핵심 |
| 이탈 예측 | PR-AUC | 양성 클래스가 불균형인 경우 |

**면접 답변 패턴:**

"이 문제에서는 [상황]이라 [지표]를 우선하겠습니다. 다만 [반대 지표]가 너무 낮아지면 [부작용]이 발생하므로 [임계값]을 함께 모니터링하겠습니다."

## 운영 환경 함정 3가지

### 함정 1 — 데이터 누수 (Data Leakage)

미래 정보가 피처에 포함되어 오프라인 성능이 과대 추정되는 문제입니다.

**실제 시나리오:** 이탈 예측 모델을 만들 때 "마지막 로그인 날짜"를 피처로 포함했습니다. 그런데 이 컬럼이 이탈 레이블 정의와 같은 기간을 참조하면 누수가 됩니다. 오프라인에서는 98% 정확도인데 실제 서비스에서는 50% 정도로 떨어지는 원인이 됩니다.

**방지 방법:** 피처 생성 시점을 예측 기준 시점보다 이전 데이터로만 제한하고, 학습/검증 분리를 시간 기반으로 수행합니다.

### 함정 2 — 클래스 불균형 (Class Imbalance)

양성 클래스가 전체의 1-5%인 경우 Accuracy가 무의미해집니다.

**잘못된 답변:** "정확도가 97%라 좋습니다." (전부 음성으로 예측해도 97%가 나오는 상황)

**좋은 답변:** "불균형 데이터라 Accuracy 대신 PR-AUC로 평가하겠습니다. 클래스 가중치를 조정하거나 SMOTE로 오버샘플링해 학습 불안정을 줄이겠습니다."

### 함정 3 — 드리프트 (Data Drift)

배포 후 시간이 지나면서 입력 데이터 분포가 학습 시점과 달라지는 현상입니다.

**실제 시나리오:** 코로나 이전 사용자 행동 패턴으로 학습한 추천 모델이 팬데믹 이후 완전히 다른 패턴에서 성능이 급락했습니다.

**대응 전략:**

```text
- 피처 분포 통계 모니터링 (평균, 분산, 최솟값/최댓값 이상 탐지)
- 예측 분포 모니터링 (양성 예측 비율의 급격한 변화)
- 재학습 트리거 정의 (성능 지표가 X% 이하로 떨어지면 재학습)
```

## 실제 인터뷰 시나리오

**시나리오:** 커머스 회사 DS 면접에서 "사용자 이탈 예측 모델을 만들어 보세요"라는 질문을 받았습니다.

**좋은 답변 흐름:**

```text
1) 문제 정의: "이탈을 '30일 이상 미접속'으로 정의하겠습니다. 예측 시점은 마지막 접속 14일 이후로 하겠습니다."

2) 레이블 및 피처: "레이블은 30일 기준 이탈 여부이고, 피처는 최근 7/14일 접속 빈도, 구매 횟수, 마지막 구매 후 경과일, 가입 채널 등을 사용하겠습니다."

3) 기준선 → 개선: "먼저 로지스틱 회귀로 기준선을 만들고 PR-AUC를 확인한 뒤, XGBoost로 성능 개선을 시도하겠습니다."

4) 평가: "클래스 불균형이 예상되므로 PR-AUC를 주 지표로 쓰겠습니다. 상위 X% 위험군에게 쿠폰을 발송하는 방식으로 실제 ROI를 계산할 수 있습니다."

5) 운영: "배포 후 주간 단위로 피처 분포와 예측 분포를 모니터링하고, PR-AUC가 기준 이하로 떨어지면 재학습을 트리거하겠습니다."
```

## 도메인별 ML 접근 차이

| 도메인 | 우선 지표 | 주요 리스크 | 특별 고려사항 |
| --- | --- | --- | --- |
| 금융 (사기 탐지) | Recall, 손실 비용 | 오탐 비용, 규제 준수 | 모델 설명 가능성, 감사 추적 |
| 헬스케어 (진단 보조) | Recall, 민감도 | 미탐이 생명 위험 | 보수적 임계값, 임상 검토 절차 |
| 커머스 (추천) | CTR, 전환율, Precision@K | 인기 편향, 필터 버블 | 탐색-활용 균형, 실험 반복 |
| SaaS (이탈 예측) | PR-AUC, Recall | 드리프트, 계절성 | 코호트 기반 평가, 재학습 주기 |

금융 도메인에서는 모델 성능보다 "왜 이 예측이 나왔는가"를 설명할 수 있어야 합니다. 헬스케어에서는 미탐 비용이 극단적으로 크기 때문에 Recall을 극대화하는 방향이 기본 설정입니다. 커머스는 빠른 실험 반복이 핵심 경쟁력입니다.

## 자주 하는 실수

| 실수 유형 | 구체적 사례 | 개선 방향 |
| --- | --- | --- |
| 모든 문제에 같은 모델 답변 | "Random Forest를 쓰겠습니다"만 반복 | 문제 유형, 데이터 크기, 해석 가능성 기준 먼저 설명 |
| AUC만 보고 끝냄 | 불균형 데이터에서도 ROC-AUC만 언급 | PR-AUC와 임계값 전략 함께 제시 |
| 데이터 누수를 모름 | 오프라인 성능이 이상할 정도로 높을 때 원인을 못 찾음 | 피처 생성 시점과 레이블 기준 시점을 항상 확인 |
| 배포 후 계획 없음 | 모델 만들면 끝이라고 생각 | 재학습 주기, 드리프트 탐지, 롤백 절차까지 말함 |
| 기준선 없이 모델부터 | XGBoost부터 시작하고 기준선과 비교 안 함 | 단순 모델 기준선을 먼저 설정하는 습관 형성 |

## 모델 운영 체크리스트

면접에서 "배포 이후 어떻게 관리하겠습니까?"라는 질문에 대한 체계적 답변:

```text
- 입력 데이터 스키마 검증 규칙이 있는가
- 학습/서빙 피처 변환 로직이 동일한가
- 배포 버전 롤백 절차가 있는가
- 성능 저하 알림 임계값이 정의되어 있는가
- 재학습 트리거 기준이 명시되어 있는가
- 장애 발생 시 온콜 담당자와 대응 시간이 있는가
```

이 체크리스트를 실제 프로젝트에 적용한 경험이 있으면 "모델을 만든 사람"이 아니라 "모델을 운영한 사람"으로 인식됩니다.

## 처음 질문으로 돌아가기

- **ML 인터뷰가 실제로 어떤 영역을 평가하는가**
  - 기초 개념, 모델 선택 근거, 평가 지표 선택 이유, 운영 함정 대응 능력 네 가지를 종합적으로 평가합니다.
- **모델 선택을 설명할 때 무엇을 먼저 말해야 하는가**
  - 문제 유형, 데이터 크기, 해석 가능성 요구, 지연 시간 제약 순서로 판단 기준을 먼저 말한 뒤 모델 이름을 언급해야 합니다.
- **평가 지표를 문제 정의와 함께 봐야 하는 이유는 무엇인가**
  - 같은 이탈 예측이라도 미탐 비용이 크면 Recall을, 오탐 비용이 크면 Precision을 우선해야 합니다. 지표 선택은 비용 구조에서 나옵니다.
- **데이터 누수, 불균형, 드리프트 같은 운영 함정에 어떻게 답하는가**
  - 각 함정의 증상과 원인을 알고, 방지 또는 대응 방법을 구체적으로 말할 수 있어야 합니다. 함정을 먼저 언급하는 것 자체가 실무 감각 신호입니다.
- **도메인별로 ML 접근이 어떻게 달라지는가**
  - 금융은 설명 가능성, 헬스케어는 안전성 우선, 커머스는 실험 속도가 핵심입니다. 같은 알고리즘도 도메인에 따라 판단 기준이 달라집니다.

## 운영 체크리스트

- [ ] 주요 평가 지표 다섯 개를 언제 쓰는지 설명할 수 있다
- [ ] 서로 다른 모델 세 가지를 선택 기준과 함께 비교할 수 있다
- [ ] 데이터 누수, 불균형, 드리프트 세 가지 함정을 말할 수 있다
- [ ] 배포 후 모니터링 계획을 포함한 ML 시스템 흐름을 설명할 수 있다
- [ ] 이탈 예측 시나리오를 처음부터 끝까지 연습해 봤다

## 정리

ML 인터뷰에서 중요한 것은 모델 이름을 많이 아는 일이 아니라, 문제와 지표와 운영 리스크를 함께 묶어 설명하는 일입니다. 기준선부터 시작해, 지표 선택 이유를 말하고, 운영 함정을 먼저 언급하고, 배포 이후 계획까지 연결해야 답변이 완성됩니다.

다음 글에서는 제품 감각과 사고 구조를 많이 보는 케이스 인터뷰를 다루겠습니다.
