# Data Science Career 101 (8/10): 첫 직장 적응

첫 데이터 직무에 합류하면 대부분은 기술보다 속도에서 압박을 느낍니다. 빨리 성과를 보여 줘야 할 것 같고, 아는 것이 부족하다는 사실이 더 크게 보이기 때문입니다. 그래서 데이터 지도도 없이 대시보드 수정이나 티켓 처리부터 반복하다가, 정작 중요한 맥락은 놓치는 경우가 많습니다.

하지만 첫 90일의 핵심은 존재감을 과시하는 데 있지 않습니다. 어떤 데이터가 어디서 오고, 누가 무엇을 중요하게 보고, 작은 신뢰를 어디서 만들 수 있는지 읽는 데 있습니다. 초반에 이 지도를 그려 두면 이후 제안의 방향도 훨씬 안정적이 됩니다.

이 글은 Data Science Career 101 시리즈의 여덟 번째 글입니다.

![Data Science Career 101 8장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/data-science-career-101/08/08-01-concept-at-a-glance.ko.png)
*Data Science Career 101 8장 흐름 개요*
> 첫 직장 적응에서 가장 중요한 것은 무엇을 할 수 있는가가 아니라 무엇을 물어봐야 하고 어떻게 답해야 하는가입니다.

## 이 글에서 다룰 문제

- 첫 90일을 어떤 단계로 나눠야 하는가
- 초반에 무엇을 듣고 기록해야 하는가
- 데이터 지도와 이해관계자를 왜 빨리 파악해야 하는가

## 이 글에서 배우는 내용

- 30/60/90 온보딩 구간
- 데이터 지도 그리기
- 이해관계자 파악
- 빠른 성과 만들기
- 문서화 습관

첫 90일은 평판의 씨앗이 심어지는 시기입니다. 이 시기에 무엇을 듣고, 무엇을 남기고, 어디에서 작은 성과를 만들었는지가 이후의 속도를 크게 바꿉니다.

특히 데이터 직무는 문맥 의존성이 높아서, 도메인과 데이터 출처를 모른 채 기술만 앞세우면 방향이 쉽게 어긋납니다. 반대로 이해관계자와 데이터 지도를 먼저 정리하면 작은 개선도 훨씬 더 적절한 문제를 겨냥하게 됩니다.

- **data map**: 데이터 소스와 쓰임새를 정리한 지도입니다.
- **stakeholder**: 내 작업의 영향을 받거나 방향을 정하는 사람입니다.
- **quick win**: 초기에 만들 수 있는 작지만 분명한 성과입니다.
- **decision log**: 결정과 근거를 남기는 기록입니다.

## 온보딩 시나리오 1 — DA 직무, 스타트업 합류 첫 달

민지는 커머스 스타트업에 DA로 합류했습니다. 첫 주에 팀장이 "MAU가 떨어지고 있으니 빨리 원인을 찾아봐"라고 말했습니다.

민지는 바로 분석에 뛰어들지 않았습니다. 대신 3가지를 먼저 확인했습니다. 첫째, MAU 정의가 팀마다 달랐습니다. 마케팅 팀은 앱 설치 기준, 제품 팀은 실제 주문 기준을 쓰고 있었습니다. 둘째, 데이터 소스가 Mixpanel, BigQuery, 수동 스프레드시트 세 군데였습니다. 셋째, 최근 2주간 프로모션 변경과 배송 정책 개편이 동시에 있었습니다.

민지는 이 맥락을 정리한 1페이지 데이터 지도를 작성하고, MAU 계산 기준을 팀 간에 통일하는 것을 첫 번째 산출물로 제안했습니다. 팀장은 "분석보다 이게 더 급했다"고 말했습니다.

이것이 첫 달 온보딩의 핵심입니다. 빠른 답보다 정확한 질문이 더 오래 남습니다.

## 온보딩 시나리오 2 — DE 직무, 중견기업 합류 60일차

재현은 물류 회사의 DE로 합류했습니다. 60일차에 팀장이 "배치 파이프라인이 매주 월요일 실패한다"는 티켓을 줬습니다.

재현은 로그를 분석하기 전에 이해관계자 지도를 그렸습니다. 데이터 공급자(ERP 팀), 데이터 소비자(BI 팀), 운영 담당자(인프라 팀)를 구분했습니다. 그 결과 월요일에만 ERP 배치 작업이 집중 실행돼 API 응답이 느려진다는 사실을 발견했습니다. 일정을 조정하는 것만으로 문제가 해결됐지만, 재현이 이 과정을 문서화해 두었기 때문에 3달 후 비슷한 문제가 생겼을 때 새 팀원이 혼자 해결할 수 있었습니다.

이해관계자를 빨리 파악하면 기술 문제의 진짜 원인도 더 빨리 보입니다.

## 전후 비교

**Before**: "들어가자마자 티켓만 빨리 처리하면 된다고 생각했다."

**After**: "지도와 관계와 지표와 문서를 남기는 일이 적응의 핵심이라는 점을 이해했다."

## 30/60/90일 온보딩 프레임

### 0-30일차: 경청하기

첫 한 달은 가능한 한 많이 듣는 편이 좋습니다. 팀이 중요하게 보는 문제와 데이터 소스를 파악해야 이후 제안의 품질이 달라집니다.

```text
- 이해관계자 1:1 미팅 10건
- 데이터 소스 목록 초안 작성
- 팀이 자주 보는 대시보드 5개 파악
- 반복되는 용어와 지표 용어집 작성
```

첫 달 체크리스트:

| 항목 | 완료 기준 |
| --- | --- |
| 팀 내 주요 이해관계자 3명 이상 1:1 완료 | 메모와 핵심 관심사 정리 |
| 데이터 소스 최소 5개 목록화 | 소유자, 갱신 주기, 사용 용도 포함 |
| 핵심 KPI 3개 이상 정의 확인 | 계산식과 사용 팀 명시 |
| 온보딩 질문 30개 이상 기록 | 답을 모르면 모른다고 기록 |

### 31-60일차: 빠른 성과 만들기

작은 승리는 신뢰의 출발점입니다. 거창한 변화보다 팀이 바로 체감할 수 있는 개선이 훨씬 효과적입니다.

```text
- 독립 분석 또는 모델 PoC 1건
- SQL 쿼리 최적화 또는 반복 작업 개선 1건
```

31-60일차 quick win 후보 예시:

| 유형 | 예시 | 신뢰 신호 |
| --- | --- | --- |
| 데이터 정의 통일 | 지표 정의 불일치 발견 및 정리 | "이 팀원이 질문을 잘 잡는다" |
| 반복 쿼리 단순화 | 30줄 쿼리를 10줄로 리팩터 | "실무 감각이 있다" |
| 대시보드 개선 | 잘못된 필터 수정 또는 지표 추가 | "작은 것도 정확히 잡는다" |
| 문서 공백 메우기 | 없던 데이터 소스 README 작성 | "문서를 남기는 사람" |

### 61-90일차: 제안하기

이 단계부터는 제안이 필요합니다. 아이디어만 말하지 말고 무엇을 어떻게 측정할지까지 붙여야 설득력이 생깁니다.

```text
- 분기 제안 항목 1건 (측정 계획 포함)
- 반복 업무 개선 제안 또는 자동화 초안
```

좋은 제안 구조:

```text
[관찰] 현재 어떤 문제가 있는가
[가설] 왜 그렇다고 보는가
[제안] 무엇을 바꾸면 좋은가
[측정] 어떻게 효과를 확인할 것인가
[리스크] 잘못될 경우 어떻게 대응할 것인가
```

## 데이터 지도 작성 가이드

데이터 지도는 개인 메모가 아니라 팀 자산입니다. 누가 소유자인지, 얼마나 자주 갱신되는지, 어디에 쓰이는지 정리해 두면 반복 질문이 크게 줄어듭니다.

```markdown
| 소스 이름 | 소유 팀 | 갱신 주기 | 주요 사용처 | 주의 사항 |
| --- | --- | --- | --- | --- |
| orders_raw | 데이터 플랫폼 | 1시간 | 매출 대시보드 | 취소 건 포함, 정제 필요 |
| user_events | 제품 팀 | 실시간 | 퍼널 분석 | 앱 버전별 스키마 차이 있음 |
| marketing_spend | 마케팅 팀 | 주 1회 수동 | CAC 계산 | 수동 업로드, 누락 위험 |
```

데이터 지도를 처음 만들 때 완벽하려 하지 않아도 됩니다. 5개 소스로 시작해 팀에 공유하면 동료들이 빠진 항목을 채워 줍니다. 이 과정 자체가 신뢰 구축입니다.

## 이해관계자 맵 작성 가이드

이해관계자 맵은 "누구에게 물어봐야 하는가"를 빠르게 파악하는 도구입니다.

| 관계 유형 | 예시 역할 | 주요 관심사 | 소통 방식 |
| --- | --- | --- | --- |
| 데이터 공급자 | 백엔드, 인프라 팀 | 파이프라인 안정성 | 슬랙, 스프린트 미팅 |
| 데이터 소비자 | 마케팅, 제품 팀 | 정확한 숫자, 속도 | 대시보드 공유, 주간 리포트 |
| 의사결정자 | 팀장, PM | 비즈니스 영향 | 1페이지 요약, 분기 보고 |
| 협업 파트너 | 다른 DA/DS | 방법론, 정의 통일 | 페어 리뷰, 코드 리뷰 |

이해관계자를 파악하는 가장 좋은 방법은 첫 달에 이 맵을 작성하고, 30일차에 팀장에게 "제가 놓친 사람이 있나요?"라고 물어보는 것입니다.

## 결정 로그 템플릿

결정 기록은 초반일수록 중요합니다. 맥락을 복원하기 쉽고, 협업 상대와의 인식 차이도 줄여 줍니다.

```markdown
## 결정 제목
날짜: YYYY-MM-DD
의사결정자:

### 결정 내용
무엇을 결정했는가

### 배경
왜 이 결정이 필요했는가

### 검토한 대안
1. 대안 A: 장점 / 단점
2. 대안 B: 장점 / 단점

### 선택 근거
왜 현재 결정을 선택했는가

### 예상 영향
이 결정이 만들어낼 결과

### 재검토 기준
언제 이 결정을 다시 봐야 하는가
```

결정 로그를 쌓으면 6개월 후 "왜 그렇게 했나요?"라는 질문에 즉시 답할 수 있습니다. 이 능력이 신뢰를 높입니다.

## 인터뷰 예시: "온보딩 경험을 말해 주세요"

다음 직장을 위한 면접에서 온보딩 경험을 이야기할 때는 "열심히 했다"가 아니라 구체적인 행동과 결과로 말해야 합니다.

**약한 답변 (피해야 할 패턴)**:
"입사 후 빠르게 적응해 팀에 기여했습니다."

**강한 답변 (권장 패턴)**:
"입사 첫 달에 데이터 소스 8개를 목록화하고, 팀이 서로 다른 MAU 정의를 쓰고 있다는 사실을 발견했습니다. 이를 통일하는 제안서를 만들어 팀 전체 미팅에서 발표했고, 이후 주간 지표 리포트의 숫자 불일치 문제가 사라졌습니다. 그 결과 마케팅 팀과의 협업 속도도 빨라졌습니다."

핵심은 [발견] → [행동] → [결과] 순서로 말하는 것입니다.

## 90일 성과 기록표

| 기간 | 핵심 산출물 | 신뢰 신호 |
| --- | --- | --- |
| 1-30일 | 이해관계자 맵, 데이터 소스 목록, 용어집 초안 | "상황을 빨리 이해한다" |
| 31-60일 | quick win 1건, 분석 메모 1건 | "작은 문제를 닫을 수 있다" |
| 61-90일 | 분기 제안서 1건, 측정 계획 포함 | "앞으로를 설계할 수 있다" |

이 표를 주간 1:1에서 팀장과 공유하면 기대치 정렬이 쉬워집니다. 특히 "이번 주 결과가 다음 단계에 어떤 영향을 주는지"를 함께 점검하면 초반 불안감이 줄고 실행 우선순위가 더 선명해집니다.

## 자주 하는 실수

| 실수 유형 | 구체적 사례 | 개선 방향 |
| --- | --- | --- |
| 첫날부터 큰 제안 밀어붙이기 | 맥락 파악 전에 "이 프로세스를 완전히 바꿔야 한다"고 주장 | 30일 후 데이터 지도 완성 후 제안하기 |
| 이해관계자 무시 | 분석만 완성하고 공유 없이 결과 발표 | 1페이지 요약으로 중간 공유 먼저 하기 |
| 데이터 출처 모른 채 분석 | 정제 전 raw 데이터로 MAU 계산해 틀린 숫자 보고 | 데이터 소스 소유자 확인 후 분석 시작 |
| 대시보드 수정만 반복 | 티켓만 처리하며 전체 맥락 파악 안 함 | 매주 1건 이상 "왜 이 지표인가" 질문 남기기 |
| 문서 남기지 않기 | 구두로만 공유해 3달 후 맥락 사라짐 | 결정할 때마다 결정 로그 1건 작성 |
| 질문을 너무 아끼기 | 모르면서 아는 척하다 2주 뒤 방향 완전히 틀림 | "모른다"를 먼저 말하고 질문 리스트 공유 |

## 시니어는 이렇게 생각합니다

잘 듣는 일도 전략입니다. 첫 달에 질문 30개를 리스트로 만들어 팀장에게 공유하면, 그것만으로 "이 사람은 잘 정리하는 사람"이라는 인식이 생깁니다.

지도는 개인 메모가 아니라 팀 자산입니다. 내가 떠나도 다음 사람이 쓸 수 있게 만들어야 진짜 자산입니다.

작은 승리가 이후 제안의 신뢰를 만듭니다. 대형 분석보다 데이터 정의 하나 통일하는 편이 더 큰 신뢰를 줍니다.

결정 기록은 팀 문화를 만듭니다. 한 사람이 결정 로그를 남기기 시작하면 팀 전체가 따라갑니다.

## 이직 타이밍 판단 기준

첫 직장 적응 이후 이직 타이밍을 고민할 때는 감정이 아니라 기준으로 판단하는 편이 좋습니다.

| 판단 항목 | 이직 신호 | 잔류 신호 |
| --- | --- | --- |
| 학습 곡선 | 6개월간 학습 정체가 지속됨 | 난도 높은 과제가 꾸준히 제공됨 |
| 영향 범위 | 반복 실행만 하고 영향 확대 없음 | 영향 범위가 분기마다 확대됨 |
| 보상 구조 | 시장 대비 과소 보상 | 성장과 보상이 함께 개선됨 |
| 팀 건강도 | 반복적 소모와 불신 | 갈등은 있어도 해결 구조가 있음 |
| 역할 적합도 | 장기 방향과 업무가 불일치 | 장기 목표와 현재 역할이 정렬됨 |

이직 사유를 면접에서 말할 때는 "연봉이 낮아서"만 말하면 약합니다. 대신 "분석 결과가 제품 의사결정까지 연결되는 환경에서 영향 범위를 확장하고 싶습니다"처럼 성장 기준으로 설명하면 설득력이 높습니다.

## 운영 체크리스트

- [ ] 이해관계자 1:1 미팅 10건을 계획했다.
- [ ] 데이터 소스 지도 초안을 만들었다.
- [ ] 첫 번째 quick win 후보를 정했다.
- [ ] 결정 로그 템플릿을 준비했다.
- [ ] 30일 체크인을 팀장과 일정으로 잡았다.

## 정리 및 다음 단계

첫 데이터 직무의 90일은 큰 프로젝트를 단번에 성공시키는 시기가 아닙니다. 팀과 데이터와 사람의 지형을 읽는 시기입니다. 1:1, 데이터 지도, 작은 승리, 문서화라는 네 축을 잘 잡아야 이후 제안과 실행도 안정적으로 붙습니다.

다음 글에서는 기술 역량과는 또 다른 축인 도메인 전문성을 어떻게 쌓을지 봅니다.

## 처음 질문으로 돌아가기

- **첫 90일을 어떤 단계로 나눠야 하는가**
  - 0-30일은 경청과 지도 작성, 31-60일은 quick win 실행, 61-90일은 측정 계획이 포함된 제안 순서로 나눕니다. 각 단계는 신뢰를 하나씩 쌓는 단위로 설계해야 합니다.
- **초반에 무엇을 듣고 기록해야 하는가**
  - 데이터 소스의 소유자와 갱신 주기, 이해관계자의 주요 관심사, 팀이 자주 쓰는 지표 정의를 기록해야 합니다. 특히 정의가 팀마다 다른 경우를 먼저 찾는 것이 중요합니다.
- **데이터 지도와 이해관계자를 왜 빨리 파악해야 하는가**
  - 데이터 출처를 모르고 분석하면 틀린 숫자를 보고할 위험이 있고, 이해관계자를 모르면 제안이 엉뚱한 곳으로 향합니다. 두 가지를 먼저 파악하면 이후 모든 작업의 정확도와 영향력이 올라갑니다.
