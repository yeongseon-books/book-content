# Data Science Career 101 (10/10): 시니어 데이터 직무로 가는 길

시니어로 성장한다는 말을 들으면 많은 사람이 먼저 기술 난도를 떠올립니다. 더 어려운 모델을 다루고, 더 복잡한 파이프라인을 만들고, 더 빨리 문제를 해결하는 모습이 시니어의 전부처럼 보이기 쉽습니다. 물론 그런 역량도 중요하지만, 실제로는 거기서부터 차이가 시작되지는 않습니다.

더 큰 변화는 문제를 보는 관점에서 생깁니다. 무엇을 만들었는지보다 무엇을 바꿨는지, 내가 혼자 잘한 일보다 팀이 더 잘 움직이게 되었는지, 당장 급한 일보다 반복될 문제의 구조를 먼저 잡았는지가 시니어의 행동을 가릅니다.

이 글은 Data Science Career 101 시리즈의 마지막 글입니다.

## 이 글에서 다룰 문제

- 시니어 데이터 직무가 무엇이 다른가
- 문제 정의 능력이 왜 시니어의 핵심 역량인가
- 영향 측정을 어떻게 계획해야 설득력이 생기는가

## 이 글에서 배우는 내용

- 시니어의 정의
- 문제 정의 능력
- 영향 측정
- 동료 증폭
- 시스템 사고

시니어는 직함보다 행동에 가깝습니다. 같은 기술 수준이어도 어떤 문제를 고르고, 어떻게 영향력을 넓히는지에 따라 역할의 무게가 달라집니다.

그래서 시니어 성장은 단순한 기술 숙련의 연장이 아닙니다. 문제 정의, 영향 측정, 문서화, 동료 증폭, 시스템 관점이 함께 붙으면서 같은 기술 역량도 훨씬 더 큰 결과로 이어집니다.

- **scope**: 책임이 미치는 범위입니다.
- **impact**: 결과가 제품과 조직에 미치는 효과입니다.
- **multiplier**: 동료의 성과까지 키우는 증폭 효과입니다.
- **systems thinking**: 끝에서 끝까지 연결해 보는 관점입니다.
- **mentorship**: 동료의 성장을 돕는 활동입니다.

## 시니어 성장 시나리오 1 — DS에서 시니어로: 문제 정의의 전환

수빈은 DS 3년차입니다. 팀장이 "이번 분기에 이탈 예측 모델 성능을 올려 달라"고 요청했습니다.

주니어 때의 수빈이었다면 바로 특성 엔지니어링과 모델 튜닝부터 시작했을 것입니다. 하지만 수빈은 먼저 "이탈 예측 성능을 올리면 어떤 의사결정이 달라지는가?"라고 물었습니다.

대화를 나눠 보니 실제 문제는 다른 곳에 있었습니다. 마케팅 팀은 이탈 예측 점수를 받아도 어떤 고객에게 어떤 오퍼를 줘야 할지 몰랐습니다. 모델이 예측한 위험 점수가 실제 캠페인 기획과 연결되는 프로세스가 빠져 있었던 것입니다.

수빈은 모델 성능 개선 대신 "이탈 위험 고객 세그먼트별 오퍼 매핑 가이드"를 만들었습니다. 마케팅 팀과 2주간 협업해 고위험 세그먼트 3개를 정의하고, 각 세그먼트에 적합한 리텐션 오퍼를 연결했습니다. 그 결과 이탈률이 8% 개선됐습니다. 모델을 튜닝했을 때보다 훨씬 큰 효과였습니다.

이것이 시니어의 문제 정의입니다. 주어진 문제를 바로 해결하기 전에 "이게 진짜 문제인가"를 먼저 묻습니다.

### 수빈이 사용한 문제 재정의 과정

| 단계 | 질문 | 수빈의 답 |
| --- | --- | --- |
| 증상 확인 | 팀장이 원하는 것이 무엇인가 | 이탈 예측 모델 성능 개선 |
| 영향 확인 | 성능이 올라가면 무엇이 달라지는가 | 마케팅 캠페인에 쓰임 |
| 문제 발굴 | 지금 캠페인이 왜 안 되는가 | 점수는 있는데 어떻게 써야 하는지 모름 |
| 문제 재정의 | 진짜 해결해야 할 문제는 무엇인가 | 점수를 실행 가능한 액션으로 연결하는 것 |

## 시니어 성장 시나리오 2 — DE에서 Staff로: 동료 증폭

태형은 DE 4년차로 파이프라인 설계 경험이 풍부했습니다. 팀에 신규 DE 3명이 합류하면서 온보딩 과정에서 같은 질문이 반복됐습니다.

"왜 이 테이블은 이런 구조인가요?", "어떤 상황에서 어떤 레이어에 넣어야 하나요?", "staging 테이블과 mart 테이블의 차이가 뭔가요?"

태형은 개별 질문에 답하는 대신 "데이터 레이어 설계 원칙" 문서를 작성했습니다. 원시 레이어, 정제 레이어, 마트 레이어의 판단 기준, 자주 생기는 실수 5가지, 코드 예시를 포함한 30페이지 가이드였습니다.

이 문서 하나가 팀의 온보딩 속도를 2배 빠르게 만들었습니다. 태형이 없을 때도 신규 팀원이 스스로 판단할 수 있게 됐고, 설계 리뷰 시간이 40% 줄었습니다.

3달 후 팀장은 태형에게 "당신이 만든 문서 덕분에 팀 속도가 유지됐다"고 말했습니다.

Staff 레벨로 가는 길은 "내가 더 빠르게 만드는 것"이 아니라 "팀 전체가 더 빠르게 만들도록 환경을 설계하는 것"입니다.

## 전후 비교

**Before**: "주어진 티켓을 빠르게 끝내는 것이 가장 중요하다고 생각했다."

**After**: "문제를 정의하고, 측정 계획을 붙여 제안하고, 동료 성과까지 키우는 쪽으로 시야를 넓힐 수 있다."

## 시니어의 5가지 행동 원칙

### 1 — 문제 정의하기

```text
증상을 쓰지 말고 문제를 써라.
"대시보드가 느리다" → "특정 시간대 쿼리 타임아웃으로 보고 지연 발생"
```

시니어는 증상과 문제를 구분합니다. 증상을 바로 고치기보다 왜 그런 현상이 생겼는지를 문제 정의 단계에서 분리해 내야 합니다.

문제 정의 템플릿:

```markdown
## 문제 정의
현상: 무엇이 관찰됐는가
영향: 누가 얼마나 영향받는가
원인 가설: 왜 그렇다고 보는가
해결 기준: 무엇이 개선되면 해결된 것인가
측정 방법: 어떻게 확인할 것인가
```

### 2 — 영향도 측정하기

좋은 제안은 실행 전에 이미 측정 계획이 붙어 있습니다. "무엇이 좋아질 것이고, 어떻게 확인할지"까지 말할 수 있어야 설득력이 생깁니다.

```markdown
가설: 이 변경이 무엇을 개선할 것인가
측정 지표: 어떤 지표로 확인할 것인가
측정 기간: 얼마나 오래 볼 것인가
기준 수치: 어느 정도 개선되면 성공인가
결과: 실제 어떻게 바뀌었는가
```

### 3 — 동료 증폭하기

```text
- 월간 1:1 멘토링
- 멘티가 아젠다를 정함
- 코드 리뷰를 교육 기회로 활용
```

시니어는 자기 성과만 내는 사람이 아닙니다. 동료의 성장을 돕는 행동이 팀 전체의 생산성을 올립니다.

좋은 리뷰 코멘트 예시:
- "이렇게 바꿔라" (지시) → "이 방식을 선택한 이유가 있나요? 대안도 같이 고려해 볼 수 있어요." (질문으로 유도)
- "틀렸다" (결과) → "이 케이스에서 어떤 상황이 발생할 수 있을지 생각해 봤나요?" (사고 확장)

### 4 — 결정 기록하기

```markdown
## 결정 로그
결정: 무엇을 결정했는가
대안: 어떤 대안을 검토했는가
근거: 왜 현재 결정을 선택했는가
영향: 이 결정이 만들어낼 결과
재검토 기준: 언제 다시 봐야 하는가
```

의사결정 기록은 단순 메모가 아닙니다. 나중에 맥락을 복원하고 같은 논의를 반복하는 비용을 줄이는 장치입니다. 6개월 후 "왜 그렇게 했나요?"라는 질문에 즉시 답할 수 있는 사람이 신뢰받는 사람입니다.

### 5 — 시스템 사고하기

```text
데이터 수집 → 처리 → 모델/분석 → 의사결정 → 운영 → 회고
```

시니어는 한 부분만 최적화하지 않습니다. 데이터 수집부터 운영과 회고까지 전체 흐름을 보고 병목을 찾습니다.

시스템 관점 질문 예시:
- "이 모델이 운영에 들어가면 모니터링은 어떻게 할 것인가?"
- "데이터가 늦게 들어오면 모델 예측이 어떻게 달라지는가?"
- "이 의사결정 결과를 언제, 어떻게 평가할 것인가?"

## 주니어 vs 시니어 행동 비교

| 상황 | 주니어 행동 | 시니어 행동 |
| --- | --- | --- |
| 모델 성능 요청 받음 | 바로 특성 엔지니어링 시작 | "성능 개선이 어떤 결정을 바꾸나요?" 먼저 묻기 |
| 버그 발견 | 즉시 수정 | 재발 방지 문서 작성 후 수정 |
| 신규 팀원 반복 질문 | 직접 답변 | FAQ 문서 만들어 공유 |
| 프로젝트 완료 | 결과 공유 | 결과 + 한계 + 다음 단계 제안 |
| 우선순위 충돌 | 더 많은 일 처리 | "하지 않을 것" 목록으로 정렬 |
| 분석 요청 | 요청대로 분석 실행 | "이 분석으로 어떤 결정을 내릴 건가요?" 확인 후 실행 |

## 시니어 커리어 래더

시니어로 가는 길은 기술 난이도보다 책임 범위의 확장으로 설명하는 편이 정확합니다.

| 레벨 | 핵심 책임 | 평가 기준 | 자주 하는 말 |
| --- | --- | --- | --- |
| Mid | 맡은 문제를 안정적으로 해결 | 품질, 속도, 재현성 | "이 작업을 완료했습니다" |
| Senior | 모호한 문제를 구조화하고 팀을 정렬 | 의사결정 영향력, 우선순위 설계 | "진짜 문제가 무엇인지 확인했습니다" |
| Staff+ | 조직 단위 기준과 시스템을 설계 | 장기 성과, 팀 생산성 증폭 | "팀 전체가 이 방식으로 일할 수 있게 됐습니다" |

Senior부터 "내가 얼마나 많이 했는가"보다 "팀이 더 잘하게 만들었는가"가 평가 중심으로 이동합니다. 이 전환을 이해하지 못하면 열심히 하는 Mid로 머물 수 있습니다.

## 시니어 승격 준비: 영향력 증거 정리

시니어 승격 준비에서 가장 자주 부족한 것은 역량이 아니라 "증거의 정리 방식"입니다. 일을 많이 했더라도 영향이 구조적으로 정리되어 있지 않으면 평가 시 설득력이 약해집니다.

| 증거 영역 | 정리 질문 | 예시 증거 |
| --- | --- | --- |
| 문제 정의 | 모호한 문제를 어떻게 구조화했는가 | 문제 프레이밍 문서, 대안 비교표 |
| 영향 측정 | 결과가 무엇을 얼마나 바꿨는가 | KPI 전후 비교, 비용/시간 절감 수치 |
| 조직 증폭 | 동료가 더 잘 일하게 만든 행동은 | 리뷰 가이드, 멘토링 기록, 표준 템플릿 |
| 시스템 개선 | 반복 문제를 어떻게 줄였는가 | 운영 자동화, 장애 재발 방지 문서 |

승격은 일회성 발표가 아니라 누적 기록의 결과입니다. 분기마다 위 표를 업데이트하면 연말에 급하게 성과를 모으는 부담이 줄어듭니다. 무엇보다 "내가 잘했다"가 아니라 "팀이 더 좋아졌다"는 증거를 남기는 습관이 시니어 역할 전환을 가장 빠르게 만듭니다.

## 5년 커리어 로드맵

시니어로 가는 길은 한 번의 승진 이벤트가 아니라 5년 단위 누적 전략에 가깝습니다.

| 연차 | 핵심 목표 | 권장 프로젝트 유형 | 학습 초점 | 검증 방식 |
| --- | --- | --- | --- | --- |
| 1년차 | 실행 안정성 확보 | 분석 리포트, 기본 모델, 데이터 정리 | SQL/Python/통계 기초 | 재현 가능한 산출물 3개 |
| 2년차 | 독립 과제 리드 | 실험 분석, 모델 개선, 파이프라인 자동화 | 지표 설계, 실험 해석, 코드 품질 | 분기 단위 오너십 과제 |
| 3년차 | 영향 범위 확장 | 타팀 협업 프로젝트, 도메인 심화 | 커뮤니케이션, 문서화, 도메인 지식 | 의사결정 반영률 상승 |
| 4년차 | 시스템 관점 강화 | 엔드투엔드 개선 과제 | 아키텍처 사고, 운영 안정화 | 성능/비용/속도 동시 개선 |
| 5년차 | 시니어 역할 정착 | 조직 표준화, 멘토링, 전략 과제 | 리더십, 우선순위 설계 | 팀 생산성 증폭 증거 |

학습 계획은 "무엇을 공부할까"보다 "무엇을 만들고 검증할까"로 적어야 실행력이 올라갑니다.

분기 단위 실행 계획:

| 분기 | 계획 예시 |
| --- | --- |
| Q1 | 핵심 역량 진단, 학습 공백 정리, 멘토 피드백 수집 |
| Q2 | 중간 난도 프로젝트 1건 완료, 결과 발표 1회 |
| Q3 | 협업 범위 확장, 타팀 과제 1건 참여 |
| Q4 | 연간 회고, 다음 해 성장 목표 재설계 |

## 인터뷰 예시: "시니어로서 어떤 영향을 줬나요?"

시니어 포지션 면접에서 가장 자주 나오는 질문은 "개인 성과"가 아니라 "팀과 조직에 어떤 변화를 만들었는가"입니다.

**약한 답변**: "다양한 모델을 만들고 성능을 올렸습니다. 여러 프로젝트를 리드했습니다."

**강한 답변**: "이탈 예측 모델을 만든 이후, 마케팅 팀이 모델 결과를 어떻게 써야 할지 몰라 실제 활용이 되지 않고 있다는 사실을 발견했습니다. 저는 고위험 세그먼트 3개를 정의하고 각 세그먼트에 맞는 오퍼 매핑 가이드를 만들어 마케팅 팀과 공유했습니다. 이후 리텐션 캠페인 효율이 개선됐고, 그 가이드는 이후 4개 캠페인에서 재사용됐습니다."

핵심은 [발견한 문제] → [내가 취한 행동] → [조직에 남은 변화] 구조로 말하는 것입니다.

### 시니어 면접 질문과 권장 답변 방향

| 질문 | 권장 답변 방향 |
| --- | --- |
| 모호한 문제를 어떻게 정의했나요? | 문제 재정의 과정 + 이해관계자 정렬 방법 + 측정 기준 |
| 팀에 어떤 기여를 했나요? | 개인 산출물이 아닌 팀 생산성 증폭 사례 |
| 기술 결정을 어떻게 내리나요? | 대안 비교 + 트레이드오프 + 결정 로그 |
| 실패한 경험이 있나요? | 실패 사례 + 배운 점 + 이후 변화 |

## 연봉 협상: 역할 범위 기반으로 제안하기

```text
1) 현재 기여: 지난 12개월 동안 만든 핵심 영향 3가지를 수치로 제시
2) 확장 책임: 다음 12개월에 맡을 문제 범위를 명확히 제시
3) 시장 정렬: 동등 역할의 보상 밴드와 차이를 설명
4) 제안안: 기본급/성과급/주식 중 우선 조정 항목을 제시
```

시니어 협상은 "더 달라"가 아니라 "확장된 책임과 보상의 일치"를 만드는 과정입니다. 역할 범위를 문서로 제시하면 협상 난도가 크게 낮아집니다.

## 자주 하는 실수

| 실수 유형 | 구체적 사례 | 개선 방향 |
| --- | --- | --- |
| 기술만 깊게 파기 | 모델 정확도 튜닝에만 집중하고 비즈니스 영향 확인 안 함 | 제안마다 측정 계획 붙이기 |
| 영향 측정 빼먹기 | 분석 끝내고 "좋아졌다"고만 발표 | KPI 전후 비교 수치 포함하기 |
| 멘토링 나중으로 미루기 | "내 일 다 끝난 다음에 도와주겠다" | 월 1회 30분 1:1 먼저 캘린더에 잡기 |
| 결정 기록 안 남기기 | 구두로만 결정하다 6개월 후 "왜 그랬나" 재논의 | 결정할 때마다 로그 1건 작성 |
| 시스템 전체 안 보기 | 모델 성능은 좋은데 운영 단계에서 장애 반복 | 배포 후 운영 체크리스트 만들기 |
| 승격 증거 미리 안 쌓기 | 연말에 급하게 성과 정리 | 분기마다 영향력 증거 표 업데이트하기 |

## 시니어는 이렇게 생각합니다

문제 정의를 먼저 합니다. 팀장이 "성능을 올려 달라"고 해도 "성능이 오르면 어떤 결정이 달라지는가"를 먼저 묻습니다.

영향 측정을 계획 단계에서 붙입니다. 실행 후 "잘 된 것 같다"가 아니라 실행 전에 이미 "이렇게 되면 성공"을 정의합니다.

동료를 증폭시키는 행동을 의식합니다. 내가 직접 해결하는 것보다 팀 전체가 해결할 수 있게 만드는 것이 더 큰 가치라는 것을 압니다.

중요한 결정을 문서로 남깁니다. 기억이 아니라 기록이 신뢰를 만든다는 것을 압니다.

시스템 전체 관점에서 병목과 리스크를 봅니다. 내 부분만 최적화하면 전체가 좋아지지 않는다는 것을 압니다.

## 운영 체크리스트

- [ ] 문제 정의 템플릿을 만들었다.
- [ ] 측정 계획이 포함된 제안을 한 번 써 봤다.
- [ ] 멘토링 대상 한 명을 정했다.
- [ ] 의사결정 기록 템플릿을 준비했다.
- [ ] 시니어 승격 증거 표를 분기별로 관리하기 시작했다.

## 연습 문제

1. 주어진 문제("검색 결과 클릭률이 낮다")를 문제 정의 템플릿으로 구조화해 보세요.
2. 내가 최근 완료한 과제에서 "영향 측정"을 어떻게 했을지 측정 계획을 소급해서 작성해 보세요.
3. 내가 팀 전체의 생산성을 높이기 위해 만들 수 있는 문서나 가이드 1가지를 제안해 보세요.

## 정리 및 시리즈 마무리

시니어 데이터 직무로 성장한다는 것은 더 많은 일을 혼자 처리하는 사람이 되는 것이 아닙니다. 더 좋은 문제를 정의하고, 영향 측정을 붙여 제안하고, 동료와 시스템까지 함께 보는 사람으로 바뀌는 일에 가깝습니다.

이 시리즈는 여기서 마무리됩니다. 데이터 커리어는 기술, 도메인, 사람, 그리고 문제를 보는 관점이 함께 쌓이면서 길이 만들어집니다.

시리즈를 마무리하는 시점에서 가장 중요한 다음 행동은 거창한 목표가 아니라, 다음 90일 계획을 실제 일정으로 옮기는 일입니다. 배운 것이 행동이 될 때 비로소 커리어가 바뀝니다.

## 처음 질문으로 돌아가기

- **시니어 데이터 직무가 무엇이 다른가**
  - 시니어는 주어진 문제를 실행하는 것을 넘어 문제 자체를 정의합니다. "이 모델을 개선하라"는 요청을 받으면 바로 튜닝에 들어가지 않고, "이 개선이 어떤 의사결정을 바꾸는가"를 먼저 묻습니다. 책임 범위가 개인 과제에서 팀 시스템으로 확장된 것이 가장 큰 차이입니다.
- **문제 정의 능력이 왜 시니어의 핵심 역량인가**
  - 잘못 정의된 문제를 아무리 완벽하게 풀어도 조직에 가치가 없습니다. 시니어는 증상과 문제를 분리하고, 해결 기준을 측정 가능한 형태로 만들며, 관계자들과 문제 정의를 먼저 정렬합니다. 이 능력이 있어야 이후 실행이 방향을 잃지 않습니다.
- **영향 측정을 어떻게 계획해야 설득력이 생기는가**
  - 실행 전에 이미 가설, 지표, 측정 기간, 기준 수치를 포함한 측정 계획을 작성해야 합니다. 사전에 합의된 기준이 있어야 결과가 나왔을 때 "성공"이라는 증거로 활용할 수 있습니다. 측정 계획 없이 실행하면 좋은 결과도 "운이 좋았다"는 평가를 받을 수 있습니다.
