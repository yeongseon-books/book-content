# Data Science Career 101 (1/10): 데이터 직무란 무엇인가

채용 공고를 수십 개 읽어도 막막한 경험이 있을 것입니다. 어떤 공고는 "데이터 사이언티스트"를 뽑으면서 SQL 대시보드를 만들라고 하고, 어떤 공고는 "데이터 분석가"를 뽑으면서 머신러닝 모델 배포 경험을 요구합니다. 직함은 그럴듯하지만 실제로 누가 무슨 문제를 푸는지 도무지 보이지 않습니다.

이 혼란은 지원자만의 문제가 아닙니다. 회사마다 데이터 직무 정의가 다르고, 심지어 같은 회사 안에서도 팀마다 역할 경계가 제각각입니다. 어떤 팀은 분석가가 실험 설계까지 맡고, 어떤 팀은 엔지니어가 지표 테이블 관리까지 책임집니다. 처음 진입하는 사람 입장에서는 어디서부터 시작해야 하는지조차 불분명합니다.

이 글은 Data Science Career 101 시리즈의 첫 번째 글입니다.

직함보다 더 안전한 독해 기준이 있습니다. 그 기준은 세 가지입니다. 이 역할은 어떤 질문을 맡는가, 어떤 산출물을 남기는가, 누구와 협업하는가. 이 세 축으로 보면 같은 "데이터 직무"라도 서로 완전히 다른 일을 하고 있다는 사실이 뚜렷하게 보이기 시작합니다.

![Data Science Career 101 1장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/data-science-career-101/01/01-01-concept-at-a-glance.ko.png)
*Data Science Career 101 1장 흐름 개요*

> 데이터 직무의 핵심은 직함이 아니라 책임 경계입니다. 각 역할이 어떤 문제를 맡고 어떤 산출물을 만드는지가 진입 기준이 되어야 합니다.

## 이 글에서 다룰 문제

- 채용 공고를 읽어도 analyst, scientist, engineer의 실제 차이가 잘 보이지 않는다
- 같은 회사에서도 역할 정의가 팀마다 달라서 어디에 지원해야 할지 판단하기 어렵다
- 직함이 아니라 무엇을 기준으로 역할을 구분해야 공부 방향을 잡을 수 있는가
- 다섯 가지 주요 역할이 각각 어떤 문제와 산출물을 다루는가
- 입문 단계에서 역할을 잘못 이해하면 어떤 학습 낭비가 생기는가

## 데이터 직무를 보는 멘탈 모델

데이터가 가치로 이어지는 과정을 단순화하면 이런 흐름입니다. 원천 데이터가 쌓이고, 그것이 정제되어 분석 가능한 형태가 되고, 분석과 모델을 거쳐 의사결정이나 제품 기능으로 연결됩니다. 이 흐름의 어느 구간을 책임지느냐가 역할을 가릅니다.

분석가(Analyst)는 이 흐름의 끝에서 일합니다. 정제된 데이터를 받아 비즈니스 질문에 답하고, 의사결정에 필요한 인사이트를 만듭니다. 사이언티스트(Scientist)는 가설을 세우고 실험과 모델로 검증하는 일을 합니다. 인과관계를 따지고 미래를 예측하는 축이라고 보면 됩니다. 엔지니어(Engineer)는 데이터가 끊기지 않고 안정적으로 흐르도록 기반을 만듭니다. ML 엔지니어는 모델을 운영 환경에서 돌리는 사람이고, 애널리틱스 엔지니어는 분석가와 엔지니어 사이에서 신뢰할 수 있는 데이터 모델을 구축합니다.

이 다섯 역할은 서로 경쟁하는 관계가 아닙니다. 하나의 데이터 조직 안에서 서로 다른 문제를 맡아 분업하는 구조입니다. 어느 역할이 더 우월한지 묻는 것 자체가 잘못된 질문입니다.

## 역할별 핵심 비교

입문 단계에서 가장 헷갈리는 부분을 같은 축으로 정리하면 차이가 분명해집니다.

| 구분 | DA (Data Analyst) | DE (Data Engineer) | DS (Data Scientist) | MLE (ML Engineer) |
| --- | --- | --- | --- | --- |
| 핵심 질문 | 무슨 일이 일어났는가, 왜 일어났는가 | 데이터가 안정적으로 흐르는가 | 어떤 가설이 맞는가, 무엇을 예측할 수 있는가 | 모델이 운영에서 안정적으로 동작하는가 |
| 대표 산출물 | 대시보드, 분석 리포트, KPI 정의서 | 데이터 파이프라인, 테이블 스키마, 품질 모니터링 | 실험 결과, 모델 프로토타입, 피처 분석 | 추론 API, 배포 파이프라인, 모니터링 대시보드 |
| 주 협업 상대 | PM, 마케팅, 사업팀 | 백엔드, 플랫폼, 분석팀 | PM, 리서치, 분석가 | 백엔드, 플랫폼, 데이터 사이언티스트 |
| 성공 지표 | 의사결정 반영률, 분석 재사용률 | 파이프라인 안정성, 지연 시간, 데이터 품질 | 실험 신뢰도, 모델 성능, 인사이트 채택률 | 서빙 안정성, 지연 시간, 성능 유지율 |
| 실패 패턴 | 지표 정의 모호, 해석 누락 | 스키마 관리 부실, 운영 자동화 부족 | 과적합, 누수, 비즈니스 맥락 부족 | 학습-서빙 불일치, 드리프트 대응 부재 |
| 초반 학습 우선순위 | SQL, 지표 설계, 스토리텔링 | SQL, 데이터 모델링, 오케스트레이션 | 통계, 실험 설계, 모델 평가 | 서빙 구조, 배포, 모니터링 |

## 각 역할의 실질적인 일

### Analyst — 질문을 숫자로 번역하는 사람

```text
Drives decisions with SQL and dashboards.
```

분석가는 팀의 판단 속도를 높이는 역할입니다. "지난달 결제 전환율이 왜 떨어졌지?"라는 질문을 받으면, 퍼널을 분해하고 세그먼트를 비교하고 어느 단계에서 이탈이 늘었는지 찾아냅니다. 결과를 대시보드나 리포트로 만들어 팀이 다음 행동을 결정하는 데 쓸 수 있게 합니다. SQL이 중심 도구인 이유가 바로 여기에 있습니다.

**실제 시나리오:** 이커머스 팀의 DA가 "신규 가입자 중 첫 구매 완료율이 전월 대비 8% 하락했다"는 보고를 받았습니다. 그는 유입 채널별로 쪼개고, 온보딩 퍼널 단계별 이탈 지점을 분석해 결제 페이지의 모바일 UI 버그를 원인으로 특정했습니다. PM이 이 정보를 바탕으로 긴급 패치 우선순위를 결정했습니다.

**하루 일과 예시:**
- 오전: 전일 KPI 이상 여부 확인 및 원인 탐색 쿼리 작성
- 오전 중반: PM과 주간 지표 리뷰 미팅 — 전환율 하락 원인 보고
- 오후: 세그먼트별 분석 대시보드 업데이트 및 인사이트 문서 작성
- 오후 후반: 다음 주 실험 지표 정의 검토 및 데이터 사이언티스트와 협의

**DA가 자주 쓰는 SQL 패턴:**

```sql
-- 퍼널 이탈 분석: 각 단계별 사용자 수 계산
SELECT
  step,
  COUNT(DISTINCT user_id) AS users,
  ROUND(
    100.0 * COUNT(DISTINCT user_id) / FIRST_VALUE(COUNT(DISTINCT user_id)) OVER (ORDER BY step_order),
    1
  ) AS retention_pct
FROM funnel_events
WHERE event_date BETWEEN '2026-05-01' AND '2026-05-31'
GROUP BY step, step_order
ORDER BY step_order;
```

### Scientist — 가설을 검증하는 사람

```text
Tests hypotheses with experiments and models.
```

사이언티스트는 질문을 가설로 바꾸고, 실험과 모델로 검증합니다. "이 기능을 바꾸면 리텐션이 올라갈까?"를 A/B 테스트로 검증하거나, "어떤 사용자가 이탈할 가능성이 높은가"를 예측 모델로 답합니다. 설명력과 검증력이 함께 요구됩니다.

**실제 시나리오:** SaaS 스타트업의 DS가 "알림 빈도를 줄이면 7일 리텐션이 오를 것이다"라는 가설을 세웠습니다. A/B 테스트를 설계하고 2주 후 결과를 분석해 통계적으로 유의미한 리텐션 개선을 확인했습니다. 실험 결과가 제품 알림 로직 개편의 근거가 되었습니다.

**하루 일과 예시:**
- 오전: 진행 중인 A/B 테스트 중간 결과 점검, 조기 종료 기준 확인
- 오전 중반: 피처 엔지니어링 실험 — 이탈 예측 모델 정밀도 개선
- 오후: 실험 결과 리포트 작성, 통계적 유의성 설명 문서 정리
- 오후 후반: 다음 분기 모델 개선 계획 로드맵 초안 작성

**DS가 자주 쓰는 실험 설계 체크리스트:**

| 항목 | 점검 내용 |
| --- | --- |
| 가설 정의 | "알림 빈도를 50% 줄이면 7일 리텐션이 3% 이상 증가한다" |
| 주 지표 | 7일 리텐션 (로그인 기준) |
| 가드레일 지표 | DAU (실험 군에서 DAU 5% 이상 하락 시 중단) |
| 샘플 크기 | power=0.8, alpha=0.05 기준 계산 결과 |
| 실험 기간 | 최소 2주 (주간 주기성 제거) |

### Engineer — 데이터 흐름을 보장하는 사람

```text
Builds pipelines and storage as data infrastructure.
```

엔지니어는 데이터가 안정적으로 흐르도록 기반을 만듭니다. 파이프라인과 스키마 품질이 무너지면 나머지 역할도 함께 흔들립니다. 분석가가 아무리 좋은 쿼리를 짜도 원천 데이터가 깨져 있으면 결과를 신뢰할 수 없습니다.

**실제 시나리오:** 핀테크 회사의 DE가 거래 원천 DB에서 웨어하우스로 오는 파이프라인에 주말 지연이 반복된다는 것을 발견했습니다. 스케줄러 설정 오류를 수정하고 데이터 품질 체크 규칙 10개를 추가해 월요일 아침 지표 리포트가 제때 생성되도록 안정화했습니다.

**하루 일과 예시:**
- 오전: 야간 파이프라인 실행 결과 확인, 품질 알럿 검토
- 오전 중반: 신규 원천 테이블 스키마 설계 및 dbt 모델 작성
- 오후: 파이프라인 성능 모니터링 대시보드 개선
- 오후 후반: 분석팀과 신규 지표 테이블 요구사항 협의

**DE가 자주 쓰는 데이터 품질 체크 패턴:**

```python
# dbt 테스트 예시: 필수 컬럼 null 여부 및 유니크 여부 검사
# models/schema.yml
models:
  - name: orders
    columns:
      - name: order_id
        tests:
          - not_null
          - unique
      - name: user_id
        tests:
          - not_null
          - relationships:
              to: ref('users')
              field: id
```

### ML Engineer — 모델을 운영하는 사람

```text
Trains, deploys, and monitors models.
```

ML 엔지니어는 모델을 연구 대상이 아니라 운영 대상으로 다룹니다. 학습된 모델을 실제 서비스에 배포하고, 응답 속도를 관리하고, 시간이 지나면서 성능이 떨어지지 않는지 모니터링합니다.

**실제 시나리오:** 추천 시스템을 운영하는 MLE가 배포된 모델의 클릭률이 3주 연속 하락하는 것을 탐지했습니다. 피처 분포 분석 결과 최근 신규 사용자 유입 패턴이 학습 데이터와 달라진 드리프트를 확인하고, 재학습 파이프라인을 트리거했습니다.

**MLE 운영 모니터링 핵심 지표:**

| 지표 | 설명 | 경보 기준 |
| --- | --- | --- |
| 추론 지연 시간 p99 | 99번째 백분위 응답 시간 | 200ms 초과 |
| 피처 드리프트 점수 | 학습 vs 서빙 피처 분포 차이 | PSI > 0.2 |
| 예측값 분포 변화 | 출력 레이블 분포 변동 | 기준 대비 ±15% |
| 모델 업타임 | 추론 API 가용성 | 99.9% 미만 |

### Analytics Engineer — 분석 기반을 만드는 사람

```text
Builds reliable analytics models with dbt and friends.
```

애널리틱스 엔지니어는 분석가와 엔지니어 사이에서 재현 가능하고 일관된 분석 기반을 만듭니다. 분석가가 매번 복잡한 전처리를 반복하지 않아도 되도록 신뢰할 수 있는 데이터 모델을 구축합니다.

**실제 시나리오:** 스타트업의 AE가 각 팀이 서로 다른 방식으로 "활성 사용자"를 정의하고 있다는 문제를 발견했습니다. dbt로 통합 사용자 활성도 모델을 구축하고 문서화해, 모든 팀이 동일한 정의를 쓰는 단일 진실 소스(single source of truth)를 완성했습니다.

## 조직 규모별 역할 분포

역할 경계는 조직 규모에 따라 크게 달라집니다. 이 차이를 이해하지 못하면 지원하는 회사의 실제 업무를 오해하기 쉽습니다.

| 조직 규모 | 데이터 팀 구성 | 역할 특성 |
| --- | --- | --- |
| 스타트업 (5명 이하 팀) | 1-2명이 분석+엔지니어링 겸임 | 광범위한 업무, 빠른 학습 필요 |
| 중소기업 (10-30명 팀) | 역할 구분 시작, 공통 파이프라인 | 분업 시작, 코드 표준화 중요 |
| 대기업 (50명 이상 팀) | 역할 세분화, 전문 플랫폼 팀 존재 | 좁고 깊은 전문성, 협업 복잡도 증가 |

**스타트업에서의 현실**: 입사 첫 주에 Airflow 파이프라인 디버깅을 하고, 같은 날 오후에 대시보드를 만드는 일이 생길 수 있습니다. 이런 환경은 빠르게 많은 것을 배울 수 있지만, 깊이 있는 전문성을 쌓기는 어렵습니다.

**대기업에서의 현실**: 역할 경계가 분명해 자신의 영역에서 깊이 있는 기여가 가능하지만, 다른 역할과 협업할 때 조율 비용이 큽니다. 분석가가 새 파이프라인을 요청하면 엔지니어링 팀 스프린트에 반영되기까지 몇 주가 걸릴 수 있습니다.

**조직 규모별 데이터 스택 비교:**

| 규모 | 데이터 웨어하우스 | 오케스트레이션 | BI 도구 | 모델 서빙 |
| --- | --- | --- | --- | --- |
| 스타트업 | BigQuery / Snowflake | cron / 간단한 Airflow | Metabase / Redash | Flask API |
| 중소기업 | Snowflake / Redshift | Airflow / Prefect | Looker / Tableau | FastAPI + Docker |
| 대기업 | 멀티 웨어하우스 | Airflow + Kubernetes | 전용 BI 플랫폼 | MLflow + Kubernetes |

## 실무에서 역할은 어떻게 섞이는가

작은 조직에서는 한 사람이 두세 역할을 겸하기도 합니다. 그래서 직함만 보면 역할을 판단하기 어렵습니다. 더 정확한 방법은 채용 공고에서 "대표 산출물"과 "협업 상대"를 찾는 것입니다.

| 공고 문장 | 숨은 역할 신호 | 준비 액션 |
| --- | --- | --- |
| "비즈니스 지표를 설계하고 대시보드를 운영합니다" | Analyst 중심 | 지표 정의서 1개와 대시보드 해석 노트 작성 |
| "데이터 파이프라인 안정화와 품질 모니터링" | Engineer 중심 | 데이터 품질 체크 규칙 5개 정리 |
| "실험 설계와 모델 성능 개선" | Scientist 또는 MLE 중심 | 가설-지표-검증 템플릿으로 모의 답변 연습 |
| "dbt 모델 설계와 데이터 품질 관리" | Analytics Engineer 중심 | dbt 프로젝트 구조와 테스트 방법 학습 |

큰 조직일수록 역할이 선명하게 분리되고, 작은 조직일수록 경계가 흐릿합니다. 입문 단계에서는 직함보다 실제 책임을 읽는 눈을 먼저 갖추는 편이 안전합니다.

## 역할 전환 가능성

한 역할로 시작했다가 다른 역할로 전환하는 경우는 매우 일반적입니다. 전환 방향과 필요한 역량을 미리 이해해 두면 커리어 계획에 도움이 됩니다.

| 전환 방향 | 추가로 필요한 역량 | 전환 난도 |
| --- | --- | --- |
| Analyst → Scientist | 통계, 실험 설계, 모델 평가 | 중간 |
| Analyst → Analytics Engineer | dbt, 데이터 모델링, SQL 최적화 | 낮음 |
| Scientist → MLE | 서빙 인프라, 배포 자동화, 모니터링 | 높음 |
| Engineer → Analytics Engineer | 비즈니스 맥락 이해, SQL 분석 패턴 | 중간 |
| MLE → Scientist | 통계 강화, 실험 설계, 비즈니스 연결 | 낮음 |

전환이 어려운 방향은 보통 도구와 사고방식이 크게 달라지는 경우입니다. Scientist에서 Engineer로의 전환은 분석 중심 사고에서 신뢰성과 자동화 중심 사고로의 전환을 요구합니다.

**전환 전 준비를 위한 실천 체크리스트:**

Analyst에서 Scientist로 전환을 준비한다면:
- Khan Academy 통계 강의 수료 후 A/B 테스트 모의 설계 1회 실습
- Kaggle 대회에서 분류 모델을 직접 평가하고 precision/recall 설명 연습
- 현재 업무에서 "이 지표가 변한 이유"를 단순 보고에서 통계적 검정으로 업그레이드

Engineer에서 Analytics Engineer로 전환을 준비한다면:
- dbt 공식 튜토리얼 완료 및 간단한 dbt 프로젝트 GitHub에 공개
- 팀의 지표 정의 불일치 사례를 1개 찾아 통합 모델 설계 제안

## 포트폴리오 관점에서 본 역할 선택

역할을 결정할 때 흔히 "어떤 기술을 좋아하는가"부터 생각하지만, 포트폴리오 전략 측면에서는 "어떤 문제를 증명할 수 있는가"가 더 중요합니다. 지원 역할에 맞는 산출물 유형을 사전에 정하면 학습과 포트폴리오 방향이 일치합니다.

| 목표 역할 | 포트폴리오에 넣어야 할 산출물 | 증명해야 할 능력 |
| --- | --- | --- |
| Analyst | 퍼널/코호트 분석, 지표 정의서, 대시보드 설명 문서 | 질문 분해, 숫자 해석, 스토리텔링 |
| Scientist | A/B 테스트 분석, 모델 비교 노트, 피처 중요도 설명 | 가설 검증, 평가 지표 선택 근거 |
| Engineer | ETL DAG, 품질 체크 규칙, 스키마 설계 문서 | 안정성, 재현성, 장애 대응 |
| MLE | 추론 API PoC, 드리프트 탐지 노트, 배포 절차 문서 | 모델 서빙, 모니터링, 운영 자동화 |
| Analytics Engineer | dbt 프로젝트, 데이터 계보 문서, 지표 정의 카탈로그 | 데이터 신뢰성, 문서화, 협업 |

**포트폴리오 완성도 채점표 예시 (Analyst 기준):**

| 항목 | 미흡 (1점) | 보통 (3점) | 우수 (5점) |
| --- | --- | --- | --- |
| 문제 정의 | "데이터 분석했음" | "전환율 하락 분석" | "신규 가입자 모바일 결제 전환율 하락 원인 규명" |
| 지표 명세 | 없음 | 지표 이름만 | 분자/분모/기준 날짜/예외 조건 포함 |
| SQL 코드 | 없음 | 단순 조회 | JOIN+집계+윈도우함수 활용 |
| 결론 | "문제 있었음" | "모바일 이탈 높음" | "모바일 결제 3단계 이탈 60% → 특정 버튼 개선 제안" |
| 한계 명시 | 없음 | "일부 데이터 제한" | "세션 기준 단일화 미적용, 기기별 추가 분석 필요" |

## 입문자가 가장 많이 놓치는 것

도구가 아니라 목적입니다. SQL을 쓴다고 모두 같은 역할이 아니고, Python을 쓴다고 모두 모델링 중심 직무도 아닙니다. 어떤 질문을 맡고 어떤 결과를 남기는지가 훨씬 더 본질적입니다.

두 번째로 자주 놓치는 것은 도메인입니다. 기술을 먼저 익히려는 충동은 자연스럽지만, 실무에서는 같은 대시보드를 보고도 비즈니스 맥락을 아는 사람이 훨씬 더 좋은 질문을 던집니다. 기술은 도구이고, 도메인이 그 도구를 올바른 방향으로 이끕니다.

세 번째로 놓치는 것은 커뮤니케이션입니다. 데이터 직무는 숫자를 다루는 일이지만, 그 숫자를 의사결정에 연결하는 과정은 반드시 사람과의 대화를 거칩니다. 분석 결과를 PM이 이해할 수 있는 언어로 바꾸는 능력, 데이터 파이프라인 장애를 이해관계자에게 명확히 설명하는 능력이 기술 역량만큼 중요합니다.

## 처음 질문으로 돌아가기

- **채용 공고를 읽어도 analyst, scientist, engineer의 실제 차이가 잘 보이지 않는다**
  - 작은 조직에서는 한 사람이 두세 역할을 겸하기 때문에 직함이 일치하지 않을 수 있습니다. 산출물과 협업 상대를 기준으로 읽으면 역할이 선명해집니다.
- **같은 회사에서도 역할 정의가 팀마다 달라서 어디에 지원해야 할지 판단하기 어렵다**
  - 공고의 "대표 산출물"과 "주요 협업 상대"를 추출하면 팀별 역할 차이가 보입니다. 직함보다 책임 기준으로 필터링하십시오.
- **직함이 아니라 무엇을 기준으로 역할을 구분해야 공부 방향을 잡을 수 있는가**
  - 핵심 질문, 산출물, 협업 상대 세 축으로 구분하면 됩니다. 이 세 가지가 정렬되면 학습 우선순위도 명확해집니다.
- **다섯 가지 주요 역할이 각각 어떤 문제와 산출물을 다루는가**
  - 역할별 핵심 비교 표를 참조하십시오. DA는 해석, DE는 흐름, DS는 검증, MLE는 운영, AE는 신뢰할 수 있는 기반이 핵심입니다.
- **입문 단계에서 역할을 잘못 이해하면 어떤 학습 낭비가 생기는가**
  - Analyst를 준비하면서 ML 모델을 먼저 공부하거나, Engineer 지원 공고에 대시보드 프로젝트만 제출하는 방향 오류가 생깁니다. 역할 정의가 먼저입니다.

## 면접 Q&A — 역할 이해 질문 실전 연습

데이터 직무 면접에서는 "왜 이 역할을 지원했는가", "이 역할에서 잘하는 것이 무엇인가"를 묻는 질문이 자주 나옵니다.

**Q: "데이터 분석가와 데이터 사이언티스트의 차이를 본인만의 언어로 설명해 보세요."**

약한 답변: "분석가는 SQL 쓰고 사이언티스트는 머신러닝 합니다."

강한 답변: "분석가는 현재 일어난 일에 대한 질문에 답하고, 사이언티스트는 미래에 일어날 일을 예측하거나 인과관계를 검증합니다. 같은 이탈 문제라도 분석가는 '어떤 세그먼트에서 이탈이 많이 일어났는가'를 파악하고, 사이언티스트는 '어떤 요인이 이탈을 유발하는가'를 검증합니다. 저는 현재 [역할]로 지원했고, [역할]의 산출물인 [산출물]을 만드는 것에 더 관심이 있습니다."

**Q: "왜 이 역할에 지원했나요? 다른 데이터 직무는 고려해 보셨나요?"**

강한 답변 구조: 본인이 자연스럽게 끌리는 문제 유형 → 해당 역할이 그 문제를 다루는 방식 → 포트폴리오에서 같은 방향으로 작업한 경험 → 지원 회사에서 이 역할이 어떤 가치를 줄 수 있는지 연결.

## 운영 체크리스트

- [ ] 지원하고 싶은 역할을 하나 골라 핵심 질문, 산출물, 협업 상대를 적어 봤다
- [ ] 관심 있는 채용 공고 3개를 역할 신호 기준으로 분해해 봤다
- [ ] 각 역할의 기본 도구를 한 번씩 적어 봤다
- [ ] "직함이 같아도 실제 일이 다를 수 있다"는 감각을 갖췄다
- [ ] 내가 오래 풀고 싶은 문제 유형이 어느 역할에 가까운지 판단했다
- [ ] 지원 대상 조직의 규모를 확인하고 역할 경계 유연성을 예상해 봤다
- [ ] 포트폴리오 채점표에서 현재 자신의 수준을 자가 평가해 봤다
- [ ] 역할 이해 면접 질문에 본인만의 언어로 답변을 작성해 봤다

## 정리

데이터 직무를 이해하는 첫걸음은 "모두 데이터를 본다"는 뭉뚱그린 시선을 버리는 일입니다. 역할마다 풀어야 하는 문제, 만드는 산출물, 협업 상대, 평가 기준이 다릅니다. 이 차이를 초반에 구분해 두면 학습 계획도 포트폴리오 방향도 훨씬 또렷해집니다. 직함보다 책임을 읽는 눈이 생기면, 채용 공고도 다르게 보이기 시작합니다.

다음 글에서는 분석가, 사이언티스트, 엔지니어 세 역할을 더 직접적으로 비교하면서 구조적 차이를 정리합니다.

## 실전 FAQ: 입문자가 가장 많이 묻는 질문

**Q. 비전공자도 데이터 직무에 지원할 수 있나요?**

네, 가능합니다. 채용 공고의 "우대 사항"에 전공을 명시한 경우는 있지만, "필수 요건"으로 전공을 요구하는 기업은 많지 않습니다. 포트폴리오와 실무 능력이 더 큰 영향을 미칩니다. 실제로 통계학·컴퓨터공학 전공자보다 사회과학·경영학 전공자가 분석가 직무에서 두각을 나타내는 경우도 흔합니다. 결국 "이 사람이 실무 문제를 풀 수 있는가"를 증명하는 것이 핵심입니다.

**Q. 데이터 분석가와 BI 개발자는 어떻게 다른가요?**

기능적으로 겹치는 부분이 많습니다. BI 개발자는 대시보드·리포트 인프라를 구축하는 데 더 집중하고, 분석가는 그 인프라 위에서 비즈니스 질문에 답하는 역할에 집중합니다. 조직 규모가 작을수록 두 역할을 한 사람이 담당하는 경우가 많습니다. 채용 공고를 볼 때는 "무엇을 만들어야 하는가(산출물)"를 보는 것이 직함보다 더 정확한 판단 기준입니다.

**Q. 데이터 사이언티스트가 되려면 논문을 써야 하나요?**

연구 중심 빅테크에서는 논문 경력을 선호하기도 하지만, 대부분의 산업 현장에서는 논문이 필수는 아닙니다. 오히려 "모델을 프로덕션에 배포한 경험"이나 "실험 결과를 비즈니스 언어로 설명한 사례"를 더 중시합니다. 논문은 실력의 신호지 조건이 아니므로, 없다면 캐글·사이드 프로젝트·오픈소스 기여로 대체할 수 있습니다.

**Q. 데이터 엔지니어링과 백엔드 개발의 차이는 무엇인가요?**

백엔드 개발자는 사용자 요청을 처리하는 서비스를 만들고, 데이터 엔지니어는 데이터가 올바르게 수집·저장·변환·전달되는 파이프라인을 만듭니다. 도구 스택이 일부 겹치지만(Python, SQL, API), 데이터 엔지니어는 대용량 처리(Spark, Kafka), 스케줄링(Airflow), 데이터 품질 관리에 더 집중합니다.

**Q. 어느 역할이 연봉이 가장 높나요?**

역할보다 조직 규모와 시장 수요에 더 크게 좌우됩니다. ML 인프라를 다루는 시니어 엔지니어가 일반 분석가보다 연봉이 높은 경향이 있지만, 비즈니스 임팩트를 명확히 수치화하는 분석가는 대기업에서 높은 처우를 받습니다. 역할 선택은 연봉보다 "어떤 일을 오래 잘할 수 있는가"를 기준으로 하는 것이 장기적으로 유리합니다.

## 데이터 직무 탐색 로드맵

역할 결정이 어렵다면 아래 순서로 탐색을 진행해 보세요.

| 단계 | 행동 | 확인 기준 |
|------|------|-----------|
| 1주차 | 관심 있는 역할의 채용 공고 5개 수집 | 공통 요건 3개 이상 파악 |
| 2주차 | 각 역할의 현직자 인터뷰 영상·블로그 3편 탐독 | "하루 일과"를 구체적으로 그릴 수 있는가 |
| 3주차 | 각 역할 핵심 도구를 하나씩 10분 체험 | SQL / Python / 파이프라인 중 어느 것이 재미있는가 |
| 4주차 | 미니 프로젝트 1개 완성 | 어떤 단계에서 가장 집중했는가 |
| 5주차 | 타깃 역할 결정 후 포트폴리오 방향 수립 | 포트폴리오 소재 3가지 이상 목록화 |

이 과정을 거치면 "느낌상 맞을 것 같아서" 대신 "해 봤더니 이 일이 맞더라"는 근거로 역할을 결정할 수 있습니다.
