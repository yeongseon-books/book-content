# Data Science Career 101 (4/10): 데이터 포트폴리오

데이터 포트폴리오를 준비할 때 가장 흔한 오해는 "코드를 올리면 곧 실력 증명이 된다"는 생각입니다. 하지만 채용 관점에서 더 중요한 것은 코드량보다 문제를 어떻게 정의했고, 어떤 판단을 했고, 결과를 어떻게 설명했는지입니다.

특히 데이터 프로젝트는 노트북 몇 개만 남겨 두면 맥락이 금방 사라집니다. 데이터 출처는 무엇인지, 비교 기준은 무엇인지, 재현은 가능한지, 결과가 왜 의미 있는지까지 같이 보여 줘야 포트폴리오가 단순 저장소가 아니라 실무 증거로 읽힙니다.

이 글은 Data Science Career 101 시리즈의 네 번째 글입니다.

![Data Science Career 101 4장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/data-science-career-101/04/04-01-concept-at-a-glance.ko.png)
*Data Science Career 101 4장 흐름 개요*

> 포트폴리오에서 가장 중요한 것은 코드 양이 아니라 문제 정의의 선명도와 결론의 행동 연결성입니다.

## 이 글에서 다룰 문제

- 데이터 포트폴리오를 어떤 프로젝트 조합으로 구성하면 좋은가
- 코드만 있는 저장소가 왜 약하게 보이는가
- README가 어떤 구조를 가져야 하는가
- 역할별로 포트폴리오 구성이 어떻게 달라지는가
- 면접관이 포트폴리오를 어떻게 읽는지 이해하는가

## 면접관이 포트폴리오를 보는 방식

채용 담당자는 평균 3-5분 안에 저장소 하나를 판단합니다. 이 시간 안에 가장 먼저 보는 것은 코드가 아니라 README입니다. README 첫 화면에서 "이 사람이 어떤 문제를 풀었고, 어떤 판단을 했는가"가 읽혀야 다음 단계로 연결됩니다.

면접관이 README에서 찾는 신호:

1. 문제 정의가 있는가 (왜 이 문제를 풀었는가)
2. 데이터 출처와 한계가 명시되어 있는가
3. 결과가 수치와 함께 한 문장으로 요약되어 있는가
4. 재현 가능한가 (실행 명령이 명시되어 있는가)
5. 후속 액션이나 한계가 솔직하게 적혀 있는가

## 세 가지 프로젝트 구성

균형 잡힌 포트폴리오는 서로 다른 역량을 보여 주는 세 유형으로 구성됩니다.

```text
- 분석 프로젝트 (analytics): 질문 정의와 SQL/시각화 해석
- 모델링 프로젝트 (model): 평가와 검증, 비즈니스 해석
- 엔지니어링 프로젝트 (pipeline): 재현성과 운영 자동화
```

단, 세 개 모두 얕게 만드는 것보다 지원 역할에 맞는 2개를 깊게 만드는 편이 효과적입니다.

## README 5섹션 템플릿

```markdown
# 프로젝트 제목

## 1. 문제 (Problem)
어떤 비즈니스 또는 운영 문제를 풀기 위한 프로젝트인가.
이 결과가 누구의 어떤 의사결정을 돕는가.

## 2. 데이터 (Data)
출처, 수집 기간, 주요 컬럼.
결측/이상치/한계를 솔직하게 명시.

## 3. 접근 방법 (Method)
분석 또는 모델링 순서.
왜 이 방법을 선택했는지 이유.
대안과 비교한 근거.

## 4. 결과 (Result)
핵심 수치 결과 1-2개.
비즈니스 해석 한 문장.
후속 액션 제안.

## 5. 재현 방법 (Reproduce)
```bash
pip install -r requirements.txt
python run.py
```
실행 환경, 데이터 다운로드 방법, 검증 절차.
```

README는 결과 요약문이 아니라 "판단 기록"이어야 합니다. 코드를 읽지 않아도 이 사람이 어떻게 생각하고 어떤 결정을 했는지 보여야 합니다.

## 프로젝트 예시 3종

### 프로젝트 A: 이탈 분석 대시보드 (Analyst)

**문제:** 신규 사용자 2주차 이탈이 전월 대비 15% 증가한 원인 파악

**데이터:** 이벤트 로그, 결제 테이블, 유입 채널 정보 (공개 e-commerce 데이터셋 활용)

**접근 방법:**
1. 코호트별 리텐션 계산 (가입 주 기준)
2. 유입 채널별 퍼널 단계 이탈 분해
3. 2주차 이탈 증가와 온보딩 단계 이벤트 상관 분석

**결과:** 모바일 앱 온보딩 3단계에서 43% 이탈 확인, 튜토리얼 간소화 실험 제안

**포트폴리오 핵심 포인트:**
- 지표 정의서 (분자/분모 명시)
- SQL로 구현한 퍼널 쿼리
- 결과를 한 문장 권고안으로 마무리

### 프로젝트 B: 수요 예측 미니 모델 (Scientist)

**문제:** 주간 재고 소진율 예측으로 발주 의사결정 지원

**데이터:** 판매 이력, 프로모션 일정, 시즌 변수 (Kaggle Rossmann 데이터셋)

**접근 방법:**
1. 기준선 (3주 이동평균) 설정
2. 시즌성, 프로모션, 요일 피처 추가
3. Ridge vs RandomForest 비교

**결과:** RandomForest가 기준선 대비 RMSE 22% 개선, 할인 기간 예측 오차가 가장 높음 → 할인 피처 개선이 다음 과제

**포트폴리오 핵심 포인트:**
- 기준선 대비 개선 수치 제시
- Precision-Recall 또는 RMSE 외 해석 설명
- 한계 솔직하게 명시 (할인 데이터 품질 문제)

### 프로젝트 C: 데이터 품질 모니터링 (Engineer)

**문제:** 매주 월요일 아침 대시보드 수치 불일치 반복으로 분석팀 신뢰도 저하

**데이터:** 원천-집계 테이블 매핑 정보, 파이프라인 로그

**접근 방법:**
1. 원천-집계 간 불일치 규칙 10개 정의
2. 누락/중복 탐지 SQL 체크 함수 구현
3. 파이프라인 실패 시 알림 자동화

**결과:** 오류 탐지 시간을 수작업 30분에서 자동 5분으로 단축, 재실행 절차 표준화 문서 작성

**포트폴리오 핵심 포인트:**
- 품질 체크 규칙 목록 명시
- 재실행 가능한 코드와 장애 대응 절차
- 개선 전/후 수치 비교

## 역할별 포트폴리오 점검표

지원 역할에 따라 포트폴리오에서 더 강조해야 할 요소가 다릅니다.

| 점검 항목 | Analyst | Scientist | Engineer |
| --- | --- | --- | --- |
| 문제 정의 선명도 | 필수 | 필수 | 필수 |
| 지표 정의서 (분자/분모) | 필수 | 권장 | 해당 없음 |
| 기준선 대비 개선 수치 | 권장 | 필수 | 권장 |
| 실험 설계 문서 | 선택 | 필수 | 해당 없음 |
| 파이프라인 재실행 절차 | 선택 | 선택 | 필수 |
| 한계와 후속 액션 | 필수 | 필수 | 필수 |
| 한 문장 권고안 | 필수 | 권장 | 권장 |

## 채용 공고 요구사항과 1:1 매핑

좋은 포트폴리오는 지원 직무와 직접 연결되는 프로젝트를 담습니다.

| 공고 요구사항 | 포트폴리오 증거 | 제출 형태 |
| --- | --- | --- |
| 지표 분석 및 대시보드 운영 | 퍼널/코호트 분석 프로젝트 | README + 대시보드 스크린샷 + 해석 문서 |
| 실험 설계와 성과 검증 | A/B 테스트 분석 프로젝트 | 실험 설계/결과/한계 문서 |
| 데이터 파이프라인 개선 | ETL 자동화 프로젝트 | DAG 설명 + 품질 체크 규칙 + 장애 대응 노트 |
| 머신러닝 모델 개발 | 예측 모델 프로젝트 | 모델 비교표 + 피처 설명 + 운영 조건 제시 |

## 자주 하는 실수

| 실수 유형 | 구체적 사례 | 개선 방향 |
| --- | --- | --- |
| 문제 없이 코드만 올림 | 노트북이 있지만 왜 이 분석을 했는지 모름 | README 첫 줄에 "이 프로젝트는 X 문제를 풀기 위해" 작성 |
| 데이터 출처 불명확 | "Kaggle에서 가져온 데이터" 한 줄 | 데이터셋 이름, 기간, 전처리 기준, 한계 명시 |
| 재현 불가능한 저장소 | 실행 명령 없이 노트북만 있음 | requirements.txt, 실행 명령, 환경 버전 추가 |
| 시각화 과잉 | 차트 30개가 설명 없이 나열됨 | 핵심 차트 1-2개와 해석 문장 집중 |
| 한계를 숨김 | "모델 정확도 95%"만 강조 | "할인 기간 예측 오차가 높아 다음 개선 과제" 솔직하게 명시 |

## 면접 연계 전략

포트폴리오는 면접 답변의 근거가 됩니다. 프로젝트를 "5분 발표"로 압축하는 연습이 필요합니다.

**5분 발표 구조:**

```text
1) 문제 (30초): 어떤 상황에서 어떤 질문을 받았는가
2) 접근 (90초): 어떤 방법을 선택하고 왜 그렇게 판단했는가
3) 결과 (60초): 무엇이 어떻게 바뀌었는가 (수치 포함)
4) 한계 (30초): 무엇을 알았고 무엇을 모르는가
5) 다음 (30초): 만약 계속했다면 무엇을 할 것인가
```

면접관이 "그 프로젝트에서 가장 어려웠던 점이 무엇인가요?"라고 물으면, 기술적 어려움보다 "어떤 가정을 어떻게 판단했는지"를 답하는 편이 더 강합니다.

## 처음 질문으로 돌아가기

- **데이터 포트폴리오를 어떤 프로젝트 조합으로 구성하면 좋은가**
  - 지원 역할에 맞는 산출물 유형 2개를 깊게 만드십시오. Analyst라면 분석 + A/B 테스트, Scientist라면 실험 + 예측 모델, Engineer라면 파이프라인 + 품질 모니터링이 기본 조합입니다.
- **코드만 있는 저장소가 왜 약하게 보이는가**
  - 코드는 "어떻게 했는가"를 보여 주지만, "왜 했는가"와 "어떤 판단을 했는가"는 README와 해석 문서에서 나옵니다. 면접관은 판단 과정을 더 중요하게 봅니다.
- **README가 어떤 구조를 가져야 하는가**
  - 문제, 데이터, 접근 방법, 결과, 재현 방법 5개 섹션이 기본입니다. 특히 한계와 후속 액션을 솔직하게 적는 것이 신뢰를 높입니다.
- **역할별로 포트폴리오 구성이 어떻게 달라지는가**
  - Analyst는 지표 정의서와 해석 문서가 핵심이고, Scientist는 실험 설계와 모델 비교표가 핵심입니다. Engineer는 재실행 절차와 품질 체크 규칙이 핵심입니다.
- **면접관이 포트폴리오를 어떻게 읽는지 이해하는가**
  - 3-5분 안에 README 첫 화면, 핵심 결과, 재현 가능성을 봅니다. "5분 발표" 형태로 자신의 프로젝트를 설명하는 연습을 해 두어야 합니다.

## 운영 체크리스트

- [ ] 서로 다른 성격의 프로젝트 2-3개를 골랐다
- [ ] 모든 프로젝트에 5섹션 README 구조를 만들었다
- [ ] 재현 명령과 환경 정보를 적어 두었다
- [ ] 한 문장 결론과 후속 액션을 남겼다
- [ ] 5분 발표 구조로 한 번 말해 봤다

## 정리

좋은 데이터 포트폴리오는 코드보다 문제 정의와 결론 전달이 더 또렷합니다. 지원 역할에 맞는 산출물 유형을 고르고, README와 재현 방법까지 갖추고, 한계를 솔직하게 드러낼 때 면접관의 신뢰를 얻습니다. 프로젝트를 하나 더 추가하기보다 기존 프로젝트의 가정, 실패 원인, 개선 반복을 정리하는 편이 포트폴리오 품질을 더 빠르게 높입니다.

다음 글에서는 데이터 직무 면접에서 빠지지 않는 SQL과 분석 인터뷰를 다루겠습니다.
