# Data Science Career 101 (2/10): 분석가 vs 사이언티스트 vs 엔지니어

입문자가 데이터 직무를 알아볼 때 가장 자주 묻는 질문은 결국 이것입니다. "분석가와 사이언티스트와 엔지니어는 정확히 뭐가 다른가요?" 겉으로 보면 모두 SQL과 Python을 쓰고, 모두 데이터를 다루기 때문에 차이가 흐릿하게 느껴질 수 있습니다.

하지만 실무에서는 누가 어떤 질문을 맡고, 어떤 결과물을 남기고, 무엇으로 평가받는지가 분명히 다릅니다. 이 차이를 모르고 준비하면 학습 계획도 넓게만 퍼지고, 지원서도 애매해지기 쉽습니다.

이 글은 Data Science Career 101 시리즈의 두 번째 글입니다.

![Data Science Career 101 2장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/data-science-career-101/02/02-01-concept-at-a-glance.ko.png)
*Data Science Career 101 2장 흐름 개요*

> 세 역할을 구분하는 가장 빠른 기준은 도구가 아니라 '목적과 산출물'을 보는 것입니다.

## 이 글에서 다룰 문제

- 분석가, 사이언티스트, 엔지니어가 각각 어떤 목적을 중심에 두는지 비교한다
- 세 역할이 만드는 대표 산출물을 정리한다
- 주요 도구와 성과 지표가 왜 달라지는지 설명한다
- 역할 선택이 커리어 방향에 어떤 영향을 주는지 살펴본다
- 주니어와 시니어가 이 주제에서 다르게 생각하는 지점을 짚는다

## 세 역할의 목적

세 역할은 공통적으로 데이터를 다루지만 각자의 목적이 다릅니다.

```text
Analyst: answer questions — 질문에 답한다
Scientist: validate hypotheses — 가설을 검증한다
Engineer: guarantee data flow — 데이터 흐름을 보장한다
```

목적이 다르면 필요한 역량도 달라집니다. 질문에 답하는 역할은 빠르고 명확한 해석 능력이 중심입니다. 가설을 검증하는 역할은 실험 설계와 통계적 사고가 핵심입니다. 데이터 흐름을 보장하는 역할은 신뢰성과 자동화 감각이 우선입니다.

## 대표 산출물 비교

직무는 산출물로 가장 선명하게 드러납니다.

```text
Analyst: dashboards, reports — 대시보드와 분석 리포트
Scientist: experiments, models — 실험 결과와 예측 모델
Engineer: pipelines, schemas — 파이프라인과 데이터 스키마
```

포트폴리오를 만들 때 지원 역할의 산출물과 일치하는 프로젝트를 골라야 합니다. Analyst 지원에 모델 코드만 있으면 미스매치입니다.

## 역할별 핵심 비교표

| 구분 | Analyst | Scientist | Engineer |
| --- | --- | --- | --- |
| 핵심 목적 | 의사결정 지원 | 가설 검증 | 데이터 흐름 보장 |
| 주요 도구 | SQL, BI Tool | Python, Notebook, Stats | Airflow, dbt, Kafka |
| 대표 산출물 | 대시보드, 지표 리포트 | 실험 설계, 모델 프로토타입 | ETL 파이프라인, 스키마 |
| 성과 지표 | 의사결정 반영률 | 실험 신뢰도, 모델 성능 | SLA, 데이터 품질 |
| 협업 상대 | PM, 마케팅, 사업팀 | PM, 리서치, 분석가 | 백엔드, 플랫폼, 분석팀 |
| 자주 쓰는 사고 방식 | 세그먼트 분해, 트렌드 해석 | 인과 추론, 모델 평가 | 데이터 모델링, 장애 대응 |

## 실제 커리어 시나리오

### 시나리오 A — Analyst 트랙

신입 DA 지은은 이커머스 팀에 합류해 첫 주에 "신규 사용자 구매 전환율이 왜 낮은가"라는 질문을 받았습니다. 그는 퍼널 단계별 이탈 지점을 SQL로 분해하고, 유입 채널별 차이를 비교해 모바일 결제 단계에서 60% 이탈이 발생한다는 사실을 발견했습니다. 이 분석이 UI 개선 스프린트의 근거가 되었습니다. 지은의 핵심 가치는 숫자를 빠르게 구조화해 팀이 다음 행동을 결정하도록 돕는 것이었습니다.

### 시나리오 B — Scientist 트랙

DS 준호는 "알림 시간대를 바꾸면 7일 리텐션이 올라갈까?"라는 가설을 받았습니다. 그는 A/B 테스트 설계를 문서화하고, 샘플 크기 계산 후 2주 실험을 진행했습니다. 결과를 통계적으로 검증해 저녁 8시 알림이 리텐션을 6% 개선한다는 결론을 도출했습니다. 준호의 핵심 가치는 "이것이 진짜 효과인가"를 신뢰할 수 있는 방법으로 판단하는 것이었습니다.

### 시나리오 C — Engineer 트랙

DE 수연은 마케팅 팀이 월요일 아침마다 리포트 수치가 틀리다고 불평하는 문제를 받았습니다. 조사 결과 원천 DB에서 웨어하우스로 오는 파이프라인이 주말에 실패하고 있었습니다. 스케줄러 설정을 수정하고 품질 체크 알럿을 추가했습니다. 수연의 핵심 가치는 다른 모든 역할이 신뢰할 수 있는 데이터를 받도록 기반을 지키는 것이었습니다.

## 면접에서 역할별 답변 방식

같은 면접 질문도 역할에 따라 좋은 답변의 구조가 달라집니다.

**질문: "전환율이 떨어졌습니다. 무엇부터 보시겠습니까?"**

| 역할 | 답변 시작 방향 | 핵심 포인트 |
| --- | --- | --- |
| Analyst | "먼저 어느 세그먼트에서 얼마나 떨어졌는지 퍼널 기준으로 확인합니다." | 지표 정의와 분해 단계 |
| Scientist | "데이터 파이프라인 문제인지, 제품 변경 영향인지, 외부 요인인지 가설 셋을 먼저 세웁니다." | 가설 구조와 검증 계획 |
| Engineer | "파이프라인 로그를 먼저 확인해 원천 데이터 수집이 정상인지 보겠습니다." | 데이터 신뢰성 검증 |

**질문: "이 모델을 어떻게 평가하시겠습니까?"**

| 역할 | 답변 시작 방향 | 핵심 포인트 |
| --- | --- | --- |
| Analyst | "어떤 의사결정에 쓰이는지 먼저 확인하고 해석 가능성을 기준으로 평가합니다." | 비즈니스 연결성 |
| Scientist | "문제 유형에 맞는 지표 precision/recall/AUC를 먼저 정하고 기준선 대비 개선 폭을 봅니다." | 지표 선택 근거 |
| Engineer | "학습-서빙 스키마 일치 여부, 응답 시간, 장애 복구 절차를 확인합니다." | 운영 안정성 |

## 역할별 포트폴리오 구성 가이드

지원 역할에 맞는 포트폴리오 구성이 있습니다.

**Analyst 포트폴리오 필수 요소**

```text
1. 비즈니스 문제를 지표로 정의한 문서
2. SQL로 구현한 퍼널/코호트 분석
3. 결과를 한 문장 권고안으로 요약한 메모
4. 가정과 한계를 명시한 분석 노트
```

**Scientist 포트폴리오 필수 요소**

```text
1. 가설-지표-검증 순서가 담긴 실험 설계 문서
2. 기준선(baseline) 대비 모델 성능 비교표
3. 피처 중요도와 선택 근거 설명
4. 결과 해석과 후속 실험 제안
```

**Engineer 포트폴리오 필수 요소**

```text
1. DAG 구조와 스케줄 설명 문서
2. 데이터 품질 체크 규칙 5개 이상
3. 장애 발생 시 복구 절차 명시
4. 재실행 가능한 파이프라인 코드
```

## 자주 하는 실수

| 실수 유형 | 구체적 사례 | 개선 방향 |
| --- | --- | --- |
| 도구만 보고 역할을 분류함 | "SQL을 쓰니까 DA겠지"라고 단정 | 산출물과 협업 상대를 먼저 확인 |
| 세 역할을 동시에 완벽하게 준비함 | 모델링, 파이프라인, 대시보드를 한꺼번에 공부 | 목표 역할 하나를 골라 집중 |
| 성과 지표를 모르는 채 지원함 | Analyst 면접에서 AUC만 말함 | 역할별 평가 기준을 외부 JD와 비교 |
| 역할 경계를 너무 엄격하게 구분함 | "DS는 파이프라인 안 해도 되겠지"라고 오해 | 조직 규모에 따라 역할이 겹친다는 점 인지 |
| 역할 선택 없이 공통 기술만 공부함 | SQL, Python, ML을 수박 겉핥기로 모두 배움 | 공통 기반 이후 역할 특화 학습 순서를 지킴 |

## 커리어 래더: 주니어에서 미드레벨로 넘어가는 기준

역할별로 다음 단계로 전환하는 기준이 다릅니다.

| 역할 | 주니어 기준 | 미드레벨 전환 신호 |
| --- | --- | --- |
| Analyst | 요청받은 분석을 정확하게 수행 | 문제를 스스로 정의하고 지표를 제안 |
| Scientist | 주어진 데이터에서 모델을 만듦 | 실험 설계와 검증 계획을 독립적으로 수립 |
| Engineer | 주어진 파이프라인을 유지보수 | 스키마 설계와 운영 자동화를 주도 |

## 시니어는 이렇게 생각합니다

주니어는 역할의 경계에 집착하는 경향이 있습니다. 시니어는 자기 역할을 깊이 파면서도 옆 역할과 대화할 수 있는 T자형 역량을 갖춥니다. Analyst가 Scientist의 실험 설계를 이해하면 더 좋은 질문을 던질 수 있고, Engineer가 Analyst의 질문 패턴을 알면 더 유용한 테이블 구조를 설계할 수 있습니다.

역할 경계는 유연하게 보되 책임은 분명히 두어야 합니다. 모든 역할을 겸하는 사람이 아니라, 핵심 역할에서 깊이 있는 기여를 하면서 협업 상대와 원활히 소통하는 사람이 오래 성장합니다.

## 처음 질문으로 돌아가기

- **분석가, 사이언티스트, 엔지니어가 각각 어떤 목적을 중심에 두는지 비교한다**
  - Analyst는 질문에 답하고, Scientist는 가설을 검증하며, Engineer는 데이터 흐름을 보장합니다. 목적이 다르면 역량 우선순위도 달라집니다.
- **세 역할이 만드는 대표 산출물을 정리한다**
  - Analyst는 대시보드와 리포트, Scientist는 실험 결과와 모델, Engineer는 파이프라인과 스키마입니다. 포트폴리오는 지원 역할의 산출물 유형과 일치해야 합니다.
- **주요 도구와 성과 지표가 왜 달라지는지 설명한다**
  - 도구는 목적을 따라옵니다. SQL을 써도 질문을 풀기 위해 쓰는지, 파이프라인을 설계하기 위해 쓰는지에 따라 역할이 나뉩니다.
- **역할 선택이 커리어 방향에 어떤 영향을 주는지 살펴본다**
  - 역할 선택은 학습 우선순위, 포트폴리오 구성, 면접 답변 방향 모두에 영향을 줍니다. 방향이 없으면 모든 것을 조금씩 하다가 어디서도 깊이가 없어집니다.
- **주니어와 시니어가 이 주제에서 다르게 생각하는 지점을 짚는다**
  - 주니어는 역할 경계를 두고 자기 영역을 지키려 하고, 시니어는 경계를 이해하면서도 옆 역할과 유연하게 협업합니다. 역할을 아는 것과 협업하는 것은 다른 능력입니다.

## 운영 체크리스트

- [ ] 세 역할의 목적을 각각 한 문장으로 설명할 수 있다
- [ ] 각 역할의 대표 산출물을 하나씩 안다
- [ ] 역할별 주요 도구를 하나씩 적어 봤다
- [ ] 지원 역할에 맞는 포트폴리오 구성을 정리했다
- [ ] 같은 면접 질문에 역할별로 다르게 답변하는 연습을 했다

## 정리

세 역할은 경쟁 관계라기보다 분업 구조에 가깝습니다. 분석가는 질문을 구조화하고, 사이언티스트는 실험과 모델로 검증하고, 엔지니어는 그 과정이 안정적으로 돌아가게 받쳐 줍니다. 어떤 역할이 본인과 맞는지는 어떤 문제를 풀 때 에너지가 올라오는지를 기준으로 판단하는 편이 좋습니다.

다음 글에서는 입문자 관점에서 실제 학습 순서를 어떻게 짜야 하는지 12주 로드맵으로 정리하겠습니다.
