# 바이브코딩을 위한 데이터 사이언스 커리어 (1/10): 데이터 직무란 무엇인가

이 글은 **바이브코딩을 위한 데이터 사이언스 커리어** 시리즈의 첫 번째 글입니다. AI와 함께 데이터 직무를 준비하는 방법을 실전 관점으로 풀어 갑니다.

---

채용 공고 수십 개를 AI에게 요약시켜 봤는데도 여전히 막막했던 경험이 있을 것입니다. "데이터 사이언티스트 모집"이라고 써 놓고 SQL 대시보드를 만들라 하고, "데이터 분석가 채용"이라면서 ML 모델 배포 경험을 요구합니다. AI에게 "이 공고 분석해 줘"라고 물어봐도 핵심이 안 잡힙니다.

바이브코딩 환경에서 데이터 커리어를 탐색하는 사람이라면 이 혼란을 더 강하게 느낄 수 있습니다. AI가 코드를 빠르게 생성해 주지만, 어떤 역할에 지원해야 할지 방향이 없으면 코드를 잘 짜도 소용이 없습니다. 데이터 직무의 지형을 먼저 읽어야 AI 툴도 올바른 방향으로 쓸 수 있습니다.

실제로 바이브코딩으로 포트폴리오를 빠르게 만드는 사람들 사이에서도 "분석가 포지션에 ML 엔지니어 포트폴리오를 들고 갔다"는 미스매치가 자주 일어납니다. 직함이 아니라 역할의 본질을 먼저 이해해야 방향이 생깁니다.

> 데이터 직무의 핵심은 직함이 아니라 책임 경계입니다. 각 역할이 어떤 문제를 맡고 어떤 산출물을 만드는지가 진입 기준이 되어야 합니다.

## 이 글에서 다룰 문제

- 채용 공고를 읽어도 analyst, scientist, engineer의 실제 차이가 잘 보이지 않는 이유는 무엇인가
- 같은 회사에서도 역할 정의가 팀마다 달라서 어디에 지원해야 할지 판단하기 어려운 상황을 어떻게 돌파하는가
- 직함이 아니라 무엇을 기준으로 역할을 구분해야 공부 방향을 잡을 수 있는가
- 다섯 가지 주요 역할이 각각 어떤 문제와 산출물을 다루는가
- 바이브코딩 환경에서 역할을 잘못 이해하면 어떤 학습 낭비가 생기는가

## 데이터 직무를 보는 멘탈 모델

데이터가 가치로 이어지는 과정을 단순화하면 이런 흐름입니다. 원천 데이터가 쌓이고, 그것이 정제되어 분석 가능한 형태가 되고, 분석과 모델을 거쳐 의사결정이나 제품 기능으로 연결됩니다. 이 흐름의 어느 구간을 책임지느냐가 역할을 가릅니다.

분석가(Analyst)는 이 흐름의 끝에서 일합니다. 정제된 데이터를 받아 비즈니스 질문에 답하고, 의사결정에 필요한 인사이트를 만듭니다. 사이언티스트(Scientist)는 가설을 세우고 실험과 모델로 검증하는 일을 합니다. 엔지니어(Engineer)는 데이터가 끊기지 않고 안정적으로 흐르도록 기반을 만듭니다.

바이브코딩 관점에서 보면, AI에게 "대시보드 만들어 줘"라고 하면 그건 Analyst 업무이고, "분류 모델 학습시켜 줘"라고 하면 그건 Scientist 업무이며, "데이터 파이프라인 자동화해 줘"라고 하면 그건 Engineer 업무입니다. AI 프롬프트의 방향이 곧 역할의 방향입니다.

## Before / After 비교

| 구분 | Before (역할 혼동) | After (역할 이해) |
|---|---|---|
| 포트폴리오 방향 | ML 모델 + 대시보드 + 파이프라인 전부 | 목표 역할에 맞는 산출물 집중 |
| AI 활용 방향 | 무작정 "데이터 분석 코드 짜 줘" | "DA 포지션 위한 퍼널 분석 SQL 짜 줘" |
| 면접 준비 | 모든 기술 스택 나열 | 역할별 핵심 질문/산출물 기준으로 정리 |

## 역할별 핵심 비교

| 구분 | DA | DS | DE | MLE |
|---|---|---|---|---|
| 핵심 질문 | 무슨 일이 일어났는가 | 어떤 가설이 맞는가 | 데이터가 안정적으로 흐르는가 | 모델이 운영에서 안정적인가 |
| 대표 산출물 | 대시보드, 분석 리포트 | 실험 결과, 모델 프로토타입 | 데이터 파이프라인, 스키마 | 추론 API, 배포 파이프라인 |
| 바이브코딩 AI 프롬프트 | SQL + 시각화 생성 | 모델 학습 + 평가 | DAG + 품질 체크 | 서빙 API + 모니터링 |

## 자주 하는 실수

| 실수 | 바이브코딩 상황에서의 문제 |
|---|---|
| 직함으로 역할 판단 | AI가 만들어 준 코드가 실제 JD와 안 맞음 |
| 산출물 없이 기술만 나열 | 포트폴리오 README가 기술 목록만 됨 |
| 역할 경계 모르고 공부 | AI에게 뭘 물어봐야 할지 방향이 없음 |
| 도메인 없이 기술만 | AI 결과를 비즈니스 맥락으로 해석 못함 |
| 세 역할 동시 준비 | 깊이 없는 포트폴리오 3개 양산 |

## AI 활용 팁

바이브코딩으로 데이터 커리어를 준비할 때 역할 이해가 된 이후의 AI 활용법:

- **DA 준비**: "다음 비즈니스 질문을 CTE 기반 SQL로 풀어 줘. 지표 정의와 NULL 처리 포함."
- **DS 준비**: "이 분류 문제에서 precision과 recall 트레이드오프를 설명하는 코드와 해석을 써 줘."
- **DE 준비**: "Airflow DAG으로 일별 집계 파이프라인 만들어 줘. 품질 체크 포함."
- **역할 분류**: "이 채용 공고에서 핵심 산출물과 협업 상대가 뭔지 분석해 줘."

## 체크리스트

- [ ] 지원하고 싶은 역할을 하나 골라 핵심 질문, 산출물, 협업 상대를 적었다
- [ ] 관심 있는 채용 공고 3개를 역할 신호 기준으로 분해해 봤다
- [ ] AI에게 역할별 프롬프트를 다르게 써서 차이를 확인했다
- [ ] "직함이 같아도 실제 일이 다를 수 있다"는 감각을 갖췄다
- [ ] 내가 오래 풀고 싶은 문제 유형이 어느 역할에 가까운지 판단했다

## 처음 질문으로 돌아가기

- **analyst, scientist, engineer의 실제 차이가 잘 보이지 않는다** — 도구가 아니라 핵심 질문과 산출물을 기준으로 구분하면 차이가 선명해집니다.
- **어디에 지원해야 할지 판단하기 어렵다** — 채용 공고에서 "대표 산출물"과 "협업 상대"를 찾는 것이 역할을 읽는 가장 빠른 방법입니다.
- **직함이 아닌 무엇을 기준으로 구분해야 하는가** — 이 역할은 어떤 질문을 맡는가, 어떤 산출물을 남기는가, 누구와 협업하는가, 이 세 축이 기준입니다.

## 정리

데이터 직무를 이해하는 첫걸음은 "모두 데이터를 본다"는 뭉뚱그린 시선을 버리는 일입니다. 역할마다 풀어야 하는 문제, 만드는 산출물, 협업 상대, 평가 기준이 다릅니다. 이 차이를 초반에 구분해 두면 바이브코딩으로 만드는 포트폴리오 방향도, AI에게 던지는 프롬프트 방향도 훨씬 또렷해집니다.
