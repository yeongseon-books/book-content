# 바이브코딩을 위한 Data Science Career 기초 (8/10): 첫 직장 적응

이 글은 "바이브코딩을 위한 Data Science Career 기초" 시리즈의 8번째 글입니다.

---

첫 데이터 직무에 합류하면 대부분은 기술보다 속도에서 압박을 느낍니다. 빨리 성과를 보여 줘야 할 것 같고, 아는 것이 부족하다는 사실이 더 크게 보이기 때문입니다. 그래서 데이터 지도도 없이 대시보드 수정이나 티켓 처리부터 반복하다가, 정작 중요한 맥락은 놓치는 경우가 많습니다.

하지만 첫 90일의 핵심은 존재감을 과시하는 데 있지 않습니다. 어떤 데이터가 어디서 오고, 누가 무엇을 중요하게 보고, 작은 신뢰를 어디서 만들 수 있는지 읽는 데 있습니다. 초반에 이 지도를 그려 두면 이후 제안의 방향도 훨씬 안정적이 됩니다.

데이터 직무는 문맥 의존성이 높아서, 도메인과 데이터 출처를 모른 채 기술만 앞세우면 방향이 쉽게 어긋납니다. 반대로 이해관계자와 데이터 지도를 먼저 정리하면 작은 개선도 훨씬 더 적절한 문제를 겨냥하게 됩니다.

30/60/90일 온보딩 구간, 데이터 지도 그리기, 이해관계자 파악, 빠른 성과 만들기, 문서화 습관을 정리합니다.

> **핵심 인사이트:** 첫 90일의 핵심은 지도를 그리는 것입니다. 데이터가 어디서 오고, 누가 무엇을 중요하게 보는지 파악하면 이후 모든 제안의 방향이 안정적이 됩니다.

## 이 글에서 다룰 문제

- 첫 90일을 어떤 단계로 나눠야 할까요?
- 초반에 무엇을 듣고 기록해야 할까요?
- 데이터 지도와 이해관계자를 왜 빨리 파악해야 할까요?
- 빠른 성과(quick win)는 어떻게 찾을까요?
- 온보딩 기간에 남겨야 할 문서는 무엇인가요?

## 온보딩 핵심 패턴

```text
30/60/90일 온보딩 구간:
1-30일: 관찰과 지도 그리기
  - 데이터 소스 목록화 (어디서 오는가?)
  - 핵심 KPI와 대시보드 파악
  - 팀과 이해관계자 파악
  - 기존 쿼리/코드베이스 읽기

31-60일: 작은 성과 만들기
  - 자주 반복되는 작업 자동화
  - 기존 대시보드 개선 1건
  - 이해관계자와 1:1 미팅

61-90일: 프로젝트 주도
  - 독립적인 분석 프로젝트 1건 완료
  - 팀 공유 발표 1회
  - 데이터 문서화 기여
```

```sql
-- 데이터 지도 탐색: 핵심 테이블 파악
SELECT table_name, pg_size_pretty(pg_total_relation_size(quote_ident(table_name)))
FROM information_schema.tables
WHERE table_schema = 'public'
ORDER BY pg_total_relation_size(quote_ident(table_name)) DESC
LIMIT 20;
```

## 변경 전후 비교

**Before: 지도 없이 빠른 성과 추구**
```text
- 데이터 출처 모르고 숫자 분석
- 이해관계자 파악 없이 보고서 작성
- 맥락 없는 개선 제안
- 팀이 이미 시도했던 분석 반복
```

**After: 지도 먼저, 성과는 그 다음**
```text
- 30일: 데이터 지도 + 이해관계자 파악
- 60일: 작은 개선 1건 + 신뢰 구축
- 90일: 독립 프로젝트 + 발표
- 문서화로 지식을 팀 자산으로 전환
```

## 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 방법 |
|------|-------------|-----------|
| 첫 주부터 큰 프로젝트 제안 | 맥락 없는 제안은 신뢰 저하 | 30일은 관찰과 질문에 집중 |
| 이해관계자 파악 없이 보고서 작성 | 니즈와 다른 내용으로 시간 낭비 | 1:1 미팅으로 먼저 기대 확인 |
| 질문을 두려워함 | 잘못된 방향으로 며칠씩 낭비 | 짧고 구체적인 질문이 전문성 표시 |
| 문서화 미룸 | 지식이 개인 경험으로 소모 | 배운 것을 그날 짧게라도 기록 |
| 팀이 이미 시도한 것 반복 | 불필요한 중복 작업 | 기존 분석/코드베이스 먼저 탐색 |

## 운영 체크리스트

- [ ] 핵심 데이터 테이블과 출처를 문서화했다
- [ ] 팀의 핵심 KPI와 대시보드를 파악했다
- [ ] 주요 이해관계자와 1:1 미팅을 진행했다
- [ ] 첫 60일 안에 quick win을 1건 만들었다
- [ ] 배운 내용을 팀 위키 또는 문서로 남겼다

## 처음 질문으로 돌아가기

- **첫 90일을 어떻게 나눠야 하나요?** 30일은 관찰과 지도 그리기, 60일은 작은 성과와 신뢰 구축, 90일은 독립 프로젝트 주도입니다.
- **데이터 지도를 먼저 그려야 하는 이유는?** 데이터 출처를 모르면 분석 방향이 언제든 잘못될 수 있습니다. 지도가 있어야 제안이 안정적입니다.
- **질문을 두려워하면 안 되는 이유는?** 짧고 구체적인 질문은 모름의 표시가 아니라 빠른 학습 의지의 표시입니다. 질문 없이 며칠을 낭비하는 것이 더 위험합니다.

## 정리

첫 직장 적응에서 빠른 성과보다 중요한 것은 데이터 지도와 이해관계자 파악입니다. 30일 관찰, 60일 작은 성과, 90일 독립 프로젝트 순서로 진행하면 신뢰와 방향 둘 다 안정적으로 잡을 수 있습니다. 다음 글에서는 도메인 전문성 쌓기를 다룹니다.
