# 바이브코딩을 위한 데이터 사이언스 커리어 (4/10): 데이터 포트폴리오

이 글은 **바이브코딩을 위한 데이터 사이언스 커리어** 시리즈의 네 번째 글입니다.

---

바이브코딩으로 포트폴리오를 만드는 사람들이 가장 많이 하는 실수가 있습니다. AI가 코드를 빠르게 만들어 주다 보니 GitHub에 저장소가 10개, 20개씩 쌓이는데, 막상 면접관이 열어보면 README는 비어 있고, 코드만 있고, 왜 이 프로젝트를 했는지 설명이 없습니다.

채용 담당자는 저장소 개수가 아니라 문제를 어떻게 정의하고 어떤 판단을 내렸는지를 봅니다. AI가 코드를 순식간에 만들어 주는 시대에, 오히려 더 중요해진 것은 "왜 이 접근을 선택했는가"와 "결과가 무엇을 의미하는가"입니다.

바이브코딩으로 만든 포트폴리오가 약해 보이는 이유는 코드가 짧거나 기술이 없어서가 아닙니다. 문제 정의와 결론이 없기 때문입니다. AI가 코드를 써줘도, 서사는 본인이 써야 합니다.

> 포트폴리오에서 가장 중요한 것은 무엇을 할 수 있는가가 아니라, 어떤 문제를 어떻게 풀었고 결론이 무엇인가입니다.

## 이 글에서 다룰 문제

- 바이브코딩으로 빠르게 만든 포트폴리오가 왜 약해 보이는가
- 코드만 있는 저장소가 왜 면접에서 불리한가
- README를 어떤 구조로 작성해야 하는가
- AI가 코드를 써줘도 포트폴리오를 강하게 만드는 방법은 무엇인가
- 바이브코딩 포트폴리오에서 재현 가능성이 왜 더 중요한가

## 바이브코딩 포트폴리오 3종 구성

### 프로젝트 1: 분석 프로젝트 (DA 포지션 필수)

AI와 함께 만들어도 이것만은 직접:
- 문제 정의 1문단 (비즈니스 맥락 포함)
- 가장 중요한 발견 1개를 한 문장으로
- 이 분석이 어떤 의사결정에 쓰이는지

### 프로젝트 2: 모델 프로젝트 (DS 포지션 필수)

```python
# AI가 코드를 써줬어도 이건 직접 작성
"""
프로젝트: 이탈 예측 모델
문제: 월 이탈률 15%를 사전에 예측해 리텐션 캠페인 대상 선정
접근: 로지스틱 회귀 vs XGBoost 비교, 임계값 최적화
결과: recall 0.72 달성, 기준선 대비 18% 개선
한계: 최근 3개월 데이터만 사용, 계절성 미반영
다음 단계: 12개월 이력 추가, 행동 피처 보강
"""
```

### 프로젝트 3: 파이프라인 프로젝트 (DE 포지션 필수)

재현 가능성이 핵심:

```bash
# AI가 만든 프로젝트라도 이건 직접 확인
git clone <repo>
uv pip install -r requirements.txt
make data    # 데이터 다운로드
make run     # 파이프라인 실행
make test    # 품질 체크
# 이 네 명령어가 README에 있어야 함
```

## Before / After 비교

| 항목 | Before (AI 복붙 포트폴리오) | After (서사 있는 포트폴리오) |
|---|---|---|
| README | 없거나 "This is my project" | 문제 → 접근 → 결과 → 재현 방법 |
| 코드 설명 | 주석 없음 | 결정 이유 노트 포함 |
| 결론 | 없음 | 한 줄 요약 + 의사결정 연결 |
| 재현성 | "제 컴퓨터에서는 됩니다" | 실행 명령어 README에 명시 |
| 면접 활용 | 링크만 줌 | "이 프로젝트에서 ~~를 해결했고, 결과는 ~~입니다" |

## 자주 하는 실수

| 실수 | AI 시대 포트폴리오에서 더 치명적 | 해결 방법 |
|---|---|---|
| README 없음 | AI도 코드 쓸 수 있는 시대에 차별화 없음 | 5섹션 README 템플릿 필수 |
| 결론 없음 | 코드만 있으면 AI가 쓴 것과 구분 안됨 | 한 문장 결론 + 의사결정 연결 |
| 재현 불가 | 협업 능력 의심 | 새 환경에서 직접 실행 테스트 |
| 시각화 과다 | 핵심이 묻힘 | 핵심 차트 1개, 비교 표 1개, 결론 1줄 |
| AI 사용 숨김 | 신뢰도 하락 | 투명하게 "AI 도움 받은 부분" 명시 |

## AI 활용 팁

포트폴리오 작성에 AI를 제대로 쓰는 방법:

- **문제 정의**: "이 데이터셋으로 어떤 비즈니스 문제를 풀 수 있는지 5가지 제안해 줘"
- **README 초안**: "이 프로젝트 README를 문제-접근-결과-재현 구조로 작성해 줘"
- **결론 문장**: "이 분석 결과를 의사결정자에게 전달하는 한 문장으로 요약해 줘"
- **약점 분석**: "이 모델의 비즈니스 한계와 개선 방향을 3가지 정리해 줘"
- **면접 준비**: "이 프로젝트를 5분 안에 설명하는 스크립트 작성해 줘"

## 체크리스트

- [ ] 서로 다른 성격의 프로젝트 3개 중 최소 1개 완성했다
- [ ] 5섹션 README를 작성했다 (문제/데이터/접근/결과/재현)
- [ ] 재현 명령어를 새 환경에서 직접 테스트했다
- [ ] 한 문장 결론을 남겼다
- [ ] AI 사용 부분을 투명하게 표시했다

## 처음 질문으로 돌아가기

- **바이브코딩 포트폴리오가 왜 약해 보이는가** — 코드는 있지만 문제 정의와 결론이 없기 때문입니다.
- **README 구조는 어때야 하는가** — 문제 → 데이터 → 접근 → 결과 → 재현 방법 5섹션이 기본입니다.
- **AI 시대에 포트폴리오를 강하게 만드는 방법** — 코드가 아니라 서사와 판단 기록이 차별화 포인트입니다.

## 정리

바이브코딩으로 포트폴리오를 만드는 속도는 빨라졌지만, 면접관이 보는 것은 변하지 않았습니다. 코드보다 문제 정의와 결론 전달이 더 또렷한 포트폴리오가 강합니다. AI가 코드를 써줘도 서사는 본인이 써야 하고, 그 서사를 README에 체계적으로 담는 것이 바이브코딩 시대의 포트폴리오 전략입니다.
