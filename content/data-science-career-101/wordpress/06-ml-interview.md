# 바이브코딩을 위한 데이터 사이언스 커리어 (6/10): ML 인터뷰

이 글은 **바이브코딩을 위한 데이터 사이언스 커리어** 시리즈의 여섯 번째 글입니다.

---

바이브코딩으로 ML 모델을 빠르게 만들다 보면 이런 경험을 합니다. scikit-learn 코드는 AI가 뚝딱 만들어 주고, Kaggle 점수도 나오는데, 막상 ML 인터뷰에서 "이 문제에 왜 이 모델을 선택했나요?"라고 물으면 할 말이 없습니다.

면접관이 보고 싶은 것은 알고리즘 암기가 아닙니다. 어떤 비즈니스 문제를 풀고 있는지, 왜 이 지표를 선택했는지, 데이터 누수는 어떻게 확인했는지, 모델이 프로덕션에서 드리프트하면 어떻게 할지를 연결해서 말할 수 있는지를 봅니다.

바이브코딩으로 ML 인터뷰를 준비하는 올바른 방법은 AI에게 모델을 만들라고 시키는 게 아니라, "왜 이 접근을 선택해야 하는가"를 설명하는 논리를 연습하는 것입니다. AI는 코드 생성이 아니라 판단 검증 도구로 써야 합니다.

> ML 인터뷰에서 가장 중요한 것은 모델 암기가 아니라 문제 정의부터 운영까지 연결하는 판단 구조입니다.

## 이 글에서 다룰 문제

- ML 인터뷰가 실제로 어떤 영역을 평가하는가
- 모델 선택을 설명할 때 무엇을 먼저 말해야 하는가
- 평가 지표를 문제 정의와 함께 봐야 하는 이유는 무엇인가
- 바이브코딩으로 만든 모델 코드를 인터뷰에서 설명하는 방법은 무엇인가
- 데이터 누수, 드리프트 같은 운영 함정을 어떻게 대비하는가

## ML 인터뷰 핵심 4영역

### 영역 1: 문제 정의와 지표 선택

```text
면접 질문: "이탈 예측 모델을 만들어야 한다면 어떻게 접근하겠습니까?"

좋은 답변 구조:
1. 문제 정의: "30일 내 이탈 예측. 이탈 정의는 30일 미접속으로 하겠습니다."
2. 지표 선택: "리텐션 캠페인에 쓰이므로 recall이 더 중요합니다.
               FN(이탈할 사람을 놓침)이 FP(캠페인 낭비)보다 비용이 큽니다."
3. 베이스라인: "단순 비율 기준선부터 시작하겠습니다."
4. 한계 인식: "클래스 불균형이 있을 것이므로 SMOTE나 class_weight 고려하겠습니다."
```

### 영역 2: 모델 선택 논리

```python
# AI에게 물어볼 것이 아니라 직접 설명할 수 있어야 하는 비교
"""
로지스틱 회귀 선택 이유:
- 해석 가능성이 중요한 경우 (왜 이탈하는지 설명해야 할 때)
- 빠른 학습과 예측 필요 시
- 선형 결정 경계로 충분한 경우

XGBoost 선택 이유:
- 비선형 관계, 상호작용 피처가 많을 때
- 성능 최대화가 목표인 경우
- feature importance로 인사이트도 얻고 싶을 때
"""
```

### 영역 3: 운영 함정 대비

```python
# 데이터 누수 체크 (바이브코딩으로 만든 모델에서 자주 놓침)
# AI에게: "이 피처 리스트에서 데이터 누수 위험 있는 것 찾아줘"

# 위험한 피처 예시:
risky_features = [
    'total_purchases',      # 타겟 시점 이후 데이터 포함 가능
    'last_activity_days',   # 타겟 정의와 겹칠 수 있음
    'churn_flag_history',   # 직접적 누수
]
```

### 영역 4: 평가 지표 해석

```python
from sklearn.metrics import classification_report, roc_auc_score

# AI가 코드를 써줘도 이 해석은 직접 해야 함
report = classification_report(y_test, y_pred)
"""
precision = 0.72: 이탈 예측한 사람 중 72%가 실제 이탈
recall = 0.68: 실제 이탈자 중 68%를 잡아냄

비즈니스 해석:
캠페인 대상 100명 중 72명이 실제 이탈 위험.
32%가 이탈하지 않을 사람에게 불필요한 캠페인을 보냄.
실제 이탈자의 32%를 놓침.

판단: recall을 0.8까지 높이면 캠페인 ROI가 어떻게 변하는지 확인 필요.
"""
```

## Before / After 비교

| 상황 | Before (AI 의존) | After (판단 구조 보유) |
|---|---|---|
| 모델 선택 | "AI가 XGBoost 추천해서" | "클래스 불균형 있고 비선형 관계라서 XGBoost" |
| 지표 선택 | "accuracy 높게 나왔어요" | "FN 비용 > FP 비용이라 recall 중심" |
| 데이터 누수 | 몰랐음 | 타겟 시점 이후 데이터 포함 여부 항상 확인 |
| 면접 설명 | "코드는 AI가 써줬어요" | 판단 이유를 단계별로 설명 |
| 운영 고려 | 없음 | 드리프트 모니터링 계획 포함 |

## 자주 하는 실수

| 실수 | 문제 | 해결 방법 |
|---|---|---|
| 알고리즘 암기에 집중 | 판단 구조 없음 | 문제 유형 → 후보 모델 → 지표 비교 연습 |
| accuracy만 보고 성공 선언 | 클래스 불균형 무시 | confusion matrix 항상 확인 |
| 데이터 누수 체크 안 함 | 실전에서 모델 실패 | feature별 타겟 시점 대비 확인 |
| 베이스라인 없이 시작 | 개선이 얼마인지 모름 | 단순 모델로 기준선 먼저 잡기 |
| 운영 계획 없음 | 프로덕션 드리프트 대응 못함 | 모니터링 지표와 재학습 기준 준비 |

## AI 활용 팁

ML 인터뷰 준비에서 AI를 올바르게 쓰는 방법:

- **모델 비교**: "이 문제에서 로지스틱 회귀 vs XGBoost를 선택하는 기준을 정리해 줘"
- **판단 검증**: "내 모델 선택 이유가 논리적인지 검토해 줘"
- **누수 체크**: "이 피처 목록에서 데이터 누수 위험 요소를 찾아줘"
- **해석 연습**: "이 confusion matrix를 비즈니스 언어로 해석해 줘"
- **운영 시나리오**: "이 이탈 예측 모델이 프로덕션에서 드리프트할 수 있는 상황 3가지 알려줘"

## 체크리스트

- [ ] 문제 유형별 (분류/회귀/군집) 적합한 모델을 이유와 함께 설명할 수 있다
- [ ] precision vs recall 트레이드오프를 비즈니스 언어로 설명할 수 있다
- [ ] 데이터 누수 체크 방법을 알고 있다
- [ ] 바이브코딩으로 만든 모델 코드를 한 줄씩 설명할 수 있다
- [ ] 모델 드리프트 개념과 모니터링 방법을 안다

## 처음 질문으로 돌아가기

- **ML 인터뷰가 실제로 무엇을 평가하는가** — 알고리즘 암기가 아니라 문제 정의부터 운영까지 연결하는 판단 구조입니다.
- **모델 선택 설명에서 무엇을 먼저 말해야 하는가** — 문제 유형, 비즈니스 제약, 데이터 특성 순서로 설명합니다.
- **평가 지표를 문제 정의와 함께 봐야 하는 이유** — FP와 FN의 비용이 비즈니스마다 다르기 때문입니다.

## 정리

ML 인터뷰는 모델 암기 시험이 아닙니다. 바이브코딩으로 코드를 빠르게 만들 수 있게 됐지만, 면접에서는 그 코드 뒤의 판단을 설명해야 합니다. AI에게 "왜 이 접근인지 검토해 줘"를 묻는 방식으로 훈련하면 ML 인터뷰 실력이 빠르게 올라갑니다.
