# 바이브코딩을 위한 MLOps 기초 (1/10): AI 모델을 서비스로 올리려면 MLOps가 왜 필요한가

이 글은 바이브코딩을 위한 MLOps 기초 시리즈의 1번째 글입니다.

Claude에게 "이 데이터로 이탈 예측 모델 만들어줘"라고 했더니 30초 만에 코드가 나왔습니다. `fit`, `predict`, 정확도 92%. 흥분해서 팀장에게 보여줬더니 "그래서 이걸 어떻게 서비스에 쓰나요?"라는 질문이 돌아왔습니다. 모델을 매일 다시 돌려야 하는지, 언제 성능이 떨어지는지, 문제가 생기면 어떻게 되돌리는지 아무것도 없었습니다.

바이브코딩 시대에 AI는 모델 코드를 순식간에 만들어 줍니다. 그런데 그 모델을 프로덕션에 올리고 6개월 후에도 제대로 동작하게 만드는 것은 완전히 다른 이야기입니다. 데이터는 변하고, 사용자 패턴도 바뀌고, 어느 순간 모델이 엉뚱한 예측을 내놓기 시작합니다. 그 순간 무엇을 해야 하는지 모른다면, AI가 만들어 준 코드가 아무리 훌륭해도 서비스는 조용히 망가집니다.

MLOps는 "AI가 만든 모델을 프로덕션에서 살아남게 만드는 운영 루프"입니다. 더 복잡한 도구를 쓰는 일이 아니라, 같은 결과를 다시 만들 수 있고, 지금 모델 상태를 알 수 있으며, 문제가 생기면 어디로 돌아갈지 명확한 시스템을 만드는 일입니다.

> AI가 코드를 만들어도, 그 모델이 6개월 뒤에도 제대로 동작하게 만드는 건 MLOps 루프가 있어야 가능합니다.

## 이 글에서 다룰 문제
- AI가 만든 모델을 서비스에 올리면 왜 시간이 지나면 성능이 떨어질까요?
- MLOps는 단순히 ML에 DevOps를 붙인 것과 무엇이 다를까요?
- 데이터, 코드, 모델을 함께 관리한다는 말이 실제로 무엇을 의미할까요?
- 바이브코딩으로 시작할 때 MLOps에서 가장 먼저 챙겨야 할 것은 무엇일까요?
- MLOps를 도입하지 않으면 어떤 문제가 실제로 생길까요?

## 드리프트 유형 — 모델이 서서히 망가지는 이유

AI가 만들어 준 모델을 그냥 배포만 해두면 시간이 지나면서 세 가지 방식으로 망가집니다.

| 드리프트 유형 | 원인 | 탐지 방법 | 대응 |
|---|---|---|---|
| 데이터 드리프트 | 입력 분포 변화 | 통계 검정 (KS, PSI) | feature 재계산, 재학습 |
| 컨셉트 드리프트 | X와 y 관계 변화 | 성능 메트릭 하락 | 재학습, 모델 교체 |
| 예측 드리프트 | 모델 출력 분포 변화 | 예측값 분포 모니터링 | 카나리 배포, 롤백 |

바이브코딩으로 만든 모델이 한 달 뒤 "갑자기 이상해졌다"면 대부분 이 세 가지 중 하나입니다. 어느 유형인지 구분해야 올바른 조치를 취할 수 있습니다.

## AI와 MLOps 작업할 때 알아야 할 핵심 개념

- **MLOps**: 모델의 학습·배포·모니터링·재학습을 반복 가능한 운영 체계로 만드는 접근입니다.
- **CT(Continuous Training)**: 데이터나 성능 변화에 맞춰 모델을 다시 학습시키는 흐름입니다.
- **모델 레지스트리**: 학습된 모델 버전과 메타데이터를 보관하는 저장소입니다.
- **드리프트**: 입력 데이터나 모델 성능이 시간에 따라 달라지는 현상입니다.
- **피처 스토어**: 학습과 서빙에서 같은 피처 정의를 재사용하게 해 주는 계층입니다.

## Before / After

**Before**: 노트북에서 모델을 만들고 파일로 저장해서 서버에 올렸습니다. 운영 상태는 누군가가 눈으로 확인하거나 사용자 불만이 올 때 알게 됩니다.

**After**: 데이터와 모델 버전이 남고, 학습이 반복 가능하며, 예측 로그와 알림을 바탕으로 다시 개선 루프를 돌립니다. AI에게 "이 모델 재학습시켜줘"라고 할 때 무엇을 기준으로 해야 하는지도 명확해집니다.

## AI가 만든 모델에 MLOps 루프 붙여보기

AI가 만든 기본 코드에 최소한의 MLOps 요소를 추가하는 예제입니다.

```python
import hashlib, json, pickle, time
from sklearn.linear_model import LogisticRegression
import numpy as np

# 1단계: 데이터 버전을 남깁니다
data = [{"x": 1, "y": 0}, {"x": 2, "y": 1}]
snap = hashlib.sha1(json.dumps(data).encode()).hexdigest()[:10]
print("data version:", snap)

# 2단계: 모델을 학습합니다
X = np.array([[d["x"]] for d in data])
y = np.array([d["y"] for d in data])
model = LogisticRegression().fit(X, y)

# 3단계: 모델을 레지스트리에 등록합니다
import os
os.makedirs("registry", exist_ok=True)
with open("registry/model_v1.pkl", "wb") as f:
    pickle.dump(model, f)

# 4단계: 메타데이터를 함께 남깁니다
meta = {"data_version": snap, "model_version": "v1", "metric": float(model.score(X, y))}
print("meta:", meta)

# 5단계: 예측 로그를 남깁니다
log = {"ts": time.time(), "pred": int(model.predict([[1.5]])[0])}
print("log:", log)
```

AI에게 모델 코드를 받은 뒤 이 다섯 단계를 추가하면, 단순한 스크립트가 아니라 추적 가능한 운영 자산이 됩니다.

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| 모델 파일만 저장하고 데이터 버전 안 남김 | 재현 불가, 성능 차이 원인 불명 | 데이터 해시를 메타데이터에 포함 |
| 배포 후 모니터링 없음 | 드리프트를 사용자가 먼저 발견 | 예측 로그와 분포 모니터링 추가 |
| 재학습 기준이 없음 | 감으로 재학습, 팀마다 판단 다름 | 성능/드리프트 기반 트리거 정의 |
| 노트북을 그대로 프로덕션에 사용 | 재현성, 책임 경계 모두 무너짐 | 학습과 서빙 코드 분리 |

## AI에게 MLOps 관련 질문하는 팁

MLOps 작업을 AI에게 요청할 때 이 정보를 함께 주면 훨씬 실용적인 코드가 나옵니다.

1. **현재 운영 단계 설명**: "수동으로 모델을 배포하고 있는 Level 0 상태입니다"
2. **데이터 규모 전달**: "매일 1만 건의 새 데이터가 쌓입니다"
3. **재학습 주기 의도**: "성능이 일정 수준 이하로 떨어지면 재학습하고 싶습니다"
4. **팀 규모 컨텍스트**: "혼자 운영하는 소규모 프로젝트입니다"

## 운영 체크리스트
- [ ] 학습에 사용한 데이터 버전을 기록할 수 있습니다
- [ ] 배포된 모델 버전이 어느 것인지 알 수 있습니다
- [ ] 예측 로그를 어딘가에 저장하고 있습니다
- [ ] 재학습 시점을 판단할 기준이 문서화되어 있습니다
- [ ] 모델이 이상해졌을 때 이전 버전으로 돌아갈 방법이 있습니다

## 처음 질문으로 돌아가기

- **AI가 만든 모델을 서비스에 올리면 왜 시간이 지나면 성능이 떨어질까요?**
  - 세상이 변하기 때문입니다. 입력 데이터 분포가 달라지거나(데이터 드리프트), X와 y의 관계 자체가 바뀌면(컨셉트 드리프트) 학습 시점의 모델은 현재 상황에 맞지 않게 됩니다.
- **MLOps는 단순히 ML에 DevOps를 붙인 것과 무엇이 다를까요?**
  - 전통적 CI/CD는 코드 동작 검증이 중심이지만, MLOps는 코드와 데이터가 결합된 모델 행태 검증까지 포함합니다. 모델은 코드만 바뀌지 않아도 데이터가 바뀌면 달라집니다.
- **데이터, 코드, 모델을 함께 관리한다는 말이 실제로 무엇을 의미할까요?**
  - 같은 데이터 + 같은 코드 = 같은 모델이 되도록 세 가지를 버전으로 묶어 추적하는 것입니다. 어느 하나가 빠지면 재현이 불가능합니다.
- **바이브코딩으로 시작할 때 MLOps에서 가장 먼저 챙겨야 할 것은 무엇일까요?**
  - 데이터 해시, 모델 메타데이터, 예측 로그 이 세 가지입니다. 거대한 플랫폼보다 이 기록들이 먼저입니다.
- **MLOps를 도입하지 않으면 어떤 문제가 실제로 생길까요?**
  - 최고 성능 모델을 다시 만들 수 없고, 배포가 매번 손작업이고, 드리프트를 사용자가 먼저 발견하고, 팀이 커질수록 혼란이 커집니다.

## 정리

바이브코딩으로 AI가 모델을 만들어 주는 속도는 이제 문제가 아닙니다. 문제는 그 모델을 프로덕션에서 오래 살아남게 만드는 일입니다. MLOps는 그 운영 루프를 시스템으로 만드는 접근입니다. 데이터 해시 하나, 메타데이터 한 줄, 예측 로그 한 줄이 쌓이면 AI가 만든 모델이 단순한 실험 결과물이 아니라 추적 가능한 운영 자산이 됩니다.
