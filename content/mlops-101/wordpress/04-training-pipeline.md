# 바이브코딩을 위한 MLOps 기초 (4/10): AI가 만든 학습 코드를 자동으로 돌리려면 — 학습 파이프라인

이 글은 바이브코딩을 위한 MLOps 기초 시리즈의 4번째 글입니다.

AI에게 "매일 새벽 2시에 모델을 다시 학습시키는 코드 만들어줘"라고 했더니 cron 설정과 `train.py` 실행 스크립트가 나왔습니다. 처음엔 잘 돌았는데, 한 달 뒤 새벽 3시에 슬랙 알림이 왔습니다. "학습 실패". 로그를 보니 전처리 단계에서 오류가 났는데, 그걸 확인하려면 300줄짜리 `train.py`를 전부 읽어야 했습니다. 어디서 실패했는지 바로 알 수 없었고, 그 전날 배치가 제대로 됐는지도 모호했습니다.

바이브코딩에서 AI는 학습 스크립트를 하나로 뚝딱 만들어 줍니다. 단일 파일로 돌아가는 동안은 문제없어 보입니다. 그런데 운영이 시작되면 이야기가 달라집니다. 데이터 수집, 전처리, 학습, 평가, 모델 등록이 모두 한 파일에 뭉쳐 있으면 어느 단계에서 실패했는지 찾기 어렵고, 일부만 다시 돌리는 것도 힘듭니다.

학습 파이프라인은 이 문제를 해결합니다. 학습 과정을 단계로 분해하고 DAG(방향성 비순환 그래프)로 연결하면, 어느 단계가 실패했는지 바로 보이고, 그 단계만 다시 돌릴 수 있으며, 바뀐 입력이 있는 구간만 재실행할 수 있습니다.

> AI가 만든 `train.py` 하나는 실험실에서 돌아갑니다. 프로덕션에서 오래 살아남으려면 단계를 나눠야 합니다.

## 이 글에서 다룰 문제
- AI가 만든 단일 학습 스크립트를 왜 여러 단계로 나눠야 할까요?
- DAG는 단순 실행 순서와 어떻게 다를까요?
- Airflow, Prefect 같은 오케스트레이터는 어디에 들어갈까요?
- 단계를 너무 크게 잡으면 어떤 문제가 생길까요?
- 바이브코딩에서 파이프라인을 설계할 때 AI에게 어떻게 요청해야 할까요?

## 오케스트레이터 비교

| 도구 | 학습 곡선 | 확장성 | 바이브코딩 추천 이유 |
|---|---|---|---|
| **Airflow** | 중간 | 대규모 | 커뮤니티 넓고 예제 풍부 |
| **Prefect** | 낮음 | 중간 | 로컬 시작 쉬움, 동적 DAG 가능 |
| **DVC Pipeline** | 낮음 | 중간 | 데이터 버전 관리와 통합 |
| **Kubeflow** | 높음 | 대규모 | Kubernetes 환경 전용 |

바이브코딩으로 처음 파이프라인을 만들 때는 Prefect나 DVC 파이프라인이 가장 빠르게 시작할 수 있습니다.

## AI와 MLOps 작업할 때 알아야 할 핵심 개념

- **단계(stage)**: 입력, 명령, 출력이 분리된 실행 단위입니다.
- **DAG**: 단계 사이의 의존 관계를 표현하는 방향성 비순환 그래프입니다.
- **멱등성**: 같은 입력이면 같은 출력을 다시 만드는 성질입니다.
- **캐싱**: 바뀐 단계만 다시 실행하도록 결과를 재사용하는 방식입니다.
- **재시도**: 일시적 오류 발생 시 같은 단계를 다시 실행하는 정책입니다.

## Before / After

**Before**: `train.py`를 cron으로 돌리고 실패하면 전체를 처음부터 다시 돌립니다. 전처리가 오래 걸리는데 학습에서 실패해도 전처리부터 다시 해야 합니다.

**After**: 전처리, 학습, 평가, 등록이 별도 단계로 나뉘어 있습니다. 학습 단계만 실패했다면 학습 단계만 재시작합니다. AI에게 "평가 단계만 다시 돌려줘"라고 요청할 수 있습니다.

## 단계를 나눈 학습 파이프라인 만들기

AI가 만든 단일 스크립트를 단계로 분리하는 예제입니다.

```python
import pandas as pd
import pickle
from sklearn.linear_model import LogisticRegression

# 1단계: 수집
def ingest():
    df = pd.DataFrame({"x": range(50), "y": [i % 2 for i in range(50)]})
    df.to_csv("/tmp/raw.csv", index=False)
    return "/tmp/raw.csv"

# 2단계: 전처리
def preprocess(path):
    df = pd.read_csv(path)
    df["x"] = (df["x"] - df["x"].mean()) / df["x"].std()
    out = "/tmp/clean.csv"
    df.to_csv(out, index=False)
    return out

# 3단계: 학습
def train(path):
    df = pd.read_csv(path)
    m = LogisticRegression().fit(df[["x"]], df["y"])
    with open("/tmp/model.pkl", "wb") as f:
        pickle.dump(m, f)
    return "/tmp/model.pkl"

# 4단계: 평가
def evaluate(data_path, model_path):
    df = pd.read_csv(data_path)
    with open(model_path, "rb") as f:
        m = pickle.load(f)
    return float(m.score(df[["x"]], df["y"]))

# 오케스트레이션
def run_pipeline():
    raw = ingest()
    clean = preprocess(raw)
    model = train(clean)
    metric = evaluate(clean, model)
    print({"metric": metric, "model": model})

run_pipeline()
```

각 함수의 입력과 출력이 명확하기 때문에, 이후 Airflow나 Prefect로 감쌀 때 구조를 그대로 쓸 수 있습니다.

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| 단계를 너무 크게 잡음 | 일부 실패에도 전체 재실행 | 입출력 기준으로 작게 분리 |
| 랜덤 시드 미고정 | 같은 입력인데 결과가 달라짐 | `random_state=42` 등 고정 |
| 출력 경로 고정 | 병렬 실행 시 파일이 덮어써짐 | run ID나 날짜를 경로에 포함 |
| 재시도 정책 없음 | 일시적 오류도 전체 실패로 처리 | retries=2 설정 |
| 알림 없음 | 야간 배치 실패를 다음날 출근 후 발견 | 슬랙/이메일 알림 연결 |

## AI에게 파이프라인 요청하는 팁

학습 파이프라인을 AI에게 요청할 때 이 정보를 함께 주면 훨씬 운영에 적합한 코드가 나옵니다.

1. **단계 명시**: "데이터 수집, 전처리, 학습, 평가, 등록 5단계로 나눠주세요"
2. **오케스트레이터 선택**: "Airflow DAG로 만들어주세요" 또는 "간단한 Python 함수로만 먼저 만들어주세요"
3. **실패 처리 요구**: "각 단계에 재시도 2회, 실패 시 슬랙 알림을 추가해주세요"
4. **캐싱 의도 전달**: "전처리 결과가 변경되지 않으면 재사용하도록 해주세요"

## 운영 체크리스트
- [ ] 학습 과정이 명확한 단계들로 분리되어 있습니다
- [ ] 각 단계의 입력과 출력이 명시되어 있습니다
- [ ] 재시도와 알림이 설정되어 있습니다
- [ ] 단계별 실행 시간을 모니터링할 수 있습니다
- [ ] 단계가 실패했을 때 그 단계만 재시작할 수 있습니다

## 처음 질문으로 돌아가기

- **AI가 만든 단일 학습 스크립트를 왜 여러 단계로 나눠야 할까요?**
  - 어디서 실패했는지 바로 찾을 수 있고, 실패한 단계만 다시 돌릴 수 있기 때문입니다. 단일 스크립트에서는 이 두 가지가 모두 어렵습니다.
- **DAG는 단순 실행 순서와 어떻게 다를까요?**
  - 단순 순서는 A→B→C처럼 직선이지만, DAG는 단계 간 의존 관계를 명시합니다. 전처리 코드가 바뀌면 그 이후 단계만 다시 돌아야 하는데, DAG가 이 관계를 정의합니다.
- **Airflow, Prefect 같은 오케스트레이터는 어디에 들어갈까요?**
  - 단계 정의는 개발자가 합니다. 오케스트레이터는 그 단계들을 스케줄링하고 실행 상태를 관리하는 인프라입니다.
- **단계를 너무 크게 잡으면 어떤 문제가 생길까요?**
  - 실패 원인을 좁히기 어렵고, 불필요하게 많은 부분을 다시 실행하게 됩니다.
- **바이브코딩에서 파이프라인을 설계할 때 AI에게 어떻게 요청해야 할까요?**
  - 단계 이름과 입출력을 먼저 설명하고, 어떤 오케스트레이터를 쓸지 명시하면 됩니다.

## 정리

바이브코딩에서 AI가 만들어 준 `train.py` 하나는 실험실에서는 충분합니다. 그런데 매일 자동으로 돌아야 하고, 실패를 빨리 복구해야 하고, 팀원이 이해할 수 있어야 하는 프로덕션에서는 단계가 나뉘어야 합니다. 좋은 파이프라인은 학습 속도보다 실패 복구 속도를 먼저 높입니다. 다음 글에서는 이렇게 만들어진 모델을 API로 배포하는 방법을 다룹니다.
