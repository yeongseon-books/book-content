# 바이브코딩을 위한 MLOps 기초 (3/10): 어제 데이터랑 오늘 데이터가 달라졌다 — 데이터 버전 관리

이 글은 바이브코딩을 위한 MLOps 기초 시리즈의 3번째 글입니다.

지난주에 AI가 만들어 준 학습 코드로 정확도 89%를 기록했습니다. 이번 주에 같은 코드를 다시 돌렸더니 84%가 나왔습니다. AI에게 물어봤더니 "코드는 동일합니다"라고 합니다. 그렇다면 왜 결과가 다를까요? 데이터가 바뀌었기 때문입니다. 데이터 파이프라인에서 뭔가 변경됐거나, 전처리 스크립트를 누군가 수정했거나, 원천 DB의 값이 업데이트됐습니다. 그런데 어떤 데이터로 지난주 결과가 나왔는지 아무 기록이 없었습니다.

바이브코딩에서 AI는 코드를 버전으로 관리하라고 git을 권장합니다. 그런데 ML에서는 코드만큼 중요한 게 데이터입니다. 같은 코드라도 다른 데이터면 다른 모델이 됩니다. 코드는 git에 남아 있어도, 그때 어떤 데이터를 사용했는지 추적하지 않으면 재현은 불가능합니다.

데이터 버전 관리는 파일 백업이 아닙니다. 팀이 같은 입력을 같은 방식으로 다시 가져와서 같은 결과를 만들 수 있게 하는 재현성 계약입니다. DVC 같은 도구를 쓰면 대용량 데이터 파일을 git에 넣지 않고도, 어떤 데이터 버전으로 어떤 모델을 만들었는지 추적할 수 있습니다.

> 코드가 같아도 데이터가 바뀌면 다른 모델이 됩니다. AI가 만든 코드를 재현하려면 데이터 버전이 반드시 함께 있어야 합니다.

---

## 이 글에서 다룰 문제
- 코드 버전만 관리하면 왜 AI가 만든 학습 결과를 재현하기 어려울까요?
- DVC와 git-LFS는 어떤 차이로 이해하면 좋을까요?
- 대용량 데이터 파일을 git 바깥에 두면서도 버전 일관성을 어떻게 유지할까요?
- 데이터 버전 관리를 하지 않으면 어떤 문제가 반복될까요?
- 바이브코딩 프로젝트에서 최소한 어떻게 시작해야 할까요?

## DVC vs git-LFS 비교

| 기준 | git-LFS | DVC |
|---|---|---|
| 파일 크기 | 수백 MB까지 적합 | GB~TB 규모 가능 |
| 파이프라인 | 없음 | `dvc.yaml`로 DAG 정의 |
| 원격 저장소 | Git 호스팅 LFS 서버 | S3, GCS, Azure, SSH 등 |
| 캐싱 | 없음 | 단계별 캐싱 지원 |
| 바이브코딩 추천 | 소규모 바이너리 몇 개 | 학습 데이터 + 파이프라인 |

바이브코딩 프로젝트에서 데이터가 수십 MB 정도라면 git-LFS로 간단하게 시작할 수 있습니다. 그 이상이거나 학습 파이프라인을 자동화하고 싶다면 DVC가 더 적합합니다.

## AI와 MLOps 작업할 때 알아야 할 핵심 개념

- **DVC**: git 위에서 데이터와 모델 버전을 추적하도록 돕는 도구입니다.
- **포인터 파일**: 해시와 메타데이터를 담아 실제 데이터 상태를 식별합니다. git에는 이 파일만 들어갑니다.
- **원격 저장소**: S3, GCS, 로컬 디렉터리처럼 실제 데이터 파일이 놓이는 장소입니다.
- **단계(stage)**: 입력, 명령, 출력이 정의된 파이프라인 단위입니다.
- **재현 실행(repro)**: 입력이 달라진 단계만 다시 실행하는 방식입니다.

## Before / After

**Before**: `data_v3_final.csv`가 팀원 노트북에만 있습니다. AI에게 "저번에 쓴 데이터로 다시 학습해줘"라고 해도 그 파일이 어디 있는지 찾을 수 없습니다.

**After**: `git pull && dvc pull`만으로 어디서나 같은 데이터셋을 다시 가져올 수 있습니다. AI에게 "data_version abc123에 해당하는 데이터로 재학습해줘"라고 정확하게 요청할 수 있습니다.

## DVC로 데이터 버전 관리 시작하기

AI가 만든 프로젝트에 데이터 버전 관리를 붙이는 최소 예제입니다.

```python
import pandas as pd
import hashlib, json

# 1단계: 샘플 데이터를 만듭니다
df = pd.DataFrame({"x": range(100), "y": [i % 2 for i in range(100)]})
df.to_csv("data.csv", index=False)

# 2단계: 포인터 파일을 흉내 냅니다 (DVC 없이 개념 확인)
h = hashlib.md5(open("data.csv", "rb").read()).hexdigest()
pointer = {"path": "data.csv", "md5": h}
with open("data.csv.ptr", "w") as f:
    json.dump(pointer, f, indent=2)
print("data pointer:", pointer)

# 3단계: 데이터 변경 감지
df.loc[0, "y"] = 1 - df.loc[0, "y"]
df.to_csv("data.csv", index=False)
new_h = hashlib.md5(open("data.csv", "rb").read()).hexdigest()
print("data changed:", new_h != h)
```

실제 DVC 사용 흐름:

```bash
# pip install dvc[s3]
# dvc init
# dvc add data/train.csv
# git add data/train.csv.dvc .gitignore
# git commit -m "Track training data v1"
# dvc push  # 원격 저장소로 업로드
```

AI에게 "DVC를 사용해서 이 데이터를 버전 관리하는 코드를 만들어줘"라고 요청하면 전체 설정 코드를 받을 수 있습니다.

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| 대용량 데이터를 git에 직접 커밋 | 저장소가 무거워지고 클론이 느려짐 | DVC나 LFS로 분리 |
| 원격 저장소 미설정 | 팀원은 포인터만 받고 데이터 못 받음 | dvc remote add 설정 필수 |
| 데이터 변경 후 버전 업데이트 안 함 | 학습 결과 차이 원인 설명 불가 | 데이터 변경 시 dvc add 재실행 |
| 데이터만 추적하고 모델은 별도 관리 | 데이터-모델 연결 고리가 약해짐 | 모델 아티팩트도 DVC로 추적 |

## AI에게 데이터 버전 관리 요청하는 팁

데이터 버전 관리가 포함된 프로젝트를 AI에게 요청할 때 이 정보를 함께 주면 좋습니다.

1. **저장소 유형 명시**: "S3 버킷을 원격 저장소로 사용합니다" 또는 "로컬 폴더로 시작합니다"
2. **데이터 규모 전달**: "학습 데이터가 약 500MB입니다"
3. **파이프라인 의도**: "전처리 단계와 학습 단계를 분리해서 관리하고 싶습니다"
4. **팀 규모 컨텍스트**: "3명이 함께 작업합니다. 원격 저장소 공유가 필요합니다"

## 운영 체크리스트
- [ ] 데이터 파일을 DVC나 LFS로 추적하고 있습니다
- [ ] 원격 저장소가 설정되어 있습니다
- [ ] 모델 아티팩트도 데이터 버전과 함께 추적합니다
- [ ] 데이터 변경 시 새 버전을 커밋하는 습관이 있습니다
- [ ] `git pull && dvc pull`로 다른 환경에서 재현이 가능합니다

## 처음 질문으로 돌아가기

- **코드 버전만 관리하면 왜 AI가 만든 학습 결과를 재현하기 어려울까요?**
  - 모델은 코드와 데이터가 만난 결과입니다. 코드가 같아도 데이터가 달라지면 다른 모델이 나옵니다.
- **DVC와 git-LFS는 어떤 차이로 이해하면 좋을까요?**
  - git-LFS는 대용량 파일을 git에서 관리하는 방식이고, DVC는 데이터 파이프라인 전체를 입력-출력 단계로 추적할 수 있는 더 강력한 도구입니다.
- **대용량 데이터 파일을 git 바깥에 두면서도 버전 일관성을 어떻게 유지할까요?**
  - DVC 포인터 파일을 git에 커밋하고, 실제 데이터는 원격 저장소에 두는 방식으로 해결합니다. 포인터의 해시가 바뀌면 데이터가 달라진 것을 시스템이 감지합니다.
- **데이터 버전 관리를 하지 않으면 어떤 문제가 반복될까요?**
  - 학습 결과를 재현할 수 없고, 성능 차이의 원인을 설명할 수 없고, 팀 협업에서 데이터 전달이 수동 작업으로 남습니다.
- **바이브코딩 프로젝트에서 최소한 어떻게 시작해야 할까요?**
  - 데이터 파일의 MD5 해시를 메타데이터에 남기는 것부터 시작하세요. 그것만으로도 "어떤 데이터로 이 모델이 만들어졌는지" 확인할 수 있습니다.

## 정리

바이브코딩에서 AI가 만들어 준 학습 코드를 재현하려면, 코드만 git에 넣는 것으로는 부족합니다. 그때 어떤 데이터를 사용했는지도 함께 고정되어야 진짜 재현이 됩니다. DVC를 사용하면 대용량 데이터 파일을 git 바깥에 두면서도 코드와 데이터를 한 버전으로 묶어 관리할 수 있습니다. 다음 글에서는 그 데이터와 코드를 자동으로 연결해 반복 실행하는 학습 파이프라인을 다룹니다.
