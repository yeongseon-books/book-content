# 바이브코딩을 위한 분산 시스템 기초 (1/10): 분산 시스템이란 무엇인가?

이 글은 **바이브코딩을 위한 분산 시스템 기초** 시리즈의 1편입니다. AI가 코드를 만들어 주는 시대에, AI가 만든 서비스를 실제로 스케일하려면 분산 시스템의 작동 원리를 알아야 합니다. 10편에 걸쳐 분산 시스템의 핵심 개념을 바이브코딩 관점에서 정리합니다.

---

바이브코딩으로 AI에게 "주문 서비스 만들어줘"라고 하면 코드는 순식간에 나옵니다. 하지만 사용자가 1만 명이 되는 순간, AI가 만들어 준 그 코드가 왜 갑자기 느려지거나 데이터를 잃는지 설명하지 못하게 됩니다. 그 답은 분산 시스템의 세 가지 현실, 즉 지연, 장애, 조정에 있습니다.

서비스를 둘로 나누는 순간, 같은 코드를 돌려도 더 이상 같은 세상에 살지 않습니다. 네트워크가 끼고, 한쪽만 느려지거나 죽을 수 있고, 각 노드가 보는 시간도 조금씩 다르기 때문입니다.

## 바이브코딩과 분산 시스템: 왜 지금 이것을 배워야 하나요?

바이브코딩(Vibe Coding)은 AI 모델과 대화하듯 코드를 작성하는 방식입니다. ChatGPT나 Claude에게 "FastAPI로 결제 API 만들어줘"라고 하면 그럴듯한 코드가 나옵니다. 문제는 그 코드가 단일 프로세스, 단일 머신을 가정하고 만들어진다는 점입니다.

**실제 서비스는 다릅니다.** 데이터베이스는 다른 서버에 있고, 결제 모듈은 외부 API를 호출하며, 사용자가 늘면 서버를 여러 대로 늘려야 합니다. 이 순간부터 AI가 만든 코드의 가정이 하나씩 깨지기 시작합니다.

### Before: 단일 머신 직관으로 AI 코드 읽기

```python
# AI가 만들어 준 주문 처리 코드 (단일 머신 가정)
def place_order(item_id: str, quantity: int):
    stock = get_stock(item_id)       # 항상 즉시 응답한다고 가정
    if stock < quantity:
        return {"error": "out of stock"}
    deduct_stock(item_id, quantity)  # 항상 성공한다고 가정
    charge_payment(quantity * price) # 항상 성공한다고 가정
    return {"ok": True}
```

이 코드는 단일 머신에서는 잘 동작합니다. 하지만 `get_stock`, `deduct_stock`, `charge_payment`가 각각 다른 서버라면 어떨까요?

### After: 분산 시스템 현실을 반영한 설계

```python
# 분산 환경을 이해하고 수정한 코드
def place_order(item_id: str, quantity: int, idempotency_key: str):
    # 타임아웃: 호출이 영원히 걸릴 수 있음
    try:
        stock = get_stock(item_id, timeout=1.0)
    except TimeoutError:
        return {"error": "재고 확인 불가 — 잠시 후 재시도"}

    if stock < quantity:
        return {"error": "품절"}

    # 멱등성 키: 재시도가 중복 처리로 이어지지 않도록
    try:
        result = charge_payment(
            quantity * price,
            idempotency_key=idempotency_key,
            timeout=2.0
        )
    except TimeoutError:
        # 모름 상태: 결제됐는지 안 됐는지 알 수 없음
        return {"status": "pending", "key": idempotency_key}

    return {"ok": True, "payment_id": result.id}
```

## 세 가지 핵심 축: 지연, 장애, 조정

### 지연: 모든 호출에는 시간이 걸린다

같은 머신 안의 함수 호출은 마이크로초입니다. 하지만 다른 서버를 호출하면 밀리초 단위로 뛰어오릅니다.

| 구간 | 전형적 지연 |
|------|------------|
| 같은 프로세스 함수 호출 | < 1μs |
| 같은 AZ 내 TCP RPC | 0.5~2ms |
| 서울 → 도쿄 | 30~50ms |
| 서울 → 미국 동부 | 80~120ms |

빛의 속도는 서울에서 버지니아까지 편도 약 60ms를 강제합니다. 코드 최적화로 줄일 수 없는 물리 법칙입니다.

### 장애: 일부가 죽어 있어도 시스템은 돌아간다

단일 머신에서 장애는 "전부 정상" 또는 "전부 정지" 둘 중 하나에 가깝습니다. 분산 환경에서는 상태 공간이 훨씬 넓어집니다.

| 장애 유형 | 호출자가 보는 것 |
|-----------|-----------------|
| 노드 크래시 | connection refused |
| 네트워크 단절 | timeout |
| 느린 노드 | timeout (크래시와 구분 불가) |
| 부분 성공 | 일부 복제본만 기록 성공 |

가장 어려운 점은 "느린 노드"와 "죽은 노드"가 호출자 관점에서 구분되지 않는다는 사실입니다. 둘 다 타임아웃으로 나타납니다.

### 조정: 여러 노드가 하나의 결정을 맞추는 과정

노드 A가 "B는 죽었다"고 판단하고, 노드 C는 "B는 방금 응답했다"고 할 때, 누구 말이 맞는가? 이 질문을 해결하려면 합의가 필요합니다. 합의에는 메시지 왕복이 필요하고, 메시지 왕복에는 지연이 붙습니다. 세 축이 순환적으로 엮여 있는 이유입니다.

## 자주 하는 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 타임아웃 없이 호출 | 응답이 영원히 오지 않을 수 있음 | 모든 외부 호출에 타임아웃 설정 |
| 멱등성 없이 재시도 | 중복 결제, 이중 처리 발생 | 멱등성 키 설계 후 재시도 |
| 벽시계 시간으로 순서 결정 | 노드마다 시계가 달라 순서 역전 | 논리 시계 또는 단조 시계 사용 |
| 부분 장애 무시 | 운영에서 가장 흔한 상태를 처리 못 함 | 모름 상태를 시스템 모델에 포함 |
| 단일 머신 지연으로 용량 계산 | 네트워크 지연이 예산을 초과 | 실제 P99 지연을 측정해 예산 설정 |

## AI 팁: AI가 만든 코드를 분산 환경에서 점검하는 법

1. **타임아웃 확인**: AI가 생성한 모든 외부 API 호출에 `timeout` 파라미터가 있는지 확인하세요.
2. **재시도 안전성 확인**: 재시도해도 부작용이 없는 연산인지(멱등성) 확인하세요.
3. **실패 시 동작 확인**: 외부 호출이 실패하면 어떤 상태를 반환하는지 코드로 확인하세요.
4. **벽시계 시간 의존 확인**: `datetime.now()`로 순서를 결정하는 코드는 분산 환경에서 위험합니다.

## 처음 질문으로 돌아가기

- **분산 시스템은 정확히 무엇이며 단일 머신 프로그램과 무엇이 다를까요?**
  독립적으로 동작하는 여러 노드가 메시지 전달을 통해 협력하는 시스템입니다. 단일 머신과 달리 지연, 부분 장애, 시계 불일치가 항상 존재합니다.

- **AI가 만든 코드가 스케일에서 실패하는 이유는 무엇일까요?**
  AI는 단일 머신의 직관으로 코드를 생성합니다. 타임아웃, 재시도, 멱등성, 부분 장애 처리가 빠져 있으면 실제 분산 환경에서 예측 불가능하게 동작합니다.

- **바이브코딩으로 서비스를 만들 때 가장 먼저 확인해야 할 것은 무엇일까요?**
  모든 외부 호출에 타임아웃이 있는지, 재시도 시 멱등성이 보장되는지, 타임아웃 발생 시 어떤 상태를 반환하는지를 먼저 점검해야 합니다.

## 정리

분산 시스템은 지연, 장애, 조정이라는 세 축에서 단일 머신 프로그램과 본질적으로 다릅니다. AI가 만들어 준 코드는 대부분 단일 머신을 가정하므로, 바이브코딩으로 서비스를 스케일하려면 이 세 축을 직접 이해하고 보완해야 합니다. 다음 글에서는 장애를 더 정밀하게 분류하는 장애 모델을 다룹니다.
