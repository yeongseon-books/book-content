# 바이브코딩을 위한 분산 시스템 기초 (5/10): 복제

이 글은 **바이브코딩을 위한 분산 시스템 기초** 시리즈의 5편입니다. AI가 만든 서비스를 스케일하려면 데이터가 어떻게 여러 노드에 복사되는지, 그 과정에서 무엇을 잃을 수 있는지를 알아야 합니다. 복제 설정 하나가 서비스가 약속하는 안전성을 통째로 바꿉니다.

---

AI에게 "PostgreSQL을 고가용성으로 설정해줘"라고 하면 replica 구성 코드가 나옵니다. 그런데 그 코드가 동기 복제인지 비동기 복제인지, 리더가 죽을 때 최근 쓰기를 얼마나 잃을 수 있는지를 모른 채 운영에 올리면 어느 날 데이터가 사라질 수 있습니다.

데이터를 여러 노드에 복사해 두면 안전할 것 같지만, 실제 운영 질문은 그 다음부터 시작됩니다.

> "복제 설정은 안전성과 속도 사이의 환율입니다. 어느 쪽을 더 중시하는지 먼저 결정해야 합니다."

## 바이브코딩과 복제: AI가 놓치는 RPO 설정

AI는 복제 설정 코드를 만들어 주지만 RPO(Recovery Point Objective, 허용 데이터 손실 시간)를 명시하지 않는 경우가 많습니다.

### Before: AI가 만든 비동기 복제 기본 설정

```python
# AI가 만들어 준 PostgreSQL 복제 설정 (비동기)
# postgresql.conf
# synchronous_commit = off  (기본값 — 비동기 복제)
# wal_level = replica

# 이 설정에서:
# - 쓰기 성능: 빠름
# - 리더 장애 시 최대 데이터 손실: 마지막 WAL flush 이후 모든 쓰기
# - RPO: 수 초 ~ 수 분
```

### After: RPO를 고려한 복제 설정

```python
# 결제/주문 같은 중요 데이터: 동기 복제
# postgresql.conf
# synchronous_commit = on        # 동기 복제 활성화
# synchronous_standby_names = '1 (replica1)'  # 최소 1개 replica 확인 후 커밋

# 로그/분석 같은 중요도 낮은 데이터: 비동기 복제
# synchronous_commit = local     # 로컬 WAL까지만 확인 후 커밋

# 애플리케이션 레이어에서 중요도에 따라 다른 연결 사용
CRITICAL_DB  = "postgresql://primary:5432/db?synchronous_commit=on"
ANALYTICS_DB = "postgresql://primary:5432/db?synchronous_commit=off"
```

## 복제 토폴로지: 세 가지 모델

| 모델 | 구조 | 장점 | 단점 |
|------|------|------|------|
| Leader-Follower | 쓰기는 리더, 읽기는 팔로워로 분산 | 단순, 읽기 스케일 가능 | 리더 병목, 복제 지연 |
| Multi-Leader | 여러 리더가 동시에 쓰기 수용 | 여러 DC에 걸쳐 쓰기 가능 | 충돌 해소 복잡 |
| Leaderless | 모든 노드가 동등, 쿼럼으로 판단 | 리더 단일 장애점 없음 | 쿼럼 설정 복잡 |

### 동기 vs 비동기 복제

```
동기 복제:
  클라이언트 → 리더 쓰기 → replica 확인 응답 대기 → 클라이언트에 OK
  RPO: 0 (데이터 손실 없음) / 지연: 높음

비동기 복제:
  클라이언트 → 리더 쓰기 → 클라이언트에 OK → (배경에서) replica로 복제
  RPO: 마지막 복제 이후 경과 시간 / 지연: 낮음
```

### 쿼럼: 몇 개의 노드에 써야 안전한가

`W + R > N` 공식이 핵심입니다. N개 노드 중 W개에 쓰고 R개에서 읽을 때, W+R이 N보다 크면 최신값을 반드시 읽을 수 있습니다.

| N | W | R | 특성 |
|---|---|---|------|
| 3 | 2 | 2 | 균형 — 1노드 장애에도 읽기/쓰기 가능 |
| 5 | 3 | 3 | 높은 내결성 — 2노드 장애까지 허용 |
| 5 | 1 | 5 | 빠른 쓰기, 느린 읽기 |

## 자주 하는 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 비동기 복제만 믿고 RPO를 0으로 가정 | 장애 시 수 분의 데이터 손실 | 중요 데이터는 동기 복제 또는 동기+비동기 혼합 |
| 복제본에서 항상 최신값 읽기 가정 | 결제 화면에서 오래된 잔액 표시 | 중요 읽기는 리더에서, 일반 읽기는 복제본에서 |
| 리더 장애 시 자동 페일오버 가정 | 수동 개입 필요하거나 split-brain 발생 | 페일오버 절차와 fencing 토큰 설계 필요 |
| 복제 지연을 모니터링하지 않음 | 복제본이 수 분 뒤처진 것을 모름 | replication lag P99를 지속 모니터링 |
| W+R≤N으로 쿼럼 설정 | 오래된 값을 읽을 수 있음 | W+R>N 조건 확인 |

## AI 팁: AI가 구성한 복제 설정 검토법

1. **RPO 확인**: "이 복제 설정에서 리더가 갑자기 죽으면 최대 몇 초 분량의 데이터를 잃을 수 있어?"
2. **동기/비동기 명시 요청**: "결제 데이터에는 동기 복제, 로그 데이터에는 비동기 복제를 사용하도록 분리해줘"
3. **복제 지연 모니터링 요청**: "PostgreSQL 복제 지연을 Prometheus로 모니터링하는 코드를 추가해줘"
4. **페일오버 절차 요청**: "리더 장애 시 자동 페일오버와 fencing 토큰 무효화 절차를 포함한 설정을 만들어줘"

```python
# 복제 지연 모니터링 예시
def check_replication_lag(conn):
    """복제 지연이 임계값 초과 시 경보"""
    result = conn.execute("""
        SELECT
            application_name,
            EXTRACT(EPOCH FROM (now() - write_lag)) AS lag_seconds
        FROM pg_stat_replication
    """)
    for row in result:
        if row["lag_seconds"] > 5.0:  # 5초 초과 시 경보
            alert(f"복제 지연 {row['lag_seconds']:.1f}초: {row['application_name']}")
```

## 처음 질문으로 돌아가기

- **동기 복제와 비동기 복제는 어떤 데이터 손실 위험을 만들까요?**
  동기 복제는 팔로워 확인 후 커밋하므로 RPO가 0에 가깝습니다. 비동기 복제는 리더가 먼저 커밋하고 나중에 팔로워로 복제하므로 장애 시 마지막 복제 이후 데이터를 잃을 수 있습니다.

- **AI가 구성한 DB 복제 설정에서 무엇을 확인해야 할까요?**
  synchronous_commit 설정(동기/비동기), 최소 동기 복제본 수, 복제 지연 모니터링 여부, 장애 시 페일오버 절차를 확인하세요.

- **RPO와 RTO가 복제 설정과 어떻게 연결될까요?**
  RPO(허용 데이터 손실)는 동기/비동기 복제 선택으로 결정됩니다. RTO(허용 서비스 중단 시간)는 자동 페일오버 속도로 결정됩니다. 둘 다 명시적으로 설계해야 합니다.

## 정리

복제 설정은 안전성(RPO)과 속도(쓰기 지연) 사이의 환율입니다. AI가 만들어 준 기본 설정이 비동기 복제라면 중요 데이터는 동기 복제로 바꾸고, 복제 지연을 모니터링하며, 페일오버 절차를 명시적으로 설계해야 합니다. 다음 글에서는 이 복제 위에서 여러 노드가 하나의 값에 동의하는 합의와 Raft를 다룹니다.
