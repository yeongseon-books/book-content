# Open Source 101 (9/10): 오픈소스 포트폴리오

오픈소스 활동을 조금 시작하고 나면 이런 고민이 생깁니다. 내 깃허브가 그냥 저장소 창고로 보이는지, 아니면 내가 어떤 문제를 어떻게 풀어 왔는지 보여 주는 포트폴리오로 보이는지입니다. 기여 횟수만 많다고 좋은 포트폴리오가 되지는 않습니다. 보는 사람은 숫자보다 맥락과 지속성을 더 봅니다.

이 글은 오픈소스 101 시리즈의 9번째 글입니다.

여기서는 깃허브 활동을 단순한 이력 나열이 아니라, 문제 선택과 해결 방식과 지속성을 보여 주는 포트폴리오로 정리하는 기준을 봅니다.

![Open Source 101 9장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/open-source-101/09/09-01-the-smallest-portfolio-structure.ko.png)
*Open Source 101 9장 흐름 개요*
> 오픈소스 포트폴리오의 강점은 **코드 목록이 아니라 협업 과정이 공개되어 있다**는 점입니다. 채용담당자는 코드와 함께 기여자의 의사소통을 읽을 수 있습니다.

## 이 글에서 다룰 문제

- 오픈소스 기여가 어떻게 포트폴리오가 될 수 있을까요?
- 프로필 소개 문서와 고정 저장소는 각각 무엇을 보여 줄까요?
- 수많은 활동 중 어떤 풀 리퀘스트를 대표 사례로 골라야 할까요?
- 이 개념을 실무에서 잘못 적용하면 어떤 문제가 생길까요?
- 이 주제에서 초보자가 가장 자주 놓치는 포인트는 무엇일까요?

## 왜 이 글이 중요한가

포트폴리오는 경력의 증거입니다. 특히 경력이 짧거나 특정 분야로 전환하려는 사람에게는, 실제로 공개된 협업 흔적이 말보다 강한 자료가 됩니다. 코드 리뷰를 받았고, 수정했고, 병합되었고, 문서를 남겼다는 기록은 면접에서 설명하기 좋은 구체성을 줍니다.

하지만 정리되지 않은 깃허브는 오히려 역효과를 낼 수 있습니다. 포크만 잔뜩 있고, 링크가 깨져 있고, 어떤 프로젝트가 대표 작업인지 알 수 없으면 보는 사람은 맥락을 읽기 어렵습니다. 포트폴리오는 양보다 편집이 중요합니다.

## 핵심 관점

좋은 포트폴리오는 두 가지를 동시에 보여 줍니다:

```text
"무엇을 했는가" (증거: PR 링크, 커밋, 릴리스)
  +
"왜 그 일이 의미 있는가" (서사: 문제 선택 이유, 접근 방식, 결과)
```

> 포트폴리오가 강해지는 이유는 숫자가 많아서가 아닙니다. 보는 사람이 "이 사람은 이런 문제를 골라 이런 방식으로 끝까지 밀어 왔구나"를 빠르게 이해할 수 있기 때문입니다.

## 핵심 개념

### 포트폴리오 구성 요소

| 요소 | 역할 | 부재 시 결과 |
|---|---|---|
| 프로필 README | 첫인상, 자기소개 | 깃허브가 저장소 목록으로만 보임 |
| 고정 저장소 (6개) | 대표 작업 전면 배치 | 방문자가 어디서 시작해야 할지 모름 |
| 대표 PR 목록 | 실제 협업 증거 | "어떤 사람인가"를 설명하기 어려움 |
| 기여 서사 | 성장 방향 설명 | 점수판처럼 보임 |
| 지속성 증거 | 꾸준한 활동 패턴 | 일회성 활동처럼 보임 |

### 고정 저장소 6개 선택 기준

```text
추천 구성:
- 원본 프로젝트 1개     ← 직접 만든 작은 도구
- 의미 있는 PR 2-3개   ← 실제 오픈소스 기여 링크
- 학습 저장소 1개       ← 특정 기술 심화 학습 기록
- 기여 중인 OSS 1개    ← 지속적으로 기여하는 프로젝트
```

## 프로필 README 작성 가이드

`<username>/<username>` 저장소를 만들면 프로필 첫 화면에 README가 표시됩니다.

```bash
# 프로필 README 저장소 생성
gh repo create yourusername --public
echo "# Hi, I'm [Your Name]" > README.md
git add README.md
git commit -m "feat: add profile README"
git push
```

## 대표 PR 선택 기준

모든 PR을 포트폴리오에 올리지 않습니다. 다음 기준으로 선별합니다.

### 좋은 대표 PR의 조건

```text
1. 실제로 머지된 PR (열려만 있는 PR보다 강력)
2. 문제 정의가 명확한 이슈와 연결됨
3. 리뷰 대화가 건설적으로 이루어짐
4. 테스트가 포함됨
5. 큰 프로젝트에 기여했다면 더 좋음
```

### 대표 PR 설명 템플릿

```markdown
### PR #142 — 로그인 세션 쿠키 버그 수정

**프로젝트**: psf/requests (PyPI 다운로드 주 3억+)

**문제**: Safari 15에서 세션 쿠키가 리다이렉트 후 초기화되는 버그

**접근 방식**:
1. 버그 재현 환경 구성 (Safari 15 + Python 3.11)
2. `HTTPAdapter.send()`의 리다이렉트 처리 코드 분석
3. 쿠키 병합 로직 수정 + 회귀 테스트 2개 추가

**결과**: 이슈 클로즈, 다음 PATCH 버전에 포함

**배운 점**: HTTP 리다이렉트 동작 방식, 쿠키 세션 관리, 대형 프로젝트 코드 리뷰 경험

**링크**: [PR](링크) | [Issue](링크) | [Commit](링크)
```

이 형식이 강한 이유는 "문제 → 접근 → 결과 → 배운 점 → 증거" 구조가 면접 답변과 동일한 흐름이기 때문입니다.

## 지속성 증거 만들기

강한 한 번보다 꾸준한 여러 번이 더 설득력 있을 때가 많습니다.

```bash
# 기여 패턴 확인
gh api users/yourusername/events/public \
  | jq '[.[] | select(.type == "PullRequestEvent")] | length'

# 주요 기여 저장소 목록
gh api users/yourusername/events/public \
  | jq '[.[] | select(.type == "PullRequestEvent") | .repo.name] | unique'
```

**권장 지속성 증거**:

```text
- 3개월 이상 동일 프로젝트에 기여 (꾸준한 관심)
- 주 2-3개 이상 커밋 (활동적인 패턴)
- 같은 프로젝트에 다양한 유형 기여 (버그 수정 + 문서 + 리뷰)
```

오픈소스 경험을 블로그 글로 정리하면 포트폴리오의 깊이가 더해집니다.

```markdown
## 블로그 글 연동 예시

### 오픈소스 기여 경험
- [첫 오픈소스 PR을 merge시키기까지](링크) — 준비 → 이슈 선택 → 리뷰 대응
- [Safari 세션 버그를 디버깅한 방법](링크) — 기술 분석 과정
- [오픈소스 코드 리뷰에서 배운 5가지](링크) — 리뷰어 관점 정리

### 프로젝트 개발기
- [mytool을 만든 이유와 첫 릴리스까지](링크)

```

프로젝트 README에 "Related Posts" 섹션을 추가하면 방문자가 개발 과정을 이해할 수 있습니다.

## 직접 따라해 보기: 포트폴리오 정리 절차

### 1단계 — 프로필 소개 문서 만들기

```bash
gh repo create yourusername --public
```

### 2단계 — 고정 항목 여섯 개 고르기

GitHub 프로필 → "Customize your pins" → 6개 선택

```text
추천 구성:
1. 직접 만든 프로젝트 (CI 배지 있는 것)
2. 가장 임팩트 있었던 OSS PR 저장소
3. 지속 기여 중인 OSS
4. 기술 학습 저장소
5-6. 추가 원본 프로젝트 또는 의미 있는 기여
```

### 3단계 — 대표 풀 리퀘스트 목록 만들기

```markdown
## Notable Open Source Contributions

| Project | PR | Description | Impact |
|---|---|---|---|
| psf/requests | [#5678](링크) | Fix Safari session cookie bug | v2.31.1 포함 |
| fastapi/fastapi | [#1234](링크) | Fix Optional type hint | v0.100.0 포함 |
| django/django | [#9012](링크) | 한국어 번역 200줄 | 공식 번역 반영 |
```

### 4단계 — 기여 서사 적기

```markdown
## My Open Source Journey

2024년 오타 수정으로 시작 →
2025년 버그 수정 PR 5개 머지 →
2026년 FastAPI 정기 이슈 트리아지 및 리뷰 참여 중

**현재 집중**: Python 비동기 처리, HTTP 클라이언트 라이브러리
```

### 5단계 — 지속성 증거 만들기

```text
목표: 최근 90일 기준 주 2회 이상 커밋 또는 리뷰
측정: GitHub 잔디 그래프 + 기여 저장소 다양성
```

## 자주 하는 실수

| 실수 | 구체적 상황 | 올바른 접근 |
|---|---|---|
| 포크만 쌓음 | 고정 항목에 포크가 5개 이상 | 포크는 숨기고 원본 프로젝트와 대표 PR 저장소 고정 |
| 프로필 README 없음 | 깃허브 프로필이 저장소 목록뿐 | `<username>/<username>` 저장소에 README 작성 |
| 깨진 링크 방치 | 대표 PR 링크가 오래된 URL 참조 | 분기마다 링크 점검, 머지된 PR은 영구 URL 사용 |
| 단발성 활동 | 3달 전 PR 1개 이후 활동 없음 | 정기적 기여 패턴 유지, 소규모라도 꾸준히 |
| 설명 없는 저장소 목록 | README 없이 저장소만 나열 | 각 저장소에 한 줄 설명 + 대표 항목 설명 작성 |

## 실무에서는 이렇게 생각한다

채용 팀이나 협업 상대는 종종 깃허브를 사전 참고 자료로 봅니다. 이때 중요한 것은 모든 저장소가 아니라, 내가 문제를 선택하고 끝까지 다듬은 흔적이 얼마나 명확한가입니다. 대표 풀 리퀘스트 몇 개와 짧은 설명만 잘 정리되어 있어도 대화의 질이 크게 달라집니다.

시니어 엔지니어는 포트폴리오를 숫자 경쟁으로 보지 않습니다. 잔디밭보다 맥락이 중요하고, 서른 개의 얕은 활동보다 세 개의 분명한 기여가 더 설득력 있습니다.

**면접에서 포트폴리오를 설명하는 방법**:

```text
좋은 설명:
"psf/requests에 기여했습니다. Safari 15에서 세션 쿠키가 리다이렉트 후
사라지는 버그였는데, HTTP 리다이렉트 처리 로직을 분석해서 쿠키 병합
위치가 잘못됐다는 걸 찾았습니다. 회귀 테스트를 추가하고 PR을 냈는데
메인테이너가 코드 스타일 제안을 해줬고, 반영 후 다음 패치 버전에
포함됐습니다."

나쁜 설명:
"GitHub에 오픈소스 기여를 했습니다. 버그 수정이요."
```

## 운영 체크리스트

- [ ] 프로필 소개 문서를 작성했습니다.
- [ ] 대표로 보여 줄 고정 항목을 골랐습니다.
- [ ] 대표 풀 리퀘스트 목록을 한곳에 정리했습니다.
- [ ] 최근 몇 달의 지속적 활동 흐름을 설명할 수 있습니다.
- [ ] 각 기여에 대해 "문제-접근-결과" 서사를 작성했습니다.

## 정리

## 처음 질문으로 돌아가기

- **오픈소스 기여가 어떻게 포트폴리오가 될 수 있을까요?**
  - 오픈소스 기여는 협업 과정이 공개됩니다. PR의 리뷰 대화, 커밋 메시지, 이슈 댓글이 모두 검증 가능한 증거로 남습니다. 이것은 이력서의 자기 소개와 달리 제3자(메인테이너)가 코드 품질을 검토하고 승인했다는 객관적 근거가 됩니다.
- **프로필 소개 문서와 고정 저장소는 각각 무엇을 보여 줄까요?**
  - 프로필 소개 문서는 "어떤 사람인가"를 보여 주는 첫인상입니다. 관심 분야, 기술 스택, 대표 기여를 한 눈에 보여 줍니다. 고정 저장소는 "어떤 일을 했는가"를 보여 주는 대표작 전시입니다. 포크가 아닌 원본 프로젝트와 의미 있는 기여를 배치합니다.
- **수많은 활동 중 어떤 풀 리퀘스트를 대표 사례로 골라야 할까요?**
  - 실제로 머지되었고, 재현 가능한 문제를 해결했으며, 리뷰 과정에서 의미 있는 피드백을 받고 개선한 PR이 좋습니다. 특히 문제 정의 → 접근 방식 → 결과를 한 단락으로 설명할 수 있는 PR을 선택하세요. 수백 줄짜리 기능 추가보다 10줄짜리 버그 수정이 더 좋은 대표 사례가 될 수 있습니다.
