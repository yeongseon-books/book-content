# 바이브코딩을 위한 프론트엔드 개발 기초 (5/10): 라우팅과 페이지

이 글은 **바이브코딩을 위한 프론트엔드 개발 기초** 시리즈의 다섯 번째 글입니다. AI에게 여러 페이지로 구성된 앱을 만들어 달라고 할 때, 라우팅이 어떻게 동작하는지 알아야 URL 문제와 배포 오류를 해결할 수 있습니다.

"AI야, 홈, 소개, 사용자 상세 페이지가 있는 React 앱 만들어줘"라고 하면 라우터 코드가 나옵니다. 그런데 배포 후 새로고침하면 404 오류가 뜨거나, 뒤로 가기가 이상하게 동작하거나, 링크를 공유하면 원하는 화면이 안 열리는 문제가 생길 수 있습니다. 라우팅의 동작 원리를 이해해야 이런 문제를 해결할 수 있습니다.

> 라우팅은 'URL과 컴포넌트 트리를 매핑하는 일'입니다. SPA / MPA / SSR / SSG 차이는 '이 매핑을 누가 언제 수행하는가(브라우저인가, 서버인가, 빌드 타임인가)'라는 한 가지 축으로 정리됩니다.

## 이 글에서 다룰 문제

- 단일 페이지 앱이 여러 화면을 보여 주는 원리는 무엇일까요?
- 경로(path)는 컴포넌트와 어떤 식으로 매핑될까요?
- 중첩 라우트와 동적 파라미터는 왜 필요한가요?
- 배포 후 새로고침 404 문제는 왜 생기고 어떻게 해결할까요?
- AI가 생성한 라우터 코드에서 자주 발생하는 문제는 무엇일까요?

## 바이브코딩 관점에서 시작하기

"AI야, React Router로 3페이지짜리 앱 만들어줘"라고 요청하면 라우터 설정 코드가 나옵니다. 하지만 "배포 후 `/about`에서 새로고침하면 404가 떠요"라는 문제가 생기면 어떻게 할까요? 이건 React Router 문제가 아니라 호스팅 서버의 SPA fallback 설정 문제입니다. 이 차이를 알아야 올바른 해결책을 AI에게 요청할 수 있습니다.

## 개념 한눈에 보기

| 용어 | 뜻 | 바이브코딩에서 왜 중요한가 |
|---|---|---|
| Route | URL 패턴과 컴포넌트의 매핑입니다. | AI가 생성한 라우터 설정을 읽고 수정하는 기준이 됩니다. |
| 중첩 라우트 | 다른 라우트 안에 들어가는 하위 라우트입니다. | 레이아웃 공유 패턴을 AI에게 요청할 때 명확한 언어를 제공합니다. |
| 동적 세그먼트 | `/users/:id`처럼 값이 들어갈 자리를 포함한 경로 패턴입니다. | 상세 페이지 URL 패턴을 AI에게 설명하는 기준이 됩니다. |
| 쿼리 문자열 | `?q=react&page=2`처럼 경로 밖에 붙는 추가 상태입니다. | 검색·필터 기능을 요청할 때 URL 상태 설계 기준이 됩니다. |
| Lazy loading | 필요한 라우트 코드만 나중에 불러오는 방식입니다. | AI에게 "코드 스플리팅 적용해줘"라고 요청하는 근거가 됩니다. |

## 전체 새로고침에서 URL 기반 화면 전환으로

| 방식 | 화면 이동 방식 | 실무 영향 |
|---|---|---|
| 서버 라우팅 + 전체 새로고침 | 클릭할 때마다 새 문서를 요청합니다. | 단순하지만 상호작용이 많은 앱에서는 전환 비용이 큽니다. |
| SPA 라우팅 | URL은 유지하면서 필요한 화면만 교체합니다. | 사용자 경험은 매끄럽지만, 새로고침과 배포 설정까지 같이 신경 써야 합니다. |

**Before (서버 라우팅, 전체 새로고침)**

```html
<a href="/about">About</a>
```

**After (SPA routing, smooth transition)**

```jsx
<Link to="/about">About</Link>
```

이 차이를 이해하면 AI가 생성한 `<Link>` 컴포넌트가 왜 일반 `<a>` 태그와 다르게 동작하는지, 배포 시 왜 SPA fallback 설정이 필요한지 자연스럽게 이해됩니다.

## AI 팁: 라우팅 요청 최적화

- **라우트 목록 먼저 제공**: "/, /about, /users/:id, 404 페이지 이렇게 4개의 라우트로 설정해줘"처럼 필요한 경로를 미리 나열하세요.
- **인증 보호 요청**: "로그인한 사용자만 접근 가능한 PrivateRoute 패턴을 포함해줘"를 명시하세요.
- **코드 스플리팅 요청**: "각 라우트를 lazy loading으로 분리해줘"를 추가하면 초기 번들이 가벼워집니다.
- **배포 설정 함께 요청**: "Netlify나 Vercel 배포 시 SPA history fallback 설정 방법도 알려줘"를 포함하세요.
- **404 페이지 포함**: "잘못된 URL에 대한 404 컴포넌트도 만들어줘"를 항상 요청하세요.

## 실수 유형과 바이브코딩 대처법

| 실수 유형 | 증상 | 바이브코딩 대처 |
|---|---|---|
| `<a>`와 `<Link>` 혼용 | SPA 장점이 사라짐 | "모든 내부 링크를 `<Link>`로 교체해줘" 요청 |
| 인증 보호 없는 경로 | URL 직접 입력으로 우회 가능 | "PrivateRoute 패턴으로 인증된 사용자만 접근 가능하게 해줘" 요청 |
| lazy loading 미적용 | 초기 번들이 무거움 | "모든 라우트를 React.lazy로 분리해줘" 요청 |
| 쿼리 문자열과 화면 상태 미동기화 | 새로고침 시 검색·필터 상태 사라짐 | "검색 상태를 URL 쿼리 파라미터로 동기화해줘" 요청 |
| 404 페이지 없음 | 잘못된 URL에서 빈 화면 | "catch-all 라우트로 404 컴포넌트 추가해줘" 요청 |

## 체크리스트

- [ ] 정적 라우트와 동적 라우트를 구분할 수 있습니다.
- [ ] `<Link>`와 `<a>`의 차이를 설명할 수 있습니다.
- [ ] `useParams`로 파라미터를 읽을 수 있습니다.
- [ ] lazy loading을 한 번 설정해 봤습니다.
- [ ] 404 페이지를 만들 수 있습니다.
- [ ] 배포 후 새로고침 404 문제의 원인과 해결 방법을 설명할 수 있습니다.

## 처음 질문으로 돌아가기

- **단일 페이지 앱이 여러 화면을 보여 주는 원리는 무엇일까요?**
  브라우저 URL을 변경하되 서버에 새 문서를 요청하지 않고, JavaScript가 URL을 읽어 해당하는 컴포넌트를 렌더링합니다. `History API`가 이 마법을 가능하게 합니다.

- **경로(path)는 컴포넌트와 어떤 식으로 매핑될까요?**
  라우터에 `{ path: "/about", element: <About /> }` 처럼 경로 패턴과 렌더링할 컴포넌트를 배열로 정의합니다. URL이 바뀌면 라우터가 일치하는 패턴을 찾아 해당 컴포넌트를 렌더링합니다.

- **배포 후 새로고침 404 문제는 왜 생길까요?**
  SPA는 모든 경로를 `index.html`로 처리해야 합니다. 그런데 기본 웹 서버는 `/about`을 `about.html` 파일로 찾아서 없으면 404를 반환합니다. 호스팅 서버에서 "모든 요청을 index.html로 리다이렉트"하는 SPA fallback 설정이 필요합니다.

## 정리

라우팅은 사용자가 무엇을 보는지 결정하는 URL 기반 상태 관리입니다. 이 흐름이 잡히면 이제 화면이 서버 데이터와 어떻게 연결되는지도 자연스럽게 이어집니다. 바이브코딩으로 라우터를 만들 때도 인증 보호, lazy loading, 404 처리를 처음부터 요청에 포함하는 습관을 들이세요.

다음 글에서는 프론트엔드가 서버에서 데이터를 가져오는 비동기 흐름을 살펴봅니다.
