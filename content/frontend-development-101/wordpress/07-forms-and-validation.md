# 바이브코딩을 위한 프론트엔드 개발 기초 (7/10): 폼과 유효성 검사

이 글은 **바이브코딩을 위한 프론트엔드 개발 기초** 시리즈의 일곱 번째 글입니다. AI에게 회원가입이나 로그인 폼을 만들어 달라고 할 때, 유효성 검사와 사용자 경험 원칙을 알아야 결과물을 올바르게 검토하고 개선할 수 있습니다.

AI가 생성한 폼은 보통 입력 필드와 제출 버튼은 있지만 실시간 검증, 친절한 에러 메시지, 접근성 속성이 빠지는 경우가 많습니다. "유효하지 않은 이메일"이라는 에러가 제출 후에야 나오거나, 스크린 리더가 에러를 읽지 못하거나, 비밀번호를 한 번만 입력받는 코드가 나올 수 있습니다.

> 폼은 '입력 받는 UI'가 아니라 '사용자 의도를 도메인 모델로 옮기는 좁은 통로'입니다. controlled vs uncontrolled, 클라이언트 검증과 서버 검증의 역할 분리가 명확하지 않으면 보안·UX·접근성이 한꺼번에 무너집니다.

## 이 글에서 다룰 문제

- controlled input과 uncontrolled input은 어떤 차이가 있을까요?
- 유효성 검사는 형식, 비즈니스 규칙, 서버 검증으로 왜 나눠 생각해야 할까요?
- 에러 메시지는 어디에, 언제 보여 주는 편이 가장 친절할까요?
- AI가 생성한 폼 코드에서 자주 빠지는 UX 요소는 무엇일까요?
- 접근성을 갖춘 폼을 만들기 위해 무엇을 명시해야 할까요?

## 바이브코딩 관점에서 시작하기

"AI야, 이메일과 비밀번호 입력받는 로그인 폼 만들어줘"라고 요청하면 HTML form 코드가 나옵니다. 그런데 이 폼이 실제 제품에서 쓰이려면 몇 가지가 더 필요합니다. 이메일 형식 실시간 검증, 비밀번호 최소 길이 경고, `<label>`과 `aria-invalid` 속성, 제출 중 버튼 비활성화. 이것들을 알아야 AI에게 처음부터 요청하거나 생성된 코드를 개선할 수 있습니다.

## 개념 한눈에 보기

| 용어 | 뜻 | 바이브코딩에서 왜 중요한가 |
|---|---|---|
| Controlled input | 입력값이 React state에 저장되는 방식입니다. | AI 생성 폼이 controlled 방식인지 확인하는 기준이 됩니다. |
| Uncontrolled input | 입력값이 DOM 안에 남아 있는 방식입니다. | 단순한 폼에서 AI가 이 방식을 쓸 수 있는데, 상태 추적이 어렵습니다. |
| Schema validation | Zod, Yup 같은 라이브러리로 선언적으로 검증하는 방식입니다. | "Zod 스키마로 검증 로직을 분리해줘"라고 요청하는 기준이 됩니다. |
| Inline error | 필드 옆이나 아래에 바로 보이는 에러 메시지입니다. | AI에게 "제출 후가 아니라 입력 중에 에러를 보여줘"라고 요청하는 개념입니다. |
| `aria-invalid` | 스크린 리더에 현재 필드가 유효하지 않음을 알리는 ARIA 속성입니다. | "접근성을 위해 aria-invalid와 aria-describedby를 추가해줘"라고 요청할 때 사용합니다. |

## 제출 후 경고창에서 입력 중 피드백으로

| 방식 | 피드백 시점 | 실무 영향 |
|---|---|---|
| 제출 후 한 번에 에러 노출 | 사용자가 제출해야만 문제를 알 수 있습니다. | 다시 돌아가 고치는 비용이 커지고 실패 경험이 거칠어집니다. |
| 입력 중 인라인 피드백 | 필드 단위로 즉시 수정 가능하게 돕습니다. | 전환율, 접근성, 폼 완료 속도 모두에 긍정적인 영향을 줍니다. |

**Before (제출 시에만 검증)**

```javascript
form.onsubmit = () => {
  if (email.value === "") alert("Please enter an email");
};
```

**After (실시간 인라인 검증 + 친절한 메시지)**

```jsx
{!isEmail(email) && email && (
  <p className="error" role="alert">
    올바른 이메일 형식이 아닙니다
  </p>
)}
```

AI에게 처음 요청할 때 "제출 버튼을 누르기 전에 각 필드에서 실시간으로 에러를 보여줘"라고 명시하면 첫 번째보다 두 번째 코드가 나옵니다.

## AI 팁: 폼 품질 향상 요청

- **접근성 속성 요청**: "모든 입력 필드에 `<label>`, `aria-invalid`, `aria-describedby`를 추가해줘"를 명시하세요.
- **실시간 검증 요청**: "onChange 이벤트에서 실시간으로 유효성을 검사하고 인라인 에러를 표시해줘"를 포함하세요.
- **제출 상태 처리 요청**: "제출 중에는 버튼을 비활성화하고 '제출 중...' 텍스트를 보여줘"를 추가하세요.
- **Zod 스키마 요청**: "검증 로직을 Zod 스키마로 분리해줘. 프론트와 백엔드 모두 재사용 가능하게"를 명시하면 더 구조적인 코드가 나옵니다.
- **키보드 접근성 요청**: "키보드만으로 폼 전체를 완료할 수 있도록 작성해줘"를 추가하세요.

## 실수 유형과 바이브코딩 대처법

| 실수 유형 | 증상 | 바이브코딩 대처 |
|---|---|---|
| 비밀번호 한 번만 입력 | 오타로 인한 가입 실패 | "비밀번호 확인 필드와 일치 검증 추가해줘" 요청 |
| 에러를 제출 후에만 표시 | 사용자가 모든 필드를 다시 확인해야 함 | "각 필드를 벗어날 때(onBlur) 에러를 표시해줘" 요청 |
| 기술적 에러 문구 그대로 노출 | "Schema validation failed"처럼 사용자에게 무의미 | "사용자 친화적인 한국어 에러 메시지로 바꿔줘" 요청 |
| `<label>` 없음 | 스크린 리더가 입력 의미를 모름 | "모든 input에 연결된 label을 추가해줘" 요청 |
| 모바일 키보드 힌트 없음 | 이메일 입력에 일반 키보드가 뜸 | "이메일 필드에 type='email', 전화번호에 type='tel' 설정해줘" 요청 |

## 체크리스트

- [ ] controlled input을 사용할 수 있습니다.
- [ ] inline 에러 메시지를 보여 줄 수 있습니다.
- [ ] 모든 입력에 `<label>`과 적절한 연결을 추가할 수 있습니다.
- [ ] `aria-invalid`와 `aria-describedby`의 역할을 설명할 수 있습니다.
- [ ] Zod나 Yup 같은 스키마 검증기를 사용해 봤습니다.
- [ ] AI가 생성한 폼에서 누락된 접근성 속성을 발견할 수 있습니다.

## 처음 질문으로 돌아가기

- **controlled input과 uncontrolled input은 어떤 차이가 있을까요?**
  controlled input은 입력값을 React state에 저장하고 `value` prop으로 연결합니다. 입력값을 언제든지 JavaScript에서 읽고 검증할 수 있어 실시간 유효성 검사에 유리합니다. uncontrolled는 ref로 DOM에서 직접 읽습니다.

- **유효성 검사는 형식, 비즈니스 규칙, 서버 검증으로 왜 나눠 생각해야 할까요?**
  형식 검사(이메일 형식 맞는지)는 프론트엔드에서, 비즈니스 규칙(이미 가입된 이메일인지)은 서버에서만 알 수 있습니다. 프론트 검증은 UX를 위한 것이고, 서버 검증은 보안을 위한 것입니다. 둘은 역할이 다릅니다.

- **에러 메시지는 어디에, 언제 보여 주는 편이 가장 친절할까요?**
  해당 필드 바로 아래에, 사용자가 필드를 떠나는 시점(onBlur) 또는 값이 변경되는 시점(onChange)에 보여 주는 것이 자연스럽습니다. 제출 버튼을 눌러야만 에러가 보이면 사용자 경험이 거칩니다.

## 정리

폼은 사용자와 가장 길게 만나는 인터페이스입니다. 바이브코딩으로 폼을 만들 때도 접근성 속성, 실시간 검증, 친절한 에러 메시지를 처음부터 요청하는 습관을 들이면 제품 품질이 크게 올라갑니다.

다음 글에서는 이 폼과 화면 전체에 일관된 모양을 부여하는 스타일링과 디자인 시스템을 살펴봅니다.
