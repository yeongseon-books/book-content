# 바이브코딩을 위한 프론트엔드 개발 기초 (8/10): 스타일링과 디자인 시스템

이 글은 **바이브코딩을 위한 프론트엔드 개발 기초** 시리즈의 여덟 번째 글입니다. AI에게 여러 화면의 스타일을 만들어 달라고 할 때, 디자인 토큰과 컴포넌트 기반 스타일 체계를 알아야 일관성이 무너지는 것을 방지할 수 있습니다.

AI가 페이지마다 스타일을 생성하면 버튼의 파란색이 페이지마다 조금씩 다르고, 간격 기준이 섞이고, 다크 모드를 나중에 붙이려면 전체를 다시 만져야 하는 상황이 생깁니다. 처음부터 디자인 토큰과 컴포넌트 기반 구조를 요청하면 이 문제를 방지할 수 있습니다.

> 스타일링의 핵심 질문은 '문법 선택'이 아니라 '스타일의 범위(scope)와 결합도를 어떻게 통제할 것인가'입니다. BEM·CSS Modules·Tailwind·CSS-in-JS는 같은 문제(전역 cascading)에 대한 서로 다른 답입니다.

## 이 글에서 다룰 문제

- 글로벌 CSS, CSS Modules, CSS-in-JS, Tailwind는 어떤 차이를 가질까요?
- 디자인 토큰은 왜 프로젝트가 커질수록 더 중요해질까요?
- 컴포넌트 라이브러리는 어떤 구조로 운영되는 편이 좋을까요?
- AI가 생성한 스타일 코드에서 자주 발생하는 일관성 문제는 무엇일까요?
- 다크 모드를 나중에 추가하지 않으려면 어떻게 설계해야 할까요?

## 바이브코딩 관점에서 시작하기

"AI야, 버튼 컴포넌트 스타일 만들어줘"라고 요청하면 CSS가 나옵니다. 하지만 다음 요청에서 "카드 컴포넌트 만들어줘"를 하면 버튼에서 쓴 파란색과 카드에서 쓰는 파란색이 다를 수 있습니다. 처음부터 "CSS 변수로 디자인 토큰 정의하고, 모든 색과 간격을 그 변수로 참조해줘"라고 요청하면 일관성 문제를 방지할 수 있습니다.

## 개념 한눈에 보기

| 용어 | 뜻 | 바이브코딩에서 왜 중요한가 |
|---|---|---|
| 디자인 토큰 | 색, 간격, 타이포그래피 같은 원자 단위 규칙입니다. | AI에게 "토큰 기반으로 작성해줘"라고 요청하면 변경이 쉬운 코드가 나옵니다. |
| CSS Modules | 클래스 이름 충돌을 자동으로 줄여 주는 방식입니다. | AI 생성 CSS에서 전역 충돌이 걱정될 때 요청하는 대안입니다. |
| CSS-in-JS | 컴포넌트 함수 안에서 스타일을 정의하는 접근입니다. | 상태 기반 스타일이 필요할 때 AI에게 옵션으로 제시할 수 있습니다. |
| Utility-first CSS | 작은 클래스를 조합해 스타일을 만드는 방식입니다. | Tailwind를 사용할 때 AI와 공유하는 공통 언어가 됩니다. |
| 컴포넌트 라이브러리 | 디자인 시스템을 구현한 재사용 가능한 컴포넌트 모음입니다. | AI에게 "새 컴포넌트 대신 기존 컴포넌트를 재사용해줘"라고 요청하는 기준입니다. |

## 페이지별 임의 스타일에서 토큰 기반 시스템으로

| 방식 | 스타일 관리 방식 | 실무 영향 |
|---|---|---|
| 페이지별 임의 값 사용 | 색상과 간격이 파일마다 흩어집니다. | 사소한 디자인 변경도 전역 수작업이 되고, 다크 모드는 특히 비싸집니다. |
| 토큰 + 컴포넌트 중심 | 값은 토큰으로, 사용법은 컴포넌트로 모읍니다. | 브랜드 변경, 코드 리뷰, 테마 확장이 훨씬 예측 가능해집니다. |

**Before (페이지마다 다른 색상)**

```css
.btn-a { background: #1d72ff; }   /* page A */
.btn-b { background: #1d70ff; }   /* page B (오타) */
```

**After (디자인 토큰)**

```css
:root { --color-primary: #1d72ff; }
.btn  { background: var(--color-primary); }
```

AI에게 "CSS 변수로 색상 토큰을 정의하고, 모든 색은 변수로만 참조해줘"라고 요청하면 두 번째 패턴의 코드가 나옵니다.

## AI 팁: 스타일 일관성 유지 요청

- **토큰 우선 요청**: "색상, 간격, 폰트 크기를 CSS 변수로 먼저 정의하고 시작해줘"를 프로젝트 초기에 요청하세요.
- **하드코딩 금지 요청**: "절대로 색상 코드를 직접 쓰지 말고 CSS 변수를 사용해줘"를 명시하세요.
- **다크 모드 사전 설계 요청**: "처음부터 dark mode 지원이 가능한 구조로 설계해줘. 토큰 값을 변경하는 방식으로"를 초기에 포함하세요.
- **Tailwind 토큰 확장 요청**: "Tailwind config에서 브랜드 색상과 커스텀 간격을 extend로 정의해줘"를 명시하세요.
- **컴포넌트 재사용 요청**: "기존 Button, Input 컴포넌트가 있으니 새로 만들지 말고 재사용해줘"를 상기시키세요.

## 실수 유형과 바이브코딩 대처법

| 실수 유형 | 증상 | 바이브코딩 대처 |
|---|---|---|
| 컴포넌트마다 색 하드코딩 | 디자인 변경 시 전체 수정 필요 | "모든 색을 CSS 변수로 교체해줘" 요청 |
| variant를 문서 없이 계속 추가 | 합의된 디자인과 코드 불일치 | "variant 목록을 컴포넌트 상단 JSDoc에 문서화해줘" 요청 |
| 다크 모드를 나중으로 미룸 | 색이 흩어져 전체 재작업 필요 | "지금 당장 dark mode를 쓰지 않더라도 토큰 구조로 준비해줘" 요청 |
| 간격을 모두 px로 박아둠 | 반응형·접근성 대응 어려움 | "px 대신 rem과 Tailwind spacing scale 사용해줘" 요청 |
| 컴포넌트 라이브러리에 비즈니스 로직 삽입 | 재사용성 저하 | "공용 컴포넌트에서 비즈니스 로직을 제거하고 순수 UI만 남겨줘" 요청 |

## 처음 질문으로 돌아가기

- **글로벌 CSS, CSS Modules, CSS-in-JS, Tailwind는 어떤 차이를 가질까요?**
  글로벌 CSS는 스코프가 없어 충돌 위험이 있습니다. CSS Modules는 파일별로 자동 스코프를 만듭니다. CSS-in-JS는 JavaScript 안에서 스타일을 정의합니다. Tailwind는 작은 유틸리티 클래스를 조합합니다. 모두 "전역 CSS 충돌을 어떻게 피할 것인가"라는 같은 문제의 다른 답입니다.

- **디자인 토큰은 왜 프로젝트가 커질수록 더 중요해질까요?**
  화면이 많아지고 개발자가 늘어날수록 같은 파란색을 서로 다른 값으로 쓰게 됩니다. 토큰으로 한곳에 정의하면 브랜드 색상 변경이 파일 하나로 끝납니다.

- **다크 모드를 나중에 추가하지 않으려면 어떻게 설계해야 할까요?**
  처음부터 색상을 `var(--color-primary)`처럼 토큰으로 참조하면, 다크 모드는 그 토큰 값만 바꾸는 문제가 됩니다. 구조 자체를 바꿀 필요가 없습니다.

## 정리

스타일링도 결국 공통 언어가 있어야 규모를 버팁니다. 바이브코딩으로 UI를 만들 때도 디자인 토큰과 컴포넌트 체계를 처음부터 요청하면 AI 생성 코드의 일관성이 크게 올라갑니다.

다음 글에서는 이 코드와 스타일을 브라우저가 읽을 수 있는 산출물로 바꾸는 빌드 도구와 번들링을 살펴봅니다.
