# 바이브코딩을 위한 프론트엔드 개발 기초 (4/10): 컴포넌트와 상태

이 글은 **바이브코딩을 위한 프론트엔드 개발 기초** 시리즈의 네 번째 글입니다. AI에게 React 컴포넌트를 만들어 달라고 요청할 때, props와 state가 어떻게 흐르는지 알아야 결과물을 올바르게 검토하고 수정할 수 있습니다.

AI가 생성한 React 코드를 보면 `useState`, `props`, 컴포넌트 분리 같은 패턴이 등장합니다. "이 상태는 어디에 있어야 하지?", "왜 이 컴포넌트가 다시 렌더링되지?", "props는 어떻게 전달하지?"라는 질문에 스스로 답할 수 있어야 코드를 효과적으로 활용할 수 있습니다.

> 컴포넌트는 'UI 조각'이 아니라 '상태(props/state)를 받아 화면을 돌려주는 함수'입니다. 이 함수형 모델이 잡히면 prop drilling·lifting state up·전역 상태 라이브러리 선택이 모두 같은 문제(상태를 어디에 둘 것인가)의 답으로 정리됩니다.

## 이 글에서 다룰 문제

- 컴포넌트 사고방식은 단순히 React 문법을 넘어서 무엇을 바꿔 줄까요?
- props와 state는 어떤 기준으로 구분해야 할까요?
- 단방향 데이터 흐름은 왜 대부분의 현대 프론트엔드 프레임워크의 기본 전제일까요?
- AI가 생성한 컴포넌트 코드에서 자주 발생하는 구조 문제는 무엇일까요?
- 상태를 어디에 두어야 할지 결정하는 기준은 무엇일까요?

## 바이브코딩 관점에서 시작하기

"AI야, 할 일 목록 앱을 React로 만들어줘"라고 요청하면 여러 컴포넌트가 나옵니다. 그런데 상태가 이상한 위치에 있거나, props가 불필요하게 깊이 전달되거나, 한 컴포넌트가 너무 많은 역할을 맡고 있을 수 있습니다. 컴포넌트와 상태 모델을 이해하면 이런 문제를 발견하고 수정을 요청할 수 있습니다.

## 개념 한눈에 보기

| 용어 | 뜻 | 바이브코딩에서 왜 중요한가 |
|---|---|---|
| 컴포넌트 | 화면의 한 조각을 그리는 함수입니다. | AI가 생성한 코드의 분리 기준을 이해하는 토대가 됩니다. |
| Props | 부모가 자식에게 내려주는 읽기 전용 값입니다. | AI가 props를 직접 수정하는 코드를 생성하면 잘못된 패턴임을 알 수 있습니다. |
| State | 컴포넌트가 내부에 유지하는 변경 가능한 값입니다. | AI에게 "이 값이 상태여야 하는지 props여야 하는지" 질문하는 기준이 됩니다. |
| 단방향 데이터 흐름 | 데이터가 위에서 아래로만 흐르는 구조입니다. | AI 코드에서 데이터가 양방향으로 흐르면 설계 문제 신호입니다. |
| 상태 끌어올리기 | 여러 자식이 공유해야 할 상태를 부모로 옮기는 방식입니다. | 두 컴포넌트가 같은 데이터를 봐야 할 때 어디에 상태를 둘지 결정하는 기준입니다. |

## 거대한 스크립트에서 컴포넌트 경계로

| 방식 | 구조 특징 | 실무 영향 |
|---|---|---|
| 한 파일에 모든 DOM 조작이 모임 | 책임 경계가 흐리고 수정 범위가 넓습니다. | 작은 변경도 파일 전체를 다시 읽어야 해서 속도가 떨어집니다. |
| 컴포넌트 단위로 역할 분리 | 입력, 출력, 상태가 작은 단위로 나뉩니다. | 테스트, 리팩터링, 팀 협업이 모두 쉬워집니다. |

**Before (모든 것이 한 파일에)**

```html
<script>
  // 1000줄의 DOM 조작 코드
</script>
```

**After (컴포넌트로 분리)**

```jsx
function App()    { ... }
function Header() { ... }
function List()   { ... }
function Item()   { ... }
```

AI에게 "한 파일에 모든 로직을 넣지 말고 역할별로 컴포넌트를 분리해줘"라고 요청하면 처음부터 더 유지보수하기 좋은 구조가 나옵니다.

## AI 팁: 컴포넌트 설계 요청 최적화

- **역할 기반 분리 요청**: "App, Header, List, Item으로 컴포넌트를 나눠서 작성해줘"처럼 구조를 먼저 정의하세요.
- **상태 위치 명시**: "상태는 가장 가까운 공통 부모에 두고, props로 자식에게 내려줘"를 요청에 포함하세요.
- **props 불변 원칙 강조**: "props는 절대로 직접 수정하지 말고, 콜백 함수를 통해 상태를 변경해줘"를 명시하세요.
- **컴포넌트 크기 제한**: "각 컴포넌트는 200줄 이하로 유지해줘"라고 요청하면 과도하게 큰 컴포넌트를 방지할 수 있습니다.
- **useEffect 최소화 요청**: "가능하면 useEffect 없이 파생 상태를 useMemo나 직접 계산으로 처리해줘"를 추가하세요.

## 실수 유형과 바이브코딩 대처법

| 실수 유형 | 증상 | 바이브코딩 대처 |
|---|---|---|
| 컴포넌트 안에서 props 직접 수정 | 예측 불가능한 상태 변화 | "props는 읽기 전용으로, 변경은 콜백으로 올려줘" 요청 |
| 모든 상태를 최상단에 몰아둠 | 성능 저하, 가독성 저하 | "상태를 가장 가까운 공통 부모에 위치시켜줘" 요청 |
| 컴포넌트가 1000줄 이상 | 읽기·수정 어려움 | "200줄 기준으로 컴포넌트를 분리해줘" 요청 |
| 매 렌더마다 이벤트 콜백 새로 생성 | 불필요한 자식 리렌더링 | "useCallback으로 콜백을 메모이제이션해줘" 요청 |
| 원본 상태와 파생 값 함께 저장 | 두 값이 불일치하는 버그 | "파생 값은 상태로 저장하지 말고 렌더 시 계산해줘" 요청 |

## 체크리스트

- [ ] 컴포넌트를 함수로 정의할 수 있습니다.
- [ ] props와 state를 구분할 수 있습니다.
- [ ] 자식에서 부모로 이벤트를 올릴 수 있습니다.
- [ ] 상태를 적절한 위치에 둘 수 있습니다.
- [ ] 단방향 데이터 흐름을 그림으로 설명할 수 있습니다.
- [ ] AI가 생성한 컴포넌트에서 상태 위치 문제를 발견할 수 있습니다.

## 처음 질문으로 돌아가기

- **컴포넌트 사고방식은 단순히 React 문법을 넘어서 무엇을 바꿔 줄까요?**
  화면을 "함수의 조합"으로 보게 됩니다. 각 함수는 입력(props)을 받아 출력(화면)을 돌려줍니다. 이 관점이 생기면 어떤 프레임워크를 써도 코드를 읽는 방식이 비슷해집니다.

- **props와 state는 어떤 기준으로 구분해야 할까요?**
  외부에서 받는 값은 props, 컴포넌트 스스로 관리하는 값은 state입니다. props는 읽기만 하고, state는 setter로만 바꿉니다. AI가 props를 직접 수정하는 코드를 생성하면 잘못된 패턴입니다.

- **단방향 데이터 흐름은 왜 대부분의 현대 프론트엔드 프레임워크의 기본 전제일까요?**
  데이터가 위에서 아래로만 흐르면 어떤 상태가 화면 어느 부분에 영향을 미치는지 추적이 쉬워집니다. 양방향이 되면 버그를 재현하고 수정하기 어려워집니다.

## 정리

컴포넌트와 상태는 화면을 조합 가능한 구조로 바꿔 줍니다. 이 관점이 잡히면 여러 화면을 연결하는 문제도 훨씬 자연스럽게 이해됩니다. 바이브코딩으로 React 코드를 만들 때도 이 원칙을 요청에 포함하면 처음부터 더 좋은 구조가 나옵니다.
