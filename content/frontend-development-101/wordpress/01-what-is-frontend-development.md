# 바이브코딩을 위한 프론트엔드 개발 기초 (1/10): 프론트엔드 개발이란 무엇인가?

이 글은 **바이브코딩을 위한 프론트엔드 개발 기초** 시리즈의 첫 번째 글입니다. AI에게 "웹 페이지 만들어줘"라고 말하기 전에, HTML·CSS·JS가 브라우저 안에서 어떻게 동작하는지 알아야 합니다. 이 시리즈는 그 기초를 10편에 걸쳐 바이브코딩 관점으로 정리합니다.

AI 코드 생성 도구가 강력해질수록 역설적으로 기초 개념이 더 중요해집니다. AI가 만들어 준 코드를 검토하고, 고치고, 배포하려면 결국 브라우저가 무엇을 어떻게 실행하는지 알아야 하기 때문입니다. 화면이 왜 안 보이는지, 버튼이 왜 반응하지 않는지, 스크립트가 왜 오류를 내는지 — 이 질문들에 답하려면 프론트엔드의 실행 모델을 이해해야 합니다.

> 프론트엔드는 'HTML/CSS/JS를 잘 다루는 일'이기 전에 '브라우저라는 런타임 위에서 상태와 화면을 동기화하는 일'입니다. 이 한 줄이 잡히면 jQuery·React·Vue·Svelte가 같은 문제를 다르게 푸는 답으로 보입니다.

## 이 글에서 다룰 문제

- 프론트엔드와 백엔드의 경계는 정확히 어디에서 나뉠까요?
- 브라우저는 HTML, CSS, JavaScript를 어떤 순서와 역할로 조합할까요?
- DOM, 렌더링, SPA 같은 단어는 왜 프론트엔드 입문에서 계속 등장할까요?
- 바이브코딩으로 웹 페이지를 만들 때 이 개념을 모르면 어떤 문제가 생길까요?
- AI가 만들어 준 프론트엔드 코드를 이해하려면 무엇부터 알아야 할까요?

## 바이브코딩 관점에서 시작하기

"AI야, 로그인 페이지 만들어줘"라고 입력하면 그럴듯한 HTML·CSS·JavaScript 코드가 나옵니다. 하지만 이 코드를 실제로 동작하게 만들고, 오류를 수정하고, 나만의 방식으로 바꾸려면 브라우저가 이 세 파일을 어떻게 읽고 실행하는지 알아야 합니다.

바이브코딩에서 프론트엔드 기초 지식은 AI 출력물을 판단하는 기준이 됩니다. "이 코드가 왜 작동하지 않지?"라는 질문에 스스로 방향을 잡을 수 있느냐, AI에게 다시 물어야만 하느냐의 차이입니다.

## 개념 한눈에 보기

| 용어 | 뜻 | 바이브코딩에서 왜 중요한가 |
|---|---|---|
| DOM | 브라우저가 HTML을 읽고 만든 트리 구조입니다. | AI가 생성한 JavaScript가 어느 요소를 건드리는지 파악하는 기준이 됩니다. |
| 렌더링 | HTML과 CSS를 실제 픽셀로 바꿔 화면에 그리는 과정입니다. | 화면이 왜 비어 보이는지 진단할 때 출발점이 됩니다. |
| 번들 | 여러 JavaScript 파일을 브라우저가 받기 쉬운 형태로 묶은 산출물입니다. | 초기 로딩 속도와 배포 결과물을 이해할 때 꼭 필요합니다. |
| SPA | 페이지 전체를 다시 로드하지 않고 JavaScript로 화면을 바꾸는 앱 구조입니다. | AI가 React나 Vue로 생성한 코드가 왜 그렇게 생겼는지 이해하게 해 줍니다. |
| Hydration | 서버가 미리 그린 HTML에 JavaScript 동작을 다시 붙이는 과정입니다. | Next.js 등 SSR 프레임워크 코드를 읽을 때 반드시 알아야 하는 개념입니다. |

## 정적 문서 웹에서 앱형 프론트엔드로

| 방식 | 화면 전환 방식 | 실무 영향 |
|---|---|---|
| 정적 문서 중심 웹 | 링크를 누를 때마다 새 HTML 문서를 다시 내려받습니다. | 구조는 단순하지만, 상호작용이 많아질수록 전환 비용이 커집니다. |
| 앱형 프론트엔드 | 브라우저 안에서 상태를 바꾸며 필요한 화면 조각만 교체합니다. | 라우팅, 상태, 번들 관리가 중요해지지만 사용자 경험은 훨씬 자연스러워집니다. |

**Before (정적 웹사이트, 1995)**

```html
<!-- 각 페이지가 별도 .html 파일 -->
<a href="/about.html">About</a>
```

**After (모던 SPA, 2025)**

```javascript
// 라우터는 한 페이지 내에서 화면을 전환합니다.
<Link to="/about">About</Link>
```

화면 변경의 책임이 서버에서 브라우저 런타임 쪽으로 이동했다는 점이 핵심입니다. 이 관점을 잡아 두면 뒤의 컴포넌트, 라우팅, API 호출 글들이 같은 계층 이야기로 이어집니다.

## AI 팁: 프론트엔드 기초와 바이브코딩

바이브코딩으로 프론트엔드를 개발할 때 AI를 더 효과적으로 활용하는 방법입니다.

- **명확한 컨텍스트 제공**: "React SPA에서 버튼 클릭 시 텍스트가 바뀌는 컴포넌트"처럼 구체적으로 요청하면 더 정확한 코드가 나옵니다.
- **DOM 구조 먼저 설명**: "id가 title인 h1과 id가 btn인 버튼이 있어. 버튼 클릭 시 h1 텍스트를 바꿔줘"처럼 HTML 구조를 먼저 알려주세요.
- **에러 메시지 복사하기**: "이 오류가 나는데 원인이 뭐야?"보다 실제 콘솔 에러 전체를 붙여넣으면 AI가 훨씬 정확하게 답합니다.
- **DevTools 결과 공유**: Elements나 Console 탭 스크린샷을 함께 제공하면 진단 품질이 크게 올라갑니다.

## 실수 유형과 바이브코딩 대처법

| 실수 유형 | 증상 | 바이브코딩 대처 |
|---|---|---|
| HTML 안에 스타일 직접 삽입 | 유지보수가 어려워짐 | AI에게 "인라인 스타일 대신 CSS 클래스로 분리해줘" 요청 |
| DOM 조작과 비즈니스 로직 혼합 | 테스트·디버깅 어려움 | "로직과 DOM 조작을 함수로 분리해줘"라고 요청 |
| DevTools 미사용 | 디버깅이 감에 의존 | AI에게 "이 코드를 DevTools로 디버깅하는 방법은?" 질문 |
| 프레임워크 남용 | 단순 페이지가 과도하게 복잡해짐 | "순수 HTML/CSS/JS로 해결 가능한지 먼저 확인해줘" 요청 |
| 모바일 대응 후순위 | 실제 사용자 경험 저하 | "모바일 퍼스트로 다시 작성해줘" 요청 |

## 체크리스트

- [ ] HTML, CSS, JavaScript의 역할을 구분할 수 있습니다.
- [ ] 로컬에서 정적 페이지를 띄울 수 있습니다.
- [ ] DevTools의 Elements, Console, Network 탭을 열어볼 수 있습니다.
- [ ] DOM이 무엇인지 설명할 수 있습니다.
- [ ] SPA를 한 문장으로 설명할 수 있습니다.
- [ ] AI가 생성한 HTML/JS 코드를 보고 어느 파일이 무슨 역할인지 파악할 수 있습니다.

## 처음 질문으로 돌아가기

- **프론트엔드와 백엔드의 경계는 정확히 어디에서 나뉠까요?**
  브라우저 안에서 실행되는 코드가 프론트엔드, 서버에서 실행되는 코드가 백엔드입니다. HTML·CSS·JS는 모두 브라우저 쪽에서 동작합니다.

- **브라우저는 HTML, CSS, JavaScript를 어떤 순서와 역할로 조합할까요?**
  HTML이 DOM 트리를 만들고, CSS가 스타일 규칙을 적용하고, JavaScript가 이벤트에 반응해 DOM을 수정합니다. 이 세 단계가 순서대로, 그리고 반복적으로 일어납니다.

- **DOM, 렌더링, SPA 같은 단어는 왜 프론트엔드 입문에서 계속 등장할까요?**
  브라우저가 화면을 그리는 핵심 파이프라인이 DOM 생성 → 스타일 계산 → 렌더링이고, SPA는 이 파이프라인을 JavaScript로 계속 업데이트하는 구조이기 때문입니다.

## 정리

프론트엔드는 브라우저 안에서 제품이 사용자와 만나는 계층입니다. 바이브코딩으로 웹을 만들 때도 HTML이 구조를 담당하고, CSS가 모양을 담당하고, JavaScript가 동작을 담당한다는 역할 분리를 이해해야 AI 출력물을 올바르게 활용할 수 있습니다.

다음 글에서는 이 계층의 가장 오래가는 기초인 HTML과 CSS를 본격적으로 살펴봅니다.
