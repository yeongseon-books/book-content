# 바이브코딩을 위한 프론트엔드 개발 기초 (3/10): JavaScript 기본

이 글은 **바이브코딩을 위한 프론트엔드 개발 기초** 시리즈의 세 번째 글입니다. AI가 JavaScript 코드를 만들어 줄 수는 있지만, 그 코드가 왜 동작하는지, 버그가 어디서 왔는지 파악하려면 기본 개념을 알아야 합니다.

AI가 생성한 JavaScript는 대체로 잘 동작하지만 가끔 이상한 버그를 냅니다. `var`를 쓰거나, 상태와 DOM을 한 함수에 뒤섞거나, 이벤트 리스너를 매번 새로 붙이는 코드가 나올 수 있습니다. 이런 코드를 알아보고 수정 방향을 잡으려면 JavaScript의 핵심 모델을 이해해야 합니다.

> JavaScript의 진짜 모델은 '이벤트 루프 위에서 도는 단일 스레드 + 비동기 큐'입니다. `setTimeout(fn, 0)`이 즉시 실행되지 않는 이유, `await`이 실제로 기다리는 것이 무엇인지가 모두 이 한 그림 위에서만 설명됩니다.

## 이 글에서 다룰 문제

- `let`과 `const`를 어떻게 구분해 쓰는 편이 좋을까요?
- 함수와 화살표 함수는 어떤 기준으로 읽고 작성하면 될까요?
- `map`, `filter`, `reduce`는 왜 for문보다 자주 권장될까요?
- AI가 생성한 JavaScript에서 자주 발생하는 패턴 문제는 무엇일까요?
- DOM 조작 코드를 AI에게 요청할 때 어떤 조건을 명시해야 할까요?

## 바이브코딩 관점에서 시작하기

"AI야, 버튼을 클릭하면 목록에 항목을 추가하는 기능 만들어줘"라고 하면 JavaScript 코드가 나옵니다. 그런데 이 코드에 `var`가 있거나, 같은 버튼에 이벤트 리스너가 중복으로 붙거나, 삭제 기능이 꼬인다면 어떻게 고쳐야 할까요? 상태와 렌더링의 역할을 이해하고 있어야 수정이 가능합니다.

## 개념 한눈에 보기

| 용어 | 뜻 | 바이브코딩에서 왜 중요한가 |
|---|---|---|
| `const` | 재할당할 수 없는 변수입니다. | AI가 `var`를 쓴 코드를 보면 `const`/`let`으로 바꿔달라고 요청할 수 있습니다. |
| 화살표 함수 | `() => {}` 형태의 간결한 함수 문법입니다. | AI 생성 코드의 콜백 함수 패턴을 읽는 기준이 됩니다. |
| 클로저 | 함수가 자신이 만들어질 당시의 환경을 기억하는 성질입니다. | 이벤트 핸들러가 왜 특정 값을 "기억"하는지 이해하는 열쇠입니다. |
| `map/filter/reduce` | 반복문 대신 컬렉션을 변환할 때 쓰는 표준 도구입니다. | AI에게 "for문 대신 배열 메서드로 작성해줘"라고 요청하는 기준입니다. |
| 이벤트 위임 | 자식마다 리스너를 붙이지 않고 부모에 한 번만 리스너를 두는 방식입니다. | 동적 목록에서 이벤트가 안 잡힐 때 원인을 파악하는 기준입니다. |

## for문 중심 코드에서 선언형 JavaScript로

| 방식 | 코드 특징 | 실무 영향 |
|---|---|---|
| `var` + 수동 반복문 | 인덱스, 임시 배열, 가변 상태를 직접 관리합니다. | 조건과 부수효과가 늘면 읽기 어려워집니다. |
| `const` + 배열 메서드 | 무엇을 변환하는지가 코드에 직접 드러납니다. | 이벤트 처리, 렌더링, 테스트 코드까지 같은 스타일로 정리하기 쉬워집니다. |

**Before (var와 for)**

```javascript
var arr = [1, 2, 3];
var doubled = [];
for (var i = 0; i < arr.length; i++) doubled.push(arr[i] * 2);
```

**After (모던 JS)**

```javascript
const arr = [1, 2, 3];
const doubled = arr.map(n => n * 2);
```

바이브코딩으로 만든 코드에서 `var`와 `for` 루프를 보면 "모던 JavaScript 문법으로 다시 작성해줘"라고 AI에게 요청하는 것이 좋습니다.

## AI 팁: JavaScript 코드 품질 향상

- **변수 선언 방식 지정**: "var 대신 const와 let을 사용해줘"를 항상 포함하세요.
- **상태-렌더링 분리 요청**: "상태 변수와 DOM 업데이트 함수를 분리해줘"라고 명시하면 더 유지보수하기 좋은 코드가 나옵니다.
- **이벤트 위임 요청**: 동적으로 생성되는 요소에 이벤트가 필요하면 "이벤트 위임 방식으로 작성해줘"라고 요청하세요.
- **에러 처리 포함 요청**: "try-catch와 에러 메시지 표시 포함해줘"를 추가하면 더 견고한 코드가 나옵니다.
- **ESLint 준수 요청**: "ESLint의 recommended 규칙을 따르도록 작성해줘"라고 하면 코드 품질이 올라갑니다.

## 실수 유형과 바이브코딩 대처법

| 실수 유형 | 증상 | 바이브코딩 대처 |
|---|---|---|
| `var` 계속 사용 | 함수 스코프 버그, 호이스팅 혼란 | "var를 모두 const/let으로 바꿔줘" 요청 |
| `==` 사용 | 예상치 못한 형변환 결과 | "모든 비교를 ===로 바꿔줘" 요청 |
| 상태와 DOM을 동시에 여러 곳에서 수정 | 진실의 출처가 사라져 디버깅 어려움 | "상태 관리와 DOM 업데이트를 분리해줘" 요청 |
| 모든 요소에 리스너 개별 부착 | 메모리·성능 낭비 | "이벤트 위임으로 리팩터링해줘" 요청 |
| async 내부 에러 미처리 | 실패가 조용히 묻힘 | "try-catch 블록과 사용자 에러 표시 추가해줘" 요청 |

## 처음 질문으로 돌아가기

- **`let`과 `const`를 어떻게 구분해 쓰는 편이 좋을까요?**
  기본값은 `const`입니다. 나중에 재할당이 필요할 때만 `let`을 씁니다. `var`는 쓰지 않습니다. 이 규칙 하나로 AI가 생성한 코드의 변수 선언 문제를 대부분 잡을 수 있습니다.

- **함수와 화살표 함수는 어떤 기준으로 읽고 작성하면 될까요?**
  이벤트 핸들러와 콜백은 화살표 함수가 더 짧고 `this` 바인딩 문제가 없어서 편합니다. 이름이 있는 독립 함수는 `function` 키워드도 충분합니다. AI 생성 코드에서 두 방식이 섞여 있으면 일관성 있게 통일해 달라고 요청하세요.

- **`map`, `filter`, `reduce`는 왜 for문보다 자주 권장될까요?**
  무엇을 변환하는지 의도가 코드에 직접 드러나기 때문입니다. `arr.filter(x => x > 0)` 한 줄은 "양수만 남겨라"는 의도가 명확합니다. for 루프는 같은 결과를 위해 더 많은 코드를 읽어야 합니다.
