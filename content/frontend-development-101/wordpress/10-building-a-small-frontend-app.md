# 바이브코딩을 위한 프론트엔드 개발 기초 (10/10): 작은 프론트엔드 앱 만들기

이 글은 **바이브코딩을 위한 프론트엔드 개발 기초** 시리즈의 마지막 글입니다. 앞서 배운 HTML·CSS·JavaScript·컴포넌트·라우팅·API·폼·스타일링·빌드 도구를 하나의 노트 앱으로 엮어 배포까지 완성합니다.

바이브코딩의 진짜 도전은 AI가 각 부분을 만들어 주는 것이 아니라, 그 부분들을 하나의 작동하는 앱으로 연결하는 것입니다. 라우팅도 알고 API도 알고 폼도 이해했는데, 막상 하나의 프로젝트로 합치려면 어디서부터 파일을 나누고 어떤 순서로 AI에게 요청해야 할지 막막해지는 경우가 많습니다.

> 바이브코딩은 AI가 코드를 생성하지만, 방향을 잡고 품질을 검토하고 배포까지 완주하는 것은 결국 개발자입니다. 이 시리즈에서 배운 기초 개념이 그 방향 감각을 만들어 줍니다.

## 이 글에서 다룰 문제

- 작은 프로젝트에서는 어떤 폴더 구조가 가장 읽기 쉬울까요?
- 앞선 1~9화 개념은 실제 앱 안에서 어떻게 이어질까요?
- 바이브코딩으로 앱을 만들 때 AI에게 어떤 순서로 무엇을 요청해야 할까요?
- 개발, 빌드, 배포 흐름은 어떤 순서로 정리되는 편이 좋을까요?
- 완성 후 어떤 기준으로 "출하 가능한 앱"이라고 판단할 수 있을까요?

## 바이브코딩 관점에서 시작하기

바이브코딩으로 노트 앱을 만든다면, AI에게 한 번에 전체를 요청하기보다 단계별로 요청하는 것이 효과적입니다. "Vite + React + TypeScript 프로젝트 만들어줘" → "react-router-dom으로 3페이지 라우팅 추가해줘" → "노트 API 클라이언트 만들어줘" → "노트 생성 폼 만들어줘" → "Netlify 배포 설정 알려줘" 순서로 진행하면 각 단계에서 검토하고 수정하기가 쉽습니다.

## 개념 한눈에 보기

| 용어 | 뜻 | 바이브코딩에서 왜 중요한가 |
|---|---|---|
| 프로젝트 구조 | 역할별로 나눈 폴더 레이아웃입니다. | AI에게 "이 구조로 파일을 나눠줘"라고 기준을 제시하는 데 사용합니다. |
| Capstone | 앞에서 배운 내용을 하나로 묶는 마무리 프로젝트입니다. | 개별 개념을 실제 제품 흐름으로 연결해 바이브코딩 역량을 완성합니다. |
| 배포 | 빌드 산출물을 공개 URL 뒤에 올리는 작업입니다. | 로컬에서 보이지 않던 환경 변수, CORS, 라우팅 문제를 드러내는 최종 검증입니다. |
| 출하 기준 | "개발 완료"가 아닌 "사용 가능한 상태"를 판단하는 체크리스트입니다. | 바이브코딩 결과물을 실제로 쓸 수 있는지 판단하는 기준이 됩니다. |

## 개념 분리 학습에서 배포 완주까지

| 상태 | 특징 | 바이브코딩 영향 |
|---|---|---|
| 개념을 따로만 아는 상태 | 각 주제는 이해했지만 서로의 연결이 약합니다. | AI에게 무엇을 어떤 순서로 요청해야 할지 막막합니다. |
| 작은 앱을 끝까지 배포한 상태 | 화면, 상태, API, 빌드, 배포가 하나의 경험으로 묶입니다. | 다음 프로젝트에서 AI를 더 효과적으로 활용하는 기준과 자신감이 생깁니다. |

**Before (개념만 아는 상태)**

```text
"라우팅은 알아. 폼도 알아. API도 이해해."
"그런데 이것들을 합쳐서 앱을 만드는 건 어떻게 하지?"
```

**After (작은 앱이 인터넷에서 동작)**

```text
https://my-notes.netlify.app
- 사용자가 노트를 추가/편집/삭제할 수 있습니다.
- 코드가 GitHub에 올라가 있습니다.
- 다음 학습자가 이 코드를 기반으로 공부할 수 있습니다.
```

바이브코딩으로 앱을 처음 배포해 보는 순간, 앞선 9개 글이 각각의 개념이 아니라 한 제품을 완성하는 연결 고리였다는 사실이 훨씬 선명해집니다.

## AI 팁: 바이브코딩으로 앱 완성하기

- **단계별 요청 전략**: 전체를 한 번에 요청하지 말고 "프로젝트 생성 → 라우팅 → API 클라이언트 → UI 컴포넌트 → 폼 → 빌드/배포" 순서로 나눠 요청하세요.
- **폴더 구조 먼저 확정**: "이 구조로 폴더를 먼저 만들어줘: src/components/, src/pages/, src/api/, src/hooks/"라고 시작하면 이후 요청이 일관성을 유지합니다.
- **README 요청 포함**: "프로젝트 완성 후 실행 방법, 환경 변수, 배포 URL을 담은 README.md도 만들어줘"를 항상 포함하세요.
- **배포 전 체크리스트 요청**: "배포 전에 확인해야 할 항목 목록 만들어줘"라고 요청하면 놓친 부분을 잡을 수 있습니다.
- **반복 개선 전략**: 배포 후 오류가 생기면 "이 오류 메시지의 원인과 해결 방법 알려줘"처럼 구체적인 에러 내용을 AI에게 전달하세요.

## 실수 유형과 바이브코딩 대처법

| 실수 유형 | 증상 | 바이브코딩 대처 |
|---|---|---|
| 모든 코드를 App.tsx에 삽입 | 100줄 초과 후 읽기 어려움 | "이 파일을 역할별로 컴포넌트와 페이지로 분리해줘" 요청 |
| 컴포넌트 안에서 API 직접 호출 | 테스트·재사용 어려움 | "API 호출을 src/api/ 폴더로 분리해줘" 요청 |
| README 없음 | 한 달 후 재실행 불가 | "지금 구조를 기준으로 README와 .env.example 만들어줘" 요청 |
| localhost에서만 확인 후 배포 | 배포 후 라우팅·CORS 오류 발생 | "Netlify/Vercel 배포 체크리스트와 자주 발생하는 오류 알려줘" 요청 |
| 완벽해질 때까지 배포 미룸 | 실제 사용자 피드백 없이 개발 지속 | 작동하는 최소 버전을 먼저 배포하고 점진적으로 개선하세요 |

## 체크리스트

- [ ] 폴더 구조를 설명할 수 있습니다.
- [ ] API 클라이언트를 컴포넌트 밖으로 분리했습니다.
- [ ] `npm run build`가 성공합니다.
- [ ] 앱이 공개 URL 뒤에서 동작합니다.
- [ ] README에 실행 방법을 적어 두었습니다.
- [ ] 배포 후 새로고침과 깊은 링크가 정상 동작합니다.
- [ ] 바이브코딩 전 과정에서 AI와 어떻게 협업했는지 설명할 수 있습니다.

## 처음 질문으로 돌아가기

- **작은 프로젝트에서는 어떤 폴더 구조가 가장 읽기 쉬울까요?**
  `components/`(재사용 UI), `pages/`(라우트별 화면), `api/`(서버 통신), `hooks/`(커스텀 훅), `styles/`(토큰·레이아웃) 다섯 폴더로 시작하면 대부분의 소규모 앱에서 충분합니다.

- **앞선 1~9화 개념은 실제 앱 안에서 어떻게 이어질까요?**
  HTML/CSS/JS(1-3화)가 컴포넌트(4화)를 만들고, 라우터(5화)가 페이지를 연결하고, API(6화)와 폼(7화)이 데이터를 주고받으며, 스타일 시스템(8화)이 일관성을 유지하고, 빌드 도구(9화)가 배포 가능한 산출물을 만듭니다.

- **바이브코딩으로 앱을 만들 때 AI에게 어떤 순서로 무엇을 요청해야 할까요?**
  1) 프로젝트 생성 및 폴더 구조 → 2) 라우팅 설정 → 3) API 클라이언트 → 4) 주요 컴포넌트 → 5) 폼과 유효성 검사 → 6) 스타일링 → 7) 빌드/배포 설정 → 8) README. 각 단계마다 확인하고 다음으로 넘어가는 것이 핵심입니다.

## 정리

여기까지 왔다면 바이브코딩으로 프론트엔드 앱을 완성하는 전체 흐름을 한 번 완주한 셈입니다. AI가 코드를 생성하더라도 그 코드가 왜 그렇게 생겼는지 이해하고, 어디를 고쳐야 할지 판단하고, 배포까지 완주하는 역량이 이 시리즈의 목표였습니다.

다음에 함께 보면 좋은 주제는 테스트, DevOps, 보안 코딩입니다. 바이브코딩으로 만든 앱에 테스트를 추가하고, 배포 자동화를 설정하고, 보안 취약점을 방지하는 방법으로 계속 확장해 보세요.
