# 바이브코딩을 위한 프론트엔드 개발 기초 (2/10): HTML과 CSS 기본

이 글은 **바이브코딩을 위한 프론트엔드 개발 기초** 시리즈의 두 번째 글입니다. AI에게 웹 페이지 레이아웃을 만들어 달라고 할 때, HTML 구조와 CSS 동작 방식을 알아야 결과물을 제대로 검토하고 수정할 수 있습니다.

AI가 생성한 HTML을 보면 `<div>`가 잔뜩 쌓인 코드와 `<header>`, `<main>`, `<article>` 같은 시맨틱 태그를 쓴 코드의 차이를 알기 어렵습니다. 하지만 두 코드는 SEO, 접근성, 유지보수 면에서 크게 다릅니다. 바이브코딩으로 화면을 빠르게 만들어도, 오래 유지되는 구조를 만들려면 이 차이를 알아야 합니다.

> HTML은 '문서 구조'이고 CSS는 '그 구조 위에 얹는 시각 규칙'입니다. div를 남발하면 안 되는 이유와 시맨틱 태그가 접근성·SEO·유지보수를 동시에 결정하는 이유가 모두 이 분리에서 출발합니다.

## 이 글에서 다룰 문제

- 시맨틱 HTML이 단순한 취향 문제가 아니라 기본 설계인 이유는 무엇일까요?
- 박스 모델은 CSS를 이해할 때 왜 가장 먼저 잡아야 할 개념일까요?
- Flexbox와 Grid는 각각 어떤 상황에서 더 적합할까요?
- AI가 생성한 레이아웃 코드에서 자주 발생하는 문제는 무엇일까요?
- 반응형 디자인을 AI에게 요청할 때 어떤 조건을 명시해야 할까요?

## 바이브코딩 관점에서 시작하기

"AI야, 카드 세 개가 나란히 배치된 섹션 만들어줘"라고 요청하면 CSS가 나옵니다. 하지만 모바일에서 가로로 넘치거나 간격이 이상하거나 의미 없는 `<div>` 더미가 나올 수 있습니다. 이때 수정 방향을 잡으려면 박스 모델과 레이아웃 시스템을 알아야 합니다.

좋은 바이브코딩은 AI 출력을 검토할 수 있는 안목에서 나옵니다. "이 `<div>` 대신 `<section>`을 쓰는 게 맞지 않아?"라고 AI에게 다시 물을 수 있어야 합니다.

## 개념 한눈에 보기

| 용어 | 뜻 | 바이브코딩에서 왜 중요한가 |
|---|---|---|
| 시맨틱 HTML | `<header>`, `<nav>`, `<article>`처럼 의미를 가진 태그입니다. | AI에게 "시맨틱 HTML로 작성해줘"라고 요청하면 품질이 달라집니다. |
| 박스 모델 | 모든 요소를 content, padding, border, margin의 조합으로 보는 방식입니다. | 간격이 이상할 때 AI 설명 없이 스스로 원인을 찾는 데 필요합니다. |
| Flexbox | 한 축 중심으로 배치하는 레이아웃 시스템입니다. | 메뉴, 카드 행, 정렬 문제를 AI에게 요청할 때 구체적인 기준이 됩니다. |
| Grid | 행과 열 두 축을 함께 다루는 레이아웃 시스템입니다. | 대시보드나 카드 매트릭스 구조를 요청할 때 명확한 언어를 제공합니다. |
| 미디어 쿼리 | 화면 크기나 환경에 따라 다른 스타일을 적용하는 문법입니다. | "모바일에서는 1열, 데스크톱에서는 3열"처럼 AI에게 조건을 명시할 수 있습니다. |

## div 더미에서 시맨틱 구조로

| 방식 | 코드 특징 | 실무 영향 |
|---|---|---|
| 의미 없는 `div` 중심 구조 | 화면 모양은 만들 수 있지만 문서 역할이 코드에 드러나지 않습니다. | 검색 엔진과 보조 기술이 구조를 추론해야 해서 품질이 흔들립니다. |
| 시맨틱 태그 중심 구조 | 구조와 역할이 태그 이름에 직접 드러납니다. | 레이아웃 변경, 접근성 보강, SEO 개선을 함께 가져가기 쉽습니다. |

**Before (의미 없는 div 더미)**

```html
<div class="header">
  <div class="nav">...</div>
</div>
<div class="content">...</div>
```

**After (시맨틱 구조)**

```html
<header><nav>...</nav></header>
<main>...</main>
<footer>...</footer>
```

겉모습이 비슷해도 두 번째 구조는 문서의 의미를 코드 안에 남깁니다. AI에게 처음 요청할 때 "시맨틱 HTML 사용"을 명시하면 첫 번째보다 두 번째 결과물이 나올 가능성이 높아집니다.

## AI 팁: HTML과 CSS 요청 최적화

- **레이아웃 방식 명시**: "Flexbox로 가로 정렬", "CSS Grid로 3열 레이아웃"처럼 원하는 레이아웃 모델을 지정하세요.
- **시맨틱 태그 요청**: "div 대신 시맨틱 태그를 사용해줘"를 요청에 포함하면 접근성과 SEO가 좋아집니다.
- **반응형 조건 명시**: "모바일(600px 이하)에서는 1열, 태블릿(900px 이하)에서는 2열, 데스크톱에서는 3열로 배치해줘"처럼 구체적인 브레이크포인트를 제시하세요.
- **디버깅 요청**: CSS가 이상하면 "DevTools에서 이 요소의 박스 모델을 어떻게 읽어야 해?"라고 물어보세요.

## 실수 유형과 바이브코딩 대처법

| 실수 유형 | 증상 | 바이브코딩 대처 |
|---|---|---|
| 모든 것을 `<div>`로만 작성 | 검색 엔진·스크린 리더 품질 저하 | "모든 div를 적절한 시맨틱 태그로 교체해줘" 요청 |
| `!important` 남발 | CSS 우선순위 혼란 | "!important 없이 선택자 특이성으로 해결해줘" 요청 |
| 고정 `px`만 사용 | 반응형 레이아웃 불안정 | "px 대신 rem, %, fr 단위로 바꿔줘" 요청 |
| 색으로만 정보 전달 | 색각 이상 사용자 접근성 저하 | "색 외에 아이콘이나 텍스트로도 상태를 표시해줘" 요청 |
| 이미지 alt 공백 | 스크린 리더 정보 누락 | "모든 이미지에 적절한 alt 텍스트 추가해줘" 요청 |

## 체크리스트

- [ ] `<header>`, `<main>`, `<footer>`를 적절히 사용할 수 있습니다.
- [ ] 박스 모델을 직접 그릴 수 있습니다.
- [ ] Flexbox와 Grid의 차이를 한 문장으로 설명할 수 있습니다.
- [ ] 미디어 쿼리로 반응형 레이아웃을 만들 수 있습니다.
- [ ] 모든 의미 있는 이미지에 적절한 `alt`를 작성할 수 있습니다.
- [ ] AI가 생성한 CSS에서 박스 모델 관련 버그를 진단할 수 있습니다.

## 처음 질문으로 돌아가기

- **시맨틱 HTML이 단순한 취향 문제가 아니라 기본 설계인 이유는 무엇일까요?**
  `<div>`는 브라우저에게 "이 요소가 무슨 역할인지" 아무것도 알려주지 않습니다. `<nav>`, `<article>`, `<header>`는 구조의 의미를 코드에 직접 담아 검색 엔진·스크린 리더·유지보수 세 가지를 동시에 개선합니다.

- **박스 모델은 CSS를 이해할 때 왜 가장 먼저 잡아야 할 개념일까요?**
  모든 HTML 요소는 박스입니다. 간격 문제의 대부분은 `padding`, `margin`, `border`가 어느 박스에 적용됐는지 모르는 데서 옵니다. 박스 모델을 알면 DevTools만으로 원인을 찾을 수 있습니다.

- **Flexbox와 Grid는 각각 어떤 상황에서 더 적합할까요?**
  Flexbox는 한 방향(가로 또는 세로) 정렬에 강하고, Grid는 행과 열 두 방향을 동시에 제어할 때 강합니다. 메뉴바·카드 행은 Flexbox, 페이지 전체 레이아웃·대시보드는 Grid를 먼저 고려합니다.

## 정리

HTML은 뼈대이고 CSS는 그 위에 입는 옷입니다. 두 역할이 분리되어 있어야 이후에 JavaScript가 자연스럽게 끼어들 수 있습니다. 바이브코딩으로 레이아웃을 만들 때도 이 원칙을 지켜달라고 AI에게 명시적으로 요청하세요.

다음 글에서는 이 구조 위에 동작을 붙이는 JavaScript 기본기를 살펴봅니다.
