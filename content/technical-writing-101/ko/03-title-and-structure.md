# Technical Writing 101 (3/10): 제목과 구조 잡기

제목은 그럴듯한데 막상 읽어 보면 어디서 핵심이 나오는지 알 수 없는 글이 있습니다. 반대로 내용은 괜찮은데 제목이 흐려서 검색 결과에서 지나쳐 버리는 글도 많습니다. 두 문제는 따로 생기는 것처럼 보여도 뿌리는 같습니다. 제목이 약속한 독자 행동과 본문 구조가 맞물리지 않았기 때문입니다.

이 글은 기술 글쓰기 101 시리즈의 3번째 글입니다.

좋은 제목은 클릭을 유도하는 문구가 아니라 글의 목적을 압축한 설계 문장입니다. 구조는 그 약속을 독자가 가장 짧게 따라가도록 만든 경로입니다. 그래서 제목과 구조는 초안 단계부터 같이 다루는 편이 훨씬 안전합니다.

여기서는 제목, 개요, 헤딩, 정리를 한 세트로 설계하는 기준을 정리합니다.

*Technical Writing 101 3장 흐름 개요*
> 제목은 약속이고, 개요는 지도이며, 본문은 그 약속을 전달하는 경로이고, 정리는 독자를 다음 행동으로 밀어 주는 마무리입니다.

## 이 글에서 다룰 문제

- 좋은 제목과 좋은 구조는 왜 항상 같이 움직여야 할까요?
- 제목은 어떻게 약속이 되고, 구조는 어떻게 그 약속을 전달할까요?
- 제목, 개요, 본문, 정리는 어떤 순서로 맞물려야 할까요?
- 이 개념을 실무에서 잘못 적용하면 어떤 문제가 생길까요?
- 이 주제에서 초보자가 가장 자주 놓치는 포인트는 무엇일까요?

## 이 글에서 배울 것

- SEO 제목 작성법
- 헤딩 계층 설계 규칙
- 도입, 본문, 정리 구조
- 개요 만들기
- 문단 다루기

## 한눈에 보는 멘탈 모델

> 제목은 약속이고, 개요는 지도이고, 본문은 전달이며, 정리는 독자를 다음 행동으로 밀어 주는 마무리입니다.

- **SEO title**: 검색 친화적인 제목입니다.
- **outline**: 초안 단계의 목차입니다.
- **heading**: 제목 레벨입니다.
- **lede**: 첫 단락입니다.
- **TL;DR**: 너무 길어서 다 읽지 못한 독자를 위한 요약입니다.

## 기술 글의 구조 다이어그램

기술 글의 표준 구조는 도입, 본문, 정리 세 부분으로 이루어집니다. 각 부분의 역할을 명확히 알면 글을 쓰는 속도가 빨라집니다.

```
기술 글 표준 구조
================
[도입부]
  H1 제목 (약속)
  |
  +-> 독자 + 목표 선언 (1-2문장)
  |   "이 글은 [독자]를 위한 글입니다"
  |
  +-> 핵심 질문 (이 글에서 다룰 문제)
  |
  +-> 이 글에서 배울 것 (목록)

[본문]
  H2 섹션 1 → What (무엇)
  H2 섹션 2 → How (어떻게)
  H2 섹션 3 → Why (왜)
  H2 Before/After 비교
  H2 문서 템플릿
  H2 자주 하는 실수 표

[정리]
  H2 정리 (핵심 3개 요약)
  H2 운영 체크리스트
  H2 연습 문제
  시리즈 목차
  참고 자료
```

도입부가 독자를 붙잡고, 본문이 약속을 전달하며, 정리가 독자를 다음 행동으로 밀어 줍니다.

## Before / After 비교: 제목과 구조 개선

### Before / After 예시 1: 명사형 vs 동사형 제목

**Before**

> "FastAPI 가이드"

**After**

> "5분 안에 첫 FastAPI 엔드포인트 실행하기"

**개선 이유**: 동사형 제목은 독자가 달성할 결과를 명시합니다. 독자는 클릭하기 전에 이 글이 자기에게 필요한지 판단할 수 있습니다.

### Before / After 예시 2: 모호한 개요 vs 행동 기반 개요

**Before**

```markdown
## 개요
## 내용 1
## 내용 2
## 정리
```

**After**

```markdown
## Python 환경 확인하기
## FastAPI 설치하기
## 첫 엔드포인트 작성하기
## 로컬 서버 실행하기
## 브라우저로 확인하기
## 다음 단계: 데이터베이스 연결
```

**개선 이유**: 두 번째 개요는 독자가 헤딩만 읽어도 이동 경로를 알 수 있습니다. 제목이 약속한 행동이 헤딩에도 이어지고, 중간 검증 지점이 드러나며, 막히는 지점까지 예고됩니다.

### Before / After 예시 3: 범위가 너무 넓은 제목

**Before**

> "웹 개발 완벽 가이드"

**After**

> "로컬에서 FastAPI REST API 만들기: 환경 설정부터 첫 응답까지"

**개선 이유**: 범위를 좁히면 독자가 이 글이 자기에게 맞는지 빠르게 판단할 수 있습니다.

### Before / After 예시 4: 제목과 본문의 불일치

**Before**

제목: "FastAPI 시작하기"이지만 본문에 Django 비교가 절반을 차지함

**After**

제목이 약속한 내용(FastAPI 시작하기)만 본문에서 다루고, Django 비교가 필요하면 별도 글로 분리

**개선 이유**: 독자가 제목을 보고 클릭했다면, 그 약속을 반드시 지켜야 합니다.

## 제목 공식 5가지

좋은 제목은 독자의 행동을 압축한 문장입니다. 아래는 실무에서 자주 쓰이는 다섯 가지 제목 패턴입니다.

| 패턴 | 형식 | 예시 | 장점 |
| --- | --- | --- | --- |
| 시간 약속형 | "N분 안에 [목표 행동]하기" | "5분 안에 첫 FastAPI 엔드포인트 실행하기" | 투자 시간과 목표가 명확 |
| 문제 해결형 | "[문제]를 [방법]으로 해결하기" | "FastAPI 422 오류를 Pydantic 검증으로 해결하기" | 독자의 문제와 빠르게 매칭 |
| 비교형 | "[A]와 [B] 비교: 언제 무엇을 써야 할까" | "Flask와 FastAPI 비교: 신규 프로젝트에서 무엇을 선택할까" | 의사결정 배경을 찾는 독자에게 적합 |
| 체크리스트형 | "[목표]를 위한 N가지 체크포인트" | "FastAPI 배포 전 확인할 7가지" | 구조 예측 가능, 빠른 스캔 |
| 단계별 가이드형 | "[시작 상태]에서 [목표 상태]로 가는 법" | "로컬 환경에서 AWS Lambda로 FastAPI 배포하기" | 출발점과 도착점이 명확 |

## 헤딩 계층 설계 규칙

헤딩은 독자가 글의 구조를 스캔할 때 가장 먼저 보는 요소입니다.

```
헤딩 계층 규칙
=============
H1: 문서당 1개만 (제목)
    |
    H2: 주요 섹션 (5개 이하 권장)
        |
        H3: H2 하위 섹션
            |
            H4: H3 하위 (꼭 필요한 경우만)

금지 패턴:
  H2 다음에 바로 H4 (계층 건너뜀)
  H1이 여러 개 (SEO 혼동)
  H2가 10개 이상 (글을 나눠야 할 신호)
```

**규칙 1: H1은 하나만**

한 글에는 H1(제목)이 하나만 있어야 합니다. 두 개 이상의 H1은 글을 쪼개라는 신호입니다.

**규칙 2: 계층을 건너뛰지 말기**

H2 다음에 바로 H4를 쓰지 않습니다. H2 → H3 → H4 순서를 지킵니다.

**규칙 3: H2는 5개 이하 (입문 글 기준)**

입문 독자를 위한 글은 H2 헤딩을 5개 이하로 유지하는 편이 좋습니다. 그보다 많으면 글을 나누거나 중첩 구조로 전환합니다.

**규칙 4: 헤딩에 동사 포함**

"## 설치" 대신 "## FastAPI 설치하기"처럼 동사를 포함하면 행동이 명확해집니다.

## 목차로 먼저 쓰기: 스캔 테스트

글을 본문부터 쓰기 시작하면 방향을 잃기 쉽습니다. 대신 목차를 먼저 만들고, 그 목차를 독자에게 보여 주듯 설계하면 글이 훨씬 안정적으로 완성됩니다.

**나쁜 목차 (개요만 나열):**

```markdown
## 개요
## 내용
## 정리
```

**좋은 목차 (독자의 행동 순서):**

```markdown
## FastAPI를 선택한 이유
## 가상환경 만들기
## 첫 엔드포인트 작성하기
## 로컬에서 실행하고 검증하기
## 자주 막히는 지점과 해결법
## 다음 단계: 데이터베이스 연결하기
```

좋은 목차는 독자가 각 섹션에서 무엇을 하게 될지 예측할 수 있게 만듭니다.

## 목차 검증 테스트: 헤딩만 읽어보기

글을 완성하기 전에 H1과 H2만 모아서 읽어 보는 테스트를 수행합니다. 독자가 헤딩만 보고도 글의 흐름을 이해할 수 있어야 합니다.

**테스트 방법:**

1. 글의 모든 H2를 추출합니다
2. 그 목록만 보고 다음 질문에 답합니다:
   - 독자가 무엇을 하게 될까요?
   - 어떤 순서로 진행되나요?
   - 이 글의 범위는 무엇인가요?

만약 이 질문에 명확하게 답할 수 없다면 H2 헤딩을 더 구체적으로 수정해야 합니다.

## 문서 템플릿: 제목과 구조 설계 카드

글을 쓰기 전에 아래 카드를 채우면 제목과 구조가 동시에 결정됩니다.

```markdown
## 글 설계 카드

**목표 행동 (독자가 글을 읽은 후 할 수 있는 것):**
  예) 로컬에서 FastAPI 엔드포인트를 실행하고 검증하기

**제목 초안 (목표 행동을 제목으로 변환):**
  예) 5분 안에 첫 FastAPI 엔드포인트 실행하기

**H2 헤딩 목록 (목표 행동을 달성하기 위한 단계):**
  1. 환경 확인하기
  2. FastAPI 설치하기
  3. 첫 엔드포인트 작성하기
  4. 로컬 서버 실행하기
  5. 브라우저로 확인하기
  6. 다음 단계

**스캔 테스트 결과 (헤딩만 읽고 흐름이 보이는가):**
  [ ] Yes → 본문 작성 시작
  [ ] No  → 헤딩 다시 수정

**비목표 (이 글에서 다루지 않는 것):**
  - 프로덕션 배포
  - 데이터베이스 연결
  - 인증 설정
```

## 평평한 구조 vs 중첩 구조

글의 구조는 크게 평평한 구조와 중첩 구조로 나뉩니다.

| 구조 유형 | 장점 | 단점 | 적합한 글 |
| --- | --- | --- | --- |
| 평평한 구조 (H2만 사용) | 스캔 속도 빠름, 단계 명확 | 복잡한 주제 다루기 어려움 | 튜토리얼, Quick Start, 체크리스트 |
| 중첩 구조 (H2 > H3 > H4) | 논리적 계층 표현 가능 | 독자가 현재 위치 파악 어려움 | 레퍼런스, 긴 가이드, 개념 설명 |

입문 독자를 위한 글에서는 평평한 구조가 더 효과적입니다. 독자가 단계별로 따라가기 쉽고, 어디까지 진행했는지 한눈에 보이기 때문입니다.

## 개요에서 본문으로: 전환 문장 패턴

개요에서 본문으로, 본문에서 다음 섹션으로 넘어갈 때는 전환 문장을 넣으면 글의 흐름이 자연스럽게 이어집니다.

**패턴 1: 결과 예고형**

"다음 단계를 따라 하면 5분 안에 첫 엔드포인트가 실행됩니다."

독자가 다음 섹션에서 무엇을 얻는지 미리 알고, 동기를 유지합니다.

**패턴 2: 문제 확인형**

"설치가 완료되었다면 이제 첫 코드를 작성해 보겠습니다."

이전 섹션을 완료한 독자만 다음 섹션으로 넘어가도록 유도합니다.

**패턴 3: 구체적 질문형**

"하지만 이 코드를 프로덕션에 배포하려면 어떻게 해야 할까요?"

독자가 다음에 겪을 질문을 미리 던져 주고, 그 답을 다음 섹션에서 제공합니다.

## 구조 품질 체크표

| 체크 항목 | 통과 기준 |
| --- | --- |
| H1 단일성 | 문서에 H1이 1개만 존재 |
| H2 가독성 | H2만 읽어도 전체 흐름 이해 가능 |
| 전환 문장 | 섹션 사이에 다음 행동 예고 문장 존재 |
| 정리 품질 | 핵심 3개 + 다음 단계 1개 포함 |
| 대상 독자 | 도입부에서 독자가 한 문장으로 명시됨 |
| 실행 가능성 | 명령 또는 절차가 구체적으로 적힘 |
| 검증 가능성 | 출력, 상태, 체크포인트가 제시됨 |
| 범위 통제 | 다루지 않는 항목(비목표 또는 한계)이 적힘 |

## 자주 하는 실수

| 실수 | 왜 문제인가 | 바로 고치는 방법 |
| --- | --- | --- |
| 명사만 있는 제목 | "FastAPI 가이드"는 약속이 비어 있다 | 동사와 결과를 함께 두어 독자가 얻는 것을 명시한다 |
| 개요가 너무 깊다 | H3, H4까지 들어간 개요는 처음 보는 독자에게 미로다 | 처음에는 H2만으로 흐름을 잡는다 |
| 첫 단락이 너무 길다 | 독자가 이 글이 자기 문제를 다루는지 판단하지 못한다 | 도입은 세 줄을 넘기지 않는다 |
| 정리가 없다 | 독자가 "그래서 다음에 뭘 해야 하지?"를 모른다 | 한 줄 정리와 다음 행동을 반드시 넣는다 |
| H1이 여러 개다 | 검색 엔진이 우선순위를 결정하지 못한다 | 문서당 H1은 하나만 유지한다 |
| 제목과 본문 불일치 | 독자가 제목 보고 클릭했지만 내용이 다르다 | 제목이 약속한 내용만 본문에서 다룬다 |

## 제목 패턴 비교 표

| 패턴 | 약한 예시 | 개선 예시 |
| --- | --- | --- |
| 명사형 | FastAPI 가이드 | 10분 안에 FastAPI 첫 엔드포인트 실행하기 |
| 범위 과다 | 백엔드 개발 완벽 가이드 | FastAPI 로컬 실행과 검증 체크리스트 |
| 결과 누락 | API 설계 메모 | 입력 검증 실패를 줄이는 FastAPI 요청 모델 설계 |
| SEO 약함 | 빠른 API 팁 | FastAPI 비동기 엔드포인트 응답 시간 줄이기 |

## 헤딩 교정 예시

| 교정 전 | 교정 후 |
| --- | --- |
| `## 소개` | `## FastAPI가 필요한 이유` |
| `## 예제` | `## 최소 엔드포인트 작성하기` |
| `## 정리` | `## 실행 결과 검증하기` |
| `## 기타` | `## 자주 막히는 오류 고치기` |

교정 후 헤딩은 독자가 어디서 무엇을 해야 하는지 바로 알 수 있습니다.

## 실습: 글 한 편의 뼈대 만들기

아래 5단계를 채우면 글의 뼈대가 완성됩니다.

```markdown
## 글 뼈대 설계

1단계 - 제목:
  "Ship your first FastAPI endpoint in five minutes"

2단계 - 개요 (H2만):
  - 환경 준비하기
  - FastAPI 설치하기
  - 첫 엔드포인트 작성하기
  - 로컬에서 실행하기
  - 브라우저로 검증하기

3단계 - 첫 단락 (3줄 이내):
  "이 글은 Python pip를 쓸 줄 아는 입문자를 위한 글입니다.
   5분 안에 첫 FastAPI 엔드포인트를 로컬에서 실행하는 법을 다룹니다.
   배포와 인증은 다루지 않습니다."

4단계 - 각 H2 아래 성공 기준 1개:
  ## 환경 준비하기
  확인: python3 --version이 3.11 이상 출력

5단계 - 정리 문장:
  "이제 직접 엔드포인트를 추가하고 경로 파라미터를 시험해 보세요."
```

## 운영 체크리스트

- [ ] 좋은 제목의 조건(동사 포함, 결과 명시)을 설명할 수 있는가
- [ ] 글의 구조를 잡는 기본 원칙을 말할 수 있는가
- [ ] 독자가 훑어보기 쉬운 구조를 만드는 방법을 설명할 수 있는가
- [ ] H2만 읽어도 전체 흐름이 보이는가
- [ ] 도입부에 독자, 목표, 범위가 명시되어 있는가

## 연습 문제

1. 제목에 동사가 없으면 왜 문제인지 한 문장으로 설명해 보세요.
2. "FastAPI 소개"를 더 좋은 제목으로 고쳐 보세요.
3. 아래 개요를 행동 기반 개요로 바꿔 보세요.
   - `## 개요`, `## 내용`, `## 결론`

## 정리

제목은 약속이고, 개요는 지도이며, 정리는 독자를 다음 행동으로 밀어 주는 마무리입니다. 제목과 H2만 먼저 잡고 스캔 테스트를 통과한 뒤 본문을 채우면, 방향을 잃지 않고 글을 완성할 수 있습니다. 다음 글에서는 이 구조 안에서 개념을 어떻게 설명해야 독자가 오래 기억하는지 봅니다.
