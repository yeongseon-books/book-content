# Technical Writing 101 (9/10): 블로그와 문서 차이

같은 주제를 다뤘다는 이유로 블로그 글과 공식 문서를 같은 선반에 올려두면 운영이 금방 어긋납니다. 장애 원인을 설명한 회고 글은 훌륭한 맥락 자료가 될 수 있지만, 지금 팀이 따라야 할 절차의 정본이 되기에는 최신성 보장이 약합니다. 반대로 공식 문서는 정본으로서 강하지만, 왜 그런 결정을 했는지까지 늘 충분히 설명하지는 못합니다.

이 글은 기술 글쓰기 101 시리즈의 9번째 글입니다.

그래서 강한 팀은 블로그와 문서를 경쟁시키지 않고 역할을 나눕니다. 경험과 해석은 블로그에 남기고, 현재의 기준과 절차는 문서에 고정한 뒤 서로를 정확하게 링크합니다.

여기서는 블로그와 문서를 역할, 최신성, 소유권 관점에서 구분하는 기준을 다룹니다.

![Technical Writing 101 9장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/technical-writing-101/09/09-01-concept-at-a-glance.ko.png)
*Technical Writing 101 9장 흐름 개요*
> 블로그는 배경과 맥락을, 문서는 현재 기준과 절차를 맡는 분업 구조가 핵심입니다.

## 이 글에서 다룰 문제

- 블로그와 공식 문서는 왜 서로 섞이면 안 될까요?
- 둘의 생명주기와 소유권은 무엇이 다를까요?
- Diátaxis의 네 구역은 이 차이를 어떻게 설명해 줄까요?
- 블로그를 공식 문서로 승격시키려면 무엇이 필요할까요?
- 블로그와 문서를 어떻게 링크로 연결해야 할까요?

## 이 글에서 배울 것

- Diátaxis의 네 구역 분류
- 블로그와 문서의 생명주기 차이
- 역할 구분 기준 (경험 vs 현재 기준)
- 블로그에서 문서로 승격하는 조건
- 블로그와 문서를 연결하는 링크 정책

글의 종류가 섞이면 독자가 길을 잃습니다. 블로그를 공식 문서처럼 인용하거나, 공식 문서를 개인 경험담처럼 쓰는 순간 신뢰의 기준이 흐려집니다.

## 한눈에 보는 멘탈 모델

> 멘탈 모델: 블로그는 경험과 해석을 담고, 문서는 지금 따라야 할 기준을 담습니다. 둘은 연결할 수 있지만 서로를 대신하면 안 됩니다.

- **Diátaxis**: 네 구역 문서 모델입니다.
- **lifecycle**: 생명주기입니다.
- **freshness**: 최신성입니다.
- **canonical**: 정본입니다.
- **archive**: 아카이브입니다.

## 블로그 vs 문서 역할 구분 구조

```
같은 주제 (예: FastAPI 인증)
            │
     ┌──────┴──────┐
     │             │
  블로그          문서
     │             │
 경험, 해석     현재 기준
 결정 배경      절차, 사양
 특정 시점      지속 업데이트
 필자 소유      팀/조직 소유
     │             │
  링크 ──────────▶ 정본 문서
  (배경 이해)      (지금 따라야 할 것)
```

블로그와 문서는 같은 주제를 다뤄도 독자에게 답하는 질문이 다릅니다. 블로그는 "왜 그렇게 했는가"를, 문서는 "지금 어떻게 해야 하는가"를 답합니다.

## Before / After 비교: 역할 혼동 vs 역할 분리

### Before / After 예시 1: 블로그를 정본으로 인용하는 경우

**Before — 블로그를 공식 문서처럼 사용**

```markdown
FastAPI 인증 구현은 [우리 팀 블로그 글](https://blog.example.com/auth-2025)을 참고하세요.
```

이 블로그가 6개월 후 낡으면 독자는 잘못된 정보를 따릅니다.

**After — 역할에 맞게 분리**

```markdown
# 인증 구현 가이드

현재 FastAPI 인증 구현 방법은 아래를 따릅니다.

[현재 기준 명시 — 코드 포함]

## 더 알아보기

결정 배경이 궁금하다면 [2025년 10월 설계 회고](https://blog.example.com/auth-2025)를 읽어 보세요.
```

문서가 정본을 유지하고, 블로그는 배경 자료로 연결됩니다.

---

### Before / After 예시 2: 버전 없는 문서 vs 버전 명시 문서

**Before — 언제 작성한 문서인지 알 수 없음**

```markdown
# 인증 방식

세션 기반 인증을 사용합니다.
```

독자는 이 문서가 현재 기준인지, 2년 전 글인지 알 수 없습니다.

**After — 버전과 업데이트 날짜 명시**

```markdown
# 인증 방식

> 최종 업데이트: 2026-05-21
> 버전: FastAPI 0.110, Python 3.11

세션 기반 인증을 사용합니다.
```

독자는 이 문서가 현재 기준임을 확인할 수 있습니다.

---

### Before / After 예시 3: 정본 링크 없는 블로그 vs 정본 링크 포함 블로그

**Before — 블로그 말미에 정본 링크 없음**

블로그 글이 오래되어도 독자가 최신 정보를 찾을 방법이 없습니다.

**After — 블로그 말미에 아카이브 안내와 정본 링크**

```markdown
> 이 글은 FastAPI 0.104 기준(2025년 10월)으로 작성되었습니다.
> 현재 공식 인증 가이드는 [docs.example.com/auth](https://docs.example.com/auth)를 참고하세요.
```

## 문서 템플릿: 블로그와 문서 역할 구분 카드

**블로그 작성 체크리스트:**

```markdown
## 작성 전 확인

- [ ] 이 글이 경험이나 해석을 공유하는가? (Yes → 블로그)
- [ ] 현재 코드베이스와 일치하는 절차를 다루는가? (Yes → 문서)
- [ ] 특정 시점의 결정 배경을 설명하는가? (Yes → 블로그)

## 블로그 글 표준 구조

제목: [주제]에 대해 우리가 배운 것 / [결정]을 한 이유

작성 시점: [날짜] 기준
버전: [패키지 버전]

[본문]

---
> 현재 공식 가이드: [링크]
```

**문서 작성 체크리스트:**

```markdown
## 작성 전 확인

- [ ] 팀이 지금 따라야 할 절차인가?
- [ ] 코드 변경과 함께 업데이트할 수 있는가?
- [ ] PR 리뷰를 받을 수 있는가?

## 문서 표준 헤더

> 최종 업데이트: [날짜]
> 버전: [버전]

[본문]
```

## 블로그 vs 공식 문서 비교 표

| 항목 | 블로그 | 공식 문서 |
| --- | --- | --- |
| **수명** | 기록 시점 기준, 아카이브 가능 | 현재 기준, 지속적 갱신 필수 |
| **업데이트 주기** | 불정기, 필요시 개정 | 코드 변경과 함께 즉시 |
| **작성 비용** | 낮음, 개인이 빠르게 발행 | 높음, 팀 리뷰와 법적 검토 필요 |
| **독자 기대** | 경험, 해석, 의견, 팀의 고민 | 정확한 사양, 절차, 기준 |
| **노후화 처리** | 아카이브 표시 또는 삭제 | 버전 분리, 마이그레이션 가이드 |
| **책임 범위** | 필자 개인 | 팀 또는 조직 |
| **커밋 주기** | 자유롭게 발행 | PR 리뷰 후 머지 |

## 판단 흐름도

```text
이 글이 현재 팀의 공식 기준인가?
  │
  ├─ Yes → 문서로 작성
  │       - 코드베이스와 함께 버전 관리
  │       - PR 리뷰 필수
  │       - 팀 소유권
  │
  └─ No  → 블로그로 작성
          - 개인 또는 팀 경험 공유
          - 문서 정본을 링크로 제공
          - 기록 시점 명시
```

## Diátaxis 네 구역

| 구역 | 목적 | 독자 질문 | 톤 |
| --- | --- | --- | --- |
| **Tutorial** | 학습 | "어떻게 시작하나요?" | 경험을 만들기 |
| **How-to** | 문제 해결 | "이걸 어떻게 하나요?" | 지시하기 |
| **Reference** | 정보 | "이 함수는 무엇을 받나요?" | 설명하기 |
| **Explanation** | 이해 | "왜 이렇게 되나요?" | 토론하기 |

블로그는 주로 Explanation에 해당합니다. "우리가 세션 인증을 선택한 이유"는 왜(Why)를 다루기 때문입니다. 공식 문서는 Tutorial, How-to, Reference에 해당합니다.

## 블로그와 문서 역할 혼동 비용 비교

역할이 섞이면 팀과 독자 양쪽에 비용이 발생합니다. 어느 쪽이 더 클지 사전에 파악해 두면 운영 결정이 빨라집니다.

| 혼동 유형 | 팀 비용 | 독자 비용 | 복구 난이도 |
| --- | --- | --- | --- |
| 블로그를 정본으로 유지 | 블로그 최신성 유지 부담 증가 | 낡은 절차를 따를 위험 | 높음 — 블로그 수정 + 독자 공지 필요 |
| 문서를 경험 공유 형식으로 작성 | 기술 리뷰 기준 불명확 | 절차와 의견을 구분 못함 | 중간 — 재구조화 필요 |
| 둘 다 같은 제목으로 운영 | 중복 유지보수 | 어느 글이 정본인지 모름 | 높음 — 한쪽 폐기 또는 명확한 구분 필요 |
| 아카이브 정책 없음 | 낡은 글이 계속 색인에 노출 | 검색 결과에서 구버전을 따름 | 중간 — 아카이브 태그 + 리디렉션 추가 |
| 정본 링크 없음 | 독자 문의가 팀으로 들어옴 | 최신 정보를 직접 찾아야 함 | 낮음 — 링크 추가만으로 해결 가능 |

## 팀 유형별 블로그·문서 분리 전략

팀 규모와 성숙도에 따라 분리 전략의 깊이가 달라집니다.

| 팀 유형 | 블로그 운영 주체 | 문서 운영 주체 | 분리 방식 |
| --- | --- | --- | --- |
| 1인 개발자 | 본인 | 본인 | 저장소 README + 별도 블로그 URL |
| 소규모 팀 (2-4명) | 작성자 개인 | 팀 공동 소유, PR 리뷰 | GitHub Discussions + docs/ 디렉토리 |
| 중간 팀 (5-20명) | 개인 블로그 또는 팀 블로그 | Tech Writer 또는 담당자 | 별도 도메인 (blog.example.com vs docs.example.com) |
| 대형 팀 (20명+) | 커뮤니케이션팀 | DevRel + Eng 공동 | 전용 CMS + 문서 플랫폼 분리 |

소규모 팀일수록 같은 사람이 두 역할을 하게 됩니다. 이때는 파일 위치와 URL로 역할을 구분하는 것만으로도 효과가 있습니다.

## 실제 시나리오: 블로그·문서 혼동이 만드는 문제

### 시나리오 A — 블로그가 사실상 문서 역할을 하다가 낡은 경우

한 스타트업 팀은 초기에 기술 블로그에 배포 절차를 상세하게 작성했습니다. 편리했기 때문에 신입 팀원 온보딩 자료로도 그 블로그를 링크했습니다.

6개월 후, 배포 도구를 교체했지만 블로그는 그대로였습니다. 신입이 블로그를 보고 구버전 절차를 따르다가 배포에 실패했습니다. 문제를 파악하는 데 반나절이 걸렸습니다.

**원인**: 블로그에 최신성 보장 의무가 없었고, 정본 문서가 없었습니다.

**개선**: 블로그에 "이 글은 2025년 6월 기준" 안내와 정본 문서 링크를 추가하고, 배포 절차는 별도 `docs/deploy.md`로 분리했습니다.

**6개월 후**: 배포 절차가 바뀔 때마다 `docs/deploy.md`만 업데이트하고 PR 리뷰를 받습니다. 블로그는 의사결정 배경 자료로 남아 있고, 신입 온보딩에는 문서 링크를 사용합니다.

---

### 시나리오 B — 문서가 경험 공유 형식으로 작성된 경우

한 팀의 API 인증 문서가 "우리가 처음에 JWT를 시도하고 세션으로 바꾼 이유"라는 제목으로 작성되어 있었습니다. 내용이 길고 자세해서 유용했지만, 실제로 지금 어떻게 구현해야 하는지는 중간 어딘가에 묻혀 있었습니다.

신입 개발자가 이 문서를 읽고 전체 의사결정 과정을 구현 가이드로 오해해 구버전 코드를 참고했습니다.

**원인**: 문서가 Explanation(이해) 형식으로 작성되었는데, 독자는 How-to(지시) 정보를 찾고 있었습니다.

**개선**: 문서를 둘로 나눴습니다. `docs/auth.md`는 현재 구현 방법만 명확하게 지시 형식으로 작성했고, 블로그에는 의사결정 배경을 남겼습니다. `docs/auth.md` 상단에 블로그 링크를 "결정 배경 읽기" 섹션으로 추가했습니다.

## 블로그에서 문서로 승격하는 조건

블로그 글이 팀 내에서 정본처럼 쓰이기 시작했다면 문서로 승격할 시점입니다.

| 신호 | 의미 | 조치 |
| --- | --- | --- |
| 블로그를 온보딩 자료로 링크함 | 절차 문서 역할을 대신하고 있음 | 절차 부분을 `docs/`로 분리 |
| 팀원이 "블로그 최신화해 주세요" 요청 | 정본 역할로 인식되고 있음 | 문서로 승격 후 블로그에 링크 |
| 코드 변경 PR에 블로그도 같이 수정 요청 | 유지보수 부담이 이미 문서 수준 | 처음부터 문서로 관리 |
| 블로그가 6개월 이상 갱신 안 됐는데 자주 인용됨 | 낡은 정보가 신뢰 자료로 쓰임 | 아카이브 표시 + 새 문서 작성 |

승격할 때는 블로그를 삭제하지 않고 상단에 아카이브 안내와 새 문서 링크를 추가하는 것이 좋습니다. 검색 유입 독자가 여전히 찾아올 수 있기 때문입니다.

## 자주 하는 실수

| 실수 | 왜 문제인가 | 바로 고치는 방법 |
| --- | --- | --- |
| 블로그를 공식 문서처럼 인용합니다 | 블로그가 낡으면 독자가 잘못된 정보를 따릅니다 | 공식 문서를 별도로 만들고 블로그에서 링크합니다 |
| 문서를 오래된 채로 둡니다 | 독자가 현재 시스템과 다른 절차를 따릅니다 | 코드 변경 PR에 문서 업데이트를 포함합니다 |
| 버전을 적지 않습니다 | 독자가 문서의 유효성을 판단하기 어렵습니다 | 모든 문서 상단에 버전과 날짜를 명시합니다 |
| 아카이브 정책이 없습니다 | 낡은 글이 정본처럼 계속 유통됩니다 | 블로그에 아카이브 표시와 최신 문서 링크를 추가합니다 |
| 정본 링크가 없습니다 | 독자가 어느 글을 따라야 하는지 모릅니다 | 블로그 말미에 항상 정본 문서 링크를 둡니다 |

## 면접에서 블로그·문서 경험 설명하기

기술 글쓰기 경험을 면접에서 설명할 때, 블로그와 문서를 구분해서 운영한 경험은 좋은 신호로 읽힙니다.

| 면접 질문 | 약한 답변 | 강한 답변 |
| --- | --- | --- |
| "문서 작성 경험이 있나요?" | "팀 블로그에 기술 글을 자주 썼습니다." | "블로그는 의사결정 배경을 남기는 용도로, 실제 절차는 `docs/` 디렉토리에 PR 리뷰를 거쳐 관리했습니다." |
| "문서 최신성을 어떻게 유지했나요?" | "주기적으로 확인했습니다." | "코드 변경 PR에 관련 문서 업데이트를 필수 항목으로 포함했고, CI에서 링크 검사를 자동으로 돌렸습니다." |
| "블로그와 공식 문서를 어떻게 구분했나요?" | "둘 다 기술 내용을 다뤘습니다." | "블로그는 Diátaxis의 Explanation 역할로, 문서는 How-to와 Reference 역할로 구분해서 작성했고, 블로그 말미에는 항상 정본 문서 링크를 달았습니다." |

## 운영 체크리스트

- [ ] 새로 쓸 글이 블로그인지 문서인지 먼저 결정했는가
- [ ] 블로그라면 기록 시점과 버전이 명시되어 있는가
- [ ] 블로그 말미에 정본 문서 링크가 있는가
- [ ] 문서라면 최종 업데이트 날짜와 버전이 있는가
- [ ] 낡은 블로그에 아카이브 안내가 있는가
- [ ] 블로그가 온보딩 자료로 사용되고 있다면 문서 승격을 검토했는가
- [ ] 코드 변경 PR에 관련 문서 업데이트가 포함되어 있는가

## 연습 문제

1. 다음 글 목록을 블로그와 문서로 분류하세요.
   - a. "우리 팀이 GraphQL 대신 REST를 선택한 이유"
   - b. "API 비밀번호 관리 정책"
   - c. "5월 10일 장애 회고"
   - d. "배포 체크리스트"
2. 블로그를 공식 문서로 승격하려면 어떤 조건이 필요한지 세 가지를 적어 보세요.
3. Diátaxis의 네 구역 중 어느 구역이 "왜 이런 설계를 했는가"를 다루는지 답하세요.

## 정리

블로그와 문서는 같은 기술을 다뤄도 역할이 다릅니다. 블로그는 경험과 배경을 남기고, 문서는 지금 따라야 할 기준을 유지합니다. 둘을 링크로 연결하는 것은 좋지만, 서로를 대신하게 두면 안 됩니다. 블로그는 항상 정본 문서를 가리키고, 문서는 코드 변경과 함께 갱신하는 규칙을 팀 수준에서 합의하면 운영 혼선을 크게 줄일 수 있습니다. 다음 글에서는 발행 직전에 무엇을 어떻게 점검해야 하는지 시리즈 마지막 정리로 이어 가겠습니다.
