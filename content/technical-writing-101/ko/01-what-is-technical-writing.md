# Technical Writing 101 (1/10): 기술 글쓰기란 무엇인가

기술 글쓰기를 처음 배울 때는 문장을 매끈하게 다듬는 일부터 떠올리기 쉽습니다. 하지만 현업에서 더 자주 문제를 만드는 것은 문체보다 방향입니다. 독자가 누구인지, 무엇을 하려는지, 어디서 막힐지를 잡지 못하면 문장이 아무리 자연스러워도 실행 가능한 문서가 되지 않습니다.

이 글은 기술 글쓰기 101 시리즈의 첫 번째 글입니다.

팀 문서, README, 튜토리얼, 장애 대응 메모가 모두 같은 이유로 중요합니다. 읽는 사람이 그 글을 바탕으로 설치하고, 실행하고, 비교하고, 복구해야 하기 때문입니다. 기술 글은 정보를 전달하는 글이면서 동시에 행동을 설계하는 글입니다.

여기서는 기술 글을 독자, 작업, 결과, 범위로 나누어 보는 기본 틀을 먼저 세웁니다.

*Technical Writing 101 1장 흐름 개요*
> 기술 글은 정보 전달을 넘어 독자의 행동을 설계하는 글입니다.

## 이 글에서 다룰 문제

- 기술 글쓰기는 일반 글쓰기와 무엇이 다를까요?
- 기술 글은 왜 설명에서 끝나지 않고 독자의 행동까지 이어져야 할까요?
- 기술 글의 목적을 독자, 작업, 결과, 범위로 나누면 무엇이 또렷해질까요?
- 이 개념을 실무에서 잘못 적용하면 어떤 문제가 생길까요?
- 이 주제에서 초보자가 가장 자주 놓치는 포인트는 무엇일까요?

## 이 글에서 배울 것

- 기술 글쓰기의 정의
- 일반 글과의 차이
- 세 가지 목적
- 독자의 행동
- 시리즈의 형태

## 한눈에 보는 멘탈 모델

> 기술 글은 정보를 나열하는 글이 아니라, 독자의 질문을 답으로 연결하고 그 답을 실제 행동으로 넘기는 글입니다.

- **technical writing**: 기술 정보를 전달하는 산문입니다.
- **audience**: 독자입니다.
- **task**: 해야 할 일입니다.
- **outcome**: 결과입니다.
- **scope**: 경계입니다.

## 기술 글쓰기의 정의

기술 글쓰기(technical writing)는 특정 독자가 특정 작업을 수행할 수 있도록 기술 정보를 정확하고 명확하게 전달하는 글쓰기입니다. 마케팅 카피나 소설과 달리 기술 글은 감동을 주는 것이 목적이 아니라, 독자가 그 글을 읽고 무언가를 할 수 있게 만드는 것이 목적입니다.

기술 글에는 여러 유형이 있습니다.

| 유형 | 목적 | 독자 | 대표 형식 |
| --- | --- | --- | --- |
| API 문서 | 함수와 클래스 레퍼런스 | 통합 개발자 | OpenAPI, JSDoc |
| 튜토리얼 | 학습 경로 제공 | 입문자 | 단계별 가이드 |
| README | 프로젝트 소개 | 기여자, 사용자 | Markdown |
| 블로그 | 경험 공유 | 동료 엔지니어 | 스토리형 포스트 |
| 팀 문서 | 내부 기준 공유 | 팀원 | 위키, Confluence |
| 장애 회고 | 사후 분석 | SRE, 팀 리더 | Incident report |

각 유형이 요구하는 문체와 구조는 다르지만, 공통점은 분명합니다. 모두 독자가 다음 행동을 할 수 있게 만들어야 합니다.

## 기술 글과 일반 글의 차이

일반 글쓰기와 기술 글쓰기는 목적이 다릅니다. 일반 글은 독자를 설득하거나 즐겁게 하거나 감동시키는 것을 목표로 합니다. 기술 글은 독자가 정확히 무언가를 할 수 있게 안내하는 것을 목표로 합니다.

### 구조 다이어그램: 일반 글 vs 기술 글

```
일반 글 흐름
============
도입 (감정적 훅)
  |
  v
본문 (서사/논증)
  |
  v
결말 (여운/인상)

기술 글 흐름
============
독자 + 목표 선언
  |
  v
전제 조건 확인
  |
  v
단계별 실행 (검증 지점 포함)
  |
  v
결과 확인 + 다음 단계
```

기술 글에서 "독자"와 "목표"를 먼저 선언하는 이유는 독자가 이 글이 자기에게 맞는지 첫 단락에서 판단해야 하기 때문입니다. 일반 글은 끝까지 읽어야 가치를 알 수 있지만, 기술 글은 첫 문단만 봐도 "내가 읽어야 할 글인가?"가 명확해야 합니다.

## 독자, 작업, 결과, 범위를 한 번에 맞추는 표

| 항목 | 약한 문장 | 더 나은 문장 |
| --- | --- | --- |
| 독자 | 개발자 | FastAPI로 첫 API를 만드는 주니어 백엔드 엔지니어 |
| 작업 | 환경 설정 | 가상환경을 만들고 의존성을 설치하기 |
| 결과 | 성공 | `(.venv)` 프롬프트가 보이고 `pip list`에 패키지가 나타나기 |
| 범위 | 파이썬 시작 | 로컬 개발 환경 준비까지만 다루기 |

이 표가 중요한 이유는 기술 글의 모호함이 대개 첫 문장에서 시작되기 때문입니다. 독자를 넓게 잡으면 작업도 넓어지고, 결과는 눈에 보이지 않게 되며, 결국 문서는 친절해 보이지만 실행은 어려운 상태로 남습니다.

## Before / After 비교: 모호한 글을 실행 문서로 바꾸기

같은 내용이라도 문장 구조에 따라 명확성이 크게 달라집니다. 아래는 실제로 자주 보이는 나쁜 문장 패턴과 개선 예시입니다.

### Before / After 예시 1: 독자가 모호한 문장

**Before**

> "이 가이드는 개발자를 위한 것입니다."

**After**

> "이 가이드는 Python을 처음 배우는 주니어 백엔드 개발자를 위한 것입니다. pip 설치와 git 기본 명령은 알고 있다고 가정합니다."

**개선 이유**: 독자가 구체적일수록 전제 지식, 예제 난이도, 생략 가능한 배경이 명확해집니다.

### Before / After 예시 2: 결과가 보이지 않는 문장

**Before**

> "설치가 성공하면 준비가 끝납니다."

**After**

> "설치가 성공하면 터미널에 `(.venv)` 프롬프트가 나타나고, `pip list`를 실행했을 때 패키지 목록이 출력됩니다."

**개선 이유**: 독자가 눈으로 확인할 수 있는 결과를 제시해야 다음 단계로 안전하게 넘어갈 수 있습니다.

### Before / After 예시 3: 명령이 실행되지 않는 문장

**Before**

> "가상환경을 만드세요."

**After**

> "터미널에서 `python3 -m venv .venv`를 실행하세요. 그 다음 `source .venv/bin/activate`로 활성화하면 프롬프트 앞에 `(.venv)`가 나타납니다."

**개선 이유**: 독자가 복사해 붙여 넣을 수 있는 명령과 성공 확인 방법을 함께 제시해야 실제 행동으로 이어집니다.

### Before / After 예시 4: 범위가 불명확한 문장

**Before**

> "Python 입문 가이드입니다."

**After**

> "이 가이드는 로컬 개발 환경 준비까지만 다룹니다. 배포, CI/CD, Docker는 다루지 않습니다."

**개선 이유**: 비목표를 적어 두면 독자는 이 글이 자기 질문에 답하는지 빠르게 판단할 수 있습니다.

## 기술 글의 계층 모델 (What / How / Why)

기술 글은 단일 계층이 아니라 세 계층으로 나누어 생각하면 훨씬 구조화하기 쉽습니다.

```
기술 글 3계층 구조
==================
계층 1: What (무엇)
  - 독자가 달성할 최종 결과
  - 예: "가상환경을 만들고 활성화하기"

계층 2: How (어떻게)
  - 단계별 명령과 예상 결과
  - 예: python3 -m venv .venv && source .venv/bin/activate
  - 성공 확인: (.venv) 프롬프트 표시

계층 3: Why (왜)
  - 이 작업이 필요한 이유
  - 다른 방법과의 차이
  - 하지 않았을 때 발생할 문제
```

**예시: 가상환경 설명**

- **What**: 가상환경은 프로젝트별로 분리된 Python 환경입니다.
- **How**: `python3 -m venv .venv && source .venv/bin/activate`
- **Why**: 전역 패키지 충돌을 피하고, 프로젝트별 의존성을 분리하기 위해서입니다.

계층 3(Why)이 없으면 독자는 명령은 따라 하지만 응용하지 못합니다. 왜 그 명령이 필요한지 알아야 비슷한 상황에서 스스로 판단할 수 있습니다.

## 문서 템플릿: 기술 글 작성 시작 카드

기술 글을 쓰기 전에 아래 여섯 줄을 먼저 채우면, 글이 설명 중심에서 행동 중심으로 자연스럽게 이동합니다.

```text
독자:
  (누가 이 글을 읽는가? 경력, 기술 수준, 역할을 구체적으로)

전제 지식:
  (독자가 이미 알고 있다고 가정하는 것 3가지)

목표 행동:
  (이 글을 읽은 후 독자가 할 수 있는 것 1가지, 동사형으로)

성공 기준:
  (성공을 눈으로 확인하는 방법, 터미널 출력/HTTP 응답/파일 존재 등)

비목표:
  (이 글에서 다루지 않는 것 2-3가지)

다음 단계:
  (이 글을 마친 독자가 읽어야 할 다음 글 또는 할 수 있는 일)
```

### 작성 예시

```text
독자:
  Python을 처음 배우는 주니어 백엔드 개발자 (경력 0-1년)

전제 지식:
  1. 터미널을 열고 명령을 입력할 수 있다
  2. Python 3.x가 설치되어 있다
  3. pip install이 무엇인지 안다

목표 행동:
  FastAPI 가상환경을 만들고 첫 엔드포인트를 로컬에서 실행하기

성공 기준:
  curl http://127.0.0.1:8000 실행 시 {"message":"Hello World"} 출력

비목표:
  1. 배포 (AWS, GCP, Docker 등)
  2. 인증 및 보안 설정
  3. 데이터베이스 연결

다음 단계:
  경로 파라미터 추가하기 (02-path-parameters.md)
```

## 기술 글 작성 순서

많은 사람이 글을 위에서부터 아래로 순서대로 쓰기 시작합니다. 하지만 기술 글은 다음 순서로 작성하는 편이 훨씬 효율적입니다.

```
기술 글 작성 순서
================
1단계: 독자 + 목표 카드 작성
   (독자, 전제 지식, 목표, 비목표, 성공 기준)
          |
          v
2단계: H2 개요만 먼저 나열
   (헤딩만 읽어도 흐름이 보여야 함)
          |
          v
3단계: 실행 가능한 코드 예제 확보
   (예제가 실제로 돌아가는지 확인)
          |
          v
4단계: 본문 작성
   (각 섹션마다 What + How + Why)
          |
          v
5단계: 검증
   (처음부터 따라 해 보기 / 동료 리뷰)
```

## 테크니컬 라이팅의 유형별 특징

| 유형 | 목적 | 독자 | 분량 | 특징 |
| --- | --- | --- | --- | --- |
| API 문서 | 함수, 클래스 레퍼런스 | 통합 개발자 | 짧고 반복적 | 정확성, 완전성, 검색 가능성 |
| 튜토리얼 | 학습 경로 제공 | 입문자 | 중간 길이 | 단계별 구조, 실행 예제, 검증 지점 |
| README | 프로젝트 소개 | 기여자, 사용자 | 짧음 | Quick Start, 설치, 예제, 라이선스 |
| 블로그 | 경험 공유 | 동료 엔지니어 | 중간~긴 길이 | 스토리, 트러블슈팅, 의사결정 배경 |

## 좋은 기술 문서의 공통 특징

형식은 달라도 좋은 기술 글은 다섯 가지 공통 특징을 보입니다.

**1. 독자가 분명합니다**

"개발자"가 아니라 "FastAPI로 첫 API를 만드는 주니어"처럼 구체적입니다. 독자를 좁게 잡을수록 설명 깊이, 용어 선택, 전제 지식이 또렷해집니다.

**2. 명령이 실행됩니다**

복사해 붙여 넣으면 바로 돌아가야 합니다. 환경 변수, 버전, 경로가 모두 갖춰져 있어야 합니다. 실행 불가능한 예제는 독자를 가르치지 못하고 좌절시킵니다.

**3. 결과가 눈에 보입니다**

"성공했습니다"가 아니라 "터미널에 `(.venv)` 프롬프트가 나타납니다"처럼 검증 가능해야 합니다.

**4. 범위가 명확합니다**

무엇을 다루고, 무엇을 다루지 않는지 미리 밝힙니다. 비목표를 적어 두면 독자는 이 글이 자기 질문에 답하는지 빠르게 판단할 수 있습니다.

**5. 낡은 정보를 지웁니다**

오래된 버전, 비추천 방법, 깨진 링크는 신뢰를 깎습니다.

## 기술 글의 수명 주기와 유지보수 전략

기술 글은 발행 후에도 계속 관리해야 합니다.

| 단계 | 기간 | 주요 작업 |
| --- | --- | --- |
| 발행 직후 | 0-1주 | 오타 수정, 독자 피드백 수집, 누락 예제 보강 |
| 안정화 | 1주-3개월 | 라이브러리 버전 업 시 코드 검증, FAQ 섹션 추가 |
| 유지보수 | 3-12개월 | 분기별 링크 체크, 코드 예제 실행 검증 |
| 아카이브 | 12개월+ | "이 글은 [version] 기준" 명시, 아카이브 경고 표시 |

## 자주 하는 실수

| 실수 | 왜 문제인가 | 바로 고치는 방법 |
| --- | --- | --- |
| 독자가 모호하다 | 난이도와 용어가 흔들린다 | 도입부에 독자와 전제 지식을 1문장으로 고정한다 |
| 이론이 너무 많다 | 독자가 행동하지 못한다 | 각 개념마다 실행 가능한 예제를 1개씩 붙인다 |
| 명령을 복사할 수 없다 | 독자가 직접 입력 중 오류를 만든다 | 코드 블록을 사용하고 버전을 고정한다 |
| 결과가 보이지 않는다 | 독자가 성공 여부를 모른다 | 단계마다 눈으로 확인 가능한 출력 1개를 붙인다 |
| 다음 단계가 없다 | 학습 흐름이 끊긴다 | 마지막에 다음 글이나 실습 링크를 2-3개 제시한다 |
| 범위가 과다하다 | 글이 길어지고 완주율이 떨어진다 | 비목표 섹션으로 제외 범위를 먼저 선언한다 |

## 협업 문서를 위한 리뷰 체크리스트

팀에서 글을 작성할 때는 동료에게 리뷰를 요청하기 전에 아래 항목을 점검합니다.

- [ ] 모든 명령을 처음부터 따라 해 보았는가
- [ ] 링크가 모두 살아 있는가
- [ ] 코드 예제가 최신 버전에서 돌아가는가
- [ ] 오타가 없는가
- [ ] 독자, 전제 지식, 목표, 비목표가 명시되어 있는가
- [ ] 제목이 글의 내용과 일치하는가
- [ ] 각 섹션이 계층 구조를 따르는가 (What, How, Why)

## 기술 글의 실패 사례 3가지

**사례 1: 독자를 너무 넓게 잡은 글**

"이 튜토리얼은 개발자를 위한 것입니다"라고 시작한 글은 초보자에게는 어렵고, 숙련자에게는 불필요합니다. 독자를 좁게 잡으면 설명 깊이가 명확해집니다.

**사례 2: 결과를 명시하지 않은 글**

"설치가 완료되었습니다"로 끝나는 단계는 독자에게 확신을 주지 못합니다. 터미널 프롬프트, 로그 출력, 파일 존재, HTTP 응답처럼 눈으로 확인할 수 있는 결과를 제시해야 합니다.

**사례 3: 오래된 정보를 방치한 글**

라이브러리가 메이저 버전을 올리면 API가 바뀌고, 설치 명령이 바뀌며, 설정 구조가 달라집니다. 이때 글을 업데이트하지 않으면 독자는 글을 따라 했지만 실패하고, 글의 신뢰를 잃게 됩니다.

## 기술 글의 평가 기준

기술 글은 다음 네 가지 기준으로 평가할 수 있습니다.

| 기준 | 설명 | 검증 방법 |
| --- | --- | --- |
| 실행 가능성 | 독자가 명령을 그대로 따라 할 수 있는가 | 명령을 복사해 붙여 넣고 실행해 보기 |
| 결과 검증 가능성 | 독자가 성공 여부를 눈으로 확인할 수 있는가 | 결과 문장이 구체적인지 확인하기 |
| 범위 명확성 | 글이 다루는 것과 다루지 않는 것이 분명한가 | 비목표 섹션이 있는지 확인하기 |
| 유지 가능성 | 글을 오래 유지보수할 수 있는 구조인가 | 링크와 코드를 분기별로 점검할 수 있는지 확인하기 |

## 실습: 짧은 기술 단락 하나 만들기

아래 5단계를 채우면 최소 기술 단락 하나가 완성됩니다.

```text
1단계 - 독자:
  Python beginners

2단계 - 작업:
  Create and activate a virtual environment

3단계 - 명령:
  python3 -m venv .venv
  source .venv/bin/activate

4단계 - 결과:
  (.venv) shows up in the prompt

5단계 - 다음 행동:
  pip install requests
```

이 단락의 핵심은 세 가지입니다. 독자가 가장 먼저 나옵니다. 명령은 짧습니다. 결과는 눈으로 확인할 수 있습니다.

## 운영 체크리스트

- [ ] 독자가 분명히 적혀 있는가
- [ ] 작업이 한 줄로 정리되는가
- [ ] 명령이 실제로 실행되는가
- [ ] 결과가 문장으로 드러나는가

## 연습 문제

1. 기술 글쓰기의 정의를 한 줄로 적어 보세요.
2. audience의 뜻을 한 줄로 적어 보세요.
3. outcome의 뜻을 한 줄로 적어 보세요.
4. 주변에서 본 기술 글 하나를 골라 독자, 작업, 결과, 범위를 표로 정리해 보세요.

## 정리

기술 글은 정보를 설명하는 데서 멈추지 않고, 독자가 바로 행동할 수 있게 만들어야 합니다. 그래서 독자, 작업, 명령, 결과, 다음 단계가 모두 분명해야 합니다. 다음 글에서는 같은 내용을 써도 누구를 위해 쓰느냐에 따라 문장이 어떻게 달라지는지 봅니다.
