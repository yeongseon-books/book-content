# 바이브코딩을 위한 CS를 위한 수학 (10/10): 알고리즘과 수학

이 글은 "바이브코딩을 위한 CS를 위한 수학" 시리즈의 마지막 글입니다.

---

바이브코딩에서 AI는 알고리즘 코드를 빠르게 만들어 줍니다. 그런데 AI가 만든 코드가 입력이 커지면 왜 느려지는지, 왜 특정 문제는 완전 탐색이 불가능한지, 더 나은 알고리즘이 있는지 판단하려면 수학적 사고가 필요합니다.

알고리즘을 처음 배울 때는 대개 구현에 집중합니다. 동작하면 일단 성공처럼 느껴집니다. 하지만 실제 시스템에서는 그다음 질문이 훨씬 중요합니다. 얼마나 빠른지, 어떤 모델로 바꿔야 풀리는지, 더 줄일 수 없는 이론적 한계는 무엇인지를 봐야 합니다.

이 지점에서 이 시리즈의 수학이 하나로 묶입니다. 조합론은 경우의 수 폭발을 설명하고, 그래프는 문제 구조를 드러내고, 확률은 무작위 알고리즘을 가능하게 하며, 미분은 최적화를 움직이고, 정보이론은 넘을 수 없는 한계를 알려 줍니다.

수학 도구들이 알고리즘 설계와 분석에서 어떻게 만나는지 묶어 정리합니다.

> **핵심 인사이트:** 좋은 알고리즘 설계는 구현 요령보다, 어떤 수학 도구로 문제를 다시 쓸지 정하는 일에 더 가깝습니다. 부분집합이 2^n개라는 사실만 알아도 완전 탐색이 언제 불가능한지 구현 전에 알 수 있습니다.

## 이 글에서 다룰 문제

- 이 시리즈에서 본 수학이 알고리즘 설계에 어떻게 합쳐질까요?
- 조합론은 왜 복잡도 분석과 연결될까요?
- 그래프 모델은 문제 해결 방식 자체를 어떻게 바꿀까요?
- 무작위 알고리즘은 언제 결정론적 알고리즘보다 나을까요?
- AI가 만든 알고리즘 코드에서 수학적으로 확인해야 할 것은 무엇인가요?

## 알고리즘과 수학 핵심 패턴

```python
# 조합론: 경우의 수 폭발 — 구현 전에 가능성 판단
def subsets(n):
    return 2 ** n

print(subsets(20))  # 1,048,576 (약 100만) → 탐색 가능
print(subsets(50))  # 1,125,899,906,842,624 → 완전 탐색 불가

# 그래프: 문제를 최단 경로로 바꾸기
from collections import deque

def shortest_path(graph, start, end):
    """BFS로 최단 경로 탐색"""
    queue = deque([(start, [start])])
    visited = {start}
    while queue:
        node, path = queue.popleft()
        if node == end:
            return path
        for neighbor in graph.get(node, []):
            if neighbor not in visited:
                visited.add(neighbor)
                queue.append((neighbor, path + [neighbor]))
    return None
```

```python
# 확률: 무작위 알고리즘 (Monte Carlo pi 근사)
import random

def estimate_pi(n_samples=100000):
    inside = sum(
        1 for _ in range(n_samples)
        if random.random()**2 + random.random()**2 <= 1
    )
    return 4 * inside / n_samples

print(f"π ≈ {estimate_pi():.4f}")

# 정보이론: 압축의 이론적 한계
import math

def shannon_limit(probs):
    """허프만 코딩이 도달할 수 있는 최소 평균 비트 수"""
    return sum(-p * math.log2(p) for p in probs if p > 0)
```

## 변경 전후 비교

**Before: 수학 없이 알고리즘 선택**
```text
- O(n²) 알고리즘으로 n=100,000 데이터 처리 → 타임아웃
- 완전 탐색 코드를 구현 후 n이 크면 느린 이유 몰라서 당황
- 모든 문제를 배열로 표현 → 그래프로 바꾸면 간단한 문제를 복잡하게 풀음
- 랜덤 알고리즘의 정확도 보장 방법을 모름
```

**After: 수학적 사고로 알고리즘 설계**
```text
- 입력 크기 n과 O(n log n) vs O(n²) 차이로 성능 예측
- 2^n 복잡도면 n≤20 정도만 완전 탐색 가능 → 미리 판단
- 의존성/경로/연결 문제 → 그래프로 모델링 후 BFS/DFS
- 샘플 수 증가 → 오차 1/√n 감소 (중심극한정리)
```

## 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 방법 |
|------|-------------|-----------|
| 복잡도 분석 없이 구현 | n이 커지면 갑자기 타임아웃 | 구현 전 O(?) 분석 먼저 |
| 완전 탐색을 n=50에 시도 | 2^50 ≈ 10^15회 연산 불가 | 조합론으로 경우의 수 먼저 계산 |
| 배열로만 문제 표현 | 관계/경로 문제에 비효율적 | 그래프 모델로 재표현 |
| 무작위 알고리즘 결과 무조건 신뢰 | 샘플 수 부족 시 오차 큼 | 샘플 수와 신뢰도 관계 계산 |
| 정보이론 한계 무시 | 이론적으로 불가능한 압축 목표 설정 | 엔트로피가 최소 코드 길이 |

# - 무작위 알고리즘이면 오차 범위와 샘플 수가 있는가?

## 운영 체크리스트

- [ ] 구현 전 시간/공간 복잡도를 분석한다
- [ ] 완전 탐색 가능 여부를 경우의 수로 먼저 판단한다
- [ ] 관계/경로/연결 문제를 그래프로 모델링할 수 있다
- [ ] 무작위 알고리즘 사용 시 샘플 수와 오차 관계를 이해한다
- [ ] 압축/손실 함수의 이론적 한계(엔트로피)를 알고 있다

## 처음 질문으로 돌아가기

- **조합론이 복잡도 분석과 연결되는 이유는?** 경우의 수를 계산하면 완전 탐색의 비용을 알 수 있습니다. 2^n, n!, C(n,k)를 구현 전에 계산하면 현실적인 알고리즘을 선택할 수 있습니다.
- **그래프 모델이 문제 해결을 바꾸는 방법은?** 최단 경로, 스케줄링, 의존성 해결, 소셜 네트워크 분석은 그래프로 표현하면 BFS/DFS/위상 정렬로 바로 풀립니다. 배열로 풀면 복잡한 문제가 그래프로는 단순해집니다.
- **무작위 알고리즘이 유용한 경우는?** 결정론적 알고리즘으로 너무 느릴 때, 샘플링으로 근사 해를 빠르게 구할 수 있습니다. 샘플 수를 늘릴수록 오차가 1/√n 속도로 줄어듭니다(몬테 카를로).

## 정리

바이브코딩에서 AI가 만들어 준 알고리즘 코드에서 시간 복잡도, 그래프 모델 적합성, 무작위 알고리즘의 오차 보장을 반드시 확인하세요. 알고리즘은 구현 이전에 먼저 수학으로 모델링되고 분석됩니다. Math for CS 101 시리즈를 통해 논리, 조합론, 확률, 선형대수, 미분, 정보이론까지 알고리즘 설계의 수학 기초를 갖추셨기를 바랍니다.
