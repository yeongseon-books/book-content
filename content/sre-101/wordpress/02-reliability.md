# 바이브코딩을 위한 SRE 기초 (2/10): Reliability

이 글은 **바이브코딩을 위한 SRE 기초** 시리즈의 두 번째 글입니다. AI가 만든 서비스가 안정적으로 운영되려면 "신뢰성"이 무엇인지 명확하게 정의해야 합니다. 감으로 "요즘 잘 돌아가는 것 같다"고 판단하는 대신, 숫자로 측정하고 관리하는 방법을 소개합니다.

---

바이브코딩으로 서비스를 만들고 나서 "잘 돌아가나요?"라는 질문을 받으면 뭐라고 답하시나요?

"요즘 장애가 없었어요", "느리다는 피드백이 별로 없었어요", "체감상 괜찮은 것 같아요" — 이런 답변은 모두 사실일 수 있지만, 신뢰성을 정의하지는 못합니다. AI가 생성한 코드를 배포한 뒤 서비스가 살아는 있는데 응답이 10초씩 걸리거나, 결과값이 가끔 틀리거나, 저장한 데이터가 사라진다면 — 그 서비스는 신뢰할 수 있다고 할 수 없습니다.

바이브코딩으로 빠르게 출시한 서비스일수록 이 문제가 두드러집니다. 기능은 완성됐지만 신뢰성의 네 가지 차원 — 가용성, 지연 시간, 정확성, 내구성 — 중 어느 것 하나라도 제대로 측정하지 않으면 사용자는 언제 어디서 실패를 경험할지 알 수 없습니다. AI 도구가 만들어 준 서비스의 안정성을 보장하려면, 신뢰성을 감상이 아니라 수치로 관리해야 합니다.

> Reliability는 하나의 숫자가 아니라 여러 차원의 조합입니다. 각 차원은 서로 다른 실패 양상을 드러내며, 서비스 특성에 따라 어떤 차원을 우선할지가 달라집니다.

## 이 글에서 다룰 문제

- reliability를 막연한 안정감이 아니라 측정 가능한 값으로 보려면 무엇이 필요할까요?
- 가용성과 지연 시간은 왜 비슷해 보이지만 다른 문제일까요?
- 정확성과 내구성은 어떤 시스템에서 특히 더 중요해질까요?
- 바이브코딩으로 만든 서비스에서 신뢰성을 처음 측정할 때 어디서 시작해야 할까요?
- AI가 생성한 코드에서 신뢰성 문제가 자주 발생하는 이유는 무엇일까요?

## 신뢰성의 네 가지 차원

신뢰성을 한 숫자로 표현하려 하면 중요한 실패 양상을 놓치게 됩니다. 가용성 하나만 보면 서비스는 멀쩡해 보일 수 있습니다. 그런데 응답이 10초씩 걸리거나, 결과가 틀리거나, 저장한 데이터가 사라진다면 사용자는 이미 실패를 경험한 것입니다.

**가용성(Availability)**: 서비스가 정상 응답을 반환한 비율입니다. 99.9% 가용성은 월간 약 43분의 장애를 허용합니다.

```python
def availability(success_requests, total_requests):
    return success_requests / total_requests
```

**지연 시간(Latency)**: 요청을 처리하는 데 걸린 시간입니다. 평균값보다 p95, p99 같은 분위수가 실제 사용자 경험에 더 가깝습니다. 100명 중 1명이 3초 이상 기다린다면 그 서비스는 느린 것입니다.

**정확성(Correctness)**: 결과가 기대한 값과 맞는 정도입니다. 결제, 권한, 정산 시스템에서는 빠르게 틀리는 것이 느리게 맞는 것보다 훨씬 위험합니다.

**내구성(Durability)**: 저장한 데이터가 유지되는 정도입니다. 백업이 있다는 사실만으로 충분하지 않고, 실제로 복구 가능한지 검증해야 합니다.

## AI 생성 코드와 신뢰성

AI 코드 생성 도구는 기능 구현에 집중하는 경향이 있습니다. 에러 처리, 타임아웃 설정, 데이터 검증 같은 신뢰성 관련 코드는 프롬프트에 명시적으로 요청하지 않으면 빠지는 경우가 많습니다. 예를 들어 AI가 생성한 결제 API 코드에 금액 검증 로직이 없다면, 정확성 차원의 신뢰성 문제가 생깁니다.

신뢰성의 네 차원을 알고 있으면 AI에게 더 정확한 요청을 할 수 있습니다. "결제 API를 만들어줘" 대신 "결제 API를 만들어줘. 금액 정확성 검증, 타임아웃 처리, 중복 요청 방지 로직을 포함해서"라고 하면 훨씬 신뢰성 있는 코드를 얻을 수 있습니다.

## Before / After: 신뢰성 측정 전후

| 상황 | 측정 전 | 측정 후 |
| --- | --- | --- |
| 서비스 상태 파악 | "요즘 괜찮은 것 같아요" | "가용성 99.7%, p99 지연 800ms" |
| 장애 감지 | 사용자 신고 후 파악 | 모니터링 알림으로 즉시 감지 |
| 배포 판단 | 느낌으로 결정 | 에러 버짓 잔량 기준으로 결정 |
| 팀 간 소통 | 의견 충돌 ("충분히 안정적" vs "아직 위험") | 같은 숫자를 보고 대화 |
| 개선 우선순위 | 가장 눈에 띄는 불만부터 | 가장 큰 신뢰성 차원 약점부터 |

## 서비스 유형별 신뢰성 우선순위

| 서비스 유형 | 1순위 | 2순위 | 이유 |
| --- | --- | --- | --- |
| 결제/정산 | 정확성 | 내구성 | 금액이 틀리면 법적 문제, 데이터 손실은 복구 불가 |
| 실시간 검색 | 지연 시간 | 가용성 | 0.5초만 느려도 이탈률 급증 |
| 파일 스토리지 | 내구성 | 가용성 | 데이터를 잃으면 복구 불가 |
| 소셜 피드 | 가용성 | 지연 시간 | 접속 자체가 안 되면 이탈 |

## 바이브코딩에서 자주 하는 실수

| 실수 | 왜 문제인가 | 개선 방법 |
| --- | --- | --- |
| 가용성만 측정 | 느리거나 틀린 결과를 놓침 | 4가지 차원을 모두 정의하고 측정 |
| 평균 지연 시간만 봄 | 일부 사용자의 느린 경험을 숨김 | p95, p99 분위수를 함께 확인 |
| 백업 있으면 안전하다고 가정 | 복구 테스트를 안 해서 막상 복구가 안 됨 | 정기적인 복구 테스트 자동화 |
| 모든 API에 동일한 기준 | 중요도 다른 서비스를 같은 비용으로 관리 | 핵심 경로와 부수 경로 차등 적용 |

## AI 팁: 신뢰성 관련 코드 요청하기

AI 도구에 신뢰성을 고려한 코드를 요청하는 방법입니다.

**지연 시간 측정 추가 요청**: "이 API에 p95, p99 지연 시간을 측정하는 Prometheus 메트릭을 추가해줘"

**정확성 검증 추가 요청**: "결제 처리 함수에 금액 소수점 처리와 중복 방지를 위한 idempotency key 검증을 추가해줘"

**내구성 확인 요청**: "이 저장 로직에 write 후 read-back 검증을 추가해줘. 저장 실패 시 알림을 보내는 코드도 포함해서"

## 운영 체크리스트

- [ ] 가용성, 지연 시간, 정확성, 내구성을 분리해서 정의했다.
- [ ] 평균 외에 p95 또는 p99를 함께 보고 있다.
- [ ] 정확성이 중요한 경로에는 자동 검증 수단이 있다.
- [ ] 데이터 손실 허용 범위와 복구 기대치를 문서화했다.
- [ ] 서비스 성격에 따라 어떤 차원을 더 우선하는지 정했다.

## 처음 질문으로 돌아가기

- **reliability를 막연한 안정감이 아니라 측정 가능한 값으로 보려면 무엇이 필요할까요?**
  - 가용성(성공 요청 비율), 지연 시간(p95/p99), 정확성(기대값 일치율), 내구성(데이터 보존율) 네 가지 차원을 각각 정의하고 수치로 측정해야 합니다. 어느 한 차원만 봐서는 신뢰성 전체를 설명할 수 없습니다.
- **AI가 생성한 코드에서 신뢰성 문제가 자주 발생하는 이유는 무엇일까요?**
  - AI 도구는 기능 요구사항에 집중하고, 에러 처리·타임아웃·데이터 검증 같은 운영 요구사항은 명시적으로 요청해야 포함됩니다. 신뢰성의 네 차원을 이해하면 AI에게 더 완전한 코드를 요청할 수 있습니다.
- **바이브코딩으로 만든 서비스에서 신뢰성을 처음 측정할 때 어디서 시작해야 할까요?**
  - 핵심 사용자 경로(예: 로그인 API)의 HTTP 성공률과 p95 지연 시간부터 시작하세요. 이 두 숫자가 보이면 목표를 세울 수 있고, 개선 방향도 명확해집니다.

## 정리

Reliability는 막연한 안정감이 아니라 가용성, 지연 시간, 정확성, 내구성이라는 네 차원의 수치로 표현되는 품질입니다. 바이브코딩으로 만든 서비스도 이 네 차원을 측정하고 관리해야 진정한 신뢰성을 확보할 수 있습니다.

다음 글에서는 SLI, SLO, SLA를 구분합니다. 무엇을 측정하고, 무엇을 목표로 삼고, 무엇을 외부 약속으로 문서화해야 하는지 정리합니다.
