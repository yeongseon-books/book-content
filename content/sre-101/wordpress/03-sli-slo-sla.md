# 바이브코딩을 위한 SRE 기초 (3/10): SLI, SLO, SLA

이 글은 **바이브코딩을 위한 SRE 기초** 시리즈의 세 번째 글입니다. AI가 만든 서비스의 신뢰성을 관리하려면 무엇을 측정하고(SLI), 어떤 목표를 세우고(SLO), 사용자에게 무엇을 약속할지(SLA) 명확히 구분해야 합니다. 세 개념이 섞이면 운영도 고객 소통도 흔들립니다.

---

바이브코딩으로 서비스를 만들고 나서 "얼마나 안정적인가요?"라는 질문을 받으면 어떻게 답하시나요?

"99.9%를 보장합니다"라고 말했다고 가정해 봅시다. 이 문장에는 빈칸이 네 개 있습니다. 무엇을 99.9%로 측정하는지, 어떤 기간 동안 재는지, 내부 운영 목표인지 외부 고객 약속인지, 그리고 지키지 못했을 때 어떻게 되는지가 빠져 있습니다. AI가 만든 서비스를 운영하는 팀이 이 빈칸을 채우지 않으면, 같은 숫자를 보고도 팀마다 다른 판단을 내리게 됩니다.

SLI, SLO, SLA는 이 빈칸을 채우는 역할을 나눕니다. 세 약어가 비슷해 보여서 실무에서 자주 섞여 쓰이지만, 혼동하는 순간 목표와 약속의 경계가 무너집니다. 바이브코딩으로 빠르게 서비스를 출시할수록 이 구분이 더 중요해집니다. 측정 없이 배포를 반복하다 보면 어느 순간 사용자의 신뢰를 잃게 됩니다.

> SLI는 무엇을 재는지, SLO는 어디까지를 목표로 삼는지, SLA는 그중 무엇을 외부에 약속하는지 정리한 층위입니다.

## 이 글에서 다룰 문제

- SLI, SLO, SLA는 각각 어떤 역할을 맡고 어디서 경계가 갈릴까요?
- 내부 목표와 외부 약속은 왜 같은 문서가 아니어야 할까요?
- 좋은 SLO에는 목표 수치 외에 어떤 정보가 반드시 들어가야 할까요?
- 바이브코딩 서비스에서 첫 SLO를 만들 때 어디서 시작해야 할까요?
- AI가 만든 서비스에서 SLI를 선택하는 기준은 무엇일까요?

## SLI, SLO, SLA 역할 비교

세 개념을 층위로 나눠서 생각하면 명확해집니다.

**SLI(Service Level Indicator)**: 서비스 수준을 측정하는 지표 자체입니다. "무엇을 어떻게 재는가"에 해당합니다. 좋은 SLI는 사용자 경험과 직결되어야 합니다.

```python
sli = {
    "name": "http_success_ratio",
    "formula": "http_2xx / http_total",
    "source": "ingress logs",
}
```

**SLO(Service Level Objective)**: 내부 운영 목표입니다. SLI에 목표 수치, 측정 기간, 오너를 붙인 것입니다. SLO가 있어야 에러 버짓을 계산하고, 배포 결정을 내릴 수 있습니다.

```python
slo = {
    "sli": "http_success_ratio",
    "target": 0.999,
    "window_days": 30,
    "owner": "payments-team",
}
```

**SLA(Service Level Agreement)**: 외부 고객과의 약속입니다. SLO보다 낮은 목표를 설정하고, 위반 시 보상과 예외 조항을 포함합니다. SLA는 법적 구속력이 있으므로 법무팀과 함께 만들어야 합니다.

| 항목 | SLI | SLO | SLA |
| --- | --- | --- | --- |
| 정의 | 서비스 수준 측정 지표 | 내부 운영 목표 | 외부 고객과의 약속 |
| 소유자 | 플랫폼/운영팀 | 제품/SRE팀 | 법무/영업팀 |
| 예시 | `http_2xx / http_total` | 30일간 99.9% 가용성 | 99.5% 위반 시 10% 크레딧 |
| 위반 시 결과 | 대시보드 주황색 | 배포 freeze, 리뷰 강화 | 보상 지급, 계약 해지 위험 |

## 바이브코딩 서비스의 첫 SLO 만들기

바이브코딩으로 만든 서비스에 첫 SLO를 도입할 때는 단순하게 시작하는 것이 좋습니다. 처음부터 모든 경로에 SLO를 만들려 하면 문서만 쌓이고 실제 운영에는 쓰이지 않습니다.

**1단계**: 핵심 사용자 경로 하나를 선택합니다 (예: 로그인 API).

**2단계**: 현재 가용성을 1주일 이상 측정합니다. 현실을 모르는 상태에서 만든 목표는 곧 무의미해집니다.

**3단계**: 현재 수치보다 약간 높은 목표를 보수적으로 설정합니다. 99.99%처럼 야심찬 목표보다 현재 99.5%라면 99.7%에서 시작합니다.

**4단계**: 에러 버짓 소진 시 어떤 행동을 할지 미리 정합니다. 버짓 50% 소진 시 배포 리뷰 강화, 80% 소진 시 배포 동결 같은 정책이 있어야 SLO가 실제로 쓰입니다.

## Before / After: SLO 도입 전후

| 상황 | SLO 도입 전 | SLO 도입 후 |
| --- | --- | --- |
| 배포 결정 | "지금 배포해도 될까요?" 논쟁 | 에러 버짓 잔량 기준으로 자동 판단 |
| 팀 간 소통 | "충분히 안정적"이라는 의견 충돌 | 같은 SLO 숫자를 보고 대화 |
| 장애 대응 우선순위 | 가장 시끄러운 불만부터 | 에러 버짓 소진 속도 기준으로 우선 |
| 신뢰성 보고 | "요즘 잘 돌아갑니다" | "이번 달 가용성 99.87%, 버짓 30% 소진" |
| 야심찬 목표의 함정 | 99.99%를 목표로 세우고 달성 못 함 | 현실적인 목표에서 시작해 점진적 개선 |

## 바이브코딩에서 자주 하는 실수

| 실수 | 왜 문제인가 | 개선 방법 |
| --- | --- | --- |
| SLO를 만들고 리뷰 안 함 | 문서만 존재하고 운영에 반영 안 됨 | 주간 SLO 리뷰 미팅 필수화 |
| SLA 수치를 SLO와 동일하게 설정 | 내부 목표 미달 시 바로 보상 발생 | SLA < SLO로 버퍼 확보 |
| 측정 기간 미명시 | 같은 수치도 해석이 달라짐 | 30일 rolling window 명시 |
| 모든 API에 동일한 SLO | 중요도 다른 서비스를 같은 기준으로 관리 | 핵심 경로와 부수 경로 차등 적용 |
| SLI 데이터 소스 누락 | 숫자 재현 불가, 팀 간 논쟁 | 쿼리문과 데이터 소스를 함께 기록 |

## AI 팁: SLO 관련 코드 요청하기

AI 도구로 SLO 관련 코드를 만들 때 활용할 수 있는 요청 방법입니다.

**SLI 측정 코드**: "HTTP 요청의 성공률을 측정하는 Prometheus Counter 메트릭을 추가해줘. 4xx 클라이언트 에러는 제외하고 5xx 서버 에러만 실패로 계산해줘"

**에러 버짓 계산기**: "월간 요청 수와 SLO 목표를 입력받아 허용 에러 수, 현재 소진 비율, 남은 버짓을 출력하는 Python 함수를 만들어줘"

**SLO 위반 알림**: "에러율이 SLO 목표의 14.4배 속도로 소진될 때 Slack 알림을 보내는 PromQL 알림 규칙을 만들어줘"

## 운영 체크리스트

- [ ] SLI의 이름, 공식, 데이터 출처를 문서화했다.
- [ ] SLO에 목표 수치, 측정 기간, 오너를 적었다.
- [ ] SLA에 보상과 예외 조항을 명시했다.
- [ ] 위반 여부를 자동 판정할 수 있다.
- [ ] 내부 목표(SLO)와 외부 약속(SLA)을 혼동하지 않는다.

## 처음 질문으로 돌아가기

- **SLI, SLO, SLA는 각각 어떤 역할을 맡고 어디서 경계가 갈릴까요?**
  - SLI는 측정 도구(무엇을 어떻게 재는가), SLO는 내부 운영 기준(어디까지를 목표로 삼는가), SLA는 외부 약속(고객에게 무엇을 보장하는가)입니다. SLO를 SLA처럼 말하면 법적 분쟁이 생길 수 있고, SLA를 SLO처럼 느슨하게 관리하면 보상 의무가 발생합니다.
- **바이브코딩 서비스에서 첫 SLO를 만들 때 어디서 시작해야 할까요?**
  - 핵심 사용자 경로 하나의 HTTP 성공률을 1주일 측정한 뒤, 현재 수치보다 조금 높은 목표를 설정합니다. 완벽한 SLO보다 실제로 보는 SLO가 훨씬 중요합니다.
- **좋은 SLO에는 목표 수치 외에 어떤 정보가 반드시 들어가야 할까요?**
  - 목표 수치 + 측정 기간(예: 30일 rolling) + 오너(책임자) + 위반 시 행동(배포 동결, 포스트모템 등)이 모두 있어야 SLO가 실제 운영 도구로 동작합니다.

## 정리

SLI, SLO, SLA는 비슷한 약어가 아니라 서로 다른 책임층입니다. SLI는 측정, SLO는 내부 목표, SLA는 외부 약속입니다. 바이브코딩으로 만든 서비스도 이 구분이 선명해야 신뢰성 숫자가 운영 판단과 고객 기대를 함께 지탱할 수 있습니다.

다음 글에서는 에러 버짓을 다룹니다. SLO를 세운 뒤 어느 정도 실패를 허용하고, 그 범위 안에서 배포 속도를 조절하는 방법을 소개합니다.
