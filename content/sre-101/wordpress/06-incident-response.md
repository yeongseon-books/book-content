# 바이브코딩을 위한 SRE 기초 (6/10): 장애 대응

이 글은 "바이브코딩을 위한 SRE 기초" 시리즈의 6번째 글입니다.

---

바이브코딩에서 AI는 모니터링 코드와 경보 설정을 빠르게 만들어 줍니다. 그런데 실제 장애가 났을 때 경보가 울리는 것과 팀이 빠르게 대응하는 것은 다른 이야기입니다. 장애가 시작되는 순간 기술 문제만 커지는 것이 아닙니다. 누가 먼저 판단할지, 누가 복구를 맡을지, 누가 고객과 내부 조직에 상태를 알릴지 정해져 있지 않으면 같은 수준의 장애도 훨씬 크게 번집니다.

장애 대응은 모두가 동시에 뛰어드는 일이 아닙니다. 역할이 분리된 팀이 정해진 순서로 움직이는 작업입니다. AI가 만든 경보 시스템이 있어도, 누가 Incident Commander를 맡고, 어느 채널에서 소통하고, 언제 장애를 닫을지 정해져 있지 않으면 대응 시간이 길어집니다.

강한 팀은 장애가 없을 때 절차를 준비합니다. 심각도 분류, 역할 정의, 정기 업데이트, 종료 기준을 미리 정해 두면 실제 장애가 났을 때 훨씬 빠르게 회복합니다.

> **핵심 인사이트:** 장애 대응은 기술 실력만으로 풀리는 문제가 아닙니다. 심각도를 영향 기준으로 정의하고, Incident Commander가 조율하고, 15분마다 상태를 업데이트하고, 종료 조건을 명확히 할 때 장애 대응 시간이 짧아집니다. 절차가 없으면 뛰어난 엔지니어도 혼란 속에서 힘을 제대로 쓰기 어렵습니다.

## 이 글에서 다룰 문제

- 심각도는 왜 느낌이 아니라 영향 기준으로 정의해야 할까요?
- Incident Commander는 무엇을 직접 하고 무엇을 하지 말아야 할까요?
- 장애 중 정기 업데이트가 왜 중요할까요?
- 타임라인은 왜 장애 중에 기록해야 할까요?
- AI가 만든 경보 시스템에서 장애 대응 관점으로 확인할 것은 무엇인가요?

## 장애 대응 핵심 패턴

```python
# 심각도 판단: 영향 기준으로 자동화
def severity(impact_users, duration_min):
    if impact_users > 10000 or duration_min > 60:
        return "SEV1"  # 즉시 전체 온콜 + 경영진
    if impact_users > 1000:
        return "SEV2"  # 15분 이내 관련 팀 온콜
    return "SEV3"      # 1시간 이내 담당 팀

# IC 지정: 온콜 담당자 첫 번째
def assign_ic(on_call):
    return on_call[0]

# 전용 채널 생성
def channel(name):
    return f"#inc-{name}"

# 정기 업데이트: 원인 몰라도 15분마다
def update(channel, msg, every_min=15):
    return {"channel": channel, "msg": msg, "every": every_min}

# 종료 조건: 복구 + 고객 영향 해소 둘 다 확인
def can_close(mitigated, customer_impact_zero):
    return mitigated and customer_impact_zero
```

```yaml
  update_interval: 30분마다

  update_interval: 필요 시
```

## 변경 전후 비교

**Before: 절차 없는 장애 대응**
```text
- 장애 발생 → 모두가 동시에 대화방에서 논의
- 누가 결정하는지 불분명, 의견 충돌
- 고객 공지를 기술 복구 후로 계속 미룸
- 대시보드가 잠깐 안정되자마자 종료 선언
- 포스트모템 없이 마무리
```

**After: 역할 분리된 장애 대응**
```text
- IC가 조율, ops lead가 복구, comms lead가 공지
- 전용 채널에서 타임라인 실시간 기록
- 원인 몰라도 15분마다 상태 업데이트
- 복구 + 고객 영향 해소 모두 확인 후 종료
- 타임라인이 포스트모템 초안이 됨
```

## 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 방법 |
|------|-------------|-----------|
| IC가 직접 디버깅 | 조율 공백 발생, 대응 혼란 | IC는 조율만, 복구는 ops lead에게 |
| 원인 파악 전 공지 없음 | 고객 불신, 문의 폭주 | 영향 범위와 다음 업데이트 시각만 알려도 됨 |
| 종료를 너무 빨리 선언 | 임시 완화를 완전 복구로 착각 | 고객 영향 실제 해소까지 확인 |
| 타임라인 장애 후에 기록 | 기억에 의존, 디테일 손실 | 장애 중 Slack 채널에 실시간 기록 |
| 심각도를 감으로 결정 | 과대/과소 대응 반복 | 영향 사용자 수, 지속 시간 기준으로 정의 |

## 운영 체크리스트

- [ ] 심각도 기준이 숫자와 영향으로 문서화되어 있다
- [ ] IC, ops lead, comms lead 역할이 정의되어 있다
- [ ] 장애별 전용 Slack 채널과 정기 업데이트 규칙이 있다
- [ ] 종료 조건이 명확히 정의되어 있다
- [ ] 타임라인이 포스트모템으로 자동으로 이어지는 구조가 있다

## 처음 질문으로 돌아가기

- **심각도를 숫자로 정의해야 하는 이유는?** 주관적 심각도는 사람마다 다르게 해석됩니다. 영향 사용자 수, 지속 시간, 핵심 기능 마비 여부를 기준으로 정의하면 누가 봐도 비슷한 판단을 내릴 수 있습니다. 그래야 온콜 호출 범위와 공지 수준도 일관됩니다.
- **IC가 직접 디버깅하면 왜 안 되는가?** IC가 복구 작업에 뛰어들면 조율 공백이 생깁니다. 누가 다음 결정을 내리는지 불분명해지고, 대응 시간이 늘어납니다. IC는 전문가들이 복구에 집중할 수 있게 조율하는 역할입니다.
- **원인을 모를 때 고객 공지를 미뤄도 되는가?** 원인을 몰라도 공지해야 합니다. 현재 영향 범위, 대응 중임을 알리고, 다음 업데이트 시각만 명시해도 신뢰를 지킬 수 있습니다. 침묵이 상황을 더 나쁘게 만듭니다.

## 정리

바이브코딩에서 AI가 만든 경보 시스템에 장애 대응 절차가 없다면, 경보는 울려도 대응이 혼란스러울 수 있습니다. 심각도 기준, IC 역할, 정기 업데이트, 종료 조건을 미리 정해 두세요. 강한 팀은 장애가 없을 때 절차를 준비합니다. 다음 글에서는 포스트모템을 다룹니다.
