# Computer Science Major 101 (4/10): 시스템 과목 이해하기

코드를 오래 쓰다 보면 결국 같은 질문으로 돌아옵니다. 이 한 줄이 왜 이렇게 동작하는지, 왜 느린지, 왜 같은 코드인데 환경에 따라 다르게 보이는지 궁금해지는 순간이 옵니다.

이 글은 컴퓨터학과 전공 학습 가이드 101 시리즈의 4번째 글입니다.

![Computer Science Major 101 4장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/computer-science-major-101/04/04-01-systems-stack-map.ko.png)
*컴퓨터학과 전공 가이드 4장 흐름 개요*

> 코드는 운영체제와 하드웨어라는 무대 위에서만 실행되므로, 시스템 과목은 그 무대를 읽는 법을 가르칩니다.

## 이 글에서 다룰 문제

- 시스템 과목은 코드 한 줄이 실제로 어떻게 동작하는지 어디까지 설명해 줄까요?
- 운영체제, 컴퓨터 구조, 컴파일러는 왜 함께 배워야 할까요?
- 프로세스, 메모리, 파일, 시간 같은 개념이 디버깅과 성능 분석에 왜 중요할까요?
- 시스템 지식이 없으면 실무에서 어떤 상황에서 막히게 될까요?
- 시스템 과목을 추상적 암기 대신 실험으로 배우는 방법은 무엇일까요?

## 왜 시스템 과목이 필요한가

성능 문제와 장애 원인 분석은 거의 항상 시스템 지식 위에서 이루어집니다. CPU, 메모리, I/O, 프로세스, 시스템 호출을 모르면 코드 바깥에서 벌어지는 비용을 읽기가 어렵습니다.

코드는 진공 속에서 실행되지 않습니다. 하드웨어 위에 구조가 있고, 운영체제가 자원을 배분하고, 컴파일러가 코드를 번역한 뒤에야 프로그램이 실제로 돌아갑니다. 시스템 과목은 이 무대를 읽는 훈련입니다.

- **운영체제(OS)**: 자원을 관리하는 소프트웨어입니다. 프로세스 스케줄링, 메모리 가상화, 파일 시스템, I/O 관리를 담당합니다.
- **프로세스(process)**: 실행 중인 프로그램 단위입니다. 독립된 메모리 공간을 가집니다.
- **스레드(thread)**: 프로세스 내 더 가벼운 실행 단위입니다. 메모리를 공유합니다.
- **레지스터(register)**: 가장 빠른 메모리 영역입니다. CPU 연산의 직접 대상입니다.
- **컴파일러(compiler)**: 소스 코드를 기계어로 번역하는 도구입니다. 최적화를 통해 실행 형태를 바꿉니다.

## 왜 여기서 막히는가: 흔한 시나리오

**시나리오 1 — "서버가 느린데 이유를 모르겠다"**

준혁은 백엔드 프로젝트를 배포했는데 응답이 간헐적으로 느려졌습니다. 로그를 보니 특정 API가 가끔 3초 이상 걸렸습니다. 코드를 보면 틀린 곳이 없는 것 같았습니다. 동료가 "CPU bound인지 I/O bound인지 먼저 봐야 한다"고 했는데 그 말 자체를 이해하지 못했습니다. 운영체제 과목에서 프로세스 스케줄링을 배웠지만 실제 디버깅과 연결하지 못했기 때문입니다.

발생 신호: 성능 문제가 생겼을 때 어디를 봐야 하는지 모르고 코드만 반복적으로 살펴봅니다. `top`이나 `htop`을 열었지만 숫자를 해석하지 못합니다.

해결 방향: CPU 사용률, 메모리 RSS, iowait, 시스템 콜 빈도를 보는 순서를 먼저 배워야 합니다. `top`, `ps`, `strace` 같은 도구는 시스템 과목 개념의 실전 인터페이스입니다. CPU 사용률이 높으면 CPU-bound, iowait이 높으면 I/O-bound입니다.

**시나리오 2 — "멀티스레드를 썼더니 결과가 가끔 틀린다"**

서영은 성능 향상을 위해 스레드를 여러 개 써서 계산을 병렬화했습니다. 그런데 결과가 매번 달라졌습니다. 락(lock)이 없어서 레이스 컨디션(race condition)이 발생한 것인데, 스레드와 메모리 공유 개념이 없었기 때문에 원인을 찾는 데 오래 걸렸습니다. 특히 재현이 안 되는 버그라 더 혼란스러웠습니다.

발생 신호: 단독 실행에서는 정상이지만 병렬 실행에서 간헐적 오류가 납니다. 실행할 때마다 다른 결과가 나옵니다.

해결 방향: 스레드가 공유 메모리에 접근할 때 동기화가 필요하다는 운영체제 개념이 필요합니다. 락, 뮤텍스, 세마포어의 차이를 이해해야 합니다. Python의 GIL, Java의 synchronized 키워드가 모두 이 개념에서 나옵니다.

**시나리오 3 — "메모리 오류 메시지를 읽지 못한다"**

재훈은 C 언어 과제에서 `segmentation fault`가 났습니다. 어디서 난 건지도 모르고, 오류 메시지도 어떻게 읽어야 할지 몰랐습니다. 컴퓨터구조에서 메모리 주소와 포인터를 배웠지만 연결이 안 된 상태였습니다. 스택과 힙이 왜 분리되어 있는지, 포인터가 무엇을 가리키는지 이해가 없었기 때문에 오류 메시지가 아무 의미 없이 보였습니다.

발생 신호: 오류 메시지가 생소하고 어디서부터 디버깅해야 할지 모릅니다. `gdb`를 열어도 backtrace를 읽지 못합니다.

해결 방향: 스택과 힙의 차이, 포인터가 메모리 주소라는 개념, 버퍼 오버플로우가 무엇인지 이해하면 `segfault`가 훨씬 읽기 쉬워집니다. `valgrind`로 메모리 오류를 시각화하는 연습이 도움이 됩니다.

## OS 개념과 실무 디버깅 신호 매핑표

| OS 핵심 개념 | 수업에서 배우는 내용 | 실무에서 보이는 신호 | 점검 명령/지표 |
| --- | --- | --- | --- |
| 프로세스/스레드 | 스케줄링, 실행 단위 | CPU 급등, 응답 지연 | `top`, `ps`, 런큐 길이 |
| 메모리 가상화 | 페이지, 캐시, 스왑 | OOM, GC 지연, 페이지 폴트 | RSS, page fault rate |
| 파일 시스템 | inode, 버퍼 캐시 | 디스크 I/O 병목 | iowait, latency |
| 시스템 콜 | user/kernel 경계 | syscall 폭증, context switch 증가 | `strace`, `perf` |
| 동기화 | 락, 세마포어 | 데드락, 처리량 저하 | lock wait time |
| 가상 메모리 | 주소 공간, 페이지 테이블 | TLB miss, 스왑 과다 | vmstat, sar |

이 표를 기준으로 보면 "느리다"라는 증상을 더 구체화할 수 있습니다. CPU-bound인지 I/O-bound인지 먼저 구분하면 해결 방향이 완전히 달라집니다.

## 시스템 감각 만들기: 코드 예시

```python
import os
import sys
import time

# 1단계 — 프로세스 ID: 프로그램이 OS 자원으로 다뤄진다는 감각
print(os.getpid())

# 2단계 — 환경 변수: 프로세스 단위의 실행 컨텍스트
print(os.environ.get("PATH", ""))

# 3단계 — 파일 디스크립터: OS가 관리하는 자원 번호
with open("/etc/hostname") as f:
    print(f.fileno())

# 4단계 — 시간 측정: 성능은 느낌이 아니라 수치
t = time.perf_counter()
sum(range(10_000_000))
elapsed = time.perf_counter() - t
print(f"elapsed: {elapsed:.4f}s")

# 5단계 — 메모리 감각: 같은 코드도 메모리 비용이 다르다
print(sys.getsizeof([0] * 1000))    # 8056 bytes
print(sys.getsizeof(range(1000)))   # 48 bytes

# 6단계 — 프로세스 생성: fork는 새 메모리 공간 복사
pid = os.fork()
if pid == 0:
    print(f"자식 프로세스: {os.getpid()}")
    os._exit(0)
else:
    print(f"부모 프로세스: {os.getpid()}, 자식: {pid}")
    os.wait()
```

이 코드에서 주목할 점:
- 프로세스에는 고유 ID가 있습니다. 프로그램이 추상적 코드가 아니라 시스템 자원이라는 감각이 생깁니다.
- 환경 변수는 프로세스 단위입니다. 로컬에서는 되는데 서버에서 안 되는 문제의 상당수가 이 차이입니다.
- 파일도 OS가 관리하는 자원입니다. 디스크립터 한도가 있으며, 고갈되면 파일 열기 실패가 납니다.
- `range(1000)`이 `[0]*1000`보다 메모리가 훨씬 적은 이유는 게으른 평가(lazy evaluation) 때문입니다.

## 컴파일러와 실행의 연결

컴파일러는 단순한 번역 도구가 아닙니다. 코드 최적화를 통해 실제 실행 경로를 바꾸고, 경우에 따라 작성한 코드와 다른 순서로 명령이 실행될 수도 있습니다.

**컴파일 단계 이해**:
1. 전처리(Preprocessing): `#include`, `#define` 처리
2. 컴파일(Compilation): 소스 코드 → 어셈블리
3. 어셈블(Assembly): 어셈블리 → 오브젝트 파일
4. 링킹(Linking): 오브젝트 파일 → 실행 파일

**최적화가 중요한 이유**: 컴파일러는 `-O2` 플래그 하나로 루프 언롤링, 인라인 치환, 불필요한 분기 제거를 수행합니다. 같은 코드도 최적화 수준에 따라 10배 이상 성능 차이가 날 수 있습니다.

**인터프리터와 컴파일러 차이**: Python은 기본적으로 인터프리터 방식입니다. 컴파일된 C보다 느린 이유 중 하나는 실행 시점마다 번역이 일어나기 때문입니다. JIT 컴파일러(PyPy, JVM)는 이 차이를 줄이기 위해 런타임 컴파일을 씁니다.

## 메모리 계층 구조

시스템 과목에서 빠지지 않는 주제가 메모리 계층입니다. 속도와 비용이 서로 반비례하는 이 구조가 캐시 설계와 성능 최적화의 근거입니다.

| 메모리 계층 | 접근 시간 | 크기 | 역할 |
| --- | --- | --- | --- |
| CPU 레지스터 | 0.1ns | 수십 바이트 | 현재 연산 대상 |
| L1 캐시 | 1ns | 수십 KB | 가장 최근 사용 데이터 |
| L2 캐시 | 5ns | 수백 KB | L1 미스 시 탐색 |
| L3 캐시(LLC) | 20ns | 수십 MB | 멀티코어 공유 캐시 |
| DRAM(주 메모리) | 80ns | 수 GB | 실행 중 프로그램 전체 |
| SSD | 100μs | 수백 GB | 영속 저장, 빠른 I/O |
| HDD | 10ms | 수 TB | 대용량 영속 저장 |

캐시 친화적 코드(cache-friendly code)를 쓰면 동일 알고리즘에서 수 배 성능이 오릅니다. 행렬 순회 순서 하나만 바꿔도 L1 캐시 히트율이 극적으로 달라집니다.

## 이 과목이 실무에서 어떻게 쓰이는가

장애 보고서를 읽다 보면 근본 원인이 애플리케이션 코드보다 OS 자원 한계로 이어지는 경우가 많습니다.

**사례 1 — 파일 디스크립터 고갈**: 소켓 연결을 닫지 않은 코드가 누적되어 `ulimit`을 초과했습니다. 새 연결을 열지 못하는 오류가 났는데, OS의 자원 한계 개념이 없으면 원인을 찾는 데 오래 걸립니다.

**사례 2 — 컨텍스트 스위치 폭증**: 스레드를 너무 많이 생성해서 스케줄링 오버헤드가 실제 연산보다 커졌습니다. `perf stat`으로 컨텍스트 스위치 횟수를 보면 바로 드러납니다.

**사례 3 — 메모리 누수**: 힙에 할당한 메모리를 반환하지 않아 RSS가 계속 늘었습니다. 가비지 컬렉션이 있는 언어에서도 참조가 남아 있으면 GC가 수거하지 못합니다.

**사례 4 — 스왑 폭증으로 인한 지연**: 메모리가 부족해 OS가 스왑 영역을 쓰기 시작하면 응답 시간이 수십 배 늘어납니다. `vmstat`의 `si/so`(swap in/out) 항목이 높으면 바로 확인해야 합니다.

## 시스템 관점 디버깅 체크리스트

시스템 문제가 의심될 때는 코드 수정 전에 관찰 순서를 고정해야 합니다.

1. 증상 재현 조건 확인: 언제, 어떤 부하에서, 얼마나 자주 발생하는가
2. CPU/메모리/I/O 중 병목 축 분류: `top`, `vmstat`, `iostat` 활용
3. 로그 타임라인 정렬: 오류 발생 직전 이벤트 시퀀스 추적
4. 시스템 콜/네트워크 경계 확인: `strace`, `tcpdump` 활용
5. 변경 전후 측정 비교: 수정 전 지표를 반드시 기록 후 변경

이 순서를 지키면 감각적 추측을 줄이고 원인을 빠르게 좁힐 수 있습니다.

## 시스템 학습 로드맵(학부 기준)

1. 프로세스/스레드/메모리 기본 개념을 그림으로 설명할 수 있게 만듭니다.
2. 간단한 서버를 실행하고 요청 처리 경로를 추적해 봅니다.
3. I/O 병목 예제를 만들어 측정 도구 사용법을 익힙니다.
4. 컴파일/링크 과정과 바이너리 실행 흐름을 연결해 봅니다.
5. 프로젝트에서 한 번 이상 성능 이슈를 재현하고 개선 기록을 남깁니다.

여기까지 오면 시스템 과목이 추상적 암기 과목이 아니라 "문제를 좁히는 기술"로 바뀝니다.

## 시스템 관점 측정 실습

측정 없이 최적화하면 감으로 하는 일이 됩니다. 아래 코드는 연산 방식이 다를 때 실제 시간 차이를 직접 확인하는 가장 간단한 실험입니다.

```python
import time
import os
import resource

def measure(label: str, fn):
    """함수 실행 시간과 메모리를 측정합니다."""
    rss_before = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
    t = time.perf_counter()
    result = fn()
    elapsed = time.perf_counter() - t
    rss_after = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
    print(f"{label}: {elapsed*1000:.2f}ms, rss_delta={rss_after - rss_before}KB")
    return result

# 캐시 친화적 탐색 vs 비친화적 탐색
n = 1000

# 행우선 순회 (cache-friendly)
matrix = [[i * n + j for j in range(n)] for i in range(n)]
measure("row-major",   lambda: sum(matrix[i][j] for i in range(n) for j in range(n)))

# 열우선 순회 (cache-unfriendly)
measure("col-major",   lambda: sum(matrix[j][i] for i in range(n) for j in range(n)))

# 리스트 컴프리헨션 vs 제너레이터
measure("list-comp",   lambda: sum([x*x for x in range(1_000_000)]))
measure("generator",   lambda: sum(x*x for x in range(1_000_000)))
```

이 실험의 결과를 직접 기록해 두면 "캐시 친화적 코드"와 "메모리 효율"이 추상적인 개념이 아닌 측정 가능한 수치로 바뀝니다.

## 시스템 과목을 팀 프로젝트에 연결하기

시스템 과목은 시험 과목으로 끝내면 효용이 급격히 줄어듭니다. 운영 로그와 측정 결과를 읽는 연습으로 연결해야 실제 역량이 됩니다.

| 관찰 신호 | 가능한 원인 | 확인 지표 | 다음 행동 |
| --- | --- | --- | --- |
| 응답 지연 급증 | CPU 경합, I/O 대기 | CPU 사용률, iowait | 병목 구간 분해 후 실험 재현 |
| 메모리 증가 | 누수, 캐시 과다 | RSS, GC 지표 | 객체 생명주기 점검 |
| 간헐적 타임아웃 | 락 경합, 네트워크 지연 | p95/p99, lock wait | 재시도 정책과 임계 구간 분리 |
| 프로세스 죽음 | OOM, 세그폴트 | dmesg, core dump | 메모리 한도와 포인터 접근 점검 |
| 처리량 갑자기 저하 | GC 멈춤, 스케줄러 경합 | GC 로그, run queue | GC 튜닝 또는 스레드 수 조정 |

학기 프로젝트에서 위 표를 장애 회고 템플릿으로 사용하면 시스템 과목 지식이 문서화 자산으로 전환됩니다.

## 시스템 과목 연계 도구 맵

시스템 지식을 실습으로 전환할 때 어떤 도구를 쓰면 좋을지 정리합니다.

| 개념 | Linux 도구 | Python 도구 | 학습 포인트 |
| --- | --- | --- | --- |
| 프로세스 상태 | `ps`, `top`, `htop` | `os.getpid()`, `psutil` | 프로세스 생명주기 |
| 메모리 사용 | `free`, `vmstat`, `/proc/$PID/status` | `resource`, `tracemalloc` | RSS vs VSZ, 누수 탐지 |
| 파일 디스크립터 | `lsof`, `ulimit -n` | `os.open()`, `f.fileno()` | 자원 고갈 시뮬레이션 |
| CPU 분석 | `perf`, `strace` | `cProfile`, `time.perf_counter` | CPU-bound 함수 찾기 |
| 디스크 I/O | `iostat`, `iotop` | `io.open()` + `seek()` | I/O-bound 특성 확인 |
| 네트워크 | `ss`, `netstat`, `tcpdump` | `socket`, `http.client` | 연결 한도와 타임아웃 |

이 표를 학기 초 스터디 그룹에서 공유하면, 실습마다 어느 도구를 써야 하는지 기준이 생깁니다.

## 자주 하는 실수 5가지

1. **메모리 주소와 값을 같은 것으로 보는 일입니다.** 포인터는 값이 아니라 위치를 담습니다.
2. **프로세스와 스레드를 혼동하는 일입니다.** 메모리 공유 여부가 핵심 차이입니다.
3. **스택과 힙을 섞어 이해하는 일입니다.** 함수 로컬 변수는 스택, 동적 할당은 힙입니다.
4. **버퍼링이 동작에 미치는 영향을 잊는 일입니다.** `print`가 즉시 나타나지 않는 이유도 여기 있습니다.
5. **시스템 호출 비용을 너무 가볍게 보는 일입니다.** 루프 안에서 반복적인 파일 열기/닫기는 성능에 즉시 영향을 줍니다.

## 운영 체크리스트

- [ ] 프로세스와 스레드의 차이를 설명할 수 있습니다.
- [ ] 메모리 영역(스택, 힙, 코드, 데이터)을 대략 구분할 수 있습니다.
- [ ] 시스템 호출 비용이 왜 중요한지 이해했습니다.
- [ ] 간단한 코드의 실행 시간과 메모리 사용량을 직접 측정했습니다.
- [ ] CPU-bound와 I/O-bound의 차이를 설명할 수 있습니다.
- [ ] `top` 또는 `htop` 출력에서 CPU, 메모리, iowait 항목을 찾을 수 있습니다.
- [ ] 간단한 멀티스레드 코드를 작성하고 레이스 컨디션이 발생하는지 확인했습니다.

## 처음 질문으로 돌아가기

- **시스템 과목은 코드 한 줄이 실제로 어떻게 동작하는지 어디까지 설명해 줄까요?**
  - CPU 레지스터 수준까지 설명할 수 있습니다. 변수 하나가 어느 레지스터에 올라가고, 함수 호출이 스택에서 어떻게 처리되고, 운영체제가 어떤 시점에 개입하는지를 추적할 수 있습니다. 이 이해가 있으면 성능 수치가 코드를 읽는 또 다른 언어가 됩니다.

- **운영체제, 컴퓨터 구조, 컴파일러는 왜 함께 배워야 할까요?**
  - 세 과목은 실행 경로의 다른 계층을 설명합니다. 컴퓨터구조는 하드웨어, 운영체제는 자원 관리, 컴파일러는 번역 과정입니다. 하나만 알면 다른 계층에서 나오는 문제를 설명하지 못합니다. 성능 문제가 컴파일러 최적화에서 기인하는지, OS 스케줄러에서 기인하는지 구분하려면 세 계층이 모두 필요합니다.

- **프로세스, 메모리, 파일, 시간 같은 개념이 디버깅과 성능 분석에 왜 중요할까요?**
  - 실무 장애의 상당수가 자원 고갈, 경쟁 조건, I/O 병목에서 시작됩니다. 이 개념들이 없으면 도구가 보여 주는 숫자를 읽지 못합니다. 준혁 시나리오처럼 `top` 화면을 열었지만 무엇을 봐야 하는지 모르는 상황이 됩니다.

- **시스템 지식이 없으면 실무에서 어떤 상황에서 막히게 될까요?**
  - 준혁 시나리오처럼 응답이 느려도 어디를 봐야 하는지 모르게 됩니다. 코드를 반복해 읽어도 답이 나오지 않는 경우, 대부분 원인이 시스템 계층에 있습니다. 서영 시나리오처럼 멀티스레드 결과가 틀려도 동기화 문제인지조차 떠올리지 못하게 됩니다.

- **시스템 과목을 추상적 암기 대신 실험으로 배우는 방법은 무엇일까요?**
  - 측정 가능한 가설을 세우는 연습이 핵심입니다. "파일을 한 줄씩 읽는 루프가 느리다"는 가설을 세웠다면 배치 읽기 버전과 시간을 비교해 수치로 근거를 남겨야 합니다. 가설 → 측정 → 비교 → 기록의 순서가 시스템 실험의 기본 루프입니다.

## 정리

시스템 과목은 코드를 더 낮은 층에서 읽게 만드는 훈련입니다. 운영체제, 컴퓨터 구조, 컴파일러, 시스템 프로그래밍 개념이 손에 잡히기 시작하면 디버깅 방식과 성능을 보는 시선도 함께 달라집니다. 학기 중에 도구를 직접 써 보고, 측정 결과를 기록하고, 장애 시나리오를 시뮬레이션해 본 경험이 졸업 후에도 오래 남습니다. 다음 글에서는 저장과 전달을 맡는 데이터베이스와 네트워크로 이어가겠습니다.
