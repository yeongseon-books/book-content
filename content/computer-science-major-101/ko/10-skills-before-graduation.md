# Computer Science Major 101 (10/10): 졸업 전 갖춰야 할 역량

졸업이 가까워질수록 많은 학생이 비슷한 불안을 느낍니다. 과목은 거의 다 들었는데, 정말 현업에 들어갈 준비가 되었는지는 잘 모르겠다는 감각입니다.

이 글은 컴퓨터학과 전공 학습 가이드 101 시리즈의 마지막 글입니다.

![Computer Science Major 101 10장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/computer-science-major-101/10/10-01-graduation-skill-map.ko.png)
*컴퓨터학과 전공 가이드 10장 흐름 개요*

> 졸업 직전 점검은 과목 이름을 세는 일이 아니라, 현업에서 바로 쓰일 다섯 축이 비어 있지 않은지 확인하는 일입니다.

## 이 글에서 다룰 문제

- 졸업장만으로는 설명되지 않는 역량은 무엇일까요?
- 기초, 시스템, 데이터, 협업, 문서화라는 다섯 축은 왜 함께 봐야 할까요?
- 학점과 자격증만으로 실력을 설명하기 어려운 이유는 무엇일까요?
- 대학원 진학과 취업 사이에서 어떤 기준으로 판단해야 할까요?
- 졸업 후 첫 12개월을 어떻게 설계해야 성장이 지속될까요?

## 왜 다섯 축이 필요한가

첫 직장에 들어간 뒤 처음 몇 달은 생각보다 중요합니다. 이 시기의 기본기가 이후 경력의 기준선을 만들기 때문에, 졸업 직전 점검은 단순한 자기평가가 아니라 출발점을 다지는 작업에 가깝습니다.

다섯 축은 따로 놀지 않습니다. 기초가 있어야 시스템을 이해하고, 시스템과 데이터를 알아야 서비스를 만들고, 협업과 문서화가 있어야 팀 안에서 결과를 확장할 수 있습니다.

- **기초 역량(fundamentals)**: 자료구조, 알고리즘, 복잡도 감각입니다.
- **시스템 감각(systems sense)**: CPU, 메모리, I/O, 네트워크를 읽는 감각입니다.
- **데이터 감각(data sense)**: SQL, 통계, 데이터 저장 구조를 다루는 능력입니다.
- **협업(collab)**: Git, PR, 이슈, CI/CD를 통해 팀으로 일하는 방식입니다.
- **문서화(writing)**: 생각과 판단을 글로 남기는 능력입니다.

다섯 축 가운데 어느 하나도 "나중에 배우면 된다"고 미루기 어렵습니다. 기초가 약하면 코딩 테스트에서 걸리고, 협업 경험이 없으면 팀 온보딩이 느려지고, 문서화 습관이 없으면 경험이 쌓여도 자산이 되지 않습니다.

## 왜 여기서 막히는가: 흔한 시나리오

**시나리오 1 — "학점은 좋은데 코딩 테스트에서 계속 탈락한다"**

성민은 4.0 학점에 가까운 GPA를 받았습니다. 하지만 기업 코딩 테스트에서 자료구조 문제가 나올 때마다 막혔습니다. 수업에서 이론은 이해했지만 빠르게 구현하는 연습이 없었기 때문입니다. 학점은 이해 능력을 보여 주지만 실행 속도는 별도로 훈련해야 합니다.

발생 신호:
- 시험에서는 좋은 성적이지만 실제 코드를 처음부터 빠르게 작성하는 데 어려움이 있습니다.
- "이론은 알겠는데 코드가 잘 안 써진다"는 느낌이 반복됩니다.
- 알고리즘 문제를 풀 때 시작 지점을 찾는 데 오랜 시간이 걸립니다.

해결 방향: 기초 자료구조 구현을 타이머 없이 20개, 타이머와 함께 20개 연습하면 속도가 붙습니다. 리스트, 스택, 큐, 이진 탐색, 정렬 각각을 "라이브러리 없이 처음부터 30분 이내에 구현"하는 연습부터 시작합니다. 이미 이론을 알고 있다면 손이 기억하는 데까지 반복하는 과정이 필요합니다.

**시나리오 2 — "포트폴리오가 없다"**

지영은 수업 과제를 모두 했지만 공개된 저장소가 없었습니다. 면접에서 "보여 줄 수 있는 프로젝트가 있나요"라는 질문에 "수업 과제가 있는데 공개는 안 되어 있어요"라고 답했습니다. 결과물이 없으면 주장만 남습니다.

발생 신호:
- GitHub 프로필에 공개 저장소가 없거나 README가 없는 비공개 저장소만 있습니다.
- 면접에서 "GitHub 링크 공유해 주실 수 있나요?"라는 질문에 답하기 어렵습니다.
- "프로젝트를 설명해 주세요"라는 요청에 수업 과제 이름만 나열하게 됩니다.

해결 방향: 수업 과제라도 개인 저장소에 README를 붙여 공개하는 것부터 시작합니다. README에는 "무엇을 만들었는가", "왜 이 설계를 선택했는가", "다음에 개선할 점은 무엇인가"를 한 단락씩만 써도 충분합니다. 의사결정 이유를 추가하는 것만으로 "과제 제출"과 "포트폴리오 항목"의 차이가 생깁니다.

**시나리오 3 — "혼자 코드는 잘 짜는데 팀에서 협업이 안 된다"**

현석은 개인 프로젝트에서는 속도가 빠르지만 팀 과제에서 PR 리뷰를 받거나 충돌을 해결하는 경험이 거의 없었습니다. 입사 후 첫 PR에서 리뷰 댓글에 어떻게 반응해야 할지 몰라 당황했습니다. 리뷰 댓글을 비판으로 받아들여 긴장했고, 어떤 수정이 필요한지 판단하는 것도 어려웠습니다.

발생 신호:
- 개인 프로젝트 경험만 있고 PR/이슈/코드 리뷰 기록이 없습니다.
- Git 브랜치 전략(예: feature 브랜치, rebase 정책)을 설명하기 어렵습니다.
- "PR에서 피드백을 받은 경험이 있나요?"라는 면접 질문에 구체적인 사례가 없습니다.

해결 방향: 오픈소스 프로젝트에 작은 기여(문서 수정, 버그 리포트)를 시작하거나 팀 프로젝트에서 리뷰어 역할을 의도적으로 맡아야 합니다. PR 댓글에 답할 때는 "수정했습니다"보다 "이 방향으로 수정했고, 이렇게 판단한 이유는 X입니다"처럼 이유를 한 줄 붙이는 습관을 들이면 빠르게 협업 감각이 생깁니다.

## 졸업 자기 점검표

```python
# 다섯 축 최소 역량 체크
skills = {
    "fundamentals": {
        "topics": ["array", "list", "tree", "graph", "hash", "sort", "binary_search"],
        "evidence": ["알고리즘 풀이 저장소", "복잡도 분석 노트"]
    },
    "systems": {
        "topics": ["process", "thread", "memory", "io", "network"],
        "evidence": ["OS/네트워크 디버깅 메모", "성능 측정 실습"]
    },
    "data": {
        "topics": ["sql", "indexing", "normalization", "stats_basics"],
        "evidence": ["SQL 과제", "데이터 분석 리포트"]
    },
    "collaboration": {
        "topics": ["git", "pull_request", "code_review", "ci"],
        "evidence": ["공개 PR 기록", "이슈 기록", "팀 프로젝트"]
    },
    "documentation": {
        "topics": ["readme", "design_doc", "post_mortem", "adr"],
        "evidence": ["README가 있는 저장소", "설계 문서", "회고"]
    }
}

# 축별 증거 유무 점검
for axis, content in skills.items():
    evidence_count = len(content["evidence"])
    status = "준비됨" if evidence_count >= 2 else "보강 필요"
    print(f"{axis}: 증거 {evidence_count}개 → {status}")

# 예시 출력:
# fundamentals: 증거 2개 → 준비됨
# systems: 증거 2개 → 준비됨
# data: 증거 2개 → 준비됨
# collaboration: 증거 3개 → 준비됨
# documentation: 증거 3개 → 준비됨
```

이 점검의 핵심은 숫자가 아니라 "말로 설명할 수 있는가"입니다. 증거가 있어도 면접에서 "이 프로젝트에서 어떤 선택을 했고 왜 그렇게 했는지"를 30초 안에 설명하기 어렵다면, 증거를 정리하는 시간이 더 필요합니다.

## 역량 증거 매핑표

졸업 전 자기 점검에서 가장 중요한 질문은 "나는 안다고 말할 수 있는가"보다 "무엇으로 보여 줄 수 있는가"입니다.

| 축 | 최소 증거 예시 | 점검 질문 | 강화 방법 |
| --- | --- | --- | --- |
| 기초 | 자료구조 풀이 저장소, 복잡도 분석 노트 | 시간 복잡도와 선택 이유를 말로 설명할 수 있는가 | 타이머 풀이 20회 반복 |
| 시스템 | OS/네트워크 디버깅 메모, 성능 측정 실습 | 느린 코드가 왜 느린지 한 계층 더 아래에서 설명할 수 있는가 | `strace`, `perf`, `vmstat` 실습 |
| 데이터 | SQL 과제, 간단한 분석 리포트 | 저장 구조와 조회 비용을 함께 설명할 수 있는가 | 인덱스 없이/있을 때 실행 계획 비교 |
| 협업 | GitHub PR, 이슈, 코드 리뷰 기록 | 혼자 코드를 쓰는 것과 팀으로 합치는 과정을 설명할 수 있는가 | 오픈소스 기여 1회, PR 리뷰 5회 |
| 문서화 | README, 설계 문서, 회고 글 | 판단 근거와 배운 점을 글로 남길 수 있는가 | 프로젝트마다 회고 1편 |

## 이 과목이 실무에서 어떻게 쓰이는가

채용과 온보딩에서는 다섯 축의 균형이 중요하게 보입니다. 특정 한 축이 완전히 비어 있으면 다른 강점도 함께 흔들립니다.

| 직무 | 주로 보는 축 | 면접에서 자주 나오는 질문 | 증거로 쓸 수 있는 것 |
| --- | --- | --- | --- |
| 백엔드 신입 | 기초 + 시스템 + 협업 | "O(n²) 코드를 O(n log n)으로 어떻게 개선했는가" | 알고리즘 저장소, PR 기록 |
| 프론트엔드 신입 | 기초 + 협업 + 문서화 | "컴포넌트 설계 결정을 어떻게 내렸는가" | 컴포넌트 설계 문서, PR |
| 데이터 직무 신입 | 데이터 + 기초 + 문서화 | "분석 결과를 이해관계자에게 설명한 경험이 있는가" | 분석 노트북, 실험 기록 |
| ML 엔지니어링 신입 | 기초 + 데이터 + 시스템 | "모델 추론 속도를 개선한 경험이 있는가" | 성능 측정 리포트, 모델 카드 |
| DevOps/SRE 신입 | 시스템 + 협업 + 문서화 | "장애 원인을 어떻게 찾는가" | 장애 회고, CI/CD 구성 기록 |

**백엔드 신입 엔지니어 기준**:
- 기초: 자료구조·알고리즘 문제 풀이 속도와 정확성
- 시스템: 응답 지연 디버깅, 메모리 이슈 파악
- 데이터: SQL 작성, 인덱스 기본 설계
- 협업: Git 브랜치 전략, PR 리뷰 경험
- 문서화: 기술 선택 이유 한 줄 설명, 장애 회고

**데이터 직무 신입 기준**:
- 기초: 통계 기초, Python 데이터 처리
- 시스템: 파이프라인 모니터링, 지연 진단
- 데이터: SQL 조인·집계, 데이터 품질 검증
- 협업: 실험 결과 공유, 리뷰 가능한 노트북
- 문서화: 실험 기록, 모델 카드

## 역량을 실무에서 어떻게 증명하는가

이력서에 "자료구조와 알고리즘을 이해합니다"라고 쓰는 것과 "이진 탐색 트리로 검색 속도를 3배 개선한 커밋 링크"를 제시하는 것은 전혀 다른 무게를 가집니다.

**기초 역량 증명 방법**

- 알고리즘 문제 풀이를 저장소에 누적하되, 단순 코드 저장이 아니라 "왜 이 알고리즘을 선택했는가"를 주석으로 남깁니다.
- 복잡도 분석 노트를 만들어 각 자료구조의 연산 비용을 직접 측정한 결과로 채웁니다.

**시스템 감각 증명 방법**

- 성능 개선 기록: "이전에는 3초 걸렸는데 인덱스를 추가하자 0.1초가 됐다"처럼 수치로 남깁니다.
- 디버깅 메모: `top`, `vmstat`, `netstat` 출력을 해석한 흔적을 노트나 블로그 글로 남깁니다.

**협업 역량 증명 방법**

- PR 히스토리를 정리합니다. 내가 작성한 PR과 내가 리뷰한 PR 각각 링크를 준비합니다.
- 팀 프로젝트 README에 "내가 맡은 부분과 기여 이유"를 명시합니다.

**문서화 역량 증명 방법**

- 회고(retrospective) 글을 프로젝트마다 한 편 씁니다. "잘된 것, 아쉬운 것, 다음에 바꿀 것" 세 가지만 포함해도 충분합니다.
- 의사결정 기록(ADR, Architectural Decision Record)을 간단한 형태로라도 남깁니다. "이 DB를 선택한 이유" 한 단락이 ADR의 시작입니다.

## 졸업 전 의사결정 프레임: 대학원 vs 취업

졸업 시점의 가장 큰 선택 중 하나는 대학원 진학과 취업 사이의 경로 결정입니다.

| 판단 기준 | 대학원 진학 우세 신호 | 취업 우세 신호 |
| --- | --- | --- |
| 관심 문제 성격 | 장기 연구 질문이 명확함 | 제품/서비스 문제 해결 선호 |
| 성과 선호 | 논문, 실험, 재현성 중심 | 출시, 운영, 사용자 지표 중심 |
| 시간 투자 | 2~5년의 집중 학습 의지 | 빠른 현장 경험 축적 선호 |
| 불확실성 감수 | 탐색 실패를 학습으로 수용 | 실행 결과를 빠르게 확인 선호 |
| 재정/생활 조건 | 장기 계획 가능 | 조기 수입 필요성 높음 |
| 피드백 선호 | 지도교수·심사위원 피드백 | 사용자·팀장·코드 리뷰 피드백 |
| 관심 영역 깊이 | 한 문제를 5년간 파고들 수 있음 | 여러 도메인을 빠르게 경험하고 싶음 |

표의 목적은 즉시 결론이 아니라 자기 인식입니다. 각 항목에 대해 솔직히 적어 보면 경로 적합도가 선명해집니다.

취업을 먼저 선택한 뒤 대학원을 고려하는 경로도 있습니다. 현업 경험 후 대학원에 진학하면 연구 문제를 실제 현장에서 가져올 수 있어 연구 방향이 더 구체적인 경우가 많습니다.

## 졸업 후 첫 12개월 로드맵

경로가 달라도 공통적으로 필요한 심화 축이 존재합니다.

| 시기 | 집중 활동 | 산출물 | 확인 질문 |
| --- | --- | --- | --- |
| 1~3개월 | 자료구조·시스템·SQL 핵심 복습, 약점 정리 | 약점 정리 노트, 풀이 저장소 | 어느 축이 가장 약한가 |
| 4~6개월 | 관심 도메인 프로젝트 1개 완성, 문서화 | README, 데모, 의사결정 기록 | 프로젝트를 남에게 설명할 수 있는가 |
| 7~9개월 | 성능/품질 개선 라운드 1회, 측정 기록 | 개선 전/후 수치 비교 리포트 | 이전 대비 얼마나 개선됐는가 |
| 10~12개월 | 결과 공개(블로그, 포트폴리오, 발표), 피드백 반영 | 공개 글 또는 발표 자료 | 외부 피드백이 한 건이라도 있는가 |

중요한 것은 학습량보다 폐루프입니다. 입력(학습)-출력(산출물)-피드백(개선)이 한 번이라도 완결되어야 실력이 자산으로 남습니다.

**경로별 집중 포인트**

- 취업 경로: 1~3개월에 코딩 테스트 대비와 기술 면접 준비를 병행합니다. 특히 "말로 설명하는 연습"을 빠뜨리기 쉬운데, 개념을 소리 내어 설명해 보는 연습이 면접에서 결정적인 차이를 만듭니다.
- 대학원 경로: 1~3개월에 관심 분야 논문 5편 이상 읽고 요약합니다. 연구 질문을 한 문장으로 쓰는 연습을 반복하면 지도교수 면담과 연구 계획서 작성 모두에 도움이 됩니다.

## 대학원 지원 타임라인과 취업 병행 전략

졸업 직전에는 대학원 지원 일정과 취업 준비가 충돌하기 쉽습니다.

| 시점 | 대학원 준비 | 취업 준비 | 공통 산출물 |
| --- | --- | --- | --- |
| D-12개월 | 관심 연구실 탐색, 논문 읽기 | 직무 탐색, 기술 스택 정리 | 역량 점검표 1차 |
| D-9개월 | SOP 초안, 추천인 후보 확정 | 포트폴리오 1차 공개 | 프로젝트 회고 문서 |
| D-6개월 | 연구 제안서 보강, 성적 정리 | 이력서/README 개편 | 대표 프로젝트 2개 고도화 |
| D-3개월 | 지원서 제출, 인터뷰 대비 | 코딩/시스템 면접 대비 | 질문 리스트와 답변 노트 |
| D-1개월 | 오퍼/합격 조건 비교 | 오퍼 비교 및 결정 | 최종 의사결정 문서 |

핵심은 같은 산출물을 두 경로에서 재사용하도록 설계하는 것입니다. 포트폴리오, 프로젝트 회고, 의사결정 문서는 취업과 대학원 지원 모두에 쓸 수 있습니다.

## 다섯 축별 3개월 강화 플랜

자기 점검 뒤에 "가장 약한 축 하나"를 골라 3개월 실행 계획으로 전환해야 합니다.

**기초 축이 약한 경우**

- 1개월차: 배열·연결 리스트·스택·큐를 라이브러리 없이 구현. 각 구현마다 복잡도 설명을 주석으로 추가.
- 2개월차: 정렬 3종(선택, 삽입, 합병), 이진 탐색, 해시 충돌 처리 구현. 타이머를 써서 "30분 이내 구현" 기준으로 반복.
- 3개월차: 그래프 탐색(BFS/DFS), DP 기본 패턴 5개 구현 후 저장소에 공개. 각 문제마다 "왜 이 접근인가" 주석 포함.

**시스템 축이 약한 경우**

- 1개월차: 프로세스/메모리 복습, `top`/`vmstat`/`strace` 실습. 실습 결과를 메모로 남깁니다.
- 2개월차: 성능 측정 실습 2개(파일 읽기 배치 vs 단건 비교, DB 조회 인덱스 없음/있음 비교).
- 3개월차: 개선 리포트 1편 작성. "문제 상황 → 원인 → 수정 → 결과(수치)" 형식으로 공개합니다.

**협업 축이 약한 경우**

- 1개월차: 오픈소스 이슈 1개 리포트. 버그를 재현 가능한 형태로 설명하는 이슈 작성 연습입니다.
- 2개월차: PR 1개 제출. 문서 수정 수준이라도 "변경 이유"를 PR 설명에 한 단락 이상 씁니다.
- 3개월차: 팀원과 코드 리뷰 세션 1회 진행. 댓글에 "수정했습니다" 대신 "이 방향으로 수정했고 이유는 X입니다"로 답합니다.

**문서화 축이 약한 경우**

- 1개월차: 기존 프로젝트 저장소에 README 추가. "무엇을 만들었는가", "왜 이 설계인가", "실행 방법" 세 항목 필수.
- 2개월차: 지난 프로젝트 회고 1편 작성. "잘된 것, 아쉬운 것, 다음에 바꿀 것" 세 항목으로 시작합니다.
- 3개월차: 의사결정 기록(ADR) 1편 작성. "이 기술을 선택한 이유와 고려한 대안"을 한 페이지 분량으로 씁니다.

## 졸업 직전 포트폴리오 최종 점검

포트폴리오는 면접 전날 완성하는 것이 아닙니다. 졸업 직전 3개월이 마지막 정리 기회입니다.

**저장소 점검**

- 공개 저장소 개수가 최소 3개 이상인가.
- 각 저장소에 README가 있고, 프로젝트 목적과 기술 선택 이유가 명시되어 있는가.
- 커밋 메시지가 "fix bug", "update"처럼 내용 없는 메시지가 아닌가. 최소한 "어떤 버그를 어떻게 고쳤는가"가 포함되어야 합니다.

**설명 준비**

- "이 프로젝트에서 가장 어려웠던 기술 결정은 무엇인가"를 2분 안에 말할 수 있는가.
- "다시 만든다면 무엇을 다르게 하겠는가"를 구체적으로 답할 수 있는가.
- "이 프로젝트에서 본인의 기여는 무엇인가"를 팀 프로젝트에서 분리해서 설명할 수 있는가.

**수치화**

- 성능 개선이 있다면 "몇 퍼센트", "몇 배"처럼 수치로 남겨야 합니다.
- 사용자 수, 처리 건수, 응답 시간 같은 지표를 하나라도 기록해 두면 설명력이 달라집니다.

## 자주 하는 실수 5가지

1. **자격증만 나열하는 일입니다.** 자격증은 지식을 증명하지만 실행 능력을 증명하지 않습니다. "정보처리기사 보유"보다 "정보처리기사 공부 중 알게 된 인덱스 원리로 쿼리 속도를 개선한 커밋"이 더 강합니다.

2. **학점만 강조하는 일입니다.** 성민 시나리오처럼 학점이 높아도 구현 속도가 없으면 코딩 테스트에서 막힙니다. 학점은 필요조건이지 충분조건이 아닙니다.

3. **GitHub가 비어 있는 일입니다.** 지영 시나리오처럼 결과물이 없으면 주장만 남습니다. 수업 과제라도 README를 붙여 공개하는 것부터 시작합니다.

4. **문서를 한 편도 남기지 않는 일입니다.** 코드만으로는 "왜 그 선택을 했는지" 설명이 안 됩니다. 회고 한 편이 설계 문서보다 더 강한 인상을 남길 때가 많습니다.

5. **회고 없이 경험을 흘려보내는 일입니다.** 같은 실수를 다음 프로젝트에서도 반복하게 됩니다. 프로젝트가 끝날 때 30분만 투자해서 "잘된 것, 아쉬운 것"을 적어 두면 다음 프로젝트에서 출발점이 달라집니다.

## 운영 체크리스트

- [ ] 다섯 축으로 자기 점검을 해 보았습니다.
- [ ] 각 축에 대응하는 증거를 구체적으로 적어 보았습니다.
- [ ] 가장 약한 영역을 표시하고 원인을 한 줄로 썼습니다.
- [ ] 다음 3개월 행동 계획을 한 줄이라도 세웠습니다.
- [ ] 취업/대학원 경로를 판단 기준 표로 비교해 보았습니다.
- [ ] 포트폴리오 저장소에 README가 있는지 점검했습니다.
- [ ] 면접에서 설명할 프로젝트 2개를 2분 안에 말하는 연습을 해 보았습니다.

## 처음 질문으로 돌아가기

- **졸업장만으로는 설명되지 않는 역량은 무엇일까요?**
  - 실행 속도, 협업 경험, 문서화 능력, 시스템 디버깅 감각입니다. 성민의 경우처럼 GPA 4.0도 "30분 안에 이진 탐색을 구현한다"를 보장하지 않습니다. 지영처럼 과제를 모두 제출해도 공개 저장소가 없으면 주장만 남습니다. 이 역량들은 직접 만든 결과물이 증거가 됩니다.

- **기초, 시스템, 데이터, 협업, 문서화라는 다섯 축은 왜 함께 봐야 할까요?**
  - 하나가 약하면 다른 축에서도 막힙니다. 현석처럼 코드는 잘 짜는데 협업 경험이 없으면 팀 온보딩에서 속도가 나오지 않습니다. 데이터는 잘 다루는데 문서화가 없으면 분석 결과를 다른 사람이 재현할 수 없습니다. 다섯 축은 독립적이지 않고 서로를 강화합니다.

- **학점과 자격증만으로 실력을 설명하기 어려운 이유는 무엇일까요?**
  - 학점은 이해 능력, 자격증은 지식 범위를 보여 주지만 "이 문제를 코드로 30분 안에 풀었다", "이 팀 프로젝트에서 이런 기술적 선택을 했고 이런 결과가 나왔다"는 증명하지 못합니다. 면접관이 보고 싶은 것은 "배웠다"가 아니라 "만들었다"입니다.

- **대학원 진학과 취업 사이에서 어떤 기준으로 판단해야 할까요?**
  - "내가 풀고 싶은 문제가 연구 수준의 질문인가, 아니면 제품에서 빠르게 확인하고 싶은 문제인가"가 핵심 기준입니다. 감정이 아니라 "어떤 환경에서 내가 더 배우는가"로 판단해야 합니다. 대학원 vs 취업 판단 기준 표의 7개 항목을 솔직하게 채워 보면 경로 적합도가 선명해집니다.

- **졸업 후 첫 12개월을 어떻게 설계해야 성장이 지속될까요?**
  - 복습 → 프로젝트 완성 → 성능 개선 → 공개·피드백의 폐루프를 12개월 안에 한 번이라도 완결하는 것이 목표입니다. 새 기술을 계속 추가하는 것보다 하나를 끝까지 가져가는 것이 더 강한 자산이 됩니다. "이전 대비 얼마나 개선됐는가"를 수치로 남기는 습관이 경력 내내 실력 성장의 기준선이 됩니다.

## 정리

졸업 전에는 과목 이수 여부보다 어떤 역량을 실제로 갖추었는지 점검하는 편이 더 중요합니다. 기초, 시스템, 데이터, 협업, 문서화라는 다섯 축으로 자신을 다시 보면 어디가 비어 있는지 분명해집니다.

성민, 지영, 현석 세 시나리오는 모두 다른 지점에서 막혔지만 공통점이 있습니다. 증거가 없었습니다. 학점, 수업 수강, 개인 실력이 있어도 보여 줄 수 있는 형태로 남아 있지 않으면 채용 과정에서 전달되지 않습니다.

가장 약한 축 하나를 골라 3개월 안에 증거 하나를 만드는 것에서 시작합니다. 이 시리즈는 여기서 마무리하지만, 다음 공부는 가장 약한 축을 메우는 일에서 시작하면 됩니다.
