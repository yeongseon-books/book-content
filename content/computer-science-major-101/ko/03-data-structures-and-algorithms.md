- 왜 자료구조와 알고리즘은 거의 모든 컴퓨터학과의 핵심 과목일까요?
- 자료구조를 배우는 일과 알고리즘을 배우는 일은 어떻게 다르고 왜 함께 가야 할까요?

## 왜 이 과목이 전공의 중심인가

자료구조와 알고리즘은 전공 의존성 그래프의 중앙 허브입니다. 이 과목이 약하면 시스템, 데이터베이스, AI 과목의 구현 속도가 함께 둔화됩니다.

구체적으로 살펴보면:
- 운영체제의 스케줄링 알고리즘은 자료구조(큐, 힙)를 기반으로 합니다.
- 데이터베이스의 인덱스는 B-트리와 해시 자료구조를 씁니다.
- 머신러닝의 k-최근접이웃(kNN)은 거리 계산과 정렬 알고리즘입니다.
- 컴파일러의 파싱은 스택과 트리 순회를 활용합니다.

복잡도를 생각하는 습관은 코드 품질을 판단하는 첫 기준이 됩니다. 기능이 맞는지만 보는 단계에서 벗어나, 입력이 커질 때 비용이 어떻게 늘어나는지 설명할 수 있어야 비로소 전공다운 문제 해결이 시작됩니다.

## 핵심 개념

- **배열(array)**: 연속된 메모리 공간을 활용하는 자료구조입니다. 인덱스 접근이 O(1)이지만 삽입·삭제는 O(n)입니다.
- **연결 리스트(linked list)**: 포인터로 연결된 구조입니다. 삽입·삭제가 O(1)이지만 인덱스 접근은 O(n)입니다.
- **트리(tree)**: 계층 구조를 표현합니다. 이진 탐색 트리는 균형이 맞을 때 O(log n)을 제공합니다.
- **그래프(graph)**: 관계를 표현하는 구조입니다. 현실의 도로망, 소셜 네트워크, 의존성 관계를 모델링합니다.
- **복잡도(complexity)**: 입력이 커질 때 비용이 늘어나는 비율입니다. O(1) < O(log n) < O(n) < O(n log n) < O(n²) 순서입니다.

> 자료구조는 데이터를 담는 방식이고, 알고리즘은 그 데이터를 처리하는 절차이며, 복잡도는 그 선택의 비용표입니다.

## 왜 여기서 막히는가: 흔한 시나리오

**시나리오 1 — "BFS와 DFS를 둘 다 외웠는데 언제 써야 할지 모른다"**

성훈은 BFS와 DFS 코드를 외웠습니다. 하지만 문제를 보면 어느 것을 써야 할지 판단이 안 됩니다. "최단 거리를 구해라" 문제에서 DFS를 시도했다가 틀렸습니다. 탐색 알고리즘의 특성을 이해하지 않고 코드만 외웠기 때문입니다.

발생 신호: 문제 유형이 조금만 바뀌어도 어떤 알고리즘을 써야 할지 감이 안 옵니다. 정답 코드를 보면 이해가 되지만 직접 떠올리지 못합니다.

해결 방향: 알고리즘보다 "이 문제에서 최단 거리가 필요한가, 전체 탐색이 필요한가"를 먼저 질문하는 습관을 만들어야 합니다. BFS는 레벨 단위 탐색이 필요할 때, DFS는 경로 탐색이나 백트래킹이 필요할 때 씁니다. 알고리즘을 외우는 시간의 절반을 "언제 이 알고리즘을 선택하는가" 기준 정리에 써야 합니다.

**시나리오 2 — "코드는 맞는데 시간 초과가 난다"**

민서는 조합 문제를 완전 탐색으로 구현해서 기능은 맞았지만 시간 초과를 받았습니다. 입력이 n=20일 때는 통과했는데 n=30이 되자 폭발했습니다. 2^30이 어느 정도 크기인지 감이 없었기 때문입니다.

발생 신호: 작은 테스트 케이스에서는 잘 되는데 제출하면 시간 초과가 반복됩니다. 로컬에서는 1초 미만이지만 채점 서버에서 TLE(Time Limit Exceeded)가 납니다.

해결 방향: 문제를 읽자마자 "입력 상한이 얼마인가"를 확인하고 허용 가능한 복잡도 상한을 먼저 계산해야 합니다. n=10^6이라면 O(n log n) 이하만 허용됩니다. n=10^3이라면 O(n²)도 허용됩니다.

**시나리오 3 — "재귀를 이해는 했는데 구현이 틀린다"**

태희는 재귀 개념은 이해했지만 실제 구현에서 base case를 잘못 설정하거나 상태를 공유해서 오류가 납니다. 재귀 호출 트리를 머릿속으로 그리지 못하기 때문입니다. 호출마다 지역 상태가 새로 만들어지는지, 공유되는지 구분이 안 됩니다.

발생 신호: 재귀 함수가 작은 입력에서는 되지만 특정 케이스에서 무한 루프에 빠지거나 잘못된 값을 돌려줍니다.

해결 방향: 재귀 함수를 작성할 때 "이 함수가 보장하는 것(불변식)"을 한 줄로 먼저 적고 시작해야 합니다. `def solve(n): # 보장: n >= 0인 경우의 답을 반환` 형식으로 계약을 명시하면 base case와 재귀 케이스 설계가 훨씬 명확해집니다.

## 자료구조 연산 복잡도 비교표

| 자료구조 | 접근 | 탐색 | 삽입 | 삭제 | 사용 맥락 |
| --- | --- | --- | --- | --- | --- |
| 배열 | O(1) | O(n) | O(n) | O(n) | 인덱스 접근이 핵심일 때 |
| 연결 리스트 | O(n) | O(n) | O(1) | O(1) | 삽입/삭제 위치가 이미 주어질 때 |
| 해시 테이블 | - | 평균 O(1) | 평균 O(1) | 평균 O(1) | 키 기반 빠른 조회가 필요할 때 |
| 이진 탐색 트리 | O(log n) | O(log n) | O(log n) | O(log n) | 정렬 상태 유지 + 동적 갱신 |
| 힙 | - | O(n) | O(log n) | O(log n) | 우선순위 큐, top-k |
| 그래프(인접 리스트) | - | O(V+E) | O(1) | O(1) | 연결 관계, 경로 문제 |

표를 해석할 때는 Big O만 보지 말고 상수 비용과 구현 복잡도도 함께 보아야 합니다. 해시 테이블의 평균 O(1)은 충돌이 없을 때의 이야기입니다. 최악은 O(n)이고, 공간 비용도 무시할 수 없습니다.

## 알고리즘 패러다임 비교

알고리즘은 개별 기법을 따로 외우기보다 패러다임 관점에서 묶어 보는 편이 유지율이 높습니다.

| 패러다임 | 핵심 질문 | 대표 문제 | 주의할 점 |
| --- | --- | --- | --- |
| 완전 탐색 | 가능한 경우를 모두 보면 되는가 | 부분집합, 순열 | 가지치기 없으면 폭발 |
| 분할 정복 | 문제를 같은 형태의 작은 문제로 나눌 수 있는가 | 병합정렬, 퀵정렬 | 병합/결합 비용 점검 |
| 그리디 | 지금 최선이 전체 최선으로 이어지는가 | 회의실 배정, 허프만 | 교환 논증 확인 |
| 동적 계획법 | 부분 문제 해를 재사용할 수 있는가 | 배낭, LIS | 상태 정의가 절반 |
| 그래프 탐색 | 관계망에서 도달/최단/연결을 묻는가 | BFS, DFS, 다익스트라 | 표현 방식 통일 |
| 투 포인터/슬라이딩 윈도우 | 선형 구조에서 조건을 만족하는 구간을 찾는가 | 부분 합, 최장 연속 구간 | 이동 조건 엄밀히 |

패러다임별로 대표 문제를 하나씩 완전히 이해한 뒤 변형 문제를 풀면, 처음 보는 문제에서도 어느 패러다임이 해당하는지 30초 안에 분류할 수 있게 됩니다.

## 핵심 알고리즘 구현 예시

```python
# 이진 탐색 — 정렬된 배열에서 로그 탐색
def bsearch(xs, t):
    lo, hi = 0, len(xs) - 1
    while lo <= hi:
        m = (lo + hi) // 2
        if xs[m] == t:
            return m
        if xs[m] < t:
            lo = m + 1
        else:
            hi = m - 1
    return -1

# 스택 — 함수 호출, 괄호 검사, 되돌리기
stack = []
stack.append(1)
stack.pop()

# 그래프 BFS — 최단 거리, 연결성
from collections import deque

def bfs(g, s):
    seen, q = {s}, deque([s])
    while q:
        u = q.popleft()
        for v in g[u]:
            if v not in seen:
                seen.add(v)
                q.append(v)
    return seen

# 복잡도 메모 습관
# 문제: 정렬된 배열에서 타겟 찾기
# 입력 상한: n = 10^6
# 핵심 연산: 구간을 절반씩 줄이는 비교
# 시간 복잡도: O(log n) → 약 20번 비교
# 공간 복잡도: O(1)

# DP 예시 — 최장 증가 부분수열(LIS)
def lis(nums):
    # 보장: dp[i] = nums[i]로 끝나는 LIS 길이
    if not nums:
        return 0
    dp = [1] * len(nums)
    for i in range(1, len(nums)):
        for j in range(i):
            if nums[j] < nums[i]:
                dp[i] = max(dp[i], dp[j] + 1)
    return max(dp)
```

## 복잡도 상한 빠른 계산표

입력 크기를 먼저 보고 허용 복잡도를 역산하는 습관이 필요합니다.

| 입력 크기(n) | 허용 복잡도 상한 | 대표 알고리즘 |
| --- | --- | --- |
| n ≤ 10 | O(n!) | 순열 완전 탐색 |
| n ≤ 20~25 | O(2^n) | 비트마스크 DP |
| n ≤ 500 | O(n³) | 플로이드-워셜 |
| n ≤ 5,000 | O(n²) | 버블/삽입 정렬, 단순 DP |
| n ≤ 10^6 | O(n log n) | 병합정렬, 이진 탐색 기반 |
| n ≤ 10^8 | O(n) | 선형 탐색, 해시 |
| n > 10^8 | O(log n) 또는 O(1) | 이진 탐색, 수학 공식 |

이 표를 외우면 문제를 읽자마자 어느 복잡도 이하의 알고리즘이 필요한지 먼저 결론을 내릴 수 있습니다.

## 이 과목이 실무에서 어떻게 쓰이는가

**API 응답 지연 문제**: 실제 서비스에서 API 지연 시간 문제를 따라가다 보면 생각보다 자주 자료구조 선택에서 출발합니다. 전체 스캔을 반복하거나, 더 나은 조회 구조를 쓰지 않거나, 중복 계산을 그대로 두는 순간 성능 문제는 서버 규모보다 먼저 코드 구조에서 시작됩니다.

**데이터베이스 인덱스**: DB의 B-트리 인덱스는 이진 탐색 트리의 일반화입니다. 어떤 컬럼에 인덱스를 걸지 판단하려면 해당 자료구조의 특성을 알아야 합니다.

**코딩 인터뷰**: 기업 코딩 인터뷰의 90% 이상은 자료구조와 알고리즘 문제입니다. 단 정답을 맞히는 것보다 "왜 이 선택을 했는지" 설명하는 능력이 더 중요합니다.

| 실무 상황 | 필요한 자료구조/알고리즘 | 핵심 판단 기준 |
| --- | --- | --- |
| 캐시 구현 | 해시 테이블 + 이중 연결 리스트 (LRU) | 접근 O(1) + 순서 유지 |
| 실시간 랭킹 | 힙 또는 정렬된 집합 | 빈번한 갱신 + top-k 조회 |
| 검색 자동완성 | 트라이(Trie) | 접두사 빠른 탐색 |
| 최단 경로 | 다익스트라, BFS | 가중치 유무에 따라 선택 |
| 의존성 순서 | 위상 정렬 | 사이클 감지 포함 |
| 중복 제거 | 해시 집합(set) | O(1) 존재 확인 |
| 구간 합 쿼리 | 세그먼트 트리, 펜윅 트리 | 갱신과 쿼리가 동시에 빈번할 때 |

## 복잡도 학습을 실전 습관으로 바꾸기

복잡도를 진짜로 체득하려면 풀이마다 세 줄 메모를 남기는 습관이 필요합니다.

1. 입력 크기 상한 (n의 최댓값)
2. 핵심 연산 횟수 (Big O 표기)
3. 메모리 사용 근거 (공간 복잡도)

이 세 줄이 있으면 같은 정답 코드라도 왜 통과했고 왜 느려질 수 있는지 설명할 수 있습니다.

문제 풀이 순서도 중요합니다. 처음 10분은 구현하지 말고 상태 정의와 자료구조 선택만 적는 시간을 두십시오. DP 문제는 점화식보다 상태 정의가 먼저이고, 그래프 문제는 알고리즘보다 표현 방식이 먼저입니다.

## 과목을 넘어 계속 성장하는 방법

자료구조와 알고리즘은 학기가 끝나도 꾸준히 손에 익혀야 하는 근육입니다. 아래 방식이 검증된 접근입니다.

**풀이 복기 습관**: 맞은 문제도 다른 방법으로 풀 수 있는지 확인합니다. 완전 탐색으로 맞혔다면 DP로 개선할 수 있는지, O(n²)으로 맞혔다면 O(n log n)이 가능한지를 봅니다.

**오답 노트 패턴화**: "틀린 이유"를 카테고리로 분류합니다. 복잡도 계산 실수, base case 오류, 오버플로우 미확인, 자료구조 선택 오류 중 어디가 반복되는지 파악하면 집중 보강 방향이 생깁니다.

**구현 → 설명 → 재구현**: 알고리즘을 구현한 뒤 종이에 직접 설명을 적어 보고, 그 설명만 보고 다시 구현합니다. 이 사이클이 3회 이상 돌면 해당 알고리즘은 거의 외우지 않아도 됩니다.

## 자주 하는 실수 5가지

1. **복잡도를 전혀 적어 보지 않는 일입니다.** 입력 크기를 무시하면 제출할 때마다 시간 초과 패턴이 반복됩니다.
2. **재귀 호출의 스택 비용을 잊는 일입니다.** 깊은 재귀는 스택 오버플로우를 일으킬 수 있습니다.
3. **해시를 만능 해법처럼 쓰는 일입니다.** 해시 충돌, 메모리 비용, 정렬 불가능성을 함께 고려해야 합니다.
4. **그래프 표현 방식을 섞어 놓고 혼동하는 일입니다.** 인접 행렬과 인접 리스트를 같은 코드에서 혼용하면 디버깅이 어려워집니다.
5. **입력 크기를 가볍게 보고 테스트를 너무 작게만 하는 일입니다.** 실제 제약 조건의 10%인 예시로만 테스트하면 제출 후 깨집니다.

## 운영 체크리스트

- [ ] 풀이에 시간 복잡도를 적어 보았습니다.
- [ ] 입력 크기 제한을 먼저 확인했습니다.
- [ ] 코드가 유지해야 할 불변식을 한 줄로 적었습니다.
- [ ] 대표 케이스와 경계 케이스(빈 입력, 단일 원소)를 테스트했습니다.
- [ ] 어떤 패러다임을 골랐는지 이유를 한 문장으로 적었습니다.
- [ ] 맞힌 문제를 다른 접근 방법으로 다시 풀어 보았습니다.
- [ ] 오답 이유를 카테고리로 분류해 오답 노트에 기록했습니다.

## 처음 질문으로 돌아가기

- **왜 자료구조와 알고리즘은 거의 모든 컴퓨터학과의 핵심 과목일까요?**
  - 전공 의존성 그래프의 중앙 허브이기 때문입니다. 운영체제의 스케줄러, 데이터베이스의 인덱스, AI의 탐색 알고리즘 모두 이 과목의 개념을 씁니다. 이 과목이 약하면 이후 과목의 구현 속도가 함께 줄어듭니다.

- **자료구조를 배우는 일과 알고리즘을 배우는 일은 어떻게 다르고 왜 함께 가야 할까요?**
  - 자료구조는 데이터를 어떻게 담을지, 알고리즘은 그 데이터를 어떻게 처리할지를 다룹니다. 데이터 모양이 알고리즘 선택을 결정하기 때문에 두 선택이 함께 맞아야 복잡도가 의미 있어집니다. 힙 없이 우선순위 큐 알고리즘은 비효율적이고, 트라이 없이 접두사 탐색 알고리즘은 느립니다.

- **시간 복잡도와 공간 복잡도는 실제 코드에서 무엇을 판단하게 해 줄까요?**
  - 입력 크기가 커졌을 때 코드가 버틸 수 있는지를 판단하게 합니다. 기능이 맞아도 복잡도가 잘못되면 실제 데이터에서 작동하지 않습니다. 민서 시나리오처럼 n=30에서 터지는 코드는 복잡도를 먼저 계산했다면 구현 전에 걸러낼 수 있었습니다.

- **코딩 인터뷰와 실무에서 이 과목은 어떻게 다르게 쓰일까요?**
  - 인터뷰에서는 정답을 맞히는 과정에서 선택 이유를 설명하는 능력을 봅니다. 실무에서는 시스템 병목을 진단하거나 데이터 구조를 설계할 때 복잡도 감각이 직접 쓰입니다. 두 맥락에서 공통적으로 필요한 것은 "왜 이 선택인가"를 설명하는 언어입니다.

- **초보자가 자료구조·알고리즘에서 가장 자주 막히는 지점은 어디일까요?**
  - 알고리즘을 외우는 방식으로 공부하는 것입니다. 성훈 시나리오처럼 BFS/DFS 코드를 외워도 언제 어느 것을 써야 하는지 판단이 안 됩니다. 패러다임 질문("이 문제에서 뭘 구하는가")부터 시작하는 습관이 이 막힘을 해결합니다.

## 정리

자료구조와 알고리즘은 특정 시험을 위한 과목이 아니라 문제 해결의 공통 언어를 익히는 과목입니다. 데이터를 어떤 모양으로 둘지, 어떤 절차로 처리할지, 비용이 얼마나 늘어날지를 함께 설명할 수 있어야 코드 품질도 함께 올라갑니다. 풀이마다 복잡도 세 줄을 남기는 습관 하나가 이 과목에서 얻을 수 있는 가장 실용적인 자산입니다. 다음 글에서는 코드가 실제로 돌아가는 바닥인 시스템 과목으로 넘어가겠습니다.
