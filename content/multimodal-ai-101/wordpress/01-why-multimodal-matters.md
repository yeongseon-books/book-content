# 바이브코딩을 위한 멀티모달 AI (1/10): 멀티모달이 중요한 이유

> 이 글은 **바이브코딩을 위한 멀티모달 AI** 시리즈 1편입니다. 텍스트 LLM만으로는 부족한 이유, early/late/hybrid fusion의 차이, 멀티모달 도입 전에 알아야 할 함정을 다룹니다.

바이브코딩으로 AI 앱을 만들다 보면 어느 순간 텍스트만으로는 해결이 안 되는 문제에 부딪힌다. 사용자가 영수증 사진을 올리고, 차트 캡처를 던지고, 스크린샷으로 오류를 보여준다. 텍스트 LLM에게 "이미지에서 텍스트를 뽑아서 처리하자"는 방식으로 우회하면 당장은 돌아가는 것처럼 보인다. 하지만 레이아웃, 색상, 시각적 관계, 표 구조는 텍스트로 환원되는 순간 이미 절반이 사라진다.

멀티모달 AI는 이 문제를 해결한다. GPT-4V, Gemini, Claude 3 같은 모델은 이미지와 텍스트를 함께 받아 하나의 추론 경로에서 처리한다. 그런데 도입하는 순간 새로운 운영 문제가 생긴다. 이미지 한 장이 토큰 비용으로 바뀌고, 해상도 전처리가 품질 문제로 바뀌며, 텍스트와 이미지가 충돌할 때 어느 쪽을 신뢰할지 정책을 정해야 한다.

멀티모달 융합 방식은 크게 세 가지다. early fusion은 입력 단계에서 modality를 합치고, late fusion은 각 modality를 별도 처리한 뒤 결합하며, hybrid fusion은 둘을 섞는다. 바이브코딩 환경에서는 API로 제공되는 VLM을 호출하는 것이 가장 빠른 시작이지만, 내부에서 어떤 융합 전략을 쓰는지 이해해야 모델 선택과 비용 판단이 가능하다.

OCR + 규칙 기반 파이프라인과 비교하면 멀티모달이 강한 영역이 뚜렷하다. 레이아웃과 의미가 동시에 중요한 문서, 텍스트로 표현되기 어려운 시각적 관계, 복합 입력에서 맥락 추론이 필요한 작업이 그 영역이다. 반면 정밀 숫자 추출처럼 OCR이 더 신뢰할 수 있는 영역도 있다.

> 멀티모달의 핵심은 이미지를 읽는 능력 자체가 아니라, 텍스트로 환원되기 전에 존재하던 정보를 추론 경로 안으로 다시 가져오는 데 있습니다.

## 이 글에서 다룰 문제

- 텍스트 LLM만으로는 왜 이미지 기반 문제에서 한계가 빠르게 드러날까요?
- 멀티모달 시스템은 어떤 업무에서 OCR + 규칙 기반보다 강한가요?
- early fusion, late fusion, hybrid fusion은 무엇이 다를까요?
- 멀티모달 도입 전에 어떤 운영 비용을 먼저 고려해야 할까요?
- 초보자가 가장 자주 놓치는 멀티모달 함정은 무엇인가요?

## Before / After: 멀티모달 도입 전후

| 상황 | 텍스트 LLM만 | 멀티모달 도입 후 |
|------|------------|----------------|
| 영수증 처리 | OCR 후 텍스트 파싱 | 이미지 직접 이해 + 구조 파악 |
| 표/차트 분석 | 텍스트 추출 후 정보 손실 | 레이아웃과 의미 동시 처리 |
| 오류 화면 디버깅 | 스크린샷 설명 요청 필요 | 이미지 직접 입력 |
| 비용 계측 | 텍스트 토큰만 계산 | 이미지 토큰 비용 별도 계산 필요 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 이미지를 항상 OCR 후 텍스트로 변환 | 시각 정보 손실 | 멀티모달 API 직접 호출 검토 |
| 해상도 전처리 없이 원본 전송 | 비용 급증, 처리 실패 | 해상도 정책 사전 수립 |
| 이미지 토큰 비용 미계측 | 월말 청구서 충격 | 이미지 토큰 비용 별도 모니터링 |
| 텍스트-이미지 충돌 시 정책 없음 | 결과 불일치 | 우선순위 정책 사전 정의 |

## AI 팁: 멀티모달 빠르게 시작하는 방법

Claude나 GPT-4에 "Python으로 이미지와 텍스트를 함께 OpenAI API에 보내는 코드를 만들어줘. base64 인코딩과 이미지 URL 두 가지 방식을 모두 보여줘"라고 요청하면 시작할 수 있다. OpenAI API에서는 `messages` 배열에 `{"type": "image_url", "image_url": {"url": "..."}}` 형태로 이미지를 포함한다. `detail` 파라미터로 `"low"` (85 토큰 고정) 또는 `"high"` (512x512 타일 기반) 중 하나를 선택해 비용을 제어한다. 처음에는 `detail="low"`로 시작해 비용을 확인한 뒤 필요한 경우에만 high로 높인다.

## 운영 체크리스트

- [ ] 이미지 토큰 비용을 텍스트와 분리해서 모니터링하는가
- [ ] 해상도 전처리 정책(최대 크기, 리사이징)을 정의했는가
- [ ] 텍스트와 이미지 정보가 충돌할 때 어느 쪽을 우선하는지 정책이 있는가
- [ ] 이미지 입력에 대한 PII 스캔 계획이 있는가
- [ ] 멀티모달 응답의 품질 평가 기준을 정의했는가

## 처음 질문으로 돌아가기

- **텍스트 LLM vs 멀티모달 선택 기준은?** 이미지의 시각적 구조, 레이아웃, 의미가 답변에 영향을 주면 멀티모달. 텍스트만 추출해도 충분하면 OCR + 텍스트 LLM.
- **이미지 토큰 비용은?** GPT-4V 기준 `detail=low`는 85 토큰, `detail=high`는 이미지 크기에 비례. 항상 먼저 계산하고 시작한다.
- **도입 전 첫 체크포인트는?** "이미지에서 어떤 정보를 추출할 것인가"를 정의하고, OCR로 충분한지 멀티모달이 필요한지 먼저 판단한다.

## 정리

멀티모달 AI는 텍스트로 환원되기 전의 시각 정보를 추론 경로 안으로 가져오는 아키텍처 변화다. 바이브코딩 환경에서 빠르게 시작하려면 VLM API 호출부터 시작하되, 이미지 토큰 비용과 해상도 정책을 처음부터 설계해야 나중에 운영 문제를 줄일 수 있다.
