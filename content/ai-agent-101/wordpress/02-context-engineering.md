# 바이브코딩을 위한 AI Agent 기초 (2/10): 컨텍스트 엔지니어링

이 글은 **바이브코딩을 위한 AI Agent 기초** 시리즈의 두 번째 글입니다.

---

바이브코딩으로 에이전트를 만들다 보면 "프롬프트를 잘 쓰면 되지 않나요?"라는 생각이 듭니다. 하지만 에이전트 수준에서는 단순한 프롬프트 작성을 넘어 **컨텍스트 전체를 설계**해야 합니다. 시스템 프롬프트, 대화 히스토리, 도구 설명, 상태 정보 — 이 네 가지가 에이전트가 받아보는 전체 맥락입니다.

컨텍스트가 부실하면 LLM은 멋대로 추측합니다. "도구를 써야 할지", "이미 알고 있는 건지", "다음 단계가 무엇인지"를 컨텍스트 없이는 알 수 없습니다. 바이브코딩에서 에이전트 품질의 80%는 컨텍스트 설계에서 결정됩니다.

이 글에서는 컨텍스트의 4가지 레이어, 좋은 시스템 프롬프트와 나쁜 시스템 프롬프트의 차이, 도구 설명을 LLM이 잘 이해하도록 작성하는 방법을 다룹니다.

> "에이전트에게 좋은 컨텍스트를 주는 것은, 팀원에게 업무 배경을 제대로 설명하는 것과 같습니다."

## 이 글에서 다룰 질문

1. 컨텍스트 엔지니어링이 단순 프롬프트 작성과 어떻게 다른가요?
2. 시스템 프롬프트에서 반드시 포함해야 할 요소는 무엇인가요?
3. 도구 설명을 LLM이 잘 이해하도록 작성하는 방법은?
4. 컨텍스트 윈도우가 꽉 차면 어떻게 해야 하나요?
5. few-shot 예시는 언제 추가하는 게 효과적인가요?

---

## 컨텍스트의 4가지 레이어

| 레이어 | 내용 | 역할 |
|--------|------|------|
| 시스템 프롬프트 | 에이전트 역할, 제약, 출력 형식 | 에이전트 정체성 정의 |
| 대화 히스토리 | 이전 메시지, 도구 호출/결과 | 현재까지의 맥락 |
| 도구 설명 | 각 도구의 이름, 용도, 파라미터 | 어떤 행동이 가능한지 |
| 상태 정보 | 현재 목표, 진행 단계, 변수 | 지금 어디에 있는지 |

바이브코딩에서 가장 자주 빠뜨리는 레이어는 **상태 정보**입니다. 에이전트가 몇 번째 시도인지, 이미 어떤 정보를 수집했는지를 프롬프트에 포함하면 LLM이 더 좋은 결정을 내립니다.

## Before / After: 시스템 프롬프트 설계

**Before (나쁜 시스템 프롬프트)**
```python
system_prompt = "당신은 도움이 되는 AI 어시스턴트입니다."
```

이 프롬프트는 에이전트에게 역할, 제약, 출력 형식 중 아무것도 알려주지 않습니다.

**After (좋은 시스템 프롬프트)**
```python
system_prompt = """당신은 고객지원 에이전트입니다.

역할: 제품 관련 문의에 답변하고 필요시 도구를 사용해 정확한 정보를 제공합니다.

제약:
- 확인되지 않은 정보는 "확인이 필요합니다"라고 답하세요
- 개인정보는 절대 기록하지 마세요
- 3번 도구 시도 후 해결 안 되면 인간 에이전트에게 에스컬레이션하세요

출력 형식:
- 먼저 상황을 파악한 뒤 행동을 결정하세요
- 각 도구 호출 전에 이유를 설명하세요"""
```

## 도구 설명: when_to_use와 when_not_to_use

도구 설명에서 가장 중요한 것은 LLM이 "언제 이 도구를 써야 하는지"를 명확히 알 수 있게 하는 것입니다.

```python
tools = [
    {
        "name": "search_product_info",
        "description": "제품 정보를 데이터베이스에서 검색합니다",
        "when_to_use": "고객이 특정 제품의 스펙, 가격, 재고를 물어볼 때",
        "when_not_to_use": "일반적인 사용 방법이나 FAQ는 직접 답변 가능",
        "parameters": {
            "product_id": "제품 코드 (예: SKU-12345)",
            "fields": "조회할 필드 목록 (price, stock, spec)"
        }
    }
]
```

`when_not_to_use`를 명시하면 LLM이 불필요한 도구 호출을 줄이고 비용을 절감할 수 있습니다.

## 흔한 실수

| 실수 | 문제 | 해결 방법 |
|------|------|-----------|
| 시스템 프롬프트에 역할만 정의 | 제약과 출력 형식 부재로 예측 불가 | 역할+제약+형식 3가지 모두 명시 |
| 도구 설명이 짧고 모호 | LLM이 언제 쓸지 모름 | when_to_use, when_not_to_use 추가 |
| 상태 정보 누락 | LLM이 맥락 없이 결정 | 현재 단계, 이미 수집한 정보 포함 |
| 컨텍스트 꽉 찰 때 무작위 삭제 | 중요 정보 손실 | 요약 전략으로 중요도 기반 압축 |

## AI 팁

컨텍스트 윈도우가 꽉 찰 때는 "요약 메모리" 전략을 씁니다. 오래된 대화 히스토리를 LLM에게 요약시켜 짧은 형태로 보존하면 토큰을 절약하면서도 핵심 맥락을 유지할 수 있습니다.

```python
def compress_history(messages: list[dict], max_tokens: int = 2000) -> list[dict]:
    if estimate_tokens(messages) <= max_tokens:
        return messages

    # 최근 N개는 그대로 유지
    recent = messages[-4:]
    older = messages[:-4]

    # 오래된 부분은 요약
    summary = llm.chat(f"다음 대화를 3줄로 요약하세요:\n{older}")

    return [{"role": "system", "content": f"이전 대화 요약: {summary}"}] + recent
```

## 체크리스트

- [ ] 시스템 프롬프트에 역할, 제약, 출력 형식이 모두 포함되어 있다
- [ ] 도구 설명에 when_to_use와 when_not_to_use를 명시했다
- [ ] 에이전트 상태 정보를 컨텍스트에 포함한다
- [ ] 컨텍스트 윈도우 크기를 모니터링하고 압축 전략이 있다
- [ ] few-shot 예시를 출력 형식 안내에 활용하고 있다

## 처음 질문으로 돌아가기

**컨텍스트 엔지니어링이 단순 프롬프트 작성과 어떻게 다른가요?** 프롬프트 작성이 한 번의 질문을 잘 쓰는 것이라면, 컨텍스트 엔지니어링은 에이전트가 받아보는 전체 정보 구조(역할, 히스토리, 도구, 상태)를 설계하는 것입니다.

**시스템 프롬프트에서 반드시 포함해야 할 요소는?** 역할 정의, 행동 제약, 출력 형식 — 이 세 가지가 최소입니다.

**도구 설명을 잘 작성하는 방법은?** name, description만으로는 부족합니다. when_to_use와 when_not_to_use를 추가하면 LLM의 도구 선택 정확도가 크게 올라갑니다.

**컨텍스트 윈도우가 꽉 차면?** 최근 메시지는 보존하고 오래된 대화는 요약 압축하는 전략을 씁니다.

**few-shot 예시는 언제?** 출력 형식이 복잡하거나 특정 패턴을 따라야 할 때, 시스템 프롬프트 내에 1~3개의 예시를 넣으면 효과적입니다.

## 정리

컨텍스트 엔지니어링은 에이전트의 "두뇌에 넣어주는 정보"를 설계하는 작업입니다. 시스템 프롬프트, 대화 히스토리, 도구 설명, 상태 정보 — 이 4가지 레이어를 잘 설계하면 에이전트의 품질이 확연히 달라집니다. 바이브코딩에서 에이전트가 엉뚱한 행동을 할 때는 대부분 컨텍스트 레이어 중 하나가 빠져 있습니다.

다음 글에서는 에이전트가 도구를 어떻게 사용하는지, **도구 사용 기초**를 다룹니다.
