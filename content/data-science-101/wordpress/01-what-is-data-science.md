# 바이브코딩을 위한 데이터 사이언스 기초 (1/10): AI에게 데이터 분석 맡기기 전에 알아야 할 것

이 글은 바이브코딩을 위한 데이터 사이언스 기초 시리즈의 1번째 글입니다.

AI 코딩 도구가 일상이 된 요즘, 많은 사람들이 이런 상황을 경험합니다. CSV 파일 하나를 AI에게 던지면서 "이 데이터 분석해줘"라고 말합니다. AI는 즉시 멋진 코드와 차트를 내놓습니다. 그런데 결과를 팀에 공유했을 때 누군가가 묻습니다. "그래서 이 숫자로 우리가 뭘 해야 하죠?" 그 순간 대답이 막힙니다.

바이브코딩의 진짜 함정은 여기에 있습니다. AI가 코드를 작성하는 건 문제가 없습니다. 문제는 어떤 코드를 요청해야 하는지, 나온 결과를 어떻게 해석해야 하는지를 모른다는 점입니다. 데이터 사이언스 워크플로를 모르면 AI에게 정확한 질문을 던질 수 없고, AI가 내놓은 결과가 맞는지 틀린지도 판단할 수 없습니다.

데이터 사이언스는 크게 네 가지 역할로 나뉩니다. 지표와 대시보드를 다루는 데이터 분석가, 예측 모델을 만드는 데이터 사이언티스트, 모델을 서비스에 올리는 ML 엔지니어, 데이터 파이프라인을 구축하는 데이터 엔지니어입니다. AI에게 분석을 요청할 때도 이 역할 구분을 알아야 "지금 내가 원하는 건 EDA야, 아니면 모델링이야"라고 정확히 지시할 수 있습니다.

바이브코딩 환경에서 데이터 사이언스를 이해한다는 것은 모든 알고리즘을 외운다는 의미가 아닙니다. 문제를 데이터 질문으로 바꾸고, AI가 내놓은 결과를 의사결정으로 연결하는 흐름을 이해한다는 의미입니다.

> 데이터 사이언스의 핵심은 AI에게 어떤 코드를 짜달라고 할지 아는 것이 아니라, 어떤 문제를 풀어달라고 할지 아는 것입니다.

## 이 글에서 다룰 문제
- 데이터 사이언스를 한 문장으로 어떻게 이해하면 좋을까요?
- 데이터 분석가, 데이터 사이언티스트, ML 엔지니어, 데이터 엔지니어는 무엇이 다를까요?
- AI에게 데이터 분석을 맡기려면 어떤 흐름을 이해해야 할까요?
- 바이브코딩 환경에서 데이터 작업이 실패하는 가장 흔한 이유는 무엇일까요?
- 문제 정의에서 의사결정까지 어떻게 연결하면 될까요?

## 데이터 사이언스란 무엇인가 — 바이브코더 관점

데이터 사이언스는 통계학, 머신러닝, 도메인 지식이 만나는 교차점입니다. 하지만 바이브코딩 맥락에서 더 실용적인 정의는 이렇습니다: 비즈니스 문제를 데이터 질문으로 바꾸고, 그 답을 실제 행동으로 연결하는 일련의 과정.

| 분야 | 주요 목적 | 바이브코딩 요청 예시 |
|---|---|---|
| 통계학 | 불확실성 하에서 추정과 검증 | "이 두 그룹의 차이가 통계적으로 유의한지 확인해줘" |
| 머신러닝 | 데이터에서 예측 모델 학습 | "이탈 예측 모델 만들어줘" |
| 데이터 사이언스 | 데이터로 비즈니스 문제 해결 | "매출 감소 원인을 데이터로 찾아줘" |

AI에게 분석을 요청할 때 이 구분이 없으면 결과물이 뭔지도 모르고 받게 됩니다.

## 데이터 사이언스 역할 구분

- **Data Analyst**: 지표와 대시보드를 통해 비즈니스 질문에 답합니다. AI 요청: "채널별 매출을 시각화해줘"
- **Data Scientist**: 모델을 만들고 예측과 최적화를 시도합니다. AI 요청: "이탈 가능성 높은 사용자 예측 모델 만들어줘"
- **ML Engineer**: 모델을 서비스 환경에 올리고 운영 가능하게 만듭니다. AI 요청: "이 모델을 API로 배포하는 코드 작성해줘"
- **Data Engineer**: 데이터 파이프라인과 웨어하우스를 설계합니다. AI 요청: "매일 자동으로 데이터를 수집하는 파이프라인 만들어줘"

## CRISP-DM: AI에게 데이터 분석 시킬 때의 기본 순서

AI에게 데이터 분석을 맡길 때 이 순서를 모르면 중간에 방향을 잃습니다.

1. **문제 이해** — "우리가 해결하려는 비즈니스 문제는 정확히 무엇인가?"
2. **데이터 이해** — "어떤 데이터가 있고 상태는 어떤가?"
3. **데이터 준비** — "분석 가능한 형태로 정제하고 변환"
4. **모델링** — "적합한 알고리즘 선택과 학습"
5. **평가** — "비즈니스 기준으로 결과 검증"
6. **배포** — "실제 운영 환경에 적용"

중요한 점은 문제를 먼저 이해하지 않고 바로 AI에게 "분석해줘"라고 하면, AI는 기술적으로 완벽하지만 비즈니스와 무관한 결과를 낼 수 있다는 것입니다.

## Before / After

**Before**: AI에게 CSV를 넘기며 "이 데이터 분석해줘"라고 합니다. AI가 멋진 차트와 통계를 냅니다. 팀 회의에서 "그래서 우리가 뭘 해야 하죠?"라는 질문에 대답을 못 합니다.

**After**: AI에게 "최근 30일 유료 구독자의 매출 감소 원인을 채널별로 분석해줘. 이탈률이 5% 이상 높은 세그먼트를 찾아줘"라고 요청합니다. 결과물이 즉시 의사결정으로 연결됩니다.

## 바이브코딩할 때 자주 하는 실수
| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| 문제 정의 없이 "분석해줘" 요청 | AI가 뭘 분석해야 할지 모름 | 지표, 기간, 대상 집단을 먼저 명시 |
| AI 결과를 그대로 팀에 공유 | 결과가 비즈니스 질문과 무관할 수 있음 | 결과를 검토하고 의사결정 문장으로 변환 |
| 역할 구분 없이 모든 걸 요청 | AI가 분석가 역할인지 엔지니어 역할인지 혼동 | 어떤 종류의 작업인지 먼저 구분 |
| EDA 없이 바로 모델링 요청 | 데이터 품질 문제가 숨어 있을 수 있음 | 먼저 데이터 탐색 단계 거치기 |

## AI에게 데이터 분석 요청하는 팁

AI에게 데이터 분석을 요청할 때 이 구조로 프롬프트를 작성하면 결과 품질이 크게 올라갑니다:

1. **분석 목적**: "이탈 감소를 위해"
2. **구체적 지표**: "30일 이탈률을"
3. **대상 집단**: "유료 구독자 중"
4. **비교 기준**: "전월 대비"
5. **기대 산출물**: "원인 세그먼트와 권장 행동으로"

예: "유료 구독자 중 최근 30일 이탈률이 전월 대비 5% 이상 높은 세그먼트를 채널별로 분석하고, 이탈 감소를 위한 행동 권장사항을 제시해줘"

## 운영 체크리스트
- [ ] 데이터 분석가, 데이터 사이언티스트, 엔지니어의 차이를 설명할 수 있습니다
- [ ] AI에게 분석을 요청할 때 지표, 기간, 대상 집단을 명시합니다
- [ ] AI가 낸 결과를 비즈니스 의사결정으로 연결할 수 있습니다
- [ ] 문제 정의 → 데이터 → 결정으로 이어지는 흐름을 이해합니다
- [ ] EDA가 모델링보다 먼저 필요한 이유를 설명할 수 있습니다

## 처음 질문으로 돌아가기

"AI에게 데이터 분석 맡기기 전에 왜 데이터 사이언스를 알아야 하나요?"

데이터 사이언스 흐름을 모르면 AI에게 정확한 질문을 던질 수 없고, AI가 낸 결과가 맞는지 틀린지도 모릅니다. 문제 정의 → 데이터 수집 → 정제 → EDA → 모델링 → 평가 → 의사결정이라는 흐름을 알아야 각 단계에서 AI에게 무엇을 요청해야 하는지 알 수 있습니다.

## 정리

데이터 사이언스는 AI가 대신 해주는 것이 아니라, AI와 함께 하는 문제 해결 과정입니다. 각 역할의 구분을 알고, CRISP-DM 흐름을 이해하고, 문제를 데이터 질문으로 바꾸는 능력이 있어야 바이브코딩으로 실제 가치를 만들 수 있습니다. 다음 글에서는 막연한 비즈니스 문제를 AI가 실제로 분석할 수 있는 데이터 질문으로 바꾸는 방법을 다룹니다.
