# 바이브코딩을 위한 DevOps 기초 (10/10): 운영 가능한 DevOps 흐름

이 글은 바이브코딩을 위한 DevOps 기초 시리즈의 마지막 글입니다.

지금까지 9개의 글에서 CI, CD, 환경 설정, IaC, 컨테이너, 모니터링, 로그, 장애 대응을 각각 다뤘습니다. 각 도구가 무엇인지는 알겠는데, 이것들이 실제로 어떻게 연결되는지 아직 그림이 안 그려지는 경우가 많습니다.

도구를 하나씩 붙이는 것만으로는 DevOps가 완성되지 않습니다. CI가 있는데 배포는 여전히 수동이거나, 배포는 자동인데 모니터링이 없거나, 모니터링은 있는데 장애에서 배우는 포스트모템이 없으면 흐름이 끊깁니다.

바이브코딩으로 코드를 빠르게 만들 수 있게 된 지금, 더 중요해진 것은 그 코드가 실제로 사용자에게 가치를 만드는 전체 흐름입니다. PR → CI → 배포 → 모니터링 → 알림 → 장애 대응 → 포스트모템 → 코드 개선. 이 루프가 빠르게 돌아야 팀이 배우고 서비스가 좋아집니다.

> 측정되지 않는 것은 개선되지 않습니다.

## 이 글에서 다룰 문제
- CI, CD, 모니터링, 장애 대응이 각각 있는데도 팀 속도가 느린 이유는 무엇일까요?
- DORA 4지표는 무엇을 측정하며 왜 함께 봐야 할까요?
- 바이브코딩 환경에서 DevOps 흐름을 어떻게 시작해야 할까요?
- 작은 팀이 거대한 DevOps 플랫폼 없이 시작하는 방법은?
- DevOps를 학습 루프로 만드는 최소한의 의식(ritual)은 무엇일까요?

## DORA 4지표: DevOps 성숙도를 측정하는 기준

Google 연구에서 나온 DORA 4지표는 속도와 안정성을 함께 측정합니다. 배포 빈도가 높으면서 실패율이 낮은 팀이 가장 좋은 성과를 냅니다.

| 지표 | 측정 항목 | Elite 수준 |
|---|---|---|
| Deploy Frequency | 얼마나 자주 배포하는가 | 하루 여러 번 |
| Lead Time for Changes | 코드가 production까지 가는 시간 | 1시간 미만 |
| Change Failure Rate | 배포가 장애를 일으킨 비율 | 15% 미만 |
| MTTR | 장애 복구까지 걸린 평균 시간 | 1시간 미만 |

이 네 지표를 처음부터 자동 수집할 필요는 없습니다. 손으로 주간 단위로 기록하는 것만으로도 팀의 현재 상태를 파악하고 개선 방향을 잡을 수 있습니다.

## 전체 DevOps 흐름을 한 장으로

```text
[코드 작성]
    → PR 생성
    → CI 실행 (lint, test, build, scan)
    → 코드 리뷰
    → main 머지
    → 스테이징 자동 배포
    → 스모크 테스트
    → (승인) → 프로덕션 배포
    → 모니터링 (RED 지표 관찰)
    → 알림 → on-call → 런북 → 복구
    → 포스트모템 → 액션 아이템
    → [코드 작성]  ← 루프 완성
```

이 루프 어딘가가 끊기면 속도나 안정성이 떨어집니다. AI가 코드를 빠르게 만들어줘도 루프가 없으면 팀이 배우지 못합니다.

## Before / After

**Before**: "CI는 있고 배포도 자동화됐는데 왜 자꾸 같은 문제가 반복되는지 모르겠다. 포스트모템은 한 번도 안 해봤다. DORA 지표는 측정 안 한다."

**After**: "매주 30분 배포 리뷰를 한다. 지난 주 배포 수, 에러 건수, 복구 시간을 같이 본다. 월간 포스트모템 읽기를 통해 반복 패턴을 찾아 시스템을 개선한다. 팀이 느리게 가는 원인이 숫자로 보인다."

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| 도구부터 도입하는 실수 | 흐름이 없으면 도구는 연결되지 않은 섬이 됨 | 현재 흐름의 병목을 먼저 파악하고 도구 선택 |
| DORA 지표 중 하나만 보는 실수 | 배포 빈도만 높이고 실패율도 같이 높아지면 의미 없음 | 네 지표를 함께 봐야 속도와 안정성 균형 확인 |
| AI가 DevOps도 해결해준다고 생각하는 실수 | AI는 개별 도구 설정은 도와줄 수 있지만 팀 운영 리듬은 사람이 만들어야 함 | AI는 도구 구성 보조로, 흐름 설계는 팀이 직접 |
| 포스트모템을 안 하는 실수 | 같은 장애가 반복되고 팀이 학습하지 못함 | SEV1/2 장애는 의무적으로 포스트모템 작성 |
| 측정 없이 개선을 주장하는 실수 | "더 빨라졌다"를 증명할 수 없음 | DORA 지표 최소한 손으로라도 주간 기록 |

## AI에게 DevOps 흐름 관련 질문하는 팁

DevOps 흐름 전체를 AI에게 물어볼 때 이 형식을 쓰면 더 유용한 답을 받습니다:

```
팀 규모: [1인 / 2-5명 / 10명 이상]
현재 상태: [CI만 있음 / CD 없음 / 모니터링 없음]
목표: [배포 자동화 / 장애 대응 체계 / DORA 측정]
기간: [30일 / 90일]
가장 큰 문제: [배포가 느림 / 장애 복구가 오래 걸림 / 같은 문제 반복]
```

"DevOps를 처음 도입하는 5명 팀을 위한 30일 실행 계획을 만들어줘. 현재는 CI는 있지만 CD는 없고, 모니터링도 없다. 이 기간 안에 스테이징 자동 배포, 기본 모니터링, 런북 3개를 만들고 싶다."처럼 구체적으로 요청하세요.

## 운영 체크리스트

- [ ] PR부터 포스트모템까지 전체 흐름이 한 그림으로 정리되어 있습니다
- [ ] DORA 4지표를 주간 단위로 확인합니다
- [ ] 주간 배포 리뷰 미팅(30분)이 정기적으로 열립니다
- [ ] 월간 포스트모템 읽기가 팀 캘린더에 잡혀 있습니다
- [ ] DevOps 흐름 개선을 책임지는 담당자가 있습니다

## 처음 질문으로 돌아가기

"바이브코딩으로 코드를 빠르게 만들 수 있게 됐는데, 왜 DevOps를 배워야 하나요?"

코드를 만드는 속도가 빨라졌다는 것은 배포와 운영의 중요성이 더 커졌다는 뜻입니다. AI가 하루에 10개의 기능을 만들어줄 수 있다면, 그 10개를 안전하게 배포하고 운영하는 흐름이 없으면 오히려 속도가 발목을 잡습니다. DevOps는 AI가 만든 코드를 실제 가치로 연결하는 인프라입니다.

## 정리

DevOps는 도구 목록이 아니라 학습 루프입니다. 코드를 만들고, 검증하고, 배포하고, 관찰하고, 장애에서 배우고, 다시 코드를 개선하는 이 루프가 빠르게 돌아야 팀이 성장합니다. 바이브코딩이 코드 생산 속도를 높여줬다면, DevOps는 그 코드가 실제 가치를 만드는 속도를 높여줍니다.
