# 바이브코딩을 위한 DevOps 기초 (9/10): 장애 대응과 on-call

이 글은 바이브코딩을 위한 DevOps 기초 시리즈의 9번째 글입니다.

AI 코딩 도구로 빠르게 기능을 만들고 배포했습니다. 그런데 새벽 2시에 서비스가 다운됐다는 알림이 옵니다. 무엇부터 해야 할까요? 코드를 다시 봐야 할까요, 서버 상태를 봐야 할까요, 팀원에게 연락해야 할까요? 절차가 없으면 이 순간에 판단력이 흐려집니다.

장애는 항상 생깁니다. 중요한 것은 "장애가 생기느냐"가 아니라 "얼마나 빨리 복구하고, 같은 장애가 다시 생기지 않게 무엇을 바꾸느냐"입니다. AI가 짠 코드도, 직접 짠 코드도 운영 환경에서는 예상치 못한 방식으로 실패합니다.

장애 대응의 핵심은 영웅적인 개인이 아닙니다. 팀이 같은 절차를 따르는 것입니다. 역할이 정해져 있고, 런북이 있고, 포스트모템으로 학습이 남는 구조가 있어야 합니다. 이 구조 없이는 같은 장애가 다른 이름으로 반복됩니다.

> 장애 대응 시스템은 기억력을 프로세스로 대체합니다.

---

## 이 글에서 다룰 문제
- 새벽 2시에 알림이 울리면 무엇부터 해야 할까요?
- SEV(장애 심각도) 정의는 왜 팀 전체의 대응 속도를 결정할까요?
- on-call은 일정표가 아니라 왜 운영 설계인가요?
- AI가 만든 코드로 생긴 장애에서 무엇을 배울 수 있을까요?
- blameless 포스트모템은 왜 팀 문화의 핵심일까요?

## 장애 심각도 정의 (SEV)

같은 에러도 상황에 따라 심각도가 다릅니다. SEV를 미리 정의해야 팀이 같은 기준으로 대응합니다.

| 심각도 | 기준 | 목표 응답 시간 |
|---|---|---|
| SEV1 | 전체 서비스 중단, 결제 불가 | 즉시 (5분 이내) |
| SEV2 | 핵심 기능 저하, 일부 사용자 영향 | 30분 이내 |
| SEV3 | 비핵심 기능 문제, 우회 가능 | 영업 시간 내 |
| SEV4 | 경미한 버그, 사용자 영향 없음 | 백로그로 처리 |

팀마다 숫자 기준은 다를 수 있지만, 팀이 같은 언어로 상황을 설명할 수 있어야 합니다.

## 장애 발생 후 첫 15분 대응 순서

```text
0-3분:  알림 확인 → SEV 판정 → incident 채널 개설
3-5분:  on-call이 런북 열기 → 최근 배포/변경 확인
5-8분:  사용자 영향 범위와 우회 가능성 확인
8-12분: IC(incident commander) 지정 → 역할 분리
12-15분: 완화 조치 실행 또는 에스컬레이션
```

이 순서에서 중요한 것: 기술 조사와 커뮤니케이션을 동시에 같은 사람이 하지 않는 것입니다. 복구하는 사람과 상태를 정리하는 사람이 분리될 때 더 빠르게 복구됩니다.

## Before / After

**Before**: "장애 알림이 오면 Slack에서 '이거 누가 보고 있나요?'가 먼저 나온다. 여러 사람이 동시에 손을 대다가 오히려 문제를 더 키운 적도 있다. 복구 후에는 지쳐서 아무것도 기록 안 하고 넘어갔다."

**After**: "SEV 기준이 있어서 첫 판단이 빠르다. on-call이 런북을 보고 첫 조치를 하고, IC가 팀 전체를 조율한다. 복구 후에는 blameless 포스트모템으로 무엇을 바꿀지 액션 아이템을 뽑는다."

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| 런북을 깊은 위키에 묻어두는 실수 | 새벽 2시에 못 찾으면 없는 것과 같음 | 알림에 런북 URL 직접 포함 |
| 포스트모템에 사람 잘못을 적는 실수 | 신뢰가 무너지면 다음에 솔직한 포스트모템이 안 나옴 | blameless 원칙: 시스템과 절차를 고침 |
| 장애 후 액션 아이템을 만들지 않는 실수 | 같은 장애가 다른 이름으로 반복됨 | owner와 기한이 있는 액션 아이템 생성 |
| 혼자 on-call을 맡는 실수 | 피로 누적으로 장기적으로 대응 품질 하락 | primary/secondary 로테이션 설계 |
| AI가 만든 코드의 장애를 AI 탓으로 돌리는 실수 | 실제 문제(테스트 부족, 검증 없는 배포)를 못 고침 | AI 생성 코드도 같은 검증 프로세스 적용 |

## AI에게 장애 대응 관련 질문하는 팁

런북이나 포스트모템 템플릿을 AI에게 요청할 때 이 정보를 포함하면 실용적인 결과를 받습니다:

```
서비스 종류: [API 서버, 데이터 파이프라인 등]
알림 종류: [에러율 급증, 응답 시간 초과, 서버 다운]
팀 규모: [1인 / 소규모 팀 / 대규모 팀]
SEV 기준: [이미 있음 / 새로 만들어야 함]
포스트모템 포함 항목: [타임라인, 근본 원인, 액션 아이템]
```

AI가 만든 런북 템플릿을 받았다면 반드시 확인할 것: 진단 단계가 실행 가능한 명령으로 되어 있는지, 롤백 명령이 포함되어 있는지, 에스컬레이션 경로가 명시되어 있는지.

## 운영 체크리스트

- [ ] SEV 기준이 팀 문서에 정의되어 있습니다
- [ ] 주요 장애 시나리오별 런북이 있습니다
- [ ] 알림에서 런북으로 바로 이동할 수 있습니다
- [ ] on-call 로테이션이 설정되어 있습니다
- [ ] 포스트모템 템플릿이 있고 SEV1/2에는 의무적으로 작성합니다

## 처음 질문으로 돌아가기

"AI가 짜준 코드니까 장애가 나면 AI가 고쳐주면 되지 않나요?"

AI는 코드를 빠르게 만들어줄 수 있지만, 새벽 2시 장애 대응을 대신해줄 수 없습니다. 장애 중에는 무엇이 문제인지, 어떤 순서로 대응해야 하는지, 어디에 알려야 하는지를 사람이 판단해야 합니다. 절차가 없으면 아무리 잘 만든 시스템도 장애 앞에서 흔들립니다. 장애 대응 체계는 코드보다 먼저 만들어야 합니다.

## 정리

장애 대응은 기술력보다 절차와 팀 구조가 결정합니다. SEV 정의, 런북, on-call 로테이션, blameless 포스트모템이 있는 팀은 같은 장애가 반복되지 않습니다. 다음 글에서는 CI부터 포스트모템까지 전체 DevOps 흐름을 하나로 연결하는 방법을 다룹니다.
