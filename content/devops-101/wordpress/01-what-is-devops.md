# 바이브코딩을 위한 DevOps 기초 (1/10): DevOps란 무엇인가?

이 글은 바이브코딩을 위한 DevOps 기초 시리즈의 1번째 글입니다.

AI 코딩 도구로 코드를 빠르게 만들 수 있게 됐습니다. 그런데 만들어진 코드를 실제 서버에 올리고, 사용자들이 접속하고, 장애가 나면 고치는 과정은 여전히 복잡합니다. 바이브코딩 시대에 AI가 코드를 쓴다면, 그 코드를 안전하게 배포하고 운영하는 흐름을 이해하는 것은 개발자의 몫입니다.

많은 사람들이 코드를 짜는 법은 AI에게 배웠지만, "이 코드를 어떻게 서버에 올리지?", "배포가 잘못됐을 때 어떻게 되돌리지?", "서비스가 느려지면 어디를 봐야 하지?"라는 질문 앞에서 멈춥니다. DevOps는 이 질문들에 대한 체계적인 답입니다.

바이브코딩으로 만든 프로젝트가 "내 컴퓨터에서만 되는 상태"에서 벗어나려면 CI/CD, 컨테이너, 모니터링 같은 DevOps 개념을 이해해야 합니다. AI에게 "배포 스크립트 짜줘"라고 요청해도, 어떤 배포 전략을 원하는지 모르면 맥락 없는 코드만 받게 됩니다.

> AI가 코드를 만들어도, 그 코드가 실제로 동작하는 환경을 설계하는 것은 사람의 몫입니다.

---

## 이 글에서 다룰 문제
- DevOps는 무엇이며, 왜 개발과 운영을 따로 보는 방식이 한계에 부딪혔을까요?
- DevOps를 도구가 아니라 문화라고 말하는 이유는 무엇일까요?
- CI, CD, SRE 같은 용어는 DevOps 흐름 안에서 어떤 역할을 할까요?
- 바이브코딩 환경에서 DevOps를 모르면 어떤 문제가 생길까요?
- 처음 시작하는 사람이 가장 자주 놓치는 DevOps의 핵심은 무엇일까요?

## 개발과 운영이 왜 따로 놀면 안 되는가

소프트웨어는 작성만으로 가치를 만들지 않습니다. 사용자에게 도달하려면 빌드되고, 배포되고, 운영되어야 합니다. 개발팀이 기능을 완성해 넘기면 운영팀이 서버에 올리는 구조에서는 두 팀이 서로 다른 목표로 움직입니다. 개발팀은 새 기능을 빠르게, 운영팀은 서비스를 안정적으로 유지하려 합니다.

이 두 목표가 충돌하면 배포가 두렵고, 배포가 두려우면 더 드물어지고, 드물어지면 한 번에 변경이 많아져 더 위험해집니다. DevOps는 이 악순환을 끊는 방법입니다.

| 비교 기준 | 전통 방식 | DevOps |
|---|---|---|
| 배포 주기 | 분기별 대규모 배포 | 하루 수십 회 작은 배포 |
| 책임 경계 | 개발 완료 후 운영팀에 이관 | 함께 전체 라이프사이클 책임 |
| 피드백 루프 | 장애 → 분석 → 수정 (수주) | 장애 → 롤백 → 수정 (수분) |
| 도구 | 수동 스크립트, 콘솔 클릭 | CI/CD, IaC, 모니터링 자동화 |

## CALMS: DevOps를 문화로 이해하는 프레임

DevOps는 Jenkins나 GitHub Actions 같은 도구가 아닙니다. Culture, Automation, Lean, Measurement, Sharing 다섯 축으로 이루어진 문화 전환입니다.

**Culture(문화)**: 개발과 운영이 같은 목표를 보고 함께 책임집니다.
**Automation(자동화)**: 반복 작업을 코드로 고정해 사람 실수를 줄입니다.
**Lean(린)**: 작게 자주 배포해 위험을 줄이고 학습을 빠르게 합니다.
**Measurement(측정)**: 배포 빈도, 복구 시간 같은 지표로 팀 상태를 봅니다.
**Sharing(공유)**: 장애 포스트모템, 런북으로 지식을 팀 자산으로 만듭니다.

## Before / After

**Before**: "코드는 완성됐는데 배포는 운영팀이 알아서 하겠지. 서버에서 에러가 나면 운영팀이 보겠지."

**After**: "PR이 머지되면 CI가 자동으로 테스트하고, 통과하면 스테이징에 자동 배포, 확인 후 프로덕션까지 자동으로 올라간다. 장애 알림도 개발팀이 받는다."

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| AI에게 "배포해줘"라고만 요청 | 어떤 환경에 어떤 방식으로 배포할지 맥락이 없어 쓸 수 없는 코드가 나옴 | 배포 전략, 대상 환경, 롤백 조건을 먼저 정하고 요청 |
| 도구를 먼저 도입하는 실수 | Jenkins, Kubernetes를 도입해도 흐름이 없으면 복잡도만 늘어남 | 현재 흐름의 병목을 먼저 파악하고 도구 선택 |
| 운영은 나중에 생각하는 실수 | 서비스가 커진 뒤에 모니터링, 배포 자동화를 추가하면 비용이 10배 | 첫 배포부터 헬스체크, 간단한 CI를 붙이는 습관 |
| DevOps를 팀 이름으로 이해하는 실수 | DevOps팀이 생겨도 문화 없이 도구만 쓰면 효과 없음 | DevOps는 협업 방식이지 조직 라벨이 아님 |
| 수동 배포를 계속 하는 실수 | 수동 배포는 매번 다른 결과를 낳고 사람 기억에 의존함 | 주요 배포 단계를 CI/CD로 코드화 |

## AI에게 DevOps 관련 질문하는 팁

DevOps 관련 작업을 AI에게 요청할 때 이 형식을 쓰면 효과적입니다:

```
작업 목적: [무엇을 자동화하거나 개선하고 싶은지]
현재 상황: [어떤 도구를 쓰고 있는지, 어떤 환경인지]
원하는 결과: [배포 방식, 검증 조건, 롤백 방법]
제약 조건: [클라우드 환경, 팀 규모, 예산]
```

예: "GitHub Actions로 Python FastAPI 앱을 AWS EC2에 배포하는 CI/CD 파이프라인을 만들고 싶습니다. 현재는 수동으로 SSH 접속해서 배포합니다. main 브랜치에 머지되면 자동으로 스테이징 배포 후 승인 시 프로덕션으로 올라가는 구조를 원합니다."

## 운영 체크리스트

- [ ] 모든 PR에서 자동 테스트가 실행됩니다
- [ ] main 머지 후 자동으로 스테이징 배포됩니다
- [ ] 프로덕션 배포 전 스모크 테스트가 있습니다
- [ ] 기본 헬스체크 엔드포인트가 있습니다
- [ ] 롤백 방법이 팀 문서에 적혀 있습니다

## 처음 질문으로 돌아가기

"AI가 코드를 만들어 주는데 DevOps를 왜 알아야 하나요?"

AI가 짜준 코드가 실제 서비스로 동작하려면 빌드, 배포, 모니터링, 장애 대응이라는 전체 흐름이 필요합니다. 이 흐름의 각 단계에서 어떤 선택을 해야 하는지, AI에게 무엇을 요청해야 하는지 알기 위해서는 DevOps 기초 개념이 반드시 있어야 합니다. 코드는 AI가 짜도, 시스템을 설계하는 것은 사람의 역할입니다.

## 정리

DevOps는 빠른 배포와 안정적인 운영이 충돌하지 않는 구조를 만드는 방법입니다. 바이브코딩으로 코드 생산 속도가 빨라질수록, 그 코드를 안전하게 배포하고 운영하는 능력이 더 중요해집니다. 다음 글에서는 코드가 자동으로 검증되는 CI 파이프라인을 다룹니다.
