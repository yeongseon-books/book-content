# Software Design 101 (1/10): 소프트웨어 설계란 무엇인가?

코드 한 줄은 바로 읽히는데, 기능 하나를 더하려는 순간 수정 범위가 예상을 훨씬 넘는 프로젝트가 있습니다. 반대로 코드가 아주 화려하지 않아도 변경이 차분하게 흘러가는 프로젝트도 있습니다. 두 코드베이스의 차이는 문법보다 설계에서 먼저 벌어집니다.

이 글은 Software Design 101 시리즈의 첫 번째 글입니다.

여기서는 소프트웨어 설계를 "예쁘게 코드를 쓰는 습관"이 아니라, 다음 변경의 비용을 좌우하는 결정의 묶음으로 정리합니다. 좋은 설계가 무엇인지, 나쁜 설계는 어떤 증상으로 드러나는지, 왜 설계가 시간이 갈수록 더 큰 차이를 만드는지도 함께 보겠습니다.

*Software Design 101 1장 흐름 개요*

> 설계는 코드를 예쁘게 쓰는 습관이 아니라 다음 변경의 비용을 미리 정하는 결정의 묶음입니다 — 같은 기능을 만든 두 코드베이스의 차이는 문법이 아니라, 변경이 들어왔을 때 손대야 하는 파일 수와 두려움의 크기에서 드러납니다.

## 이 글에서 다룰 문제

- 좋은 코딩과 좋은 설계는 무엇이 다를까요?
- 설계 품질은 어떤 신호로 판단할 수 있을까요?
- 설계 실패는 코드베이스에서 어떤 증상으로 드러날까요?
- 이 설계 원칙을 무시하면 코드베이스가 어떻게 변질될까요?
- 팀 규모가 커질 때 이 원칙의 중요성은 어떻게 달라질까요?

설계는 화면에 바로 드러나지 않습니다. 하지만 다음 요구사항이 들어오는 순간 바로 티가 납니다. 결제 수단 하나를 추가하려는데 파일 열두 개를 수정해야 한다면, 그 비용은 기능의 복잡도보다 설계의 구조에서 나옵니다.

처음 출시만 보면 설계는 사치처럼 보일 수 있습니다. 그러나 운영이 길어질수록 코드는 계속 바뀌고, 설계가 좋지 않은 시스템은 같은 속도로 기능을 추가해도 점점 더 비싸게 움직입니다. 그래서 설계 부채는 이자가 붙는다고 말합니다.

## 전체 그림

요구사항은 설계 결정으로 바뀌고, 설계 결정은 코드로 굳어집니다. 그리고 그 코드는 다음 요구사항이 들어왔을 때의 변경 비용을 결정합니다. 이 순환을 이해하면 설계를 단발성 산출물이 아니라 계속 누적되는 비용 구조로 보게 됩니다.

```text
요구사항
   ↓
설계 결정 (모듈 경계, 책임, 의존성 방향)
   ↓
코드로 굳어짐
   ↓
다음 변경의 비용을 결정
   ↓ (다시 요구사항으로)
```

## 기본 용어

- <strong>소프트웨어 설계</strong>: 모듈, 책임, 의존성에 관해 내리는 결정의 묶음입니다.
- <strong>아키텍처</strong>: 설계 결정 가운데 가장 큰 단위의 구조를 가리킵니다.
- <strong>결합도</strong>: 모듈끼리 얼마나 강하게 얽혀 있는지를 뜻합니다.
- <strong>응집도</strong>: 한 모듈 안의 요소들이 얼마나 같은 목적을 향하는지를 뜻합니다.
- <strong>변경 비용</strong>: 다음 수정을 넣는 데 필요한 시간, 위험, 검증 범위를 뜻합니다.

## 변경 전과 변경 후

**변경 전 — 설계 없이 빠르게 작성한 코드**

```python
# bad_design.py
# 결제, 저장, 알림이 모두 한 함수에 섞여 있음
def process_payment(user_id, amount, method):
    if method == "card":
        import stripe
        stripe.Charge.create(amount=amount, currency="krw")
    elif method == "bank":
        import bank_sdk
        bank_sdk.transfer(user_id, amount)
    # 저장
    import psycopg2
    conn = psycopg2.connect(...)
    conn.execute("INSERT INTO payments ...")
    # 알림
    import smtplib
    smtplib.SMTP("smtp.example.com").sendmail(...)
```

**변경 후 — 책임을 분리한 코드**

```python
# good_design.py
# 각 책임이 독립된 모듈에 있음
class PaymentGateway:
    def charge(self, amount: int) -> str: ...

class PaymentRepo:
    def save(self, payment: Payment) -> None: ...

class Notifier:
    def send(self, user_id: str, msg: str) -> None: ...

def process_payment(
    gateway: PaymentGateway,
    repo: PaymentRepo,
    notifier: Notifier,
    user_id: str,
    amount: int,
) -> None:
    tx_id = gateway.charge(amount)
    repo.save(Payment(user_id=user_id, tx_id=tx_id, amount=amount))
    notifier.send(user_id, f"결제 완료: {amount}원")
```

결제 수단을 추가할 때 아래 구조에서는 `PaymentGateway`를 구현하는 새 클래스만 추가하면 됩니다. `process_payment` 함수는 건드리지 않아도 됩니다.

설계는 당장의 속도보다 누적 비용을 다루는 일입니다. 처음 며칠은 차이가 작아 보여도, 변경이 다섯 번 열 번 쌓이면 격차가 급격히 커집니다.

## 좋은 설계를 가늠하는 다섯 가지 신호

### 1단계 — 변경 시뮬레이션

```python
# 1_change_sim.py
# "결제 수단 추가" 시 몇 개 파일을 건드려야 할까요?
files_touched = ["payment.py"]  # 파일 하나면 강한 신호입니다.
```

새 결제 수단을 넣는데 파일 하나만 수정하면 꽤 좋은 출발입니다. 같은 작업에 라우터, 서비스, 저장소, 템플릿, 테스트 유틸까지 함께 수정해야 한다면 설계가 변경을 넓게 퍼뜨리고 있다고 볼 수 있습니다.

### 2단계 — 의존성 그래프

```python
# 2_deps.py
# A -> B -> C (한 방향) 구조는 괜찮습니다.
# A <-> B (cycle) 구조는 design smell입니다.
```

의존성 순환은 설계 냄새 가운데 가장 값싼 경고입니다. 두 모듈이 서로를 알아야만 유지되는 구조는 시간이 갈수록 더 단단해지고, 테스트와 리팩터링을 어렵게 만듭니다.

### 3단계 — 모듈 책임

```python
# 3_responsibility.py
# 모듈을 한 문장으로 설명하지 못하면 책임 경계가 흐릿한 것입니다.
PAYMENT = "결제 도메인 — 외부 게이트웨이를 호출하고 도메인 규칙을 적용합니다"
```

모듈을 한 문장으로 설명할 수 없다면, 그 모듈은 이미 여러 역할을 품고 있을 가능성이 큽니다. 이름과 설명이 어긋나면 응집도도 함께 낮아집니다.

### 4단계 — 테스트 가능성

```python
# 4_testable.py
# IO 없이 domain 모듈만 단독으로 테스트할 수 있나요?
def can_test_alone(module):
    return module.no_io and module.no_globals
```

설계는 테스트에서 거짓말을 덜 합니다. 도메인 모듈을 데이터베이스나 네트워크 없이 단독 검증할 수 있다면, 책임 분리와 의존성 방향이 비교적 잘 잡혀 있을 가능성이 높습니다.

### 5단계 — 온보딩 곡선

```text
# 5_onboard.txt
Can a new teammate understand a module in 30 minutes?
```

설계는 사람을 위한 일입니다. 새 팀원이 모듈 하나를 이해하는 데 한참 걸린다면 코드 양보다 구조가 더 큰 문제일 수 있습니다. 온보딩 속도는 설계 품질을 꽤 정직하게 보여 줍니다.

## 설계 비용 누적 시각화

좋은 설계와 나쁜 설계의 비용 차이는 시간이 지날수록 벌어집니다.

```text
변경 횟수  | 나쁜 설계 누적 비용 | 좋은 설계 누적 비용
-----------|---------------------|--------------------
1회        | 1일                 | 1.5일  (초기 투자)
5회        | 8일                 | 5일
10회       | 20일                | 8일
20회       | 50일                | 13일
```

초기에는 나쁜 설계가 빠르지만, 변경이 누적될수록 좋은 설계의 이점이 급격히 커집니다. 이것이 "설계 부채에 이자가 붙는다"는 말의 의미입니다.

## 빠르게 검증해 보기

설계를 논의할 때는 감으로 말하기보다, 같은 변경을 실제 코드베이스에 대입해 보는 편이 훨씬 정확합니다. 아래처럼 가장 자주 들어오는 요구사항 하나를 고른 뒤, 수정 파일 수와 의존성 방향을 함께 적어 보세요.

```text
변경 시나리오: 결제 수단 추가
수정 파일 수: 1개 / 4개 / 9개
순환 의존: 없음 / 있음
테스트 범위: 도메인만 / 도메인+DB / 전체 회귀
```

**Expected output:** 같은 기능을 넣을 때 수정 파일 수가 적고, 순환 의존이 없고, 테스트 범위를 좁게 유지할수록 설계 품질이 더 좋다는 근거가 보입니다.

이 간단한 표만으로도 "이 코드는 읽기 좋은가?"보다 "이 구조는 다음 변경을 얼마나 비싸게 만드는가?"라는 질문으로 시선을 옮길 수 있습니다.

## 실패 신호와 먼저 볼 것

| 실패 신호 | 먼저 볼 것 |
| --- | --- |
| 기능 하나를 넣는데 여러 폴더를 모두 연다 | 변경이 어느 모듈 경계에서 새고 있는지 확인합니다 |
| 작은 수정인데 통합 테스트만 믿어야 한다 | 도메인 규칙이 IO와 붙어 있지 않은지 봅니다 |
| 새 팀원이 구조 설명을 오래 못 한다 | 모듈 책임을 한 문장으로 요약해 봅니다 |

실패 신호를 빠르게 읽는 습관이 생기면, 설계는 추상적인 미학이 아니라 운영 비용을 낮추는 진단 도구가 됩니다.

## 자주 하는 실수

| 실수 | 왜 문제인가 | 올바른 접근 |
| --- | --- | --- |
| "지금 돌아가면 됐다"는 사고 | 변경 1회는 괜찮지만 10회가 되면 전체가 경직 | 처음부터 책임 경계를 명확히 구분 |
| 폴더 이름만 나누고 책임은 그대로 | 구조는 화려하지만 실제 결합도는 그대로 | 폴더가 아니라 변경 이유를 기준으로 분리 |
| 리팩터링 = 설계라고 착각 | 리팩터링은 수단, 설계는 방향 | 무엇을 위해 구조를 바꾸는지 먼저 정의 |
| 모든 것을 추상화 | 불필요한 간접 계층이 생겨 이해 비용 증가 | 실제로 바뀔 가능성이 높은 것만 추상화 |
| ADR 없이 설계 결정 | 몇 달 뒤 "왜 이렇게 됐는지" 아무도 모름 | 중요한 결정마다 짧은 ADR을 남김 |

## 이 코드에서 먼저 볼 점

- 변경 범위, 의존성, 책임, 테스트 가능성을 같이 봐야 설계가 보입니다.
- 개별 함수의 아름다움보다 다음 수정의 파급 범위가 더 중요한 판단 기준입니다.
- 새 팀원이 빨리 읽을 수 있는 구조는 대개 변경에도 강합니다.

## 자주 헷갈리는 지점

많은 팀이 리팩터링과 설계를 같은 말처럼 씁니다. 둘은 겹치지만 같지는 않습니다. 리팩터링은 구조를 바꾸는 행위이고, 설계는 그 구조가 어떤 방향을 가져야 하는지에 관한 판단입니다.

또 하나 흔한 오해는 "코드가 깔끔하면 설계도 좋다"는 생각입니다. 함수 이름이 좋고 포매팅이 잘 되어 있어도, 결제 로직 하나를 바꾸기 위해 시스템 전체를 건드려야 한다면 설계는 좋은 편이 아닙니다. 읽기 좋은 코드와 바꾸기 좋은 구조는 서로 도와주지만, 동일한 목표는 아닙니다.

## 설계 수준별 판단 기준

설계 품질을 논의할 때 어느 수준의 문제를 보는지 구분하면 대화가 더 명확해집니다.

```text
함수 수준:  이름, 인자 수, 추상화 높이
모듈 수준:  책임 범위, 공개 API 크기, 내부 응집도
패키지 수준: 의존성 방향, 순환 여부, 경계 명확성
시스템 수준: 서비스 분리, 통신 방식, 장애 격리
```

코드 리뷰에서 함수 수준 피드백과 모듈 수준 피드백을 섞어 쓰면 논의가 어수선해집니다. 어느 수준을 보고 있는지 먼저 맞추는 것이 좋습니다.

## 실무에서는 이렇게 본다

강한 팀은 설계를 추상적인 취향 문제가 아니라 비용 문제로 다룹니다. 어떤 변경이 몇 개 파일로 퍼졌는지, 어떤 모듈에 순환 의존이 생겼는지, 중요한 결정이 문서로 남았는지를 계속 확인합니다.

이때 ADR(Architecture Decision Record)이 큰 역할을 합니다. 설계 결정과 이유를 함께 남겨 두면 새 팀원이 같은 논쟁을 반복하지 않아도 되고, 몇 달 뒤 왜 이런 구조를 택했는지도 다시 추적할 수 있습니다.

```text
# ADR 예시 템플릿
제목: 결제 모듈을 도메인에서 분리
날짜: 2026-05-01
상태: 승인됨
맥락: 결제 수단이 늘어날수록 도메인 코드 수정 빈도가 높아짐
결정: PaymentGateway 인터페이스를 도메인에 두고 구현은 인프라에 위치시킴
결과: 도메인 테스트가 DB 없이도 가능해짐, 결제 벤더 교체가 어댑터 하나로 끝남
```

## 설계 결정 트리

어떤 문제가 보일 때 어느 방향으로 생각을 이어가야 할지 빠르게 정리한 참고 경로입니다.

```text
새 기능을 추가하려 할 때

파일을 몇 개 열어야 하는가?
    ├── 1~2개 → 설계가 변경을 잘 가두고 있음
    ├── 3~5개 → 경계를 다시 점검할 타이밍
    └── 6개 이상 → 결합도가 높음, 모듈 경계 재설계 필요

수정한 코드를 어떻게 검증할 수 있는가?
    ├── 도메인만 단독 테스트 가능 → 좋은 신호
    ├── DB 연결 없이는 안 됨 → 도메인·인프라 결합 의심
    └── 전체 회귀 테스트 필수 → 결합도 매우 높음

새 팀원이 이 모듈을 이해하는 데 얼마나 걸리는가?
    ├── 30분 이내 → 모듈 책임이 명확
    ├── 반나절 → 책임이 복잡하거나 문서 부족
    └── 하루 이상 → 구조적 문제 or 과도한 의존성
```

## 설계를 개선하는 작은 첫걸음

설계 개선은 한 번에 대규모로 하기보다, 작은 단계를 반복하는 편이 현실적입니다.

```text
1주차: 모듈을 한 문장으로 설명해 보기
  → "이 모듈은 [무엇]을 [누구에게] 한다"
  → 설명이 안 되면 책임이 너무 많다는 신호

2주차: 의존성 그래프 그리기
  → 화살표 방향을 그림으로 그려서 순환을 찾기
  → 순환이 보이면 가장 끊기 쉬운 곳 하나만 자르기

3주차: 단독 테스트 가능한 모듈 하나 만들기
  → DB, HTTP 없이 도메인 함수 하나를 독립 테스트
  → 어렵다면 의존성 방향을 먼저 확인

4주차: 변경 시뮬레이션 한 번 해보기
  → 가장 자주 오는 요구사항을 고르고
  → 수정해야 할 파일을 미리 나열해 보기
```

## 설계를 코드 리뷰에 녹이는 방법

설계 품질을 높이는 가장 효과적인 시점은 코드가 합쳐지기 직전입니다. 리뷰에서 아래 질문을 루틴으로 사용하면 팀 전체의 설계 감각이 올라갑니다.

```text
코드 리뷰 설계 체크포인트

1. 이 PR에서 어떤 모듈이 새로 생겼는가?
   → 새 모듈의 책임을 한 문장으로 설명할 수 있는가?

2. 의존성 방향이 바뀌었는가?
   → 도메인이 새로운 외부 라이브러리를 import하지는 않는가?

3. 변경 범위가 예상 범위 안에 있는가?
   → 이 기능을 위해 건드린 파일이 예상보다 많지 않은가?

4. 이 코드를 테스트하려면 무엇이 필요한가?
   → DB나 네트워크 없이 핵심 로직만 검증할 수 있는가?
```

설계 리뷰는 별도 단계가 아니라 기능 리뷰 안에 자연스럽게 포함되어야 합니다. 처음에는 어색하더라도 위 네 가지 질문을 매 PR마다 한 번씩만 물어봐도 팀 설계 수준이 꾸준히 올라갑니다.

## 기술 부채와 설계 부채의 차이

기술 부채는 "지름길을 선택했을 때 나중에 갚아야 할 비용"이고, 설계 부채는 그 중에서도 구조적 결정에서 비롯되는 비용입니다.

```text
기술 부채 예시                   설계 부채 예시
─────────────────────────────────────────────────
함수 이름이 불분명함              모듈 경계가 흐림
주석이 오래됨                     의존성 순환이 있음
중복 코드가 있음                  도메인에 인프라가 섞임
테스트가 없음                     변경 한 번에 파일 10개 수정
포매팅이 일관되지 않음            새 팀원이 구조를 파악하기 어려움

기술 부채는 대개 국소적.          설계 부채는 전체 개발 속도에 영향.
```

설계 부채가 더 무서운 이유는 국소적이지 않기 때문입니다. 코드 한 줄이 지저분한 것은 그 줄만 고치면 됩니다. 하지만 모듈 경계가 흐리면 매 기능 추가마다 시스템 전체가 영향을 받습니다.

## 설계 결정과 코딩 결정의 차이

설계 결정은 코드를 어떻게 쓸지가 아니라, 어떤 구조를 선택할지에 관한 것입니다. 두 범주를 구분하면 팀 논의가 훨씬 생산적이 됩니다.

| 구분 | 코딩 결정 | 설계 결정 |
| --- | --- | --- |
| 예시 | 함수 이름, 들여쓰기, 변수명 | 모듈 경계, 의존성 방향, 인터페이스 |
| 변경 비용 | 낮음 (IDE로 즉시 수정) | 높음 (구조 전체에 영향) |
| 검토 시점 | 코드 리뷰 | 설계 리뷰, PR 전 |
| 영향 범위 | 해당 파일 | 여러 모듈, 팀 작업 방식 |
| 되돌리기 | 쉬움 | 어려움 (리팩터링 필요) |

설계 결정은 한 번 굳으면 되돌리는 비용이 크기 때문에, 코딩을 시작하기 전에 더 많은 시간을 투자할 가치가 있습니다.

## 운영 체크리스트

- [ ] 각 모듈을 한 문장으로 설명할 수 있는가?
- [ ] 의존성 순환이 없는가?
- [ ] 자주 일어나는 변경의 수정 범위가 작은가?
- [ ] 도메인 모듈을 고립된 상태로 테스트할 수 있는가?
- [ ] 중요한 설계 결정이 ADR 같은 문서로 남아 있는가?

## 설계 부채를 측정하는 실용적인 지표

설계 부채를 "느낌"으로만 다루면 우선순위를 잡기 어렵습니다. 아래 지표를 스프린트마다 측정하면 부채가 쌓이는 속도를 객관적으로 볼 수 있습니다.

```text
지표 1: PR당 평균 수정 파일 수
  측정: git log --name-only 분석
  기준: 5개 이하면 양호, 10개 이상이면 경계 재검토 필요

지표 2: 도메인 단독 테스트 비율
  측정: 전체 테스트 중 DB/네트워크 없이 도는 비율
  기준: 70% 이상이면 의존성 방향이 잘 잡힌 것

지표 3: 모듈당 평균 import 수
  측정: 각 파일의 import 줄 수 평균
  기준: 10개 이하면 결합도가 낮음

지표 4: 신규 팀원 온보딩 시간
  측정: 첫 PR 제출까지 걸리는 시간
  기준: 1주 이내면 구조가 파악하기 쉬운 것
```

이 네 가지 지표만 주기적으로 보고해도 설계 상태를 정량적으로 추적할 수 있습니다.

## 현업 적용 관점에서 다시 정리

설계를 정의할 때는 "변경 비용"을 기준축으로 잡아야 합니다. 문법 난도가 아니라, 기능 변화가 들어올 때 경계가 어디까지 흔들리는지를 봐야 설계 품질을 설명할 수 있습니다.

## 정리

설계는 코드를 예쁘게 쓰는 습관이 아니라 다음 변경의 비용을 미리 정하는 결정의 묶음입니다 — 같은 기능을 만든 두 코드베이스의 차이는 문법이 아니라, 변경이 들어왔을 때 손대야 하는 파일 수와 두려움의 크기에서 드러납니다. 이 글에서는 전체 그림부터 현업 적용 관점에서 다시 정리까지 이 원칙을 구체적으로 살펴봤습니다. 핵심은 개념을 외우는 것이 아니라 실무에서 어떤 판단을 바꾸는지 이해하는 데 있습니다.

## 처음 질문으로 돌아가기

- **좋은 코딩과 좋은 설계는 무엇이 다를까요?**
  - 좋은 코딩은 코드를 읽기 좋게 만드는 일이고, 좋은 설계는 다음 변경을 값싸게 만드는 일입니다. 둘은 서로 돕지만 같은 목표가 아닙니다.
- **설계 품질은 어떤 신호로 판단할 수 있을까요?**
  - 변경 시뮬레이션, 의존성 방향, 모듈 책임 설명 가능성, 단독 테스트 가능성, 온보딩 속도 다섯 가지로 판단합니다.
- **설계 실패는 코드베이스에서 어떤 증상으로 드러날까요?**
  - 기능 하나 수정에 파일 여러 개가 열리고, 작은 수정도 통합 테스트 전체를 돌려야 하며, 새 팀원이 구조 설명을 오래 못 하는 형태로 드러납니다.
