# 바이브코딩을 위한 데이터베이스 시스템 기초 (4/10): 인덱스

이 글은 **바이브코딩을 위한 데이터베이스 시스템 기초** 시리즈의 4번째 글입니다. AI 코딩 도구로 빠르게 서비스를 만들 때 데이터베이스가 왜 그렇게 동작하는지 이해하면, AI가 만든 쿼리의 문제를 직접 발견하고 수정할 수 있습니다.

---

AI가 만든 백엔드가 개발할 때는 빠르다가 사용자 수가 늘면서 점점 느려지는 경험을 하셨나요? 대부분의 경우 원인은 인덱스입니다. 데이터가 1000건일 때는 풀스캔도 빠르지만, 100만 건이 되면 같은 쿼리가 수십 배 느려집니다. 인덱스를 이해하면 이 문제를 예방할 수 있습니다.

데이터베이스 성능 이야기를 시작하면 거의 항상 인덱스로 돌아옵니다. 실제로 많은 느린 쿼리는 "인덱스가 없어서" 혹은 "있지만 잘못 설계되어서" 생깁니다. 동시에, 인덱스를 무턱대고 늘리면 쓰기 성능이 망가지고 디스크 사용량이 불어나며, 옵티마이저 판단도 오히려 흐려질 수 있습니다.

> 인덱스는 책 뒤의 색인과 정확히 같습니다. 특정 단어 하나를 찾는 일은 빨라지지만, 책 전체를 처음부터 끝까지 한 번 읽는 일은 오히려 더 느려질 수 있습니다.

- 단일 인덱스, 복합 인덱스, 커버링 인덱스는 무엇이 다를까요?
- 어떤 경우에는 인덱스가 사실상 의미가 없어질까요?
- AI가 만든 스키마에 인덱스가 없을 때 어떻게 추가해야 할까요?
- 인덱스를 너무 많이 만들면 어떤 문제가 생길까요?

## B-tree 인덱스의 직관

루트에서 시작해 내부 노드를 한 단계씩 좁혀 가면, 리프 노드에서 실제 행 위치를 얻습니다. 트리 깊이가 거의 일정하기 때문에 데이터가 매우 커져도 몇 번의 점프로 원하는 지점에 도달할 수 있습니다.

```
[루트 페이지]
  keys: 100 | 500
   /          |
1..99       100..499     500..
[리프A]      [리프B]    [리프C]
```

`WHERE customer_id = 377` 조건은 루트에서 100과 500 사이 분기를 고른 뒤 해당 리프 범위에서 짧게 찾습니다. 반면 인덱스가 없으면 전체 행을 순차 스캔해야 합니다.

**핵심 용어**

- **B-tree 인덱스**: 가장 흔한 인덱스 형태입니다. 정렬된 키와 포인터를 균형 트리 구조로 유지합니다.
- **선택성(Selectivity)**: 특정 값이 전체 테이블 중 얼마나 적은 행을 가리키는지입니다. 1/1000이면 좋고, 1/2면 거의 쓸모가 없습니다.
- **복합 인덱스(Composite Index)**: 여러 컬럼을 함께 묶은 인덱스입니다. 컬럼 순서가 매우 중요합니다.
- **커버링 인덱스(Covering Index)**: 쿼리에 필요한 컬럼이 모두 인덱스 안에 들어 있는 경우입니다.

## 바이브코딩 관점: AI가 인덱스를 빠뜨리는 이유

AI는 스키마를 만들 때 기능 동작에 집중하고 성능을 나중에 고려하는 경향이 있습니다. 특히 다음 상황에서 인덱스가 빠집니다.

| 상황 | AI가 빠뜨리는 인덱스 | 실제 영향 |
|---|---|---|
| 외래키 컬럼 | `user_id REFERENCES users(id)` | JOIN이 풀스캔으로 실행 |
| 자주 필터링하는 컬럼 | `WHERE status = 'active'` | 데이터 증가 시 급격히 느려짐 |
| 정렬 기준 컬럼 | `ORDER BY created_at DESC` | 정렬을 위한 별도 Sort 단계 발생 |
| 복합 조건 | `WHERE user_id = ? AND status = ?` | 단일 인덱스만 있으면 비효율 |

## Before / After: 인덱스 없는 조회 vs 인덱스 추가 후

**Before — 인덱스 없는 10만 행 조회 (AI가 자주 만드는 상태)**

```sql
SELECT * FROM orders WHERE user_id = 7;
-- 100ms (full scan of 100,000 rows)
```

**After — 적절한 인덱스 하나 추가**

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);
SELECT * FROM orders WHERE user_id = 7;
-- 1ms 미만 (index lookup)
```

선택성이 좋은 컬럼에 적절한 인덱스 하나만 있어도 100배 가까운 차이가 나는 경우는 드물지 않습니다.

## 복합 인덱스 선두 컬럼 규칙

AI에게 "성능을 위한 인덱스 추가해줘"라고 요청하면 단일 컬럼 인덱스만 추가하는 경우가 많습니다. 복합 인덱스는 선두 컬럼이 핵심입니다.

```sql
CREATE INDEX idx_orders_tenant_status_created
ON orders (tenant_id, status, created_at);
```

- `WHERE tenant_id = 10` → 인덱스 범위 탐색 가능 (좋음)
- `WHERE tenant_id = 10 AND status = 'PAID'` → 더 좁은 범위 (더 좋음)
- `WHERE status = 'PAID'` 만 → 선두 컬럼 없어 인덱스 효율 급락 (나쁨)

## 자주 하는 실수 5가지

| 번호 | 실수 | 왜 문제인가 |
|---|---|---|
| 1 | 모든 컬럼에 인덱스를 건다 | 쓰기 비용과 디스크 사용량이 폭증합니다 |
| 2 | 선택성이 낮은 컬럼에 단일 인덱스 | `is_active`, `status` 같은 컬럼은 단독 인덱스로 힘을 못 씁니다 |
| 3 | 복합 인덱스 컬럼 순서 잘못 설정 | 가장 자주 첫 조건으로 쓰이는 컬럼이 앞에 와야 합니다 |
| 4 | 인덱스 만들고 EXPLAIN 안 확인 | 인덱스가 있어도 자동으로 쓰이는 것은 아닙니다 |
| 5 | `LIKE '%foo%'`가 B-tree를 탈 것이라 기대 | 선행 와일드카드는 인덱스를 무력화합니다 |

## AI 팁: 인덱스 설계를 AI에게 요청하는 방법

AI에게 인덱스 설계를 요청할 때 쿼리 패턴을 함께 제공하면 훨씬 나은 결과를 얻을 수 있습니다.

```
다음 쿼리들이 자주 실행됩니다. 적절한 인덱스를 설계해주세요:

1. SELECT * FROM orders WHERE user_id = ? ORDER BY created_at DESC LIMIT 20
2. SELECT * FROM orders WHERE status = 'pending' AND created_at > ?
3. SELECT COUNT(*) FROM orders WHERE user_id = ? AND status = 'paid'

각 인덱스에 대해 어떤 쿼리를 위한 것인지도 주석으로 표시해주세요.
```

AI가 인덱스를 추가할 때 반드시 검증해야 할 사항입니다.

- 생성 후 EXPLAIN으로 실제로 인덱스를 타는지 확인
- 선택성이 낮은 컬럼(true/false, 상태값)에 단일 인덱스가 있는지 검토
- 쓰기 비중이 높은 테이블에 인덱스가 너무 많지 않은지 확인

## 처음 질문으로 돌아가기

- **B-tree 인덱스는 어떤 직관으로 이해하면 좋을까요?**
  루트에서 시작해 몇 번의 분기만으로 원하는 값의 위치를 찾는 균형 트리입니다. 데이터가 많아져도 탐색 깊이가 거의 일정합니다.

- **인덱스가 사실상 의미 없어지는 경우는 언제일까요?**
  선택성이 낮은 컬럼(true/false 등), WHERE 절에 함수를 적용한 경우, 선두 컬럼이 조건에 없는 복합 인덱스 사용 시 옵티마이저가 인덱스를 무시할 수 있습니다.

- **AI가 만든 스키마에 인덱스가 없을 때 어떻게 추가해야 할까요?**
  실제 실행되는 쿼리의 WHERE, JOIN, ORDER BY 컬럼을 확인하고, EXPLAIN으로 풀스캔 여부를 확인한 뒤 인덱스를 추가하고 다시 EXPLAIN으로 검증합니다.

## 정리

인덱스는 "어디에 만들까"보다 "어디에는 만들지 않을까"의 판단에 가깝습니다. AI가 만든 스키마에 인덱스가 없다면 실제 쿼리 패턴을 분석해서 직접 추가해야 합니다. 다음 글에서는 여러 쓰기 작업을 안전하게 묶는 핵심 메커니즘, 트랜잭션과 ACID를 다룹니다.
