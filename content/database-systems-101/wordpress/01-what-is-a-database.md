# 바이브코딩을 위한 데이터베이스 시스템 기초 (1/10): 데이터베이스 시스템이란 무엇인가?

이 글은 **바이브코딩을 위한 데이터베이스 시스템 기초** 시리즈의 1번째 글입니다. AI 코딩 도구로 빠르게 서비스를 만들 때 데이터베이스가 왜 그렇게 동작하는지 이해하면, AI가 만든 쿼리의 문제를 직접 발견하고 수정할 수 있습니다.

---

AI에게 "사용자 잔액을 차감하는 코드 짜줘"라고 요청하면 그럴싸한 코드가 나옵니다. 하지만 두 요청이 동시에 들어오면 잔액이 이상해질 수 있고, 서버가 중간에 죽으면 절반만 차감된 상태가 남을 수 있습니다. 이런 문제가 생기는 근본 이유는 데이터베이스 시스템이 무엇을 보장하고 무엇을 보장하지 않는지 모르기 때문입니다.

파일 하나에 JSON을 저장해도 데이터는 남습니다. 그래서 처음에는 "그냥 파일을 잘 관리하면 되는 것 아닌가?"라는 생각이 들 수 있습니다. 문제는 시스템이 진짜 시스템처럼 행동하기 시작하는 순간입니다. 사용자 둘이 동시에 같은 값을 바꾸고, 프로세스가 중간에 죽고, "특정 조건을 만족하는 데이터만 빠르게 찾아 달라"는 요구가 붙는 순간부터 파일은 저장소일 뿐이고, 데이터베이스는 별도의 소프트웨어 계층이라는 사실이 드러납니다.

데이터베이스 관리 시스템(DBMS)은 단순한 저장 엔진이 아닙니다. 동시 접근, 장애 복구, 무결성, 질의 처리라는 네 가지 어려운 문제를 한 번에 맡는 소프트웨어입니다. 이 관점을 먼저 잡아 두면 이후에 나오는 SQL, 인덱스, 트랜잭션, 격리 수준이 왜 필요한지 자연스럽게 이어집니다.

> "우리는 데이터베이스를 쓴다"는 말은 사실 "동시성 제어, 장애 복구, 일관성을 애플리케이션에서 직접 구현하지 않는다"는 뜻입니다.

## 이 글에서 다룰 질문

- 파일과 DBMS의 결정적인 차이는 무엇일까요?
- DBMS가 가장 많은 비용을 들여 보장하는 네 가지 성질은 무엇일까요?
- 관계형, 문서형, 키-값 저장소는 각각 어디에 강할까요?
- AI가 생성한 DB 코드에서 가장 자주 빠지는 부분은 무엇일까요?
- 바이브코딩 시 데이터 손실이 발생하는 가장 흔한 원인은 무엇일까요?

## DBMS란 무엇인가

DBMS는 애플리케이션과 디스크 사이에 위치하면서, 여러 클라이언트의 요청을 받아 캐시와 로그, 온디스크 상태를 일관되게 맞춥니다.

```
Application ──→ DBMS ──→ Storage (Disk)
                  │──→ Buffer / Cache
                  └──→ Log (WAL)
Other clients ──→ DBMS
```

애플리케이션은 SQL로 원하는 결과를 선언하고, 어떻게 잠그고 어떻게 디스크에 기록할지는 DBMS가 책임집니다.

**핵심 용어**

- **DBMS**: PostgreSQL, MySQL, SQLite 같은 데이터베이스 관리 시스템입니다.
- **스키마**: 테이블, 컬럼, 타입처럼 데이터 구조를 정의한 명세입니다.
- **트랜잭션**: 모두 반영되거나 모두 취소되어야 하는 SQL 문들의 묶음입니다.
- **영속성(Durability)**: 커밋된 변경이 즉시 장애가 나더라도 살아남는 성질입니다.
- **동시성 제어**: 여러 클라이언트가 동시에 같은 데이터를 다뤄도 결과를 일관되게 유지하는 메커니즘입니다.

## 바이브코딩 관점: AI가 놓치는 것

AI 코딩 도구가 생성하는 데이터베이스 코드에는 패턴이 있습니다. 단순한 CRUD는 잘 만들어지지만, 동시성 보호와 장애 복구는 자주 빠집니다. AI는 "행복한 경로(happy path)"를 기준으로 코드를 만들기 때문입니다.

다음은 AI가 자주 생성하는 패턴과 실제 문제입니다.

| AI 생성 패턴 | 숨어있는 문제 |
|---|---|
| 파일에 JSON 직접 쓰기 | 두 요청 동시 실행 시 데이터 덮어쓰기 |
| 트랜잭션 없이 여러 UPDATE | 중간 실패 시 불일치 상태 |
| 문자열 포매팅으로 SQL 조립 | SQL 인젝션 취약점 |
| 에러 핸들링 없는 DB 연결 | 연결 풀 고갈, 커넥션 누수 |
| 스키마 제약 없이 데이터 삽입 | 잘못된 데이터가 조용히 저장됨 |

## Before / After: 파일 저장 vs DBMS

**Before — 파일을 직접 다루는 방식 (AI가 자주 제안하는 패턴)**

```python
import json

def deposit(user_id: str, amount: int) -> None:
    with open("accounts.json", "r") as f:
        data = json.load(f)
    data[user_id] = data.get(user_id, 0) + amount
    with open("accounts.json", "w") as f:
        json.dump(data, f)
```

사용자가 한 명일 때는 멀쩡해 보입니다. 하지만 두 프로세스가 동시에 실행되면 한쪽 입금이 조용히 사라질 수 있고, `json.dump` 중간에 장애가 나면 파일 자체가 망가질 수 있습니다.

**After — DBMS가 동시성과 영속성을 담당하는 방식**

```python
import sqlite3

def deposit(db: sqlite3.Connection, user_id: str, amount: int) -> None:
    with db:  # transaction
        db.execute(
            "UPDATE accounts SET balance = balance + ? WHERE user_id = ?",
            (amount, user_id),
        )
```

이제 동시성 처리는 DBMS가 잠금으로 맡고, 장애 복구는 WAL(Write-Ahead Log) 메커니즘으로 맡습니다. 애플리케이션은 "잔액을 올려 달라"는 의도만 표현합니다.

## 자주 하는 실수 5가지

| 번호 | 실수 | 왜 문제인가 |
|---|---|---|
| 1 | DBMS를 "조금 더 고급스러운 파일"로 본다 | 동시성과 장애 복구가 빠진 비교는 처음부터 비교가 아닙니다 |
| 2 | 스키마 없이 시작한다 | 처음에는 유연해 보여도, 6개월 뒤 정리 비용이 두 배로 돌아옵니다 |
| 3 | 모든 쓰기를 자동 커밋에 맡긴다 | 두 줄짜리 갱신도 중간에 실패하면 데이터가 어긋날 수 있습니다 |
| 4 | 문자열 포매팅으로 SQL을 만든다 | SQL 인젝션의 정석적인 진입점입니다 |
| 5 | 복구를 테스트하지 않는다 | 최근에 복원해 보지 않은 백업은 희망 사항에 가깝습니다 |

## AI 팁: DB 관련 코드 생성 요청 시 체크포인트

AI에게 데이터베이스 코드를 요청할 때 이 문구를 프롬프트에 추가하면 더 안전한 코드를 얻을 수 있습니다.

```
다음 조건을 반드시 포함해주세요:
1. 트랜잭션으로 모든 쓰기를 감싸기
2. ? 플레이스홀더 사용 (문자열 포매팅 금지)
3. 예외 발생 시 롤백 처리
4. 연결은 컨텍스트 매니저(with 문)로 관리
```

생성된 코드에서 다음이 빠져 있으면 반드시 수동으로 추가해야 합니다.

- `BEGIN` / `COMMIT` / `ROLLBACK` 경계
- 스키마의 `NOT NULL`, `CHECK`, `FOREIGN KEY` 제약
- 파라미터 바인딩 (`?` 또는 `%s`)

## 처음 질문으로 돌아가기

- **파일과 DBMS의 결정적인 차이는 무엇일까요?**
  파일은 저장소이고 DBMS는 동시성, 장애 복구, 무결성, 질의 처리를 함께 맡는 소프트웨어 계층입니다. 실패 처리 책임이 애플리케이션 코드에 남는 것과 DBMS가 분담하는 것의 차이입니다.

- **DBMS가 가장 많은 비용을 들여 보장하는 네 가지 성질은 무엇일까요?**
  원자성(Atomicity), 일관성(Consistency), 격리성(Isolation), 영속성(Durability), 즉 ACID입니다. 트랜잭션이 이 네 가지를 묶어서 보장합니다.

- **AI가 생성한 DB 코드에서 가장 자주 빠지는 부분은 무엇일까요?**
  트랜잭션 경계와 예외 처리에서의 롤백입니다. AI는 성공 경로 코드는 잘 만들지만 부분 실패 시 복구 코드는 자주 생략합니다.

## 정리

DBMS는 데이터를 넣어 두는 장소가 아니라, 동시성·영속성·일관성·질의를 한꺼번에 해결하는 소프트웨어입니다. AI가 만든 코드가 프로덕션에서 데이터를 깨뜨리는 이유는 대부분 이 계층을 이해하지 못한 채 코드를 수용했기 때문입니다. 다음 글에서는 SQL이 기대고 있는 더 근본적인 모델, 관계형 모델을 살펴봅니다.
