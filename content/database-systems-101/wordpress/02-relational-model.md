# 바이브코딩을 위한 데이터베이스 시스템 기초 (2/10): 관계형 모델

이 글은 **바이브코딩을 위한 데이터베이스 시스템 기초** 시리즈의 2번째 글입니다. AI 코딩 도구로 빠르게 서비스를 만들 때 데이터베이스가 왜 그렇게 동작하는지 이해하면, AI가 만든 쿼리의 문제를 직접 발견하고 수정할 수 있습니다.

---

AI에게 "주문 테이블 만들어줘"라고 요청하면 보통 하나의 테이블에 사용자 이름, 이메일, 상품 정보를 모두 집어넣은 스키마가 나옵니다. 처음에는 동작합니다. 하지만 사용자가 이메일을 바꾸면 모든 주문 행을 수정해야 하고, 그 중 하나라도 빠지면 "진실이 둘"이 되는 상태가 됩니다. 이것이 관계형 모델을 이해해야 하는 이유입니다.

테이블은 익숙합니다. 하지만 관계형 데이터베이스를 오래 다루는 팀일수록 "행과 열의 모음"이라는 표현만으로는 만족하지 않습니다. 관계형 모델의 진짜 힘은 화면에 보이는 표 모양이 아니라, 그 표 뒤에서 무엇을 하나의 사실로 보고 어떤 키와 제약으로 연결할지를 명확하게 강제하는 데 있기 때문입니다.

이 관점을 잡고 나면 SQL도 덜 임의적으로 보입니다. SELECT, JOIN, 제약, 정규화가 모두 한 모델 위에 올라가 있다는 사실이 보이기 시작합니다.

> SQL은 절차형 언어가 아닙니다. 관계 위에 정의된 연산 집합이기 때문에, 어떻게가 아니라 무엇을 기술합니다.

## 이 글에서 다룰 질문

- 테이블에서 말하는 관계, 튜플, 속성은 각각 무엇을 가리킬까요?
- 기본키와 외래키는 정확히 무엇을 보장할까요?
- NULL과 무결성 제약은 어떤 의미를 가질까요?
- AI가 만든 스키마에서 관계형 모델 위반을 어떻게 찾을까요?
- 외래키 없이 설계하면 어떤 문제가 생길까요?

## 관계형 모델의 핵심 구조

테이블 하나가 곧 하나의 관계이고, 그 안의 한 행이 튜플이며, 각 컬럼이 속성입니다. 키는 특정 행을 유일하게 식별하는 속성 또는 속성 집합입니다.

```
Schema (table definition)
         ↓
Relation: rows of one shape
    ├── Tuple (row)
    ├── Attribute (column)
    ├── Primary key
    └── Foreign key → other relation
```

**핵심 용어**

- **관계(Relation)**: 같은 모양의 튜플들의 집합입니다. 일상적으로는 테이블이라고 부릅니다.
- **튜플(Tuple)**: 하나의 행입니다. 단순한 위치가 아니라 속성 이름으로 해석되는 값 묶음입니다.
- **속성(Attribute)**: 이름과 도메인(타입)을 가진 컬럼입니다.
- **기본키(Primary Key)**: 한 행을 유일하게 식별하는 최소 속성 집합입니다. NULL이 될 수 없습니다.
- **외래키(Foreign Key)**: 다른 관계의 기본키를 가리키는 속성으로, 참조 무결성을 강제합니다.

## 바이브코딩 관점: AI가 만드는 스키마의 전형적인 문제

AI는 요청한 기능을 빠르게 구현하는 방향으로 스키마를 만듭니다. 가장 자주 보이는 패턴은 하나의 테이블에 모든 것을 넣는 방식입니다.

| 문제 유형 | AI가 생성하는 스키마 | 실제 발생 문제 |
|---|---|---|
| 중복 저장 | 주문마다 user_email 저장 | 이메일 변경 시 모든 행 수정 필요 |
| 외래키 미사용 | user_id만 저장, FK 없음 | 존재하지 않는 사용자 참조 가능 |
| NULL 허용 남발 | 모든 컬럼 nullable | 의미 불명확, 쿼리 복잡성 증가 |
| 자연키를 PK로 | email을 PRIMARY KEY로 | 이메일 변경 시 참조 전체 갱신 |

## Before / After: 모든 것을 하나의 테이블에 vs 관계로 분리

**Before — 하나의 테이블에 모두 넣기 (AI가 자주 생성하는 패턴)**

```sql
CREATE TABLE orders (
    id        INTEGER PRIMARY KEY,
    user_name TEXT,
    user_email TEXT,
    product   TEXT,
    price     INTEGER
);
```

한 사용자가 두 번 주문하면 이메일이 두 번 저장됩니다. 이메일이 바뀌면 모든 주문 행을 수정해야 합니다. "한 사실은 한 곳에"라는 약속이 처음부터 깨집니다.

**After — 관계로 분리하기**

```sql
CREATE TABLE users (
    id    INTEGER PRIMARY KEY,
    name  TEXT NOT NULL,
    email TEXT NOT NULL UNIQUE
);

CREATE TABLE orders (
    id      INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id),
    product TEXT    NOT NULL,
    price   INTEGER NOT NULL CHECK (price >= 0)
);
```

사용자 정보는 `users`에 한 번만 존재하고, 주문은 외래키로 그 사용자를 참조합니다. 이메일 변경은 한 행 수정으로 끝납니다.

## 자주 하는 실수 5가지

| 번호 | 실수 | 왜 문제인가 |
|---|---|---|
| 1 | 외래키를 편의상 끈다 | 몇 달 뒤 dangling reference 디버깅 비용이 돌아옵니다 |
| 2 | 모든 컬럼에 NULL 허용 | 의미가 흐려지고 쿼리가 더 복잡해집니다 |
| 3 | 이메일·전화번호를 기본키로 쓴다 | 값이 바뀔 수 있는 키는 참조 비용을 키웁니다 |
| 4 | 표시용 데이터를 여러 테이블에 중복 저장 | 한쪽만 수정되면 진실이 둘이 됩니다 |
| 5 | JOIN을 피하려고 앱 코드에서 데이터 합침 | N+1 쿼리와 최적화 손실이 동시에 생깁니다 |

## AI 팁: 스키마 생성 요청 시 품질 높이는 방법

AI에게 스키마 설계를 요청할 때 다음 지침을 프롬프트에 추가하면 관계형 모델을 더 잘 반영한 결과를 얻을 수 있습니다.

```
스키마 설계 시 다음 규칙을 따라주세요:
1. 각 사실은 정확히 한 테이블에만 저장
2. 관계는 외래키(REFERENCES)로 표현
3. NULL은 의도적으로만 허용, 기본값은 NOT NULL
4. 기본키는 자동 증가 정수형 surrogate key 사용
5. 참조 무결성(FK)을 스키마에 명시
```

AI가 생성한 스키마에서 다음 신호를 찾으면 관계형 모델 위반을 의심해야 합니다.

- 같은 이메일이나 이름이 여러 테이블에 반복 등장
- `REFERENCES` 키워드 없이 `_id` 컬럼만 존재
- 모든 컬럼이 `TEXT` 타입이고 제약이 없음

## 처음 질문으로 돌아가기

- **테이블에서 말하는 관계, 튜플, 속성은 각각 무엇을 가리킬까요?**
  관계는 같은 모양의 행들의 집합(테이블), 튜플은 하나의 행, 속성은 이름과 타입을 가진 컬럼입니다.

- **기본키와 외래키는 정확히 무엇을 보장할까요?**
  기본키는 각 행의 유일성을 보장하고, 외래키는 다른 테이블의 실제 존재하는 행만 참조할 수 있도록 참조 무결성을 강제합니다.

- **AI가 만든 스키마에서 관계형 모델 위반을 어떻게 찾을까요?**
  같은 정보(이메일, 이름 등)가 여러 테이블에 반복되는지, `_id` 컬럼에 `REFERENCES`가 없는지, NULL이 무분별하게 허용되는지 확인합니다.

## 정리

관계형 모델은 "테이블은 같은 모양의 행들의 집합이고, 행은 키로 식별되며, 관계는 외래키로 표현된다"는 단순한 약속으로 요약됩니다. AI가 만드는 스키마가 이 약속을 얼마나 지키는지 확인하는 것이 바이브코딩에서 데이터 품질을 지키는 첫 번째 단계입니다. 다음 글에서는 그 모델 위에서 실제로 실행되는 언어, SQL과 쿼리 처리 과정을 살펴봅니다.
