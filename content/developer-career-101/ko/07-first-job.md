# Developer Career 101 (7/10): 첫 직장 적응

첫 직장에 들어가면 빨리 실력을 증명해야 한다는 압박부터 느끼기 쉽습니다. 하지만 대부분의 팀이 초반 90일에 보고 싶은 것은 완성된 실력보다 배우는 방식, 질문하는 태도, 작은 기여를 쌓아 가는 속도입니다.

이 글은 Developer Career 101 시리즈의 7번째 글입니다.

![Developer Career 101 7장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/developer-career-101/07/07-01-concept-at-a-glance.ko.png)
*Developer Career 101 7장 흐름 개요*
> 첫 직장 적응의 핵심은 주어진 일을 빠르게 완료하는 것보다, 일하는 방식과 팀의 기준을 이해하고 점진적으로 자율성을 확대하는 데 있습니다.

## 이 글에서 다룰 문제

- 첫 개발자 직장에서 처음 90일은 무엇에 집중해야 할까요?
- 많이 아는 척하기보다 질문하고 기록하는 태도가 왜 더 중요할까요?
- 첫 PR과 1:1은 어떻게 신뢰를 만드는 장치가 될까요?
- 이 개념을 실무에서 잘못 적용하면 어떤 문제가 생길까요?
- 이 주제에서 초보자가 가장 자주 놓치는 포인트는 무엇일까요?

## 이 글에서 배울 것

- 온보딩 전략
- 질문을 모으는 기술
- 작은 기여를 만드는 법
- 피드백 루프 운영 방식
- 관계를 만드는 기본기

첫인상은 이후 1년 반 가까운 협업 분위기에 영향을 주는 경우가 많습니다. 초반에 어떻게 배우고 소통했는지가 이후 성장 속도와 신뢰의 바닥이 됩니다.

> 첫 직장의 초반 90일은 실력을 증명하는 시기라기보다, 배우는 방식과 협업 태도를 보여 주는 시기입니다.

좋은 온보딩은 혼자 버티는 과정이 아닙니다. 먼저 배우고, 질문하고, 작은 기여를 내고, 피드백으로 보정하는 루프가 돌아야 자리를 빨리 잡을 수 있습니다.

- 온보딩: 조직과 코드베이스에 적응하는 기간입니다.
- 버디: 가까이에서 도와주는 동료 멘토입니다.
- **1:1**: 일대일 미팅입니다.
- 섀도잉: 옆에서 보며 배우는 방식입니다.
- **심리적 안전감**: 말해도 괜찮다는 감각입니다.

## 개선 전/후

**Before**: "혼자 공부해서 알아내려 합니다."

**After**: "질문을 모아서 정리하고 작은 PR을 보냅니다."

## 직접 해보기: 90일 계획 세우기

### 1단계 — Day 30: Learn

```text
- explore the codebase
- shadow an oncall
- write a glossary
```

처음 30일은 무작정 성과를 내기보다 맥락을 넓게 잡는 기간입니다. 코드베이스 구조를 훑고, 온콜이나 배포 흐름을 관찰하고, 팀 용어집을 만들어 두면 질문의 질이 올라갑니다.

### 2단계 — Day 60: Curate Questions

```markdown
## 질문 노트
- why is X faster than Y?
- what is Z's retention policy?
```

질문은 즉흥적으로 흩어지기 쉽습니다. 노트에 모아 두면 중복 질문이 줄고, 1:1이나 버디 미팅에서 더 짧고 선명하게 물을 수 있습니다.

### 3단계 — Day 90: First PR

```bash
git checkout -b first-fix
# 작은 범위 변경
```

첫 PR은 크지 않을수록 좋습니다. 범위가 작은 버그 수정이나 문서 개선부터 시작해야 리뷰도 빨리 받고 신뢰도 쉽게 쌓입니다.

### 4단계 — Use 1:1s

```text
weekly with manager, biweekly with mentor
```

1:1은 상태 보고 시간이 아니라 피드백을 받는 시간입니다. 막막한 고민을 쌓아 두지 말고, 질문 노트를 바탕으로 구체적으로 가져가는 편이 좋습니다.

### 5단계 — Retro

```markdown
- went well: code reading
- gap: question frequency
- next: one question per day
```

온보딩 회고는 잘한 점과 부족한 점을 빠르게 드러냅니다. 초반에는 작은 보정만 해도 체감 성장 속도가 크게 달라집니다.

## 첫 90일을 설계할 때 보는 기준

| 기간 | 우선순위 | 확인할 산출물 |
| --- | --- | --- |
| 0~30일 | 맥락 파악과 용어 정리 | 팀 용어집, 구조 메모 |
| 31~60일 | 질문의 질 높이기 | 질문 노트, 1:1 아젠다 |
| 61~90일 | 작은 기여와 피드백 루프 | 첫 PR, 회고 메모 |
| 공통 | 모르는 것을 빨리 드러내기 | 도움 요청 기록, 체크인 루틴 |

## 실제 적응 사례: 성공과 실패

**성공 사례**: 입사 첫 달에 팀 용어집과 아키텍처 메모를 만든 주니어 개발자가 있었습니다. 처음에는 "이런 걸 써서 뭐하나" 싶었지만, 두 달 후 새로 입사한 팀원이 같은 자료를 보고 빠르게 적응했습니다. 그 결과 입사 3개월 만에 "함께 일하기 좋은 사람"이라는 평가를 받았고, 리뷰어로 지정되는 기회도 생겼습니다.

**실패 사례**: 반대로 모르는 것을 숨기며 혼자 해결하려 했던 케이스도 있습니다. 2주 동안 같은 문제를 붙잡고 있다가 뒤늦게 질문했는데, 알고 보니 이미 팀 내 해결책이 있었습니다. 이 경험으로 "모르면 빨리 물어보는 것이 예의"라는 팀 문화를 몸으로 배웠습니다.

**실패 사례 2**: 첫날부터 팀의 기존 코드 스타일을 자신의 방식으로 바꾸려 했던 개발자가 있었습니다. PR에서 팀이 수년간 써온 패턴을 "더 나은 방법"으로 리팩터하자고 제안했습니다. 기술적으로 틀리지는 않았지만, 팀 맥락을 이해하기 전에 변화를 제안한 것이 오히려 관계를 어색하게 만들었습니다. 처음 90일은 제안보다 이해가 먼저입니다.

## 초반 90일 팀 유형별 적응 전략

팀 문화와 구조에 따라 온보딩 전략이 달라집니다.

| 팀 유형 | 특징 | 적응 전략 | 주의할 점 |
| --- | --- | --- | --- |
| 스타트업 소규모 팀 | 문서 부족, 빠른 결정 | 구두 소통 많이, 대신 직접 문서화 | 맥락이 사람 머릿속에만 있음 |
| 대기업 팀 | 프로세스 많음, 승인 단계 | 프로세스 먼저 파악, 체크리스트 활용 | 변경 절차를 무시하면 문제 |
| 원격 팀 | 비동기 소통 기본 | 글로 남기는 습관, 주기적 체크인 | 눈에 안 보이면 잊혀지기 쉬움 |
| 레거시 코드 많은 팀 | 기술 부채 높음 | 왜 이렇게 되었는지 먼저 이해 | 리팩터 제안은 3개월 후부터 |

## 코드베이스 파악 전략

처음 합류한 코드베이스는 지도 없이 새 도시를 걷는 것과 같습니다. 무작위로 탐색하기보다 순서를 정하면 훨씬 빠르게 구조가 보입니다.

**1단계 — 진입점 찾기**: 서비스가 시작되는 지점부터 찾습니다. main 함수, 서버 초기화 파일, 또는 배포 스크립트가 어디 있는지 확인합니다.

**2단계 — 요청 흐름 따라가기**: 가장 자주 호출되는 API 하나를 골라 요청이 들어와서 응답이 나가기까지의 경로를 코드에서 직접 따라갑니다.

**3단계 — 데이터 모델 파악**: 핵심 엔티티(사용자, 주문, 상품 등)의 스키마를 먼저 이해합니다. 데이터 구조가 보이면 비즈니스 로직도 빠르게 읽힙니다.

**4단계 — 테스트 코드 읽기**: 테스트는 기능 명세서입니다. 어떤 케이스가 테스트되는지 보면 팀이 중요하게 생각하는 시나리오를 알 수 있습니다.

## 인터뷰 준비: 첫 직장 경험 질문

**질문 — "첫 직장에서 가장 어려웠던 점이 무엇이었나요?"**

약한 답변: "코드가 복잡해서 어려웠습니다."

강한 답변: "레거시 코드베이스의 맥락을 파악하는 것이 처음에 가장 어려웠습니다. 이를 해결하기 위해 팀 용어집과 아키텍처 다이어그램을 직접 만들었고, 그 과정에서 온콜 섀도잉을 2회 참여했습니다. 결과적으로 3개월 후 신규 팀원 온보딩 자료로 활용됐습니다."

**질문 — "팀에서 의견 충돌이 있을 때 어떻게 해결했나요?"**

약한 답변: "팀원의 의견을 따랐습니다."

강한 답변: "PR 리뷰에서 코드 구조에 대한 의견 차이가 있었습니다. 저는 제 접근법의 장점을 설명했지만, 팀원의 관점도 타당하다는 걸 알았습니다. 대신 두 방법의 트레이드오프를 짧은 메모로 정리해 공유했고, 팀 리드가 최종 결정을 내릴 수 있도록 판단 자료를 제공했습니다. 결과적으로 팀원의 방향으로 결정됐고, 저는 그 이유를 더 명확히 이해하게 됐습니다."

**질문 — "첫 직장에서 실패했던 경험을 이야기해 주세요."**

강한 답변 구조: 상황(S) → 문제(T) → 내가 한 행동(A) → 결과와 배운 점(R) 순서로 말합니다. "실패"를 감추기보다 배움으로 전환하는 서사가 설득력 있습니다.

## 자주 하는 실수

| 실수 | 왜 발생하는가 | 개선 방법 |
| --- | --- | --- |
| 모르는 것을 숨긴다 | 무능하게 보일까봐 두렵기 때문 | "이 부분을 찾아봤는데 아직 불명확합니다"라고 먼저 말하는 연습을 한다 |
| 질문을 너무 크게 던진다 | 문제를 정리하지 않고 물어보기 때문 | 질문 전 3가지를 먼저 정리한다: 상황, 시도한 것, 막힌 이유 |
| PR을 전혀 보내지 않는다 | 완벽하지 않으면 내면 안 된다고 생각하기 때문 | 작은 PR을 먼저 보내고 피드백으로 개선하는 루프를 만든다 |
| 1:1을 건너뛴다 | 할 말이 없다고 느끼기 때문 | 질문 노트에서 2개를 골라 아젠다로 만들어 매번 가져간다 |
| 메모를 남기지 않는다 | 나중에 기억할 수 있다고 착각하기 때문 | 미팅 후 5분 안에 핵심 메모를 팀 채널에 공유하는 루틴을 만든다 |

## 시니어 엔지니어는 이렇게 생각합니다

- 질문은 민폐가 아니라 예의입니다.
- 작은 PR이 진전입니다.
- 1:1은 신뢰를 만드는 시간입니다.
- 노트는 커리어 자산입니다.
- 관찰은 학습의 일부입니다.

## 운영 체크리스트

- [ ] 용어집을 만들었습니다.
- [ ] 질문 노트를 만들었습니다.
- [ ] 첫 PR을 보냈습니다.
- [ ] 1:1 루틴을 잡았습니다.

## 연습 문제

1. 심리적 안전감을 한 줄로 설명해 보세요.
2. 버디와 멘토의 차이를 한 줄로 적어 보세요.
3. 작은 PR 예시를 한 줄로 적어 보세요.
4. 첫 30일 동안 만들어야 할 산출물 두 가지를 적어 보세요.
5. 좋은 1:1 아젠다에 포함해야 할 항목을 세 가지 적어 보세요.

## 커뮤니케이션 템플릿: 상태 공유 메시지

- 오늘 완료: 무엇을 끝냈는지 한 줄
- 현재 리스크: 막힌 지점과 원인 한 줄
- 요청 사항: 누구에게 어떤 도움이 필요한지 한 줄
- 다음 계획: 오늘 안에 끝낼 다음 작업 한 줄

## 온보딩 체크리스트: 팀 신뢰를 얻는 기본 루틴

- 개발 환경 설정 문서의 빈칸을 직접 채웠는가
- 리뷰 피드백을 같은 주 안에 반영했는가
- 모르는 용어를 팀 위키에 정리했는가
- 배포 전 체크리스트를 스스로 실행했는가
- 온콜 로테이션 참관을 1회 이상 했는가
- 매니저와 30/60/90일 기대치를 명시적으로 확인했는가

## 정리

첫 직장에서의 좋은 출발은 혼자 버티는 데서 나오지 않습니다. 배우고, 질문하고, 작은 기여를 내고, 피드백으로 조정하는 루프를 빠르게 만드는 것이 핵심입니다. 다음 글에서는 본업과 병행해도 무너지지 않는 사이드 프로젝트 운영 원칙을 정리하겠습니다.

## 처음 질문으로 돌아가기

- **첫 개발자 직장에서 처음 90일은 무엇에 집중해야 할까요?**
  - 처음 30일은 맥락 파악, 31~60일은 질문의 질 높이기, 61~90일은 작은 기여와 피드백 루프 만들기에 집중합니다. 실력 증명은 그 이후에 자연스럽게 따라옵니다.
- **많이 아는 척하기보다 질문하고 기록하는 태도가 왜 더 중요할까요?**
  - 팀이 초반에 평가하는 것은 기술 완성도가 아니라 학습 속도와 협업 태도입니다. 모르는 것을 빨리 드러내는 사람이 더 빠르게 신뢰를 얻습니다.
- **첫 PR과 1:1은 어떻게 신뢰를 만드는 장치가 될까요?**
  - 작은 PR은 "실행 가능한 사람"이라는 신호를 주고, 1:1은 방향을 보정하는 피드백 채널입니다. 두 가지를 정기적으로 운영하면 신뢰 회로가 빠르게 만들어집니다.
