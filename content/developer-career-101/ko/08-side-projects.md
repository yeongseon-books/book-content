# Developer Career 101 (8/10): 사이드 프로젝트와 학습

사이드 프로젝트를 시작할 때는 대개 아이디어가 너무 큽니다. 하지만 본업과 함께 가져가야 하는 프로젝트는 재미보다 지속 가능성이 더 중요하고, 멋진 비전보다 작게 끝내는 구조가 더 중요합니다.

이 글은 Developer Career 101 시리즈의 8번째 글입니다.

![Developer Career 101 8장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/developer-career-101/08/08-01-concept-at-a-glance.ko.png)
*Developer Career 101 8장 흐름 개요*
> 사이드 프로젝트의 가치는 얼마나 정교한 기술을 썼느냐가 아니라, 요구사항 정의부터 배포와 유지보수까지 전체 책임을 져본 경험입니다.

## 이 글에서 다룰 문제

- 본업과 충돌하지 않는 좋은 사이드 프로젝트는 어떤 조건을 가져야 할까요?
- 너무 큰 아이디어 대신 작은 MVP로 시작해야 하는 이유는 무엇일까요?
- 시간 박스, 공개, 피드백은 사이드 프로젝트를 어떻게 지속 가능하게 만들까요?
- 이 개념을 실무에서 잘못 적용하면 어떤 문제가 생길까요?
- 이 주제에서 초보자가 가장 자주 놓치는 포인트는 무엇일까요?

## 이 글에서 배울 것

- 프로젝트를 고르는 기준
- 시간 박스 운영법
- 공개와 피드백 수집법
- 회사 업무와 분리하는 법
- 지속 가능성 전략

좋은 사이드 프로젝트는 학습과 증거를 동시에 남깁니다. 반대로 범위가 크고 경계가 모호하면 피로만 쌓이고 결과물이 남지 않기 쉽습니다.

> 사이드 프로젝트의 핵심은 대단한 아이디어가 아니라, 작게 끝내고 배움을 남기는 구조입니다.

사이드 프로젝트는 길게 버티는 마라톤이 아닙니다. 아이디어를 고르고, 시간을 제한하고, 작게 내보내고, 피드백을 받아 다음 사이클로 넘어가는 구조가 있어야 지치지 않습니다.

- **사이드 프로젝트**: 취미 또는 보조 성격의 개인 프로젝트입니다.
- **시간 박스**: 경계를 둔 시간 슬롯입니다.
- **MVP**: 최소 기능 제품입니다.
- 문라이팅: 공개하지 않은 부업입니다.
- **이해 충돌**: 의무가 충돌하는 상태입니다.

## 개선 전/후

**Before**: "아이디어는 많지만 끝낸 것이 없습니다."

**After**: "분기마다 작은 MVP 하나를 실제로 배포합니다."

## 직접 해보기: 사이드 프로젝트 운영하기

### 1단계 — Pick the Idea

```text
criteria:
- interest
- learning value
- no conflict with day job
```

좋은 아이디어는 화려한 아이디어가 아닙니다. 흥미가 있고, 배울 것이 분명하며, 본업과 충돌하지 않아야 오래 가져갈 수 있습니다.

### 2단계 — Time Box

```text
4 hours/week (Sat 09-13)
```

사이드 프로젝트는 남는 시간에 하는 일이 아니라 미리 예약된 시간에 하는 일이어야 합니다. 시간을 무한정 쓰기 시작하면 건강과 본업 둘 다 흔들리기 쉽습니다.

### 3단계 — Define MVP

```markdown
- 1 core feature
- 1 command
- 1 README
```

MVP는 끝선을 만드는 장치입니다. 핵심 기능 하나와 최소한의 문서만으로도 첫 공개는 충분히 가능합니다.

### 4단계 — Publish

```bash
gh repo create --public
# 프로젝트 소개문 + 라이선스 + 첫 릴리스
```

공개하지 않으면 피드백도 늦고 동기부여도 약해집니다. 작은 저장소라도 README와 LICENSE, 첫 릴리스를 남기면 프로젝트가 실제 자산으로 바뀝니다.

### 5단계 — Separation Policy

```text
- no company assets
- IP review with employer
```

본업과의 분리는 안전장치입니다. 회사 자산을 섞지 말고, 지식재산권 규정을 확인해 두어야 나중에 불필요한 문제를 피할 수 있습니다.

## 사이드 프로젝트를 고를 때 쓰는 점수표

| 기준 | 높은 점수를 주는 경우 | 경고 신호 |
| --- | --- | --- |
| 학습 가치 | 지금 커리어 공백을 직접 메운다 | 이미 익숙한 것만 반복한다 |
| 완주 가능성 | 4~6주 안에 MVP를 낼 수 있다 | 핵심 기능이 세 개 이상이다 |
| 공개 가능성 | README와 데모로 설명할 수 있다 | 결과가 눈에 보이지 않는다 |
| 경계 관리 | 회사 자산, 고객 데이터와 분리된다 | 계약 조항이 모호하다 |

## 실제 사이드 프로젝트 사례

**성공 사례 1 — 문제에서 시작한 CLI 도구**: 팀에서 매번 환경변수 설정 파일을 복사하는 시간 낭비를 경험한 백엔드 개발자가 있었습니다. 이 문제를 해결하기 위해 주말 4시간씩 3주 동안 CLI 도구를 만들었습니다. GitHub에 공개했더니 두 달 만에 스타 150개가 생겼고, 이 프로젝트가 이직 면접에서 "실제 문제를 해결한 경험"으로 강하게 작용했습니다.

**성공 사례 2 — 학습 목적의 오픈소스 기여**: 주니어 개발자가 자주 쓰는 오픈소스 라이브러리에서 문서가 불명확한 부분을 찾아 PR을 보냈습니다. 처음에는 작은 문서 수정이었지만, 메인테이너와 대화하면서 코드 기여로 이어졌습니다. 6개월 후 해당 저장소의 기여자 목록에 이름이 올라갔고, 이후 시니어 개발자와의 네트워크가 형성됐습니다.

**실패 사례 — 너무 큰 아이디어**: "모든 개발자가 쓸 수 있는 프로젝트 관리 도구"를 만들겠다고 시작한 개발자가 있었습니다. 기능 목록이 20개를 넘었고, 아키텍처 설계만 두 달을 넘겼습니다. 결국 코드 한 줄 없이 포기했습니다. 아이디어를 "슬랙 채널에서 오늘 할 일을 정리해 주는 봇"으로 줄였더라면, 2주 만에 MVP가 나왔을 것입니다.

## 커리어 단계별 사이드 프로젝트 전략

**주니어 단계**: 기술 기초를 증명하는 프로젝트가 효과적입니다. CRUD API, 간단한 CLI 도구, 작은 웹 앱처럼 완성도가 명확한 것이 좋습니다. 복잡한 아키텍처보다 배포 링크와 README 품질이 더 중요합니다.

**미드 단계**: 현재 직무에서 경험한 실제 문제를 사이드 프로젝트로 해결하는 것이 가장 강합니다. "회사에서 이런 문제를 자주 겪어서 이걸 만들었습니다"라는 맥락이 있으면 포트폴리오 설명이 훨씬 설득력 있습니다.

**시니어 준비 단계**: 오픈소스 기여나 팀이 쓸 수 있는 도구를 만드는 것이 좋습니다. 팀 생산성에 기여하는 사이드 프로젝트는 기술 역량과 영향력을 동시에 보여줍니다.

## 10주 사이드 프로젝트 로드맵

| 주차 | 목표 | 산출물 | 완료 기준 |
| --- | --- | --- | --- |
| 1-2주 | 문제 정의/범위 고정 | PRD 1페이지, 핵심 사용자 시나리오 | 제외 기능 목록이 명확함 |
| 3-4주 | MVP 구현 | 핵심 기능 1개 동작 | 데모 영상 3분 촬영 가능 |
| 5-6주 | 데이터/로그 추가 | DB 스키마, 구조화 로그 | 오류 재현 경로 추적 가능 |
| 7-8주 | 테스트/배포 | 테스트 20개, CI 파이프라인 | 재배포 30분 내 가능 |
| 9-10주 | 문서화/공유 | README, 회고, 발표 자료 | 타인이 1시간 내 실행 가능 |

## 스킬 로드맵: 사이드 프로젝트로 역량 확장하기

| 기간 | 핵심 기술 | 습관 | 결과물 |
| --- | --- | --- | --- |
| 1-3개월 | 배포 / CI 파이프라인 구성 | 매주 토요일 4시간 시간박스 | 첫 MVP 배포, README |
| 4-6개월 | 관측성 / 에러 처리 | 배포마다 회고 1페이지 작성 | 운영 대시보드, 런북 |
| 7-9개월 | 테스트 / 코드 품질 | 기능 추가 전 테스트 먼저 | 테스트 커버리지 60% 이상 |
| 10-12개월 | 오픈소스 기여 / 사용자 피드백 | 월 1회 변경 로그 공개 | 외부 사용자 5명 이상 |

## 인터뷰 준비: 사이드 프로젝트 질문

**질문 — "사이드 프로젝트에 대해 소개해 주세요."**

약한 답변: "개인 학습 목적으로 만든 TODO 앱입니다."

강한 답변: "팀 미팅 노트가 슬랙과 노션에 분산되어 회의 후 액션 아이템 추적이 어려운 문제를 경험했습니다. 이를 해결하기 위해 슬랙 봇으로 미팅 요약을 자동 생성하는 도구를 만들었습니다. Python과 Slack API를 사용했고, OpenAI로 요약을 생성합니다. 현재 팀 3개에서 사용 중이며 주당 미팅 후속 시간을 30% 줄였습니다."

**질문 — "이 프로젝트에서 가장 어려웠던 기술적 도전은 무엇이었나요?"**

약한 답변: "처음 써보는 기술이라 어려웠습니다."

강한 답변: "Slack API의 rate limit이 예상보다 낮아서, 대화가 많은 채널에서 요약 생성이 실패하는 문제가 있었습니다. 재시도 로직과 지수 백오프를 구현했고, 큐를 추가해 대용량 채널도 처리할 수 있게 했습니다. 이 경험으로 외부 API 통합 시 rate limit을 먼저 확인하는 습관이 생겼습니다."

**질문 — "왜 이 기술 스택을 선택했나요?"**

강한 답변 구조: 문제 → 시도한 해결책 → 선택한 이유 → 결과 순서로 말합니다.

## 학습과 사이드 프로젝트 연결표

| 학습 주제 | 프로젝트 적용 과제 | 완료 신호 |
| --- | --- | --- |
| 인증/인가 | 로그인/권한 분리 구현 | 권한 테스트 통과 |
| 데이터 모델링 | 핵심 엔티티 스키마 재설계 | 쿼리 응답 속도 개선 |
| 관측성 | 에러 로깅/알람 추가 | 장애 원인 10분 내 파악 |
| 배포 자동화 | CI 파이프라인 구축 | 태그 기반 배포 성공 |
| 테스트 설계 | 핵심 비즈니스 로직 테스트 | 변경 후 회귀 없음 확인 |

## 공개 배포 전 점검표

| 항목 | 확인 질문 |
| --- | --- |
| 실행 재현성 | 다른 사람이 10분 안에 실행 가능한가 |
| 오류 처리 | 실패 시 사용자에게 행동 지침이 보이는가 |
| 관측성 | 최소한의 로그와 상태 페이지가 있는가 |
| 문서 품질 | 문제 정의와 아키텍처 선택 이유가 명확한가 |
| 라이선스 | LICENSE 파일이 있는가 |
| 보안 | 민감한 키/비밀번호가 저장소에 없는가 |

## 자주 하는 실수

| 실수 | 왜 발생하는가 | 개선 방법 |
| --- | --- | --- |
| 회사 코드를 섞는다 | 업무 중 아이디어가 떠오르기 때문 | 사이드 프로젝트는 반드시 개인 장비와 개인 계정으로만 진행한다 |
| 시간을 무한정 쓴다 | 완성하고 싶은 욕심 때문 | 주당 시간 예산을 정하고 초과하지 않는다 |
| MVP를 너무 크게 잡는다 | 처음부터 완벽하게 만들고 싶기 때문 | 기능을 줄이는 것이 완주의 핵심이라는 것을 기억한다 |
| 라이선스를 빼먹는다 | 개인 프로젝트라서 중요하지 않다고 생각하기 때문 | 저장소 생성 직후 LICENSE 파일을 먼저 추가한다 |
| 끝내 배포하지 않는다 | 아직 준비가 안 됐다고 느끼기 때문 | "완벽한 배포"보다 "불완전한 첫 배포"가 낫다는 원칙을 지킨다 |

## 시니어 엔지니어는 이렇게 생각합니다

- 작게 시작합니다.
- 배포가 동기부여를 만듭니다.
- 시간 박스가 건강을 지킵니다.
- 분리는 직업 안전입니다.
- 지속성이 결국 차이를 만듭니다.

3. MVP 기준을 한 줄로 적어 보세요.
4. 사이드 프로젝트 아이디어를 평가할 때 확인해야 할 3가지 기준을 적어 보세요.
5. 포트폴리오에서 사이드 프로젝트를 설명할 때 반드시 포함해야 할 정보를 두 가지 적어 보세요.

## 정리

좋은 사이드 프로젝트는 큰 꿈을 오래 품는 프로젝트가 아니라, 본업과 충돌하지 않는 범위 안에서 작게 만들고 실제로 끝내는 프로젝트입니다. 아이디어, 시간, 공개, 경계가 정리되면 사이드 프로젝트는 학습과 포트폴리오를 동시에 남겨 줍니다. 다음 글에서는 혼자 공부하는 한계를 넘기 위해 멘토링과 네트워킹을 어떻게 운영할지 정리하겠습니다.

## 처음 질문으로 돌아가기

- **본업과 충돌하지 않는 좋은 사이드 프로젝트는 어떤 조건을 가져야 할까요?**
  - 흥미가 있고, 배울 것이 분명하며, 본업과 충돌하지 않아야 합니다. 회사 자산과 분리되고, 4~6주 안에 MVP를 낼 수 있는 범위여야 지속됩니다.
- **너무 큰 아이디어 대신 작은 MVP로 시작해야 하는 이유는 무엇일까요?**
  - 범위가 크면 완주 확률이 급격히 떨어집니다. "기능을 추가하는 것"보다 "기능을 삭제하는 것"이 완주의 핵심입니다.
- **시간 박스, 공개, 피드백은 사이드 프로젝트를 어떻게 지속 가능하게 만들까요?**
  - 시간 박스는 건강을 지키고, 공개는 책임감을 만들며, 피드백은 다음 사이클의 동기부여가 됩니다. 세 가지가 함께 돌아야 지속됩니다.
