# Developer Career 101 (6/10): 시스템 디자인 인터뷰

시스템 디자인 인터뷰를 처음 보면 커다란 박스를 몇 개 그리고 끝내는 시험처럼 느껴지기 쉽습니다. 하지만 실제로는 요구사항을 정리하고, 대략 계산하고, 구성 요소를 세우고, 트레이드오프를 설명하는 순서를 얼마나 안정적으로 가져가는지가 더 중요합니다.

이 글은 Developer Career 101 시리즈의 6번째 글입니다.

![Developer Career 101 6장 흐름 개요](https://yeongseon-books.github.io/book-public-assets/assets/developer-career-101/06/06-01-concept-at-a-glance.ko.png)
*Developer Career 101 6장 흐름 개요*
> 시스템 디자인에서 가장 중요한 것은 정답보다는, 요구사항을 확인하고 제약 조건을 명시한 후 트레이드오프를 설명하는 과정입니다.

## 이 글에서 다룰 문제

- 시스템 디자인 인터뷰에서 면접관은 무엇을 실제로 평가할까요?
- 요구사항 확인, 추정, 상위 설계, 심화 설명은 어떤 순서로 진행해야 할까요?
- 트레이드오프와 병목을 말하지 못하면 왜 답변이 얕아 보일까요?
- 이 개념을 실무에서 잘못 적용하면 어떤 문제가 생길까요?
- 이 주제에서 초보자가 가장 자주 놓치는 포인트는 무엇일까요?

## 이 글에서 배울 것

- 네 단계 절차
- 요구사항을 끌어내는 법
- 러프한 추정 방법
- 컴포넌트 설계 방법
- 심화 설명과 트레이드오프 정리 방식

시스템 디자인은 시니어 레벨을 가르는 대표 필터입니다. 면접관은 정답 그림보다, 제약 속에서 우선순위를 세우고 판단을 설명하는 방식을 더 유심히 봅니다.

> 시스템 디자인 인터뷰는 큰 그림을 예쁘게 그리는 시험이 아니라, 제약 속에서 판단을 설명하는 시험입니다.

디자인 답변은 순서가 중요합니다. 요구사항을 정리하지 않고 박스부터 그리면 과하게 설계하거나 엉뚱한 방향으로 갈 수 있습니다. 반대로 요구사항, 추정, 상위 구조, 심화 설명의 순서를 지키면 답변이 훨씬 안정적으로 들립니다.

- **기능 요구사항**: 시스템이 해야 하는 기능입니다.
- **비기능 요구사항**: 성능과 가용성 같은 제약입니다.
- 추정: 거칠지만 방향을 잡는 계산입니다.
- 트레이드오프: 선택의 비용입니다.
- 병목: 전체를 제한하는 지점입니다.

## 개선 전/후

**Before**: "박스를 몇 개 그리면 된다고 생각합니다."

**After**: "요구사항, 추정, 설계, 심화 설명 순서로 답합니다."

## 직접 해보기: URL 단축기 설계하기

### 1단계 — Requirements

```text
functional: shorten, redirect, analytics
non-functional: 100M URLs, 99.99% availability
```

기능 요구사항과 비기능 요구사항을 먼저 나눠야 합니다. 단축과 리다이렉트, 통계가 필요한지부터 확인하고, 규모와 가용성 기준을 붙여야 설계 범위가 정해집니다.

### 2단계 — Estimate

```text
QPS: 1000 reads/s, 10 writes/s
storage: 100M * 500 bytes = 50 GB
```

추정은 정답을 맞히는 문제가 아니라 설계의 바닥을 만드는 단계입니다. 읽기와 쓰기 비중, 저장 용량 정도만 잡아도 캐시와 저장소 선택의 감이 생깁니다.

### 3단계 — Components

```text
LB → API → KV store
analytics → Kafka → DW
```

상위 구조에서는 주요 흐름이 보이면 충분합니다. 요청이 어디로 들어와 저장되고, 분석 데이터가 어디로 빠지는지 정도를 선명하게 설명하는 편이 좋습니다.

### 4단계 — Deep Dive

```text
- collision: base62 + counter
- cache: redis (LRU)
- DR: multi-AZ
```

심화 설명은 하나의 병목이나 핵심 설계 결정을 깊게 파는 단계입니다. 충돌 처리, 캐시 전략, 장애 복구 같은 지점에서 시니어다운 깊이가 드러납니다.

### 5단계 — Trade-offs

```text
SQL vs KV: consistency vs performance
```

트레이드오프를 말하지 않으면 설계가 평면적으로 보입니다. 어떤 선택이 어떤 비용을 가져오는지 설명해야 판단의 질이 드러납니다.

## 시스템 디자인 답변에서 깊이를 만드는 질문

| 단계 | 스스로 던질 질문 | 답변에 꼭 남길 것 |
| --- | --- | --- |
| 요구사항 | 지금 풀어야 할 핵심 시나리오는 무엇인가 | 기능/비기능 분리 |
| 추정 | 읽기와 쓰기 비율이 저장소 선택을 어떻게 바꾸는가 | QPS, 용량, 성장 가정 |
| 상위 설계 | 병목이 생기면 어디부터 흔들리는가 | 주요 흐름과 저장 경계 |
| 심화 설명 | 어떤 선택이 가장 큰 비용을 만드는가 | 캐시, 일관성, 장애 복구 트레이드오프 |

## 커리어 단계별 시스템 디자인 답변 수준

시스템 디자인 답변은 지원하는 레벨에 따라 기대 깊이가 다릅니다.

**주니어 지원 시**: 고수준 구조를 명확히 설명하는 것이 목표입니다. 모든 컴포넌트를 완벽하게 알지 않아도, 주요 요청 흐름과 저장소 경계를 설명할 수 있으면 충분합니다. 모르는 부분은 "이 부분은 더 알아봐야 할 것 같습니다"라고 솔직하게 말하는 것이 침묵보다 낫습니다.

**미드 지원 시**: 병목 지점 1~2개를 깊게 파야 합니다. 단순히 캐시를 추가한다고 말하는 것에서 끝내지 말고, 캐시 무효화 정책과 캐시 히트율 목표, 장애 시 폴백 전략까지 말해야 합니다.

**시니어 지원 시**: 운영 관점과 비즈니스 리스크까지 포함해야 합니다. "이 아키텍처가 초기에는 좋지만 트래픽이 10배 성장하면 어떤 부분부터 바꿔야 하는가"처럼 단계별 확장 전략을 말할 수 있어야 합니다.

## 실제 시스템 디자인 면접 사례

**사례 1 — 주니어의 성공적인 답변**: 신입 지원자가 "채팅 시스템을 설계하라"는 질문을 받았습니다. 처음에는 WebSocket부터 그리려 했지만, 먼저 "일대일 채팅인지 그룹 채팅인지, 메시지 기록 저장이 필요한지"를 확인했습니다. 요구사항 정리만으로도 면접관이 "올바른 방향으로 사고하고 있다"고 판단했고, 이후 단계에서 모르는 부분은 솔직하게 "저는 이 부분까지 알고 있고 여기서 트레이드오프가 있을 것 같다"고 말했습니다. 결과적으로 최종 합격했습니다.

**사례 2 — 미드 레벨 지원자의 흔한 실수**: 3년 차 개발자가 피드 서비스 설계 질문에서 요구사항 확인 없이 바로 팬아웃 전략을 설명하기 시작했습니다. 면접관이 "사용자가 몇 명 정도인지 가정했나요?"라고 물었을 때 답하지 못했고, 이미 그린 아키텍처가 요구사항에 맞지 않는다는 것을 뒤늦게 깨달았습니다. 추정 단계를 건너뛴 결과였습니다.

**사례 3 — 시니어 지원자의 차별화 포인트**: 시니어 지원자가 결제 시스템 설계 질문에서 단순히 아키텍처를 그리는 데 그치지 않고, "이 설계에서 가장 큰 위험은 중복 결제 처리입니다. 멱등성 키를 어떻게 구현할지와 장애 시 보상 트랜잭션 전략을 먼저 논의하고 싶습니다"라고 말했습니다. 비즈니스 리스크를 먼저 인식했다는 점에서 높은 평가를 받았습니다.

## 시스템 디자인 준비: 실전 케이스 학습법

| 케이스 | 핵심 학습 포인트 | 준비 기간 |
| --- | --- | --- |
| URL 단축기 | 해시 충돌, KV 저장소, 캐시 전략 | 1주 |
| 채팅 시스템 | WebSocket, 메시지 순서, 오프라인 처리 | 1주 |
| 피드 서비스 | 팬아웃, 읽기/쓰기 비율, 정렬 | 1주 |
| 결제 시스템 | 멱등성, 트랜잭션, 장애 복구 | 1주 |
| 검색 자동완성 | 트라이, 캐시, 실시간성 | 1주 |

## 설계 답변 기본 템플릿

1. 문제 경계 확정: 사용자, 기능, 비기능 요구사항 확인
2. 대략적 용량 산정: QPS, 저장 용량, 읽기/쓰기 비율
3. API와 데이터 모델: 핵심 엔티티와 계약 정의
4. 고수준 아키텍처: 요청 경로, 캐시, 비동기 큐 배치
5. 병목/장애 대응: 단일 장애점, 백프레셔, 재시도 정책
6. 마무리 트레이드오프: CAP/비용/운영 복잡도 정리

## 아키텍처 트레이드오프 설명 훈련

| 선택지 | 장점 | 리스크 | 언제 적합한가 |
| --- | --- | --- | --- |
| 단일 DB 확장 | 단순한 운영 | 수직 확장 한계 | 초기 단계, 낮은 QPS |
| 읽기 복제본 | 조회 확장 용이 | 복제 지연 | 읽기 비중이 높은 서비스 |
| 샤딩 | 큰 확장성 | 라우팅 복잡도 증가 | 데이터 폭증 구간 |
| CQRS | 읽기/쓰기 최적화 분리 | 이벤트 동기화 관리 | 읽기/쓰기 패턴이 극단적으로 다를 때 |
| 이벤트 소싱 | 감사 추적, 재생 가능 | 쿼리 복잡도 증가 | 규정 준수가 중요한 금융/결제 |

## 인터뷰 준비: 시스템 디자인 핵심 질문

**질문 — "이 설계에서 가용성과 일관성 중 무엇을 선택했나요?"**

약한 답변: "가용성이 중요하다고 생각합니다."

강한 답변: "이 서비스에서 사용자가 가장 많이 경험하는 시나리오는 읽기이고, 약간의 일관성 지연(최종 일관성)은 허용 가능합니다. 그래서 가용성을 우선했고, 쓰기 실패 시 재시도 큐와 멱등성 키로 데이터 손실을 방지하는 방향으로 보완했습니다."

**질문 — "단일 데이터베이스에서 시작해 언제 샤딩을 도입하겠습니까?"**

강한 답변 구조: 현재 단계 기준 설명 + 병목이 나타나는 임계값 + 마이그레이션 전략 + 운영 영향 평가 순서로 말합니다.

## 요구사항 확인 질문 뱅크

면접에서 즉시 꺼낼 수 있는 요구사항 확인 질문 목록입니다.

**사용자/규모 관련**:
- "동시 사용자 수는 어느 정도로 가정할까요?"
- "읽기와 쓰기 비율은 어떻게 되나요?"
- "데이터 보존 기간은 얼마나 되나요?"

**기능 범위 관련**:
- "검색 기능도 포함해야 하나요, 아니면 기본 CRUD만 먼저 설계할까요?"
- "알림 기능은 이번 설계 범위에 포함하나요?"

**비기능 요구사항 관련**:
- "가용성 목표는 99.9%인가요, 아니면 99.99%인가요?"
- "읽기 지연시간 목표값은 어느 정도인가요?"
- "지역별 분산 배포가 필요한가요?"

## 용량 추정 훈련: 자주 쓰는 기준값

| 항목 | 기준값 | 활용 예시 |
| --- | --- | --- |
| 평균 텍스트 메시지 | 100 bytes | 채팅 시스템 저장 용량 추정 |
| 평균 이미지 | 300 KB | 이미지 업로드 서비스 대역폭 추정 |
| Redis 캐시 항목 | ~1 KB | 캐시 메모리 크기 추정 |
| DB 행 평균 크기 | 500 bytes | 관계형 DB 용량 추정 |
| 일일 활성 사용자 → QPS | DAU × 평균 요청 수 / 86400 | 어떤 서비스든 기본 QPS 계산 |

## 시스템 디자인 면접 일정표 (6주)

| 주차 | 핵심 주제 | 실전 연습 | 회고 포인트 |
| --- | --- | --- | --- |
| 1주 | 요구사항 정리 프레임 | 채팅 시스템 요구사항 정리 2회 | 질문 누락 개수 |
| 2주 | 용량 추정 | URL 단축기 QPS/스토리지 계산 3회 | 단위 변환 실수 |
| 3주 | 데이터 모델링 | 피드 서비스 스키마 설계 2회 | 정규화/비정규화 근거 |
| 4주 | 병목/확장 전략 | 캐시 계층 설계 2회 | 장애 지점 식별 |
| 5주 | 일관성/가용성 | 주문 시스템 트랜잭션 설계 | 보상 트랜잭션 설명력 |
| 6주 | 모의 면접 | 60분 실전 2회 | 시간 배분 안정성 |

## 승진 기준과 연결되는 답변 매트릭스

| 평가 항목 | 주니어 기준 | 미들 기준 | 시니어 기준 |
| --- | --- | --- | --- |
| 문제 분해 | 기능 단위로 설명 | 트래픽/장애 시나리오 포함 | 비즈니스 리스크까지 구조화 |
| 기술 선택 | 단일 솔루션 제시 | 대안 비교 제시 | 비용/운영/조직 영향까지 비교 |
| 확장 전략 | Scale Out 언급 | 병목 포인트 기반 확장 | 단계별 마이그레이션 계획 제시 |
| 운영 관점 | 로그/모니터링 언급 | SLI/SLO 기준 제안 | 온콜/복구 절차까지 설계 |

## 스킬 로드맵: 시스템 디자인 역량 쌓기

| 기간 | 핵심 기술 | 학습 방법 | 결과물 |
| --- | --- | --- | --- |
| 1-4주 | 요구사항 정리 / 용량 추정 | 케이스 2개 매주 1회씩 설계 | 요구사항 질문 10개 목록 |
| 5-8주 | 데이터 모델링 / 캐시 전략 | 각 케이스 심화 설명 추가 | 트레이드오프 비교 메모 5개 |
| 9-12주 | 장애 복구 / 관측성 | 모의 면접 주 1회 | 60분 완주 모의 면접 2회 |
| 3개월 이후 | 설계 문서 작성 / 리뷰 | 실무 설계 결정에 ADR 적용 | 팀 내 설계 리뷰 1회 발표 |

## 자주 하는 실수

| 실수 | 왜 발생하는가 | 개선 방법 |
| --- | --- | --- |
| 요구사항을 건너뛴다 | 빨리 설계를 보여주고 싶기 때문 | 요구사항 확인 질문을 5개 이상 준비해 루틴화한다 |
| 추정을 전혀 하지 않는다 | 어림잡기가 두렵기 때문 | "대략 이 정도로 가정하겠습니다"로 시작하는 습관을 만든다 |
| 트레이드오프를 말하지 않는다 | 정답만 제시하면 된다고 착각하기 때문 | 모든 설계 결정에 대안 하나를 붙이는 훈련을 한다 |
| 병목을 짚지 못한다 | 전체 그림만 보기 때문 | "이 시스템에서 가장 먼저 터지는 곳은 어디인가"를 항상 자문한다 |
| 시간 관리를 못한다 | 한 부분에 과도하게 집중하기 때문 | 각 단계별 시간 배분을 모의 면접에서 연습한다 |

## 시니어 엔지니어는 이렇게 생각합니다

- 디자인은 대화입니다.
- 추정은 근육입니다.
- 트레이드오프는 설계의 언어입니다.
- 심화 설명이 깊이를 보여 줍니다.
- 시간 관리도 훈련입니다.

## 운영 체크리스트

- [ ] 기능과 비기능 요구사항을 나눴습니다.
- [ ] 추정을 명시했습니다.
- [ ] 트레이드오프를 말했습니다.
- [ ] 병목 하나를 깊게 설명했습니다.

## 연습 문제

1. QPS를 한 줄로 설명해 보세요.
2. 비기능 요구사항 예시를 한 줄로 적어 보세요.
3. 병목 예시를 한 줄로 적어 보세요.
4. URL 단축기 설계에서 해시 충돌을 어떻게 처리할지 두 줄로 설명해 보세요.
5. 읽기 복제본과 샤딩의 차이를 한 줄로 설명해 보세요.

## 정리

시스템 디자인 인터뷰는 정답 도안을 맞히는 시험이 아니라, 제한된 시간 안에 요구사항을 구조화하고 판단을 설명하는 시험입니다. 요구사항, 추정, 상위 설계, 심화 설명의 순서를 몸에 익히면 답변이 훨씬 안정적으로 정리됩니다. 다음 글에서는 면접을 넘어 실제 첫 직장에서 처음 90일을 어떻게 보내야 하는지 정리하겠습니다.

## 처음 질문으로 돌아가기

- **시스템 디자인 인터뷰에서 면접관은 무엇을 실제로 평가할까요?**
  - 정답 그림이 아니라 요구사항을 구조화하고 제약 속에서 우선순위를 세우는 방식을 평가합니다. 판단의 질과 설명의 일관성이 핵심입니다.
- **요구사항 확인, 추정, 상위 설계, 심화 설명은 어떤 순서로 진행해야 할까요?**
  - 기능/비기능 요구사항 확인 → 용량 추정 → 상위 구조 → 병목 심화 설명 → 트레이드오프 순서입니다. 요구사항 없이 설계부터 그리면 방향이 틀어질 수 있습니다.
- **트레이드오프와 병목을 말하지 못하면 왜 답변이 얕아 보일까요?**
  - 트레이드오프 없이 제시하는 설계는 "이게 유일한 방법"처럼 들립니다. 실제 시스템 설계에는 항상 선택의 비용이 있고, 그 비용을 인식한다는 것이 경험의 증거입니다.
