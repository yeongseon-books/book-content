# 바이브코딩을 위한 AI 웹 개발 (7/7): 평가와 개선

> 이 글은 **바이브코딩을 위한 AI 웹 개발** 시리즈 7편입니다. 키워드 스코어링, LLM-as-Judge, RAG 메트릭으로 AI 앱 품질을 측정하고 CI에 통합하는 방법을 다룹니다.

바이브코딩으로 AI 앱을 빠르게 만들고 배포했다면, 이제 가장 어려운 질문이 남는다. "잘 되고 있는 건가?" 일반 소프트웨어는 단위 테스트와 통합 테스트로 검증할 수 있지만, AI 앱은 정해진 정답이 없다. 같은 질문에 매번 다른 표현으로 답이 나오고, "좋은 답변"의 기준도 맥락에 따라 달라진다.

평가의 첫 걸음은 테스트 셋을 만드는 것이다. 실제 사용자 질문이나 예상 시나리오를 JSON으로 정리하고, expected_keywords나 reference_answer를 함께 기록한다. 키워드 스코어링은 가장 간단한 방법으로, 응답에 예상 키워드가 몇 개 포함됐는지 비율을 계산한다.

LLM-as-Judge는 한 단계 위다. GPT-4 같은 강력한 모델에게 "이 응답이 기준을 충족하는지 1-5점으로 평가해줘"라고 요청하면, 키워드 매칭으로 잡을 수 없는 의미적 품질을 측정할 수 있다. 판단 근거(rationale)도 함께 요청하면 어디서 실패하는지 파악하기 쉽다.

RAG 시스템은 검색 품질과 응답 품질을 분리해서 측정해야 한다. retrieval_hit@k는 정답 문서가 상위 k개 안에 들어오는지, faithfulness는 응답이 검색 문서에 근거하는지, citation_coverage는 인용 출처가 충분한지를 본다. 검색이 나쁜데 응답만 좋아 보이는 경우를 잡으려면 두 메트릭을 함께 봐야 한다.

이 평가를 CI에 통합하면 바이브코딩의 빠른 반복 속도를 유지하면서도 품질 저하를 자동으로 감지할 수 있다. 프롬프트를 수정했을 때 이전보다 나빠졌는지 즉시 알 수 있다.

> AI 앱 평가는 "맞다/틀리다"가 아니라 "얼마나 기준에 가까운가"를 측정하는 일입니다. 테스트 셋, 스코어링 함수, CI 통합이 갖춰지면 바이브코딩의 속도를 안전하게 유지할 수 있습니다.

## 이 글에서 다룰 문제

- AI 앱 품질을 어떻게 측정해야 할까요?
- 키워드 스코어링과 LLM-as-Judge는 어떻게 다른가요?
- RAG 시스템의 검색 품질과 응답 품질은 어떻게 분리해서 평가할까요?
- 평가를 CI에 통합하는 방법은 무엇인가요?
- 평가 결과를 바탕으로 어떻게 개선해야 할까요?

## Before / After: 평가 도입 전후

| 상황 | 평가 없이 | 평가 도입 후 |
|------|----------|------------|
| 품질 확인 | 수동으로 몇 가지 테스트 | 테스트 셋 자동 실행 |
| 프롬프트 변경 | 체감으로 판단 | 스코어 비교로 확인 |
| RAG 오류 | 검색인지 응답인지 모름 | retrieval_hit@k로 분리 |
| 배포 전 검증 | 생략하거나 수동 | CI에서 자동 품질 게이트 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 테스트 셋 없이 체감으로 평가 | 프롬프트 변경 영향 추적 불가 | 최소 20-30개 테스트 케이스 확보 |
| 키워드 스코어링만 사용 | 의미적으로 맞아도 0점 | LLM-as-Judge 병행 |
| RAG 전체를 하나로 평가 | 어디서 실패하는지 모름 | 검색(retrieval_hit@k)과 응답(faithfulness) 분리 |
| 평가를 CI에서 제외 | 배포 후 품질 저하 발견 | PR마다 자동 평가 실행 |

## AI 팁: 평가 빠르게 시작하는 방법

Claude나 GPT-4에 "Python으로 AI 챗봇 평가 스크립트를 만들어줘. 테스트 셋은 JSON 파일로 읽고, 키워드 스코어링과 LLM-as-Judge를 같이 실행하고, 결과를 CSV로 저장해줘"라고 요청하면 작동하는 코드를 얻을 수 있다. 테스트 셋은 `{"question": "...", "expected_keywords": ["..."], "reference_answer": "..."}`  형태로 시작한다. LLM-as-Judge는 `"다음 응답을 1-5점으로 평가하고 이유를 JSON으로 답해줘"` 형태의 system 프롬프트로 구성한다. GitHub Actions에서는 `pytest` 또는 `python eval.py --fail-below 0.8`로 품질 게이트를 만들 수 있다.

## 운영 체크리스트

- [ ] 최소 20개 이상의 테스트 케이스를 JSON으로 관리하는가
- [ ] 키워드 스코어링과 LLM-as-Judge를 병행하는가
- [ ] RAG 시스템은 retrieval_hit@k와 faithfulness를 분리해서 측정하는가
- [ ] 평가 결과를 CI에서 자동으로 실행하고 임계값 이하 시 실패 처리하는가
- [ ] 프롬프트 변경 시 이전 버전과 스코어를 비교하는가

## 처음 질문으로 돌아가기

- **키워드 스코어링 vs LLM-as-Judge 차이는?** 키워드 스코어링은 빠르고 결정론적이지만 의미를 놓친다. LLM-as-Judge는 느리고 비용이 있지만 맥락을 이해한다. 두 가지를 함께 써야 한다.
- **RAG 평가를 분리해야 하는 이유는?** 검색이 나쁜데 응답이 좋아 보이거나, 검색이 좋은데 응답이 나쁜 경우를 구분해야 개선 방향을 잡을 수 있다.
- **CI 통합의 핵심은?** 평가 스크립트를 PR마다 자동 실행하고, 기준 스코어 이하 시 merge를 막는 품질 게이트가 핵심이다.

## 정리

AI 앱 평가는 테스트 셋, 스코어링 함수, CI 통합 세 가지로 구성된다. 키워드 스코어링으로 기본 커버리지를 잡고, LLM-as-Judge로 의미적 품질을 측정하고, RAG 메트릭으로 검색과 응답을 분리한다. 이 구조가 있으면 바이브코딩의 빠른 반복 속도를 유지하면서도 품질이 떨어지는 순간을 즉시 감지할 수 있다.
