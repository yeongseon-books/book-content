# 바이브코딩을 위한 AI 웹 개발 (2/7): 프롬프트 엔지니어링 기초

> 이 글은 **바이브코딩을 위한 AI 웹 개발** 시리즈 2편입니다. system/user 역할 분리, 출력 계약 설계, 프롬프트 버전 관리를 다룹니다.

바이브코딩으로 AI 앱을 만들다 보면 같은 모델을 써도 결과가 천차만별이라는 걸 금방 느낀다. 누구는 바로 쓸 수 있는 결과를 얻고, 누구는 몇 번 묻다가 그냥 넘어간다. 차이는 모델 성능보다 요청을 어떻게 구조화했는지에서 갈린다.

AI는 마음을 읽지 않는다. "보고서 좀 써줘"라고만 말하면 주제, 분량, 독자, 형식이 비어 있어서 가장 무난한 답이 나온다. 서비스 코드 안에서 재사용할 프롬프트는 실패할 때 원인을 좁힐 수 있어야 한다. 프롬프트 엔지니어링은 글쓰기 감각만이 아니라 디버깅 감각과 검증 습관까지 포함한다.

system과 user 역할은 명확히 분리해야 한다. system은 모델의 기본 역할, 태도, 금지 사항이고, user는 지금 수행해야 할 구체적인 작업과 입력값이다. 좋은 프롬프트의 네 원칙은 역할(모델에게 전문성 부여), 맥락(도메인과 제약 설명), 출력 포맷(JSON/마크다운 등 형식 명시), 제약(하지 말아야 할 것 명시)이다.

temperature와 max_tokens도 제어해야 한다. 창의적 작업은 temperature를 높이고, 결정론적 파싱이 필요하면 0.0으로 고정한다. max_tokens는 응답 비용과 직결되므로 적절한 상한을 두어야 한다.

프롬프트는 코드처럼 버전 관리해야 한다. 같은 입력에 대해 어제와 오늘 응답이 달라진 원인을 추적하려면 프롬프트 버전과 함께 기록이 남아야 한다.

> 프롬프트는 영리한 문장이 아니라 실행 가능한 계약입니다. system은 오래 유지되는 규칙, user는 이번 작업의 입력이고, 이 분리가 모델 동작을 안정적으로 만드는 핵심입니다.

## 이 글에서 다룰 문제

- system과 user 역할은 각각 어떤 책임을 가져야 할까요?
- 좋은 프롬프트의 네 가지 원칙은 무엇인가요?
- temperature와 max_tokens는 어떻게 설정해야 할까요?
- 프롬프트를 버전 관리해야 하는 이유는 무엇인가요?
- 출력 포맷 계약을 어떻게 설계해야 파싱이 안정적일까요?

## Before / After: 프롬프트 구조화 전후

| 상황 | 구조화 전 | 구조화 후 |
|------|-----------|-----------|
| 응답 일관성 | 매번 달라짐 | 출력 포맷 계약으로 안정화 |
| 실패 원인 파악 | "모델이 이상함" | 어느 제약이 빠졌는지 좁힘 |
| 프롬프트 변경 영향 | 모름 | 버전 관리 + regression 비교 |
| 응답 파싱 | 매번 수동 처리 | JSON 출력 계약으로 자동화 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| system과 user를 한 메시지에 혼합 | 역할 구분 없어 불안정 | system에 역할/제약, user에 작업만 |
| 출력 형식 미명시 | 마크다운/JSON 혼재 | "JSON으로 응답해줘" 명시 |
| temperature를 기본값으로 방치 | 창의/결정론 구분 불가 | 작업 특성에 맞게 조정 |
| 프롬프트를 코드에 하드코딩 | 버전 추적 불가 | 별도 파일/변수로 분리 관리 |

## AI 팁: 프롬프트 구조 빠르게 설계하는 방법

Claude나 GPT-4에 "Python으로 시스템 프롬프트와 유저 프롬프트를 분리하고, JSON 출력 계약을 강제하며, temperature=0으로 결정론적 응답을 받는 코드를 만들어줘"라고 요청하면 바로 쓸 수 있는 구조를 얻을 수 있다. system 메시지에 역할, 제약, 출력 형식을 넣고, user 메시지에는 실제 입력만 넣는 것이 핵심이다. 프롬프트는 Python 파일의 상수나 별도 텍스트 파일로 분리해서 버전 관리한다.

## 운영 체크리스트

- [ ] system 메시지에 역할, 도메인, 출력 형식, 금지 사항을 명시했는가
- [ ] user 메시지에는 이번 작업 입력만 들어가는가
- [ ] temperature를 작업 특성에 맞게 설정했는가
- [ ] max_tokens 상한을 설정해 비용을 통제하는가
- [ ] 프롬프트를 코드에서 분리해 버전 관리하는가

## 처음 질문으로 돌아가기

- **system vs user 역할 차이는?** system은 오래 유지되는 역할과 제약, user는 이번 요청의 구체적인 작업과 입력이다.
- **출력 포맷 계약이 중요한 이유는?** 형식을 명시하지 않으면 마크다운, JSON, 자유 텍스트가 뒤섞여 파싱이 어려워진다.
- **프롬프트 버전 관리가 필요한 이유는?** 어제와 오늘 응답이 달라진 원인을 추적하려면 프롬프트 변경 이력이 있어야 한다.

## 정리

프롬프트 엔지니어링은 "잘 물어보는 기술"이 아니라 실행 가능한 계약을 설계하는 일이다. system과 user를 분리하고, 출력 형식을 명시하고, 제약을 구체적으로 쓰면 모델 동작이 훨씬 예측 가능해진다. 이 습관이 있어야 바이브코딩의 빠른 속도를 유지하면서도 일관된 AI 기능을 만들 수 있다.
