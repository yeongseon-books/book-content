# 바이브코딩을 위한 LLM 밑바닥부터 (1/9): 글자를 숫자로 바꾸기

이 글은 바이브코딩을 위한 LLM 밑바닥부터 시리즈의 1번째 글입니다.

LLM을 처음 배울 때 가장 흔한 오해는 모델이 문장을 그대로 읽는다는 생각입니다. 하지만 신경망이 실제로 받는 것은 문자열이 아니라 정수 배열입니다. 토크나이저는 단순한 전처리 단계가 아니라, 텍스트를 정수로 바꾸는 엄격한 계약입니다. 이 계약이 바뀌면 같은 데이터셋도 다른 학습 문제로 바뀝니다.

바이브코딩에서 이 개념이 중요한 이유는 단순합니다. AI에게 토크나이저 코드를 요청할 때 char-level과 서브워드의 차이를 모르면, 생성된 코드가 어떤 입력 계약을 만드는지 검증할 수 없기 때문입니다.

> 모델은 텍스트를 읽지 않습니다. 토크나이저가 정의한 규칙에 따라 만들어진 정수 시퀀스만 읽습니다. 이 출발점을 정확히 잡지 못하면 이후 임베딩·어텐션·학습의 모든 개념이 조금씩 공중에 뜹니다.

---

## 이 글에서 다룰 문제

- 모델은 왜 문자열 대신 정수 시퀀스를 입력으로 받아야 할까요?
- 문자 단위·단어 단위·서브워드 토큰화는 각각 무엇을 얻고 무엇을 잃을까요?
- BPE는 어떤 식으로 어휘를 조금씩 키워 갈까요?
- vocab 밖 문자를 잘못 다루면 어떤 장애가 생길까요?
- 자주 하는 실수와 그 해결책은 무엇일까요?

토크나이저를 이해하면 AI가 생성한 LLM 코드의 입력 계약을 검증할 수 있게 됩니다. 이것이 바이브코딩 시대에 이 개념을 배우는 이유입니다.

## Before / After

**Before — AI에게 컨텍스트 없이 질문:**

```
Q: "GPT 모델 입력 전처리 코드 만들어줘"
→ 어떤 토큰화 방식인지 불명확
→ vocab 밖 문자 처리 없어 런타임 오류
→ encode/decode 역변환 쌍이 빠진 코드 생성
```

**After — 개념을 이해하고 구체적으로 질문:**

```
Q: "TinyShakespeare 텍스트에서 char-level 토크나이저를 만들어줘.
    stoi, itos, encode, decode를 포함하고,
    encode(decode(ids)) == ids를 검증하는 테스트도 넣어줘"
→ 완전한 양방향 변환 보장
→ vocab 크기와 입력 계약 명확화
```

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| encode/decode 역변환을 검증하지 않음 | 데이터가 손상되어도 모름 | encode(decode(ids)) == ids 항상 확인 |
| vocab 밖 문자 처리 생략 | 런타임 KeyError로 서버 중단 | unknown char 드롭 또는 UNK 토큰 처리 |
| 토크나이저와 모델을 다른 vocab으로 실행 | 토큰 의미가 어긋나 쓰레기 출력 | 어댑터와 베이스는 항상 같은 토크나이저 |
| 서브워드 토크나이저를 char-level 코드에 그대로 붙임 | vocab 크기, 특수 토큰 불일치 | 방식을 먼저 결정하고 코드 요청 |
| 토큰 수와 문자 수를 같다고 가정 | 길이 기반 로직이 모두 틀림 | len(encode(text))가 len(text)와 다를 수 있음 |

## AI 협업 팁

토크나이저 관련 효과적인 AI 프롬프트 패턴:

1. **char-level 요청**: "텍스트 파일에서 고유 문자 집합으로 stoi/itos 딕셔너리를 만들고 encode/decode 함수를 작성해줘"
2. **검증 요청**: "encode(decode(ids)) == ids를 assert하는 단위 테스트 코드 작성해줘"
3. **vocab 점검 요청**: "텍스트에서 vocab 밖 문자를 찾아 경고하는 함수 작성해줘"

예시 프롬프트:
> "input.txt에서 char-level 토크나이저를 만들어줘. sorted(set(text))로 vocab 구성, stoi/itos 딕셔너리, encode/decode 함수, encode(decode(ids)) == ids 검증 테스트 포함해줘."

## 운영 체크리스트

- [ ] 모델이 정수 시퀀스만 입력으로 받는 이유를 설명할 수 있는가?
- [ ] char-level과 서브워드 토큰화의 차이를 한 문장으로 설명할 수 있는가?
- [ ] encode(decode(ids)) == ids를 검증했는가?
- [ ] vocab 밖 문자를 만났을 때 어떻게 처리하는지 결정했는가?
- [ ] vocab 크기가 이후 임베딩 행렬 크기에 연결된다는 점을 이해했는가?

## 처음 질문으로 돌아가기

토크나이저를 배운 지금, AI에게 이 주제로 더 정확한 질문을 할 수 있게 되었습니다. 입력 계약을 명시한 사람과 그렇지 않은 사람이 AI에게 받는 코드의 신뢰도는 크게 다릅니다.

## 정리

토크나이저는 바이브코딩을 위한 LLM 밑바닥부터 시리즈의 출발점입니다. char-level 방식으로 encode/decode를 구현하고, vocab 계약이 이후 임베딩과 모델 전체에 어떻게 연결되는지 이해했습니다. 다음 글에서는 정수 ID를 벡터로 바꾸는 임베딩을 다룹니다.
