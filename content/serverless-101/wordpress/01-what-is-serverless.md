# 바이브코딩을 위한 서버리스 기초 (1/10): 서버리스란 무엇인가?

이 글은 **바이브코딩을 위한 서버리스 기초** 시리즈의 첫 번째 글입니다. AI가 생성한 함수를 서버 없이 바로 배포하고 싶다면, 서버리스가 무엇인지부터 정확히 이해해야 합니다. 이 시리즈는 바이브코딩 환경에서 실제로 마주치는 배포, 비용, 실패 시나리오를 중심으로 서버리스 개념을 10편에 걸쳐 설명합니다.

---

## 바이브코딩과 서버리스, 왜 연결해서 봐야 할까요?

AI에게 "주문 접수 API 만들어줘"라고 하면 1분 안에 Python 함수 코드가 나옵니다. 그런데 그 함수를 어디에, 어떻게 올릴지는 AI가 대신 결정해 주지 않습니다. 바로 이 순간, 서버리스가 가장 자주 선택됩니다.

> 서버리스는 서버가 사라진 것이 아니라, 서버 관리·확장·과금의 단위가 요청 한 건 단위로 잘게 쪼개진 모델입니다.

이 개념을 모르면 AI가 만들어 준 코드를 배포한 뒤 왜 느린지, 왜 갑자기 비용이 나오는지, 왜 가끔 실패하는지 설명하기 어렵습니다. 서버리스를 이해한다는 말은 AI가 만든 함수의 운영 계약을 이해한다는 뜻입니다.

## 이 글에서 다룰 문제

- 서버리스는 정확히 무엇을 플랫폼에 넘기는 실행 모델일까요?
- 첫 번째 서버리스 함수는 어떤 입력 계약과 응답 계약으로 시작해야 할까요?
- 로컬 호출과 실제 배포 사이에서 최소한 무엇을 맞춰 두어야 할까요?
- 서버리스 환경에서 이 개념이 전통 서버와 어떻게 다르게 작동할까요?
- 비용과 성능 사이 트레이드오프는 어디서 발생할까요?

---

## 서버리스가 뭔지 모르면 배포 후에 막힙니다

바이브코딩으로 함수를 뚝딱 만들었는데, 막상 배포하고 나면 이런 일이 생깁니다. 첫 번째 호출이 유독 느리고, 동시 요청이 몰리면 데이터베이스가 터지고, 한 달 뒤 청구서에 예상치 못한 금액이 찍혀 있습니다. 이 모든 것이 "서버리스가 어떻게 작동하는가"를 몰라서 생기는 일입니다.

서버리스를 처음 들으면 대개 "서버를 안 만지는 방식이구나"라고 이해합니다. 방향은 맞지만, 그 한 문장만으로는 이후 판단이 자꾸 틀어집니다. 서버가 사라지는 것이 아니라 **서버 운영 책임의 기본값이 플랫폼으로 이동**하기 때문입니다.

그래서 서버리스 입문에서 가장 먼저 잡아야 할 질문은 "함수를 어떻게 쓰지?"가 아닙니다. **"이 워크로드를 정말 서버리스로 시작해도 되는가?"**입니다. 이 판단을 먼저 해 두어야 첫 번째 함수 예제도 의미가 생기고, 뒤이어 나올 FaaS, 트리거, 콜드 스타트, 비용 이야기도 같은 멘탈 모델 안에서 읽힙니다.

## Before vs After: 서버리스 도입 전후 변화

| 구분 | Before (전통 서버) | After (서버리스) |
|------|-------------------|-----------------|
| 서버 관리 | 직접 프로비저닝, 패치, 스케일링 | 플랫폼이 담당 |
| 비용 단위 | 서버 시간 고정 과금 | 실행 시간 × 메모리 × 호출 수 |
| 배포 단위 | 전체 앱 또는 컨테이너 | 함수 단위 |
| 콜드 스타트 | 없음 (상시 기동) | 유휴 후 첫 호출 시 지연 발생 |
| 상태 관리 | 프로세스 메모리 활용 가능 | 외부 저장소 필수 |

## 자주 하는 실수

| 실수 | 왜 문제인가 | 올바른 접근 |
|------|------------|------------|
| 함수 안에 세션 저장 | 인스턴스가 재시작되면 데이터 소실 | Redis 등 외부 저장소 사용 |
| 모든 워크로드에 서버리스 적용 | 장시간 작업은 타임아웃으로 실패 | 적합성 결정 사다리 먼저 통과 |
| 평균 지연만 모니터링 | 콜드 스타트가 p99를 크게 높임 | p95/p99 지표 추적 |
| 메모리 최소값 고정 | 실행 시간 증가로 총비용 상승 가능 | 측정 후 튜닝 |

## AI 팁: 바이브코딩에서 서버리스 시작하기

AI에게 함수를 만들어 달라고 할 때 이렇게 물어보세요.

> "이 함수가 서버리스에 적합한지 적합성 결정 사다리로 먼저 평가해줘. 요청이 수 초 안에 끝나는지, 상태를 외부 저장소에 분리할 수 있는지, 트래픽이 불규칙한지 각각 판단해줘."

AI가 코드를 만들어 주더라도, 그 코드가 서버리스 환경에서 안전한지는 사람이 질문해야 합니다. 특히 다음 세 가지를 항상 확인하세요.

1. 입력 이벤트와 응답 형식이 명시되어 있는가
2. 상태를 외부 저장소로 분리할 계획이 있는가
3. 요청 추적용 `request_id` 필드를 남기는가

---

## 서버리스 적합성 결정 사다리

AI가 만든 함수를 배포하기 전에 이 네 가지 질문을 먼저 통과시키세요.

1. **요청이 수 초 안에 끝나는가?**
   - 예: 다음 질문으로 갑니다.
   - 아니오: 장시간 작업, 실시간 스트리밍은 다른 실행 환경이 더 적합합니다.

2. **호출마다 필요한 상태를 외부 저장소에서 읽고 쓸 수 있는가?**
   - 예: 다음 질문으로 갑니다.
   - 아니오: 프로세스 메모리에 상태를 오래 붙잡아야 한다면 서버리스 기본값은 위험합니다.

3. **트래픽이 들쭉날쭉하거나 예측하기 어려운가?**
   - 예: 서버리스의 탄력성이 강점이 됩니다.
   - 아니오: 일정하고 지속적인 부하라면 상시 실행 환경이 비용상 더 단순할 수 있습니다.

4. **플랫폼이 정한 타임아웃, 패키징, 런타임 제약을 받아들일 수 있는가?**
   - 예: 서버리스가 좋은 출발점입니다.
   - 아니오: 세밀한 런타임 제어가 필요하다면 컨테이너나 VM이 더 낫습니다.

## 핵심 개념: 첫 번째 서버리스 함수의 배포 계약

AI가 만든 함수라도 배포 전에 아래 네 가지 계약이 명확해야 합니다.

| 항목 | 계약 내용 | 왜 중요한가 |
|------|----------|------------|
| 이벤트 형식 | HTTP 이벤트의 `body`는 JSON 문자열 | 로컬 테스트와 실제 플랫폼 입력을 맞추기 위해 |
| 타임아웃 예산 | 이 함수는 수 초 안에 끝나는 작업만 담당 | 장시간 처리를 섞으면 재시도 비용 급증 |
| 상태 경계 | 주문 상태 자체는 함수 안에 저장하지 않음 | 프로세스 메모리는 신뢰할 수 있는 저장소가 아님 |
| 로그 필드 | `request_id`, `order_id`, `next_step` 포함 | 중복 처리와 장애 추적의 최소 단서 |

## 처음 질문으로 돌아가기

- **서버리스는 정확히 무엇을 플랫폼에 넘기는 실행 모델일까요?**
  - 패치, 기본 스케일링, 실행 인프라 운영 같은 반복 작업을 플랫폼에 넘기고, 개발자는 이벤트 계약, 상태 경계, 시간 예산, 관측성 기준을 더 명확하게 설계해야 합니다.

- **첫 번째 서버리스 함수는 어떤 입력 계약과 응답 계약으로 시작해야 할까요?**
  - HTTP 이벤트 하나를 받아 검증하고, 플랫폼이 기대하는 형식으로 응답을 돌려주는 최소 계약부터 시작합니다. `event`, `context` 입력, JSON 응답 형식, 추적용 `request_id` 포함이 기본입니다.

- **로컬 호출과 실제 배포 사이에서 최소한 무엇을 맞춰 두어야 할까요?**
  - 이벤트 모양, 런타임 버전, 환경 변수, 핸들러 경로 네 가지를 먼저 맞춰야 합니다. 이 네 가지가 다르면 로컬에서 잘 되는 코드가 배포 후에 실패합니다.

## 정리

서버리스의 핵심은 서버 삭제가 아니라 책임 이동입니다. 플랫폼이 실행 환경 준비와 기본 운영을 맡는 대신, 개발자는 이벤트 계약, 상태 경계, 시간 예산, 관측성 기준을 더 명확하게 설계해야 합니다.

바이브코딩으로 AI가 함수를 만들어 주더라도, 그 함수를 서버리스에 올리는 순간 이 계약은 개발자가 직접 챙겨야 합니다. 다음 글에서는 실제로 패키지를 만들고 실행하고 측정하는 FaaS 워크플로를 살펴봅니다.
