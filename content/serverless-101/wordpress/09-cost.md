# 바이브코딩을 위한 Serverless 기초 (9/10): 비용

이 글은 "바이브코딩을 위한 Serverless 기초" 시리즈의 9번째 글입니다.

---

바이브코딩에서 AI는 서버리스 코드를 빠르게 만들어 줍니다. "호출이 있을 때만 돈을 내니 저렴하다"는 말은 맞지만, 실제 청구서는 훨씬 복합적입니다. 어느 날 갑자기 청구서가 열 배가 된 이야기는 대개 호출당 단가 문제가 아니라 구조 문제입니다.

서버리스 비용은 호출 수 × 실행 시간 × 메모리의 곱입니다. 그런데 메모리를 낮추면 비용이 줄어들 것 같지만 실행 시간이 길어지면 총비용이 올라갈 수 있습니다. 메모리를 올리면 CPU도 함께 올라가 실행이 빨라져서 오히려 총비용이 낮아지는 경우도 있습니다. 데이터 전송 비용은 특히 이미지, 동영상, 대용량 응답을 다루는 시스템에서 함수 비용보다 더 커질 수 있는데 AI가 만든 코드에서는 이 부분이 빠지기 쉽습니다.

AI가 만든 서버리스 아키텍처에서 비용 관련 설정을 확인하지 않으면, 메모리가 기본값으로 고정된 채 최적화 없이 운영됩니다. 비용은 기술 세부 옵션이 아니라 아키텍처 선택 기준입니다.

> **핵심 인사이트:** 서버리스 비용은 호출 수 × 실행 시간 × 메모리의 곱이고, 모든 최적화는 결국 이 세 값 중 하나를 줄이는 일로 돌아옵니다. 메모리를 올려 실행 시간을 줄이면 총비용이 낮아지는 구간이 존재합니다. 데이터 전송과 연계 서비스 비용도 반드시 포함해 총비용으로 비교해야 합니다.

## 이 글에서 다룰 문제

- 서버리스 비용은 어떤 항목들의 합으로 결정될까요?
- 메모리 설정은 왜 성능뿐 아니라 비용에도 직접 연결될까요?
- 데이터 전송과 연계 서비스 비용은 왜 자주 놓칠까요?
- 비용 최적화 실험은 어떻게 설계해야 할까요?
- AI가 만든 서버리스 코드에서 비용 관점으로 확인할 것은 무엇인가요?

## 서버리스 비용 핵심 패턴

```python
# 비용 구성 요소 계산 모델 (AWS Lambda 예시)
def calls_cost(n, unit_price=0.0000002):
    """호출당 비용"""
    return n * unit_price

def gb_seconds(memory_mb, duration_ms, n):
    """메모리 × 실행 시간 × 호출 수"""
    return (memory_mb / 1024) * (duration_ms / 1000) * n

def egress_cost(gb, price_per_gb=0.09):
    """데이터 송신 비용: 자주 놓치는 항목"""
    return gb * price_per_gb

def total_cost(n, mem_mb, dur_ms, gb_out):
    return (
        calls_cost(n)
        + gb_seconds(mem_mb, dur_ms, n) * 0.0000166667
        + egress_cost(gb_out)
    )
```

```python
# 메모리 튜닝 스윕: 최적 메모리 크기 찾기
sizes = [128, 256, 512, 1024]
for s in sizes:
    cost = total_cost(1_000_000, s, 200, 5)
    print(f"Memory: {s}MB -> Cost: ${cost:.4f}")

# 결과 예시:
# Memory: 128MB -> Cost: $0.2167  (느리지만 저렴)
# Memory: 512MB -> Cost: $0.2043  (균형)
# Memory: 1024MB -> Cost: $0.2312 (빠르지만 비쌈)
# → 512MB가 최적일 수 있음
```

```text
# 기능별 원가 분해 예시
| 기능            | 월 호출    | 평균 실행 | 추정 비용 |
|----------------|-----------|---------|---------|
| 주문 접수 API   | 1,200만    | 90ms   | $48     |
| 결제 승인 비동기 | 1,000만    | 140ms  | $55     |
| 정산 배치 이벤트 | 800만      | 220ms  | $71     |

# 최적화 실험 기록
| 실험           | 변경 전     | 변경 후         | 효과           |
|--------------|------------|----------------|--------------|
| 메모리 상향    | 512MB/180ms | 1024MB/110ms  | 지연 39% 감소  |
| 배치 처리      | 개별 쓰기   | 25건 묶음 쓰기  | DB 요청 60% 감소|
| 불필요 로그 제거 | 전체 본문 로그 | 오류 중심 로그 | 로그 비용 35% 감소 |
```

## 변경 전후 비교

**Before: 호출당 단가만 보는 관점**
```text
- 메모리를 최소값(128MB)에 고정
- 실행 시간 측정 없이 코드 배포
- 데이터 전송 비용 계산 안 함
- 연계 서비스(API GW, DynamoDB, SQS) 비용 누락
```

**After: 총비용 관점으로 최적화**
```text
- 메모리 크기별 실행 시간 측정 후 최적 선택
- 총비용 = 호출 + GB-초 + 전송 + 연계 서비스
- 기능별 원가 분해로 최적화 우선순위 결정
- 비용 경보로 급증 즉시 감지
```

## 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 방법 |
|------|-------------|-----------|
| 메모리를 최소값에 고정 | 실행 시간 길어져 총비용 증가 | 메모리 튜닝 스윕으로 최적값 측정 |
| 데이터 전송 비용 무시 | 이미지/동영상 서비스에서 주비용 항목 | CDN/객체 저장소 직접 제공 고려 |
| 연계 서비스 비용 누락 | API GW, DynamoDB, SQS 비용이 함수 비용 초과 | 총소유비용으로 비교 |
| 프로비저닝 유휴 비용 추적 안 함 | 호출 없어도 비용 발생 | 유휴 시간 대비 지연 개선 효과 측정 |
| 비용 경보 없음 | 청구서 받기 전까지 급증 모름 | 일일 비용 7일 평균 대비 30% 초과 경보 |

## AI 활용 팁

```
# AI에게 이렇게 요청하세요:
"Lambda 함수 비용 최적화를 도와줘.
현재 메모리 128MB, 평균 실행 200ms, 월 1000만 호출.
메모리 256/512/1024MB별 총비용을 비교하고,
데이터 전송과 DynamoDB 비용도 포함해서 계산해줘"

# AI 결과물 검증 체크포인트:
# - 호출 비용, GB-초, 데이터 전송을 모두 포함하는가?
# - 메모리 크기별 실행 시간 변화를 측정하는가?
# - 연계 서비스(API GW, DB, 큐) 비용이 포함되어 있는가?
# - 비용 경보 기준이 설정되어 있는가?
# - 최적화 실험 전후로 지연과 오류율을 함께 측정하는가?
```

## 운영 체크리스트

- [ ] 메모리 크기별 총비용을 실제 측정값으로 비교했다
- [ ] 데이터 전송량을 측정하고 있다
- [ ] 연계 서비스(API GW, DynamoDB, SQS) 비용이 총비용에 포함된다
- [ ] 일일 비용 급증(7일 평균 30% 초과) 경보가 설정되어 있다
- [ ] 최적화 실험 시 지연과 오류율을 함께 기록한다

## 처음 질문으로 돌아가기

- **서버리스 비용의 구성 요소는?** 호출 수, 실행 시간 × 메모리(GB-초), 데이터 송신, API Gateway 요청, DynamoDB 읽기/쓰기, SQS 메시지가 합산됩니다. 함수 비용만 보면 실제 청구서를 예측할 수 없습니다.
- **메모리를 올리면 비용이 오르는가?** 항상 그렇지 않습니다. 메모리를 올리면 CPU도 올라 실행 시간이 줄어듭니다. GB-초 비용이 낮아져 총비용이 감소하는 구간이 자주 있습니다. 실제 측정 없이 감으로 결정하지 마세요.
- **데이터 전송 비용이 왜 자주 놓칠까요?** 함수 실행 비용은 콘솔에서 바로 보이지만, 데이터 전송 비용은 네트워크 사용량 메트릭을 따로 봐야 합니다. 이미지나 동영상을 응답으로 직접 반환하는 구조라면 전송 비용이 함수 비용보다 더 커집니다.

## 정리

바이브코딩에서 AI가 만든 서버리스 코드에서 메모리 설정, 데이터 전송, 연계 서비스 비용을 반드시 확인하세요. 호출당 단가만 보면 전체 비용을 예측할 수 없습니다. 메모리 튜닝 스윕으로 최적 메모리를 찾고, 기능별 원가 분해로 최적화 우선순위를 정하세요. 다음 글에서는 서버리스 앱 설계 전체를 종합합니다.
