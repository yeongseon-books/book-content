# 바이브코딩을 위한 서버리스 기초 (5/10): 스케일링

이 글은 **바이브코딩을 위한 서버리스 기초** 시리즈의 다섯 번째 글입니다. 서버리스는 자동으로 확장된다는 말은 맞습니다. 하지만 "무한히" 확장된다는 말은 함정입니다. 함수는 빠르게 늘어나도 데이터베이스와 외부 API, 연결 풀은 유한합니다.

---

## "서버리스는 자동으로 확장되니까 괜찮지 않나요?"

바이브코딩으로 만든 API가 갑자기 트래픽을 받기 시작했습니다. Lambda 인스턴스는 빠르게 늘어났는데, 몇 초 뒤 데이터베이스 연결 오류가 쏟아졌습니다. Lambda는 10배로 늘었는데 DynamoDB나 RDS의 연결 수는 그만큼 늘어나지 않았기 때문입니다.

> 서버리스는 같은 함수의 복사본을 더 많이 띄워 확장하므로, 확장 단위가 서버가 아닌 요청 한 건이고, 그 차이가 상태·제한·동시성에 대한 사고방식을 바꿉니다.

자동 확장의 비용은 종종 함수가 아니라 다운스트림이 지불합니다. 이 점을 모르면 트래픽이 올라갈수록 시스템이 더 불안정해지는 역설을 만납니다.

## 이 글에서 다룰 문제

- 서버리스의 동시성 모델은 어떻게 이해해야 할까요?
- 버스트와 지속 트래픽은 왜 다르게 봐야 할까요?
- 예약 동시성은 무엇을 보호하기 위한 장치일까요?
- 서버리스 환경에서 이 개념이 전통 서버와 어떻게 다르게 작동할까요?
- 비용과 성능 사이 트레이드오프는 어디서 발생할까요?

---

## 바이브코딩 API가 트래픽을 받으면 생기는 일

AI가 만들어 준 주문 API를 배포했는데, 마케팅 이벤트로 동시 요청이 100배 늘었습니다.

- Lambda 인스턴스: 1개 → 80개 (빠르게 늘어남)
- DynamoDB 연결: 80개의 Lambda가 동시에 쓰기 → 핫 파티션 발생
- 외부 결제 API: 동시 호출 80개 → 결제사 429 Too Many Requests

Lambda만 빠르게 늘었을 뿐, 뒤쪽 시스템은 무너졌습니다. 이것이 예약 동시성을 설정해야 하는 이유입니다.

---

## Before vs After: 스케일링 보호 전략

| 구분 | Before (보호 없음) | After (동시성 제한) |
|------|------------------|---------------------|
| Lambda 동시성 | 무제한 확장 | ReservedConcurrentExecutions: 80 |
| DB 연결 | 무제한 연결 시도 | 동시성 상한으로 간접 보호 |
| 외부 API | 동시 호출 폭탄 | 큐 버퍼링으로 속도 제어 |
| 장애 전파 | 전체 시스템 마비 | 함수 스로틀링으로 격리 |

## 자주 하는 실수

| 실수 | 왜 문제인가 | 올바른 접근 |
|------|------------|------------|
| 동시성 상한 미설정 | 갑작스러운 트래픽에 DB 연결 고갈 | `ReservedConcurrentExecutions` 명시 |
| 재시도 즉시 반복 | 오류 발생 시 재시도 폭탄으로 부하 2배 | 지수 백오프 적용 |
| 버스트를 지속 트래픽처럼 설계 | 스파이크 대응 vs 지속 부하 대응 방식 다름 | 큐 버퍼링으로 시간 분산 |
| 외부 API 호출 한도 무시 | 429 오류 쏟아짐 | 토큰 버킷이나 비동기 완충 적용 |

## AI 팁: 바이브코딩에서 스케일링 설계하기

AI에게 Lambda 함수 설정을 만들어 달라고 할 때 이렇게 물어보세요.

> "이 Lambda 함수에 ReservedConcurrentExecutions를 설정해줘. 백엔드 DynamoDB의 쓰기 TPS 상한이 1000이고, 함수 평균 실행 시간이 400ms라면 안전한 동시성 상한은 얼마일지 계산해줘. 재시도는 지수 백오프로 설정해줘."

동시성을 설정할 때 이 계산을 활용하세요.

- 초당 처리 가능한 요청 = 동시성 / 평균 실행 시간(초)
- 예: 동시성 80, 평균 400ms → 초당 200건 처리 가능
- DB가 초당 1000건 쓰기를 지원한다면 동시성 80은 안전함

## 스케일링 핵심 용어

| 용어 | 뜻 | 운영에 주는 의미 |
|------|-----|----------------|
| 동시성 | 동시에 실행 중인 함수 인스턴스 수 | 현재 시스템이 받는 병렬 압력의 크기 |
| 버스트 한도 | 짧은 구간에서 급격히 늘어날 수 있는 상한 | 초기 급증을 어디까지 흡수할지 결정 |
| 예약 동시성 | 특정 함수에 고정 배정한 동시성 예산 | 중요한 함수와 다운스트림 보호에 사용 |
| 스로틀링 | 한도를 넘는 호출을 지연 또는 거절하는 동작 | 시스템 전체를 보호하는 안전장치 |
| 백프레셔 | 다운스트림이 감당 가능한 속도로만 흐르게 만드는 기법 | 재시도 폭주와 연결 고갈 방지 |

## 장애 관점 점검표

| 신호 | 가장 먼저 볼 항목 | 흔한 대응 |
|------|----------------|----------|
| 데이터베이스 타임아웃 | 연결 풀 포화 여부 | 예약 동시성, 큐 버퍼링 |
| 외부 API 429 | 공급자 호출 한도 | 백오프, 비동기 완충 |
| 다른 함수까지 느려짐 | 계정 단위 동시성 예산 | 중요 함수에 예약 동시성 배정 |
| 큐 적체 증가 | 소비 속도와 배치 크기 | 워커 수 조정, 핸들러 단순화 |

## 처음 질문으로 돌아가기

- **서버리스의 동시성 모델은 어떻게 이해해야 할까요?**
  - 동시성 = 동시에 실행 중인 함수 인스턴스 수입니다. 초당 요청 수 × 평균 실행 시간(초)으로 필요한 동시성을 추정할 수 있습니다. 이 숫자를 알아야 DB 연결 상한과 비교해 안전한 한도를 설정할 수 있습니다.

- **버스트와 지속 트래픽은 왜 다르게 봐야 할까요?**
  - 짧은 피크는 큐와 버스트 한도로 버틸 수 있지만, 지속 트래픽은 근본적인 처리량 설계 문제로 이어집니다. 버스트는 시간으로 분산시키고, 지속 트래픽은 처리량을 설계해야 합니다.

- **예약 동시성은 무엇을 보호하기 위한 장치일까요?**
  - 속도를 높이기 위한 기능이 아닙니다. 특정 함수가 지나치게 자원을 써서 다른 함수를 굶기거나 데이터베이스를 마비시키지 않도록 경계를 세우는 방어선입니다.

---

## 정리

서버리스 스케일링의 본질은 무한 확장이 아니라 통제된 확장입니다. 바이브코딩으로 만든 함수라도 배포 시 `ReservedConcurrentExecutions`를 반드시 설정하세요. 함수가 빠르게 늘어나도 DB와 외부 API는 유한합니다. 다음 글에서는 무상태 함수가 상태 있는 비즈니스를 어떻게 처리하는지 살펴봅니다.
