# 바이브코딩을 위한 서버리스 기초 (3/10): 트리거와 이벤트

이 글은 **바이브코딩을 위한 서버리스 기초** 시리즈의 세 번째 글입니다. AI가 만든 함수를 배포했다면, 이제 그 함수가 어떻게 깨어나는지 이해할 차례입니다. 함수는 스스로 실행되지 않습니다. 트리거가 있어야 깨어납니다.

---

## "일단 HTTP 연결하면 되지 않나요?"라는 생각의 함정

바이브코딩으로 API를 만들 때 가장 자연스러운 선택은 HTTP 트리거입니다. 하지만 "주문 접수 → 결제 → 메일 발송"을 모두 HTTP 체인으로 연결하면, 메일 서버가 느려지는 순간 주문 응답 전체가 늦어집니다. 트리거 선택은 함수 본문만큼 중요한 설계 결정입니다.

> Trigger는 함수를 깨우는 사건이고 Event는 그 사건이 가져오는 데이터입니다. 서버리스 코드의 입력은 이 둘로만 들어옵니다.

트리거를 고른다는 것은 "언제 실패하면 어떻게 재시도할 것인가"를 고르는 일입니다. 이 차이를 무시하면 로컬에서 잘 돌아가는 코드가 운영에서 무너집니다.

## 이 글에서 다룰 문제

- HTTP, 큐, 스케줄 트리거는 호출 의미가 어떻게 다를까요?
- 비동기 소비자에서는 왜 멱등성이 기본 전제가 될까요?
- DLQ는 단순한 보조 기능이 아니라 왜 운영의 핵심 관찰 지점일까요?
- 서버리스 환경에서 이 개념이 전통 서버와 어떻게 다르게 작동할까요?
- 비용과 성능 사이 트레이드오프는 어디서 발생할까요?

---

## 트리거를 잘못 고르면 생기는 일

바이브코딩으로 만든 주문 처리 시스템이 있습니다. 주문이 들어오면 결제를 처리하고, 영수증 메일을 보내고, 통계 서버에 기록합니다. 이걸 모두 하나의 HTTP 요청 안에 동기로 처리했더니, 결제는 됐는데 메일 서버 타임아웃이 나면서 전체 요청이 실패했습니다. 사용자는 결제가 됐는지 안 됐는지 알 수 없습니다.

이 문제의 해법은 트리거 분리입니다. HTTP 요청은 빠르게 받아 큐에 넣고 `202 Accepted`를 반환하고, 결제·메일·통계는 큐 트리거로 분리해서 처리합니다.

---

## Before vs After: 트리거 선택 변화

| 구분 | Before (동기 체인) | After (트리거 분리) |
|------|-------------------|---------------------|
| 주문 응답 시간 | 결제 + 메일 + 통계 시간 합산 | HTTP 큐 삽입 시간만 |
| 메일 서버 장애 영향 | 주문 전체 실패 | 메일 함수만 재시도 |
| 재시도 단위 | 전체 흐름 재실행 | 실패 단계만 재시도 |
| 중복 처리 위험 | 없음 (동기라 한 번만) | 멱등성 키 필수 |

---

## 자주 하는 실수

| 실수 | 왜 문제인가 | 올바른 접근 |
|------|------------|------------|
| 모든 처리를 HTTP 체인으로 연결 | 한 단계 지연이 전체 응답 지연 | 후처리는 큐 트리거로 분리 |
| 멱등성 키 없이 큐 소비 | 재전달 시 중복 처리 발생 | 외부 저장소에 처리 기록 |
| DLQ 미설정 | 반복 실패 메시지가 조용히 사라짐 | 반드시 DLQ 연결 |
| 재시도 횟수 무제한 | 독성 메시지가 계속 큐를 점유 | maxReceiveCount 설정 |

## AI 팁: 바이브코딩에서 트리거 설계하기

AI에게 API를 만들어 달라고 할 때 이렇게 물어보세요.

> "이 주문 처리 흐름에서 동기로 처리해야 할 부분과 비동기 큐로 분리해야 할 부분을 나눠줘. HTTP 트리거는 빠른 응답이 필요한 것만 담당하고, 시간이 걸리는 후처리는 SQS 트리거로 분리해줘. 멱등성 키와 DLQ도 포함해줘."

비동기 큐를 쓰면 반드시 이 세 가지를 함께 만들어야 합니다.

1. 멱등성 키 저장소 (DynamoDB, Redis 등)
2. DLQ 설정 (maxReceiveCount: 3~5)
3. 실패 페이로드에 `message_id`, `retry_count`, `error` 필드 포함

---

## 트리거 선택 매트릭스

| 트리거 | 지연 시간 기대치 | 재시도 기본값 | 잘 맞는 작업 |
|--------|----------------|--------------|-------------|
| HTTP | 즉시 응답 | 클라이언트 재시도 | API 요청, 동기 검증 |
| 큐 | 수 초~수 분 허용 | at-least-once 재전달 기본 | 비동기 후처리, 배치 소비 |
| 스케줄 | 주기 기준 실행 | 다음 주기 재실행 | 정기 집계, 정리 작업 |

트리거를 고르면 설계의 중심도 따라 바뀝니다. HTTP를 고르면 사용자 지연 시간이 설계 중심이 되고, 큐를 고르면 중복 처리와 DLQ가 설계 중심이 됩니다.

---

## 핵심 시나리오: HTTP에서 큐 소비와 멱등 처리까지

1. HTTP 요청이 `/orders`로 들어옵니다.
2. 요청 핸들러는 검증 후 큐에 메시지를 넣고 `202 Accepted`를 반환합니다.
3. 큐 소비자는 메시지를 읽고, `idempotency_key`를 외부 저장소에 기록한 뒤 주문 후처리를 수행합니다.
4. 같은 메시지가 다시 오면 소비자는 중복 처리를 건너뜁니다.
5. 반복 실패 메시지는 DLQ로 이동하고, 운영자는 재처리합니다.

중복 처리 문제가 생겼을 때 확인하는 순서도 정해두면 좋습니다.

1. **메시지 ID 확인**: 정말 같은 메시지인지, 비슷하지만 다른 메시지인지 구분
2. **멱등성 키 기록 조회**: 키가 저장되지 않았는지, 저장 시점이 너무 늦었는지 확인
3. **재시도 횟수와 마지막 오류 확인**: 일시 실패인지 영구 실패인지 구분
4. **DLQ 페이로드 확인**: 실패 메시지가 격리되어 있다면 여기서 원인 분석 시작

---

## 운영 체크리스트

- [ ] HTTP와 큐 트리거의 성공 의미를 분리해서 설계했는가
- [ ] 멱등성 키를 외부 저장소에 기록하는 계약이 있는가
- [ ] 재시도 한도와 DLQ 이동 기준이 명시되어 있는가
- [ ] 중복 처리 사고 시 무엇부터 확인할지 운영 순서를 알고 있는가

---

## 처음 질문으로 돌아가기

- **HTTP, 큐, 스케줄 트리거는 호출 의미가 어떻게 다를까요?**
  - HTTP는 즉시 응답과 사용자 지연이 핵심이고, 큐는 중복 처리와 재시도가 핵심이며, 스케줄은 재진입성과 겹침 방지가 핵심입니다. 트리거는 문법이 아니라 운영 계약입니다.

- **비동기 소비자에서는 왜 멱등성이 기본 전제가 될까요?**
  - 네트워크 오류, 플랫폼 타임아웃, 다운스트림 일시 실패만으로도 같은 메시지는 쉽게 다시 들어옵니다. 비동기 트리거는 기본적으로 at-least-once라고 가정해야 안전합니다.

- **DLQ는 단순한 보조 기능이 아니라 왜 운영의 핵심 관찰 지점일까요?**
  - DLQ에는 메시지 ID, 재시도 횟수, 원본 페이로드, 실패 원인이 남아야 합니다. 이 정보가 있어야 "무엇이, 몇 번째 재시도에서, 어떤 이유로 실패했는지"를 기준으로 재처리할 수 있습니다.

---

## 정리

트리거와 이벤트를 이해한다는 것은 함수 진입점을 외우는 일이 아닙니다. 호출 방식이 곧 실패 방식이고, 실패 방식이 곧 재시도·멱등성·DLQ 설계로 이어진다는 사실을 이해하는 일입니다. 바이브코딩으로 빠르게 함수를 만들었다면, 그 함수가 어떤 트리거로 깨어나고 실패하면 어떻게 처리되는지도 함께 설계해야 합니다.
