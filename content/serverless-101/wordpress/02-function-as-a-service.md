# 바이브코딩을 위한 서버리스 기초 (2/10): 함수형 서비스(FaaS)란 무엇인가?

이 글은 **바이브코딩을 위한 서버리스 기초** 시리즈의 두 번째 글입니다. AI가 만든 함수를 서버리스에 올린다는 것은 결국 FaaS(Function as a Service)에 배포하는 일입니다. 함수 코드만 있으면 될 것 같지만, 실제로는 패키지, 런타임, 아티팩트 점검이라는 루프가 따라옵니다.

---

## AI가 함수를 만들어도 배포는 직접 해야 합니다

바이브코딩으로 함수 코드는 금방 나옵니다. 그런데 "이 코드를 Lambda에 올려줘"라고 해도 AI는 실제 배포 환경을 모릅니다. 패키지 크기가 얼마인지, 의존성이 런타임과 맞는지, 핸들러 경로가 올바른지는 직접 확인해야 합니다.

> FaaS는 함수 하나를 배포 단위·실행 단위·과금 단위로 만들어, 서버 운영을 코드 안의 함수 정의 한 줄로 줄여 줍니다.

서버리스를 책임 이동 관점으로 이해했다면, FaaS는 그 책임 이동이 실제 배포 단위에서 어떻게 보이는지를 보여 줍니다. 패키지 크기, 런타임 차이, 메모리 튜닝, 콜드 스타트를 감이 아닌 측정으로 다루게 됩니다.

## 이 글에서 다룰 문제

- FaaS의 실행 계약은 핸들러, 런타임, 패키지 사이에서 어떻게 만들어질까요?
- 실제 배포 전에는 어떤 파일 구조와 명령 순서로 검증하는 편이 좋을까요?
- 패키지 크기와 의존성 수는 왜 실행 시간과 콜드 스타트에 직접 영향을 줄까요?
- 서버리스 환경에서 이 개념이 전통 서버와 어떻게 다르게 작동할까요?
- 비용과 성능 사이 트레이드오프는 어디서 발생할까요?

---

## 바이브코딩 함수, 배포 전에 꼭 확인할 것들

AI가 만들어 준 함수를 받았을 때 "일단 올려보자"라고 하면 로컬에서는 잘 됐는데 배포 후 실패하는 일이 자주 생깁니다. 이유는 거의 항상 네 가지 중 하나입니다.

1. 런타임 버전이 다릅니다. (로컬 Python 3.12, 플랫폼 3.11)
2. 환경 변수가 빠져 있습니다. (로컬에 `.env` 파일이 있었지만 배포 패키지에는 없음)
3. 패키지 안에 필요한 파일이 없습니다. (`app.py`는 들어갔는데 설정 파일이 빠짐)
4. 핸들러 경로가 틀렸습니다. (`module.function` 지정이 다름)

이 네 가지를 먼저 체크하면, "내 코드 문제인지 배포 설정 문제인지"를 빠르게 구분할 수 있습니다.

---

## Before vs After: FaaS 배포 방식 변화

| 구분 | Before (감으로 배포) | After (루프로 검증) |
|------|---------------------|---------------------|
| 의존성 관리 | 전체 venv 올리기 | `-t package`로 필요한 것만 분리 |
| 검증 방법 | 배포 후 콘솔에서 테스트 | 로컬 스모크 테스트 먼저 |
| 패키지 점검 | ZIP 크기만 확인 | 포함 파일 목록도 확인 |
| 메모리 튜닝 | 최소값 고정 | 패키지 가볍게 → 측정 → 조정 순서 |

---

## 자주 하는 실수

| 실수 | 왜 문제인가 | 올바른 접근 |
|------|------------|------------|
| 핸들러와 검증 파일을 함께 두기 | 배포 단위와 검증 단위가 섞임 | `app.py`와 `smoke_test.py` 분리 |
| 스모크 테스트 없이 바로 배포 | 핸들러 로직 실패인지 설정 실패인지 모름 | 로컬 성공 후 배포 |
| 대형 의존성 무심코 추가 | 패키지 크기 증가 → 콜드 스타트 악화 | `requirements.txt` 최소화 유지 |
| 메모리 낮게 고정 | 실행 시간 늘어나 총비용 오를 수 있음 | 메모리 512/1024MB 비교 측정 |

## AI 팁: 바이브코딩에서 FaaS 패키지 만들기

AI에게 함수를 배포할 준비를 해달라고 할 때 이렇게 물어보세요.

> "이 핸들러를 Lambda에 배포할 수 있는 최소 패키지 구조로 만들어줘. requirements.txt, app.py, smoke_test.py를 분리하고, ZIP 패키지를 만드는 bash 스크립트도 포함해줘."

그 다음에는 반드시 이 순서를 지키세요.

1. `python3 smoke_test.py` 로컬 성공 확인
2. `ls -lh function.zip` 패키지 크기 확인
3. `python3 -m zipfile -l function.zip | head -20` 포함 파일 확인
4. 그 다음에야 메모리와 런타임 설정 조정

---

## FaaS 핵심: 빌드에서 패키징, 실행, 측정까지의 루프

FaaS를 제대로 다루는 팀은 거의 항상 이 순서로 움직입니다.

**1단계 - 의존성을 별도 폴더에 설치**

```bash
python3 -m pip install -r requirements.txt -t package
cp app.py package/
```

**2단계 - 아티팩트를 하나의 ZIP으로 묶기**

```bash
cd package && zip -r ../function.zip . && cd ..
```

**3단계 - 로컬 스모크 테스트**

```bash
python3 smoke_test.py
```

**4단계 - 패키지 크기와 포함 파일 확인**

```bash
ls -lh function.zip
python3 -m zipfile -l function.zip | head -20
```

**5단계 - 측정 후 메모리 조정**

패키지 무게를 먼저 줄인 다음, 실제 측정값을 기반으로 메모리를 비교합니다.

| 메모리 | warm p95 | cold p95 | 월 비용(가정) |
|--------|---------|---------|-------------|
| 512MB | 230ms | 980ms | 31달러 |
| 1024MB | 170ms | 620ms | 44달러 |
| 1536MB | 150ms | 520ms | 61달러 |

## 운영 체크리스트

- [ ] `requirements.txt`, 핸들러, 스모크 테스트가 분리되어 있는가
- [ ] 배포 전 아티팩트 크기와 포함 파일을 확인했는가
- [ ] 메모리 조정 전에 의존성 축소와 패키지 점검을 먼저 했는가
- [ ] 로컬과 관리형 런타임 차이를 추적할 첫 점검 항목을 알고 있는가

## 처음 질문으로 돌아가기

- **FaaS의 실행 계약은 핸들러, 런타임, 패키지 사이에서 어떻게 만들어질까요?**
  - 개발자는 핸들러를 작성하고, 의존성을 함께 묶어 패키지를 만들고, 플랫폼은 그 패키지를 특정 런타임에서 로드한 뒤 핸들러를 호출합니다. FaaS 성능과 안정성은 핸들러 코드 + 패키지 내용 + 런타임 준비 비용의 합으로 결정됩니다.

- **실제 배포 전에는 어떤 파일 구조와 명령 순서로 검증하는 편이 좋을까요?**
  - `requirements.txt`, `app.py`, `smoke_test.py`를 분리하고, 로컬 스모크 테스트 성공 → 패키지 크기 확인 → 포함 파일 점검 → 메모리 조정 순서로 진행합니다.

- **패키지 크기와 의존성 수는 왜 실행 시간과 콜드 스타트에 직접 영향을 줄까요?**
  - 핸들러보다 먼저 패키지가 로드되고, 패키지보다 먼저 런타임이 준비됩니다. 초기화 비용은 핸들러 본문이 실행되기도 전에 지연 시간으로 청구됩니다.

---

## 정리

FaaS는 함수를 올리는 기능이 아니라, 핸들러·런타임·패키지·측정 루프를 하나의 운영 계약으로 묶는 모델입니다. 바이브코딩으로 코드를 빠르게 만들더라도, FaaS 배포 루프는 생략할 수 없습니다. 다음 글에서는 이 함수가 실제 운영에서 어떤 방식으로 깨워지는지, 트리거와 이벤트 흐름을 살펴봅니다.
