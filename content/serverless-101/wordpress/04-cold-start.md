# 바이브코딩을 위한 서버리스 기초 (4/10): 콜드 스타트

이 글은 **바이브코딩을 위한 서버리스 기초** 시리즈의 네 번째 글입니다. AI가 만든 함수를 배포하고 처음 호출했을 때 유독 느린 경험을 했다면, 그것이 바로 콜드 스타트입니다. 평균 지연이 괜찮아 보여도 실제 사용자 경험은 나쁠 수 있는 이유이기도 합니다.

---

## "처음 호출만 느리면 그냥 넘어가도 되지 않나요?"

바이브코딩으로 빠르게 만든 API를 배포하면 이런 말을 자주 합니다. "로컬에서는 빠른데 배포하면 처음만 느려요. 그다음부터는 괜찮아요." 이 말에 숨어 있는 위험은, 그 "처음"이 결제나 로그인처럼 사용자 만족도가 가장 높아야 하는 순간에 발생할 수 있다는 점입니다.

> Cold start는 플랫폼이 함수를 필요할 때 올리는 시간이고, 서버리스의 모든 아키텍처 결정은 호출 비용과 이 시작 세금 사이의 trade-off입니다.

콜드 스타트는 성능 최적화 팁이 아니라, 어떤 경로에 얼마만큼의 지연을 허용할지 결정하는 설계 변수입니다.

## 이 글에서 다룰 문제

- 함수의 첫 호출은 왜 느릴까요?
- 콜드 스타트는 어떤 단계들의 합으로 생길까요?
- 평균이 아니라 p99를 봐야 하는 이유는 무엇일까요?
- 서버리스 환경에서 이 개념이 전통 서버와 어떻게 다르게 작동할까요?
- 비용과 성능 사이 트레이드오프는 어디서 발생할까요?

---

## 바이브코딩 함수의 콜드 스타트 패턴

AI가 만들어 준 함수에서 콜드 스타트를 크게 만드는 주범은 보통 이 세 가지입니다.

1. **과도한 import**: AI가 편의상 `import pandas as pd`를 포함시켰지만, 실제로 pandas는 쓰지 않음
2. **핸들러 안에서 클라이언트 매번 생성**: 매 호출마다 DB 연결을 새로 열기 때문에 웜 인스턴스 이점을 스스로 버림
3. **무거운 모델 로딩**: AI가 ML 코드를 추가했는데, 모델 로딩이 핸들러 안에 있어 매 호출마다 로딩

이 세 가지를 고치는 것만으로도 콜드 스타트를 크게 줄일 수 있습니다.

## Before vs After: 콜드 스타트 완화 변화

| 구분 | Before (최적화 전) | After (최적화 후) |
|------|------------------|-----------------|
| 의존성 | 사용하지 않는 대형 라이브러리 포함 | 필요한 것만 requirements.txt에 |
| DB 연결 | 핸들러 안에서 매번 생성 | 핸들러 바깥 전역에서 한 번 생성 |
| 모델 로딩 | 매 호출마다 로딩 | 전역 변수로 한 번 로딩 후 재사용 |
| 모니터링 | 평균 지연만 확인 | p95/p99 지연 추적 |

## 자주 하는 실수

| 실수 | 왜 문제인가 | 올바른 접근 |
|------|------------|------------|
| 평균만 보고 p99 무시 | 콜드 스타트가 꼬리 지연을 크게 끌어올림 | p95/p99 지표로 추적 |
| 핸들러 안에서 클라이언트 매번 생성 | 웜 인스턴스 이점 소멸 | 전역 변수로 초기화 |
| 무거운 의존성 무심코 추가 | 패키지 크기 증가 → 초기화 시간 증가 | AI 코드의 import 목록 검토 |
| 프로비저닝을 기본값처럼 사용 | 비용이 급증함 | 지연 민감 경로에만 선택적 적용 |

## AI 팁: 바이브코딩에서 콜드 스타트 줄이기

AI가 만든 함수 코드를 받았을 때 이렇게 물어보세요.

> "이 함수의 콜드 스타트를 줄이려면 어떻게 해야 할까? import 중에 불필요한 것이 있는지 확인해줘. DB 클라이언트나 무거운 초기화 코드가 핸들러 안에 있다면 핸들러 바깥으로 옮겨줘."

그리고 배포 전에 이 순서로 확인하세요.

1. `requirements.txt`에서 실제로 사용하는 라이브러리만 남기기
2. 전역 클라이언트 초기화 코드가 핸들러 밖에 있는지 확인
3. 초기화 시간 측정 코드 삽입 후 콜드 vs 웜 비교
4. p95 지연이 기준을 넘으면 메모리 상향 검토, 그래도 안 되면 프로비저닝

---

## 콜드 스타트 단계별 구조

콜드 스타트가 단일 원인이 아니라는 점을 이해하면 해결책이 보입니다.

| 단계 | 내용 | 최적화 방법 |
|------|------|-----------|
| 실행 환경 생성 | 컨테이너 스핀업 | 프로비저닝된 동시성 |
| 런타임 초기화 | Python/Node 인터프리터 시작 | 런타임 선택 (Java보다 Python이 빠름) |
| 패키지 로딩 | 코드와 의존성 로드 | 패키지 크기 최소화 |
| 핸들러 바깥 초기화 | 전역 변수, DB 연결 | 불필요한 초기화 제거 |

---

## 콜드 스타트 벤치마크 예시

| 설정 | p50 | p95 | cold p95 | 비고 |
|------|-----|-----|---------|------|
| 512MB | 105ms | 390ms | 1180ms | 기본 |
| 1024MB | 88ms | 250ms | 760ms | 메모리 상향 |
| 1024MB + 프로비저닝 3 | 82ms | 145ms | 170ms | 비용 증가 |

p95 목표가 300ms라면 512MB는 부적합합니다. 반대로 p95 800ms를 허용할 수 있다면 프로비저닝 없이 메모리 상향만으로도 충분할 수 있습니다.

## 처음 질문으로 돌아가기

- **함수의 첫 호출은 왜 느릴까요?**
  - 실행 환경 생성, 런타임 초기화, 코드와 의존성 로딩이 모두 합쳐져 첫 호출 지연으로 나타납니다. 이미 재사용 중인 웜 인스턴스가 많으면 평균은 좋아 보이지만, 몇 번의 콜드 스타트가 꼬리 지연을 끌어올립니다.

- **콜드 스타트는 어떤 단계들의 합으로 생길까요?**
  - 실행 환경 생성 + 런타임 초기화 + 패키지 로딩 + 핸들러 바깥 초기화 코드 실행. 단계마다 최적화 방법이 다릅니다.

- **평균이 아니라 p99를 봐야 하는 이유는 무엇일까요?**
  - 결제나 로그인처럼 중요한 경로는 몇 번의 느린 호출이 전체 만족도를 크게 깎을 수 있습니다. 평균은 대부분의 웜 호출로 좋아 보이지만, 사용자가 체감하는 것은 그 몇 번의 느린 호출입니다.

---

## 정리

콜드 스타트는 서버리스의 결함이 아니라 실행 모델의 비용입니다. 중요한 것은 그 비용을 어디서 줄이고 어디서 수용할지 구분하는 일입니다. 바이브코딩으로 AI가 만든 함수를 그대로 배포하면 패키지가 무겁거나 초기화 코드가 핸들러 안에 있는 경우가 많습니다. 배포 전에 반드시 이 부분을 점검하세요. 다음 글에서는 스케일링과 동시성 모델을 살펴봅니다.
