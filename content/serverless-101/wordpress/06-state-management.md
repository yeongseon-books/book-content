# 바이브코딩을 위한 서버리스 기초 (6/10): 상태 관리

이 글은 **바이브코딩을 위한 서버리스 기초** 시리즈의 여섯 번째 글입니다. AI가 만든 함수를 보면 종종 전역 변수에 세션을 저장하거나, 함수 안에 카운터를 두는 코드가 포함되어 있습니다. 서버리스에서는 이런 코드가 조용히 망가집니다.

---

## "전역 변수에 저장하면 빠르지 않나요?"

바이브코딩으로 만든 로그인 API에서 세션 토큰을 전역 딕셔너리에 저장했습니다. 로컬 테스트에서는 잘 됩니다. 그런데 배포하면 요청이 다른 Lambda 인스턴스로 가는 순간 세션이 없어집니다. 스케일링이 일어나면 새 인스턴스에는 전역 변수가 비어 있기 때문입니다.

> 서버리스 함수는 본질적으로 stateless이므로, 필요한 '상태'는 외부 저장소(DB·캐시·큐)에 두고 함수는 그것을 읽고 쓰는 코드일 뿐입니다.

무상태는 상태가 전혀 없다는 뜻이 아닙니다. 상태를 함수 프로세스 안에 두지 않는다는 뜻입니다. 이 차이를 이해하면 서버리스가 제약이 아니라 분리 원칙으로 읽히기 시작합니다.

## 이 글에서 다룰 문제

- 무상태 함수가 상태 있는 비즈니스를 어떻게 처리할까요?
- 세션, 캐시, 데이터 저장소, 워크플로 상태는 어디에 둬야 할까요?
- TTL과 멱등 토큰은 왜 상태 관리의 핵심일까요?
- 서버리스 환경에서 이 개념이 전통 서버와 어떻게 다르게 작동할까요?
- 비용과 성능 사이 트레이드오프는 어디서 발생할까요?

---

## 바이브코딩 함수의 상태 관련 흔한 패턴

AI가 만들어 준 코드에서 아래 패턴을 발견하면 즉시 수정해야 합니다.

```python
# 위험한 패턴 - 전역 변수에 상태 저장
sessions = {}  # Lambda 인스턴스마다 다른 딕셔너리!

def login_handler(event, context):
    user_id = event["body"]["user_id"]
    sessions[user_id] = {"logged_in": True}  # 다른 인스턴스에는 반영 안 됨
    return {"statusCode": 200}
```

이 코드는 단일 인스턴스 로컬 환경에서는 동작하지만, 서버리스에서는 인스턴스가 여러 개로 늘어나거나 재시작되면 세션이 사라집니다.

---

## Before vs After: 상태 관리 변화

| 구분 | Before (함수 내부 상태) | After (외부 저장소 분리) |
|------|----------------------|------------------------|
| 세션 저장 | 전역 변수 딕셔너리 | Redis / DynamoDB |
| 처리 완료 기록 | 인메모리 집합 | DynamoDB TTL 항목 |
| 워크플로 상태 | 함수 내부 분기 | Step Functions / 외부 상태 머신 |
| 캐시 | 전역 변수 재사용 | 조건부 웜 캐시 (단기 재사용 허용) |

---

## 자주 하는 실수

| 실수 | 왜 문제인가 | 올바른 접근 |
|------|------------|------------|
| 전역 변수에 세션 저장 | 인스턴스 교체 시 상태 소실 | Redis, DynamoDB 등 외부 저장소 |
| TTL 없이 상태 무한 축적 | 저장 비용 누적, 정합성 문제 | 보존 기간 명시 |
| 멱등 토큰 미사용 | 재시도 시 중복 처리 | 처리 완료 토큰 외부 저장 |
| 복잡한 흐름을 함수 하나에 | 재시도 시 어디서 다시 시작할지 불명확 | Step Functions 등으로 분리 |

## AI 팁: 바이브코딩에서 상태 관리 점검하기

AI가 만든 함수 코드에서 상태를 찾아 수정할 때 이렇게 물어보세요.

> "이 함수 코드에서 전역 변수나 인스턴스 로컬 상태로 저장되는 것들을 모두 찾아줘. 각각을 외부 저장소(DynamoDB, Redis, S3 등)로 옮기는 방법도 알려줘. TTL이 필요한 항목도 표시해줘."

상태를 외부화할 때 이 세 가지를 기본 계약으로 두세요.

1. **멱등성 키**: 같은 요청을 다시 받았을 때 같은 결과를 보장
2. **TTL**: 수명 정책이 없으면 비용과 정합성 문제 발생
3. **낙관적 잠금**: 동시 업데이트 충돌 방지

---

## 상태 유형별 저장 전략

| 상태 유형 | 적합한 저장소 | TTL 필요 여부 |
|----------|-------------|--------------|
| 사용자 세션 | Redis, DynamoDB | 필요 (24시간~7일) |
| 처리 완료 기록 | DynamoDB | 필요 (12~48시간) |
| 영속 비즈니스 데이터 | DynamoDB, RDS | 불필요 (명시적 삭제) |
| 워크플로 진행 상태 | Step Functions, DynamoDB | 워크플로 완료 시 삭제 |
| 짧은 캐시 | Lambda 전역 변수 (주의) | 함수 수명 = 캐시 수명 |

Lambda 전역 변수는 웜 인스턴스에서만 재사용됩니다. 비즈니스 상태를 저장하면 안 되고, DB 연결처럼 재사용 가능한 클라이언트 객체에만 활용하세요.

---

## 상태 충돌 시나리오와 대응

| 시나리오 | 문제 | 대응 |
|--------|------|------|
| 동일 주문 두 번 결제 요청 | 중복 결제 | 멱등 토큰 + 조건부 쓰기 |
| 취소와 승인 거의 동시 도착 | 최종 상태 불명확 | 낙관적 잠금 (version 필드) |
| 재시도 중 네트워크 타임아웃 | 처리됐는지 알 수 없음 | 멱등 키로 중복 확인 |

## 운영 체크리스트

- [ ] 세션을 외부 저장소로 분리했는가
- [ ] 데이터베이스 연결 재사용 전략을 정했는가
- [ ] TTL 정책을 명시했는가
- [ ] 복잡한 워크플로를 함수 밖으로 분리했는가

## 처음 질문으로 돌아가기

- **무상태 함수가 상태 있는 비즈니스를 어떻게 처리할까요?**
  - 함수는 상태를 소유하는 주체가 아니라 상태를 읽고 갱신하는 작업자입니다. 세션은 Redis, 영속 데이터는 DynamoDB, 워크플로 상태는 Step Functions에 두고 함수는 읽고 쓰기만 합니다.

- **세션, 캐시, 데이터 저장소, 워크플로 상태는 어디에 둬야 할까요?**
  - 세션은 Redis/DynamoDB, 영속 데이터는 DynamoDB/RDS, 워크플로 상태는 Step Functions이 적합합니다. 각각 접근 패턴과 수명, 일관성 요구가 다르므로 하나의 저장소에 모두 몰아넣는 것은 비효율적입니다.

- **TTL과 멱등 토큰은 왜 상태 관리의 핵심일까요?**
  - TTL이 없으면 오래된 상태와 처리 완료 토큰이 누적되어 저장 비용과 정합성 문제가 함께 커집니다. 멱등 토큰이 없으면 재시도 시 중복 처리가 발생합니다. 둘 다 서버리스에서는 선택이 아닌 기본값입니다.

---

## 정리

서버리스에서 상태를 다루는 핵심은 상태를 없애는 것이 아니라 위치를 분명히 하는 일입니다. 바이브코딩으로 만든 함수에 전역 변수 상태가 있다면, 그것은 서버리스 환경에서 우연히 동작하는 코드입니다. 배포 전에 반드시 외부 저장소로 분리하고, TTL과 멱등 토큰을 추가하세요. 다음 글에서는 큐와 이벤트 기반 아키텍처를 살펴봅니다.
