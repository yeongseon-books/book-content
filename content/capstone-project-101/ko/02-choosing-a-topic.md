# Capstone Project 101 (2/10): 주제 선정

좋아 보이는 아이디어는 많지만, 한 학기 안에 끝까지 밀 수 있는 아이디어는 훨씬 적습니다. 캡스톤 주제 선정이 어려운 이유도 여기에 있습니다.

좋은 주제는 멋있어 보이는 주제가 아니라 팀이 끝까지 책임질 수 있는 주제입니다. 그래서 주제를 고를 때는 흥미, 사용자 가치, 구현 가능성, 발표 난도를 함께 봐야 합니다.

이 글은 Capstone Project 101 시리즈의 2번째 글입니다. 여기서는 후보를 비교하는 기준을 만들고, 범위가 큰 아이디어를 학기 안에 맞는 주제로 줄이는 방법을 설명합니다.

> 좋은 주제는 새롭기만 한 주제가 아니라, 팀이 시간 안에 설명하고 구현하고 발표할 수 있는 범위로 정리된 주제입니다.

## 이 글에서 다룰 문제

- 좋은 캡스톤 주제는 어떤 조건을 갖춰야 할까요?
- 흥미로운 아이디어와 실제로 해낼 수 있는 아이디어는 어떻게 구분할까요?
- 후보를 비교할 때 팀이 함께 볼 기준은 무엇일까요?
- 이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?
- 면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?

## 주제가 프로젝트 전체를 결정하는 이유

주제가 흔들리면 남은 학기도 같이 흔들립니다. 초반에 잘 고른 주제는 이후 요구사항 정리, MVP 설계, 발표 준비까지 계속 팀을 도와줍니다. 반대로 멋있어 보인다는 이유만으로 주제를 정하면 구현을 시작하기도 전에 범위와 난도가 팀을 압도하기 쉽습니다.

좋은 팀은 유행보다 완주 가능성을 먼저 봅니다. 캡스톤은 아이디어 경연이 아니라, 제한된 시간 안에 작지만 설득력 있는 결과물을 만드는 과정이기 때문입니다.

### 실패 패턴: 트렌드 먼저 보기

1주차. "AI 튜터를 만들자"는 제안이 나옵니다. 팀원 4명 모두 동의합니다. 흥미롭고, 최신 기술을 쓰며, 면접에서도 멋지게 들립니다.

2주차. API 비용을 계산하자 월 30만 원이 나옵니다. 대학원생 수준의 프롬프트 설계 경험이 필요하다는 것도 알게 됩니다.

3주차. "그러면 AI는 나중에 추가하고 일단 일반 추천 시스템을 만들자"는 방향 전환이 일어납니다. 사실상 주제가 바뀐 것인데, 아무도 공식적으로 인정하지 않습니다.

6주차. 추천 시스템 로직이 예상보다 복잡해집니다. 팀원 간에 무엇을 만들고 있는지 설명이 달라지기 시작합니다.

12주차. 발표 준비를 하면서 왜 이 주제를 선택했는지 명확하게 설명하기 어려워집니다.

### 성공 패턴: 완주 가능성 먼저 보기

1주차. 팀이 후보 12개를 모읍니다. "수강 신청 시간표 충돌 검사기"가 후보 중 하나입니다. 별로 화려하지 않습니다.

2주차. 1차 필터를 적용합니다. "2주 안에 핵심 데모 가능한가?"에 충돌 검사기가 유일하게 "예"로 통과합니다.

3주차. 비교 점수표를 작성합니다. 충돌 검사기가 가장 높은 점수를 받습니다.

4주차. 핵심 입력 파싱 로직을 구현합니다. 예상대로 동작합니다.

12주차. 발표에서 "팀원 모두가 실제로 겪는 문제를 골랐고, 2주 안에 핵심 흐름을 검증했다"고 설명합니다. 면접관이 고개를 끄덕입니다.

## 선택 실패와 성공 비교

**실제로 많이 보이는 선택 실패 사례:**

- "GPT API를 써서 AI 튜터를 만든다" — API 비용이 예상보다 크고, 평가 기준을 정하기 어렵습니다.
- "부동산 가격 예측 모델을 만든다" — 데이터 수집에 2-3주가 걸리고, 예측 정확도를 발표에서 설명하기 복잡합니다.
- "소셜 미디어 플랫폼을 만든다" — 회원 관리, 피드 알고리즘, 알림까지 모두 Must가 되어 범위를 감당하기 어렵습니다.

**실제로 잘 작동한 선택 사례:**

- "수강 신청 시간표 충돌 검사기" — 사용자가 명확하고, 데모 기준이 선명하며, 2주 안에 핵심 흐름을 구현할 수 있습니다.
- "도서관 좌석 현황 알리미" — 문제가 관찰 가능하고, 학교 내 공개 데이터를 활용 가능합니다.
- "팀 프로젝트 역할 분배 도우미" — 대상 사용자가 팀 자신이라 피드백을 즉시 받을 수 있습니다.

## 주제 비교 매트릭스

후보를 세 개 이상 두고 아래처럼 같은 축으로 점수를 매기면, 감으로 정한 결정인지 근거가 있는 결정인지 바로 드러납니다.

```text
후보 | 사용자 문제 | 영향 | 구현 가능성 | 데이터 접근성 | 데모 선명도 | 합계
수강 충돌 검사기 | 5 | 5 | 5 | 4 | 5 | 24
감정 일기 추천기 | 3 | 3 | 4 | 3 | 3 | 16
캠퍼스 길찾기   | 4 | 4 | 2 | 2 | 4 | 16

결론: 수강 충돌 검사기가 가장 작고, 가장 빨리 데모 가치가 드러난다.
이유: 데모 선명도가 5점으로 발표 리스크가 낮고, 데이터 접근성도 양호하다.
탈락한 후보 보존: 캠퍼스 길찾기는 구현 가능성이 낮으나 문제는 명확해 범위 조정 대안으로 활용 가능.
```

### 비교 점수표 작성 방법

각 점수 축은 1-5점으로 판단하되, 점수를 매기기 전에 축의 의미를 팀이 함께 정의합니다. "구현 가능성 5점"이 무엇을 의미하는지 팀원마다 다르면 점수 자체가 의미 없어집니다.

```text
[축 정의 예시]

사용자 문제 (1-5):
  5 = 팀원 중 직접 겪은 사람이 있고, 3명 이상에게 확인됨
  3 = 존재는 확인되나 빈도나 심각도 불명확
  1 = 추측 또는 잠재적 문제

구현 가능성 (1-5):
  5 = 팀 내 경험자 있고, 2주 내 핵심 흐름 구현 가능
  3 = 참고할 오픈소스 있으나 커스터마이징 필요
  1 = 팀 내 경험자 없고, 외부 의존성 높음

데모 선명도 (1-5):
  5 = 입력 → 처리 → 결과가 30초 안에 눈에 보임
  3 = 데모 시나리오가 가능하나 복잡한 설명 필요
  1 = 배경 지식 없이는 데모 의미를 이해하기 어려움
```

### 비교표 작성 체크 포인트

- 점수 축이 서로 겹치지 않는지 확인합니다. "사용자 가치"와 "영향"이 같은 의미가 되지 않도록 주의합니다.
- 데이터 접근성처럼 뒤늦게 터지는 리스크를 별도 축으로 둡니다.
- 최종 결론 옆에 한두 문장 이유를 남깁니다.
- 탈락한 후보도 보존해 두면 범위 조정 때 대안으로 되살릴 수 있습니다.

## 4단계 주제 선정 프로세스

### 1단계 — 후보 목록 작성

팀원 각자 3개씩 후보를 적어 오면 팀 전체 후보가 12개 이상이 됩니다. 이 단계에서는 평가를 보류하고 나열만 합니다. 비슷한 주제는 묶고, 전혀 다른 방향은 분리해 둡니다.

후보는 적어도 세 개는 두는 편이 좋습니다. 둘만 놓으면 찬반 구도가 되기 쉽고, 세 개 이상이면 비교가 시작됩니다.

팀원이 각자 후보를 독립적으로 작성하는 것도 중요합니다. 회의실에서 같이 쓰면 발언권이 큰 사람의 아이디어로 쏠리기 쉽습니다. "독립 작성 후 공유" 방식이 더 다양한 후보를 만들어냅니다.

```text
[후보 목록 템플릿]

팀원 A:
  1. 수강 신청 시간표 충돌 검사기
  2. 캠퍼스 맛집 리뷰 필터링 앱
  3. 졸업 요건 자동 계산기

팀원 B:
  1. 도서관 좌석 현황 알리미
  2. 팀 역할 분배 도우미
  3. 학식 식당 메뉴 예측기

팀원 C:
  1. 자전거 주차 공간 안내 시스템
  2. 강의실 빈 시간 확인 앱
  3. 졸업 논문 마감 알리미

팀원 D:
  1. 익명 피어 리뷰 플랫폼
  2. 과목 선배 리뷰 aggregator
  3. 캠퍼스 이벤트 통합 캘린더
```

### 2단계 — 1차 필터 적용

아래 필터를 통과하지 못하는 후보는 즉시 제거합니다.

| 필터 질문 | 통과 기준 | 충돌 검사기 예시 |
| --- | --- | --- |
| 2주 안에 핵심 데모를 만들 수 있는가 | 예 | 파싱 + 비교 로직 2주 내 가능 |
| 필요한 데이터에 접근 가능한가 | 예 또는 대안 경로 존재 | 수강편람 PDF 공개됨 |
| 팀원 중 핵심 기술 경험자가 있는가 | 최소 1명 이상 | Python 사용자 2명 있음 |
| 발표 시간 15분 안에 설명할 수 있는가 | 예 | 입력 → 충돌 표시 흐름이 단순 |

필터를 통과하지 못한 후보도 완전히 삭제하지 않습니다. 탈락 이유와 함께 별도 문서에 보관합니다. 이후 범위를 조정할 때 대안으로 살릴 수 있습니다.

### 3단계 — 비교 점수표 작성

1차 필터를 통과한 후보 3개를 나란히 두고 점수를 매깁니다. 점수를 매기는 과정에서 팀원들이 서로 다른 가정을 가지고 있다는 사실이 드러나고, 그 차이를 대화로 좁히는 것이 이 단계의 진짜 목적입니다.

점수표 작성 후 각 팀원이 숫자를 설명하는 시간을 갖습니다. "나는 구현 가능성을 4점으로 줬는데, Python 파싱은 쉽지만 시각화 쪽이 걱정돼서"처럼 이유를 말하면 팀 전체가 공유하지 못했던 위험 신호를 미리 발견합니다.

### 4단계 — 최종 선택과 이유 문서화

숫자가 높다고 자동으로 선택하지 않습니다. 최종 선택은 점수를 근거로 팀 대화를 마무리하는 단계입니다. 왜 이 후보를 골랐는지 한두 문장으로 남겨 두면 이후 범위 조정 때 기준이 됩니다.

```text
최종 선택: 수강 신청 시간표 충돌 검사기
선택 이유: 팀 모두가 복수전공 학생이라 문제를 직접 이해하고,
          샘플 데이터로 2주 내 데모 가능성이 확인되었음.
제외 항목: 감정 일기 추천기는 GPT API 비용 문제로 제외.
          캠퍼스 길찾기는 지도 데이터 접근 불가로 제외.
재검토 조건: 만약 학교 수강편람 데이터 접근이 막히면
            도서관 좌석 현황 알리미로 전환 고려.
```

## 주제 선정 직후 작성할 문서

### 문제 정의 선행 문서

주제를 골랐다면 바로 구현으로 넘어가기보다 문제 정의 문서를 먼저 고정해야 합니다. 주제 선정 직후 가장 많이 발생하는 오류는 "이미 모두가 같은 문제를 이해하고 있다"는 착각입니다. 실제로는 팀원마다 다른 사용자를 상정하고, 다른 성공 기준을 떠올립니다.

```text
[문제 이름]
수강 신청 시간표 충돌 검사기

[한 줄 요약]
복수전공 학생이 수강 신청 직전 시간표 충돌을 30초 안에 확인하기 어렵다.

[사용자]
핵심 사용자 1: 복수전공 신청 예정인 2학년 (팀원 지인 5명 이상 확인 가능)
핵심 사용자 2: 학점 이수 계획을 세우는 졸업 학기 학생
제외 사용자:  대학원생, 교환학생 (시간표 형식 상이)

[관찰 사실]
현재 사용자가 겪는 불편: 과목 코드와 시간을 종이에 수기로 옮겨 비교
불편이 발생하는 시점: 수강 신청 시작 1-2일 전 계획 수립 시
불편을 확인한 근거: 팀원 3명 직접 경험, 주변 7명 인터뷰

[문제 문장]
복수전공 학생은 수강 신청 전날 다수 과목의 시간대를 동시에 비교해야 할 때,
손으로 옮겨 쓰거나 여러 탭을 열어 대조해야 하기 때문에 30초 안에 충돌 여부를
확인하기 어렵다.

[성공 기준]
정량 지표 1: 첫 사용자 3명 중 2명 이상이 30초 안에 충돌 여부를 확인
정량 지표 2: 설명 없이 핵심 흐름을 끝내는 비율 70% 이상

[핵심 가정]
가정 A: 사용자가 과목 코드와 시간 정보를 텍스트로 붙여 넣을 수 있다
가정 B: 수강편람 시간표 형식이 학기마다 일정하다

[비범위]
이번 학기에서 하지 않을 것:
  - 수강 신청 사이트 자동 연동
  - 대체 과목 자동 추천
  - 모바일 앱 지원
```

이 템플릿의 핵심은 작성 난이도가 아니라 검토 난이도를 낮춘다는 사실입니다. 항목이 정해져 있으면 팀원이 서로 다른 전제를 가지고 있어도 어디에서 충돌하는지 바로 보입니다.

### 리스크 레지스터 — 주제 선정 단계

주제 선정과 동시에 주요 리스크를 문서화합니다. 나중에 "그때 이미 알았는데"라는 상황을 막기 위해서입니다.

```text
[리스크 레지스터 v0.1 — 주제 선정 단계]

리스크 ID | 내용 | 발생 확률 | 영향도 | 대응 계획
R01 | 수강편람 데이터 형식 불일치 | 중 | 높음 | 입력 전처리 단계 추가 / 수동 입력 폼 대안
R02 | API 호출 제한 또는 비용 초과 | 낮음 | 높음 | 오프라인 파싱 방식으로 전환
R03 | 핵심 개발자 이탈 | 낮음 | 매우 높음 | 기능별 문서화 2주 단위 업데이트
R04 | 발표 데모 실패 | 중 | 높음 | 녹화 영상 백업 + 정적 스크린샷 준비
```

## 4주 사전 검증 타임라인

주제를 정한 직후, 구현 전에 핵심 가정을 빠르게 검증하는 4주 계획을 세웁니다.

```text
주차      1주        2주        3주        4주
문제 정의  ████
데이터 확인           ████
핵심 스파이크                  ████
데모 초안                                 ████
```

| 주차 | 목표 | 완료 기준 | 위험 신호 |
| --- | --- | --- | --- |
| 1주차 | 문제 문장 확정 | 팀 전체 동의, 문서화 완료 | 팀원마다 다른 사용자를 말함 |
| 2주차 | 데이터/환경 확보 | 샘플 입력 1건 파싱 성공 | 수강편람 형식 비정형 판명 |
| 3주차 | 핵심 로직 스파이크 | 충돌 여부 결과값 출력 성공 | 비교 알고리즘이 예상보다 복잡 |
| 4주차 | 데모 초안 | 60초 시연 1회 성공 | 데모 장면이 3개를 넘음 |

스파이크(spike)는 "이것이 작동하는가"를 확인하는 최소 구현입니다. 완성도를 높이는 작업이 아닙니다. 스파이크 결과가 "작동한다"면 구현 방향이 확정되고, "작동하지 않는다"면 지금이 방향을 바꿀 마지막 기회입니다.

### 스파이크 코드 예시 — 충돌 검사 핵심 로직

```python
# spike/conflict_check.py
# 목적: 핵심 충돌 검사 로직이 작동하는지 확인 (완성도 무관)
# 결과: 2025-03-05 — 기본 파싱과 충돌 감지 동작 확인

from dataclasses import dataclass

@dataclass
class Course:
    code: str
    day: str        # 예: "월", "화"
    start: int      # 예: 9 (9시)
    end: int        # 예: 11 (11시)

def parse_course(text: str) -> Course:
    """
    입력 형식: "CS101 월 09:00-11:00"
    스파이크 단계: 형식이 고정되어 있다고 가정
    """
    parts = text.strip().split()
    code = parts[0]
    day = parts[1]
    time_parts = parts[2].split("-")
    start = int(time_parts[0].split(":")[0])
    end = int(time_parts[1].split(":")[0])
    return Course(code=code, day=day, start=start, end=end)

def has_conflict(a: Course, b: Course) -> bool:
    """두 과목이 시간 충돌하는지 확인"""
    if a.day != b.day:
        return False
    return not (a.end <= b.start or b.end <= a.start)

# 스파이크 실행
if __name__ == "__main__":
    courses = [
        parse_course("CS101 월 09:00-11:00"),
        parse_course("MA201 월 10:00-12:00"),  # CS101과 충돌
        parse_course("ENG301 화 13:00-15:00"),  # 충돌 없음
    ]

    print("=== 충돌 검사 스파이크 결과 ===")
    for i in range(len(courses)):
        for j in range(i + 1, len(courses)):
            a, b = courses[i], courses[j]
            conflict = has_conflict(a, b)
            status = "충돌" if conflict else "정상"
            print(f"{a.code} vs {b.code}: {status}")

# 예상 출력:
# CS101 vs MA201: 충돌
# CS101 vs ENG301: 정상
# MA201 vs ENG301: 정상
```

스파이크 결과는 팀 채널에 공유합니다. "이 로직이 작동한다"는 확인이 팀의 자신감을 만들고, 이후 요구사항 논의를 훨씬 구체적으로 만들어줍니다.

## 자주 하는 실수

| 실수 유형 | 구체적 상황 | 결과 | 예방 방법 |
| --- | --- | --- | --- |
| 트렌드 추종 | "요즘 LLM이 대세니까 RAG 시스템을 만들자" | 구현 범위가 감당 불가 | 팀 역량과 일정으로 먼저 필터링 |
| 역량 과대평가 | "우리 팀이라면 할 수 있다"고 판단 | 2주차부터 일정이 밀림 | 과거 비슷한 프로젝트 구현 시간을 참고 |
| 감으로 결정 | 비교표 없이 "이게 더 좋아 보인다" | 왜 이걸 선택했는지 나중에 설명 못함 | 최소 3개 후보를 같은 기준으로 비교 |
| 모호한 평가 축 | "사용성"이라는 축이 팀마다 다른 의미 | 점수가 의미 없어짐 | 각 축에 구체적 판단 기준을 명시 |
| 대안 미보존 | 탈락 후보를 즉시 삭제 | 범위 조정 때 대안이 없음 | 탈락 이유와 함께 문서에 보존 |

## 팀 리뷰 진행 방식

### 주제 선정 회의 구조

주제 선정 회의는 70분 이내로 끝냅니다. 시간이 길어지면 에너지가 떨어지고 결론 없이 끝날 가능성이 높습니다.

```text
[주제 선정 회의 타임라인]

0-10분:  각자 준비한 후보 발표 (1인당 2분)
10-20분: 1차 필터 적용 — 통과/탈락 분류
20-40분: 통과 후보 3개 점수표 작성 및 이유 공유
40-60분: 토론 — 점수 차이가 큰 항목 중심으로
60-70분: 최종 결정 및 문서화 담당자 지정
```

### 문서 리뷰 진행 방식

문서 리뷰는 20분 내로 끝내는 것이 좋습니다. 처음 5분은 작성자가 설명하고, 다음 10분은 질문만 받습니다. 마지막 5분은 수정 항목을 확정합니다.

이때 "좋다/나쁘다" 같은 감상 대신 "어떤 항목이 비어 있는가"로 말해야 문서 품질이 올라갑니다. "데이터 접근 경로가 비어 있다", "성공 기준에 숫자가 없다"처럼 구체적인 빈칸을 지목하는 것이 "좀 더 구체적으로 써 주세요"보다 훨씬 실행하기 쉬운 피드백입니다.

### Git 브랜치에서 주제 문서 관리

주제 선정 결과와 비교 문서를 Git 저장소에서 함께 관리하면 이후 "왜 이 주제를 골랐는가"라는 질문에 증거로 답할 수 있습니다.

```bash
# 저장소 초기 구조 설정
git init capstone-conflict-checker
cd capstone-conflict-checker

# 문서 디렉토리 생성
mkdir -p docs/decisions
mkdir -p spike

# 주제 선정 문서 커밋
git add docs/decisions/topic-selection.md
git commit -m "docs: 주제 선정 비교표 및 최종 결정 문서화

- 후보 12개 중 1차 필터 통과 3개
- 비교 매트릭스: 수강 충돌 검사기 24점 (1위)
- 최종 선택: 수강 신청 시간표 충돌 검사기
- 탈락 후보 보존: 감정 일기 추천기, 캠퍼스 길찾기"

# 스파이크 결과 커밋
git add spike/conflict_check.py
git commit -m "spike: 충돌 검사 핵심 로직 동작 확인

- 기본 파싱: 정상
- 충돌 감지: 정상
- 결론: 구현 방향 확정"
```

## 처음 질문으로 돌아가기

- **좋은 캡스톤 주제는 어떤 조건을 갖춰야 할까요?**
  팀이 시간 안에 설명하고, 구현하고, 발표할 수 있는 범위로 정리되어야 합니다. 구체적으로는 2주 안에 핵심 데모가 가능하고, 필요한 데이터에 접근할 수 있으며, 발표에서 15분 안에 설명 가능한 수준이어야 합니다. "멋진가"가 아니라 "완주할 수 있는가"가 첫 번째 기준입니다.

- **흥미로운 아이디어와 실제로 해낼 수 있는 아이디어는 어떻게 구분할까요?**
  "2주 안에 핵심 데모를 만들 수 있는가"라는 질문에 명확히 답할 수 있으면 해낼 수 있는 아이디어입니다. 답이 "만들다 보면 방법이 생긴다"라면 흥미로운 아이디어입니다. 스파이크를 2주 안에 완성할 수 있는지 확인하는 것이 가장 확실한 방법입니다.

- **후보를 비교할 때 팀이 함께 볼 기준은 무엇일까요?**
  사용자 문제의 선명도, 구현 가능성, 데이터 접근성, 데모 선명도 네 가지를 같은 형식으로 평가해야 합니다. 점수보다 중요한 것은 팀이 각 항목에 대해 같은 기준으로 판단하고 있는지 확인하는 과정입니다. 점수 차이가 크게 나는 항목이 실제 위험 신호입니다.

- **이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?**
  일정이 밀릴 때 무엇을 줄여야 할지 기준이 없어집니다. 팀원마다 "중요한 기능"이 다르게 느껴지고, 발표 2주 전에도 범위가 결정되지 않는 상황이 만들어집니다. 주제 선정 단계의 30분이 후반 3주의 혼란을 막습니다.

- **면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?**
  왜 이 주제를 선택했는지 근거를 설명하는 능력입니다. "흥미로웠다"가 아니라 "사용자 문제가 명확하고 데모 가능성이 높았으며 팀 역량으로 2주 안에 핵심 흐름을 검증했기 때문이다"라고 말할 수 있어야 합니다. 비교 과정과 탈락 이유까지 설명할 수 있으면 더욱 좋습니다.

## 운영 체크리스트

- [ ] 후보가 세 개 이상 있습니다.
- [ ] 팀원 각자 독립적으로 후보를 작성했습니다.
- [ ] 1차 필터(2주 데모 가능 여부, 데이터 접근성)를 통과한 후보만 비교표에 있습니다.
- [ ] 세 가지 이상 평가 기준이 팀 공동으로 정의되어 있습니다.
- [ ] 점수표와 함께 각 점수의 판단 이유가 적혀 있습니다.
- [ ] 최종 선택 이유가 1-2문장으로 적혀 있습니다.
- [ ] 탈락한 후보와 탈락 이유가 문서에 보존되어 있습니다.
- [ ] 재검토 조건(대안 전환 기준)이 명시되어 있습니다.
- [ ] 문제 정의 선행 문서가 작성되었습니다.
- [ ] 스파이크 계획이 수립되어 있습니다.

## 정리와 다음 글

주제 선정은 흥미 경쟁이 아니라 완주 가능성을 고르는 일입니다. 비교 기준을 먼저 세우고, 작은 데모 가치가 가장 빨리 드러나는 후보를 고르면 이후 요구사항과 MVP도 훨씬 안정적으로 정리됩니다. 주제를 고른 직후에는 문제 정의 선행 문서를 작성하고, 스파이크로 핵심 가정을 2주 안에 검증하는 것이 다음 단계입니다. 다음 글에서는 선택한 주제를 문제 문장으로 바꾸는 방법을 다룹니다.
