# Capstone Project 101 (10/10): 프로젝트 회고

프로젝트가 끝나면 팀은 보통 안도감부터 느낍니다. 그 순간 바로 흩어지면 이번 학기의 시행착오는 다시 개인 기억으로만 남습니다.

회고의 목적은 감정을 털어놓는 데서 멈추지 않고, 사실과 원인과 다음 행동을 문서로 남기는 데 있습니다. 그래야 이번 프로젝트의 실패와 성공이 다음 프로젝트의 입력이 됩니다.

이 글은 Capstone Project 101 시리즈의 마지막 글입니다. 여기서는 KPT, 데이터, 원인 분석, 다음 행동을 묶어 회고를 학습 문서로 남기는 방법을 정리합니다.

> 좋은 회고는 잘못한 사람을 찾는 문서가 아니라, 어떤 사실이 있었고 무엇을 바꿀지 정리하는 다음 프로젝트의 출발 문서입니다.

## 이 글에서 다룰 문제

- 회고가 책임 공방으로 흐르지 않게 하려면 무엇이 필요할까요?
- KPT 형식은 왜 초보 팀에게 특히 유용할까요?
- 데이터는 회고의 어떤 부분을 단단하게 만들어 줄까요?
- 이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?
- 면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?

## 회고 없이 끝나면 무슨 일이 생기는가

회고 없이 프로젝트를 닫는 팀에서 자주 반복되는 패턴이 있습니다.

- 다음 프로젝트에서 같은 이유로 일정이 밀립니다.
- "저번에도 이런 문제가 있었는데"라고 말하지만 어떻게 해결했는지 기억이 없습니다.
- 팀원이 졸업 후 포트폴리오 인터뷰에서 "이 프로젝트에서 가장 어려웠던 점과 해결 방법"을 설명하지 못합니다.
- 기술적으로는 성장했지만 협업 방식은 이전과 같습니다.

회고를 제대로 한 팀은 다릅니다. 다음 프로젝트 시작 때 지난 회고를 열어 "저번에는 테스트 버퍼가 부족했으니 이번엔 1주차부터 테스트 일정을 포함하자"라고 말합니다.

## 회고 액션 로그

회고가 실제 변화로 이어지려면 다음 행동을 아래처럼 작고 선명하게 적는 편이 좋습니다.

```text
구분     내용                                      담당자       기한
Keep     요구사항 변경 기록을 남겼고 일정 충격이 줄었다  팀 리드     다음 프로젝트에도 유지
Problem  데모 리허설이 부족해 발표 직전 오류를 발견했다  팀 전체     회고 시점 기록
Try      매주 금요일 20분 리허설 슬롯을 고정한다       QA 담당      다음 프로젝트 1주차
Action   배포 체크리스트 템플릿을 저장소에 추가한다    백엔드 담당  다음 프로젝트 1주차
```

## KPT 확장형 회고 프레임워크

| 구분 | 질문 | 기록 예시 | 다음 액션 연결 |
| --- | --- | --- | --- |
| Keep | 무엇이 잘 작동했는가 | 요구사항 변경 로그가 일정 충격을 줄임 | 동일 템플릿 재사용 |
| Problem | 반복된 문제는 무엇인가 | 데모 직전 통합 테스트 실패 다수 발생 | 테스트 주기 앞당김 |
| Try | 다음에 시도할 것은 무엇인가 | 매주 리허설 슬롯 고정 운영 | 캘린더 선점 |
| Learn | 이번에 새로 배운 원칙은 무엇인가 | 범위 제외 문서화가 품질을 높임 | MVP 문서 표준 반영 |
| Stop | 중단할 습관은 무엇인가 | 회의 중 결정을 구두로만 합의 | 결정 로그 의무화 |

KPT를 확장할 때는 항목을 늘리는 것보다 실행 항목과의 연결을 강화하는 것이 중요합니다. 각 항목 끝에 "다음 행동"이 없으면 회고는 기록으로만 끝납니다.

## 5단계 회고 프로세스

### 1단계 — KPT 틀 채우기

회고 회의 시작 전에 각 팀원이 아래 항목을 개인별로 5분간 작성합니다.

```text
Keep (잘한 것):
  -
  -

Problem (아쉬운 것):
  -
  -

Try (다음에 시도할 것):
  -
  -
```

개인 작성 후 공유하면 같은 문제를 다른 시각으로 바라보는 팀원을 발견할 수 있습니다.

### 2단계 — 데이터로 근거 붙이기

감정보다 수치로 회고를 붙잡습니다.

```text
회고 데이터 예시:
- 구현 속도: 주당 평균 기능 3.2개 (계획 5개)
- 테스트 통과율: 최종 94% (목표 90% 이상 달성)
- 리허설 횟수: 총 3회 (목표 5회 미달)
- 블로커 평균 해결 시간: 1.8일 (목표 1일)
- 일정 편차: 2주차 +2일, 5주차 +1일, 전체 +3일
```

데이터는 "기억보다 기록"을 실천하는 방법입니다. 프로젝트 중에 주간 점검 보드를 운영했다면 이 데이터는 이미 있습니다.

### 3단계 — Five Whys 원인 분석

가장 중요한 Problem 항목에 대해 "왜" 질문을 5번 이어서 합니다.

```text
문제: 데모 직전 통합 테스트 실패

왜 1: 왜 통합 테스트가 실패했는가?
  → 백엔드 API 응답 형식이 바뀌었는데 프런트가 알지 못했다

왜 2: 왜 API 응답 형식 변경을 공유하지 않았는가?
  → PR에 API 스펙 변경 내용을 명시하지 않았다

왜 3: 왜 PR에 API 스펙 변경을 명시하지 않았는가?
  → PR 템플릿에 "API 변경 여부" 항목이 없었다

왜 4: 왜 PR 템플릿에 그 항목이 없었는가?
  → 프로젝트 초기에 PR 템플릿을 간단하게만 만들었다

근본 원인: PR 템플릿이 API 계약 변경을 추적하지 않음
다음 액션: PR 템플릿에 "API 스펙 변경 여부 및 영향 범위" 항목 추가
```

Five Whys는 누가 잘못했는지보다 왜 이런 조건이 반복됐는지를 보는 데 도움이 됩니다.

### 4단계 — 다음 행동 정의

다음 행동에는 담당자, 구체적 내용, 기한이 함께 있어야 합니다.

| 기준 | 나쁜 예 | 좋은 예 |
| --- | --- | --- |
| 구체성 | 테스트를 열심히 한다 | 매주 화요일 통합 테스트 10케이스 실행 |
| 책임성 | 팀이 확인한다 | QA 담당이 결과를 이슈로 보고 |
| 기한성 | 다음에 반영한다 | 다음 프로젝트 2주차까지 반영 |
| 측정성 | 품질을 높인다 | 결함 재오픈율 20% 이하 유지 |

### 5단계 — 학습 요약 문서화

다음 프로젝트에서 바로 꺼내 쓸 수 있는 짧은 문장으로 정리합니다.

```text
이번 캡스톤에서 학습한 원칙:
1. 범위 제외 목록이 있어야 범위가 지켜진다
2. 블로커는 24시간 내에 공유해야 팀 전체가 조정할 수 있다
3. 데모 리허설은 최소 2회, 발표 2주 전부터 시작한다
4. PR 템플릿에 API 변경 여부를 포함해야 통합 충돌을 줄인다
5. 테스트 시간은 구현 시간의 최소 30%로 일정에 포함한다
```

## 개인 성장 기록 양식

팀 회고와 별도로 개인 회고를 작성합니다. 팀 회고는 시스템과 프로세스에 집중하고, 개인 회고는 역량 성장과 다음 학습 계획에 집중합니다.

```text
[기본 정보]
이름:
역할:
기간:

[성과]
이번 프로젝트에서 가장 기여한 결과 2개:
  1.
  2.

[기술 성장]
새롭게 익힌 기술/도구:
다음 프로젝트에서 재사용할 항목:

[협업 성장]
의사소통에서 잘한 점:
다음에 개선할 협업 습관:

[실패와 교훈]
가장 큰 실수 1개:
원인:
재발 방지 행동:

[다음 4주 계획]
학습 목표:
실행 계획:
측정 기준:
```

## 다음 프로젝트 이관 문서

회고 문서가 이 수준으로 남으면 캡스톤이 단발성 과제가 아니라 운영 자산으로 전환됩니다.

| 항목 | 이번 프로젝트 교훈 | 다음 프로젝트 적용 규칙 |
| --- | --- | --- |
| 문제 정의 | 사용자 범위를 넓게 잡아 초반 흔들림 발생 | 첫 주에 제외 사용자까지 문서화 |
| 일정 관리 | 테스트 버퍼 부족 | 매주 0.5일 회귀 테스트 고정 |
| 협업 방식 | PR 리뷰 기준 불일치 | 코드 리뷰 체크리스트 저장소에 고정 |
| 발표 준비 | 리허설 횟수 부족 | 발표 2주 전부터 주 2회 리허설 |
| 범위 관리 | 제외 목록이 없어 범위 확장 반복 | MVP 계약서에 제외 목록 5개 이상 명시 |

## 회고 후 48시간 규칙

회고가 끝난 뒤 48시간 안에 액션 아이템을 실제 작업 도구로 옮기지 않으면 실행 확률이 급격히 낮아집니다.

회고 회의 종료 직후 세 가지를 수행합니다.

1. 액션 아이템을 GitHub Issues 또는 Notion에 등록합니다.
2. 담당자와 기한을 확정합니다.
3. 다음 점검 일정을 캘린더에 선점합니다.

## 자주 하는 실수

| 실수 유형 | 구체적 상황 | 왜 문제인가 | 예방 방법 |
| --- | --- | --- | --- |
| 책임 공방으로 흐름 | "그때 B가 늦게 말해서" | 개인 비난이 시작되면 다음 행동이 나오지 않음 | "사람이 아니라 시스템"에서 원인 찾기 |
| 감정만 기록 | "힘들었다, 뿌듯했다" | 다음 프로젝트에 적용할 실행 항목이 없음 | KPT 형식으로 구조화 |
| 다음 행동 없음 | "잘 정리됐다" 하고 회고 종료 | 회고가 기록으로만 남음 | 모든 Problem에 Try 또는 Action 연결 |
| 데이터 없음 | "많이 힘들었어"로 일정 이슈 설명 | 원인 분석이 감상에 머뭄 | 주간 점검 보드 데이터를 회고에 가져옴 |
| 다음 프로젝트와 미연결 | "이번 학기는 끝났으니 다음에 생각하자" | 같은 실수를 다음 팀원들도 반복 | 이관 문서를 저장소에 커밋 |

## 처음 질문으로 돌아가기

- **회고가 책임 공방으로 흐르지 않게 하려면 무엇이 필요할까요?**
  - "사람이 아니라 시스템"에서 원인을 찾는 규칙이 필요합니다. Five Whys로 원인을 추적하면 자연스럽게 개인 비난이 아닌 프로세스 개선으로 대화가 이어집니다. 또한 데이터(블로커 해결 시간, 테스트 통과율 등)를 근거로 삼으면 감정 논쟁을 줄일 수 있습니다.

- **KPT 형식은 왜 초보 팀에게 특히 유용할까요?**
  - 구조가 단순하기 때문입니다. 잘한 것, 아쉬운 것, 다음에 시도할 것 세 칸만 채우면 됩니다. 복잡한 회고 형식은 처음 하는 팀에게 "어디서부터 시작하는가"라는 질문이 발생합니다. KPT는 그 진입장벽이 낮으면서도 실행 가능한 결론을 이끌어냅니다.

- **데이터는 회고의 어떤 부분을 단단하게 만들어 줄까요?**
  - 감정 논쟁을 줄이는 역할을 합니다. "A가 느렸다"는 주장 대신 "블로커 평균 해결 시간이 1.8일로 목표 1일을 초과했다"고 말하면 원인 분석이 사실에서 시작됩니다. 또한 "우리 팀이 잘했는가"를 직관 대신 수치로 판단할 수 있습니다.

- **이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?**
  - 이 단계는 프로젝트 후반이 아니라 "다음 프로젝트의 초반"에 영향을 줍니다. 회고 없이 끝낸 팀은 다음 프로젝트에서 같은 실수를 반복합니다. 포트폴리오 인터뷰에서 "이 프로젝트에서 무엇을 배웠는가"라는 질문에 구체적으로 답하지 못하는 경우도 많습니다.

- **면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?**
  - 경험에서 학습을 추출하는 능력입니다. "힘들었지만 잘 마쳤습니다" 대신 "데모 직전 통합 테스트 실패가 있었습니다. 원인은 PR 템플릿에 API 변경 추적 항목이 없었던 것이었고, 다음 프로젝트에서는 이를 반영했습니다"처럼 문제-원인-해결-적용을 설명할 수 있어야 합니다.

## 운영 체크리스트

- [ ] KPT 표가 있습니다.
- [ ] 회고 데이터(속도, 테스트율, 리허설 횟수 등)가 모여 있습니다.
- [ ] 가장 중요한 Problem에 Five Whys가 적용되었습니다.
- [ ] 세 개 이상의 다음 행동이 담당자와 기한과 함께 있습니다.
- [ ] 개인 성장 기록이 작성되었습니다.
- [ ] 다음 프로젝트 이관 문서가 저장소에 커밋되었습니다.
- [ ] 48시간 내 액션 아이템이 이슈로 등록되었습니다.

## 정리 — 시리즈를 마치며

회고는 프로젝트의 마지막 문서이면서 다음 프로젝트의 첫 문서입니다. KPT, 데이터, 원인 분석, 다음 행동을 함께 남기면 이번 캡스톤의 시행착오가 다음 작업의 자산으로 바뀝니다.

Capstone Project 101 시리즈 10편을 통해 캡스톤 프로젝트의 전체 흐름을 다루었습니다.

1. **무엇인가** — 기능이 아니라 문제-데모-회고의 흐름
2. **주제 선정** — 완주 가능성 기준의 비교 선택
3. **문제 정의** — 사용자·가정·지표가 담긴 기준 문장
4. **요구사항 정리** — 스토리·수용 기준·우선순위 연결
5. **팀 역할** — 주 책임자·백업·결정 권한 구조
6. **MVP 설계** — 핵심 흐름 하나를 끝까지 연결
7. **기술 스택** — 친숙도·학습 비용·운영 부담 균형
8. **일정 관리** — 계획과 실제의 차이를 드러내는 리듬
9. **발표 자료** — 문제-해결-결과 서사 구조
10. **회고** — 사실과 다음 행동을 남기는 학습 문서

이 열 가지 흐름을 한 번 완주한 팀은 다음 프로젝트를 다른 수준에서 시작합니다.
