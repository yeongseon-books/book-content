# Capstone Project 101 (8/10): 일정 관리

대부분의 캡스톤 일정은 마지막 주에 갑자기 망가지지 않습니다. 실제로는 중간부터 조금씩 밀리는데, 그 차이를 일찍 드러내는 장치가 없어서 마지막에 한꺼번에 터집니다.

좋은 일정은 보기 좋은 계획표가 아니라 계획과 실제의 차이를 계속 드러내는 시스템입니다. 마일스톤, 주간 계획, 버퍼, 블로커 기록이 모두 필요한 이유도 여기에 있습니다.

이 글은 Capstone Project 101 시리즈의 8번째 글입니다. 여기서는 마일스톤, 주간 계획, 스탠드업, 위험 버퍼를 묶어 현실적인 일정 운영 리듬을 만드는 방법을 설명합니다.

> 좋은 일정은 완벽한 예측이 아니라, 계획과 실제의 차이를 빨리 드러내고 조정할 수 있게 만드는 운영 리듬입니다.

## 이 글에서 다룰 문제

- 왜 완벽해 보이는 계획이 실제로는 자주 무너질까요?
- 마일스톤과 주간 계획은 어떻게 구분해서 써야 할까요?
- 데일리 스탠드업은 왜 짧고 반복 가능해야 할까요?
- 이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?
- 면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?

## 일정이 실제로 무너지는 이유

캡스톤 일정이 무너지는 가장 흔한 원인 세 가지:

**1. 구현 시간 과소 추정**
"이 기능은 하루면 될 것 같다"는 생각으로 시작했는데 실제로는 3일이 걸립니다. 예상보다 오래 걸리는 이유는 기술 학습, 디버깅, 팀원 간 통합 충돌 때문입니다.

**2. 테스트와 안정화 시간 미포함**
기능 구현만 일정에 넣고 테스트, 버그 수정, 데모 안정화는 "나중에"로 미룹니다. 그 "나중"이 발표 전날이 됩니다.

**3. 블로커를 늦게 공유**
"좀 더 해보다 말할게"라는 생각으로 2-3일 혼자 해결하다 공유하면, 팀 전체의 일정에 영향이 퍼집니다.

### 일정 과소 추정의 심리학

왜 우리는 반복적으로 일정을 낙관적으로 추정할까요? 심리학에서는 이를 "계획 오류(Planning Fallacy)"라고 부릅니다. 자신의 과거 경험을 기억에서 소환할 때, 성공 사례는 잘 기억하고 실패 사례는 무의식적으로 희석하는 경향이 있습니다.

캡스톤 팀에서 흔히 보이는 패턴:

- "저번 프로젝트에서 API 연동은 반나절이면 됐었는데" — 하지만 그 프로젝트는 내부 API였고 이번은 외부 서비스입니다.
- "어려운 부분만 3일이고, 나머지는 하루면 되지 않나?" — 코드 작성은 하루여도 통합 테스트와 디버깅이 이틀입니다.
- "팀원들도 다 잘하니까 금방 되겠지" — 각자 잘해도 서로의 코드를 합치는 순간 충돌이 생깁니다.

이 오류를 줄이는 방법은 간단합니다. 추정할 때 "최악의 경우는 얼마나 걸릴까?"를 반드시 묻고, 낙관 추정값과 최악 추정값의 평균으로 계획을 세우는 것입니다.

```text
추정 공식 예시:
낙관 추정: 1일
최악 추정: 4일
평균 → 계획에 넣을 값: 2.5일 → 3일로 반올림

버퍼 포함 최종 배정: 3일 × 1.3 = 약 4일
```

## 일정 실패 유형과 예방 방법

일정이 무너지는 패턴을 미리 알고 있으면 조기에 감지할 수 있습니다.

| 실패 유형 | 조기 신호 | 발생 시점 | 예방 방법 |
| --- | --- | --- | --- |
| 구현 시간 과소 추정 | "오늘 안에 됩니다" 말이 3일째 반복 | 1-3주차 | 작업마다 1.5배 버퍼 시간 사전 설정 |
| 통합 충돌 | API 형식 불일치 문제 반복 | 3-4주차 | 2주차에 인터페이스 먼저 고정 |
| 데모 실패 | 5주차에도 60초 데모 성공 0회 | 4-5주차 | 매주 한 번 60초 데모 리허설 |
| 발표 자료 미완성 | 발표 전날 슬라이드 처음 작성 | 7-8주차 | 6주차에 슬라이드 초안 작성 |
| 버퍼 없는 계획 | 어느 주에도 여유가 없음 | 전체 기간 | 전체 일정 20%를 버퍼로 확보 |

이 표를 팀 내 공유하고, 각 신호가 나타날 때 즉시 체크인 미팅을 열기로 합의하면 조기 대응이 빨라집니다.

## 마일스톤 4개 구조

마일스톤은 너무 잘게 쪼개기보다 결과가 보이는 단위로 세 개에서 다섯 개 정도 두는 편이 좋습니다.

| 마일스톤 | 정의 | 증빙 산출물 | 통과 조건 |
| --- | --- | --- | --- |
| M1 요구사항 잠금 | Must 범위 확정 | 요구사항 시트 v1 | 변경 요청 보류 규칙 합의 |
| M2 MVP 연결 | 핵심 흐름 동작 | 데모 영상 초안 | 1회 성공 시연 |
| M3 품질 안정화 | 결함 위험 축소 | 테스트 리포트 | 주요 결함 0건 |
| M4 발표 준비 | 전달력 검증 | 슬라이드, 데모 각본 | 리허설 시간 준수 |

### 마일스톤 통과 판정 회의

마일스톤은 날짜가 지나간다고 자동으로 통과되는 것이 아닙니다. 통과 조건이 충족됐는지 팀이 함께 확인하는 짧은 회의가 필요합니다.

**M2 MVP 연결 통과 판정 예시:**

```text
회의 시간: 15분
참여자: 팀 전체
확인 항목:
  1. 핵심 흐름 (입력 → 처리 → 결과)을 실제로 시연할 수 있는가?
  2. 데모 영상 또는 라이브 시연이 1회 이상 성공했는가?
  3. 다음 마일스톤(M3)을 위한 테스트 계획이 있는가?
결론: 통과 / 보류 (보류 시 3일 이내 재확인 일정 잡기)
```

통과 조건에 주관적 판단 대신 "시연 성공 1회", "테스트 통과율 90%" 같은 숫자 기준을 두면, 팀원 간 이견이 크게 줄어듭니다.

| 8주차 | 최종 발표 | 시간 내 완료, Q&A 대응 | 없음 (리허설로 준비) |

### 주차별 "이것만은 반드시" 체크 항목

각 주가 끝날 때 아래 항목을 확인하는 것만으로도 일정 편차를 일찍 잡을 수 있습니다.

| 주차 | 반드시 확인 | 놓쳤을 때 조치 |
| --- | --- | --- |
| 1주차 末 | Must 기능 목록이 문서로 존재하는가? | 다음 날 오전 90분 워크숍으로 확정 |
| 2주차 末 | 실제 데이터로 입력이 한 번이라도 동작했는가? | 3주차 첫 날 데이터 확보를 최우선 작업으로 설정 |
| 3주차 末 | 핵심 흐름 중 50% 이상 구현됐는가? | 4주차 신기능 추가 금지, 기존 흐름 완성 집중 |
| 4주차 末 | 배포 환경에서 1회 이상 동작했는가? | 5주차 첫 이틀을 배포 설정 전용으로 확보 |
| 5주차 末 | 주요 결함 수가 줄고 있는가 (증가하지 않는가)? | 신기능 전면 중단, 결함 수정 모드 전환 |
| 6주차 末 | 60초 데모를 팀원이 아닌 외부인에게 시연했는가? | 7주차 초 외부 리뷰어 섭외 후 추가 리허설 |

## 주간 실행 보드

아래 같은 보드는 예쁜 간트 차트보다 훨씬 빨리 현실을 보여 줍니다.

```text
주차     목표                  완료 조건               블로커                버퍼 사용
1주차    요구사항 확정          Must 스토리 승인         없음                  0일
2주차    핵심 흐름 구현         입력과 결과 화면 연결     CSV 데이터 정리 지연   1일
3주차    데모 리허설            60초 시연 성공           로그인 오류 재현       2일
4주차    발표 자료 확정         Q&A 준비 완료            없음                  0.5일
```

### 주간 계획 작성 절차 — 월요일 15분

주간 계획을 잘 작성하는 팀과 그렇지 않은 팀의 차이는 월요일 아침 15분에 있습니다.

```text
1단계 (5분): 지난 주 완료 항목 확인
  - 완료 기준을 충족한 항목만 "완료"로 표시
  - 부분 완료는 이번 주로 이월

2단계 (5분): 이번 주 목표 설정
  - 마일스톤 기준으로 이번 주 내 끝내야 할 것 3개 이하
  - 각 항목마다 "완료 기준" 1문장 추가

3단계 (5분): 블로커 예상 목록 작성
  - "이번 주 막힐 가능성이 있는 것"을 미리 나열
  - 각 블로커마다 담당자와 해결 기한 지정
```

이 절차를 지키는 팀은 매주 금요일 점검 때 "생각보다 많이 했네요"가 아니라 "3번 항목이 예상보다 늦어지고 있으니 범위를 줄입시다"라는 구체적인 대화를 합니다.

## 데일리 스탠드업 형식

스탠드업은 짧고 반복 가능한 형식이어야 합니다. 길어지는 순간 공유보다 회의가 됩니다.

```text
형식 (각 팀원 3분 이내):
1. 어제 완료한 것
2. 오늘 할 것
3. 막힌 것 (있다면 어떤 도움이 필요한가)
```

스탠드업의 목적은 보고가 아니라 블로커의 조기 발견입니다. 누군가 "막힌 것"에 무언가를 말하면 스탠드업 후 즉시 그 사람과 관련 담당자가 따로 논의합니다.

### 스탠드업 유형별 비교

스탠드업을 어떻게 운영하느냐에 따라 효과가 크게 달라집니다.

| 유형 | 운영 방식 | 지속 시간 | 효과 | 주의 사항 |
| --- | --- | --- | --- | --- |
| 좋은 스탠드업 | 어제/오늘/막힌 것 3가지만 | 10-15분 | 블로커 조기 발견 | 토론은 별도 미팅으로 분리 |
| 나쁜 스탠드업 | 각자 진행 상황 상세 보고 | 30-45분 | 정보 공유에 그침 | 팀 에너지 소모 과다 |
| 없는 스탠드업 | 비동기 채팅으로만 소통 | — | 블로커 발견 지연 | 2-3일 늦게 알게 됨 |

캡스톤 팀에서 "스탠드업이 매번 45분"이라면, 토론을 스탠드업에 끌고 오는 습관을 고쳐야 합니다.

### 스탠드업 진행자 로테이션

스탠드업의 진행자를 팀원이 돌아가며 맡으면 두 가지 효과가 있습니다. 첫째, 특정 인원이 항상 "사회자"가 되는 고착을 막습니다. 둘째, 진행자를 맡은 날은 시간 제한을 직접 관리해야 하므로 스탠드업의 목적을 더 잘 이해하게 됩니다.

```text
스탠드업 진행자 역할:
- 시간 타이머 설정 (팀원당 3분)
- "막힌 것"이 나오면 "스탠드업 후 따로 얘기하겠습니다" 안내
- 스탠드업 종료 후 1줄 요약을 팀 채널에 남기기

예시 1줄 요약:
"4/15 스탠드업: 로그인 오류(민준 담당, 오늘 중), 결제 API 테스트(소영) 진행 중, 이슈 없음"
```

### 블로커 24시간 규칙

스탠드업과 별개로, 팀에서 합의해야 할 가장 중요한 규칙 하나:

> **혼자 해결을 시도한 시간이 24시간을 초과하면, 해결 여부와 관계없이 즉시 팀에 공유합니다.**

이 규칙이 없으면 개인 성향에 따라 어떤 사람은 3시간 만에 공유하고, 어떤 사람은 5일을 혼자 씨름하다 공유합니다. 후자의 경우 팀 전체 일정에 연쇄 지연이 생깁니다.

## 위험 버퍼 계산

버퍼는 낭비가 아니라 안전장치입니다.

```text
8주 프로젝트의 버퍼 계산:
총 작업 기간: 8주 = 40일
권장 버퍼: 20% = 8일
버퍼 배치:
  - 3주차 말 (통합 이슈 대응): 2일
  - 5주차 말 (테스트 초과 대응): 3일
  - 7주차 말 (발표 자료 수정): 3일
```

버퍼 사용 규칙:

- 블로커가 발생하면 즉시 버퍼에서 인정합니다.
- 버퍼가 50% 이상 소진되면 Must 기능 중 일부를 Should로 재분류합니다.
- 버퍼가 없는 주간에 새 기능 추가를 제안하면 다음 주로 이월합니다.

### 버퍼 소진 단계별 대응

버퍼가 얼마나 남았느냐에 따라 팀의 행동 수준이 달라져야 합니다.

| 버퍼 잔여 | 상태 | 권장 조치 |
| --- | --- | --- |
| 80% 이상 | 여유 | 정상 진행 |
| 50–80% | 주의 | 다음 주 계획 재검토, Should 기능 우선순위 재확인 |
| 30–50% | 경계 | Should 기능 일부 삭제, 팀 리드 보고 |
| 30% 미만 | 위험 | Must 기능 범위 축소 검토, 비상 대응 회의 소집 |
| 0% | 비상 | 발표 범위 최소화, 데모 시나리오 단순화 |

비상 상황에서 가장 흔한 실수는 "어떻게든 원래 범위를 다 구현하겠다"는 집착입니다. 이 경우 모든 기능이 반쯤 동작하는 상태로 발표에 임하게 됩니다. 작동하는 핵심 흐름 하나를 완전히 보여 주는 것이 항상 낫습니다.

## 일정 편차 실제 사례: 어떻게 복구했는가

### 시나리오 A — 조기 발견으로 복구 성공

3주차 스탠드업에서 백엔드 담당자가 "외부 API 연동이 예상보다 복잡해서 이틀 더 필요하다"고 공유했습니다. 팀은 즉시 4주차 버퍼 2일을 당겨 쓰고, 프런트 담당자를 API 통합 지원에 투입했습니다.

결과: 4주차 말에 핵심 흐름이 연결되었고, 발표는 예정대로 진행됐습니다.

### 시나리오 B — 늦은 발견으로 발표 직전 혼란

6주차 리허설에서 처음으로 배포 환경 테스트를 했습니다. 로컬에서는 잘 되던 기능이 배포 환경에서 5개 중 2개가 동작하지 않았습니다. 배포 설정 문제를 해결하는 데 이틀이 걸렸고, 발표 자료는 전날 급하게 만들었습니다.

이 팀이 3주차에 배포 환경 테스트를 한 번이라도 했다면 훨씬 여유 있게 준비할 수 있었을 것입니다.

### 시나리오 C — 팀원 이탈 상황에서의 일정 재조정

5주차에 팀원 한 명이 개인 사정으로 2주간 참여가 어렵게 되었습니다. 이 팀은 다음 단계를 밟았습니다.

**1단계: 현황 파악 (당일)**
- 이탈 팀원이 담당하던 기능 목록 확인
- 현재 완료된 비율 파악 (예: 70% 구현 완료)

**2단계: 분류 (다음 날)**
- 이미 70% 완료된 기능 → 남은 팀원 중 1명이 인계
- 미착수였던 Should 기능 2개 → 발표 범위에서 제외
- 발표 스크립트에서 해당 기능 언급 삭제

**3단계: 역할 재배분**
- 팀 리드가 백엔드 일부를 직접 맡음
- QA 담당자가 프런트엔드 검수도 겸임
- 전체 일정 1주 연장 없이 범위 축소로 해결

결과: 발표는 원래 일정대로 진행됐고, 실제 구동하는 핵심 흐름 2개로 깔끔하게 시연했습니다.

**핵심 교훈:** 팀원 이탈은 예외가 아니라 발생 가능한 위험입니다. RACI에 백업 담당자를 기록해 두고, 주간 계획에 인계 가능한 항목 목록을 미리 만들어 두면 대응 속도가 크게 달라집니다.

## 테스트 전략표 — 일정과 연계

일정에서 가장 자주 과소평가되는 것이 테스트 시간입니다.

| 테스트 수준 | 목적 | 담당 | 실행 시점 | 합격 기준 |
| --- | --- | --- | --- | --- |
| 단위 테스트 | 핵심 함수 로직 검증 | 개발자 | 기능 개발 직후 | 핵심 함수 통과율 90% 이상 |
| 통합 테스트 | 컴포넌트 간 연결 검증 | QA + 개발자 | 주 1회 | 핵심 흐름 100% 통과 |
| 회귀 테스트 | 기존 기능 영향 확인 | QA | 배포 전 | 주요 시나리오 실패 0건 |
| 데모 리허설 테스트 | 발표 환경 재현 검증 | 팀 전체 | 발표 전 주 2회 | 60초 데모 3회 연속 성공 |

### 테스트 시간 예산 잡기

기능 구현 시간을 100으로 봤을 때, 테스트에 필요한 시간 비율 참고 기준:

```text
단위 테스트 작성: 기능 구현 시간의 30-40%
통합 테스트 수행: 기능 구현 시간의 20-30%
회귀 테스트 + 버그 수정: 기능 구현 시간의 40-60%
데모 환경 검증: 2-3시간 (별도)
```

즉, 기능 구현에 10일이 걸린다면 테스트와 안정화에 추가로 9-13일이 필요하다는 계산이 나옵니다. 처음엔 과장처럼 보이지만, 실제로 이 범위를 계획에 포함한 팀과 포함하지 않은 팀의 발표 당일 컨디션 차이는 매우 큽니다.

## 일정 조정 의사결정 프레임

변경 요청이 들어올 때 아래 질문으로 판단합니다.

```text
질문 1: 이 변경이 핵심 흐름을 강화하는가?
질문 2: 이 변경이 발표 데모 성공 확률을 높이는가?
질문 3: 이 변경으로 Must 테스트 범위가 증가하는가?
질문 4: 증가한 범위를 현재 인력으로 감당 가능한가?
결론: 2개 이상 '아니오'면 다음 주로 이월
```

### 변경 요청 실제 대화 예시

실제 팀에서 이 프레임이 어떻게 작동하는지 보겠습니다.

**상황:** 4주차 금요일, 팀원이 "사용자 알림 기능을 추가하면 완성도가 높아질 것 같아요"라고 제안합니다.

```text
팀 리드: "프레임으로 한 번 확인해 봅시다."

질문 1 (핵심 흐름 강화): 아니오 — 알림은 보조 기능
질문 2 (데모 성공 확률): 아니오 — 없어도 데모 가능
질문 3 (테스트 범위 증가): 예 — 알림 발송/수신 테스트 추가 필요
질문 4 (현재 인력으로 감당): 아니오 — 5주차는 테스트 주간

결론: 이월. "5주차 테스트를 마치고 버퍼가 2일 이상 남으면 추가 검토합시다."
```

이 대화 자체가 팀의 의사결정 능력을 보여 주는 증거가 됩니다. 면접에서 "범위 변경 요청을 어떻게 처리했나요?"라는 질문에 이 대화를 그대로 설명할 수 있습니다.

## 주간 점검 보드 템플릿

| 항목 | 계획 | 실제 | 편차 | 조치 |
| --- | --- | --- | --- | --- |
| 구현 완료율 | 60% | 45% | -15% | 범위 축소 검토 |
| 테스트 통과율 | 90% | 82% | -8% | 회귀 테스트 추가 |
| 리허설 횟수 | 2회 | 1회 | -1회 | 일정 재배치 |
| 블로커 해결율 | 100% | 75% | -25% | 백업 담당자 투입 |

편차를 기록할 때는 변명보다 조치가 중요합니다. "왜 늦었는가"를 1문장으로 적고, "무엇을 줄일 것인가"를 바로 결정해야 다음 주가 안정됩니다.

### 주간 점검 회의 진행 방식

주간 점검 보드를 채우는 것만으로는 부족합니다. 15-20분 회의에서 이 보드를 함께 보며 다음 절차를 밟습니다.

```text
1. 지난 주 목표 대비 실제 확인 (5분)
   - 완료: 표시하고 넘어감
   - 미완료: 이유 1문장 + 이월 여부 결정

2. 이번 주 목표 확정 (5분)
   - 마일스톤 기준 이번 주 내 끝내야 할 것
   - 각 항목 담당자와 완료 기준 명시

3. 버퍼 잔여 확인 (3분)
   - 현재 버퍼 상태 → 단계별 대응 조치 결정

4. 블로커 예상 목록 (2분)
   - 이번 주 막힐 가능성 있는 것 나열
   - 24시간 내 해결 안 될 경우 공유 담당자 지정
```

이 회의를 매주 같은 시간에, 같은 방식으로 하면 팀원들이 준비 없이도 자연스럽게 참여합니다. 형식이 반복되면 인지 부담이 줄어들고, 내용에 집중할 수 있습니다.

| 실수 유형 | 구체적 상황 | 왜 문제인가 | 예방 방법 |
| --- | --- | --- | --- |
| 버퍼 없는 계획 | 기능 구현 시간만 계획 | 예상 밖 문제 하나에 전체 일정 붕괴 | 전체 일정의 20%를 버퍼로 확보 |
| 스탠드업 길어짐 | 블로커 토론을 스탠드업에서 함 | 15분이 45분이 되고 집중력 손실 | 스탠드업은 공유만, 토론은 따로 |
| 감으로 진행률 판단 | "많이 온 것 같다" | 실제 완료된 기능을 세면 30%인 경우 많음 | 완료 기준이 충족된 항목 수로만 측정 |
| 주간 계획 고정 | 지난주 계획을 수정 없이 이번 주 사용 | 현실과 계획이 점점 멀어짐 | 매주 월요일 계획을 현실에 맞게 조정 |
| 블로커 늦게 공유 | "조금 더 해보다 말할게" | 2-3일 지연 후 팀 전체에 영향 | 24시간 내 해결 안 되면 즉시 공유 |

### "많이 온 것 같다" 함정 피하기

진행률을 감으로 판단하는 팀에서 가장 흔히 볼 수 있는 현상:

- 3주차 화요일: "60-70% 온 것 같아요"
- 3주차 금요일: "아 생각보다 아직 많이 남았네요. 50% 정도?"
- 4주차 월요일: "이번 주 빡세게 하면 될 것 같아요"
- 4주차 금요일: "핵심 흐름이 아직 연결이 안 됐어요"

이 패턴을 막는 방법은 단 하나입니다. "완료 기준이 충족된 기능 수 / 전체 Must 기능 수"를 숫자로 세는 것입니다.

```text
올바른 진행률 측정 예시:
Must 기능 총 8개
완료 기준을 통과한 기능: 3개 (입력 처리, 계산 로직, 결과 화면)
진행률: 3/8 = 37.5%

잘못된 진행률 측정 예시:
"거의 절반은 온 것 같아요" → 측정 불가능, 의사결정 불가
```

## 처음 질문으로 돌아가기

- **왜 완벽해 보이는 계획이 실제로는 자주 무너질까요?**
  - 계획은 이상적인 상태를 가정하지만 실제는 그렇지 않습니다. 디버깅이 예상보다 2배 오래 걸리고, 팀원 일정이 엇갈리고, 통합 단계에서 충돌이 발생합니다. 이런 현실을 계획에 반영하지 않으면 버퍼 없이 꽉 찬 계획이 첫 번째 문제에서 무너집니다.

- **마일스톤과 주간 계획은 어떻게 구분해서 써야 할까요?**
  - 마일스톤은 "무엇이 끝났는가"를 판단하는 큰 단위입니다. MVP 연결, 품질 안정화, 발표 준비처럼 결과가 보이는 단위로 4-5개를 둡니다. 주간 계획은 "이번 주에 어떤 작업을 끝내는가"를 정하는 실행 단위입니다. 마일스톤은 목적지이고 주간 계획은 경로입니다.

- **데일리 스탠드업은 왜 짧고 반복 가능해야 할까요?**
  - 스탠드업의 목적은 블로커의 조기 발견입니다. 길어지면 팀원들이 준비하고 발표하는 발표회가 됩니다. 짧고 반복 가능해야 매일 지속할 수 있고, 그 반복이 블로커를 24시간 내에 드러내는 리듬을 만듭니다.

- **이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?**
  - 4주차까지는 "바쁜데 진행 중"이고, 5주차에 갑자기 "발표가 3주 남았는데 핵심 흐름이 연결이 안 되었다"는 것을 발견합니다. 마지막 2주를 기능 구현과 발표 준비를 동시에 하며 보내게 됩니다.

- **면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?**
  - 일정 편차를 어떻게 발견하고 조정했는가를 설명하는 능력입니다. "3주차에 API 연동 이슈로 1일 지연이 발생했습니다. 바로 공유하여 팀 전체가 인식했고, 4주차 버퍼 1일을 당겨 사용했습니다"처럼 구체적으로 말할 수 있어야 합니다.

## 면접 Q&A — 일정 관리 경험 말하기

면접에서 일정 관리 관련 질문이 나오면, 구체적 숫자와 조치를 함께 말하는 것이 핵심입니다.

### Q1: "프로젝트에서 일정이 밀렸던 경험이 있나요? 어떻게 대응했나요?"

**나쁜 답변:**
"네, 중간에 좀 밀렸는데 팀원들이 열심히 해서 어떻게든 됐습니다."

**좋은 답변:**
"3주차 스탠드업에서 외부 API 연동이 예상보다 2일 더 걸린다는 사실을 파악했습니다. 바로 팀에 공유했고, 4주차에 예약해 둔 버퍼 2일을 당겨 사용하기로 결정했습니다. 프런트 담당자가 백엔드 지원을 하루 돕고, Should 기능 1개를 다음 주로 이월했습니다. 덕분에 4주차 말에 핵심 흐름이 연결됐고 발표는 예정대로 진행됐습니다."

### Q2: "팀 프로젝트에서 계획 대비 실행의 차이를 어떻게 추적했나요?"

**좋은 답변:**
"매주 월요일 아침 15분 동안 주간 계획 보드를 작성했습니다. 완료 기준이 충족된 기능 수를 숫자로 세서 진행률을 측정했고, 편차가 발생하면 '왜 늦었는가' 1문장과 '무엇을 줄일 것인가' 결정을 바로 기록했습니다. 6주 프로젝트 동안 주요 마일스톤을 모두 예정일에 통과할 수 있었습니다."

### Q3: "캡스톤 프로젝트에서 가장 어려웠던 일정 관리 상황은?"

**좋은 답변:**
"5주차에 팀원 한 명이 개인 사정으로 참여가 어려워졌습니다. 그날 바로 해당 팀원의 담당 기능 목록을 공유받고, 이미 70% 완료된 기능은 제가 인계받고, 미착수 Should 기능 2개는 발표 범위에서 제외했습니다. 발표 스크립트도 수정해서 제외된 기능을 언급하지 않도록 했습니다. 일정 연장 없이 원래 발표 날짜를 지킬 수 있었습니다."

## 운영 체크리스트

- [ ] 마일스톤 4개가 정의되어 있습니다.
- [ ] 각 마일스톤마다 숫자 기반 통과 조건이 있습니다.
- [ ] 주간 계획표가 있습니다.
- [ ] 데일리 스탠드업 형식이 정해져 있습니다.
- [ ] 전체 일정의 20% 버퍼가 반영되어 있습니다.
- [ ] 블로커 공유 기준(24시간)이 합의되어 있습니다.
- [ ] 주간 점검 보드 형식이 있습니다.
- [ ] 3주차 이전에 배포 환경 테스트를 1회 이상 했습니다.
- [ ] 버퍼 소진 단계별 대응 기준이 팀 내 합의됐습니다.
- [ ] RACI에 각 기능의 백업 담당자가 기록돼 있습니다.
- [ ] 매주 월요일 15분 계획 회의가 정례화됐습니다.
- [ ] 주간 진행률을 "완료 기준 충족 기능 수"로 측정하고 있습니다.

## 정리와 다음 글

일정 관리는 바쁜 상태를 기록하는 일이 아니라 차이를 빨리 드러내는 일입니다. 마일스톤, 주간 계획, 블로커, 버퍼를 함께 운영하면 캡스톤 후반의 불확실성을 훨씬 안정적으로 다룰 수 있습니다. 다음 글에서는 이렇게 만든 결과를 발표 자료로 어떻게 정리할지 다룹니다.
