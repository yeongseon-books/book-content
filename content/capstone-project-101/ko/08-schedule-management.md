# Capstone Project 101 (8/10): 일정 관리

대부분의 캡스톤 일정은 마지막 주에 갑자기 망가지지 않습니다. 실제로는 중간부터 조금씩 밀리는데, 그 차이를 일찍 드러내는 장치가 없어서 마지막에 한꺼번에 터집니다.

좋은 일정은 보기 좋은 계획표가 아니라 계획과 실제의 차이를 계속 드러내는 시스템입니다. 마일스톤, 주간 계획, 버퍼, 블로커 기록이 모두 필요한 이유도 여기에 있습니다.

이 글은 Capstone Project 101 시리즈의 8번째 글입니다. 여기서는 마일스톤, 주간 계획, 스탠드업, 위험 버퍼를 묶어 현실적인 일정 운영 리듬을 만드는 방법을 설명합니다.

> 좋은 일정은 완벽한 예측이 아니라, 계획과 실제의 차이를 빨리 드러내고 조정할 수 있게 만드는 운영 리듬입니다.

## 이 글에서 다룰 문제

- 왜 완벽해 보이는 계획이 실제로는 자주 무너질까요?
- 마일스톤과 주간 계획은 어떻게 구분해서 써야 할까요?
- 데일리 스탠드업은 왜 짧고 반복 가능해야 할까요?
- 이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?
- 면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?

## 일정이 실제로 무너지는 이유

캡스톤 일정이 무너지는 가장 흔한 원인 세 가지:

**1. 구현 시간 과소 추정**
"이 기능은 하루면 될 것 같다"는 생각으로 시작했는데 실제로는 3일이 걸립니다. 예상보다 오래 걸리는 이유는 기술 학습, 디버깅, 팀원 간 통합 충돌 때문입니다.

**2. 테스트와 안정화 시간 미포함**
기능 구현만 일정에 넣고 테스트, 버그 수정, 데모 안정화는 "나중에"로 미룹니다. 그 "나중"이 발표 전날이 됩니다.

**3. 블로커를 늦게 공유**
"좀 더 해보다 말할게"라는 생각으로 2-3일 혼자 해결하다 공유하면, 팀 전체의 일정에 영향이 퍼집니다.

## 마일스톤 4개 구조

마일스톤은 너무 잘게 쪼개기보다 결과가 보이는 단위로 세 개에서 다섯 개 정도 두는 편이 좋습니다.

| 마일스톤 | 정의 | 증빙 산출물 | 통과 조건 |
| --- | --- | --- | --- |
| M1 요구사항 잠금 | Must 범위 확정 | 요구사항 시트 v1 | 변경 요청 보류 규칙 합의 |
| M2 MVP 연결 | 핵심 흐름 동작 | 데모 영상 초안 | 1회 성공 시연 |
| M3 품질 안정화 | 결함 위험 축소 | 테스트 리포트 | 주요 결함 0건 |
| M4 발표 준비 | 전달력 검증 | 슬라이드, 데모 각본 | 리허설 시간 준수 |

## 8주 프로젝트 간트 차트

```text
주차        1   2   3   4   5   6   7   8
문제/요구사항 ███ ██
MVP 구현         ████████
통합 테스트              ████████
발표 자료 준비                   ████████
리허설 및 수정                       ████████
```

| 주차 | 목표 | 완료 기준 | 위험 신호 |
| --- | --- | --- | --- |
| 1주차 | 문제 정의 및 요구사항 고정 | Must 스토리 팀 전체 승인 | 요구사항 변경 3건 이상 |
| 2주차 | 핵심 데이터/입력 경로 확보 | 샘플 입력 정상 처리 | 외부 데이터 접근 지연 |
| 3주차 | 핵심 흐름 구현 1 | 입력→계산 연결 | API 연동 실패 반복 |
| 4주차 | 핵심 흐름 구현 2 | 계산→결과 화면 연결 | 통합 충돌 3건 이상 |
| 5주차 | 테스트와 결함 수정 | Must 테스트 통과율 90% | 회귀 버그 증가 |
| 6주차 | 데모 리허설 | 60초 데모 3회 연속 성공 | 데모 실패 2회 이상 |
| 7주차 | 발표 자료 확정 | 슬라이드 팀 전체 리뷰 완료 | 슬라이드 장수 15장 초과 |
| 8주차 | 최종 발표 | 시간 내 완료, Q&A 대응 | 없음 (리허설로 준비) |

## 주간 실행 보드

아래 같은 보드는 예쁜 간트 차트보다 훨씬 빨리 현실을 보여 줍니다.

```text
주차     목표                  완료 조건               블로커                버퍼 사용
1주차    요구사항 확정          Must 스토리 승인         없음                  0일
2주차    핵심 흐름 구현         입력과 결과 화면 연결     CSV 데이터 정리 지연   1일
3주차    데모 리허설            60초 시연 성공           로그인 오류 재현       2일
4주차    발표 자료 확정         Q&A 준비 완료            없음                  0.5일
```

## 데일리 스탠드업 형식

스탠드업은 짧고 반복 가능한 형식이어야 합니다. 길어지는 순간 공유보다 회의가 됩니다.

```text
형식 (각 팀원 3분 이내):
1. 어제 완료한 것
2. 오늘 할 것
3. 막힌 것 (있다면 어떤 도움이 필요한가)
```

스탠드업의 목적은 보고가 아니라 블로커의 조기 발견입니다. 누군가 "막힌 것"에 무언가를 말하면 스탠드업 후 즉시 그 사람과 관련 담당자가 따로 논의합니다.

## 위험 버퍼 계산

버퍼는 낭비가 아니라 안전장치입니다.

```text
8주 프로젝트의 버퍼 계산:
총 작업 기간: 8주 = 40일
권장 버퍼: 20% = 8일
버퍼 배치:
  - 3주차 말 (통합 이슈 대응): 2일
  - 5주차 말 (테스트 초과 대응): 3일
  - 7주차 말 (발표 자료 수정): 3일
```

버퍼 사용 규칙:

- 블로커가 발생하면 즉시 버퍼에서 인정합니다.
- 버퍼가 50% 이상 소진되면 Must 기능 중 일부를 Should로 재분류합니다.
- 버퍼가 없는 주간에 새 기능 추가를 제안하면 다음 주로 이월합니다.

## 테스트 전략표 — 일정과 연계

일정에서 가장 자주 과소평가되는 것이 테스트 시간입니다.

| 테스트 수준 | 목적 | 담당 | 실행 시점 | 합격 기준 |
| --- | --- | --- | --- | --- |
| 단위 테스트 | 핵심 함수 로직 검증 | 개발자 | 기능 개발 직후 | 핵심 함수 통과율 90% 이상 |
| 통합 테스트 | 컴포넌트 간 연결 검증 | QA + 개발자 | 주 1회 | 핵심 흐름 100% 통과 |
| 회귀 테스트 | 기존 기능 영향 확인 | QA | 배포 전 | 주요 시나리오 실패 0건 |
| 데모 리허설 테스트 | 발표 환경 재현 검증 | 팀 전체 | 발표 전 주 2회 | 60초 데모 3회 연속 성공 |

## 일정 조정 의사결정 프레임

변경 요청이 들어올 때 아래 질문으로 판단합니다.

```text
질문 1: 이 변경이 핵심 흐름을 강화하는가?
질문 2: 이 변경이 발표 데모 성공 확률을 높이는가?
질문 3: 이 변경으로 Must 테스트 범위가 증가하는가?
질문 4: 증가한 범위를 현재 인력으로 감당 가능한가?
결론: 2개 이상 '아니오'면 다음 주로 이월
```

## 주간 점검 보드 템플릿

| 항목 | 계획 | 실제 | 편차 | 조치 |
| --- | --- | --- | --- | --- |
| 구현 완료율 | 60% | 45% | -15% | 범위 축소 검토 |
| 테스트 통과율 | 90% | 82% | -8% | 회귀 테스트 추가 |
| 리허설 횟수 | 2회 | 1회 | -1회 | 일정 재배치 |
| 블로커 해결율 | 100% | 75% | -25% | 백업 담당자 투입 |

편차를 기록할 때는 변명보다 조치가 중요합니다. "왜 늦었는가"를 1문장으로 적고, "무엇을 줄일 것인가"를 바로 결정해야 다음 주가 안정됩니다.

## 자주 하는 실수

| 실수 유형 | 구체적 상황 | 왜 문제인가 | 예방 방법 |
| --- | --- | --- | --- |
| 버퍼 없는 계획 | 기능 구현 시간만 계획 | 예상 밖 문제 하나에 전체 일정 붕괴 | 전체 일정의 20%를 버퍼로 확보 |
| 스탠드업 길어짐 | 블로커 토론을 스탠드업에서 함 | 15분이 45분이 되고 집중력 손실 | 스탠드업은 공유만, 토론은 따로 |
| 감으로 진행률 판단 | "많이 온 것 같다" | 실제 완료된 기능을 세면 30%인 경우 많음 | 완료 기준이 충족된 항목 수로만 측정 |
| 주간 계획 고정 | 지난주 계획을 수정 없이 이번 주 사용 | 현실과 계획이 점점 멀어짐 | 매주 월요일 계획을 현실에 맞게 조정 |
| 블로커 늦게 공유 | "조금 더 해보다 말할게" | 2-3일 지연 후 팀 전체에 영향 | 24시간 내 해결 안 되면 즉시 공유 |

## 처음 질문으로 돌아가기

- **왜 완벽해 보이는 계획이 실제로는 자주 무너질까요?**
  - 계획은 이상적인 상태를 가정하지만 실제는 그렇지 않습니다. 디버깅이 예상보다 2배 오래 걸리고, 팀원 일정이 엇갈리고, 통합 단계에서 충돌이 발생합니다. 이런 현실을 계획에 반영하지 않으면 버퍼 없이 꽉 찬 계획이 첫 번째 문제에서 무너집니다.

- **마일스톤과 주간 계획은 어떻게 구분해서 써야 할까요?**
  - 마일스톤은 "무엇이 끝났는가"를 판단하는 큰 단위입니다. MVP 연결, 품질 안정화, 발표 준비처럼 결과가 보이는 단위로 4-5개를 둡니다. 주간 계획은 "이번 주에 어떤 작업을 끝내는가"를 정하는 실행 단위입니다. 마일스톤은 목적지이고 주간 계획은 경로입니다.

- **데일리 스탠드업은 왜 짧고 반복 가능해야 할까요?**
  - 스탠드업의 목적은 블로커의 조기 발견입니다. 길어지면 팀원들이 준비하고 발표하는 발표회가 됩니다. 짧고 반복 가능해야 매일 지속할 수 있고, 그 반복이 블로커를 24시간 내에 드러내는 리듬을 만듭니다.

- **이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?**
  - 4주차까지는 "바쁜데 진행 중"이고, 5주차에 갑자기 "발표가 3주 남았는데 핵심 흐름이 연결이 안 되었다"는 것을 발견합니다. 마지막 2주를 기능 구현과 발표 준비를 동시에 하며 보내게 됩니다.

- **면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?**
  - 일정 편차를 어떻게 발견하고 조정했는가를 설명하는 능력입니다. "3주차에 API 연동 이슈로 1일 지연이 발생했습니다. 바로 공유하여 팀 전체가 인식했고, 4주차 버퍼 1일을 당겨 사용했습니다"처럼 구체적으로 말할 수 있어야 합니다.

## 운영 체크리스트

- [ ] 마일스톤 4개가 정의되어 있습니다.
- [ ] 주간 계획표가 있습니다.
- [ ] 데일리 스탠드업 형식이 정해져 있습니다.
- [ ] 전체 일정의 20% 버퍼가 반영되어 있습니다.
- [ ] 블로커 공유 기준(24시간)이 합의되어 있습니다.
- [ ] 주간 점검 보드 형식이 있습니다.

## 정리와 다음 글

일정 관리는 바쁜 상태를 기록하는 일이 아니라 차이를 빨리 드러내는 일입니다. 마일스톤, 주간 계획, 블로커, 버퍼를 함께 운영하면 캡스톤 후반의 불확실성을 훨씬 안정적으로 다룰 수 있습니다. 다음 글에서는 이렇게 만든 결과를 발표 자료로 어떻게 정리할지 다룹니다.
