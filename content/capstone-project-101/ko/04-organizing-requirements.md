# Capstone Project 101 (4/10): 요구사항 정리

요구사항 문서가 기능 목록으로만 끝나면 일정이 밀릴 때 무엇을 줄여야 할지 결정하기 어렵습니다. 구현이 끝났는지도 사람마다 다르게 해석합니다.

좋은 요구사항 문서는 기능 이름을 모아 놓은 목록이 아니라 사용자 스토리, 수용 기준, 비기능 조건, 우선순위를 연결한 작은 계약서에 가깝습니다.

이 글은 Capstone Project 101 시리즈의 4번째 글입니다. 여기서는 문제 문장을 실제 구현 대상과 검증 항목으로 바꾸는 요구사항 문서 구조를 설명합니다.

> 요구사항 문서는 기능을 모아 두는 저장소가 아니라, 무엇을 만들고 무엇을 검증할지 합의하는 추적 가능한 문서입니다.

## 이 글에서 다룰 문제

- 왜 기능 목록만으로는 요구사항이 충분하지 않을까요?
- 사용자 스토리와 기능 설명은 무엇이 다를까요?
- 수용 기준은 어느 정도까지 구체적이어야 할까요?
- 이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?
- 면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?

## 기능 목록 vs 요구사항 문서

요구사항은 바뀔 수 있습니다. 중요한 점은 바뀌더라도 무엇이, 왜 바뀌었는지 따라갈 수 있어야 한다는 사실입니다. 기능 이름만 적혀 있으면 변경이 생길 때 우선순위를 다시 정하기 어렵고, 테스트 범위도 흐려집니다.

### 실패 패턴: 기능 이름만 나열하기

5주차. "충돌 검사 기능은 끝났는데, 공유 기능이 아직이에요. 그런데 공유 기능이 정확히 무엇인지 기억이 나지 않아요."

팀원 A는 URL 공유라고 생각했고, 팀원 B는 이메일 전송이라고 생각했으며, 팀원 C는 Kakao 공유 버튼이라고 생각하고 있었습니다. "공유 기능"이라는 네 글자만 있었기 때문입니다.

발표 2주 전. "이게 완성된 건가요?"라는 질문에 팀원마다 다른 답이 나옵니다. 수용 기준이 없기 때문입니다.

### 성공 패턴: 스토리 + 수용 기준으로 합의하기

2주차. "ST-4: 학생으로서 충돌 결과 링크를 복사해서 팀원에게 보내고 싶다. 수용 기준: 공유 버튼 클릭 시 현재 세션 결과 URL이 클립보드에 복사된다."

팀원 모두 같은 문장을 보고 있습니다. 5주차에 기능이 완료되면 버튼을 클릭해서 URL이 복사되는지 확인하면 됩니다. 논쟁이 없습니다.

**기능 목록(불충분):**

```text
- 시간표 입력 기능
- 충돌 계산 기능
- 결과 표시 기능
- 공유 기능
```

**요구사항 문서(충분):**

```text
ID: ST-1
사용자 스토리: 복수전공 학생으로서 내 수강 신청 시간표를 입력해서
              충돌 여부를 30초 안에 확인하고 싶다
수용 기준:
  - 시간표를 텍스트로 붙여넣기 할 수 있다
  - 입력 후 1초 안에 충돌 여부가 표시된다
  - 충돌 과목과 시간대가 명확히 구분된다
비기능 요구: 모바일 우선, 로그인 없이 체험 가능
우선순위: Must
연결 기능: F-1 일정 입력, F-2 충돌 계산, F-3 결과 화면
```

차이는 "무엇을"이 아니라 "누가, 왜, 어떻게 확인하는지"가 함께 담겼다는 점입니다.

## 요구사항 시트 예시 — 수강 충돌 검사기

아래처럼 ID를 붙여 문서를 쓰면 구현 항목과 테스트 체크리스트를 나중에 연결하기가 쉬워집니다.

| ID | 유형 | 사용자 스토리 | 수용 기준 | 우선순위 |
| --- | --- | --- | --- | --- |
| ST-1 | 기능 | 학생으로서 시간표를 텍스트로 입력하고 싶다 | 샘플 3개 입력 시 오류 없이 저장 | Must |
| ST-2 | 기능 | 학생으로서 충돌 과목을 즉시 보고 싶다 | 충돌 케이스 10개 중 10개 검출 | Must |
| ST-3 | 기능 | 학생으로서 결과를 시각적으로 보고 싶다 | 핵심 정보 1스크롤 내 표시 | Should |

| NF-3 | 비기능 | — | 로그인 없이 핵심 흐름 체험 가능 | Must |

## 5단계 요구사항 작성 프로세스

### 1단계 — 사용자 스토리 작성

사용자 스토리는 "누구로서 무엇을 하고 싶다"는 형식으로 적습니다.

```text
형식: [사용자 역할]로서 [목표]를 하고 싶다, 그래서 [가치]를 얻고 싶다.

나쁜 예: 충돌 검사 기능을 구현한다
좋은 예: 복수전공 학생으로서 수강 신청 전에 시간표 충돌 여부를 바로 확인하고 싶다,
        그래서 잘못된 신청을 줄이고 싶다.
```

사용자 스토리를 INVEST 기준으로 점검합니다. 각 스토리가 독립적(Independent), 협상 가능(Negotiable), 가치 있음(Valuable), 추정 가능(Estimable), 작음(Small), 테스트 가능(Testable)한지 확인합니다.

```text
[INVEST 점검 예시 — ST-2]

ST-2: 학생으로서 충돌 과목을 즉시 보고 싶다

I (Independent): ST-1 입력과 독립 실행 불가 → 의존성 명시 필요
N (Negotiable): "즉시"의 의미를 협상 가능 → 수용 기준에서 "1초 이내"로 확정
V (Valuable): 핵심 가치 — 이것 없으면 제품 의미 없음
E (Estimable): 약 3-5일 추정 가능
S (Small): 충분히 작음 — 1개 스프린트 내 처리 가능
T (Testable): 충돌 케이스 10개로 100% 검출 여부 확인 가능
```

### 2단계 — 수용 기준 작성

수용 기준은 "이 기능이 완성되었는지 어떻게 알 수 있는가"를 정의합니다.

```text
나쁜 수용 기준: 빠르게 동작한다, 사용하기 편하다
좋은 수용 기준:
  - 5개 과목이 포함된 시간표를 30초 안에 입력할 수 있다
  - 결과가 1초 안에 표시된다
  - 충돌이 없는 경우 "충돌 없음" 메시지가 표시된다
  - 잘못된 형식 입력 시 명확한 오류 메시지가 나타난다
  - 모바일 390px 폭에서 레이아웃이 깨지지 않는다
```

수용 기준을 Given-When-Then 형식으로 작성하면 테스트 케이스로 바로 변환하기 쉽습니다.

```text
[Given-When-Then 예시 — ST-2]

Given: 사용자가 CS101 월 9-11시, MA201 월 10-12시를 입력했다
When:  "검사" 버튼을 클릭한다
Then:  1초 이내에 "CS101 - MA201: 월 10-11시 충돌" 메시지가 표시된다
And:   충돌 없는 과목은 목록에 표시되지 않는다

Given: 사용자가 형식 오류 텍스트를 입력했다
When:  "검사" 버튼을 클릭한다
Then:  2초 이내에 "입력 형식 오류: 'CS101 월 9시-11시' 형식으로 입력하세요" 메시지가 표시된다
```

### 3단계 — 비기능 요건 분리

비기능 요건은 기능 설명에 섞지 않고 따로 분리해야 합니다. 성능, 접근성, 보안, 유지보수성이 대표적인 비기능 요건입니다.

| 비기능 범주 | 예시 기준 | 테스트 방법 |
| --- | --- | --- |
| 성능 | 핵심 API 평균 응답 시간 1초 이하 | pytest + time.time() 측정 |
| 접근성 | 모바일 390px 폭에서 정상 동작 | Chrome DevTools 모바일 뷰 |
| 보안 | 사용자 시간표 데이터를 서버에 영구 저장하지 않음 | 서버 로그 확인 |
| 가용성 | 로그인 없이 핵심 기능 체험 가능 | 익명 세션으로 전체 흐름 테스트 |

비기능 요건을 구현 후에 발견하면 수정 비용이 큽니다. 특히 성능 요건은 아키텍처 결정 시점에 함께 검토해야 합니다.

### 4단계 — 우선순위 라벨링

우선순위는 일정이 흔들릴 때 가장 큰 힘을 발휘합니다. 모든 항목이 중요해 보이더라도 반드시 나눠 두어야 합니다.

| 라벨 | 정의 | 기준 | 충돌 검사기 예시 |
| --- | --- | --- | --- |
| Must | 핵심 흐름을 성립시키는 기능 | 없으면 데모 불가 | 시간표 입력, 충돌 검출, 오류 처리 |
| Should | 품질을 높이는 기능 | 없어도 데모는 가능 | 시각화, 결과 하이라이팅 |
| Could | 여유가 있을 때 추가 가능 | 있으면 좋음 | 공유 기능, 히스토리 |
| Won't | 이번 학기 제외 | 문서에만 기록 | 자동 연동, 대체 과목 추천 |

Must가 전체의 60%를 넘으면 범위 과대를 의심합니다. 처음에는 Must가 많아 보이지만 "이게 없으면 데모가 불가능한가"를 한 번 더 물어보면 절반 이하로 줄어드는 경우가 많습니다.

```text
[Must 줄이기 프로세스]

1단계: 모든 팀원이 각자 Must/Should/Could/Won't를 매긴다
2단계: Must가 가장 많은 팀원이 각 항목에 대해 "이것 없이 데모가 가능한가?"를 묻는다
3단계: "없어도 되지만 있으면 더 좋다"는 것은 Should로 이동
4단계: Must가 전체의 40-50%가 되면 균형이 맞다
```

### 5단계 — 추적성 연결

요구사항 ID와 구현 항목을 연결해 두면 변경 영향 범위를 빠르게 파악할 수 있습니다.

| 요구사항 ID | 사용자 스토리 | 수용 기준 | 테스트 케이스 | 데모 장면 |
| --- | --- | --- | --- | --- |
| ST-1 | 시간표를 입력한다 | 입력 오류 없이 저장 | TC-01, TC-02 | 장면 1 |
| ST-2 | 충돌 과목을 본다 | 충돌 100% 검출 | TC-03, TC-04, TC-05 | 장면 2 |
| ST-3 | 결과를 시각적으로 본다 | 1스크롤 내 표시 | TC-06 | 장면 2 |
| ST-5 | 오류 메시지를 받는다 | 2초 내 오류 표시 | TC-07 | 장면 3 |

## 요구사항과 테스트 코드 연결

요구사항 ID를 테스트 코드에 직접 표기하면 커버리지와 추적이 동시에 됩니다.

```python
# tests/test_requirements.py
# 각 테스트 함수명에 요구사항 ID를 포함시켜 추적성을 확보합니다

import pytest
import time
from src.conflict_checker import ConflictChecker

@pytest.fixture
def checker():
    return ConflictChecker()

class TestST1_ScheduleInput:
    """ST-1: 학생으로서 시간표를 텍스트로 입력하고 싶다"""

    def test_tc01_valid_input_accepted(self, checker):
        """TC-01: 유효한 형식의 시간표 입력 처리"""
        raw = "CS101 월 09:00-11:00\nMA201 화 13:00-15:00"
        result = checker.parse(raw)
        assert len(result) == 2
        assert result[0].code == "CS101"

    def test_tc02_multiple_courses_parsed(self, checker):
        """TC-02: 5개 과목 샘플 오류 없이 파싱"""
        raw = "\n".join([
            "CS101 월 09:00-11:00",
            "MA201 화 13:00-15:00",
            "ENG301 수 09:00-11:00",
            "PHY101 목 13:00-15:00",
            "CHE201 금 09:00-11:00",
        ])
        result = checker.parse(raw)
        assert len(result) == 5


class TestST2_ConflictDetection:
    """ST-2: 학생으로서 충돌 과목을 즉시 보고 싶다"""

    def test_tc03_conflict_detected(self, checker):
        """TC-03: 충돌하는 과목 쌍 검출"""
        raw = "CS101 월 09:00-11:00\nMA201 월 10:00-12:00"
        courses = checker.parse(raw)
        conflicts = checker.find_conflicts(courses)
        assert len(conflicts) == 1

    def test_tc04_no_conflict_on_different_day(self, checker):
        """TC-04: 다른 요일 과목은 충돌 없음"""
        raw = "CS101 월 09:00-11:00\nMA201 화 09:00-11:00"
        courses = checker.parse(raw)
        conflicts = checker.find_conflicts(courses)
        assert len(conflicts) == 0

    def test_tc05_result_within_one_second(self, checker):
        """TC-05: NF-1 성능 요건 — 1초 이내 응답 (수용 기준)"""
        raw = "\n".join([f"SUBJ{i:03d} 월 {9+i:02d}:00-{10+i:02d}:00"
                         for i in range(20)])
        start = time.time()
        courses = checker.parse(raw)
        checker.find_conflicts(courses)
        assert time.time() - start < 1.0


class TestST5_ErrorHandling:
    """ST-5: 학생으로서 잘못 입력한 경우 오류 메시지를 받고 싶다"""

    def test_tc07_invalid_format_raises_error(self, checker):
        """TC-07: 잘못된 형식 입력 시 ValueError 발생"""
        with pytest.raises(ValueError, match="입력 형식"):
            checker.parse("잘못된입력형식")
```

## 역할 분담과 협업 도구 연결

요구사항이 정리되면 다음으로 필요한 것은 역할-도구-의사결정 흐름의 일치입니다.

| 역할 | 담당 요구사항 범위 | 주요 산출물 | 승인 기준 |
| --- | --- | --- | --- |
| 팀 리드 | 요구사항 우선순위 유지 | 요구사항 시트, 변경 로그 | 변경 사유와 영향 범위 기록 |
| 백엔드 담당 | ST-2, NF-1 | API 명세, 계산 로직 | 테스트 통과율 100% |
| 프런트엔드 담당 | ST-1, ST-3, ST-5, NF-2 | 화면 흐름, 와이어프레임 | 60초 데모 가능 |
| QA 담당 | 전체 수용 기준 검증 | 테스트 시나리오, 결함 목록 | Must 기능 전부 통과 |

**협업 도구 선택 원칙:**

| 도구 | 권장 용도 | 주의 사항 |
| --- | --- | --- |
| Notion | 요구사항 초안, 회의록 | 버전 추적이 약함 — 중요 결정은 Git에도 저장 |
| GitHub Issues | 구현 이슈, 버그, 액션 아이템 | 요구사항 ID와 Issue ID를 연결해 사용 |
| Google Sheets | 우선순위 표, 일정 추적 | 실시간 공동 편집에 적합 |
| Figma | UI 흐름, 데모 스토리보드 | 와이어프레임은 수용 기준과 함께 저장 |

한 도구로 모든 문제를 해결하려 하지 않습니다. 문서 중심 도구, 작업 추적 도구, 소통 도구를 최소 조합으로 구분해야 운영이 단순해집니다.

## 요구사항 변경 관리

### 변경 요청 처리 프로토콜

구현 중 요구사항 변경 요청이 들어올 때는 아래 절차를 따릅니다.

```text
1) 변경 제안 등록: 무엇을, 왜 바꾸는지 3문장 작성
2) 영향 분석: 어떤 요구사항 ID, 기능, 테스트에 영향을 미치는지 확인
3) 우선순위 재검토: Must 기능 개수 변화 여부 확인
4) 역할 지정: 주 책임자/백업/검토자 지정
5) 승인/보류 결정: Must/Should 기준으로 판단
6) 기록 보존: 변경 로그에 날짜와 이유 추가
```

이 프로토콜을 적용하면 "아이디어는 좋지만 지금은 안 한다"를 근거 있게 설명할 수 있습니다.

### 변경 로그 예시

```text
[요구사항 변경 로그]

날짜        | ID    | 변경 내용                        | 이유              | 결정자
2025-03-10 | ST-4  | Could → Won't로 우선순위 낮춤   | 일정 여유 없음   | 팀 리드
2025-03-18 | NF-1  | 1초 이하 → 0.5초 이하로 강화   | 사용자 테스트 피드백 | 팀 전체
2025-03-25 | ST-6  | 새 스토리 추가 — 과목 삭제 기능  | UX 테스트에서 필요성 확인 | 팀 전체
2025-04-02 | ST-6  | Should → Must로 격상            | 없으면 데모 흐름 끊김 | 팀 리드
```

변경 로그는 복잡하게 만들지 않습니다. 날짜, 무엇이 바뀌었는지, 왜, 누가 결정했는지만 남기면 충분합니다.

## 자주 하는 실수

| 실수 유형 | 구체적 상황 | 왜 문제인가 | 예방 방법 |
| --- | --- | --- | --- |
| 기능 이름만 나열 | "충돌 검사 기능, 결과 화면 기능" | 완료 여부를 판단할 기준이 없음 | 수용 기준을 각 스토리에 필수 포함 |
| 비기능 요건 누락 | 기능만 적고 성능 기준 없음 | 발표 당일 느린 응답에 당황 | 비기능 요건 표를 별도로 작성 |
| 모든 항목을 Must로 설정 | "다 중요하다" | 일정이 밀릴 때 무엇을 줄일지 결정 불가 | "없으면 데모 불가"인 것만 Must |
| 수용 기준이 주관적 | "빠르다, 편하다, 명확하다" | 구현 후 완료 여부 논쟁 발생 | 시간·횟수·비율로 수치화 |
| 추적성 없음 | 요구사항과 테스트가 연결 안 됨 | 발표에서 어떤 요구사항을 보여주는지 설명 불가 | ID 기반 연결을 초기에 설정 |

## 처음 질문으로 돌아가기

- **왜 기능 목록만으로는 요구사항이 충분하지 않을까요?**
  기능 이름만 있으면 "완성되었는가"를 판단할 기준이 없습니다. 수용 기준이 없으면 구현이 끝났는지 팀마다 다르게 해석하고, 일정이 밀릴 때 무엇을 줄여야 할지 결정할 기준도 없어집니다. "공유 기능"이 URL 복사인지 이메일 전송인지도 기능 이름만으로는 알 수 없습니다.

- **사용자 스토리와 기능 설명은 무엇이 다를까요?**
  기능 설명은 "시스템이 무엇을 하는가"를 말합니다. 사용자 스토리는 "누가 무엇을 왜 원하는가"를 말합니다. "충돌 검사 기능"은 기능 설명이고, "복수전공 학생으로서 충돌 여부를 바로 확인하고 싶다"는 사용자 스토리입니다. 사용자 스토리는 기능의 목적을 함께 담기 때문에 범위를 자를 때 기준이 됩니다.

- **수용 기준은 어느 정도까지 구체적이어야 할까요?**
  팀원이 논쟁 없이 "통과/실패"를 판단할 수 있는 수준이어야 합니다. "1초 안에 결과가 나온다", "충돌 케이스 10개 중 10개 검출"처럼 시간·비율·횟수로 적으면 충분합니다. Given-When-Then 형식으로 적으면 테스트 케이스로 바로 전환되어 검증도 쉬워집니다.

- **이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?**
  범위 분쟁이 생깁니다. 누군가는 "이 기능이 MVP에 포함된다"고 생각하고, 다른 누군가는 "선택 사항"으로 생각합니다. 발표 직전에 Must 기능이 구현되지 않았다는 것을 발견하기도 합니다. 요구사항 정리 단계 2시간이 발표 전날 밤샘 작업 8시간을 막습니다.

- **면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?**
  요구사항을 추적 가능하게 관리하는 능력입니다. "무엇을 왜 Must로 정했는가", "요구사항이 변경되었을 때 어떻게 처리했는가", "수용 기준을 어떻게 테스트로 연결했는가"를 근거 있게 설명할 수 있으면 높은 평가를 받습니다.

## 운영 체크리스트

- [ ] 다섯 개 이상의 사용자 스토리가 있습니다.
- [ ] 각 스토리에 수용 기준이 붙어 있습니다.
- [ ] 수용 기준이 시간·횟수·비율로 수치화되어 있습니다.
- [ ] 비기능 요건 표가 있습니다.
- [ ] 우선순위 라벨이 있고, Must가 60% 이하입니다.
- [ ] 요구사항 ID가 테스트 케이스와 연결되어 있습니다.
- [ ] 변경 요청 처리 절차가 정해져 있습니다.
- [ ] 변경 로그가 날짜·이유·결정자와 함께 기록되어 있습니다.
- [ ] Won't 항목이 이유와 함께 문서화되어 있습니다.

## 정리와 다음 글

요구사항 정리는 기능 목록을 예쁘게 적는 일이 아니라, 범위와 완료 조건을 추적 가능하게 만드는 작업입니다. 스토리, 수용 기준, 비기능 요구, 우선순위를 함께 적어 두면 이후 설계와 일정 판단이 훨씬 빨라집니다. 변경이 생겨도 어디에 영향이 가는지 바로 파악할 수 있습니다. 다음 글에서는 이 일을 팀 안에서 어떻게 나눌지 다룹니다.
