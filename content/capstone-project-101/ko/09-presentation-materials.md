# Capstone Project 101 (9/10): 발표 자료 만들기

발표 자료가 길어지는 가장 흔한 이유는, 팀이 만든 모든 기능을 다 보여 주려 하기 때문입니다. 하지만 청중은 보통 기능 개수보다 왜 이 프로젝트가 의미 있었는지부터 알고 싶어 합니다.

좋은 발표 자료는 기능 카탈로그가 아니라 선택과 결과를 설명하는 서사입니다. 무엇을 왜 만들었는지, 어떤 결과가 나왔는지, 다음에 무엇을 바꿀지까지 짧게 이어져야 설득력이 생깁니다.

이 글은 Capstone Project 101 시리즈의 9번째 글입니다. 여기서는 문제·해결·결과 구조로 슬라이드를 설계하고, 데모 실패 대비안과 Q&A까지 함께 준비하는 방법을 다룹니다.

> 좋은 발표는 만든 기능을 다 보여 주는 자리가 아니라, 문제와 선택과 결과를 짧은 서사로 묶어 청중이 바로 이해하게 만드는 자리입니다.

## 이 글에서 다룰 문제

- 왜 기능 목록 중심 발표는 지루해질까요?
- 문제·해결·결과 구조는 왜 전달력이 높을까요?
- 슬라이드는 어떻게 구성해야 한 장당 메시지가 선명할까요?
- 이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?
- 면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?

## 발표 실패 패턴과 성공 패턴

**실패 패턴 — "기능 카탈로그 발표":**

- 슬라이드 1: 프로젝트 소개
- 슬라이드 2-10: 기능 A 설명, 기능 B 설명, 기능 C 설명...
- 슬라이드 11: 사용 기술 목록
- 슬라이드 12: 고생했습니다, 감사합니다
- 결과: 심사위원이 "그래서 이 프로젝트가 왜 필요한가요?"를 질문합니다.

**성공 패턴 — "문제-해결-결과 서사":**

- 슬라이드 1-2: "복수전공 학생이 수강 신청에서 겪는 불편" — 청중이 공감합니다.
- 슬라이드 3-4: "왜 이 접근 방식을 선택했는가" — 결정의 근거가 보입니다.
- 슬라이드 5: 60초 데모 — 실제 작동을 봅니다.
- 슬라이드 6-7: "무엇이 검증되었고 무엇이 남았는가" — 학습이 보입니다.
- 결과: 심사위원이 "다음 단계 계획이 있나요?"를 질문합니다.

## 발표 슬라이드 밀도 비교

슬라이드 한 장에 담긴 정보량과 발표 효과는 반비례하는 경우가 많습니다.

| 슬라이드 유형 | 정보 밀도 | 청중 반응 | 권장 여부 |
| --- | --- | --- | --- |
| 텍스트 10줄 + 기능 설명 | 매우 높음 | 읽느라 발표자 목소리 무시 | 지양 |
| 핵심 메시지 1문장 + 이미지 | 낮음 | 발표자 말에 집중 | 권장 |
| 비교 표 (Before/After) | 중간 | 차이를 시각적으로 파악 | 상황에 따라 |
| 기능 목록 나열 | 높음 | "이게 왜 필요하지?" 의문 | 지양 |
| 데이터/수치 중심 | 중간 | 성과를 명확히 확인 | 권장 |

한 슬라이드에 담을 수 있는 핵심 메시지를 미리 한 문장으로 정하고, 그 문장이 없으면 슬라이드를 만들지 않습니다.

## 발표 운영 시트

슬라이드 파일보다 먼저 아래 같은 운영 시트를 만들면 발표 흐름이 훨씬 안정됩니다.

```text
구간        시간  핵심 메시지                       백업 자료
문제 설명   2분   왜 이 문제가 실제로 불편한가        사용자 인터뷰 1장
해결 방식   2분   왜 이 흐름을 선택했는가            요구사항 표 1장
데모        3분   핵심 흐름 60초 시연               스크린샷 3장 + 녹화 영상
결과와 학습 2분   무엇이 확인되었고 무엇이 남았는가   피드백 요약 표
Q&A         6분   스택, 테스트, 범위 컷 설명         ADR, 회고 메모
```

## 10장 슬라이드 표준 구조

| 슬라이드 번호 | 제목 | 핵심 메시지 | 시각 자료 | 발표 시간 |
| --- | --- | --- | --- | --- |
| 1 | 문제 배경 | 왜 이 문제가 실제로 불편한가 | 사용자 상황 이미지 | 1분 |
| 2 | 사용자 정의 | 누구를 위한 해결인가 | 사용자 집단 설명 | 30초 |
| 3 | 기존 방식 한계 | 현재 불편의 구체적 근거 | 비교 표 또는 수치 | 1분 |
| 4 | 우리의 접근 | 핵심 흐름 선택 이유 | 시스템 흐름도 | 1분 |
| 5 | MVP 범위 | 무엇을 포함했고 무엇을 제외했는가 | 범위 표 | 30초 |
| 6 | 데모 | 핵심 흐름이 실제로 동작하는가 | 실시간 시연 | 3분 |
| 7 | 검증 결과 | 무엇이 수치로 확인되었는가 | 지표 표 | 1분 |
| 8 | 한계와 가정 | 무엇이 아직 검증 안 되었는가 | 가정 목록 | 30초 |
| 9 | 다음 단계 | 다음에 무엇을 바꿀 것인가 | 로드맵 | 30초 |
| 10 | 팀 학습 | 이 프로젝트에서 무엇을 배웠는가 | 요약 3문장 | 1분 |

한 슬라이드에 한 메시지만 담습니다. 슬라이드가 "두 가지를 동시에 설명한다"는 생각이 들면 두 장으로 나눕니다.

## 데모 각본 — 60초 버전

```text
0:00-0:10  오프닝
"지금부터 복수전공 학생이 수강 신청 전에 겪는 불편을
 30초 안에 해결하는 흐름을 보여드리겠습니다."

0:10-0:25  입력 단계
"수강 신청할 과목 5개를 텍스트로 붙여넣습니다."
(실제 시연: 샘플 시간표 붙여넣기)

0:25-0:45  계산/결과 단계
"검사 버튼을 누르면 충돌 과목과 시간대가 즉시 표시됩니다."
(실제 시연: 결과 화면 표시)

0:45-0:55  가치 확인
"기존에는 메모장에 수기로 비교했던 작업을
 이제 10초 안에 완료할 수 있습니다."

0:55-1:00  전환
"네트워크 이슈 발생 시 동일 흐름을 녹화 영상으로
 이어서 설명하겠습니다."
```

### 데모 안정화 체크리스트

- [ ] 발표 당일 환경(네트워크, 화면 크기)과 동일한 환경에서 3회 연속 성공
- [ ] 발표 10분 전 최종 확인 실행
- [ ] 스크린샷 3장과 녹화 영상 USB에 백업
- [ ] 네트워크 실패 시 "백업 자료로 전환하겠습니다" 문장 연습
- [ ] 데모 조작자와 발표자 역할 명확히 구분

## 데모 실패 유형과 즉각 대응 스크립트

데모 실패 상황을 미리 연습해 두면 발표 당일 당황하지 않습니다.

| 실패 유형 | 즉각 대응 | 전환 문장 |
| --- | --- | --- |
| 네트워크 오류 | 스크린샷으로 전환 | "인터넷 연결 문제가 있어, 사전에 준비한 캡처 화면으로 동일한 흐름을 설명하겠습니다." |
| 서버 응답 없음 | 녹화 영상 재생 | "서버 상태를 확인하는 동안, 동일한 시연을 담은 영상을 먼저 보여드리겠습니다." |
| 입력 오류 | 샘플 데이터 재입력 | "시연용 데이터를 다시 입력하겠습니다. 30초 안에 재시도하겠습니다." |
| 화면 공유 실패 | 노트북 직접 제시 | "화면 공유 연결을 재시도하는 동안, 잠시 Q&A를 먼저 진행하겠습니다." |

이 네 가지 시나리오를 리허설에서 최소 한 번씩 연습해 두면 발표 당일 당황 없이 진행할 수 있습니다.

## Q&A 준비표

| 질문 유형 | 예상 질문 | 답변 핵심 | 근거 문서 |
| --- | --- | --- | --- |
| 기술 선택 | 왜 이 스택을 골랐는가 | 팀 3명이 경험, 학습 비용 낮음 | ADR-001 |
| 범위 조정 | 왜 특정 기능을 제외했는가 | 데모 기여도 대비 난도 높음 | MVP 범위 표 |
| 테스트 | 신뢰성을 어떻게 확인했는가 | 통합 테스트 X개 시나리오 통과 | 테스트 리포트 |
| 확장 계획 | 다음 단계는 무엇인가 | 추천 기능/모바일 개선 | 로드맵 슬라이드 |
| 사용자 검증 | 실제 사용자 피드백이 있는가 | 3명 테스트, 결과 Y점 | 피드백 요약 표 |
| 성공 기준 | 성공했다고 판단한 근거는 | 30초 내 결과 확인 2/3명 달성 | 성공 지표 문서 |

### Q&A 답변 구조: 약한 답변과 강한 답변 비교

| 질문 | 약한 답변 | 강한 답변 |
| --- | --- | --- |
| 왜 로그인을 안 넣었나요? | "시간이 없어서요." | "로그인은 데모에서 직접 보여줄 필요가 없고 구현 비용이 높아 Won't로 분류했습니다. 제외 이유는 문서에 명시되어 있습니다." |
| 실제 사용자가 있나요? | "주변 친구들이 써봤습니다." | "복수전공 학생 3명에게 설명 없이 사용하게 했고, 2명이 결과 화면에 도달했습니다. 피드백 평균은 이해도 4.3점이었습니다." |
| 다음에 뭘 개선할 건가요? | "더 좋게 만들겠습니다." | "피드백에서 '결과를 저장하고 싶다'는 의견이 2명에게서 나왔습니다. 다음 단계는 세션 저장 기능과 모바일 UI 개선입니다." |

## 리허설 운영 원칙

발표는 리허설 횟수에 비례해 안정됩니다.

| 리허설 단계 | 시점 | 목적 | 체크 항목 |
| --- | --- | --- | --- |
| 1차 리허설 | 발표 2주 전 | 전체 흐름 확인 | 슬라이드 순서, 시간 측정 |
| 2차 리허설 | 발표 1주 전 | 데모 안정화 | 데모 연속 성공, Q&A 답변 |
| 최종 리허설 | 발표 전날 | 최종 확인 | 시간 준수, 백업 자료 점검 |

리허설에서 확인할 사항:

- 발표자 교대 지점을 초 단위로 표시합니다.
- 데모 실패 시 백업 전환 문장을 연습합니다.
- 각 슬라이드의 "한 줄 결론"을 고정합니다.
- 예상 질문 6개를 랜덤으로 뽑아 답변 리허설을 수행합니다.
- 시간 초과 시 줄일 슬라이드를 미리 지정합니다.

## 자주 하는 실수

| 실수 유형 | 구체적 상황 | 왜 문제인가 | 예방 방법 |
| --- | --- | --- | --- |
| 슬라이드에 텍스트 과다 | 슬라이드 하나에 글이 10줄 이상 | 청중이 읽는 동안 발표자 목소리를 듣지 않음 | 핵심 문장 1개 + 시각 자료로 제한 |
| 기능 나열 | "기능 A는 이렇고, 기능 B는 이렇고" | 왜 만들었는지 맥락이 없음 | 문제-해결-결과 순서 고수 |
| 데모 백업 없음 | 라이브 데모만 준비 | 네트워크 실패 시 데모 공백 발생 | 스크린샷 + 녹화 영상 필수 |
| Q&A 즉흥 대응만 | "질문이 나오면 그때 생각하자" | 기술 선택 이유를 즉석에서 설명 못함 | 예상 질문 6개 이상 미리 준비 |
| 시간 초과 | 연습 없이 발표 당일 처음 시간 측정 | 데모와 Q&A 시간을 잃음 | 리허설에서 시간을 실제 측정 |
| 팀원 역할 미분리 | 발표자 = 데모 조작자 | 발표 중 집중력이 분산됨 | 발표자와 데모 조작자를 명확히 분리 |

## 처음 질문으로 돌아가기

- **왜 기능 목록 중심 발표는 지루해질까요?**
  - 청중은 "무엇을 만들었는가"보다 "왜 이것을 만들었는가"와 "그래서 어떻게 달라졌는가"에 관심이 있습니다. 기능 목록은 "무엇을"만 보여주기 때문에 청중이 연결해야 할 이유를 스스로 찾아야 합니다. 그 연결이 어렵거나 없으면 발표가 지루해집니다.

- **문제·해결·결과 구조는 왜 전달력이 높을까요?**
  - 청중이 자연스럽게 따라올 수 있는 순서이기 때문입니다. 문제를 이해하면 해결의 선택 이유가 납득되고, 해결 과정을 이해하면 결과의 의미가 명확해집니다. 이 순서를 따르면 청중이 별도의 노력 없이 맥락을 파악할 수 있습니다.

- **슬라이드는 어떻게 구성해야 한 장당 메시지가 선명할까요?**
  - 슬라이드를 만들 때 "이 슬라이드의 핵심 메시지는 한 문장으로 무엇인가"를 먼저 정합니다. 그 문장이 없으면 슬라이드를 만들지 않습니다. 있으면 그 문장만 크게 보여주고 나머지는 시각 자료로 보완합니다.

- **이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?**
  - 발표 전날 슬라이드를 처음 만들기 시작합니다. 무엇을 먼저 설명해야 할지 방향이 없어서 기능 설명부터 채우기 시작합니다. 데모 각본이 없어서 발표 당일 처음으로 순서를 정합니다. Q&A에서 기술 선택 이유를 즉흥적으로 답합니다.

- **면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?**
  - 구조화된 커뮤니케이션 능력입니다. 복잡한 프로젝트를 제한된 시간 안에 핵심만 전달하는 능력, 예상치 못한 질문에 근거 있게 답하는 능력, 결과와 한계를 균형 있게 설명하는 능력을 봅니다.

## 운영 체크리스트

- [ ] 발표 운영 시트(구간, 시간, 핵심 메시지, 백업 자료)가 있습니다.
- [ ] 10장 슬라이드 구성이 확정되어 있습니다.
- [ ] 데모 각본이 60초 이내로 작성되어 있습니다.
- [ ] 백업 자료(스크린샷 3장 + 녹화 영상)가 준비되어 있습니다.
- [ ] Q&A 준비표에 6개 이상의 예상 질문이 있습니다.
- [ ] 리허설을 최소 2회 이상 완료했습니다.
- [ ] 데모 실패 4가지 시나리오를 리허설에서 연습했습니다.
- [ ] 발표자와 데모 조작자 역할이 구분되어 있습니다.

## 정리와 다음 글

발표 자료의 핵심은 많이 보여 주는 것이 아니라 빨리 이해시키는 것입니다. 문제·해결·결과 구조, 데모 각본, 백업 자료, Q&A 근거를 함께 준비하면 발표가 훨씬 단단해집니다. 다음 글에서는 프로젝트를 마친 뒤 학습을 남기는 회고를 다룹니다.
