# Capstone Project 101 (7/10): 기술 스택 선택

기술 스택 선택이 어렵다는 말에는 보통 두 가지가 섞여 있습니다. 새로운 기술을 써 보고 싶은 마음과, 학기 안에 반드시 끝내야 한다는 현실입니다.

캡스톤에서는 이 둘이 자주 충돌합니다. 그래서 좋은 기술보다 지금 우리 팀이 무리 없이 다룰 수 있는 기술을 먼저 정의해야 합니다.

이 글은 Capstone Project 101 시리즈의 7번째 글입니다. 여기서는 친숙도, 학습 비용, 운영 부담, 문서 품질을 함께 보며 현실적인 기술 선택 기준을 정리합니다.

> 좋은 기술 스택은 가장 화려한 조합이 아니라, 지금 팀이 일정 안에 배우고 구현하고 운영할 수 있는 조합입니다.

- 왜 가장 새로운 스택이 항상 정답은 아닐까요?
- 팀의 친숙도는 왜 일정과 직접 연결될까요?
- 학습 비용과 운영 부담은 어떻게 따져야 할까요?

- 면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?

## 기술 선택 실패 패턴과 성공 패턴

**실패 패턴 — "최신 기술로 인상 남기기":**

- FastAPI + React + PostgreSQL + Redis + Celery + Docker + Kubernetes를 선택합니다.
- 2주차: Celery 비동기 설정이 예상보다 복잡합니다.
- 3주차: Redis 캐시 무효화 로직에 2일을 씁니다.
- 4주차: Docker 컨테이너 간 네트워크 이슈로 배포가 안 됩니다.
- 발표 주: 핵심 기능이 안정화되지 않아 데모가 불안합니다.

**성공 패턴 — "지금 팀에 맞는 선택":**

- Flask + HTML(Jinja2 템플릿) + SQLite를 선택합니다.
- 2주차: 핵심 충돌 계산 로직 구현에 집중합니다.
- 3주차: 결과 화면 완성 후 에지 케이스 처리합니다.
- 4주차: 데모 안정화와 테스트에 집중합니다.
- 발표 주: 핵심 흐름이 100% 안정적으로 동작합니다.

차이는 기술 수준이 아니라 팀이 소화할 수 있는 복잡도를 현실적으로 판단했느냐입니다.

## 스택 복잡도 수준별 캡스톤 적합성

기술 스택의 복잡도는 기능 수가 아니라 팀이 처음 접하는 개념의 수로 측정하는 것이 더 정확합니다.

| 복잡도 | 예시 조합 | 새로 배워야 할 개념 수 | 6주 프로젝트 적합성 |
| --- | --- | --- | --- |
| 낮음 | Flask + Jinja2 + SQLite | 0-1개 (팀이 이미 아는 것) | 매우 적합 |
| 중간 | FastAPI + React + PostgreSQL | 2-3개 (비동기, 컴포넌트, ORM) | 조건부 적합 (팀 경험 있을 때) |
| 높음 | FastAPI + React + Redis + Celery | 4-5개 | 부적합 (학습에 시간 대부분 소비) |
| 매우 높음 | 위 + Docker + Kubernetes | 6개 이상 | 캡스톤에서 금지 수준 |

"조건부 적합"인 스택도 팀원 중 해당 기술을 실무 수준으로 아는 사람이 없으면 높음과 같은 위험이 됩니다. 친숙도 점수를 실제로 재봐야 합니다.

## ADR — 기술 결정 기록 예시

기술 선택은 말로만 합의하면 나중에 다시 흔들리기 쉽습니다. 아래처럼 한 장짜리 ADR을 남기면 변경 판단이 빨라집니다.

```text
ADR-001: 백엔드 프레임워크로 Flask를 선택한다

상태: Accepted
날짜: 2026-05-21
작성자: 백엔드 담당

문맥:
- 팀원 4명 중 3명이 Flask 경험이 있고, 6주 안에 데모를 만들어야 한다
- FastAPI는 비동기 처리와 Pydantic 학습 비용이 있다
- Django는 ORM과 관리자 기능이 MVP에 불필요

결정:
- Flask로 구현하고, 필요 시 FastAPI로 이전하는 조건을 명시한다

감수할 단점:
- 자동 문서화(OpenAPI)는 별도로 작성해야 한다
- 입력 검증 라이브러리를 추가로 선택해야 한다

재검토 조건:
- 인증, 비동기 API, 관리자 기능 범위가 크게 늘어날 때
```

## 기술 스택 결정표 — 영역별 비교

| 영역 | 후보 A | 후보 B | 후보 C | 선택 기준 | 최종 선택 |
| --- | --- | --- | --- | --- | --- |
| 백엔드 | FastAPI | Flask | Django | 팀 친숙도 + 학습 비용 | Flask |
| 프런트엔드 | React | Vue | HTMX+Jinja2 | 구현 속도 + 데모 안정성 | HTMX+Jinja2 |
| 데이터베이스 | PostgreSQL | SQLite | MongoDB | 설정 복잡도 | SQLite |
| 배포 | Render | Railway | 로컬 실행 | 설정 시간 + 무료 티어 | Render |
| 테스트 | pytest | unittest | 없음 | 표준 + 생태계 | pytest |

## 5단계 기술 선택 프로세스

### 1단계 — 후보 정리

후보는 너무 많이 늘리지 말고 비교 가능한 범위로 줄이는 편이 좋습니다. 각 영역마다 2-3개만 비교합니다.

```text
백엔드: FastAPI vs Flask (Django는 MVP에 과잉)
프런트엔드: React vs HTMX (Vue는 팀 경험 없음)
DB: PostgreSQL vs SQLite (Redis는 MVP 범위 초과)
```

### 2단계 — 친숙도 평가

친숙도는 단순 취향이 아니라 속도와 리스크에 직접 연결됩니다. 익숙한 도구는 구현뿐 아니라 디버깅도 빠릅니다.

| 기술 | 팀 경험자 수 | 경험 깊이 | 친숙도 점수 |
| --- | --- | --- | --- |
| Flask | 3/4명 | 중급 | 5점 |
| FastAPI | 1/4명 | 입문 | 2점 |
| Django | 0/4명 | 없음 | 1점 |

### 3단계 — 학습 비용 추산

학습 비용을 솔직하게 적는 것이 중요합니다. "배우면 된다"는 생각은 일정 계획에서 위험한 가정입니다.

| 기술 | 학습 비용 | 이유 |
| --- | --- | --- |
| Flask | 낮음 (0.5일) | 이미 팀 대부분이 경험 |
| FastAPI | 중간 (3일) | 비동기 + Pydantic 학습 |
| React | 높음 (5일) | 컴포넌트 + 상태관리 학습 |
| HTMX | 낮음 (1일) | HTML 기반, 빠른 적응 |

### 4단계 — 운영 부담 평가

운영 부담은 배포, 설정, 모니터링, 오류 대응까지 포함합니다. 구현이 쉬워도 운영이 무거우면 전체 부담이 커질 수 있습니다.

| 기술 | 운영 부담 | 주요 이유 |
| --- | --- | --- |
| SQLite | 매우 낮음 | 파일 기반, 설정 없음 |
| PostgreSQL | 중간 | 서버 설정, 연결 관리 |
| Render (배포) | 낮음 | Git push = 자동 배포 |
| Docker | 높음 | 이미지 빌드, 네트워크 설정 |

### 5단계 — 점수 계산과 결정

복잡한 모델보다 단순한 계산이 팀 합의에 더 도움이 됩니다.

```text
점수 = 친숙도 - 학습 비용 - 운영 부담 (각 1-5점)

FastAPI: 2 - 3 - 2 = -3
Flask:   5 - 1 - 1 = +3
Django:  1 - 4 - 3 = -6

선택: Flask (점수 +3, 팀 경험 풍부)
결정 이유: 6주 일정에서 학습 비용이 가장 낮고 디버깅이 빠름
```

## 기술 스택 선택 시나리오: 실제 팀 사례

### 시나리오 A — "팀 경험을 우선한 팀"

팀 구성: 백엔드 3명(Flask 경험), 프런트 1명(HTML/CSS 경험)
선택 스택: Flask + Jinja2 + SQLite

3주차에 팀원 한 명이 "React가 포트폴리오에 더 좋을 것 같다"고 제안했습니다. 팀은 이 ADR을 보여 주며 "현재 프런트 담당자가 React 경험이 없고, 남은 3주 안에 핵심 흐름 완성이 우선"이라고 설명했습니다.

6개월 후: 발표는 성공했고, 팀원은 이 경험을 "기술 선택 근거를 설명한 경험"으로 면접에서 활용했습니다.

### 시나리오 B — "새 기술을 무리하게 도입한 팀"

팀 구성: 백엔드 2명, 프런트 2명 (모두 React 입문 수준)
선택 스택: FastAPI + React + PostgreSQL + Docker

2주차에 Docker 설정에서 컨테이너 간 통신 문제가 생겼습니다. 1주를 여기에 썼고, 5주차에도 핵심 계산 로직이 불안정했습니다.

6개월 후: 발표는 어찌저찌 끝났지만 팀은 "스택 선택을 잘못했다"고 회고했습니다. 이 사례는 "새 기술 도입에서 배운 교훈"으로 면접에서 활용할 수는 있었습니다.

## 구현 품질 기준표

기술 스택을 선택한 뒤에는 구현 단계의 품질 기준을 즉시 정의합니다.

| 항목 | 기준 | 측정 방법 | 실패 시 조치 |
| --- | --- | --- | --- |
| 가독성 | 함수가 한 가지 책임만 수행 | 코드 리뷰 | 함수 분리 |
| 오류 처리 | 예외가 사용자 메시지로 연결 | 시나리오 테스트 | 오류 핸들러 추가 |
| 테스트 | Must 기능 단위 테스트 존재 | 테스트 리포트 | 테스트 케이스 작성 |
| 성능 | 핵심 API 평균 응답 1초 이내 | 간단 부하 측정 | 쿼리/로직 최적화 |
| 일관성 | 포맷터/린터 규칙 준수 | 자동 검사 | 포맷 수정 |
| 변경 안정성 | 수정 시 회귀 테스트 통과 | CI 또는 수동 체크리스트 | 원인 분석 후 재수정 |

## CI/CD 호환성 점검

기술 선택과 함께 CI/CD 환경 호환성을 확인합니다.

```yaml
name: capstone-ci
on:
  pull_request:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install -r requirements.txt
      - run: pytest -q
      - run: python -m flake8 src/
```

호환성 점검 항목:

- 선택한 런타임 버전이 CI 환경과 동일한지 확인합니다.
- 빌드 시간이 10분을 넘지 않는지 점검합니다.
- 시크릿 주입 방식이 로컬과 배포 환경에서 일관적인지 확인합니다.
- 롤백 절차를 문서로 기록하고 한 번 이상 실행해 봅니다.

## 기술 스택 변경을 검토해야 할 신호

초기에 선택한 스택을 바꾸는 결정은 어렵습니다. 그러나 아래 신호가 두 가지 이상 나타나면 변경을 검토할 필요가 있습니다.

| 신호 | 기준 | 판단 방법 |
| --- | --- | --- |
| 학습에 시간 대부분 소비 | 구현 시간의 50% 이상 | 주간 시간 기록 검토 |
| 같은 오류 반복 발생 | 동일 오류 3회 이상 | 블로커 기록 확인 |
| 핵심 흐름 미연결 상태 지속 | 3주차 이후에도 연결 안 됨 | MVP 진행률 점검 |
| 팀 외부 도움 없이 디버깅 불가 | StackOverflow 의존도 과다 | 실무 생산성 측정 |

변경을 결정했다면 반드시 ADR에 이유를 기록하고, 변경에 드는 시간 비용을 현재 스택 유지 비용과 비교해야 합니다.

## 자주 하는 실수

| 실수 유형 | 구체적 상황 | 왜 문제인가 | 예방 방법 |
| --- | --- | --- | --- |
| 인기만 보고 선택 | "요즘 다들 FastAPI 쓰니까" | 팀 학습 비용이 일정을 잠식 | 팀 친숙도 점수를 먼저 매김 |
| 팀 역량 무시 | "배우면 된다"고 계획 | 구현보다 학습에 시간이 더 걸림 | 과거 프로젝트 구현 속도 기준으로 추산 |
| 운영 비용 뒤늦게 발견 | Docker 설정에 3일을 씀 | 핵심 기능 구현 일정 압박 | 스택 선택 시 배포 복잡도 먼저 확인 |
| 결정 기록 없음 | "왜 Flask를 선택했는지 기억 안 남" | 발표 Q&A에서 근거를 설명 못함 | ADR을 작성해 저장소에 보관 |
| 과잉 스택 선택 | Redis + Celery + Docker Compose | MVP에 불필요한 복잡도 추가 | "MVP 없이도 필요한가"로 필터링 |

## 처음 질문으로 돌아가기

- **왜 가장 새로운 스택이 항상 정답은 아닐까요?**
  - 새 기술은 학습 비용, 디버깅 비용, 배포 비용이 모두 높습니다. 캡스톤의 일정은 짧기 때문에 그 비용이 핵심 기능 구현 시간을 잠식합니다. 발표에서 가장 중요한 것은 기술 선택이 아니라 핵심 흐름이 안정적으로 동작하는 것입니다.

- **팀의 친숙도는 왜 일정과 직접 연결될까요?**
  - 익숙한 기술은 구현뿐 아니라 디버깅도 빠릅니다. 처음 보는 에러 메시지를 해결하는 데 2-3시간이 걸리는 것과 15분이 걸리는 것은 일정에서 큰 차이입니다. 6주 프로젝트에서 이 차이가 쌓이면 발표 품질이 달라집니다.

- **학습 비용과 운영 부담은 어떻게 따져야 할까요?**
  - 학습 비용은 "팀원이 첫 번째 기능을 구현하는 데 걸리는 시간"으로 추산합니다. 운영 부담은 "배포하고 오류가 났을 때 수정하는 데 걸리는 시간"으로 추산합니다. 두 값을 더하면 실질적인 기술 선택 비용이 됩니다.

- **이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?**
  - 발표 2주 전에 배포 환경에서 처음 실행해보고 충돌을 발견합니다. 로컬에서는 잘 되는데 배포 환경에서 안 되는 문제로 마지막 주를 보냅니다. 기술 선택 논쟁이 구현 단계에서 다시 시작됩니다.

- **면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?**
  - 기술 선택에 대한 근거를 설명하는 능력입니다. "Flask를 선택한 이유는 팀원 3명이 경험이 있고, 6주 안에 안정적으로 데모를 만들기 위해서였습니다. FastAPI도 고려했으나 비동기 학습 비용이 일정에 부담이 될 것으로 판단했습니다"처럼 말할 수 있어야 합니다.

## 운영 체크리스트

- [ ] 각 영역에 후보 2-3개가 있습니다.
- [ ] 팀 친숙도 점수가 수치로 적혀 있습니다.
- [ ] 학습 비용이 일 단위로 추산되어 있습니다.
- [ ] 운영 부담 항목이 포함되어 있습니다.
- [ ] ADR이 작성되어 저장소에 있습니다.
- [ ] CI 환경 호환성이 확인되었습니다.
- [ ] 스택 변경 기준이 사전에 합의되어 있습니다.

## 정리와 다음 글

기술 스택 선택은 취향 경쟁이 아니라 리스크 조정입니다. 친숙도, 학습 비용, 운영 부담을 함께 보고 기록까지 남기면 기술 결정이 프로젝트를 돕는 방향으로 움직입니다. 다음 글에서는 이 선택을 일정으로 어떻게 관리할지 다룹니다.
