# Capstone Project 101 (1/10): 캡스톤 프로젝트란 무엇인가

학기 초, 팀원들이 처음 모여 앉습니다. 누군가 "AI로 뭔가 만들어 보자"고 말하고, 나머지는 고개를 끄덕입니다. 세 번째 회의쯤 되면 기능 목록이 스무 개를 넘습니다. 다섯 번째 회의에서는 어느 기능부터 시작할지 아무도 확신하지 못합니다. 그리고 학기 마지막 주, 반쯤 완성된 기능들이 뒤엉킨 채로 발표 날을 맞습니다.

이 패턴이 반복되는 이유는 기술 부족이 아닙니다. 캡스톤을 "큰 과제"로 이해했기 때문입니다. 캡스톤은 기능 몇 개를 구현하는 수업이 아닙니다. 문제를 정하고, 제한된 시간 안에 검증 가능한 결과를 만들고, 그 과정을 다시 설명하는 연습입니다. 이 관점이 없으면 초반의 주제 선정부터 마지막 발표와 회고까지 기준이 계속 바뀝니다.

캡스톤을 제대로 이해한 팀은 초반부터 다르게 시작합니다. 기능 목록보다 "어떤 사람이 어떤 불편을 겪는가"를 먼저 적고, 발표 당일 무엇을 보여 줄지를 미리 그려 봅니다. 그 한 가지 관점이 요구사항, MVP 설계, 일정, 발표 준비까지 학기 내내 팀의 판단을 안내하는 기준이 됩니다.

이 글은 Capstone Project 101 시리즈의 첫 번째 글입니다. 캡스톤을 일반 과제와 구분하는 기준과, 시리즈 전체를 읽을 때 붙잡아야 할 기본 흐름을 정리합니다.

> 캡스톤은 큰 기능을 많이 만드는 수업이 아니라, 문제 정의부터 데모와 회고까지 하나의 실무 흐름으로 연결하는 작은 제품 개발 연습입니다.

## 이 글에서 다룰 문제

- 캡스톤 프로젝트는 일반 과제와 무엇이 다를까요?
- 왜 많은 학교가 졸업 직전 과목으로 캡스톤을 운영할까요?
- 좋은 캡스톤은 기능 수보다 무엇으로 평가해야 할까요?
- 프로젝트 시작 시점에 무엇을 먼저 문서로 만들어야 할까요?
- 팀이 처음 모이면 가장 먼저 어떤 합의를 해야 할까요?

## 캡스톤과 일반 과제의 차이

일반 과제는 정답과 채점 기준이 비교적 분명합니다. 요구사항이 주어지고, 그것을 구현하면 됩니다. 캡스톤은 다릅니다. 문제를 어떻게 정의할지, 누구를 사용자로 볼지, 어디까지 만들지, 무엇을 데모로 보여 줄지까지 스스로 정해야 합니다. 결과물뿐 아니라 판단 과정 자체가 훈련 대상입니다.

| 비교 항목 | 일반 과제 | 캡스톤 프로젝트 |
| --- | --- | --- |
| 문제 출처 | 교수가 제시 | 팀이 발굴 |
| 채점 기준 | 사전에 명시 | 팀이 성공 지표 정의 |
| 사용자 | 명시되지 않음 | 팀이 직접 설정 |
| 범위 | 고정 | 팀이 의도적으로 자름 |
| 결과물 평가 | 기능 동작 여부 | 문제 해결 설득력 |
| 완료 기준 | 제출 | 데모와 회고 |

현업에서도 첫 프로젝트의 구조는 비슷합니다. 문제를 설명하고, 사용자 가치를 정리하고, 제한된 시간 안에 설득력 있는 결과를 만들어야 합니다. 이 구조를 처음 경험하는 자리가 캡스톤입니다.

## 실제 프로젝트 예시로 보는 차이

### 나쁜 시작 패턴 — "AI 캠퍼스 도우미"

1주차 회의에서 AI 챗봇, 학사 일정 알림, 강의실 예약, 식당 메뉴 추천, 분실물 신고, 학생증 갱신 안내, 교내 셔틀 시간표 기능을 목록화합니다. 팀원 모두 "좋아 보인다"며 동의합니다.

3주차에 챗봇 API 비용이 예상의 10배임을 발견합니다. 4주차에 식당 메뉴 데이터가 공개 API로 제공되지 않는다는 것을 확인합니다. 5주차에 학교 포털 데이터 접근 권한을 얻지 못합니다.

8주차(발표 주): 강의실 예약 화면만 절반쯤 완성된 채로 발표합니다. 심사위원이 "그래서 이 프로젝트가 어떤 문제를 해결하나요?"라고 묻습니다.

### 좋은 시작 패턴 — "수강 신청 시간표 충돌 검사기"

1주차 첫 회의에서 "복수전공 학생이 수강 신청 직전에 시간표 충돌을 30초 안에 확인하기 어렵다"는 문제를 한 문장으로 정합니다. 팀원 중 복수전공 학생 2명이 "이 문제를 실제로 경험했다"고 말합니다.

데모 기준을 "샘플 시간표 입력 후 60초 내 충돌 여부 표시"로 고정합니다. 제외 항목을 명시합니다: 로그인, 데이터 영구 저장, 추천 알고리즘, 소셜 공유.

2주차: 입력, 계산, 결과 표시 세 화면만 Must로 정의하고 구현을 시작합니다.

8주차: 핵심 흐름 전체가 안정적으로 동작하는 결과를 발표합니다. "왜 이 문제를 선택했는가", "왜 이 기능들을 제외했는가"를 명확히 설명합니다. 심사위원이 "다음 단계로 무엇을 추가할 계획인가요?"라고 묻습니다.

차이는 기술 실력이 아닙니다. 시작 시점에 무엇을 기준으로 삼았느냐입니다.

## 한 장짜리 프로젝트 브리프

캡스톤을 일반 과제와 구분하는 가장 쉬운 방법은, 프로젝트 시작 시점에 아래처럼 한 장짜리 브리프를 만들 수 있는지 보는 것입니다. 이 문서 하나가 학기 내내 팀의 판단 기준이 됩니다.

```text
[프로젝트 브리프]
프로젝트 제목: 수강 신청 시간표 충돌 검사기

대상 사용자: 복수전공 학생(우선), 신입생(2순위)
제외 사용자: 교직원, 대학원생, 외부 사용자

문제 문장:
  복수전공 학생은 수강 신청 직전에 여러 과목의 시간표를
  수동으로 비교해야 해서 30초 안에 충돌 여부를 확인하기 어렵다.

핵심 가치: 30초 안에 충돌 여부를 확인한다

데모 기준:
  샘플 시간표(5개 과목)를 텍스트로 붙여넣고
  60초 안에 충돌 여부와 충돌 과목 이름을 표시한다.

성공 기준:
  1. 첫 사용자 3명 중 2명 이상이 설명 없이 핵심 흐름을 끝낸다.
  2. 결과 계산이 1초 이내에 완료된다.

MVP 포함 항목:
  - 시간표 텍스트 입력
  - 충돌 여부 계산
  - 결과 화면 표시

MVP 제외 항목:
  - 로그인/회원 가입
  - 데이터베이스 영구 저장
  - 추천 알고리즘
  - 소셜 공유
  - 모바일 앱
  - 다국어 지원

주요 리스크:
  - 시간표 입력 형식이 다양할 수 있음 → 샘플 형식 1개로 고정
  - 발표장 인터넷 불안정 가능성 → 오프라인 스크린샷 백업 준비
```

각 항목을 채울 때 확인해야 할 사항입니다.

- 문제 문장이 기능 설명이 아니라 사용자 상황으로 적혀 있는지 확인합니다. "충돌 검사 기능을 만든다"가 아니라 "30초 안에 확인하기 어렵다"가 되어야 합니다.
- 핵심 가치가 시간, 정확도, 편의 같은 변화로 표현되어 있는지 봅니다.
- 데모 기준이 발표 당일 실제로 재현 가능한 수준인지 점검합니다.
- 성공 기준이 팀 내부 감상이 아니라 관찰 가능한 행동인지 살핍니다.
- 제외 항목이 포함 항목보다 많아야 범위가 제대로 잘린 것입니다.

## 주제 선정 평가 매트릭스

캡스톤의 출발점은 결국 주제 선택입니다. 초기에는 반드시 비교 가능한 틀을 먼저 만들고, 그 틀로 후보를 검증해야 합니다.

| 평가 항목 | 1점 기준 | 3점 기준 | 5점 기준 | 가중치 |
| --- | --- | --- | --- | --- |
| 사용자 문제 명확성 | 사용자 불명확 | 사용자 집단은 있으나 상황 모호 | 사용자와 상황이 한 문장으로 명확 | 0.25 |
| 검증 가능성 | 데모 기준 없음 | 데모 가능하지만 측정 약함 | 데모와 성공 지표가 모두 명확 | 0.20 |
| 구현 실현성 | 핵심 기술 전원 미경험 | 일부 경험 보유 | 핵심 기술 다수 경험 보유 | 0.20 |
| 데이터/리소스 접근성 | 접근 경로 없음 | 부분 접근 가능 | 시작 시점에 확보 가능 | 0.15 |
| 발표 전달력 | 설명이 추상적 | 설명 가능하나 핵심 약함 | 3분 내 설득 가능한 구조 | 0.10 |
| 확장 여지 | 확장 경로 불명확 | 제한적 확장 가능 | 확장 가설 2개 이상 명확 | 0.10 |

합계 숫자보다 더 중요한 것은 항목별 편차입니다. 총점이 높아도 `검증 가능성`이 낮다면 학기 후반 발표 준비 단계에서 위험이 크게 드러납니다.

### 좋은 주제와 나쁜 주제 비교

| 구분 | 좋은 주제 예시 | 나쁜 주제 예시 | 차이의 핵심 |
| --- | --- | --- | --- |
| 문제 정의 | 수강 신청 직전 시간표 충돌 확인이 느리다 | AI로 대학생활을 혁신한다 | 좋은 주제는 문제가 관찰 가능함 |
| 사용자 범위 | 신입생과 복수전공생 | 대학생 전체, 교직원, 외부 사용자 | 좋은 주제는 첫 사용자가 좁음 |
| 데모 가능성 | 샘플 데이터로 60초 시연 가능 | 대규모 실시간 데이터 연동 필수 | 좋은 주제는 발표 환경에서 재현 가능 |
| 기술 복잡도 | 기존 프레임워크로 구현 가능 | 다중 모델, 실시간 스트리밍, 추천 엔진 동시 구축 | 좋은 주제는 핵심 리스크가 제한됨 |
| 성공 기준 | 첫 사용자가 30초 내 충돌 여부 확인 | 사용자 만족도 향상 | 좋은 주제는 측정 기준이 명확함 |

## 프로젝트 제안서 1페이지 템플릿

캡스톤을 정의한 직후에 가장 먼저 만들어야 할 문서는 제안서 초안입니다. 제안서는 팀이 같은 문제를 같은 단어로 합의했는지 확인하는 문서입니다.

```text
[제안서 초안 v1]
프로젝트명:
작성일:
팀원:

1. 문제 요약(3문장):

2. 핵심 사용자:
   주 사용자:
   보조 사용자:
   제외 사용자:

3. 핵심 시나리오(5단계 이내):
   1단계:
   2단계:
   3단계:
   4단계:
   5단계:

4. MVP 범위:
   포함:
   제외:

5. 성공 지표(수치 2개):
   지표 1:
   지표 2:

6. 데모 방식:
   방식: 라이브 / 녹화 / 혼합
   백업 계획:

7. 주요 리스크와 대응:
   리스크 1: / 대응:
   리스크 2: / 대응:
```

`MVP 비범위`를 명시하면 학기 중반에 발생하는 범위 확장을 미리 제어할 수 있습니다. 팀원이나 지도교수가 "이 기능도 넣으면 어떨까"라고 제안할 때 "비범위로 문서에 명시한 항목입니다"라고 근거 있게 답할 수 있습니다.

## 팀 운영 기초 규칙

프로젝트 브리프를 완성한 뒤 바로 다음으로 해야 할 것이 팀 운영 규칙 합의입니다.

### Git 브랜치 전략 최소 규칙

| 항목 | 규칙 | 이유 |
| --- | --- | --- |
| 기본 브랜치 | `main` 보호 | 직접 푸시를 막아 품질 유지 |
| 작업 브랜치 | `feat/*`, `fix/*`, `docs/*` | 변경 목적을 이름에서 즉시 식별 |
| 병합 방식 | PR + 1인 승인 | 단독 판단으로 인한 누락 방지 |
| 머지 조건 | 테스트 통과, 충돌 없음 | 데모 직전 회귀 실패 예방 |

```bash
# 작업 브랜치 생성 및 첫 커밋
git checkout -b docs/project-brief
git add docs/project-brief.md
git commit -m "docs: add initial project brief and scope"
git push -u origin docs/project-brief

# PR 생성 후 팀원 1인 승인 후 main에 머지
# main 브랜치 직접 푸시는 금지
```

### 의사결정 기록 규칙

구두로만 합의하면 나중에 "그때 그렇게 말했나"라는 분쟁이 생깁니다. 모든 중요한 결정은 이슈나 문서에 남깁니다.

```markdown
## 결정 로그

### 2026-09-10: 로그인 기능 MVP 제외 결정
- 결정: 로그인 기능을 MVP 범위에서 제외한다
- 이유: 구현 비용(2일 예상) 대비 데모 기여도 낮음
         익명 사용으로도 핵심 흐름(충돌 확인) 검증 가능
- 대안: 발표 후 확장 단계에서 추가 검토
- 결정자: 팀 전체 합의

### 2026-09-12: 입력 형식을 텍스트 붙여넣기로 고정
```

## 처음 질문으로 돌아가기

- **캡스톤 프로젝트는 일반 과제와 무엇이 다를까요?**
  - 일반 과제는 정해진 요구사항을 구현하면 됩니다. 캡스톤은 문제 선택, 사용자 정의, 범위 설정, 성공 기준까지 모두 팀이 스스로 정해야 합니다. 결과물보다 판단 과정 자체가 훈련 대상입니다.

- **왜 많은 학교가 졸업 직전 과목으로 캡스톤을 운영할까요?**
  - 현업에서 요구하는 핵심 역량이 "문제를 정의하고 제한된 시간 안에 설득력 있는 결과를 만드는 능력"이기 때문입니다. 캡스톤은 그 전체 흐름을 학교 환경에서 경험하는 유일한 기회입니다.

- **좋은 캡스톤은 기능 수보다 무엇으로 평가해야 할까요?**
  - 핵심 사용자 흐름을 끝까지 연결했는가, 문제 정의와 데모 결과가 일치하는가, 무엇을 배웠는지 설명할 수 있는가로 평가해야 합니다. 기능이 20개여도 흐름이 연결되지 않으면 설득력이 없습니다.

- **프로젝트 시작 시점에 무엇을 먼저 문서로 만들어야 할까요?**
  - 한 장짜리 프로젝트 브리프입니다. 사용자, 문제 문장, 핵심 가치, 데모 기준, 성공 기준, 제외 항목이 한 페이지에 담겨야 팀 합의의 기준점이 됩니다.

- **팀이 처음 모이면 가장 먼저 어떤 합의를 해야 할까요?**
  - 문제 문장과 데모 기준, 그리고 Git 브랜치 전략과 의사결정 기록 규칙입니다. 이 네 가지가 정해지면 이후 요구사항, MVP, 일정, 발표 준비까지 모든 결정의 기준이 생깁니다.

## 운영 체크리스트

- [ ] 프로젝트를 한 줄로 설명할 수 있습니다.
- [ ] 첫 사용자 집단이 10명 이하로 정해져 있습니다.
- [ ] 핵심 가치가 변화 중심으로 적혀 있습니다.
- [ ] 성공 기준에 숫자가 들어 있습니다.
- [ ] 발표용 데모 형식이 정해져 있습니다.
- [ ] 제외 항목이 5개 이상 명시되어 있습니다.
- [ ] `main` 브랜치 보호 규칙이 설정되어 있습니다.
- [ ] 의사결정 기록 방식이 합의되어 있습니다.
- [ ] 제안서 초안이 팀 전체와 공유되었습니다.

## 정리

캡스톤의 출발점은 기능 목록이 아니라 프로젝트 전체 흐름을 보는 관점입니다. 문제 정의, 요구사항, MVP, 데모, 회고가 하나의 체인으로 이어져야 이후 판단도 흔들리지 않습니다. 캡스톤은 가장 거대한 제품이 아니라 가장 설득력 있게 완주한 제품을 만드는 연습입니다. 그 기준을 초반에 잡으면 남은 아홉 장의 내용이 하나의 방향으로 정렬됩니다.
