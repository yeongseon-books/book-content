# Capstone Project 101 (1/10): 캡스톤 프로젝트란 무엇인가

학기 초, 팀원들이 처음 모여 앉습니다. 누군가 "AI로 뭔가 만들어 보자"고 말하고, 나머지는 고개를 끄덕입니다. 세 번째 회의쯤 되면 기능 목록이 스무 개를 넘습니다. 다섯 번째 회의에서는 어느 기능부터 시작할지 아무도 확신하지 못합니다. 그리고 학기 마지막 주, 반쯤 완성된 기능들이 뒤엉킨 채로 발표 날을 맞습니다.

이 패턴이 반복되는 이유는 기술 부족이 아닙니다. 캡스톤을 "큰 과제"로 이해했기 때문입니다. 캡스톤은 기능 몇 개를 구현하는 수업이 아닙니다. 문제를 정하고, 제한된 시간 안에 검증 가능한 결과를 만들고, 그 과정을 다시 설명하는 연습입니다. 이 관점이 없으면 초반의 주제 선정부터 마지막 발표와 회고까지 기준이 계속 바뀝니다.

캡스톤을 제대로 이해한 팀은 초반부터 다르게 시작합니다. 기능 목록보다 "어떤 사람이 어떤 불편을 겪는가"를 먼저 적고, 발표 당일 무엇을 보여 줄지를 미리 그려 봅니다. 그 한 가지 관점이 요구사항, MVP 설계, 일정, 발표 준비까지 학기 내내 팀의 판단을 안내하는 기준이 됩니다.

이 글은 Capstone Project 101 시리즈의 첫 번째 글입니다. 캡스톤을 일반 과제와 구분하는 기준과, 시리즈 전체를 읽을 때 붙잡아야 할 기본 흐름을 정리합니다.

> 캡스톤은 큰 기능을 많이 만드는 수업이 아니라, 문제 정의부터 데모와 회고까지 하나의 실무 흐름으로 연결하는 작은 제품 개발 연습입니다.

## 이 글에서 다룰 문제

- 캡스톤 프로젝트는 일반 과제와 무엇이 다를까요?
- 왜 많은 학교가 졸업 직전 과목으로 캡스톤을 운영할까요?
- 좋은 캡스톤은 기능 수보다 무엇으로 평가해야 할까요?
- 프로젝트 시작 시점에 무엇을 먼저 문서로 만들어야 할까요?
- 팀이 처음 모이면 가장 먼저 어떤 합의를 해야 할까요?

## 캡스톤과 일반 과제의 차이

일반 과제는 정답과 채점 기준이 비교적 분명합니다. 요구사항이 주어지고, 그것을 구현하면 됩니다. 캡스톤은 다릅니다. 문제를 어떻게 정의할지, 누구를 사용자로 볼지, 어디까지 만들지, 무엇을 데모로 보여 줄지까지 스스로 정해야 합니다. 결과물뿐 아니라 판단 과정 자체가 훈련 대상입니다.

현업에서도 첫 프로젝트의 구조는 비슷합니다. 문제를 설명하고, 사용자 가치를 정리하고, 제한된 시간 안에 설득력 있는 결과를 만들어야 합니다. 캡스톤을 잘 이해한 팀은 기능 목록보다 문제와 데모를 먼저 붙잡습니다.

## 한 장짜리 프로젝트 브리프

캡스톤을 일반 과제와 구분하는 가장 쉬운 방법은, 프로젝트 시작 시점에 아래처럼 한 장짜리 브리프를 만들 수 있는지 보는 것입니다.

```text
프로젝트 제목: 수강 신청 시간표 충돌 검사기
대상 사용자: 복수전공 학생과 신입생
문제 문장: 수강 신청 직전에 시간표 충돌을 직접 계산하느라 시간이 오래 걸린다
핵심 가치: 30초 안에 충돌 여부를 확인한다
데모 기준: 샘플 시간표를 넣고 충돌 여부와 추천 대안을 보여 준다
성공 기준: 첫 사용자가 설명 없이 핵심 흐름을 끝낸다
```

- 문제 문장이 기능 설명이 아니라 사용자 상황으로 적혀 있는지 확인합니다.
- 핵심 가치가 시간, 정확도, 편의 같은 변화로 표현되어 있는지 봅니다.
- 데모 기준이 발표 당일 실제로 재현 가능한 수준인지 점검합니다.
- 성공 기준이 팀 내부 감상이 아니라 관찰 가능한 행동인지 살핍니다.

## 주제 선정 평가 매트릭스

캡스톤의 출발점은 결국 주제 선택입니다. 주제는 한 번 고르고 끝나는 명사가 아니라, 학기 내내 의사결정을 통과시키는 기준 문장입니다. 초기에는 반드시 비교 가능한 틀을 먼저 만들고, 그 틀로 후보를 검증해야 합니다.

| 평가 항목 | 질문 | 1점 기준 | 3점 기준 | 5점 기준 | 가중치 |
| --- | --- | --- | --- | --- | --- |
| 사용자 문제 명확성 | 누가 어떤 불편을 겪는가가 선명한가 | 사용자 불명확 | 사용자 집단은 있으나 상황 모호 | 사용자와 상황이 한 문장으로 명확 | 0.25 |
| 검증 가능성 | 한 학기 안에 데모와 피드백이 가능한가 | 데모 기준 없음 | 데모 가능하지만 측정 약함 | 데모와 성공 지표가 모두 명확 | 0.20 |
| 구현 실현성 | 팀 기술 역량으로 구현 가능한가 | 핵심 기술 전원 미경험 | 일부 경험 보유 | 핵심 기술 다수 경험 보유 | 0.20 |
| 데이터/리소스 접근성 | 필요한 데이터와 환경을 확보 가능한가 | 접근 경로 없음 | 부분 접근 가능 | 시작 시점에 확보 가능 | 0.15 |
| 발표 전달력 | 문제-해결-결과를 짧게 설명 가능한가 | 설명이 추상적 | 설명 가능하나 핵심 약함 | 3분 내 설득 가능한 구조 | 0.10 |
| 확장 여지 | MVP 이후 확장 방향이 존재하는가 | 확장 경로 불명확 | 제한적 확장 가능 | 확장 가설 2개 이상 명확 | 0.10 |

합계 숫자보다 더 중요한 것은 항목별 편차입니다. 총점이 높아도 `검증 가능성`이 낮다면 학기 후반 발표 준비 단계에서 위험이 크게 드러납니다. 반대로 총점이 약간 낮아도 사용자 문제 명확성과 데모 가능성이 높다면 캡스톤에서는 더 안전한 선택입니다.

### 좋은 주제와 나쁜 주제 비교

| 구분 | 좋은 주제 예시 | 나쁜 주제 예시 | 차이의 핵심 |
| --- | --- | --- | --- |
| 문제 정의 | 수강 신청 직전 시간표 충돌 확인이 느리다 | AI로 대학생활을 혁신한다 | 좋은 주제는 문제가 관찰 가능함 |
| 사용자 범위 | 신입생과 복수전공생 | 대학생 전체, 교직원, 외부 사용자 | 좋은 주제는 첫 사용자가 좁음 |
| 데모 가능성 | 샘플 데이터로 60초 시연 가능 | 대규모 실시간 데이터 연동 필수 | 좋은 주제는 발표 환경에서 재현 가능 |
| 기술 복잡도 | 기존 프레임워크로 구현 가능 | 다중 모델, 실시간 스트리밍, 추천 엔진 동시 구축 | 좋은 주제는 핵심 리스크가 제한됨 |
| 성공 기준 | 첫 사용자가 30초 내 충돌 여부 확인 | 사용자 만족도 향상 | 좋은 주제는 측정 기준이 명확함 |

## 프로젝트 제안서 1페이지 템플릿

캡스톤을 정의한 직후에 가장 먼저 만들어야 할 문서는 제안서 초안입니다. 제안서는 팀이 같은 문제를 같은 단어로 합의했는지 확인하는 문서입니다.

```text
프로젝트명:
문제 요약(3문장):
핵심 사용자:
핵심 시나리오(5단계 이내):
MVP 범위(포함):
MVP 비범위(제외):
성공 지표(수치 2개):
데모 방식(라이브/녹화/혼합):
주요 리스크와 대응:
```

`MVP 비범위`를 명시하면 학기 중반에 발생하는 범위 확장을 미리 제어할 수 있습니다.

### Git 브랜치 전략 최소 규칙

문서 합의가 끝났으면 바로 저장소 운영 규칙을 정해야 합니다.

| 항목 | 규칙 | 이유 |
| --- | --- | --- |
| 기본 브랜치 | `main` 보호 | 직접 푸시를 막아 품질 유지 |
| 작업 브랜치 | `feat/*`, `fix/*`, `docs/*` | 변경 목적을 이름에서 즉시 식별 |
| 병합 방식 | PR + 1인 승인 | 단독 판단으로 인한 누락 방지 |
| 머지 조건 | 테스트 통과, 충돌 없음 | 데모 직전 회귀 실패 예방 |

```bash
git checkout -b feat/problem-card
git add .
git commit -m "add initial problem card and scope"
git push -u origin feat/problem-card
```

## 처음 질문으로 돌아가기

- **캡스톤 프로젝트는 일반 과제와 무엇이 다를까요?**
  일반 과제는 정답과 채점 기준이 정해져 있지만, 캡스톤은 문제 정의부터 데모까지 스스로 기준을 만들어야 합니다. 결과물뿐 아니라 판단 과정 자체가 훈련의 대상입니다.

- **왜 많은 학교가 졸업 직전 과목으로 캡스톤을 운영할까요?**
  현업 초기 프로젝트 경험을 학교에서 체험하기 위해서입니다. 문제를 정의하고, 시간 안에 결과를 만들고, 의사결정을 설명하는 경험은 취업 직후 그대로 반복됩니다.

- **좋은 캡스톤은 기능 수보다 무엇으로 평가해야 할까요?**
  문제를 얼마나 명확히 정의했는지, 데모를 얼마나 설득력 있게 만들었는지, 팀의 판단 과정을 얼마나 잘 기록했는지를 봐야 합니다. 기능이 많아도 핵심 흐름이 설명되지 않으면 설득력이 약합니다.

- **프로젝트 시작 시점에 무엇을 먼저 문서로 만들어야 할까요?**
  한 장짜리 프로젝트 브리프입니다. 사용자, 문제 문장, 핵심 가치, 데모 기준, 성공 기준이 한 페이지에 담겨야 팀의 대화가 같은 언어로 이어집니다.

- **팀이 처음 모이면 가장 먼저 어떤 합의를 해야 할까요?**
  주제보다 기준을 먼저 합의해야 합니다. 어떤 문제를 풀고, 누구를 위해 만들고, 어떤 결과를 발표 당일 보여 줄지에 대한 기준이 없으면 주제를 정해도 방향이 흔들립니다.

## 운영 체크리스트

- [ ] 프로젝트를 한 줄로 설명할 수 있습니다.
- [ ] 첫 사용자 집단이 정해져 있습니다.
- [ ] 가치가 변화 중심으로 적혀 있습니다.
- [ ] 성공 기준에 숫자가 들어 있습니다.
- [ ] 발표용 데모 형식이 정해져 있습니다.
- [ ] `main` 브랜치 보호 규칙이 설정되어 있습니다.
- [ ] 제안서 초안이 팀 전체와 공유되었습니다.

## 정리

캡스톤의 출발점은 기능 목록이 아니라 프로젝트 전체 흐름을 보는 관점입니다. 문제 정의, 요구사항, MVP, 데모, 회고가 하나의 체인으로 이어져야 이후 판단도 흔들리지 않습니다. 캡스톤은 가장 거대한 제품이 아니라 가장 설득력 있게 완주한 제품을 만드는 연습입니다. 그 기준을 초반에 잡으면 남은 아홉 장의 내용이 하나의 방향으로 정렬됩니다.
