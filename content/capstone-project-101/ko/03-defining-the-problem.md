# Capstone Project 101 (3/10): 문제 정의

문제 정의가 흐리면 팀은 계속 해결책만 바꿉니다. 기능은 늘어나는데 왜 만드는지 설명은 점점 약해지는 경우가 많습니다.

문제 문장은 프로젝트의 기준점입니다. 요구사항을 넣을지 뺄지, MVP를 어디까지 자를지, 발표에서 무엇을 강조할지 모두 이 문장으로 다시 돌아와야 합니다.

이 글은 Capstone Project 101 시리즈의 3번째 글입니다. 여기서는 기능 설명과 문제 정의를 구분하고, 사용자·가정·지표가 함께 들어 있는 문제 카드를 만드는 방법을 다룹니다.

> 문제 문장은 기능 목록의 앞줄이 아니라, 이후 모든 요구사항과 우선순위를 묶어 주는 기준 문장입니다.

## 이 글에서 다룰 문제

- 왜 문제 문장이 흐리면 해결책도 같이 흔들릴까요?
- 기능 설명과 문제 정의는 어떻게 다를까요?
- 사용자, 가치, 가정, 측정 기준을 한 장에 담으려면 무엇을 적어야 할까요?
- 이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?
- 면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?

## 문제 정의가 프로젝트 품질을 결정하는 이유

문제 정의는 프로젝트 품질의 절반을 좌우합니다. 문제가 선명하면 어떤 요구사항을 넣어야 하는지, 어떤 기능을 빼야 하는지, 데모에서 무엇을 보여 줘야 하는지가 자연스럽게 정리됩니다. 반대로 문제 문장이 흐리면 새 기능 제안이 나올 때마다 다 중요해 보이고, 진행 상황도 계속 다시 정의됩니다.

### 실패 패턴: 기능 중심으로 시작하기

3주차. "충돌 검사 기능을 만들고, 시각화도 넣고, 대체 과목 추천까지 하면 어떨까요?" 팀이 흥분합니다. 기능이 늘어날수록 발표가 풍성해 보입니다.

5주차. 대체 과목 추천 로직이 예상보다 복잡합니다. 과목 데이터 구조가 일관되지 않습니다. 팀원 A가 "이 기능을 빼야 하지 않을까요?"라고 말하자, 팀원 B가 "그러면 발표에서 보여줄 게 없지 않아요?"라고 반박합니다.

두 사람 모두 다른 문제를 상정하고 있습니다. 팀원 A는 "충돌 여부 확인"이 핵심이라고 생각하고, 팀원 B는 "추천까지 해야 완성형"이라고 생각합니다. 둘 다 맞을 수도 있지만, 이 차이를 해소할 기준 문장이 없습니다.

### 성공 패턴: 문제 문장부터 고정하기

2주차. 팀이 문제 카드를 작성합니다. "복수전공 학생은 수강 신청 전날 여러 과목 시간대를 동시에 비교해야 할 때, 수기로 옮겨야 해서 30초 안에 충돌 여부를 확인하기 어렵다."

5주차. 대체 과목 추천 기능 논의가 다시 나옵니다. 팀원 B가 "이 기능이 문제 카드의 문제를 해결하나요?"라고 묻습니다. "대체 과목 추천은 충돌 여부 확인이 아니라 다음 단계입니다. 이번 학기 범위 밖으로 보존합시다." 논의가 5분 만에 끝납니다.

## 기능 설명과 문제 정의의 차이

| 구분 | 기능 설명 (잘못된 방식) | 문제 정의 (올바른 방식) |
| --- | --- | --- |
| 시간표 관련 | "시간표 충돌 검사 기능을 만든다" | "복수전공 학생이 수강 신청 직전 30초 안에 충돌 여부를 확인하기 어렵다" |
| 식당 관련 | "메뉴 추천 알고리즘을 구현한다" | "학식 식당 대기 시간이 예측 불가능해 점심을 먹지 못하고 돌아가는 학생이 있다" |
| 도서관 관련 | "좌석 예약 시스템을 만든다" | "도서관 빈 좌석이 있어도 학생들이 실시간으로 파악하기 어렵다" |

기능 설명은 "무엇을 만드는가"를 말합니다. 문제 정의는 "누가 왜 불편한가"를 말합니다. 이 차이가 이후 모든 의사결정의 질을 가릅니다.

기능 설명으로 시작하면 기능을 추가하거나 제거할 때 기준이 없어집니다. "이 기능을 넣어야 하나요?"라는 질문에 "그게 있으면 더 좋지 않아요?"라는 답만 나옵니다. 문제 문장이 있으면 "이 기능이 그 문제를 해결하나요?"라는 질문으로 바뀝니다.

## 문제 카드 — 최소 문서 구성

짧은 문제 카드 하나만 잘 써도 해결책 논의의 질이 크게 달라집니다.

```text
관찰: 수강 신청 직전에 시간표 충돌을 수동으로 계산하느라 시간이 오래 걸린다
핵심 사용자: 복수전공 학생, 신입생 (1학년과 3학년 이상 복수전공 학생 우선)
문제 문장: 수강 신청 전 30초 안에 충돌 여부를 확인하기 어렵다
핵심 가정 1: 시간표 데이터를 텍스트나 CSV로 쉽게 넣을 수 있다
핵심 가정 2: 사용자가 충돌 결과를 보고 대체 과목을 스스로 선택한다
성공 지표 1: 첫 사용자 3명 중 2명 이상이 30초 안에 충돌 여부를 확인한다
성공 지표 2: 설명 없이 핵심 흐름을 끝내는 비율이 70% 이상이다
```

### 문제 카드 작성 체크 포인트

- 문제 문장이 해결책 이름으로 시작하지 않는지 확인합니다. "충돌 검사 시스템"이 아니라 "충돌 여부 확인이 어렵다"로 시작해야 합니다.
- 핵심 사용자를 좁혀 쓰고 있는지 점검합니다. "대학생"이 아니라 "복수전공 3학년 이상"처럼 구체적이어야 합니다.
- 숨겨진 가정을 별도 항목으로 끌어올립니다. "CSV로 넣을 수 있다"는 가정을 문서 밖에 두면 구현 단계에서 갑자기 문제가 됩니다.
- 지표가 시간, 정확도, 완료율처럼 측정 가능한 값인지 봅니다.

## 5단계 문제 정의 실습

### 1단계 — 관찰 작성

관찰은 실제 상황이 바로 떠오르게 적습니다. "대학생이 불편하다"가 아니라 "수강 신청 당일 학생들이 메모장에 과목 코드를 손으로 적어 비교하는 장면을 목격했다"처럼 구체적 사실에 가까워야 합니다.

관찰을 확인하는 방법은 세 가지입니다.

- 직접 경험: 팀원 자신이 겪은 불편입니다.
- 인터뷰: 주변 5-10명에게 직접 질문합니다.
- 관찰: 실제 사용 장면을 보거나 기록을 확인합니다.

```text
[관찰 기록 예시]

관찰 일시: 2025-03-02 수강 신청 직전
관찰 장소: 공대 열람실
관찰 내용: 학생 6명 중 4명이 수강편람 PDF를 열어놓고 노트에 수기로 과목 시간을
           옮겨 적은 후, 종이에서 직접 충돌 여부를 확인하는 모습을 목격함.
           나머지 2명은 엑셀 스프레드시트를 이용함.
관찰자: 팀원 A, B
추가 확인: 팀원 C가 같은 날 인터뷰 5명 진행, 모두 수기 또는 엑셀 사용 확인.
```

### 2단계 — 사용자 좁히기

사용자를 좁히는 이유는 배제가 아니라 집중입니다. 모두를 사용자로 잡는 순간 맥락이 사라집니다. 첫 사용자는 팀이 실제로 연락할 수 있는 사람이어야 합니다.

```text
나쁜 예: 사용자 = 대학생
좋은 예: 사용자 = 우리 학교 복수전공 신청 예정인 2학년 학생
          (팀원 지인 중 5명 확인 가능, 연락처 보유)
```

사용자를 좁힐 때는 "이 사람들이 현재 어떻게 이 문제를 해결하고 있는가"라는 질문도 함께 답합니다. 현재 해결 방식이 "수기로 옮기기"라면 대안이 얼마나 편해야 사용자가 바꿀지 가늠할 수 있습니다.

```text
[사용자 프로필 카드]

이름(가명): 민수 (2학년, 전산학 + 경영 복수전공)
현재 방식: 수강편람 PDF + 노트에 수기 기록 + 손으로 비교
소요 시간: 30-60분 (과목 10-15개 비교 시)
불편 지점: "어떤 과목이 충돌하는지 한눈에 볼 수 없다"
전환 조건: "1-2분 안에 결과가 나오면 바로 쓸 것 같다"
```

### 3단계 — 문제 문장 작성

문제 문장은 "누가 언제 무엇을 왜 하기 어려운가"를 담습니다.

```text
형식: [사용자]는 [상황]에서 [행동]을 하기 [어려운 이유] 때문에 어렵다.

예시: 복수전공 신청 예정인 학생은 수강 신청 직전에
      여러 과목의 시간대를 동시에 비교하기 어렵다.
      현재는 종이에 수기로 옮겨야 하기 때문이다.
```

문제 문장을 작성한 후 팀 전체가 각자 읽고 동의하는지 확인합니다. 한 명이라도 "내가 생각한 문제는 이게 아닌데요"라고 말하면, 그 차이가 바로 이 단계에서 해소되어야 할 정렬 문제입니다.

### 4단계 — 가정 드러내기

가정을 숨기면 구현 단계에서 갑자기 복잡도가 커집니다. 입력 방식, 데이터 출처, 사용자 행동처럼 숨어 있는 전제를 문서에 올려야 합니다.

| 가정 항목 | 내용 | 검증 방법 | 실패 시 대안 |
| --- | --- | --- | --- |
| 입력 방식 | 사용자가 CSV나 텍스트로 시간표를 붙여넣을 수 있다 | 테스트 사용자 3명에게 직접 해보게 함 | 수동 입력 폼 제공 |
| 데이터 형식 | 학교 시간표 데이터가 일정한 형식을 가짐 | 실제 수강편람 확인 | 형식 정규화 단계 추가 |
| 사용자 행동 | 충돌 발견 후 대체 과목을 스스로 찾는다 | 인터뷰로 확인 | 대체 과목 추천 기능 추가 고려 |
| 접근 환경 | 웹 브라우저로 접근 가능하다 | 테스트 환경 확인 | 로컬 실행 버전 제공 |

가정을 문서화하면 두 가지 효과가 생깁니다. 첫째, 팀원이 서로 다른 가정을 가지고 있었다는 사실이 드러납니다. 둘째, 구현 중에 가정이 틀렸을 때 "이미 알고 있던 리스크였다"고 말하고 빠르게 대안으로 전환할 수 있습니다.

### 5단계 — 성공 지표 설정

지표는 잘 만들었는지 판단하는 최소 기준입니다. 숫자가 들어가야 데모와 테스트가 쉬워집니다.

```text
나쁜 지표: 사용자가 만족한다
좋은 지표: 첫 사용자가 30초 안에 충돌 여부를 확인한다

나쁜 지표: 빠르다
좋은 지표: 결과 계산이 1초 이내에 완료된다

나쁜 지표: 쓰기 편하다
좋은 지표: 설명 없이 핵심 흐름을 끝낸 비율이 70% 이상이다
```

지표 설정 후에는 "이 지표를 어떻게 측정할 것인가"도 함께 정합니다. 측정 방법이 없는 지표는 결국 "느낌"으로 평가하게 됩니다.

```python
# tests/test_performance.py
# 성공 지표 자동 검증 예시

import time
import pytest
from src.conflict_checker import check_conflicts, parse_schedule_text

SAMPLE_INPUT = """
CS101 월 09:00-11:00
MA201 월 10:00-12:00
ENG301 화 13:00-15:00
PHY101 수 09:00-11:00
""".strip()

def test_result_within_one_second():
    """성공 지표 2: 결과 계산이 1초 이내에 완료된다"""
    courses = parse_schedule_text(SAMPLE_INPUT)
    start = time.time()
    result = check_conflicts(courses)
    elapsed = time.time() - start

    assert elapsed < 1.0, f"계산 시간 초과: {elapsed:.2f}초"

def test_conflict_detected_correctly():
    """성공 지표 1의 전제: 충돌이 정확하게 감지된다"""
    courses = parse_schedule_text(SAMPLE_INPUT)
    conflicts = check_conflicts(courses)

    # CS101(월 9-11)과 MA201(월 10-12)은 충돌해야 함
    conflict_pairs = [(c.a.code, c.b.code) for c in conflicts]
    assert ("CS101", "MA201") in conflict_pairs or \
           ("MA201", "CS101") in conflict_pairs

def test_no_false_positive():
    """충돌 없는 과목 쌍에 대해 오탐이 없어야 함"""
    courses = parse_schedule_text(SAMPLE_INPUT)
    conflicts = check_conflicts(courses)

    conflict_pairs = set()
    for c in conflicts:
        conflict_pairs.add(frozenset([c.a.code, c.b.code]))

    # ENG301(화)과 PHY101(수)은 다른 요일이라 충돌 없음
    assert frozenset(["ENG301", "PHY101"]) not in conflict_pairs
```

## MVP 범위 설정 체크리스트

문제 정의가 끝났다고 해서 범위가 자동으로 정리되지는 않습니다. 문제 정의 문장을 기준으로 MVP 범위를 자르는 체크리스트를 통과시켜야 합니다.

| 점검 항목 | 예/아니오 | 근거 문장 |
| --- | --- | --- |
| 핵심 사용자가 한 문장으로 정의되어 있는가 | | |
| 핵심 흐름이 3~5단계 이내로 설명되는가 | | |
| 데모에서 재현 가능한 입력 데이터가 준비되는가 | | |
| 성공 지표가 시간/완료율 등 수치로 표현되는가 | | |
| 외부 의존성 실패 시 대체 경로가 있는가 | | |
| 이번 학기 범위 밖 항목이 문서화되어 있는가 | | |
| Must 기능이 전체 후보의 절반 이하인가 | | |
| 발표 리허설 기준으로 5분 내 시연 가능한가 | | |

체크리스트는 점수표가 아니라 경보 장치입니다. "아니오"가 3개 이상이면 구현을 멈추고 범위를 다시 잘라야 합니다.

### 범위 밖 항목 보존

"하지 않을 것"을 명시하는 것은 "포기"가 아니라 "의도적 제외"입니다. 이후 발표에서 "왜 이 기능을 넣지 않았는가"라는 질문에 답하는 근거가 됩니다.

```text
[비범위 항목 목록 v1.0]

항목 | 제외 이유 | 재검토 시점
수강 신청 사이트 자동 연동 | 외부 API 접근 불가, 인증 복잡도 높음 | 졸업 프로젝트 단계
대체 과목 자동 추천 | 과목 데이터 수집 범위 초과, 추천 품질 기준 불명확 | 다음 시즌
모바일 앱 지원 | 웹 기반으로도 핵심 가치 전달 가능 | 다음 버전
다른 학교 수강편람 지원 | 형식 다양성으로 파싱 복잡도 증가 | 검토 보류
```

## CI 파이프라인 — 문제 정의 연계형

문제 정의가 문서로 끝나면 실행력이 떨어집니다. PR 단계에서 문제 문장과 범위를 자동으로 검증하는 최소 파이프라인을 함께 설계합니다.

```yaml
# .github/workflows/ci.yml
name: capstone-ci
on:
  pull_request:
    branches: [main]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - name: 의존성 설치
        run: pip install -r requirements.txt
      - name: 단위 테스트 실행
        run: pytest -q tests/
      - name: 성능 지표 검증 (1초 이내)
        run: pytest -q tests/test_performance.py -v
      - name: 문제 범위 검사 스크립트
        run: python scripts/check_problem_scope.py
```

코드 리뷰 체크리스트에도 문제 정의와 연결된 항목을 포함합니다.

- 변경 내용이 문제 문장과 직접 연결되는지 확인합니다.
- 새 기능이 MVP 범위 안에 있는지 확인합니다.
- 입력/출력 예시가 데모 시나리오와 일치하는지 점검합니다.
- 실패 케이스 테스트가 최소 1건 이상 포함되어 있는지 확인합니다.
- 문서(README/결정 로그)가 함께 갱신되었는지 확인합니다.

### PR 설명 템플릿

```markdown
## 변경 요약
<!-- 이 PR이 해결하는 문제 카드의 어떤 부분에 해당하는지 명시 -->

문제 카드 연결:
- [ ] 이 변경은 문제 문장과 직접 연결됩니다
- [ ] 새 기능은 MVP 범위 안에 있습니다
- [ ] 비범위 항목을 구현하지 않았습니다

## 변경 내용
<!-- 무엇을 어떻게 변경했는지 -->

## 테스트 방법
<!-- 어떻게 확인했는지 -->

## 데모 시나리오 영향
<!-- 이 변경이 데모 흐름을 어떻게 바꾸는지 또는 바꾸지 않는지 -->
```

## 자주 하는 실수

| 실수 유형 | 구체적 상황 | 왜 문제인가 | 예방 방법 |
| --- | --- | --- | --- |
| 해결책을 문제로 적음 | "AI 추천 기능이 없어서 문제다" | 해결책이 바뀌면 문제 문장도 바뀌어야 함 | "사용자가 X를 하기 어렵다" 형식 강제 |
| 사용자를 "모두"로 설정 | "이 기능은 모든 학생에게 필요하다" | 누구를 먼저 테스트할지 결정 불가 | 최초 테스트 가능한 10명 이하로 좁힘 |
| 가정을 문서 밖에 둠 | "당연히 CSV 형식일 거야" | 구현 중 데이터 형식 불일치 발견 | 가정 항목을 문제 카드에 명시 |
| 지표가 감상형 | "사용자가 편리하게 느끼면 성공" | 데모 후 성공 여부 판단 불가 | 시간·완료율·정확도로 수치화 |
| 문제 재정의를 실패로 봄 | "문제 문장을 바꾸면 처음부터 다시 하는 것 같다" | 개선 기회를 놓침 | 재정의는 건강한 학습 과정으로 인식 |

## 문제 정의 버전 관리

문제 문장은 프로젝트 중간에 바뀔 수 있습니다. 바뀌는 것 자체는 문제가 아닙니다. 문제는 바뀐 이유를 기록하지 않는 것입니다.

```text
[문제 정의 변경 이력]

v1.0 (2025-03-05): 최초 작성
  "수강 신청 직전 충돌 여부를 수동으로 확인하기 어렵다"

v1.1 (2025-03-15): 사용자 범위 조정
  "복수전공 학생"으로 구체화.
  이유: 인터뷰 결과, 단일 전공 학생은 충돌 빈도 낮음.

v1.2 (2025-04-01): 성공 지표 수정
  30초 → 60초로 완화.
  이유: 실제 사용 테스트에서 30초가 현실적으로 어려움 확인.
  단, 핵심 문제 문장은 유지.
```

버전을 기록해 두면 "왜 처음 계획과 달라졌는가"라는 질문에 근거로 답할 수 있습니다.

## 처음 질문으로 돌아가기

- **왜 문제 문장이 흐리면 해결책도 같이 흔들릴까요?**
  문제 문장이 없으면 새 기능 제안이 나올 때마다 "이것도 중요하다"가 되기 때문입니다. 문제 문장이 있으면 "이 기능이 문제 문장을 해결하는가"라는 질문 하나로 포함 여부를 결정할 수 있습니다. 이 질문 하나가 수십 번의 회의 논쟁을 줄입니다.

- **기능 설명과 문제 정의는 어떻게 다를까요?**
  기능 설명은 "무엇을 만드는가"를 말하고, 문제 정의는 "누가 왜 불편한가"를 말합니다. "충돌 검사 기능을 만든다"는 기능 설명이고, "학생이 30초 안에 충돌 여부를 확인하기 어렵다"는 문제 정의입니다. 기능 설명으로 시작하면 왜 만드는지를 잃고, 문제 정의로 시작하면 무엇을 만들지가 자연스럽게 따라옵니다.

- **사용자, 가치, 가정, 측정 기준을 한 장에 담으려면 무엇을 적어야 할까요?**
  관찰 사실, 핵심 사용자(좁게), 문제 문장("~하기 어렵다" 형식), 숨겨진 가정(입력 방식, 데이터 형식, 사용자 행동), 성공 지표(시간 또는 완료율 수치)를 순서대로 적으면 됩니다. 항목 수가 7개 이하라도 이 순서를 지키면 팀원 간 전제 차이가 바로 드러납니다.

- **이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?**
  어떤 기능을 넣을지 뺄지 매번 토론해야 합니다. 발표 당일 무엇을 강조해야 할지 결정하지 못합니다. 회고에서 "왜 이걸 만들었는지"를 설명하기 어려워집니다. 문제 정의 단계 1시간이 이후 10-15시간의 비생산적인 논의를 막습니다.

- **면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?**
  문제를 사용자 관점에서 정의하는 능력입니다. "어떤 문제를 해결하려고 했는가"라는 질문에 사용자, 상황, 어려움, 지표를 포함한 답변을 할 수 있는지 봅니다. 기능 목록을 나열하는 답변은 이 역량을 보여주지 못합니다. 가정이 바뀌었을 때 어떻게 대응했는지도 함께 설명하면 더 좋습니다.

## 운영 체크리스트

- [ ] 문제를 한 문단 안에서 설명할 수 있습니다.
- [ ] 첫 사용자 집단이 구체적으로 적혀 있습니다.
- [ ] 가치가 변화 중심으로 서술되어 있습니다.
- [ ] 핵심 가정이 문서에 드러나 있습니다.
- [ ] 가정별 검증 방법과 실패 시 대안이 있습니다.
- [ ] 성공 지표에 숫자가 들어 있습니다.
- [ ] 성공 지표를 측정하는 방법이 정해져 있습니다.
- [ ] MVP 범위 체크리스트를 통과했습니다.
- [ ] 비범위 항목과 제외 이유가 문서화되어 있습니다.
- [ ] 문제 정의 버전 이력이 기록되어 있습니다.

## 정리와 다음 글

문제 정의는 기능 목록의 서문이 아니라 프로젝트의 기준점입니다. 사용자, 가정, 지표를 함께 적어 두면 요구사항과 MVP를 자를 때도 훨씬 단단한 판단이 가능합니다. 문제 정의 문서는 팀이 흔들릴 때마다 돌아오는 기준점이므로, 완성도보다 명확성에 집중해서 작성합니다. 다음 글에서는 이 기준을 실제 요구사항 문서로 바꾸겠습니다.
