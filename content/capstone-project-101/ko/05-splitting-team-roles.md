# Capstone Project 101 (5/10): 팀 역할 나누기

역할이 모호한 팀은 모두가 바빠 보이는데도 결정이 느립니다. 누가 최종 판단을 내리고 누가 백업하는지가 분명하지 않기 때문입니다.

캡스톤에서 역할 분담은 사람을 칸에 넣는 일이 아니라 병목을 줄이는 구조를 만드는 일입니다. 특히 짧은 일정에서는 주 책임자와 백업 구조가 없으면 일정 충격이 바로 전체 팀에 퍼집니다.

이 글은 Capstone Project 101 시리즈의 5번째 글입니다. 여기서는 주 책임자, 백업 담당자, 결정 권한을 나눠 팀 협업 속도를 높이는 기본 구조를 정리합니다.

> 역할 분담의 핵심은 사람을 분류하는 것이 아니라, 일이 막혔을 때 누가 결정하고 누가 이어받을지 미리 정하는 데 있습니다.

## 이 글에서 다룰 문제

- 역할이 겹치면 왜 결정이 느려질까요?
- 팀에서 자주 쓰는 핵심 역할은 무엇일까요?
- 주 책임자와 백업은 어떻게 정하는 편이 좋을까요?
- 이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?
- 면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?

## 역할이 모호할 때 실제로 일어나는 일

역할이 없는 팀에서 자주 보이는 패턴이 있습니다.

- API 스펙을 누가 먼저 정해야 하는지 결정을 미루다 백엔드와 프런트가 별도로 구현 후 충돌합니다.
- 요구사항 변경을 Slack에서 구두로 합의했는데, 팀원마다 다르게 기억합니다.
- 테스트 담당이 없어서 발표 전날 처음으로 통합 테스트를 시작합니다.
- 리드가 없어서 "누가 발표 자료를 만드는가"가 마지막 주에 결정됩니다.

역할이 분명한 팀은 이런 상황을 미리 설계로 예방합니다. 회의가 짧아지고, 변경이 생겨도 누구와 바로 조율해야 하는지 명확합니다.

**역할 모호함이 만드는 비용:**

| 상황 | 역할 모호할 때 | 역할 명확할 때 |
| --- | --- | --- |
| API 스펙 결정 | 2일 논의 후 타협 | 백엔드 담당이 30분 내 제안 |
| 요구사항 변경 | 팀원마다 기억이 다름 | 리드가 기록하고 즉시 공유 |
| 발표 자료 작성 | 마지막 주에 누가 할지 결정 | 4주차부터 팀 리드가 작성 시작 |
| 통합 테스트 | 발표 전날 처음 시도 | QA 담당이 2주차부터 체크리스트 작성 |

## 핵심 역할 5가지 정의

| 역할 | 핵심 책임 | 없을 때 나타나는 문제 |
| --- | --- | --- |
| 팀 리드 | 전체 흐름과 우선순위 조율, 일정 편차 관리 | 결정이 늦어지고 방향이 매번 흔들림 |
| 백엔드 담당 | 서버 로직, API 설계, 데이터 처리 | API 스펙이 프런트와 맞지 않음 |
| 프런트엔드 담당 | 사용자 화면, 상호작용, 데모 흐름 | 데모 장면이 불안정하고 UX가 어색함 |
| 데이터 담당 | 데이터 수집, 전처리, 분석 | 샘플 데이터가 발표 직전까지 준비 안 됨 |
| QA 담당 | 테스트 시나리오 작성, 결함 추적 | 발표 당일 치명적 버그 발견 |

4명 팀이라면 팀 리드가 QA를 겸하거나, 백엔드 담당이 데이터를 겸하는 형태로 조정합니다. 중요한 것은 각 역할이 누구에게 연결되어 있는지 문서로 명확히 하는 것입니다.

**팀 규모별 역할 조합 예시:**

| 팀 인원 | 권장 역할 조합 | 겸임 구조 |
| --- | --- | --- |
| 3명 | 리드+QA, 백엔드, 프런트+데이터 | 리드가 QA, 프런트가 데이터 담당 겸임 |
| 4명 | 리드, 백엔드+데이터, 프런트, QA | 백엔드가 데이터 담당 겸임 |
| 5명 | 리드, 백엔드, 프런트, 데이터, QA | 단독 역할 가능 |
| 6명 | 리드, 백엔드×2, 프런트, 데이터, QA | 백엔드를 두 명이 나눠 담당 |

## 역할 책임 매트릭스

작은 팀이라도 아래처럼 책임 문장을 적어 두면 회의 시간이 크게 줄어듭니다.

```text
업무             | 주 책임자        | 백업             | 결정 권한
요구사항 변경    | 팀 리드          | 프런트엔드 담당  | 리드 승인
API 설계         | 백엔드 담당      | 데이터 담당      | 백엔드 제안, 리드 승인
데모 시나리오    | QA 담당          | 팀 리드          | QA 제안, 팀 합의
배포 점검        | 백엔드 담당      | 프런트엔드 담당  | 배포 체크리스트 기준
발표 자료        | 팀 리드          | QA 담당          | 팀 전체 리뷰
```

### RACI 표 기반 책임 배정 예시

| 작업 | 책임자(R) | 승인자(A) | 협업자(C) | 공유 대상(I) |
| --- | --- | --- | --- | --- |
| 문제 정의 확정 | 팀 리드 | 지도교수 | 전원 | 전원 |
| API 명세 | 백엔드 담당 | 팀 리드 | 프런트엔드 담당 | 전원 |
| MVP 구현 | 개발 담당 | 팀 리드 | QA 담당 | 전원 |
| 테스트/검증 | QA 담당 | 팀 리드 | 개발 담당 | 전원 |
| 발표 자료 | 발표 담당 | 팀 리드 | 전원 | 지도교수 |

RACI는 복잡하게 늘리기보다 꼭 필요한 결정과 작업만 담는 편이 실전에 더 도움이 됩니다.

## 백업 구조 설계

백업 담당자를 미리 정해 두어야 결원이나 일정 충돌이 생겨도 작업이 멈추지 않습니다.

| 주 담당 | 백업 담당 | 이관 조건 |
| --- | --- | --- |
| 팀 리드 | 프런트엔드 담당 | 리드가 48시간 이상 응답 불가 시 |
| 백엔드 담당 | 데이터 담당 | 구현 블로커 24시간 해결 불가 시 |
| 프런트엔드 담당 | QA 담당 | 데모 화면 이슈 48시간 미해결 시 |
| QA 담당 | 팀 리드 | 발표 직전 주 테스트 완료 지연 시 |

백업은 "대신 하는 사람"이 아니라 "알고 있어야 하는 사람"입니다. 따라서 주 책임자는 주기적으로 백업 담당자에게 현재 상태를 공유해야 합니다.

**백업 담당자 온보딩 루틴:**

| 주기 | 공유 내용 | 방법 |
| --- | --- | --- |
| 매주 월요일 | 이번 주 작업 우선순위 | 스탠드업에서 1분 공유 |
| 기능 완료 시 | 구현 방식과 테스트 결과 | PR 코멘트에 요약 |
| 블로커 발생 시 | 문제와 시도한 방법 | 즉시 메시지로 공유 |

## 6주 일정과 역할 연계 계획

역할이 정해졌다면 다음 과제는 역할을 시간축에 배치하는 일입니다.

| 주차 | 목표 | 주 책임 역할 | 완료 기준 | 위험 신호 |
| --- | --- | --- | --- | --- |
| 1주차 | 문제 정의 및 요구사항 고정 | 팀 리드 | Must 스토리 승인 | 요구사항 변경 3건 이상 |
| 2주차 | 핵심 데이터/입력 경로 확보 | 백엔드, 데이터 | 샘플 입력 정상 처리 | 외부 데이터 접근 지연 |
| 3주차 | 핵심 흐름 구현 | 프런트엔드, 백엔드 | 입력→계산→결과 흐름 연결 | 통합 실패 반복 |
| 4주차 | 테스트와 결함 수정 | QA | Must 테스트 통과율 90% 이상 | 회귀 버그 증가 |
| 5주차 | 발표 데모 리허설 | 팀 전체 | 60초 데모 3회 연속 성공 | 데모 실패 2회 이상 |
| 6주차 | 발표/회고 문서 확정 | 팀 리드, QA | 발표 자료, 회고 액션 로그 완료 | 문서 누락 |

## 역할 전환 시나리오: 실제 충돌 예시

**시나리오 A: 백엔드 담당이 시험 기간과 겹쳤을 때**

3주차에 백엔드 담당이 전공 시험으로 2일간 응답이 불가능해졌습니다. 백업 구조가 없었다면 팀 전체의 통합 작업이 멈춥니다.

백업 구조가 있다면: 데이터 담당이 이관 조건을 확인하고, 백엔드 담당이 2주차 말에 공유한 API 명세와 현재 코드 상태를 바탕으로 간단한 API 목업을 만들어 프런트엔드가 병렬로 작업을 이어 갑니다. 백엔드 담당이 돌아왔을 때는 목업을 실제 구현으로 교체하면 됩니다.

**시나리오 B: QA 담당이 합류가 늦었을 때**

첫 2주는 팀 리드가 QA를 겸하다가 3주차부터 새 팀원이 QA 역할을 맡았습니다. 역할 매핑 문서가 있어서 인수인계가 30분 미팅 하나로 끝났습니다. 테스트 시나리오 초안이 이미 문서에 있었기 때문입니다.

## 협업 브랜치 전략

역할과 브랜치 규칙을 함께 고정하면 회의 시간이 줄고 결정 속도가 빨라집니다.

- 기능 단위로 `feat/<owner>/<topic>` 브랜치를 생성합니다.
- 하루 1회 이상 원격 저장소에 푸시해 변경 이력을 공개합니다.
- PR 본문에 목적, 변경, 검증 3개 항목을 고정합니다.
- 리뷰 체크리스트를 통과하지 못하면 머지를 보류합니다.

```text
PR 템플릿
- 목적: 어떤 문제를 해결하는 변경인가
- 변경: 핵심 수정 3가지
- 검증: 실행한 테스트와 결과
```

```bash
# 백엔드 담당의 API 구현 브랜치 예시
git checkout -b feat/backend/conflict-calculator
git add src/calculator.py tests/test_calculator.py
git commit -m "feat: add time slot conflict detection logic"
git push -u origin feat/backend/conflict-calculator
```

## 역할 검토 주기

역할은 한 번 정했다고 끝나지 않습니다. 진행 중 바뀌는 현실을 반영할 주기가 필요합니다.

- **주간 점검 (10분)**: 각 역할 담당자가 지난 주 완료 항목과 이번 주 계획을 한 줄씩 공유합니다.
- **역할 변경 기록**: 역할이 바뀌면 날짜와 이유를 문서에 남깁니다.
- **블로커 즉시 공유**: 24시간 이상 막힌 항목은 다음 스탠드업을 기다리지 않고 즉시 공유합니다.

**역할 변경 기록 예시:**

```text
날짜: 2026-05-14
변경: QA 담당 → 팀 리드 (임시 겸임)
이유: QA 담당 병원 방문으로 1주일 불참
복귀 예정: 2026-05-21
이관 사항: 테스트 시나리오 문서 공유 완료
```

## 면접에서 역할 질문에 답하는 방법

캡스톤 면접에서 역할 관련 질문이 자주 나옵니다. 좋은 답변과 약한 답변의 차이를 알아 두면 좋습니다.

| 면접 질문 | 약한 답변 | 강한 답변 |
| --- | --- | --- |
| "팀에서 어떤 역할을 맡았나요?" | "백엔드를 주로 했습니다" | "백엔드 담당으로 API 설계를 주도했고, 데이터 담당의 백업을 겸했습니다. 3주차에 데이터 접근 이슈가 생겼을 때 이관 조건에 따라 임시로 담당을 넘겨받아 해결했습니다" |
| "팀 갈등이 있었을 때 어떻게 해결했나요?" | "잘 협력했습니다" | "API 명세 방향에 대한 의견 차이가 있었습니다. 백엔드와 프런트 담당의 요구사항을 문서로 정리한 뒤 트레이드오프를 표로 만들어 팀 리드에게 결정 권한을 넘겼습니다. 기록이 있어서 결정 이유를 나중에도 설명할 수 있었습니다" |

## 자주 하는 실수

| 실수 유형 | 구체적 상황 | 왜 문제인가 | 예방 방법 |
| --- | --- | --- | --- |
| 공동 책임자 지정 | "API는 백엔드와 프런트가 같이 맡는다" | 실제로는 둘 다 상대방이 결정하길 기다림 | 한 사람을 주 책임자로 명시 |
| 백업 없음 | "팀 리드가 모든 결정을 내린다" | 리드가 블록되면 전체가 멈춤 | 모든 역할에 백업을 1명 이상 지정 |
| QA를 마지막에만 투입 | "구현이 끝나면 테스트하자" | 발표 전날 치명적 버그 발견 | QA를 2주차부터 체크리스트에 참여 |
| 역할 변경 미기록 | "구두로 역할 바꿨다" | 나중에 "누가 그 결정을 했는가" 분쟁 | 변경 로그에 날짜와 이유 기록 |
| 리드가 모든 것을 끌어안음 | 팀 리드가 개발+관리+발표를 모두 담당 | 한 사람에게 과부하, 결정 지연 | 명확한 위임과 결정 권한 분리 |
| 백업에게 상태를 공유 안 함 | 주 담당만 현재 상황을 앎 | 이관 시 처음부터 시작해야 함 | 주간 스탠드업에서 백업에게 1분 브리핑 |

## 처음 질문으로 돌아가기

- **역할이 겹치면 왜 결정이 느려질까요?**
  - "A가 결정하겠지"라고 B도 생각하고, "B가 먼저 결정해야 한다"고 A도 생각하는 상태가 됩니다. 누가 먼저 결정해야 하는지 불분명하기 때문에 결정이 미루어지고, 결국 마감 직전에 급하게 처리됩니다.

- **팀에서 자주 쓰는 핵심 역할은 무엇일까요?**
  - 팀 리드(조율), 백엔드 담당(서버/API), 프런트엔드 담당(화면/UX), 데이터 담당(데이터 처리), QA 담당(검증) 다섯 가지입니다. 4명 이하 팀에서는 겸임이 불가피하지만 각 역할이 누구에게 속하는지는 문서로 명시해야 합니다.

- **주 책임자와 백업은 어떻게 정하는 편이 좋을까요?**
  - 주 책임자는 해당 영역에서 가장 경험이 많은 사람 또는 가장 관심 있는 사람으로 정합니다. 백업은 해당 영역을 두 번째로 잘 아는 사람으로 정합니다. 중요한 것은 백업이 실제로 상황을 파악하고 있어야 한다는 점입니다. 주 책임자가 주기적으로 백업에게 현재 상태를 공유해야 합니다.

- **이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?**
  - 발표 2주 전에 "누가 발표 자료를 만드는가", "누가 최종 데모를 조작하는가", "QA 결과를 누가 리뷰하는가"가 결정되지 않은 상태가 됩니다. 그 시점에 역할을 나누면 학습 없이 분업만 하게 됩니다.

- **면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?**
  - 팀에서 자신의 역할과 기여를 명확하게 설명하는 능력입니다. "저는 백엔드 담당으로서 충돌 계산 API를 설계했고, 주간 리뷰에서 QA 담당과 테스트 기준을 맞췄습니다"처럼 구체적으로 말할 수 있어야 합니다.

## 운영 체크리스트

- [ ] 주 역할 매핑이 문서에 있습니다.
- [ ] 모든 역할에 백업 담당자가 지정되어 있습니다.
- [ ] RACI 표가 있습니다.
- [ ] 주간 역할 검토 주기가 있습니다.
- [ ] 브랜치 네이밍 규칙이 정해져 있습니다.
- [ ] PR 템플릿이 저장소에 설정되어 있습니다.
- [ ] 역할 변경 기록 양식이 있습니다.
- [ ] 백업 담당자에게 현재 상태를 공유하는 주기가 있습니다.

## 정리와 다음 글

팀 역할 분담은 업무를 예쁘게 나누는 일이 아니라 병목을 줄이는 설계입니다. 주 책임자, 백업, 결정 권한이 분명해야 캡스톤 일정 충격을 견딜 수 있습니다. 백업 구조는 역할이 바뀌는 순간뿐 아니라 평상시에도 팀 전체의 문제 인식 수준을 높이는 효과가 있습니다. 다음 글에서는 이 구조를 바탕으로 MVP 범위를 어떻게 자를지 다룹니다.
