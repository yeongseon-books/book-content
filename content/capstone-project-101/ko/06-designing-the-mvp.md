# Capstone Project 101 (6/10): MVP 설계

많은 팀이 MVP를 '기능을 조금만 만드는 것'으로 이해합니다. 그래서 모든 기능을 반쯤 만들고도 핵심 흐름은 끝내지 못하는 일이 자주 생깁니다.

MVP는 작은 완성품이 아니라 가장 중요한 가설을 가장 빨리 검증하는 설계입니다. 그래서 무엇을 넣을지보다 무엇을 의도적으로 빼는지가 더 중요할 때가 많습니다.

이 글은 Capstone Project 101 시리즈의 6번째 글입니다. 여기서는 핵심 사용자 흐름, 범위 제외 목록, 데모 기준, 피드백 수집을 한 세트로 묶는 MVP 설계 방식을 다룹니다.

> MVP의 목적은 기능 수를 줄이는 것이 아니라, 핵심 사용자 흐름 하나를 끝까지 연결해 팀이 실제로 배울 수 있는 상태를 만드는 데 있습니다.

## 이 글에서 다룰 문제

- MVP는 왜 작은 완성품보다 학습 도구에 가깝다고 할까요?
- 핵심 흐름 하나를 고른다는 말은 무엇을 남기고 무엇을 버린다는 뜻일까요?
- 범위 밖 항목을 문서로 적는 일은 왜 중요할까요?
- 이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?
- 면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?

## MVP를 잘못 이해한 팀과 잘 이해한 팀

**MVP를 "기능 축소"로 이해한 팀:**

- 시간표 입력: 50% 구현
- 충돌 계산: 30% 구현
- 결과 화면: 20% 구현
- 공유 기능: 10% 구현
- 발표 당일: 어떤 기능도 완전히 동작하지 않음

**MVP를 "핵심 흐름 완결"로 이해한 팀:**

- 시간표 입력(텍스트): 100% 구현
- 충돌 계산: 100% 구현
- 결과 화면(기본형): 100% 구현
- 공유 기능: 범위 제외로 명시
- 발표 당일: 핵심 흐름이 60초 안에 완전히 동작

차이는 기술 실력이 아니라 무엇을 의도적으로 빼는지를 결정했느냐입니다.

## MVP 오해 유형별 증상 비교

팀이 MVP를 잘못 이해했을 때 나타나는 패턴은 크게 세 가지입니다.

| 오해 유형 | 증상 | 결과 | 올바른 이해 |
| --- | --- | --- | --- |
| 기능 축소로 이해 | 모든 기능을 30~50%씩 구현 | 발표 당일 어떤 흐름도 동작 안 함 | 핵심 흐름 1개를 100% 완성 |
| 프로토타입과 혼동 | "일단 만들어 보고 봄" | 완료 기준이 없어 범위가 계속 늘어남 | 사전에 성공 기준을 숫자로 정의 |
| 알파 버전으로 이해 | 버그는 있지만 기능은 전부 있는 상태 | 구현 범위가 처음 계획의 3배로 확장 | 범위 밖 항목을 명시적으로 제외 |

이 세 유형 모두 공통 원인이 있습니다. 범위 제외 목록이 없다는 점입니다. 제외 항목이 없으면 추가 요청이 들어올 때마다 새로운 협상을 해야 합니다.

## MVP 계약서 — 핵심 문서

MVP를 지킬 때 가장 도움이 되는 문서는 짧은 계약서입니다. 팀이 이번 학기에 지킬 경계를 아래처럼 문장으로 적습니다.

```text
핵심 흐름: 시간표 입력 → 충돌 계산 → 결과 화면 표시
범위 밖: 결제, 관리자 대시보드, 다국어, 추천 알고리즘 고도화,
        소셜 공유, 회원 가입/로그인
데모 기준: 샘플 데이터로 60초 안에 흐름 전체를 보여 준다
성공 기준: 첫 사용자 3명 중 2명 이상이 설명 없이 결과 화면에 도달한다
피드백 질문:
  Q1. 이 결과가 이해하기 쉬웠는가? (1-5)
  Q2. 속도가 충분히 빨랐는가? (1-5)
  Q3. 실제 수강 신청에서 써볼 의향이 있는가? (예/아니오)
```

### MVP 계약서 체크 포인트

- 핵심 흐름이 한 문장으로 읽히는지 확인합니다. 두 줄이 넘으면 아직 범위가 큽니다.
- 범위 밖 항목이 충분히 많은지 봅니다. 범위 밖 목록이 핵심 흐름보다 짧으면 아직 덜 잘라낸 것입니다.
- 데모 기준이 실제 발표 환경에서 재현 가능한지 점검합니다. "인터넷이 필요한" 의존성은 발표장에서 실패 위험이 됩니다.
- 피드백 질문이 다음 결정으로 이어질 수 있는 수준인지 살핍니다.

## 기능 우선순위 매트릭스

어떤 기능이 MVP에 들어가고 어떤 기능이 제외될지를 아래 매트릭스로 결정합니다.

| 기능 | 사용자 가치 | 구현 난도 | 데모 기여도 | 분류 |
| --- | --- | --- | --- | --- |
| 시간표 텍스트 입력 | 높음 | 낮음 | 높음 | Must |
| 충돌 계산 | 매우 높음 | 중간 | 매우 높음 | Must |
| 결과 화면 (기본형) | 높음 | 중간 | 높음 | Must |
| 결과 시각화 (차트) | 중간 | 높음 | 중간 | Should |
| 소셜 공유 | 중간 | 낮음 | 낮음 | Could |
| 로그인/회원 관리 | 낮음 | 높음 | 낮음 | Won't |
| 추천 알고리즘 고도화 | 낮음 | 매우 높음 | 낮음 | Won't |

이 매트릭스를 채울 때 "데모 기여도"가 핵심 기준입니다. 발표에서 직접 보여줄 수 없는 기능은 Must가 될 수 없습니다.

### 팀 규모별 MVP 범위 조정 기준

팀 규모에 따라 MVP에 담을 수 있는 적정 범위가 달라집니다.

| 팀 규모 | 권장 Must 기능 수 | 핵심 흐름 길이 | 주의할 점 |
| --- | --- | --- | --- |
| 2명 | 2-3개 | 2단계 이내 | 한 명이 빠지면 전체가 멈추지 않도록 백업 담당 지정 |
| 3-4명 | 3-4개 | 3단계 이내 | 프런트·백엔드 통합 충돌을 대비해 인터페이스 먼저 고정 |
| 5-6명 | 4-5개 | 3-4단계 이내 | 기능이 늘어날수록 통합 테스트 일정을 별도로 확보 |

2명 팀이 기능 5개를 Must로 잡으면 발표 주에 코드 빚이 쌓이고 디버깅에 모든 시간을 씁니다. 팀 크기를 먼저 보고 범위를 조정해야 합니다.

## 5단계 MVP 설계 프로세스

### 1단계 — 핵심 흐름 선정

핵심 흐름은 사용자가 가장 중요한 가치를 얻는 최단 경로입니다. 한 문장으로 적어야 합니다.

```text
나쁜 예: 사용자가 로그인 후 시간표를 입력하고 충돌을 확인하고 결과를 저장하고 공유한다
좋은 예: 시간표를 붙여넣고 충돌 여부를 확인한다
```

한 줄로 안 적히면 아직 너무 큽니다.

### 2단계 — 제외 목록 작성

범위 밖 항목은 소극적인 문서가 아니라, MVP를 지키는 가장 강한 장치입니다. 빼 두어야 핵심이 살아납니다.

```text
제외 항목:
- 로그인/회원 가입 (구현 비용 대비 데모 가치 낮음)
- CSV 파일 업로드 (텍스트 입력으로 대체)
- 결과 이메일 발송 (이메일 서버 설정 복잡도)
- 모바일 앱 (웹으로 충분히 데모 가능)
- 데이터베이스 영구 저장 (세션 내 처리로 대체)
```

### 3단계 — 데모 시나리오 작성

데모 순서를 먼저 적어 두면 구현 우선순위가 자연스럽게 정렬됩니다.

```text
장면 1 (20초): 문제 상황 소개 — "시간표를 손으로 비교하는 불편함"
장면 2 (20초): 시간표 텍스트 붙여넣기
장면 3 (20초): 검사 버튼 클릭 및 결과 확인
총 60초 시연, 네트워크 오류 대비 스크린샷 3장 준비
```

데모 장면이 세 개를 넘으면 발표 중 실패 가능성이 높아집니다.

### 4단계 — 성공 기준 설정

성공 기준은 감상을 숫자로 바꾸는 작업입니다.

```text
사용자 성공: 첫 사용자 3명 중 2명 이상이 설명 없이 결과 화면에 도달
속도 기준: 결과 계산 1초 이내
오류 기준: 데모 시연 중 에러 0건
```

### 5단계 — 피드백 폼 준비

피드백 항목이 없으면 발표는 박수로 끝나고 학습은 남지 않습니다. MVP는 결과물인 동시에 실험이기도 합니다.

```text
피드백 질문 3가지:
1. 충돌 결과를 이해하기 쉬웠나요? (1-5)
2. 응답 속도에 만족했나요? (1-5)
3. 실제 수강 신청에 앞서 사용해볼 의향이 있나요? (예/아니오)
```

## MVP 범위 조정 의사결정 흐름

MVP를 만들다 보면 중간에 새로운 기능 요청이 들어옵니다. 이때 아무 기준 없이 수락하거나 거절하면 팀 내 갈등이 생기기 쉽습니다. 아래 흐름으로 판단하면 설명 가능한 결정을 빠르게 내릴 수 있습니다.

```text
새 기능 요청이 들어왔을 때:

질문 1: 이 기능이 없으면 핵심 흐름이 동작하지 않는가?
  ├─ 예 → Must로 추가 (단, 기존 Must 중 하나를 Should로 내려야 함)
  └─ 아니오 → 질문 2로

질문 2: 이 기능이 데모에서 직접 보여줄 수 있는가?
  ├─ 예 → Should로 분류 (시간 남으면 구현)
  └─ 아니오 → Won't로 분류 (제외 목록에 추가)

최종 확인: 이 결정을 제외 목록 문서에 날짜와 이유를 적어 두었는가?
```

이 흐름을 사용하면 "왜 이 기능을 넣지 않았는가"를 나중에 면접에서도 명확히 설명할 수 있습니다.

## 기술 설계 문서 — ADR 예시

MVP 범위를 정한 뒤에는 핵심 기술 결정을 ADR로 남깁니다.

```text
ADR-001: 충돌 계산을 서버 측에서 수행한다

상태: Accepted
날짜: 2026-05-21

문맥:
- 프런트와 백엔드 모두 계산 로직을 넣으면 불일치 위험이 커진다
- 발표 데모에서 일관성이 핵심이다

결정:
- 충돌 계산은 서버 단일 모듈에서 수행한다
- 프런트는 입력 수집과 결과 표시만 담당한다

대안:
1) 클라이언트 계산: 구현 빠르나 규칙 불일치 위험
2) 서버 계산: API 왕복 필요하나 규칙 일원화 가능

결과:
- 테스트 범위를 서버 테스트로 집중 가능
- API 지연 모니터링 기준 추가 필요
```

## MVP 수용 기준표

MVP 설계의 핵심은 "완료 판정 기준"입니다. 완료 기준이 없으면 구현이 끝났는지 판단할 수 없습니다.

| 기능 | 완료 조건 | 실패 조건 | 검증 방법 |
| --- | --- | --- | --- |
| 시간표 입력 | 샘플 5건 정상 처리 | 필수 필드 누락 시 오작동 | 단위 테스트 + 수동 시연 |
| 충돌 계산 | 충돌 탐지 정확도 100% | 충돌 누락 1건 이상 | 테스트 데이터셋 검증 |
| 결과 화면 | 핵심 정보 1스크롤 내 표시 | 핵심 정보 누락 | 체크리스트 검토 |
| 응답 속도 | 평균 1초 이내 | 2초 초과 사례 발생 | 반복 테스트 5회 평균 |

## 실제 MVP 설계 시나리오: 6개월 후 돌아보기

### 시나리오 A — 범위 제외 목록을 철저히 지킨 팀

3주차에 지도교수가 "실시간 다중 사용자 비교 기능도 있으면 좋겠다"고 제안했습니다. 팀은 MVP 계약서의 제외 목록을 보여 주며 "로그인/회원 관리가 전제로 필요한 기능이고, 현재 Won't로 분류된 항목입니다. 다음 학기 확장 주제로 남겨 두겠습니다"라고 답했습니다.

6개월 후: 발표는 60초 데모가 3회 연속 성공했고, 사용자 3명 중 2명이 설명 없이 결과 화면에 도달했습니다. 지도교수는 "범위를 명확히 관리한 것이 인상적이었다"고 평가했습니다. 팀원 중 한 명이 이 경험을 이직 면접에서 "우선순위 조정 경험"으로 이야기했고 좋은 평가를 받았습니다.

### 시나리오 B — 중간에 기능 추가를 수락한 팀

4주차에 팀원 한 명이 "소셜 공유는 2시간이면 될 것 같다"며 추가를 제안했습니다. 팀이 수락했고, 공유 기능은 실제로 3일이 걸렸습니다. 5주차에 통합 테스트에서 공유 URL 생성 로직과 결과 화면 렌더링 사이에 충돌이 발생했습니다.

6개월 후: 발표 전날까지 디버깅이 이어졌고, 데모는 가까스로 성공했습니다. 팀은 "소셜 공유를 넣은 결정이 가장 아쉬웠다"고 회고했습니다.

두 시나리오의 차이는 초기에 제외 목록을 얼마나 강하게 지켰는지에 있습니다.

## 자주 하는 실수

| 실수 유형 | 구체적 상황 | 왜 문제인가 | 예방 방법 |
| --- | --- | --- | --- |
| 기능 개수로 진행률 계산 | "기능 8개 중 4개 완료" | 핵심 흐름이 연결되지 않을 수 있음 | "핵심 흐름이 동작하는가"로 진행률 측정 |
| 처음부터 모든 예외 처리 | "모든 입력 형식을 다 지원해야" | 구현이 복잡해지고 일정이 밀림 | Happy path만 먼저 완성 |
| 데모 시나리오 없이 구현 | "만들다 보면 보여줄 것이 생긴다" | 발표 당일 데모 순서를 모름 | 구현 전에 데모 각본 먼저 작성 |
| 피드백 항목 없음 | "발표 끝나면 다 끝이다" | 무엇을 배웠는지 정리할 수 없음 | 피드백 질문 3개를 미리 준비 |
| 범위 제외 목록이 빈약 | 제외 항목이 2개 이하 | 구현 중 범위 확장 요청을 막기 어려움 | 제외 항목 최소 5개 이상 명시 |
| 성공 기준이 감상 수준 | "잘 되면 성공이다" | 발표 후 무엇을 배웠는지 알 수 없음 | 사전에 수치 기준을 명시 |

## 면접에서 MVP 설계 경험을 설명하는 방법

MVP 관련 면접 질문은 보통 "왜 특정 기능을 제외했는가"와 "범위를 어떻게 결정했는가" 형태로 나옵니다.

| 질문 | 약한 답변 | 강한 답변 |
| --- | --- | --- |
| 기능을 어떻게 우선순위 정했나요? | "중요한 것부터 했습니다." | "데모 기여도와 구현 난도로 매트릭스를 만들어 Must/Should/Won't로 분류했고, 제외 목록을 명시해 변경 요청에 대응했습니다." |
| 왜 이 기능을 넣지 않았나요? | "시간이 없어서요." | "로그인 기능은 데모에서 직접 보여줄 필요가 없었고, 구현 비용이 높아 Won't로 분류했습니다. 제외 이유를 문서에 남겨 팀 합의를 만들었습니다." |
| 발표에서 가장 잘된 점은? | "팀워크가 좋았습니다." | "핵심 흐름을 60초 안에 완전히 보여주는 데모를 3회 연속 성공했고, 피드백 질문 3개를 통해 다음 개선 방향을 도출했습니다." |

## 처음 질문으로 돌아가기

- **MVP는 왜 작은 완성품보다 학습 도구에 가깝다고 할까요?**
  - MVP의 목적은 핵심 가설이 맞는지 빠르게 확인하는 데 있습니다. "사용자가 설명 없이 충돌을 확인할 수 있는가"라는 가설을 검증하는 것이 목적이고, 그 결과로 무엇을 배웠는지가 다음 단계를 결정합니다.

- **핵심 흐름 하나를 고른다는 말은 무엇을 남기고 무엇을 버린다는 뜻일까요?**
  - "사용자가 처음 들어와서 가장 중요한 가치를 얻는 최단 경로"만 남기고 나머지는 전부 제외 목록에 넣는다는 뜻입니다. 수강 충돌 검사기에서는 "텍스트 입력 → 계산 → 결과 표시"만 남기고 공유, 저장, 추천은 제외합니다.

- **범위 밖 항목을 문서로 적는 일은 왜 중요할까요?**
  - 팀원이나 지도교수가 "이 기능도 넣으면 좋겠다"고 제안할 때 "이미 제외로 결정한 항목입니다"라고 근거 있게 답할 수 있기 때문입니다. 제외 목록이 없으면 매번 새로운 협상을 해야 합니다.

- **이 단계를 건너뛰면 프로젝트 후반에 어떤 문제가 발생할까요?**
  - 5주차에도 "이 기능을 넣어야 하는가"를 논의합니다. 발표 2주 전에 핵심 흐름이 연결되지 않은 채 부가 기능만 여러 개 반쯤 구현된 상태가 됩니다.

- **면접관이 이 부분에서 주로 확인하려는 역량은 무엇일까요?**
  - 우선순위 조정과 범위 컷팅 능력입니다. "왜 이 기능을 제외했는가"를 "데모 기여도 대비 구현 난도가 높아서"처럼 근거 있게 설명할 수 있으면 좋은 평가를 받습니다.

## 운영 체크리스트

- [ ] 핵심 흐름이 한 문장으로 정의되어 있습니다.
- [ ] 범위 밖 항목 목록이 5개 이상 있습니다.
- [ ] 데모 시나리오가 3장면 이내로 작성되어 있습니다.
- [ ] 성공 기준에 수치가 포함되어 있습니다.
- [ ] 피드백 질문 3개가 준비되어 있습니다.
- [ ] MVP 수용 기준표가 있습니다.
- [ ] 제외 항목에 제외 이유가 적혀 있습니다.
- [ ] 팀 규모에 맞는 Must 기능 수를 조정했습니다.

## 정리와 다음 글

MVP는 작은 제품이 아니라 작은 실험입니다. 핵심 흐름, 범위 제외 목록, 데모 기준, 피드백 질문을 함께 적어 두면 학기 중간의 흔들림 속에서도 무엇을 지켜야 하는지 선명해집니다. 다음 글에서는 이 MVP를 어떤 기술 스택으로 구현할지 다룹니다.
