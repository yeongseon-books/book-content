# 바이브코딩을 위한 벡터 검색 (5/6): 청크 전략

이 글은 바이브코딩을 위한 벡터 검색 시리즈의 5번째 글입니다.

임베딩 모델에는 하드 토큰 한도가 있습니다. `all-MiniLM-L6-v2`는 최대 256 서브워드 토큰만 처리합니다. PDF 한 페이지도 이 한계를 쉽게 넘깁니다. 긴 문서를 한 번에 넣으면 경계 뒤의 내용이 잘리거나 너무 많은 정보가 하나의 벡터에 압축되어 검색 정밀도가 떨어집니다. 청킹은 긴 문서를 임베딩 가능한 크기의 조각으로 나누는 작업이며, 어떻게 나누느냐가 검색 품질에 직접 영향을 줍니다. 청크가 너무 작으면 문맥을 잃고, 너무 크면 서로 무관한 내용이 섞입니다.

바이브코딩에서 이 개념이 중요한 이유는 단순합니다. AI에게 문서 분할 코드를 요청할 때 chunk_size, overlap, 메타데이터 보존을 명시하지 않으면, 모델 토큰 한도를 고려하지 않은 기본값으로 동작하는 코드가 생성되기 때문입니다.

> 청킹은 전처리 부가 작업이 아니라, 검색 시스템이 어떤 문맥 단위를 기억할지 결정하는 설계 단계입니다.

---

## 이 글에서 다룰 문제

- 긴 문서를 그대로 임베딩하지 않고 왜 청크로 나눠야 할까요?
- chunk_size와 overlap은 검색 품질과 비용 사이에서 어떤 균형을 만들까요?
- 청크에 메타데이터를 붙이지 않으면 답변 경로에서 무엇이 막힐까요?
- 자주 하는 실수와 그 해결책은 무엇일까요?
- 이 개념을 실무에 적용하는 방법은 무엇일까요?

청크 전략을 이해하면 AI에게 "chunk_size=256, overlap=32, 소스 메타데이터 포함으로 긴 문서를 분할하고 각 청크의 토큰 수를 검증하는 코드"를 정확하게 요청할 수 있습니다. 이것이 바이브코딩 시대에 이 개념을 배우는 이유입니다.

## Before / After

**Before — AI에게 컨텍스트 없이 질문:**

```
Q: "긴 문서를 검색용 청크로 나누는 코드 작성해줘"
→ chunk_size 기본값, 토큰 한도 무시
→ overlap 없어 경계 문맥 손실
→ 메타데이터 없음
```

**After — 개념을 이해하고 구체적으로 질문:**

```
Q: "all-MiniLM-L6-v2의 토큰 한도(256)를 고려해
    chunk_size=200, overlap=40으로 문서를 분할해줘.
    각 청크에 source 파일명과 chunk_index를 메타데이터로 추가해줘.
    분할 후 각 청크의 실제 토큰 수를 출력해 한도 내에 있는지 확인해줘"
→ 모델 한도 안에 드는 청크
→ 추적 가능한 출처 메타데이터
```

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| 토큰 한도 없이 chunk_size만 설정 | 문자 수와 토큰 수가 다름 | 모델 max_seq_length 확인 후 설정 |
| overlap=0 사용 | 경계에 걸친 정보 검색 불가 | 10~20% overlap으로 경계 문맥 보존 |
| 메타데이터 없이 청킹 | 답변 출처 추적 불가 | source, chunk_index를 각 청크에 포함 |
| 너무 작은 청크 | 문맥 없는 조각만 생성 | 최소 100토큰 이상 유지 |
| 단락 경계 무시하고 고정 길이 분할 | 문장 중간에서 잘림 | RecursiveCharacterTextSplitter로 자연 경계 우선 |

## AI 협업 팁

청크 전략 관련 효과적인 AI 프롬프트 패턴:

1. **토큰 기반 분할 요청**: "all-MiniLM-L6-v2 토크나이저로 실제 토큰 수를 계산해 chunk_size=200 이하가 되도록 분할하는 코드 작성해줘"
2. **청크 품질 검증 요청**: "분할 후 청크별 토큰 수 분포(min, max, mean)와 너무 짧은 청크(50토큰 미만) 수를 출력하는 검증 코드 작성해줘"
3. **메타데이터 포함 분할 요청**: "각 청크에 source 파일명, chunk_index, 원본 문서 총 청크 수를 메타데이터로 포함하는 분할 함수 작성해줘"

예시 프롬프트:
> "긴 텍스트를 RecursiveCharacterTextSplitter(chunk_size=256, chunk_overlap=32)로 분할해줘. 각 청크에 source='doc.txt'와 chunk_index를 메타데이터로 추가. 분할 후 청크 수, 평균 길이, 최대/최소 길이를 출력해줘."

## 운영 체크리스트

- [ ] 각 청크에 source와 위치 메타데이터가 포함됐는가?
- [ ] 분할 후 청크 품질(길이 분포, 너무 짧은 청크)을 검증했는가?

## 처음 질문으로 돌아가기

청크 전략을 배운 지금, AI에게 이 주제로 더 정확한 질문을 할 수 있게 되었습니다. 토큰 한도와 메타데이터를 명시한 사람과 그렇지 않은 사람이 AI에게 받는 청킹 코드의 품질은 크게 다릅니다.
