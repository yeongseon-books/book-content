# 바이브코딩을 위한 벡터 검색 (6/6): 벡터 검색 파이프라인

이 글은 바이브코딩을 위한 벡터 검색 시리즈의 마지막 글입니다.

앞선 다섯 편에서는 임베딩, 유사도 척도, FAISS, 청킹을 각각 따로 살펴봤습니다. 이번 글에서는 그 부품들을 하나의 실행 가능한 파이프라인으로 조립합니다. 문서를 불러오고, 청크로 나누고, 임베딩하고, FAISS 인덱스에 저장한 뒤, 자연어 쿼리로 결과를 검색하는 전체 흐름입니다. 벡터 검색 파이프라인은 거대한 한 덩어리 기능이 아니라 인덱싱 단계와 검색 단계를 분리해 각각 교체 가능하게 만드는 구조입니다. 이 분리가 없으면 문서가 바뀔 때마다 전체를 다시 실행해야 하고 어디서 품질이 떨어졌는지 추적하기 어렵습니다.

바이브코딩에서 이 개념이 중요한 이유는 단순합니다. AI에게 벡터 검색 파이프라인을 요청할 때 인덱싱과 검색을 분리하고 재인덱싱 트리거 조건을 명시하지 않으면, 단일 스크립트에 모든 것을 섞어 넣는 유지보수 불가능한 코드가 생성되기 때문입니다.

> 벡터 검색 파이프라인은 거대한 한 덩어리 기능이 아니라, 인덱싱 단계와 검색 단계를 분리해 각각 교체 가능하게 만드는 구조입니다.

---

## 이 글에서 다룰 문제

- 벡터 검색 파이프라인은 임베딩 한 번이 아니라 어떤 단계들의 연결일까요?
- 하이브리드 검색은 언제 단순 벡터 검색보다 안전할까요?
- 문서가 바뀌었을 때 재인덱싱과 운영 로그는 무엇을 기준으로 움직여야 할까요?
- 자주 하는 실수와 그 해결책은 무엇일까요?
- 이 개념을 실무에 적용하는 방법은 무엇일까요?

벡터 검색 파이프라인을 이해하면 AI에게 "인덱싱(청킹→임베딩→FAISS 저장)과 검색(임베딩→FAISS 검색→결과 반환)을 분리된 함수로 구현하고 문서 변경 시 재인덱싱 조건을 명시한 코드"를 정확하게 요청할 수 있습니다. 이것이 바이브코딩 시대에 이 개념을 배우는 이유입니다.

## Before / After

**Before — AI에게 컨텍스트 없이 질문:**

```
Q: "문서를 로드해서 벡터 검색 가능하게 만드는 코드 작성해줘"
→ 인덱싱과 검색이 하나의 함수에 섞임
→ 문서 변경 시 전체 재실행
→ 운영 로그 없음
```

**After — 개념을 이해하고 구체적으로 질문:**

```
Q: "인덱싱 파이프라인(build_index)과 검색 파이프라인(search)을 분리해줘.
    build_index는 docs 로드→청킹→임베딩→FAISS 저장 순서로.
    search는 쿼리 임베딩→FAISS 검색→메타데이터 매핑 순서로.
    index.faiss가 이미 있으면 build_index를 건너뛰는 캐시 로직 포함.
    BM25 키워드 검색과 벡터 검색을 결합하는 하이브리드 검색 버전도 추가해줘"
→ 교체 가능한 모듈형 파이프라인
→ 불필요한 재인덱싱 방지
```

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| 인덱싱과 검색을 하나의 함수로 | 문서 변경 시 불필요한 전체 재실행 | build_index와 search를 분리된 함수로 |
| 인덱스 캐시 확인 없음 | 변경 없어도 매번 재인덱싱 | 파일 존재 여부 + 문서 변경 시간 확인 |
| 벡터 검색만 의존 | 희귀 키워드나 고유명사에서 실패 | BM25와 결합한 하이브리드 검색 고려 |
| 재인덱싱 로그 없음 | 언제 무엇을 기준으로 재구축했는지 모름 | 타임스탬프와 문서 수를 로그에 기록 |
| 검색 결과에 출처 없음 | 어떤 청크에서 나온 답인지 추적 불가 | 결과에 source와 chunk_index 포함 |

## AI 협업 팁

벡터 검색 파이프라인 관련 효과적인 AI 프롬프트 패턴:

1. **파이프라인 분리 요청**: "build_index(docs) 함수와 search(query, k=5) 함수를 분리해 작성해줘. build_index는 인덱스가 이미 있으면 건너뛰는 캐시 로직 포함"
2. **하이브리드 검색 요청**: "rank_bm25로 키워드 점수와 FAISS 벡터 유사도를 0.5:0.5로 결합하는 hybrid_search 함수 작성해줘"
3. **재인덱싱 트리거 요청**: "docs/ 폴더의 파일 수정 시각과 저장된 인덱스 생성 시각을 비교해 재인덱싱 필요 여부를 판단하는 함수 작성해줘"

예시 프롬프트:
> "벡터 검색 파이프라인을 두 함수로 구현해줘. build_index(docs): 청킹→임베딩→FAISS IndexFlatIP 저장. search(query, k=5): 쿼리 임베딩→검색→소스 메타데이터 반환. index.faiss가 있으면 build_index 건너뜀. BM25+벡터 하이브리드 버전도 추가."

## 운영 체크리스트

- [ ] 인덱싱(build_index)과 검색(search)이 분리된 함수로 구현됐는가?
- [ ] 인덱스 캐시 확인으로 불필요한 재인덱싱을 방지하는가?
- [ ] 검색 결과에 출처(source, chunk_index)가 포함되는가?
- [ ] 문서 변경 시 재인덱싱 트리거 조건이 명시됐는가?
- [ ] 키워드 검색이 필요한 경우를 위한 하이브리드 검색 옵션이 있는가?

## 처음 질문으로 돌아가기

벡터 검색 파이프라인을 배운 지금, AI에게 이 주제로 더 정확한 질문을 할 수 있게 되었습니다. 인덱싱과 검색 분리를 명시한 사람과 그렇지 않은 사람이 AI에게 받는 파이프라인 코드의 유지보수성은 크게 다릅니다.

## 정리

벡터 검색 파이프라인은 바이브코딩을 위한 벡터 검색 시리즈의 마지막 단계입니다. 임베딩, 거리 척도, FAISS, 청킹이 인덱싱과 검색으로 분리된 파이프라인으로 조립됐습니다. 하이브리드 검색의 필요성과 재인덱싱 조건 관리까지 이해한 지금, 운영 가능한 벡터 검색 시스템을 설계할 준비가 됐습니다.
