# 바이브코딩을 위한 컨테이너 기초 (9/10): Containers vs VMs

이 글은 **바이브코딩을 위한 컨테이너 기초** 시리즈의 아홉 번째 글입니다.

AI가 만든 앱을 배포할 때 "컨테이너로 할까요, VM으로 할까요?"라는 질문이 나옵니다. 단순히 "컨테이너가 더 빠르고 가볍습니다"가 전부가 아닙니다. 어떤 상황에서 어느 것이 더 적합한지 판단하는 기준이 필요합니다.

---

## 오늘의 핵심 질문

AI가 만든 SaaS 앱을 고객별로 격리해서 실행해야 합니다. 컨테이너를 쓰면 될까요, 아니면 VM이 필요할까요? 성능과 보안 사이에서 어떻게 선택해야 할까요?

> "Containers vs VMs의 핵심은 '어느 게 낫다'는 게 아니라, 격리 수준과 리소스 오버헤드를 어느 정도 감수할지에 따라 선택하는 것입니다."

## 이 글에서 다룰 문제

- 컨테이너와 VM은 어떤 격리 모델 차이를 가질까요?
- 커널 공유는 왜 보안에 영향을 줄까요?
- 바이브코딩 앱을 배포할 때 컨테이너가 적합한 경우는?
- 컨테이너 대신 VM이 필요한 경우는?
- Docker Desktop이 내부적으로 VM을 사용한다는 것은 어떤 의미일까요?

## 바이브코딩 관점에서 컨테이너 vs VM 선택

AI가 만든 앱을 어디서 실행할지 결정할 때 자주 나오는 시나리오:

**시나리오 1**: 개인 프로젝트 또는 팀 내부 도구
- 빠른 배포, 쉬운 업데이트가 중요
- 컨테이너 적합

**시나리오 2**: 고객별 데이터를 완전히 격리해야 하는 SaaS
- 고객 A의 앱이 고객 B의 데이터에 접근할 수 없어야 함
- VM 또는 microVM 고려 필요

**시나리오 3**: CI/CD 파이프라인에서 빌드 환경
- 빠른 시작, 격리된 빌드 환경
- 컨테이너 최적

**시나리오 4**: 특정 커널 버전이 필요한 워크로드
- 컨테이너는 호스트 커널을 공유하므로 불가
- VM 필요

### 구조적 차이

```text
VM 기반:
  App → Guest OS (각자 커널 보유) → Hypervisor → Host OS

컨테이너 기반:
  App → Container (호스트 커널 공유) → Container Runtime → Host OS
```

VM은 각자 Guest OS를 부팅하므로 수백 MB 메모리와 수초 부팅 시간이 필요합니다. 컨테이너는 호스트 커널을 그대로 쓰므로 수 MB 메모리와 밀리초 시작이 가능합니다.

**핵심 개념:**

- **hypervisor**: VM을 부팅하고 관리하는 가상화 계층
- **guest kernel**: VM 내부에서 독립적으로 실행되는 커널
- **container**: 호스트 커널을 공유하는 프로세스 격리 단위
- **microVM**: Firecracker 같은 경량 VM. AWS Lambda가 사용

---

## 비교표: 바이브코딩 앱 배포 기준

| 항목 | 컨테이너 | VM |
|------|----------|-----|
| 시작 시간 | 밀리초~수초 | 수초~수분 |
| 메모리 오버헤드 | 낮음 | 높음 (Guest OS 포함) |
| 격리 강도 | 커널 공유 전제 | 커널 완전 분리 |
| 배포 속도 | 빠름 | 느림 |
| 운영 복잡도 | 낮음 (Docker/K8s) | 높음 |
| 멀티테넌트 격리 | 보통 | 강함 |
| 적합한 경우 | 대부분 앱 배포 | 강한 격리 요구 |

---

## 적용 전후: 배포 환경 선택

**Before**: 모든 것을 VM으로 운영

```text
3개 마이크로서비스를 VM으로 운영:
- 각 VM: 1 vCPU, 2GB RAM
- 총: 3 vCPU, 6GB RAM
- 부팅: 각 30~60초
- 업데이트: 각각 수동 재배포
```

**After**: 일반 서비스는 컨테이너로 전환

```bash
# 같은 3개 서비스, 컨테이너로
docker run -d --name svc-a --cpus=0.5 --memory=256m myorg/svc-a:1.0
docker run -d --name svc-b --cpus=0.5 --memory=256m myorg/svc-b:1.0
docker run -d --name svc-c --cpus=0.5 --memory=256m myorg/svc-c:1.0
# 총: 1.5 CPU, 768MB RAM, 시작 <1초
```

현대적인 운영에서는 **VM 위에 Kubernetes를 올리고, 그 위에 컨테이너를 실행**하는 하이브리드가 가장 흔합니다.

---

## 자주 하는 실수

| 실수 | 결과 | 해결 방법 |
|------|------|-----------|
| 컨테이너 = 완전한 격리라고 생각 | 멀티테넌트 보안 취약 | 강한 격리 요구엔 VM 또는 microVM 검토 |
| 모든 것을 VM으로 운영 | 비용과 배포 속도 문제 | 일반 앱은 컨테이너로 전환 |
| Mac/Windows의 Docker가 직접 실행인 줄 앎 | 성능 차이 이해 못 함 | Docker Desktop은 내부적으로 VM 사용 |
| 커널 의존 워크로드를 컨테이너에 넣음 | 동작 안 함 | VM 사용 |
| 격리 요구사항 분석 없이 결정 | 나중에 아키텍처 변경 | 초기에 격리 요구사항 명확화 |

```
앱 특성:

우선순위:

2. 빠른 배포
3. 비용 최적화

각 옵션의 장단점과 추천 이유를 설명해 주세요.
```

## 처음 질문으로 돌아가기

**고객별 격리가 필요한 SaaS 앱에서 컨테이너만 쓰면 될까요?**

컨테이너는 호스트 커널을 공유하므로 커널 취약점이 발견되면 같은 호스트의 모든 컨테이너가 영향을 받을 수 있습니다. 강한 멀티테넌트 격리가 필요하면 VM 또는 microVM(Firecracker)을 사용하거나, gVisor, Kata Containers 같은 강화된 런타임을 검토해야 합니다. AWS Fargate나 Lambda는 내부적으로 microVM을 사용해 이 문제를 해결합니다.

---

## 정리

컨테이너와 VM은 경쟁 관계가 아니라 상호 보완적입니다. 대부분의 바이브코딩 앱은 컨테이너가 적합합니다. 빠른 배포, 낮은 비용, 쉬운 운영이 장점입니다. 강한 멀티테넌트 격리나 커널 독립성이 필요한 경우 VM 또는 하이브리드를 검토합니다.
