# 바이브코딩을 위한 컨테이너 기초 (1/10): Container란 무엇인가?

이 글은 **바이브코딩을 위한 컨테이너 기초** 시리즈의 첫 번째 글입니다.

AI가 만들어 준 앱은 "로컬에서는 잘 됩니다." 그런데 팀원에게 넘기거나 서버에 올리는 순간 "왜 안 되지?"가 시작됩니다. 컨테이너는 그 문제를 끊는 도구입니다. 이 시리즈는 바이브코딩으로 만든 앱을 컨테이너로 패키징하고 어디서든 동일하게 실행하는 방법을 단계적으로 정리합니다.

---

## 오늘의 핵심 질문

AI가 Python 앱을 생성해 줬습니다. 로컬에서는 완벽하게 돌아가는데, 팀원 컴퓨터에서 실행하면 에러가 납니다. "내 환경에서는 되는데"라는 상황, 컨테이너는 이 문제를 어떻게 해결할까요?

> "컨테이너의 가치는 휴대성입니다. '내 로컬에서는 되는데'가 아니라 '어디서나 같게 된다'가 핵심입니다."

---

## 이 글에서 다룰 문제

- 컨테이너를 한 문장으로 정확히 어떻게 정의해야 할까요?
- 컨테이너는 호스트와 무엇을 공유하고, 무엇을 격리할까요?
- VM과의 결정적인 차이는 어디에서 생길까요?
- 바이브코딩으로 만든 앱을 컨테이너로 감싸면 무엇이 달라질까요?
- 이 개념을 실무에서 잘못 적용하면 어떤 문제가 생길까요?

---

## 바이브코딩 관점에서 컨테이너가 필요한 이유

AI가 FastAPI 앱을 만들어 줬다고 가정해 봅니다. 코드는 완벽합니다. 그런데 팀원이 실행하려면 Python 버전을 맞춰야 하고, 특정 라이브러리를 설치해야 하고, 환경 변수를 설정해야 합니다. 이 과정에서 "왜 안 되지?"가 반복됩니다.

컨테이너는 앱과 그 앱이 필요한 모든 환경을 하나의 박스 안에 담습니다. Python 버전, 설치된 라이브러리, 환경 설정까지 모두 포함됩니다. 이 박스를 실행하면 어떤 컴퓨터에서든 똑같이 동작합니다.

바이브코딩의 흐름은 이렇게 됩니다:

1. AI가 앱 코드를 생성합니다
2. Dockerfile을 작성해 앱을 컨테이너 이미지로 패키징합니다
3. 이미지를 레지스트리에 올립니다
4. 어디서든 `docker run` 한 줄로 실행합니다

컨테이너를 이해하지 않으면 바이브코딩으로 만든 앱은 내 컴퓨터에서만 돌아가는 데모로 끝납니다.

### 컨테이너란 무엇인가

컨테이너는 **호스트 커널을 공유하는 격리된 프로세스 묶음**입니다. VM처럼 게스트 운영 체제를 통째로 부팅하지 않습니다. 대신 호스트 커널을 공유한 채 애플리케이션 프로세스를 격리해서 실행합니다.

```bash
# 호스트에서 실행
docker run -d --name demo nginx:1.27-alpine
ps aux | grep nginx
# nginx 프로세스가 호스트 프로세스 목록에 보임

# 컨테이너 내부에서 실행
docker exec demo ps aux
# PID 1부터 시작하는 별도의 프로세스 트리가 보임
```

이 두 출력의 차이가 namespace의 핵심입니다. 호스트에서는 실제 PID가 보이고, 컨테이너 안에서는 격리된 PID 공간이 보입니다. 같은 프로세스를 다른 시점에서 관찰하는 것이지, 별도 운영 체제가 동작하는 것이 아닙니다.

**핵심 용어:**

- **Container**: 격리된 프로세스 묶음입니다.
- **Image**: 컨테이너가 시작할 때 사용하는 정적인 템플릿입니다.
- **Namespace**: 프로세스, 네트워크, 파일시스템 뷰를 분리합니다.
- **cgroups**: CPU와 메모리 사용량 상한을 제어합니다.
- **Runtime**: 컨테이너를 실제로 실행하는 엔진입니다.

---

## 적용 전후: 바이브코딩 앱의 환경 문제

**Before**: AI가 만든 FastAPI 앱을 팀원에게 넘깁니다.

```text
개발자 A 로컬: macOS, Python 3.11, libpq 15
개발자 B 로컬: Ubuntu 22.04, Python 3.10, libpq 14
CI 서버:      Amazon Linux 2, Python 3.9, libpq 13
→ 각 환경에서 다른 방식으로 실패
```

**After**: 컨테이너 이미지 하나로 통일합니다.

```text
이미지: python:3.11-slim + requirements.txt + app 코드
개발자 A 로컬: docker run → 동일 이미지 실행
개발자 B 로컬: docker run → 동일 이미지 실행
CI 서버:      docker run → 동일 이미지 실행
→ 모든 환경에서 동일하게 동작
```

---

## 자주 하는 실수

| 실수 | 결과 | 해결 방법 |
|------|------|-----------|
| 포트 매핑을 빼먹음 | 컨테이너에 접근 불가 | `-p 호스트포트:컨테이너포트` 추가 |
| 컨테이너와 이미지를 혼동 | 잘못된 명령 사용 | 이미지=템플릿, 컨테이너=실행 인스턴스로 구분 |
| 정리 안 하고 방치 | 디스크 낭비 | `docker rm`, `docker rmi` 정기 실행 |
| root로 실행 | 보안 위험 | Dockerfile에 `USER` 지시어 추가 |
| "내 로컬에서는 된다" 믿음 | 환경별 실패 | 컨테이너로 환경을 코드화 |

## AI 팁: 컨테이너 첫 실행에서 막힐 때

바이브코딩으로 앱을 만들다가 컨테이너 관련 에러가 나면 AI에게 이렇게 물어보세요:

```
docker run -d -p 8080:80 --name web nginx:latest
이 명령을 실행했을 때 [에러 메시지]가 나옵니다.
포트 충돌이나 이름 충돌 가능성을 확인하고 해결 방법을 알려주세요.
```

AI는 에러 메시지를 분석해서 정확한 원인과 해결책을 제안합니다. 컨테이너 에러는 대부분 포트 충돌, 이름 중복, 이미지 없음 중 하나입니다.

## 체크리스트

- [ ] Docker가 설치되어 있고 버전을 확인했습니다
- [ ] image와 container의 차이를 설명할 수 있습니다
- [ ] `docker run`, `docker ps`, `docker rm` 명령을 사용해 봤습니다
- [ ] 포트 매핑(`-p`)의 의미를 이해합니다
- [ ] 컨테이너 실행 후 정리까지 해 봤습니다

## 처음 질문으로 돌아가기

**AI가 만든 앱이 "내 환경에서만 된다"는 문제를 컨테이너는 어떻게 해결할까요?**

컨테이너는 앱 코드, Python 버전, 라이브러리, 환경 설정을 하나의 이미지 안에 담습니다. 이 이미지를 실행하면 어떤 컴퓨터에서든 동일한 결과가 납니다. "내 환경에서만 된다"는 말이 사라집니다.

---

## 정리

컨테이너를 이해하는 가장 좋은 출발점은 "호스트 커널을 공유하는 격리된 프로세스 묶음"이라는 정의입니다. 이 정의가 잡히면 왜 이미지가 필요하고, 왜 런타임이 필요하며, 왜 바이브코딩으로 만든 앱을 컨테이너로 감싸야 하는지 자연스럽게 연결됩니다.

다음 글에서는 이 컨테이너가 어떤 정적 템플릿, 즉 이미지와 레이어 구조 위에서 만들어지는지 살펴봅니다.
