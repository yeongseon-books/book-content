# 바이브코딩을 위한 LLM 파인튜닝 (5/6): 모델 평가

이 글은 바이브코딩을 위한 LLM 파인튜닝 시리즈의 5번째 글입니다.

파인튜닝 직후 생성 샘플 몇 개만 보고 품질을 판단하면, 우연히 잘 나온 예시를 개선으로 착각하기 쉽습니다. 5편은 평가를 감이 아니라 파이프라인으로 만드는 단계입니다. 내부 신호인 perplexity를 먼저 보고, 그 위에 골든 세트 기반 평가를 쌓으면 평가도 자동화된 루프로 굴릴 수 있습니다.

바이브코딩에서 이 개념이 중요한 이유는 단순합니다. AI가 생성한 평가 코드가 실제로 올바른 신호를 주는지 확인하려면, 정량 평가와 정성 평가의 차이를 알아야 하기 때문입니다.

> 평가 단계는 파인튜닝 데모가 거짓말을 시작하는 지점입니다 — perplexity 같은 정량 신호를 먼저, 생성 샘플은 그다음에 봐야 하고, 그 사이의 간극이야말로 회귀가 숨어드는 자리입니다.

---

## 이 글에서 다룰 문제

- perplexity는 무엇이고 어떻게 계산할까요?
- 학습 전후 perplexity 비교만으로는 왜 평가가 충분하지 않을까요?
- 골든 세트는 어떻게 설계하고 채점할까요?
- 자주 하는 실수와 그 해결책은 무엇일까요?
- 이 개념을 실무에 적용하는 방법은 무엇일까요?

평가는 화려하지 않지만 파인튜닝 파이프라인의 신뢰를 만드는 단계입니다. 이것이 바이브코딩 시대에 이 개념을 배우는 이유입니다.

## Before / After

**Before — AI에게 컨텍스트 없이 질문:**

```
Q: "파인튜닝 후 모델 평가 코드 작성해줘"
→ 생성 샘플만 출력하는 코드 생성
→ 수치 기반 비교 없이 "잘 됐다"고 판단
→ 회귀 발생해도 감지 불가
```

**After — 개념을 이해하고 구체적으로 질문:**

```
Q: "학습 전후 perplexity를 비교하는 함수와
    골든 세트 키워드 채점 함수를 작성해줘.
    model.eval()과 torch.no_grad() 적용,
    학습/평가 데이터 분리도 포함해줘"
→ 내부 신호와 사용자 품질을 분리한 평가 파이프라인
→ 회귀 감지 기준선 자동화
```

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| perplexity만 보고 배포 결정 | 형식 준수·사실성·안전성은 별도 평가 필요 | 정량 + 정성 두 축 모두 확인 |
| 학습 데이터로 평가 | 숫자가 과도하게 낙관적으로 보임 | hold-out 세트 반드시 분리 |
| model.eval() 빼먹음 | 드롭아웃이 살아 있어 같은 입력에 다른 출력 | 평가 시작 전 model.eval() 필수 |
| 골든 세트를 한 번 만들고 끝 | 모델이 바뀌면 평가 항목도 함께 자라야 | 매주 5~10개씩 추가하는 루틴 |
| 마지막 체크포인트만 평가 | 언제부터 나빠졌는지 알 수 없음 | eval_steps로 중간중간 측정 |

## AI 협업 팁

모델 평가 관련 효과적인 AI 프롬프트 패턴:

1. **perplexity 계산 요청**: "model.eval()과 torch.no_grad()를 적용한 perplexity 계산 함수를 작성해줘"
2. **골든 세트 설계 요청**: "instruction/expected_contains 형식의 JSONL 골든 세트 채점 함수를 작성해줘"
3. **회귀 기준 요청**: "perplexity가 5% 이상 나빠지면 경고를 출력하는 함수를 추가해줘"

예시 프롬프트:
> "학습 전후 perplexity를 비교하는 evaluate_run 함수를 작성해줘. model.eval()과 torch.no_grad() 적용, hold-out 세트 사용, 골든 세트 키워드 채점까지 포함해줘."

모델 평가는 바이브코딩을 위한 LLM 파인튜닝의 핵심 주제 중 하나입니다. 빠른 정량 기준선인 perplexity와 느린 정성 평가인 골든 세트를 층으로 나눠 운용하면 평가가 자동화된 루프로 자리 잡습니다. 다음 글에서는 모델 서빙을 다룹니다.
