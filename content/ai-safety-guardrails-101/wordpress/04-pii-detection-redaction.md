# 바이브코딩을 위한 AI 안전 가드레일 (4/10): PII 감지와 마스킹

> 이 글은 **바이브코딩을 위한 AI 안전 가드레일** 시리즈 4편입니다. LLM 앱에서 개인정보(PII)가 누출되는 경로와 이를 막는 구조적 접근을 다룹니다.

바이브코딩으로 LLM 앱을 빠르게 만들다 보면 개인정보 보호는 나중에 생각하게 된다. "사용자가 개인정보를 굳이 입력하겠어?"라고 생각하기 쉽지만, 실제 운영에서는 사용자가 카드 번호, 주소, 주민식별자를 입력창에 그대로 붙여 넣는 일이 생각보다 자주 일어난다. 더 교묘한 문제는 RAG 문서나 고객지원 기록 같은 검색 문맥 안에 다른 사람의 개인정보가 섞여 있다가 응답에 그대로 재노출되는 경우다.

LLM 앱에서 PII 문제는 두 방향에서 발생한다. 사용자가 입력으로 보내는 방향, 그리고 모델이 문맥에서 읽어 출력으로 내보내는 방향. 입력만 마스킹하면 충분하다고 생각하기 쉽지만, 실제 누출은 출력과 로그에서 더 자주 발생한다.

이 주제가 까다로운 이유는 법무, 보안, 제품 요구가 한 지점에 겹치기 때문이다. 최소 수집 원칙을 지켜야 하고, 사용자 삭제 요청에 대응해야 하며, 동시에 모델이 문맥을 이해할 정도의 정보는 유지하고 싶다. 무조건 `<PERSON>`으로 바꾸면 개인정보는 줄지만 모델 품질도 함께 무너진다. 가역적 토큰화는 이 균형을 맞추는 실용적인 방법이다.

바이브코딩 환경에서는 구조화된 PII(이메일, 전화번호, 카드번호)는 regex로 빠르게 잡고, 이름이나 주소 같은 비정형 정보는 Presidio 같은 NER 도구로 보완하며, 필요할 때는 요청 단위 가역적 토큰화로 문맥 일관성을 유지하는 방식이 현실적이다.

> PII 보호의 핵심은 정보를 숨기는 것이 아니라, 모델이 볼 정보와 시스템이 보관할 정보를 분리하는 것입니다.

## 이 글에서 다룰 문제

- LLM 앱에서 PII 누출은 어디서 발생할까요?
- regex와 Presidio는 각각 어떤 상황에서 쓸까요?
- 단순 마스킹 대신 가역적 토큰화가 필요한 이유는 무엇인가요?
- 출력 단계에서 다시 PII를 검사해야 하는 이유는 무엇인가요?
- GDPR, HIPAA 같은 규제 요구와 기술 구현을 어떻게 연결할까요?

## Before / After: PII 보호 전후

| 상황 | 보호 없이 | 보호 적용 후 |
|------|-----------|-------------|
| 사용자가 카드번호 입력 | 모델에 원문 전달, 로그에 기록 | 입력 단계에서 마스킹, 로그에 해시만 |
| RAG 문서에 타인 이메일 포함 | 응답에 재노출 | 검색 문맥 사전 마스킹, 출력 재검사 |
| 고객지원 요약에 전화번호 포함 | 원문 재노출 | 가역적 토큰화로 문맥 유지 후 복원 제한 |
| 삭제 요청 처리 | 캐시에 사본 잔류 | 저장소 분리로 완전 삭제 가능 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| regex만 사용 | 이름, 주소 등 비정형 PII 누락 | NER 기반 도구(Presidio) 조합 |
| 입력만 마스킹 | 출력, 로그에서 누출 | 입력·문맥·출력·로그 각각 별도 검사 |
| 단순 `<PERSON>` 치환 | 동일 인물 구분 불가, 모델 품질 저하 | 요청 단위 가역적 토큰화 |
| 삭제 요청을 원문 저장소에만 적용 | 캐시, 로그에 잔류 | 모든 저장소 분리 및 TTL 관리 |

## AI 팁: PII 보호 빠르게 시작하는 방법

Claude나 GPT-4에 "Python으로 Presidio를 사용한 PII 탐지와 가역적 토큰화를 구현해줘"라고 요청하면 기본 골격을 얻을 수 있다. 구조화된 PII(이메일, 전화번호, 카드번호)는 `re` 모듈로 빠르게 시작하고, 이름과 주소는 Presidio의 `AnalyzerEngine`으로 보완한다. 가역적 토큰화는 요청 단위로만 매핑을 유지하고 응답 복원 후 즉시 만료시키는 것이 핵심이다. outbound re-check는 같은 탐지 함수를 출력에도 다시 적용하는 한 줄이면 된다.

## 운영 체크리스트

- [ ] 구조화된 PII용 regex와 비정형 PII용 NER 도구를 함께 운영하는가
- [ ] 문맥 일관성이 중요한 경우 요청 단위 가역적 토큰화를 적용하는가
- [ ] 입력, 검색 문맥, 출력, 로그를 각각 별도 PII 검사 지점으로 두는가
- [ ] 해외 모델 공급사 사용 여부와 데이터 보관 정책을 사용자 고지와 일치시키는가
- [ ] 삭제 요청과 보존 기간 만료 처리를 자동화하고 문서화했는가

## 처음 질문으로 돌아가기

- **PII 누출은 어디서 발생하나?** 입력, RAG 검색 문맥, 출력, 로그 네 곳에서 모두 발생한다. 입력만 막으면 나머지 세 경로가 열려 있다.
- **regex vs Presidio?** regex는 형식이 고정된 PII(이메일, 카드번호)에 빠르고 적합하다. Presidio는 이름, 주소처럼 비정형인 정보까지 NER로 잡는다.
- **가역적 토큰화가 필요한 이유는?** 단순 마스킹은 동일 인물을 구분 못하고 모델 추론 품질을 떨어뜨린다. 가역적 토큰화는 문맥 일관성을 유지하면서 원문 보호가 가능하다.

## 정리

PII 보호는 단일 마스킹 함수로 끝나지 않는다. 무엇을 모델에 보내는지, 무엇을 로그에 남기는지, 무엇을 다시 복원할 수 있어야 하는지를 함께 설계해야 한다. 이 문제를 데이터 흐름 관점으로 보면 기술 선택과 규제 대응이 훨씬 명확해진다.

실무적으로는 regex와 Presidio 조합으로 탐지 정확도를 높이고, 필요할 때는 가역적 토큰화로 문맥 품질을 유지하는 방식이 현실적이다. 여기에 outbound re-check와 저장소 분리를 추가해야 실제 누출을 줄일 수 있다.
