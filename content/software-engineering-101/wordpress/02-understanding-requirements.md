# 바이브코딩을 위한 소프트웨어 공학 기초 (2/10): 요구사항 이해하기

이 글은 **바이브코딩을 위한 소프트웨어 공학 기초** 시리즈의 두 번째 글입니다. AI가 코드를 대신 만들어주는 시대에도, 소프트웨어 공학 지식이 없으면 프로젝트가 실패하는 이유를 10편에 걸쳐 풀어갑니다.

---

바이브코딩에서 가장 흔한 실패 패턴이 있습니다. AI에게 "검색 기능 만들어줘"라고 하면 코드가 나옵니다. 그런데 완성하고 나서 보니 "아, 우리가 원한 건 이게 아니었어요"라는 말이 나옵니다.

왜 이런 일이 생길까요? AI는 여러분이 적은 대로 만들어줍니다. 하지만 여러분이 실제로 원하는 것은 적은 것보다 훨씬 복잡합니다. 이 간격을 메우는 것이 바로 요구사항 작업입니다.

> 요구사항은 익숙한 말일수록 사람마다 다른 그림을 떠올립니다. PM·디자이너·개발자·AI 모두 완료 기준을 명시적으로 일치시키지 않으면, 초반의 작은 오해가 나중에 전체를 다시 만드는 상황을 만듭니다.

## 이 글에서 다룰 문제

- 좋은 요구사항은 어떤 조건을 만족해야 할까요?
- 사용자 스토리와 인수 기준은 각각 무엇을 맡을까요?
- 기능 요구사항과 비기능 요구사항은 왜 따로 적어야 할까요?
- AI에게 요구사항을 잘못 전달하면 어떤 문제가 생길까요?
- 바이브코딩 프로젝트에서 초보자가 가장 자주 놓치는 포인트는 무엇일까요?

---

## 바이브코딩에서 요구사항이 중요한 이유

AI에게 코드를 요청할 때, 여러분이 적는 프롬프트가 곧 요구사항입니다. 요구사항이 모호하면 AI도 모호한 코드를 만듭니다. 그리고 나중에 "이게 아닌데?"라고 깨달았을 때는 이미 많은 시간을 쏟은 뒤입니다.

실무에서 코드 결함의 상당수가 요구사항 단계에서 시작된다고 말합니다. 바이브코딩이라고 다르지 않습니다. 오히려 AI가 빠르게 코드를 만들어주는 만큼, 잘못된 방향으로 빠르게 달려갈 수도 있습니다.

## Before / After: 모호한 요구사항 vs 명확한 요구사항

**Before — 바이브코딩의 전형적인 요청**

```text
"검색 기능 만들어줘"
```

AI는 뭔가를 만들어줍니다. 하지만 이게 맞는 건지 아무도 모릅니다.

**After — 측정 가능한 요구사항**

```text
사용자(역할)가 상품 목록(범위)에서 키워드(입력)로 검색하면
관련도 순(정렬)으로 500ms 이내(성능)에 결과를 볼 수 있어야 한다.
```

한 문장 안에 역할, 범위, 입력, 정렬, 성능까지 들어가면 AI도 훨씬 정확한 코드를 만들어줍니다.

## 요구사항을 단계적으로 다듬는 방법

### 1단계 — 사용자 스토리 쓰기

```text
등록된 사용자로서,
이메일로 비밀번호 재설정 링크를 받고 싶다.
그래야 빠르게 계정 접근을 복구할 수 있기 때문이다.
```

역할(누가), 행동(무엇을), 가치(왜)가 한 줄에 들어가면 이 기능이 누구를 위한 것인지 선명해집니다.

### 2단계 — 인수 기준 붙이기

```text
- 등록된 이메일로 60초 안에 메일이 도착한다
- 링크는 30분 후 만료된다
- 링크는 한 번 사용하면 즉시 무효가 된다
- 미등록 이메일도 동일한 응답을 보낸다 (정보 유출 방지)
```

"충분히 빨라야 한다" 같은 표현으로는 완료를 판단할 수 없습니다. AI에게 시킬 때도 이 기준이 없으면 검증할 방법이 없습니다.

### 3단계 — 비기능 요구사항 적기

```text
- 가용성: 월 99.9%
- 보안: 단일 사용 토큰
- 관측성: 발송/사용 카운터를 로그로 남김
```

바이브코딩에서 가장 많이 빠지는 부분이 비기능 요구사항입니다. AI가 만든 코드가 느리거나, 보안이 취약하거나, 장애가 났을 때 원인을 찾기 어렵다면 대부분 비기능 요구사항을 처음부터 정하지 않은 탓입니다.

### 4단계 — 모호함을 드러내는 질문 던지기

```text
- 누가 이 기능을 사용하나요?
- 얼마나 자주 사용되나요?
- 실패하면 어떻게 되나요?
- 어디서 측정하나요?
- "완료"의 기준은 무엇인가요?
```

AI에게 코드를 요청하기 전에 이 질문들에 먼저 답하면, 요청하는 프롬프트가 훨씬 명확해집니다.

### 5단계 — 문서로 남기기

```markdown
## 기능: 비밀번호 재설정
### 목표
- 로그인 실패 문의를 월 30% 줄인다

### 사용자 스토리
- 사용자는 이메일 인증으로 비밀번호를 재설정할 수 있어야 한다

### 인수 기준
- Given 유효한 이메일 / When 재설정 요청 / Then 60초 안에 메일 발송
- Given 만료된 토큰 / When 재설정 시도 / Then 재요청 안내 문구 노출

### 비기능 요구사항
- p95 응답 시간 300ms 이하
- 실패율 1% 이하

### 제외 범위
- 소셜 로그인 계정 비밀번호 재설정은 제외
```

이 문서를 AI에게 붙여 넣으면 훨씬 완성도 높은 코드가 나옵니다.

## 바이브코딩 프로젝트에서 자주 나오는 실수

| 실수 | 결과 | 해결책 |
|------|------|--------|
| "빠르게", "적절히" 같은 단어로 요구사항 작성 | AI가 모호한 코드 생성, 나중에 다시 만들어야 함 | 수치와 조건으로 구체화 |
| 기능 요구사항만 적고 비기능 요구사항 생략 | 느리거나 안전하지 않은 코드 | 성능, 보안, 관측성 명시 |
| 실패 케이스(예외 상황) 미정의 | 장애 시 동작 예측 불가 | 실패 시나리오도 인수 기준에 포함 |
| 구두로만 합의하고 문서화 안 함 | 며칠 뒤 같은 논의 반복 | 짧더라도 문서로 남기기 |

## AI 팁: 요구사항을 AI 프롬프트로 변환하기

요구사항 문서가 준비됐다면, AI에게 이렇게 요청해보세요.

```
다음 요구사항에 맞는 비밀번호 재설정 API를 만들어줘:

[요구사항 문서 붙여넣기]

특히 아래 인수 기준을 모두 통과하는 단위 테스트도 함께 작성해줘:
- 유효한 이메일로 요청 시 60초 안에 메일 발송 (모킹 처리)
- 만료된 토큰으로 시도 시 재요청 안내
- 미등록 이메일도 동일한 응답
```

요구사항이 명확할수록 AI의 결과물도 명확해집니다.

## 처음 질문으로 돌아가기

- **좋은 요구사항은 어떤 조건을 만족해야 할까요?**
  - 테스트 가능해야 합니다. "충분히 빠르다"가 아니라 "p95 응답 300ms 이하"처럼 측정할 수 있어야 나중에 완료를 판단할 수 있습니다.

- **기능 요구사항과 비기능 요구사항은 왜 따로 적어야 할까요?**
  - 기능은 "무엇을 하는가"이고 비기능은 "얼마나 잘 하는가"입니다. AI는 기능 코드를 잘 만들지만, 성능·보안·관측성은 명시적으로 요청하지 않으면 빠지기 쉽습니다.

- **AI에게 요구사항을 잘못 전달하면 어떤 문제가 생길까요?**
  - AI는 적은 대로 만듭니다. 모호하게 적으면 모호한 코드가 나오고, 나중에 전부 다시 만들어야 하는 상황이 됩니다.

## 정리

요구사항은 AI에게 코드를 요청하기 전에 해야 할 가장 중요한 작업입니다. 역할, 행동, 가치, 인수 기준, 비기능 요구사항을 갖추면 AI가 만드는 코드의 품질도 달라집니다.

다음 글에서는 설계와 구현의 차이를 다룹니다. AI가 코드를 만들기 전에 왜 설계 단계가 필요한지, 그리고 어떻게 AI와 함께 설계를 할 수 있는지 살펴봅니다.
