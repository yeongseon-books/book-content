# 바이브코딩을 위한 소프트웨어 공학 기초 (5/10): 테스트 전략

이 글은 **바이브코딩을 위한 소프트웨어 공학 기초** 시리즈의 다섯 번째 글입니다. AI가 코드를 대신 만들어주는 시대에도, 소프트웨어 공학 지식이 없으면 프로젝트가 실패하는 이유를 10편에 걸쳐 풀어갑니다.

---

바이브코딩으로 빠르게 기능을 만들다 보면, 테스트는 "나중에 하면 되지"라고 미루기 쉽습니다. 그런데 나중에 기능이 10개, 20개가 됐을 때 테스트 없이 코드를 수정하면 어떻게 될까요?

아무것도 건드리기 무서워집니다. AI한테 리팩터링 시켰더니 기존 기능이 망가졌는데, 어디가 망가졌는지 알 수가 없는 상황이 됩니다. 이게 테스트 없는 바이브코딩 프로젝트의 현실입니다.

> 테스트 전략은 테스트 개수 문제가 아니라, 올바른 층에 올바른 종류를 배치해서 빠르고 신뢰할 수 있는 피드백을 만드는 문제입니다.

## 이 글에서 다룰 문제

- 단위 테스트, 통합 테스트, E2E 테스트는 각각 어떤 역할을 맡을까요?
- 테스트 피라미드와 아이스크림 콘 구조는 무엇이 다를까요?
- AI가 만든 코드에 테스트가 없으면 어떤 문제가 생길까요?
- 커버리지 수치가 높아도 불안한 이유는 무엇일까요?
- 바이브코딩에서 테스트를 어떻게 시작해야 할까요?

---

## 테스트 없는 바이브코딩의 위험

바이브코딩으로 결제 기능을 만들었습니다. 처음엔 잘 됩니다. 그런데 몇 주 후 다른 기능을 추가하면서 결제 로직을 살짝 건드렸습니다.

테스트가 없다면? 배포하고 나서야 "결제가 안 된다"는 고객 문의가 옵니다.

테스트가 있다면? AI가 코드를 수정한 직후, 30초 만에 "결제 관련 테스트 3개 실패"라는 피드백이 옵니다. 배포 전에 잡을 수 있습니다.

테스트는 AI가 만든 코드를 다시 수정할 때도 안전망 역할을 합니다.

## Before / After: 아이스크림 콘 vs 피라미드

**Before — 아이스크림 콘 구조 (잘못된 방식)**

```text
E2E 80% + 통합 15% + 단위 5%
-> CI가 느리고, 테스트가 flaky하고, 디버깅이 지옥
```

**After — 피라미드 구조 (권장 방식)**

```text
단위 70% + 통합 25% + E2E 5%
-> CI가 빠르고, 실패 위치가 명확
```

같은 테스트 예산이라도 어디에 두느냐에 따라 팀의 체감 속도가 크게 달라집니다.

## 바이브코딩 프로젝트에서 테스트 만들기

### 1단계 — 단위 테스트부터 시작하기

```python
def add(a: int, b: int) -> int:
    return a + b

def test_add():
    assert add(2, 3) == 5
```

AI에게 "이 함수에 대한 단위 테스트 작성해줘"라고 하면 금방 만들어줍니다. 단위 테스트는 가장 빠르고, 가장 많이 가져가야 하는 층입니다.

### 2단계 — 외부 의존성은 가짜 구현으로 통합 테스트

```python
class FakeOrderRepo:
    def __init__(self):
        self.items = []
    def save(self, x):
        self.items.append(x)

def test_order_service():
    repo = FakeOrderRepo()
    service = OrderService(repo)
    service.create({"id": 1})
    assert repo.items == [{"id": 1}]
```

실제 데이터베이스 대신 가짜 구현(Fake)을 쓰면 빠르고 안정적으로 통합 테스트를 할 수 있습니다.

### 3단계 — E2E는 핵심 시나리오만

```python
def test_checkout_flow(client):
    client.post("/cart", json={"sku": "A"})
    r = client.post("/checkout")
    assert r.status_code == 200
```

E2E 테스트는 모든 동작을 덮는 게 아니라, 사용자 여정에서 가장 중요한 흐름만 확인합니다.

### 4단계 — CI에서 테스트 층별로 실행

```yaml
jobs:
  unit:
    steps: [{ run: pytest tests/unit -q }]
  integration:
    steps: [{ run: pytest tests/integration -q }]
  e2e:
    if: github.ref == 'refs/heads/main'
    steps: [{ run: pytest tests/e2e -q }]
```

모든 PR에 모든 테스트를 같은 방식으로 돌릴 필요는 없습니다. 빠른 테스트 먼저, 느린 테스트는 나중에.

## 바이브코딩 프로젝트에서 자주 나오는 실수

| 실수 | 결과 | 해결책 |
|------|------|--------|
| 테스트를 나중으로 미룸 | 기능이 쌓일수록 테스트 추가가 더 어려워짐 | 기능 만들 때 테스트도 함께 |
| 커버리지 숫자만 높이려 함 | 숫자는 높지만 버그는 잡히지 않음 | 의미 있는 테스트 케이스 작성 |
| E2E 테스트만 잔뜩 만듦 | CI가 10분 이상 걸리고 flaky 테스트 발생 | 단위 테스트 비중 늘리기 |
| AI가 만든 코드라 테스트 불필요 | 수정할 때마다 전체가 흔들림 | AI 코드도 테스트 필수 |

## AI 팁: AI와 함께 테스트 작성하기

AI는 테스트 코드를 만드는 데도 뛰어납니다. 이렇게 요청해보세요.

```
다음 함수에 대한 단위 테스트를 작성해줘:

[함수 코드]

아래 케이스를 모두 커버해줘:
- 정상 입력 (여러 가지)
- 경계값 (최솟값, 최댓값)
- 잘못된 입력 (예외 발생 케이스)
- 엣지 케이스 (빈 입력, None 등)
```

그리고 테스트가 실패하면:

```
다음 테스트가 실패했어. 원인을 분석하고 수정해줘:

[실패한 테스트 코드]
[실패 메시지]
```

테스트를 먼저 AI에게 작성하게 하고, 그 테스트를 통과하는 구현 코드를 다시 AI에게 만들게 하는 방식(TDD)도 효과적입니다.

## 커버리지의 함정

커버리지 80%라는 숫자는 "코드의 80%가 실행됐다"는 의미일 뿐, "80%는 안전하다"는 의미가 아닙니다.

```python
def divide(a, b):
    return a / b

def test_divide():
    assert divide(10, 2) == 5  # 커버리지 100%
    # 하지만 divide(10, 0) 은 테스트하지 않음
    # ZeroDivisionError 는 운영에서 터짐
```

의미 있는 테스트는 숫자보다 실패 케이스, 경계 조건, 예외 상황을 포함해야 합니다.

## 처음 질문으로 돌아가기

- **단위 테스트, 통합 테스트, E2E 테스트는 각각 어떤 역할을 맡을까요?**
  - 단위: 함수 하나가 올바르게 동작하는지 (빠름, 많이). 통합: 여러 컴포넌트가 함께 잘 동작하는지 (중간). E2E: 사용자가 겪는 핵심 시나리오 (느림, 적게).

- **커버리지 수치가 높아도 불안한 이유는 무엇일까요?**
  - 커버리지는 코드가 실행됐다는 것만 말해줍니다. 실패 케이스, 경계값, 예외 상황을 테스트하지 않으면 숫자가 높아도 버그가 숨어있을 수 있습니다.

- **바이브코딩에서 테스트를 어떻게 시작해야 할까요?**
  - 가장 중요한 함수 하나를 골라 단위 테스트를 먼저 만드세요. AI에게 "이 함수의 정상/실패/경계 케이스에 대한 테스트 코드 만들어줘"라고 하면 됩니다.

## 정리

테스트는 AI가 만든 코드를 안전하게 수정하고, 버그를 일찍 잡고, 프로젝트가 커져도 속도를 유지하게 해주는 핵심 도구입니다. 단위 테스트를 두텁게, E2E는 핵심 시나리오만 — 이 구조가 자리잡으면 AI와 함께 빠르게 달리면서도 안전할 수 있습니다.

다음 글에서는 버전 관리와 릴리스를 다룹니다. AI가 만든 코드를 어떻게 안전하게 배포하고, 문제가 생겼을 때 빠르게 롤백하는지 살펴봅니다.
