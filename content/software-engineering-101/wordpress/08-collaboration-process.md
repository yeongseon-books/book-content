# 바이브코딩을 위한 소프트웨어 공학 기초 (8/10): 협업 프로세스

이 글은 **바이브코딩을 위한 소프트웨어 공학 기초** 시리즈의 여덟 번째 글입니다. AI가 코드를 대신 만들어주는 시대에도, 소프트웨어 공학 지식이 없으면 프로젝트가 실패하는 이유를 10편에 걸쳐 풀어갑니다.

---

팀에서 바이브코딩을 쓰면 이런 상황이 자주 생깁니다. A 팀원은 AI로 인증 모듈을 만들고, B 팀원은 AI로 결제 모듈을 만들었는데, 합치려고 보니 서로 완전히 다른 방식으로 만들어서 충돌이 납니다. 결정을 어떻게 내렸는지 기록도 없고, 회의에서 이야기했다는데 결론을 아무도 적어두지 않았습니다.

이건 바이브코딩의 문제가 아니라 협업 프로세스의 문제입니다. AI가 아무리 빠르게 코드를 만들어줘도, 팀이 같은 방향으로 움직이지 않으면 속도는 오히려 혼란을 키웁니다.

> 좋은 협업 프로세스는 사람의 시간을 보호하고 결정의 흔적을 남깁니다. AI가 코드를 빠르게 만들수록, 방향을 맞추는 과정이 더 중요해집니다.

## 이 글에서 다룰 문제

- 바이브코딩 팀에서 어떻게 방향을 맞출 수 있을까요?
- RFC는 무엇이고, 어떻게 쓰면 될까요?
- 회의를 줄이면서도 명확성을 유지하는 방법은 무엇일까요?
- 결정 로그는 왜 중요하고, 어떻게 남기면 될까요?
- AI를 협업 도구로 활용하는 방법은 무엇일까요?

---

## 바이브코딩 팀에서 협업 프로세스가 왜 중요한가

AI 없이 코딩할 때도 협업은 어렵습니다. 바이브코딩 팀에서는 이 어려움이 더 커질 수 있습니다. 각자 AI한테 빠르게 구현을 시키다 보면, 기술적 결정이 각자의 대화 세션에 흩어집니다. "AI가 이렇게 만들어줬어요"가 결정 근거가 되고, 왜 그런 구조를 선택했는지 아무도 모릅니다.

결정 프로세스 없이 빠르게 달리면, 나중에 통합할 때 전부 다시 만들어야 하는 상황이 됩니다. 속도가 오히려 손실이 됩니다.

## Before / After: 회의 중심 vs RFC + 짧은 결정 회의

**Before — 모든 결정을 회의에서**

```text
주 12번 회의, 결정 기록 없음 -> 같은 논쟁 반복
```

**After — RFC + 비동기 + 짧은 결정 회의**

```text
3일 비동기 RFC 토론 -> 30분 결정 회의 -> 결정 로그 기록
```

회의는 논의를 시작하는 자리가 아니라, 충분히 익은 논의를 닫는 자리일 때 효과적입니다.

## 바이브코딩 팀의 협업 흐름 만들기

### 1단계 — RFC(Request for Comments) 템플릿

```markdown
## 제목: 알림 채널 추상화 방법

## 문제 정의
현재 이메일만 지원하는데, 카카오톡과 SMS도 추가 예정.
매번 조건문을 늘리는 방식은 유지보수가 어려움.

## 제안
Notifier 프로토콜로 추상화하여 각 채널을 독립적으로 구현

## 대안
- 직접 if/elif 처리
- 외부 알림 SaaS 도입

## 위험 요소
- 초기 구조 설계에 시간 투자 필요
- 팀 전체가 Protocol 패턴 이해 필요

## 열린 질문
- 실패 시 재시도 정책은 어디서 관리?
```

AI에게 "다음 기술적 문제에 대한 RFC 초안을 작성해줘"라고 할 수 있습니다. AI가 만든 초안을 팀이 검토하고 의견을 더하는 방식입니다.

### 2단계 — 비동기 코멘트로 토론

```markdown
@alice [blocking] 인프라 비용 추정이 빠져있어요
@bob [question] 마이그레이션 다운타임은 얼마나 될까요?
@carol [nit] 용어가 문서마다 다르게 사용되고 있어요
```

태그가 있으면 어떤 코멘트가 결정을 막는지 빠르게 구분할 수 있습니다.

### 3단계 — 짧은 결정 회의

```text
30분, 5명 이하, 안건은 RFC 링크 하나.
회의 시작 전에 모두 RFC를 읽어옴.
```

회의 하나에 RFC 하나만 다룹니다. 여러 주제를 한 회의에서 다루면 어느 것도 제대로 결론이 안 납니다.

### 4단계 — 결정 로그 남기기

```markdown
| 날짜 | 주제 | 결정 | 담당자 | 승인자 |
|------|------|------|--------|--------|
| 2026-05-04 | 알림 채널 추상화 | Notifier Protocol 도입 | Alice | Bob |
```

결정 로그가 있으면 "그때 뭐라고 했더라?"를 다시 처음부터 물어볼 일이 줄어듭니다.

### 5단계 — 핸드오프 메모

```markdown
## 어제까지 완료
- API 스펙 합의 완료

## 오늘 목표
- 핸들러 구현

## 블로킹 이슈
- 토큰 형식 확인 대기 중 (@bob에게 물어봐야 함)
```

시차가 있는 팀이나, 다음 날 이어서 작업할 때 핸드오프 메모는 사람 사이를 잇는 비동기 인터페이스 역할을 합니다.

## 바이브코딩 팀에서 자주 나오는 실수

| 실수 | 결과 | 해결책 |
|------|------|--------|
| "AI가 이렇게 만들었어요"가 결정 근거 | 왜 그 구조인지 아무도 모름 | 결정 이유를 RFC나 ADR로 기록 |
| 결정 승인자 없이 코멘트만 쌓임 | 논의가 끝나지 않고 표류 | 각 RFC에 승인자 한 명 지정 |
| 회의에서만 논의하고 기록 없음 | 참석자마다 다른 기억 | 회의 후 결정 로그 필수 |
| 각자 AI로 만들다 합칠 때 충돌 | 대규모 재작업 | 방향을 먼저 RFC로 맞추고 구현 |

## AI 팁: AI를 협업 도구로 활용하기

AI는 협업 과정에서도 유용한 도구입니다.

**RFC 초안 작성:**
```
다음 기술적 문제에 대한 RFC를 작성해줘:
- 문제: [기술 스택이나 아키텍처 문제 설명]
- 독자: 백엔드 개발자 3명
- 결정이 필요한 이유: [왜 지금 결정해야 하는가]
```

**회의록 정리:**
```
다음 회의 내용을 정리해줘:
- 결정된 사항
- 열린 질문과 담당자
- 다음 검토 시점

[회의 내용 붙여넣기]
```

**결정 로그 생성:**
```
다음 논의를 결정 로그 테이블 형식으로 정리해줘:
[슬랙 또는 문서 내용]
```

## 처음 질문으로 돌아가기

- **바이브코딩 팀에서 어떻게 방향을 맞출 수 있을까요?**
  - 구현 전에 RFC로 방향을 먼저 맞추고, 결정 로그로 기록을 남기는 것이 핵심입니다. AI가 각자 다른 방향으로 만들기 전에 팀이 합의를 먼저 해야 합니다.

- **회의를 줄이면서도 명확성을 유지하는 방법은 무엇일까요?**
  - 비동기 RFC 토론으로 대부분의 논의를 처리하고, 동기 회의는 결론을 닫는 데만 씁니다. 회의는 토론 도구가 아니라 결정 도구입니다.

- **결정 로그는 왜 중요하고, 어떻게 남기면 될까요?**
  - 나중에 "왜 이렇게 만들었지?"라는 질문이 생겼을 때, 결정 로그가 있으면 5분 만에 맥락을 복원할 수 있습니다. 날짜, 주제, 결정, 이유, 담당자만 기록하면 됩니다.

## 정리

AI가 코드를 빠르게 만들어줄수록, 팀이 같은 방향으로 움직이는 협업 프로세스가 더 중요해집니다. RFC, 비동기 토론, 결정 로그, 핸드오프 메모가 자리잡으면 팀은 빠르게 달리면서도 방향을 잃지 않습니다.

다음 글에서는 유지보수와 기술부채를 다룹니다. AI가 만든 코드가 쌓이면서 생기는 기술부채를 어떻게 관리하고, 안전하게 개선할 수 있는지 살펴봅니다.
