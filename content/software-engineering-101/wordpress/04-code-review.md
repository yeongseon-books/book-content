# 바이브코딩을 위한 소프트웨어 공학 기초 (4/10): 코드 리뷰

이 글은 **바이브코딩을 위한 소프트웨어 공학 기초** 시리즈의 네 번째 글입니다. AI가 코드를 대신 만들어주는 시대에도, 소프트웨어 공학 지식이 없으면 프로젝트가 실패하는 이유를 10편에 걸쳐 풀어갑니다.

---

"AI가 만들어줬으니까 괜찮겠지"라고 생각하면서 코드 리뷰를 건너뛰는 경우가 있습니다. AI가 만든 코드니까 사람이 만든 것보다 더 믿을 수 있다고 느끼기도 합니다.

그런데 AI는 요청한 기능을 만들어주지만, 그 코드가 시스템 전체 맥락에서 올바른지, 운영 위험이 없는지, 팀이 나중에 이해할 수 있는지까지는 판단하지 않습니다. 그게 코드 리뷰의 역할입니다.

> 좋은 코드 리뷰는 판결문이 아니라 합의 과정입니다. AI가 만든 코드도 예외가 없습니다.

## 이 글에서 다룰 문제

- 코드 리뷰는 버그 찾기와 지식 공유 중 어느 게 더 중요할까요?
- AI가 만든 코드를 어떻게 리뷰해야 할까요?
- 리뷰하기 쉬운 PR은 어떻게 만들 수 있을까요?
- 리뷰어는 실제로 어떤 항목을 먼저 볼까요?
- 바이브코딩 프로젝트에서 코드 리뷰를 건너뛰면 어떤 일이 생길까요?

---

## AI 코드도 리뷰가 필요한 이유

AI가 만든 코드에서 실제로 자주 발견되는 문제들이 있습니다.

- **보안 취약점**: AI는 현재 동작하는 코드를 만들지만, SQL 인젝션이나 인증 우회 같은 보안 패턴은 놓치기 쉽습니다.
- **시스템 맥락 누락**: AI는 우리 서비스의 다른 모듈이 어떻게 동작하는지 모릅니다. 기존 코드와 충돌하거나 중복된 기능을 만들 수 있습니다.
- **운영 위험**: 로그가 없거나, 에러 처리가 부실하거나, 성능 문제가 숨어있을 수 있습니다.
- **팀 컨벤션 불일치**: AI는 우리 팀의 코딩 규칙을 모릅니다.

코드 리뷰는 이런 문제를 사용자가 만나기 전에 잡는 마지막 안전망입니다.

## Before / After: 몰아넣은 PR vs 잘 나눈 PR

**Before — 모든 변경을 하나의 PR에**

```text
PR 제목: 기능 추가 + 버그 수정 + 리팩터링
-> 리뷰하기 불가능, 의도가 섞임
```

**After — 의도별로 나눈 작은 PR**

```text
1) fix: 만료된 토큰 처리 시 500 오류 수정
2) feat: 알림 채널 추상화
3) chore: 불필요한 로그 정리
```

작은 PR은 리뷰 속도를 높이고, 사고가 났을 때 원인을 좁히는 데도 유리합니다.

## 리뷰 가능한 PR 만들기

### 1단계 — 제목 한 줄로 의도 쓰기

```text
fix(auth): 만료된 리프레시 토큰에서 500 대신 401 반환
```

제목만 읽어도 변경의 본질이 보여야 합니다.

### 2단계 — PR 본문 템플릿 채우기

```markdown
## 무엇을 바꾸는가
만료된 리프레시 토큰에 대해 401을 반환합니다.

## 왜 바꾸는가
현재는 500을 던져서 알림이 폭주합니다.

## 어떻게 검증하는가
AuthService.refresh()에서 ExpiredTokenError를 401로 매핑합니다.

## 테스트
단위 테스트 + 수동 cURL 테스트
```

What, Why, How, Test 네 칸만 있어도 리뷰어는 바로 맥락을 잡을 수 있습니다.

### 3단계 — 자동화로 사람 부담 줄이기

```yaml
jobs:
  check:
    steps:
      - run: ruff check .      # 코드 스타일
      - run: mypy app           # 타입 검사
      - run: pytest -q          # 테스트
```

들여쓰기, 포매팅 같은 건 기계한테 맡기고, 사람은 설계와 운영 리스크에 집중해야 합니다.

### 4단계 — 머지 가능한 작은 단위로 나누기

```text
- PR 1: 데이터 모델 변경
- PR 2: 서비스 로직
- PR 3: 핸들러와 라우팅
```

가장 작은 머지 가능 단위를 찾는 능력이 협업 속도를 좌우합니다.

### 5단계 — 코멘트에 강도 표시하기

```text
[nit] user_id 네이밍을 통일하면 더 좋을 것 같아요.
[question] 이 분기가 N+1 쿼리를 유발할 수 있을까요?
[blocking] 시크릿 키가 로그에 노출됩니다. 머지 전에 수정 필수.
```

코멘트에 의사결정 강도를 함께 적으면 토론이 빨라지고 오해가 줄어듭니다.

## AI 코드 리뷰 체크리스트

AI가 만든 코드를 리뷰할 때 특별히 확인해야 할 항목들입니다.

| 체크 항목 | 확인 이유 |
|-----------|-----------|
| 보안 취약점 (SQL 인젝션, XSS 등) | AI가 보안 패턴을 놓치기 쉬움 |
| 에러 처리와 예외 상황 | AI는 주로 정상 경로에 집중 |
| 기존 코드와의 충돌/중복 | AI는 우리 코드베이스를 모름 |
| 로그와 모니터링 포인트 | AI는 운영 관점을 빠뜨리기 쉬움 |
| 팀 컨벤션 준수 | AI는 팀 규칙을 모름 |
| 성능 문제 (N+1 쿼리 등) | AI가 쿼리 최적화를 놓치기 쉬움 |

## 바이브코딩 프로젝트에서 자주 나오는 실수

| 실수 | 결과 | 해결책 |
|------|------|--------|
| "AI가 만들었으니 믿을 수 있다" | 보안·운영 문제를 운영 환경에서 발견 | AI 코드도 반드시 리뷰 |
| 거대한 PR로 리뷰 요청 | 리뷰어가 핵심을 놓침 | PR을 작게 나누기 |
| 자동화 없이 모든 걸 사람이 확인 | 스타일 지적에 리뷰 시간 낭비 | CI로 기계적 검사 자동화 |
| 코드가 아닌 사람을 향한 코멘트 | 팀 분위기 악화, 리뷰 꺼림 | 항상 코드 중심 코멘트 |

## AI 팁: AI와 함께하는 코드 리뷰

AI를 코드 리뷰 보조 도구로 활용할 수 있습니다.

```
다음 코드를 리뷰해줘. 특히 아래 관점에서 확인해줘:
1. 보안 취약점이 있는가?
2. 에러 처리가 충분한가?
3. 성능 문제가 있는가?
4. 테스트가 없는 경로가 있는가?

[코드 붙여넣기]
```

단, AI의 리뷰 결과도 최종 판단은 사람이 해야 합니다. AI가 "괜찮다"고 해도 시스템 맥락을 모르기 때문에 놓치는 부분이 있을 수 있습니다.

## 처음 질문으로 돌아가기

- **코드 리뷰는 버그 찾기와 지식 공유 중 어느 게 더 중요할까요?**
  - 둘 다 중요합니다. 버그를 찾는 건 단기 목표, 지식을 팀이 공유하는 건 장기 목표입니다. AI가 만든 코드일수록 팀이 이해하는 과정이 더 중요해집니다.

- **리뷰하기 쉬운 PR은 어떻게 만들 수 있을까요?**
  - 작게 나누고, 의도를 제목에 담고, What/Why/How/Test를 본문에 적으면 됩니다. 크기가 작은 PR일수록 리뷰 품질도 높아집니다.

- **바이브코딩 프로젝트에서 코드 리뷰를 건너뛰면 어떤 일이 생길까요?**
  - AI가 만든 보안 취약점, 운영 문제, 팀 컨벤션 위반이 운영 환경에서 터집니다. 비용은 리뷰 시간의 수십 배가 됩니다.

## 정리

코드 리뷰는 AI가 만든 코드도 예외가 없습니다. 오히려 AI 코드일수록 시스템 맥락을 모르는 코드가 들어올 수 있어 더 꼼꼼한 리뷰가 필요합니다. 작은 PR, 명확한 의도, 자동화된 기본 검사가 코드 리뷰를 효율적으로 만듭니다.

다음 글에서는 테스트 전략을 다룹니다. AI가 만든 코드를 어떻게 테스트해야 하는지, 바이브코딩 프로젝트에서 테스트 없이 계속 나아가면 어떤 일이 벌어지는지 살펴봅니다.
