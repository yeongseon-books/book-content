# 바이브코딩을 위한 소프트웨어 공학 기초 (9/10): 유지보수와 기술부채

이 글은 **바이브코딩을 위한 소프트웨어 공학 기초** 시리즈의 아홉 번째 글입니다. AI가 코드를 대신 만들어주는 시대에도, 소프트웨어 공학 지식이 없으면 프로젝트가 실패하는 이유를 10편에 걸쳐 풀어갑니다.

---

바이브코딩으로 6개월 동안 기능을 계속 추가했습니다. 처음엔 빠르게 진행됐는데, 어느 순간부터 새 기능을 추가하는 데 점점 더 오래 걸립니다. AI한테 "이 기능 추가해줘"라고 하면, AI가 코드를 만들어주긴 하는데 기존 코드와 어떻게 맞물리는지 파악하는 데만 30분이 걸립니다.

이게 기술부채가 쌓인 결과입니다. AI가 코드를 빠르게 만들어줄수록, 아이러니하게도 기술부채도 빠르게 쌓일 수 있습니다.

> 기술부채는 존재 자체가 문제가 아닙니다. 의식하지 못한 채 쌓이는 것, 그리고 누가 언제 갚을지 계획이 없는 것이 문제입니다.

## 이 글에서 다룰 문제

- 바이브코딩에서 기술부채가 왜 빠르게 쌓이는 걸까요?
- 기술부채는 어떻게 분류하고 관리할 수 있을까요?
- AI가 만든 코드를 안전하게 개선하는 방법은 무엇일까요?
- 부채 상환 우선순위는 어떻게 정해야 할까요?
- "나중에 한 번에 고치자"가 왜 위험한 생각인가요?

---

## 바이브코딩에서 기술부채가 빠르게 쌓이는 이유

AI는 현재 요청을 처리하는 데 최적화되어 있습니다. 기존 코드 전체를 고려하면서 가장 일관된 구조를 만드는 데는 한계가 있습니다.

예를 들어:
- A 팀원이 AI로 만든 인증 모듈은 `user_id`를 정수로 사용
- B 팀원이 AI로 만든 결제 모듈은 `userId`를 문자열로 사용
- 합치려고 보니 타입도 다르고 네이밍도 다름

각각을 AI한테 만들어달라고 할 때는 빠르고 쉬웠는데, 전체를 통합하려고 보면 엄청난 불일치가 생깁니다. 이 불일치가 쌓인 게 기술부채입니다.

## Before / After: 한 번에 대형 리팩터링 vs 점진적 상환

**Before — "나중에 한 번에 고치자"**

```text
12개월 후 대폭 리팩터링 시도 -> 장애 + 일정 폭발
```

**After — 스프린트마다 조금씩 갚기**

```text
매 스프린트 5~10%, 측정하고 우선순위 정해서 -> 점진적 개선
```

부채 상환은 큰 선언보다 작고 반복 가능한 흐름일 때 안전합니다.

## 기술부채를 코드처럼 관리하기

### 1단계 — 부채 라벨 달기

```python
# DEBT: 세금 계산이 PaymentService로 유출됨
# 마감: 2026년 3분기, 담당: @alice
def charge(amount): ...
```

부채에는 맥락, 담당자, 상환 시점이 필요합니다. 없으면 단순한 불평으로 남습니다.

### 2단계 — 부채 인덱스 만들기

```markdown
| ID | 영역 | 심각도 | 담당 | 마감 |
|----|------|--------|------|------|
| D-12 | billing | 높음 | alice | 2026 Q3 |
| D-13 | auth | 중간 | bob | 2026 Q4 |
```

검색 가능한 부채만 실제로 우선순위를 매길 수 있습니다.

### 3단계 — Strangler Fig 패턴으로 안전하게 교체

```python
def charge(amount):
    if feature_flag("new_billing"):
        return new_billing.charge(amount)
    return legacy.charge(amount)  # 기존 코드 유지
```

기존 코드를 한 번에 갈아엎기보다, 기능 플래그로 점진 교체합니다. 문제가 생기면 플래그만 끄면 됩니다.

### 4단계 — deprecated API 단계적으로 제거하기

```python
import warnings

def old_api(*a, **kw):
    warnings.warn(
        "old_api는 deprecated입니다. new_api를 사용해주세요",
        DeprecationWarning,
        stacklevel=2
    )
    return new_api(*a, **kw)
```

경고 → 호출자 추적 → 제거를 한꺼번에 하지 말고 단계별로 나눕니다.

### 5단계 — 부채 지표 추적하기

```text
- 평균 순환 복잡도
- 테스트 커버리지 변화 추이
- 스프린트당 부채 항목 해소 수
- 장애 후 평균 복구 시간(MTTR)
```

측정하지 않는 부채는 우선순위에서 밀리기 쉽습니다.

## 바이브코딩으로 생긴 기술부채 유형

| 부채 유형 | 바이브코딩에서의 원인 | 해결 접근 |
|-----------|---------------------|-----------|
| 네이밍 불일치 | 각자 AI한테 만든 코드의 컨벤션 차이 | 점진적 rename + 타입 통일 |
| 중복 로직 | AI가 비슷한 기능을 여러 곳에 만듦 | 공통 모듈 추출 |
| 테스트 공백 | "일단 만들고 테스트는 나중에" | 핵심 경로부터 테스트 추가 |
| 에러 처리 누락 | AI가 정상 경로에 집중 | 점진적 방어 코드 추가 |
| 문서 없는 복잡 로직 | AI가 생성한 이해하기 어려운 코드 | 리팩터링 + docstring 추가 |

## AI 팁: AI로 기술부채 관리하기

**부채 탐지:**
```
다음 코드에서 기술부채를 찾아줘:
- 중복된 로직
- 이해하기 어려운 복잡도
- 테스트가 없는 중요 경로
- 에러 처리 누락

[코드 붙여넣기]
```

**안전한 리팩터링:**
```
다음 코드를 리팩터링해줘. 단, 아래 조건을 지켜줘:
1. 기존 동작이 변하면 안 됨 (테스트로 확인)
2. 한 번에 너무 많이 바꾸지 말고 작은 단계로
3. 각 단계에서 테스트를 통과해야 다음으로 진행

[코드 붙여넣기]
```

**부채 우선순위:**
```
다음 부채 목록을 사용자 영향과 상환 비용 기준으로 우선순위를 매겨줘:

[부채 목록]
```

## 처음 질문으로 돌아가기

- **바이브코딩에서 기술부채가 왜 빠르게 쌓이는 걸까요?**
  - AI는 각 요청을 독립적으로 처리합니다. 전체 코드베이스의 일관성을 자동으로 유지하지 않기 때문에, 빠르게 기능을 추가할수록 불일치와 중복이 쌓입니다.

- **"나중에 한 번에 고치자"가 왜 위험한 생각인가요?**
  - 나중은 대개 오지 않습니다. 부채가 너무 많이 쌓이면 "한 번에 고치는" 작업 자체가 새로운 장애를 만들기 쉽습니다. 작게 꾸준히 갚는 게 더 안전합니다.

- **AI가 만든 코드를 안전하게 개선하는 방법은 무엇일까요?**
  - 먼저 테스트를 만들어 현재 동작을 고정하고, Strangler Fig 패턴으로 점진적으로 교체하며, 기능 플래그로 되돌릴 수 있는 구조를 유지합니다.

## 정리

기술부채는 바이브코딩 프로젝트에서 피할 수 없지만, 관리는 할 수 있습니다. 부채를 인식하고, 측정하고, 우선순위를 정해서 매 스프린트 조금씩 갚아나가는 습관이 프로젝트를 오래 살아남게 합니다.

다음 글에서는 시리즈 마지막으로 좋은 소프트웨어의 기준을 다룹니다. AI가 만든 코드가 진짜 좋은 소프트웨어인지 어떻게 판단하는지 살펴봅니다.
