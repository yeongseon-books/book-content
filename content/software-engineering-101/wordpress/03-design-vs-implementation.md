# 바이브코딩을 위한 소프트웨어 공학 기초 (3/10): 설계와 구현의 차이

이 글은 **바이브코딩을 위한 소프트웨어 공학 기초** 시리즈의 세 번째 글입니다. AI가 코드를 대신 만들어주는 시대에도, 소프트웨어 공학 지식이 없으면 프로젝트가 실패하는 이유를 10편에 걸쳐 풀어갑니다.

---

AI가 만들어준 코드를 보면 처음에는 깔끔합니다. 그런데 기능을 더 붙이다 보면 어느 순간 이런 생각이 듭니다. "이 코드 구조가 뭔가 이상한데... 근데 어디가 문제인지 모르겠다."

이게 바로 설계 없이 구현만 한 결과입니다. AI는 지금 요청한 기능을 만들어줄 수 있습니다. 하지만 전체 시스템이 어떤 구조로 돌아가야 하는지, 나중에 어떤 부분이 바뀔 수 있는지를 미리 고려하는 건 설계 단계의 일입니다.

> 설계와 구현은 같은 일이 아닙니다. 설계는 '무엇을 분리하고 어느 책임을 어디에 둘 것인가'를 정하는 단계이고, 이 질문이 없으면 AI가 만든 코드도 금방 엉킵니다.

## 이 글에서 다룰 문제

- 잘 작성된 코드와 잘 설계된 시스템은 무엇이 다를까요?
- 설계는 "무엇을", 구현은 "어떻게"라는 말은 실제로 무슨 뜻일까요?
- ADR은 언제 쓰고, 어떻게 활용할 수 있을까요?
- AI가 설계까지 해줄 수 있을까요? 한계는 무엇일까요?
- 바이브코딩에서 설계를 빠뜨리면 어떤 일이 생길까요?

---

## 바이브코딩에서 설계를 빠뜨리면 생기는 일

바이브코딩으로 알림 기능을 만든다고 가정해봅시다. 처음엔 이메일만 보내면 됩니다. AI한테 시키면 금방 됩니다.

3개월 뒤, 카카오톡 알림도 추가해달라는 요청이 옵니다. 이때 설계가 없었다면?

```python
# 설계 없이 AI가 만든 코드
def send_notification(user_id, message):
    # 처음엔 이메일만
    send_email(user_id, message)

# 카카오톡 추가 요청 후
def send_notification(user_id, message):
    send_email(user_id, message)
    send_kakao(user_id, message)  # 그냥 덧붙임

# SMS도 추가 요청 후
def send_notification(user_id, message):
    send_email(user_id, message)
    send_kakao(user_id, message)
    send_sms(user_id, message)
    # ... 이렇게 계속 늘어남
```

코드는 동작하지만, 어디가 문제인지 보이시나요? 새 채널을 추가할 때마다 이 함수를 고쳐야 하고, 테스트하기도 어렵고, 나중엔 아무도 건드리기 싫어하는 코드가 됩니다.

## Before / After: 설계 없이 vs 설계 후

**Before — 구현만 생각한 접근**

```text
"그냥 짜고 나중에 리팩터링하자" -> 결정이 코드 안에 숨어버림
```

**After — 설계를 먼저 생각한 접근**

```text
인터페이스 정의 -> 구현체 분리 -> ADR로 결정 기록 -> 단순한 코드
```

설계가 밖으로 드러나면 구현은 오히려 단순해집니다.

## 설계와 구현을 분리하는 단계별 접근

### 1단계 — 인터페이스부터 세우기

```python
from typing import Protocol

class Notifier(Protocol):
    def send(self, user_id: str, body: str) -> None: ...
```

AI에게 "Notifier 인터페이스를 정의해줘, 이메일·카카오톡·SMS를 모두 지원할 수 있게"라고 하면 이런 코드가 나옵니다. 구현 전에 책임 경계를 먼저 정의하는 것입니다.

### 2단계 — 구현체를 분리하기

```python
class EmailNotifier:
    def send(self, user_id: str, body: str) -> None:
        # 이메일 전송 로직
        ...

class KakaoNotifier:
    def send(self, user_id: str, body: str) -> None:
        # 카카오톡 전송 로직
        ...
```

이제 새 채널이 추가돼도 기존 코드를 건드리지 않고 새 클래스만 만들면 됩니다.

### 3단계 — ADR로 결정 기록하기

ADR(Architecture Decision Record)은 "왜 이런 구조를 선택했는가"를 짧게 남기는 문서입니다.

```markdown
# ADR-007: 알림 채널 추상화
- 배경: 이메일·SMS·카카오톡이 자주 추가됨
- 결정: Notifier 프로토콜로 추상화
- 대안: 직접 if/elif 처리, 외부 SaaS 연동
- 결과: 단위 테스트 쉬움, 성능 비용 거의 없음
```

6개월 뒤에 "왜 이렇게 만들었지?"라는 질문을 받았을 때, ADR이 있으면 바로 답할 수 있습니다.

### 4단계 — YAGNI: 지금 필요 없는 건 만들지 않기

YAGNI(You Aren't Gonna Need It)는 "오늘 필요하지 않은 것을 미리 만들지 않는" 원칙입니다.

```python
# 아직 채널이 두 개뿐인데 이런 걸 만들 필요는 없다
# class NotifierFactory: ...       # 미래를 위한 과도한 추상화
# class NotifierRegistry: ...      # 지금은 불필요
```

AI는 종종 "미래를 위해" 복잡한 구조를 만들어줍니다. 하지만 지금 필요하지 않은 복잡함은 나중에 짐이 됩니다. YAGNI를 기억하세요.

### 5단계 — 관측성도 설계에 포함하기

```python
import logging
log = logging.getLogger(__name__)

class EmailNotifier:
    def send(self, user_id: str, body: str) -> None:
        log.info("알림 전송", extra={"user": user_id, "channel": "email"})
        # 전송 로직
```

로그는 나중에 붙이는 게 아니라, 설계 단계에서 "어디서 무엇을 관찰할 것인가"를 결정해야 합니다.

## 바이브코딩 프로젝트에서 자주 나오는 실수

| 실수 | 결과 | 해결책 |
|------|------|--------|
| 설계 없이 바로 AI에게 구현 요청 | 기능 추가 때마다 기존 코드 대규모 수정 | 인터페이스 먼저 정의 |
| "일단 짜고 나중에 고치자" | 나중에 고칠 시간이 없음 | 작은 설계라도 먼저 |
| AI가 만든 복잡한 추상화 그대로 수용 | 불필요한 복잡도 | YAGNI 원칙 적용 |
| 결정 이유를 기록 안 함 | 6개월 뒤 같은 논쟁 반복 | ADR 한 장이라도 남기기 |

## AI 팁: 설계 단계에서 AI 활용하기

AI는 설계 도구로도 유용합니다. 이렇게 활용해보세요.

```
알림 시스템을 설계해줘. 지금은 이메일만 있지만,
나중에 카카오톡과 SMS도 추가될 예정이야.
- 새 채널을 추가할 때 기존 코드를 최소한으로 수정하는 구조
- 각 채널을 독립적으로 테스트할 수 있는 구조
- Python의 Protocol을 사용한 인터페이스 예시 코드 포함

설계 결정 이유도 ADR 형식으로 함께 작성해줘.
```

이렇게 요청하면 AI가 구현 코드뿐만 아니라 설계 근거까지 만들어줍니다. 물론 그 결과를 검토하고 판단하는 건 사람의 몫입니다.

## 처음 질문으로 돌아가기

- **잘 작성된 코드와 잘 설계된 시스템은 무엇이 다를까요?**
  - 잘 작성된 코드는 지금 읽기 좋은 코드입니다. 잘 설계된 시스템은 나중에 바꾸기 쉬운 구조입니다. AI는 잘 작성된 코드를 만드는 데 뛰어나지만, 잘 설계된 구조는 먼저 사람이 방향을 잡아야 합니다.

- **ADR은 언제 쓰고, 어떻게 활용할 수 있을까요?**
  - 큰 결정을 내릴 때마다 씁니다. 길 필요 없이, 나중에 "왜 이렇게 만들었는가"를 복원할 수 있으면 충분합니다. 팀이 작아도, 심지어 혼자 작업해도 ADR은 미래의 나에게 도움이 됩니다.

- **바이브코딩에서 설계를 빠뜨리면 어떤 일이 생길까요?**
  - 처음에는 빠르게 진행됩니다. 하지만 기능이 3~4개 넘어가는 시점부터 코드가 엉키고, 새 기능을 추가할 때마다 기존 코드를 대규모로 수정해야 하는 상황이 됩니다.

## 정리

설계는 코드를 짜기 전에 "무엇을 어떤 경계로 나눌지" 생각하는 일입니다. AI가 만들어준 코드가 잘 돌아가더라도, 구조적 결정을 미리 해두지 않으면 나중에 더 큰 비용을 치릅니다.

다음 글에서는 코드 리뷰를 다룹니다. 바이브코딩 프로젝트에서 AI가 만든 코드를 어떻게 검토하고, 팀이 함께 품질을 유지하는지 살펴봅니다.
