# 바이브코딩을 위한 소프트웨어 공학 기초 (6/10): 버전 관리와 릴리스

이 글은 **바이브코딩을 위한 소프트웨어 공학 기초** 시리즈의 여섯 번째 글입니다. AI가 코드를 대신 만들어주는 시대에도, 소프트웨어 공학 지식이 없으면 프로젝트가 실패하는 이유를 10편에 걸쳐 풀어갑니다.

---

바이브코딩으로 열심히 만든 기능을 배포했는데, 결제가 안 된다는 신고가 들어옵니다. 패닉 상태에서 무엇을 어떻게 되돌려야 할지 모릅니다.

버전 관리와 릴리스 프로세스가 없는 바이브코딩 프로젝트의 전형적인 장면입니다. AI가 아무리 빠르게 코드를 만들어줘도, 그 코드를 안전하게 사용자에게 전달하고 문제가 생겼을 때 빠르게 복구하는 능력이 없으면 모든 게 무너집니다.

> 릴리스는 한 번의 이벤트가 아니라 회복 가능한 과정입니다. 작게 자주 보내고, 신호가 나쁘면 즉시 되돌릴 수 있어야 사용자 신뢰가 형성됩니다.

## 이 글에서 다룰 문제

- 브랜치 전략은 어떻게 잡아야 할까요?
- 버전 번호는 어떻게 정해야 할까요?
- 배포 후 사고가 났을 때 어떻게 빠르게 롤백할 수 있을까요?
- AI가 코드를 만들어줄 때 버전 관리를 어떻게 연결할까요?
- 바이브코딩에서 릴리스 프로세스가 없으면 어떤 일이 생길까요?

## 바이브코딩에서 버전 관리가 중요한 이유

AI가 코드를 만들어줄 때마다 직접 서버에 올리는 방식으로 운영하면 어떻게 될까요?

- 어떤 버전의 코드가 지금 서버에 올라가 있는지 모릅니다
- 문제가 생겼을 때 무엇을 되돌려야 하는지 모릅니다
- 어떤 변경이 문제를 일으켰는지 추적할 수 없습니다
- 팀원이 각자 다른 코드를 수정하다 충돌이 납니다

버전 관리는 AI가 만든 코드의 흔적을 남기고, 언제든 안전한 상태로 돌아갈 수 있게 해주는 타임머신입니다.

## Before / After: 대형 배포 vs 점진 배포

**Before — 한 번에 몰아서 배포**

```text
2주치 기능 200개 PR 한꺼번에 배포
-> 문제 원인을 찾을 수 없음
```

**After — 작게 자주 배포**

```text
하루에 여러 번 작은 변경 -> 5% 트래픽 먼저 -> 모니터링 -> 전체 배포
```

작고 자주 배포할수록 문제가 생겨도 범위를 빨리 좁힐 수 있습니다.

## 버전 관리와 릴리스 파이프라인 만들기

### 1단계 — 의미 있는 커밋 메시지 쓰기

```text
feat(auth): 리프레시 토큰 순환 기능 추가
fix(billing): 금액 0원 청구서 처리 오류 수정
chore(deps): fastapi 0.110으로 업그레이드
```

커밋 메시지를 이렇게 형식화하면(Conventional Commits), 나중에 버전과 체인지로그를 자동으로 만들 수 있습니다. AI에게 "이 변경사항을 Conventional Commits 형식으로 커밋 메시지 작성해줘"라고 하면 됩니다.

### 2단계 — 시맨틱 버저닝(SemVer)으로 버전 정하기

```text
feat  -> MINOR 버전 증가 (1.1.0 -> 1.2.0)
fix   -> PATCH 버전 증가 (1.2.0 -> 1.2.1)
BREAKING CHANGE -> MAJOR 버전 증가 (1.2.1 -> 2.0.0)
```

버전 번호는 감으로 정하지 않습니다. 변경 유형이 버전을 결정하게 하면 일관성이 생깁니다.

### 3단계 — 체인지로그 자동 생성하기

```yaml
- uses: googleapis/release-please-action@v4
  with:
    release-type: python
```

PR이 머지될 때마다 릴리스 PR과 체인지로그가 자동으로 생성되게 할 수 있습니다.

### 4단계 — 카나리 배포로 안전하게 노출하기

```yaml
strategy:
  canary:
    weight: 5  # 5% 트래픽만 먼저 새 버전으로
    after:
      metrics: error_rate < 0.5%
      duration: 10m
```

전체 사용자에게 한 번에 새 버전을 보내지 않고, 5%에게 먼저 보내서 문제가 없는지 확인합니다.

### 5단계 — 롤백을 1분 안에 할 수 있게 준비하기

```bash
kubectl rollout undo deployment/api
```

롤백은 문서에만 있는 절차가 아니라, 실제로 1분 안에 끝날 수 있어야 합니다. 배포 전에 롤백 명령을 실제로 테스트해두세요.

## 바이브코딩 프로젝트에서 자주 나오는 실수

| 실수 | 결과 | 해결책 |
|------|------|--------|
| 커밋 없이 서버에 직접 올림 | 어떤 코드가 서버에 있는지 모름 | 모든 변경을 Git으로 관리 |
| 버전 번호를 감으로 결정 | 사용자가 변경 범위를 예측 못함 | SemVer 규칙 따르기 |
| 롤백 방법을 모름 | 장애 시 수동으로 재배포하다 시간 낭비 | 롤백 명령을 미리 준비하고 테스트 |
| 체인지로그를 사용자 관점으로 안 씀 | 사용자가 무엇이 바뀌었는지 모름 | 사용자 언어로 변경사항 작성 |

## AI 팁: AI와 함께하는 버전 관리

AI를 릴리스 프로세스에 활용하는 방법:

```
다음 PR들이 머지됐어. 시맨틱 버저닝과 Conventional Commits 형식으로
체인지로그를 작성해줘. 사용자가 이해할 수 있는 언어로:

PR 목록:
- feat(auth): 소셜 로그인 추가
- fix(billing): 환불 처리 오류 수정
- perf(search): 검색 속도 30% 개선
```

AI가 사용자 관점의 체인지로그 초안을 만들어주면, 사람이 검토하고 다듬으면 됩니다.

## 처음 질문으로 돌아가기

- **배포 후 사고가 났을 때 어떻게 빠르게 롤백할 수 있을까요?**
  - 롤백 명령을 미리 준비하고, 실제로 테스트해두는 것이 핵심입니다. 장애 상황에서 처음 해보는 롤백은 대개 늦고 어설픕니다.

- **AI가 코드를 만들어줄 때 버전 관리를 어떻게 연결할까요?**
  - AI가 코드를 만들어주면, 그 변경사항을 Conventional Commits 형식으로 커밋하고 PR로 만드세요. AI에게 커밋 메시지도 같이 작성해달라고 할 수 있습니다.

- **바이브코딩에서 릴리스 프로세스가 없으면 어떤 일이 생길까요?**
  - 배포 후 사고가 났을 때 무엇을 어떻게 되돌려야 할지 모르는 상황이 됩니다. 가장 중요한 순간에 아무것도 할 수 없게 됩니다.

## 정리

버전 관리와 릴리스는 AI가 만든 코드를 사용자에게 안전하게 전달하는 마지막 관문입니다. 작은 변경을 자주 배포하고, 빠르게 롤백할 수 있는 구조가 갖춰지면 바이브코딩 프로젝트도 안정적으로 운영할 수 있습니다.

다음 글에서는 문서화를 다룹니다. AI가 만든 코드를 팀이 이해할 수 있게 하고, 나중에 다시 봐도 맥락을 파악할 수 있는 문서 작성법을 살펴봅니다.
