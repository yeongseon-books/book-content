# 바이브코딩을 위한 소프트웨어 공학 기초 (10/10): 좋은 소프트웨어의 기준

이 글은 **바이브코딩을 위한 소프트웨어 공학 기초** 시리즈의 마지막 글입니다. AI가 코드를 대신 만들어주는 시대에도, 소프트웨어 공학 지식이 없으면 프로젝트가 실패하는 이유를 10편에 걸쳐 풀어갑니다.

---

"AI가 만들어줬으니 좋은 코드겠지요"라는 말을 많이 듣습니다. 하지만 "좋은 코드"와 "좋은 소프트웨어"는 다른 이야기입니다.

AI가 만든 코드가 지금 잘 돌아간다고 해서 6개월 후에도 잘 돌아간다는 보장은 없습니다. 팀이 계속 빠르게 기능을 추가할 수 있는지, 장애가 났을 때 빠르게 복구하는지, 새 팀원이 빠르게 이해할 수 있는지 — 이것들이 좋은 소프트웨어의 진짜 기준입니다.

> 기능이 동작하는 소프트웨어와 좋은 소프트웨어는 같은 말이 아닙니다. 좋은 소프트웨어의 신호는 코드 스타일이 아니라 변경 리드 타임, 사고 복구 속도, 신규 팀원 적응 시간처럼 코드 바깥에서 드러납니다.

## 이 글에서 다룰 문제

- AI가 만든 코드가 좋은 소프트웨어인지 어떻게 판단할 수 있을까요?
- 품질은 어떤 축으로 측정해야 할까요?
- SOLID 원칙은 바이브코딩에서 어떻게 활용할 수 있을까요?
- 좋은 소프트웨어를 만들기 위해 팀이 할 수 있는 최소한의 것은 무엇일까요?
- 이 시리즈에서 배운 것들이 실제로 어떻게 연결되는 걸까요?

---

## AI 코드가 "좋은 소프트웨어"가 되는 조건

AI는 요청한 기능을 만들어줍니다. 하지만 좋은 소프트웨어는 그 이상을 요구합니다.

**기능이 동작하는 코드:**
- 로그인이 된다
- 결제가 처리된다
- 검색이 결과를 반환한다

**좋은 소프트웨어:**
- 로그인이 느려졌을 때 5분 안에 원인을 파악할 수 있다
- 결제 로직이 바뀌어도 기존 기능이 깨지지 않는다
- 새 팀원이 2주 안에 검색 기능을 개선할 수 있다

이 차이를 만드는 건 이 시리즈에서 다룬 소프트웨어 공학 지식입니다.

## Before / After: "잘 돌아간다" vs 품질 속성 측정

**Before — 기능 중심 판단**

```text
"잘 돌아간다" = 유일한 기준
-> 6개월 후 변경 비용 폭발
```

**After — 품질 속성 측정**

```text
리드 타임, 장애율, MTTR, 유지보수성 점수
-> 개선 방향이 보임
```

측정하지 않으면 개선도 어렵습니다.

## 좋은 소프트웨어를 만드는 단계별 접근

### 1단계 — SRP: 하나의 클래스는 하나의 역할

```python
class Invoice:           # 역할 1: 데이터
    ...

class InvoicePrinter:    # 역할 2: 출력
    ...
```

AI가 만든 코드를 보면 하나의 클래스가 너무 많은 일을 하는 경우가 자주 있습니다. 클래스가 여러 이유로 바뀐다면 유지보수 비용이 빠르게 올라갑니다.

### 2단계 — DIP: 구체 구현보다 추상 경계에 의존

```python
class OrderService:
    def __init__(self, repo: "Repo"):  # 인터페이스에 의존
        self.repo = repo
```

구체적인 구현에 의존할수록 나중에 바꾸기 어려워집니다. AI에게 "이 코드를 인터페이스 기반으로 리팩터링해줘"라고 하면 도움을 받을 수 있습니다.

### 3단계 — 복잡도 측정하기

```bash
radon cc app/ -a -nb
```

복잡도는 느낌이 아니라 수치로 볼 수 있습니다. AI가 만든 함수가 너무 복잡하면 쪼개달라고 요청하세요.

### 4단계 — 리드 타임 측정하기

변경이 코드로 만들어져서 사용자에게 전달되기까지 얼마나 걸리는지 추적합니다. 이 시간이 길어지면 프로세스 어딘가에 병목이 있다는 신호입니다.

### 5단계 — 외부 신호로 품질 판단하기

```text
- 새 팀원의 첫 PR까지 걸린 시간
- 장애 후 평균 복구 시간(MTTR)
- 새 기능 리드 타임
- 사용자 만족도(NPS, CSAT)
```

내부 코드 지표만으로는 드러나지 않는 진실이 외부 신호에 있습니다.

## 좋은 소프트웨어를 위한 품질 기준표

팀이 같은 기준으로 품질을 판단하려면 기준을 먼저 합의해야 합니다.

```markdown
## 우리 팀의 품질 기준선

- 신뢰성: 월간 가용성 99.9% 이상
- 성능: p95 응답 시간 300ms 이하
- 변경 용이성: 평균 PR 리드 타임 2일 이하
- 복구성: MTTR 30분 이하
- 이해 가능성: 새 팀원 온보딩 2주 내 핵심 흐름 이해
```

이 기준이 있으면 "AI가 만든 코드가 좋은가?"라는 질문에 감이 아닌 데이터로 답할 수 있습니다.

## 이 시리즈에서 배운 것들이 어떻게 연결되는가

| 챕터 | 핵심 교훈 | AI 코드에 적용하는 방법 |
|------|-----------|------------------------|
| 1. 소프트웨어 공학이란 | 코딩 != 엔지니어링 | AI 코드도 운영 가능한 구조로 |
| 2. 요구사항 | 모호함을 줄여야 AI도 잘 만듦 | 요구사항 먼저 정리하고 AI에 요청 |
| 3. 설계 vs 구현 | 구조 먼저, 코드 나중 | 인터페이스 정의 후 AI에 구현 요청 |
| 4. 코드 리뷰 | AI 코드도 리뷰 필수 | 보안·운영·컨텍스트 관점 리뷰 |
| 5. 테스트 전략 | 피라미드 구조로 테스트 | AI에게 테스트도 함께 요청 |
| 6. 버전 관리 | 작게 자주 배포 | 롤백 가능한 구조 만들기 |
| 7. 문서화 | 결정의 맥락을 남기기 | ADR, README, 런북 준비 |
| 8. 협업 | 방향 먼저 맞추고 구현 | RFC로 합의 후 AI에 요청 |
| 9. 기술부채 | 부채는 관리해야 하는 비용 | 점진적 상환 계획 세우기 |
| 10. 품질 기준 | 외부 신호로 판단 | 팀 기준선 합의하기 |

## AI 팁: AI로 품질 개선하기

**코드 품질 점검:**
```
다음 코드의 품질을 SOLID 원칙 관점에서 검토해줘:
- 각 원칙이 어떻게 위반되는지
- 개선 방법
- 우선순위 (사용자 영향이 큰 것부터)

[코드 붙여넣기]
```

**품질 기준 수립 도움:**
```
우리 팀의 소프트웨어 품질 기준을 만들어야 해.
다음 정보를 참고해서 측정 가능한 기준을 제안해줘:
- 팀 규모: 3명
- 서비스 종류: B2C 앱
- 현재 배포 주기: 2주에 한 번
- 주요 관심사: 안정성, 빠른 기능 추가
```

## 처음 질문으로 돌아가기

- **AI가 만든 코드가 좋은 소프트웨어인지 어떻게 판단할 수 있을까요?**
  - "잘 돌아가는가"만으로는 부족합니다. 변경하기 쉬운가, 장애를 빠르게 복구할 수 있는가, 팀이 이해하고 개선할 수 있는가를 함께 봐야 합니다.

- **SOLID 원칙은 바이브코딩에서 어떻게 활용할 수 있을까요?**
  - 교리처럼 적용하면 오히려 복잡해집니다. "이 코드를 나중에 바꾸기 쉬운가?"라는 질문의 도구로 사용하세요. AI에게 SOLID 관점에서 코드 리뷰를 요청할 수도 있습니다.

- **이 시리즈에서 배운 것들이 실제로 어떻게 연결되는 걸까요?**
  - 요구사항을 명확히 하면 AI가 더 잘 만들어줍니다. 설계를 먼저 하면 AI 코드가 시스템에 잘 맞습니다. 테스트가 있으면 AI 리팩터링이 안전합니다. 문서가 있으면 팀이 AI 코드를 이해할 수 있습니다. 이 모든 것이 좋은 소프트웨어를 향한 연결 고리입니다.

## 정리

이 시리즈를 통해 바이브코딩에서 소프트웨어 공학이 왜 필요한지 살펴봤습니다.

AI는 빠르게 코드를 만들어주는 강력한 도구입니다. 하지만 그 코드가 시간이 지나도 유지 가능하고, 팀이 함께 발전시킬 수 있고, 사고가 났을 때 빠르게 복구할 수 있는 소프트웨어가 되려면 소프트웨어 공학 지식이 필요합니다.

AI가 코드를 만들어주는 시대일수록, 그 코드를 올바르게 방향 잡고 판단하는 엔지니어링 능력이 더 중요해집니다.

이 시리즈를 통해 바이브코딩 프로젝트를 한 단계 더 발전시키는 데 도움이 됐으면 합니다.
