# 바이브코딩을 위한 소프트웨어 공학 기초 (7/10): 문서화

이 글은 **바이브코딩을 위한 소프트웨어 공학 기초** 시리즈의 일곱 번째 글입니다. AI가 코드를 대신 만들어주는 시대에도, 소프트웨어 공학 지식이 없으면 프로젝트가 실패하는 이유를 10편에 걸쳐 풀어갑니다.

---

"코드가 있으면 문서는 필요 없어요. AI한테 물어보면 설명해주잖아요."

바이브코딩 프로젝트에서 자주 듣는 말입니다. 그런데 AI한테 "이 코드가 왜 이렇게 만들어졌나요?"라고 물어보면 AI는 "그렇게 작성된 것 같습니다"라고 답합니다. AI는 그 결정이 왜 내려졌는지 모릅니다.

문서화가 없으면 팀이 커질수록, 시간이 지날수록, "왜 이렇게 만들었지?"라는 질문이 반복됩니다. 그때마다 원래 만든 사람을 붙잡아야 합니다.

> 문서화는 친절의 문제가 아니라 비동기 협업의 기반입니다. AI가 만든 코드도, 그 결정의 맥락을 사람이 기록하지 않으면 나중에 누구도 이해할 수 없습니다.

## 이 글에서 다룰 문제

- AI가 만든 코드에 문서가 없으면 어떤 문제가 생길까요?
- 좋은 README는 최소한 어떤 내용을 담아야 할까요?
- ADR은 코드 주석과 어떻게 다를까요?
- docstring은 왜 중요하고, AI는 이걸 잘 만드나요?
- 장애 상황에서 문서가 없으면 어떤 일이 벌어질까요?

---

## AI 코드에 문서가 없으면 생기는 일

바이브코딩으로 6개월 만에 프로젝트를 키웠습니다. AI가 수백 개의 함수와 모듈을 만들었습니다. 그런데:

- 새 팀원이 합류했습니다. 어디서 시작해야 할지 모릅니다.
- 장애가 났습니다. 어느 모듈이 어떤 역할을 하는지 파악하는 데만 1시간이 걸립니다.
- "왜 이 로직이 이렇게 돼있어요?"라는 질문에 원래 만든 사람도 기억이 없습니다.

문서가 없으면 모든 정보는 특정 사람의 기억에 묶입니다. 그 사람이 바쁘거나 없으면 팀 전체가 느려집니다.

## Before / After: 하나의 거대한 위키 vs 목적별 문서

**Before — "위키 어딘가에 있어요"**

```text
모든 정보가 하나의 위키에 -> 아무도 어디 있는지 모름
```

**After — 목적별로 나눈 문서**

```text
docs/tutorials/    # 처음 배우는 사람을 위한
docs/how-to/       # 특정 작업을 하는 방법
docs/reference/    # API 레퍼런스
docs/explanation/  # 왜 이렇게 만들었는가
```

문서가 많은 게 문제가 아니라, 독자가 어디서 시작해야 할지 모르는 상태가 문제입니다.

## 바이브코딩 프로젝트에서 문서 만들기

### 1단계 — README 5개 블록

```markdown
## 이 프로젝트가 하는 일
[한 문장 설명]

## 왜 만들었나
[존재 이유]

## 빠른 시작 (60초)
[복사해서 바로 실행되는 명령어]

## 설정
[환경 변수 표]

## 더 알아보기
[링크들]
```

AI에게 "우리 프로젝트의 README를 이 5개 블록 구조로 작성해줘"라고 하면 초안을 만들어줍니다.

### 2단계 — ADR(Architecture Decision Record) 한 장

```markdown
# ADR-012: Redis 캐시 도입
- 배경: 상품 목록 API 응답이 p95 기준 2초를 초과
- 결정: Redis로 상품 목록 1분 캐시
- 대안: 폴링 최소화, DB 쿼리 최적화
- 결과: 응답 시간 평균 1.8초 감소, 운영 복잡도 증가
```

AI가 "Redis를 도입해야 할 것 같아"라고 코드를 만들어줬다면, 왜 그 결정을 내렸는지 ADR로 남겨두세요. 6개월 뒤의 나에게 가장 도움이 됩니다.

### 3단계 — docstring과 타입 힌트

```python
def compute_invoice(amount: int, tax_rate: float) -> int:
    """세금 포함 금액을 센트 단위로 반환합니다.

    Args:
        amount: 세전 금액 (센트)
        tax_rate: 세율 (0.0 ~ 1.0)

    Returns:
        세금 포함 총액 (센트)

    Raises:
        ValueError: amount가 음수일 때
    """
```

AI는 타입 힌트와 docstring을 잘 만들어줍니다. "이 함수에 타입 힌트와 docstring을 추가해줘"라고만 하면 됩니다.

### 4단계 — 런북(Runbook): 장애 대응 절차서

```markdown
# 장애 대응 런북: 결제 실패율 급증

## 증상
- 5분 평균 결제 실패율 5% 초과

## 즉시 확인
1. 결제 서비스 헬스 체크
2. 최근 배포 여부
3. 외부 결제 게이트웨이 상태

## 임시 완화
- 에러율 10% 초과 시 즉시 롤백

## 복구 후 조치
- 원인 분석 문서 작성
```

런북은 새벽 장애 상황에서 잠이 덜 깬 상태로도 따라갈 수 있어야 합니다. AI에게 "이 시스템의 주요 장애 시나리오별 런북을 만들어줘"라고 할 수 있습니다.

### 5단계 — 온보딩 체크리스트

```markdown
## 새 팀원 첫 30일
- [ ] 저장소 클론, 로컬 환경 설정
- [ ] 첫 PR 올리기 (오타 수정이라도)
- [ ] 첫 번째 장애 쉐도잉
- [ ] 핵심 기능 3개 직접 사용해보기
```

새 팀원이 합류했을 때 누군가 옆에서 설명해줘야 한다면, 그건 문서가 부족하다는 신호입니다.

## 바이브코딩 프로젝트에서 자주 나오는 실수

| 실수 | 결과 | 해결책 |
|------|------|--------|
| "AI가 설명해줄 수 있잖아요" | AI는 왜 이렇게 만들었는지 모름 | 결정 맥락을 ADR로 남기기 |
| README 없이 배포 | 새 팀원이 시작을 못함 | 5개 블록 README 만들기 |
| 런북 없이 운영 | 장애 시 파악에만 1시간 | 핵심 장애 시나리오 런북 준비 |
| 문서 소유자가 없음 | 문서가 점점 오래되고 신뢰 불가 | 각 문서에 담당자와 검토 일자 명시 |

## AI 팁: AI를 문서 작성 도구로 활용하기

AI는 문서 초안 작성에도 탁월합니다.

```
다음 함수의 docstring을 작성해줘:
- 함수가 하는 일을 한 줄로
- 매개변수 설명
- 반환값 설명
- 발생 가능한 예외

[함수 코드]
```

```
다음 시스템의 README를 작성해줘:
- 프로젝트 한 줄 소개
- 로컬 실행 방법 (단계별로)
- 환경 변수 목록
- 기여 방법

[프로젝트 설명]
```

단, AI가 만든 문서는 반드시 사람이 검토하고 실제로 실행해보면서 확인해야 합니다. AI는 "이렇게 실행하면 됩니다"라고 쓰지만, 실제로 안 되는 경우가 있습니다.

## 처음 질문으로 돌아가기

- **AI가 만든 코드에 문서가 없으면 어떤 문제가 생길까요?**
  - 모든 정보가 특정 사람의 기억에 묶입니다. 그 사람이 없으면 팀 전체가 느려지고, 장애 대응 시간이 늘어납니다.

- **ADR은 코드 주석과 어떻게 다를까요?**
  - 코드 주석은 "어떻게(How)"를 설명하고, ADR은 "왜(Why)"를 설명합니다. AI가 만든 코드에는 "왜 이 구조를 선택했는가"가 없습니다. ADR이 그 이유를 기록합니다.

- **장애 상황에서 문서가 없으면 어떤 일이 벌어질까요?**
  - 장애 원인 파악에 몇 배의 시간이 걸립니다. 런북이 있다면 10분에 끝날 일이 1시간이 되기도 합니다.

## 정리

문서화는 AI가 만든 코드가 팀과 시간을 넘어서 살아남게 하는 일입니다. README, ADR, docstring, 런북이 제자리에 있으면 팀은 특정 개인의 기억에 덜 의존하게 됩니다.

다음 글에서는 협업 프로세스를 다룹니다. AI와 함께 팀으로 일할 때, 어떻게 소통하고 결정을 내리고 기록을 남기는지 살펴봅니다.
