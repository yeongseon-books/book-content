# 바이브코딩을 위한 클린 코드 (10/10): AI 코드를 리뷰하는 방법

이 글은 바이브코딩을 위한 클린 코드 시리즈의 마지막 글입니다.

팀이 바이브코딩을 도입한 뒤 코드 리뷰가 이상해졌습니다. AI가 만든 400줄짜리 PR이 올라옵니다. 리뷰어는 "AI가 만든 거니까 동작은 하겠지"라는 생각으로 빠르게 승인하거나, 반대로 AI 코드의 모든 세부사항을 꼼꼼히 검토하다가 한 시간이 걸립니다. 리뷰 문화가 무너지고 있었습니다.

AI 코드를 리뷰하는 것은 사람이 쓴 코드를 리뷰하는 것과 다른 관점이 필요합니다. AI는 동작하는 코드를 빠르게 만들지만, 이 시리즈에서 다룬 모든 문제를 가져올 수 있습니다. 나쁜 이름, 거대 함수, 중첩 if, 중복 코드, `except: pass`, 테스트 불가능한 구조.

반면 AI 코드는 문법 오류나 단순한 로직 실수가 적습니다. 그래서 리뷰어가 봐야 할 것도 달라집니다. 세부 구현보다 구조와 경계를, 변수명 오타보다 이름의 의미를, 코드 자체보다 "다음에 이 코드를 수정할 때 얼마나 쉬울 것인가"를 봐야 합니다.

> AI 코드 리뷰의 핵심은 동작 확인이 아니라 유지보수 가능성 평가입니다.

---

## 이 글에서 다룰 문제
- AI가 만든 PR을 리뷰할 때 무엇을 중점적으로 봐야 하나요?
- 팀이 AI 코드 품질 기준을 어떻게 만들어야 할까요?
- 리뷰 코멘트를 실행 가능하게 작성하는 방법은 무엇인가요?
- 반복되는 AI 코드 문제를 자동화로 처리하는 방법은 무엇인가요?
- 바이브코딩 팀에서 코드 리뷰 문화를 어떻게 유지하나요?

## AI 코드 리뷰의 5가지 핵심 관점

### 1. 이름과 의도

AI는 동작하는 코드를 만들지만 의미 있는 이름을 보장하지 않습니다.

```
리뷰 질문:
- 함수 이름만 보고 무엇을 하는지 알 수 있는가?
- 변수명이 `a`, `data`, `temp` 같은 무의미한 이름인가?
- 도메인 언어와 코드 이름이 일치하는가?
```

### 2. 함수 크기와 책임

AI는 하나의 요청을 하나의 큰 함수에 담는 경향이 있습니다.

```
리뷰 질문:
- 함수가 한 가지 일만 하는가?
- 함수 본문을 읽었을 때 목차처럼 읽히는가?
- 한 함수가 검증, 계산, 저장, 알림을 모두 하는가?
```

### 3. 에러 처리

AI가 가장 자주 망치는 영역입니다.

```
리뷰 질문:
- except: pass나 빈 except 블록이 있는가?
- 에러 정보가 보존되는가?
- 입력 검증이 함수 초반에 있는가?
```

### 4. 테스트 가능성

```
리뷰 질문:
- 외부 의존성이 주입되는가?
- datetime.now(), requests.get() 같은 것이 함수 내부에 직접 있는가?
- 이 코드를 테스트하려면 무엇이 필요한가?
```

### 5. 중복과 구조

```
리뷰 질문:
- 같은 로직이 여러 곳에 있는가?
- 정책 상수가 여러 곳에 흩어져 있는가?
- 이 코드를 다음 달에 수정할 때 어디를 찾아야 하는가?
```

## 실행 가능한 리뷰 코멘트 작성

리뷰 코멘트는 실행 가능해야 합니다. "이 함수 너무 길어요"는 작성자가 무엇을 해야 할지 알기 어렵습니다.

```
나쁜 리뷰 코멘트:
"이 함수가 너무 길어요."

좋은 리뷰 코멘트:
"SUGG: process_order가 검증, 계산, 저장, 알림을 모두 하고 있어서
수정 시 영향 범위를 파악하기 어렵습니다.
validate_order, calculate_total, save_order, notify_user로
나누면 각 단계를 독립적으로 테스트할 수 있습니다.
(참고: 이번 PR에서 하거나 후속 PR로 처리해도 됩니다)"
```

우선순위 라벨을 사용하면 무엇이 필수이고 무엇이 선택인지 명확해집니다.

```
MUST: 병합 전에 반드시 수정
SUGG: 권장하지만 이번 PR에서 안 해도 됨
NIT: 사소한 개선 (선택)
QUESTION: 의도 확인 필요
```

## AI 코드 품질 자동화

반복되는 AI 코드 문제는 사람이 매번 지적하지 말고 도구로 처리해야 합니다.

```yaml
# CI 파이프라인
- run: ruff check .           # 이름 규칙, 코드 스타일
- run: ruff check . --select C90  # 순환 복잡도 (함수가 너무 복잡한지)
- run: pytest -q              # 테스트 통과 여부
```

```toml
# pyproject.toml
[tool.ruff.lint]
select = ["E", "F", "N", "B", "C90"]

[tool.ruff.lint.mccabe]
max-complexity = 10  # 이 이상이면 CI 실패
```

자동화가 처리할 수 있는 문제는 자동화에 맡기고, 사람은 "이 구조가 다음 변경을 쉽게 하는가"라는 더 중요한 질문에 집중해야 합니다.

## Before / After

```text
# 나쁜 리뷰 코멘트
"This function is too long."

# 좋은 리뷰 코멘트
"SUGG: process_payment가 60줄입니다.
validate_payment_input, calculate_discounted_amount,
charge_payment_gateway, send_receipt로 나누면:
1) 각 단계를 독립적으로 테스트할 수 있고
2) 할인 로직 변경 시 영향 범위가 명확해집니다.
이번 PR에서 분리하거나, 후속 리팩터링 PR에 이슈 링크해도 됩니다."
```

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| "AI가 만든 거니까 동작하겠지"로 승인 | 구조 문제가 쌓임 | AI 코드도 동일한 기준으로 리뷰 |
| 400줄 AI PR 한 번에 리뷰 | 아무도 제대로 못 읽음 | PR을 작게 만들도록 요청 |
| 취향 중심 코멘트 | 불필요한 마찰 | 근거(유지보수 비용)로 대화 |
| 반복 지적을 자동화하지 않음 | 리뷰어 시간 낭비 | lint 규칙으로 전환 |
| 리뷰에서 배운 것을 기록하지 않음 | 같은 실수 반복 | 팀 가이드에 패턴 추가 |

## AI에게 클린 코드 요청하는 팁

```
프롬프트 예시:
"이 PR을 만들어줘.
PR 규칙:
- 하나의 PR은 한 가지 책임만 다룰 것
- 400줄을 넘으면 분리할 것
- PR 설명에 What(무엇을 바꿨는지), Why(왜), How(어떻게 검증했는지), Risk(위험은 무엇인지) 포함
- 리팩터링과 기능 추가는 별도 PR로 분리"
```

## 운영 체크리스트
- [ ] PR이 한 가지 책임만 다루는가?
- [ ] CI가 통과하는가?
- [ ] 이름, 함수 크기, 에러 처리, 테스트 가능성을 모두 확인했는가?
- [ ] 리뷰 코멘트에 우선순위 라벨이 있는가?
- [ ] 반복되는 문제를 자동화로 옮길 수 있는가?

## 처음 질문으로 돌아가기

- **AI가 만든 PR을 리뷰할 때 무엇을 중점적으로 봐야 하나요?**
  동작 확인보다 이름의 의미, 함수의 단일 책임, 에러 처리 방식, 테스트 가능성, 중복 구조에 집중합니다.

- **팀이 AI 코드 품질 기준을 어떻게 만들어야 할까요?**
  반복되는 리뷰 코멘트를 lint 규칙으로 전환하고, PR 템플릿으로 기준을 고정하고, 팀 가이드에 AI 코드 패턴을 정리합니다.

- **반복되는 AI 코드 문제를 자동화로 처리하는 방법은?**
  `ruff`, `pytest` 같은 도구를 CI에 연결합니다. 같은 지적이 세 번 이상 반복되면 lint 규칙으로 전환을 고려합니다.

## 정리

바이브코딩이 코딩의 속도를 높였다면, 코드 리뷰는 그 품질을 유지하는 마지막 게이트입니다. AI 코드 리뷰는 동작 확인이 아니라 유지보수 가능성 평가입니다. 이름, 함수 크기, 에러 처리, 테스트 가능성이라는 이 시리즈에서 다룬 모든 관점이 리뷰 기준이 됩니다. 반복되는 문제는 자동화하고, 사람은 "이 코드가 다음 변경을 쉽게 하는가"라는 더 중요한 질문에 집중하세요.

이 시리즈 전체를 통해 다룬 것은 결국 하나입니다. AI가 만든 코드를 받은 뒤, 그것을 내가 미래에도 수정할 수 있는 코드로 만드는 방법입니다. 이름, 함수, 조건문, 중복, 에러, 주석, 테스트, 리팩터링, 리뷰. 이 9가지 습관이 쌓이면 AI와 함께 일하는 방식이 훨씬 지속 가능해집니다.
