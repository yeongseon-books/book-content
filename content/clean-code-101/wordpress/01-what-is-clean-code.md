# 바이브코딩을 위한 클린 코드 (1/10): AI 코드는 돌아가지만 읽기 어렵다

이 글은 바이브코딩을 위한 클린 코드 시리즈의 1번째 글입니다.

ChatGPT나 Claude에게 "주문 처리 함수 짜줘"라고 시켰더니 80줄짜리 코드가 나왔습니다. 실행해 봤더니 동작합니다. 기뻤습니다. 그런데 일주일 뒤 요구사항이 바뀌어서 수정하려고 코드를 열었을 때, 어디를 건드려야 할지 전혀 감이 안 왔습니다. 변수 이름은 `d`, `t`, `r`이고, 함수 안에 검증, 계산, 저장, 이메일 발송이 전부 들어 있었습니다. 건드리면 다른 곳이 깨질 것 같아 결국 AI에게 다시 물어봤습니다. AI는 또 새 코드를 뱉어냈고, 이번에도 어딘가 비슷한 문제가 있었습니다.

바이브코딩에서 가장 많이 겪는 패턴입니다. AI는 동작하는 코드를 빠르게 만들어 줍니다. 하지만 그 코드가 왜 그렇게 작성되었는지, 어떤 경계로 나뉘어 있는지는 설명하지 않습니다. 그 결과 코드베이스는 점점 쌓이지만, 각 부분이 무엇을 하는지 파악하는 데 드는 시간도 같이 늘어납니다.

클린 코드는 "예쁜 코드"를 만드는 취향 문제가 아닙니다. AI가 생성한 코드를 내가 다음 달에도 수정할 수 있게 만드는 실용적인 기술입니다. 함수 길이, 변수 이름, 분기 깊이 같은 작은 원칙들이 모이면 "건드리면 깨질 것 같은 코드"와 "어디를 고쳐야 하는지 바로 보이는 코드"의 차이가 됩니다.

> AI가 생성한 코드가 동작한다는 것은 시작일 뿐입니다. 클린 코드는 그 코드를 다음에도 수정할 수 있게 만드는 작업입니다.

---

## 이 글에서 다룰 문제
- AI가 만든 코드가 동작하는데도 왜 수정하기 무서운가요?
- 클린 코드를 판단할 때 어떤 신호를 먼저 봐야 할까요?
- 함수 길이, 변수 이름, 들여쓰기가 실제 유지보수 비용에 얼마나 영향을 미칠까요?
- AI에게 코드를 받은 뒤 바로 배포하면 어떤 위험이 생길까요?
- 기술 부채를 "나중에 고치면 된다"고 두면 실제로 비용이 어떻게 변할까요?

## AI가 코드를 만드는 방식의 특성

AI는 주어진 요청을 "동작하는 방식"으로 가장 빠르게 채웁니다. 이름의 일관성, 함수의 크기, 책임의 경계 같은 것은 명시적으로 요청하지 않으면 최적화 대상이 아닙니다. 짧은 변수명 `d`는 AI 입장에서 완전히 유효한 선택입니다. 동작하니까요.

문제는 코드를 나중에 읽고 수정하는 사람, 즉 미래의 나 자신이 그 코드를 처음 보는 사람과 같은 상황에 놓인다는 것입니다. 코드는 한 번 작성되고 여러 번 읽힙니다. 그래서 가독성은 단순한 미학이 아니라 변경 비용을 결정하는 실질적인 요소입니다.

### 클린 코드의 핵심 신호

AI 코드를 받은 뒤 가장 먼저 확인해야 할 신호들이 있습니다.

**1. 함수 길이**
```python
# AI가 생성한 코드 (나쁜 예)
def process_order(order_data, user_id, db, email_client, logger):
    # 검증 로직 20줄
    # 가격 계산 20줄
    # 데이터 저장 20줄
    # 이메일 발송 20줄
    # 로깅 10줄
    pass  # 총 90줄
```

함수가 20줄을 넘기 시작하면 너무 많은 일을 하고 있다는 신호입니다. AI는 하나의 요청에 모든 것을 채워 넣는 경향이 있습니다.

**2. 변수 이름**
```python
# AI가 자주 만드는 패턴
def f(d, t):
    return d * (1 + t)

# 클린 코드 버전
def calculate_total_with_tax(amount: int, tax_rate: float) -> float:
    return amount * (1 + tax_rate)
```

두 번째 버전은 길이가 조금 늘었을 뿐이지만, 호출하는 쪽에서 의도가 바로 보입니다.

**3. 들여쓰기 깊이**
```python
# AI가 생성한 중첩 if
def check_order(user, order, payment):
    if user:
        if user.is_active:
            if order:
                if order.is_valid:
                    if payment.is_confirmed:
                        return True
    return False
```

들여쓰기가 3단을 넘으면 가드 절(Guard Clause)로 평탄화할 수 있다는 신호입니다.

## Before / After

```python
# AI가 생성한 코드
def f(d, t):
    return d * (1 + t)
```

```python
# 클린 코드 버전
def calculate_total_with_tax(amount: int, tax_rate: float) -> float:
    """세금을 포함한 최종 금액을 계산합니다."""
    return amount * (1 + tax_rate)
```

코드 길이는 거의 같지만, 두 번째는 인자가 무엇을 뜻하는지, 반환값이 무엇인지 이름만으로 전달됩니다.

## 바이브코딩할 때 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|------|------------|------|
| AI 코드를 그대로 배포 | 한 달 뒤 수정 불가 | 이름과 구조를 먼저 정리 |
| 동작 확인만 하고 리뷰 생략 | 기술 부채 누적 | 간단한 클린 코드 체크 추가 |
| 긴 함수 방치 | 디버깅과 변경이 동시에 어려움 | 함수 하나의 책임 하나 원칙 |
| 의미 없는 변수명 방치 | 코드 전체를 읽어야 이해 가능 | 이름 변경 요청 프롬프트 추가 |
| 기술 부채를 나중으로 미룸 | 복리로 비용이 증가 | 받은 즉시 최소 정리 |

## AI에게 클린 코드 요청하는 팁

AI에게 코드를 요청할 때 다음 조건을 추가하면 훨씬 읽기 좋은 결과를 얻을 수 있습니다.

```
프롬프트 예시:
"주문 처리 함수를 만들어줘.
조건:
- 함수는 한 가지 일만 해야 함
- 변수명과 함수명은 의도를 명확히 드러내야 함
- 들여쓰기는 2단 이하로 유지
- 각 함수는 20줄 이하"
```

이렇게 요청하면 AI도 제약 조건을 따르려고 시도합니다. 완벽하지 않더라도 시작점이 훨씬 좋아집니다.

## 운영 체크리스트
- [ ] 함수가 20줄 이하인가?
- [ ] 인자가 3개 이하인가?
- [ ] 들여쓰기 깊이가 3 이하인가?
- [ ] 이름이 의도를 말하는가?
- [ ] 이 코드를 한 달 뒤에 수정할 수 있겠는가?

## 처음 질문으로 돌아가기

- **AI가 만든 코드가 동작하는데도 왜 수정하기 무서운가요?**
  함수가 너무 많은 일을 하고, 이름이 의도를 숨기고, 들여쓰기가 깊으면 어디를 건드려야 하는지 파악하는 것 자체가 어렵습니다. 동작한다는 것은 시작일 뿐이고, 수정 가능성은 구조에서 옵니다.

- **클린 코드를 판단할 때 어떤 신호를 먼저 봐야 할까요?**
  함수 길이, 인자 개수, 들여쓰기 깊이, 이름의 정직성이 핵심 신호입니다. `radon cc`나 `ruff`로 측정하면 감상이 아닌 근거로 판단할 수 있습니다.

- **기술 부채를 나중에 고치면 된다고 두면?**
  지연할수록 수정 시간이 복리로 증가합니다. 지금 1시간이면 3개월 뒤에는 5시간이 될 수 있습니다.

## 정리

AI는 동작하는 코드를 빠르게 줍니다. 클린 코드는 그 코드를 미래에도 수정할 수 있게 만드는 작업입니다. 이름, 함수 크기, 분기 깊이라는 작은 원칙이 모여 "건드리면 깨지는 코드"와 "안심하고 수정할 수 있는 코드"의 차이를 만듭니다. 다음 글에서는 AI가 가장 자주 잘못 만드는 변수명 문제를 다룹니다.
