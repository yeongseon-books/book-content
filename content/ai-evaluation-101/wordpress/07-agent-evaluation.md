# 바이브코딩을 위한 AI 평가 (7/10): 에이전트 평가하기 — 단일 응답이 아닌 trajectory

> 이 글은 **바이브코딩을 위한 AI 평가** 시리즈 7편입니다. AI 에이전트의 행동 궤적(trajectory) 전체를 평가하는 방법을 다룹니다.

바이브코딩으로 AI 에이전트를 만들면 평가가 갑자기 어려워진다. 단순한 Q&A 앱은 입력 → 출력을 보면 됐는데, 에이전트는 여러 단계를 거치며 도구를 호출하고 결정을 내린다. 최종 답변만 보면 중간 과정에서 무슨 일이 있었는지 알 수 없다.

에이전트 평가에서는 trajectory가 핵심이다. 에이전트가 목표를 달성하기 위해 선택한 행동들의 시퀀스 전체를 본다. "도구를 올바른 순서로 호출했는가?", "불필요한 도구 호출이 있었는가?", "오류가 발생했을 때 올바르게 복구했는가?"

Trajectory 평가에는 세 가지 측면이 있다. 첫째, 결과 평가(Outcome): 최종 목표를 달성했는가? 둘째, 효율성 평가(Efficiency): 불필요한 단계 없이 목표에 도달했는가? 셋째, 안전성 평가(Safety): 위험한 도구 호출이나 데이터 접근이 없었는가?

도구 사용 평가도 중요하다. 에이전트가 올바른 도구를 골랐는가? 도구에 전달한 파라미터가 정확한가? 도구 결과를 올바르게 해석했는가? 이 세 가지가 모두 맞아야 좋은 에이전트다.

환경 시뮬레이터가 있으면 훨씬 풍부한 평가가 가능하다. 실제 API를 호출하지 않고 시뮬레이션 환경에서 에이전트를 실행해 결정론적으로 평가할 수 있다. 바이브코딩 환경에서는 처음에 실제 도구로 시작해도 좋지만, 프로덕션 수준에서는 샌드박스 환경이 필요하다.

> 에이전트를 평가할 때는 "결과가 좋으면 됐다"는 생각을 버려야 한다. 운 좋게 맞은 결과보다 올바른 과정이 더 중요하다. 과정이 올바르지 않으면 다음번에는 같은 결과를 보장할 수 없다.

## 이 글에서 다룰 문제

- 에이전트 평가가 단순 Q&A 평가와 근본적으로 다른 이유는 무엇인가요?
- Trajectory 평가에서 무엇을 측정해야 할까요?
- 도구 선택과 파라미터 정확도를 어떻게 평가할 수 있나요?
- 환경 시뮬레이터 없이 에이전트를 어떻게 평가할 수 있나요?
- 멀티-에이전트 시스템은 어떻게 평가하나요?

## Before / After: 에이전트 평가 전후

| 상황 | 평가 없이 | Trajectory 평가 후 |
|------|---------|-------------------|
| 실패 원인 파악 | "왜 실패했는지 모름" | 3번째 도구 호출에서 파라미터 오류 |
| 불필요한 API 호출 | 비용 폭증 원인 불명 | 평균 7회 호출이어야 하는데 12회 |
| 안전성 검증 | "혹시 위험한 일을 하진 않을까" 불안 | 위험 패턴 자동 탐지 |
| 개선 방향 | 막막함 | 효율성 낮은 단계 집중 개선 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 최종 결과만 평가 | 과정 오류 탐지 불가 | Trajectory 전체 기록 및 평가 |
| 결정론적 환경 없음 | 평가 재현 불가 | 시뮬레이터 또는 테스트 픽스처 구축 |
| 안전성 평가 누락 | 프로덕션에서 위험 행동 발생 | 위험 패턴 체크리스트 필수 |
| 단일 태스크만 평가 | 실제 사용 범위 미반영 | 다양한 태스크 유형 커버 |

## AI 팁: 에이전트 trajectory 빠르게 기록하는 법

LangChain이나 LangSmith를 쓰면 에이전트의 모든 단계를 자동으로 기록할 수 있다. 직접 구현한다면, 각 도구 호출 전후에 로그를 남기는 래퍼(wrapper)를 만드는 것이 가장 간단하다. 기록된 trajectory를 LLM-as-Judge에 넣어서 "이 행동 시퀀스가 최적인가?"를 평가하는 방식도 효과적이다.

## 운영 체크리스트

- [ ] 에이전트의 모든 도구 호출을 로그로 기록하는가
- [ ] Trajectory 전체를 기반으로 결과, 효율성, 안전성을 평가하는가
- [ ] 도구 선택과 파라미터 정확도를 독립적으로 평가하는가
- [ ] 위험한 행동 패턴을 자동으로 탐지하는 체크리스트가 있는가
- [ ] 평가 환경과 프로덕션 환경을 분리했는가

## 처음 질문으로 돌아가기

- **에이전트 평가가 Q&A 평가와 다른 이유는?** 여러 단계의 결정을 연쇄적으로 내리기 때문에, 어느 단계에서 문제가 생겼는지 분리해서 봐야 한다.
- **Trajectory에서 무엇을 측정?** 결과(목표 달성), 효율성(불필요 단계), 안전성(위험 패턴).
- **시뮬레이터 없이 평가 방법은?** 실제 도구 호출 로그를 남기고, LLM-as-Judge로 trajectory를 사후 평가한다.

## 정리

에이전트 평가는 단순히 "결과가 맞는가"를 넘어선다. 올바른 과정을 거쳐 결과에 도달했는가가 핵심이다. Trajectory를 기록하고, 단계별로 평가하고, 위험 패턴을 탐지하는 것이 에이전트 품질 관리의 기본이다.
