# 바이브코딩을 위한 AI 평가 (6/10): RAG 시스템 평가하기

> 이 글은 **바이브코딩을 위한 AI 평가** 시리즈 6편입니다. RAG(Retrieval-Augmented Generation) 시스템의 검색 품질과 생성 품질을 분리해 평가하는 방법을 다룹니다.

바이브코딩으로 RAG 앱을 만들면 흔한 함정에 빠진다. "답변이 나오긴 하는데 왜 틀렸지?" 또는 "검색은 잘 되는데 답변이 이상해"라는 상황이다. RAG는 두 단계—검색(Retrieval)과 생성(Generation)—로 이루어져 있어서, 어느 단계에서 문제가 생겼는지 구분하는 것이 핵심이다.

RAG 평가는 이 두 단계를 분리해서 측정한다. 검색 단계 평가에서는 "올바른 문서가 검색됐는가"를 본다. Recall@K, MRR, nDCG 같은 지표를 쓴다. 생성 단계 평가에서는 두 가지를 본다. 충실성(Faithfulness): 답변이 검색된 문서에 근거하는가? 관련성(Answer Relevance): 답변이 질문에 적절한가?

RAGAS 프레임워크는 이 세 가지를 한 번에 측정하는 도구다. Context Precision, Context Recall, Faithfulness, Answer Relevance를 자동으로 계산해준다. 바이브코딩 환경에서 RAG 앱을 처음 평가할 때 가장 빠르게 시작할 수 있는 도구다.

할루시네이션 감지도 중요하다. LLM이 검색된 문서에 없는 내용을 사실처럼 생성하는 경우를 탐지해야 한다. "답변의 각 주장이 검색된 문서에 있는가"를 LLM-as-Judge로 체크하는 방식이 가장 실용적이다.

RAG 앱을 만든 바이브코더에게 전달하고 싶은 메시지는 이것이다: 전체 파이프라인을 한 번에 평가하지 말라. 검색이 맞는지 먼저 확인하고, 그다음 생성이 검색 결과를 올바르게 활용하는지 확인하라. 이 순서가 문제를 훨씬 빠르게 찾게 해준다.

> RAG에서 답변이 나쁜 이유는 두 가지다. 잘못된 문서를 가져왔거나, 올바른 문서를 잘못 활용했거나. 이 둘을 구분하지 못하면 개선 방향을 잡기 어렵다.

## 이 글에서 다룰 문제

- RAG 평가를 검색 단계와 생성 단계로 분리해야 하는 이유는 무엇인가요?
- Faithfulness와 Answer Relevance는 각각 무엇을 측정하고 어떻게 계산하나요?
- RAGAS 프레임워크를 어떻게 시작할 수 있나요?
- RAG 시스템의 할루시네이션을 어떻게 탐지할 수 있나요?
- Context Window가 가득 찰 때 어떤 평가 문제가 생기나요?

## Before / After: RAG 평가 전후

| 상황 | 평가 없이 | RAG 평가 적용 후 |
|------|---------|----------------|
| 답변 오류 원인 | "모델이 나쁜가? 데이터가 나쁜가?" 불명 | 검색 Recall@5 0.43 → 검색 단계 문제 |
| 할루시네이션 | 사용자가 발견해서 보고 | Faithfulness 0.61로 자동 탐지 |
| 청크 설정 개선 | 근거 없이 크기 조정 | Context Precision 변화로 효과 측정 |
| 새 문서 추가 효과 | 체감으로만 판단 | 지표 변화로 정량 확인 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 전체 파이프라인만 평가 | 어디서 문제인지 모름 | 검색/생성 단계 분리 측정 |
| 검색 없이 생성만 평가 | 검색 품질 저하 탐지 불가 | Recall@K 필수 측정 |
| 단일 질의 유형만 테스트 | 엣지 케이스 놓침 | 사실형/추론형/비교형 균형 |
| 할루시네이션 미확인 | 틀린 정보 사용자에게 노출 | Faithfulness 점수 모니터링 |

## AI 팁: RAGAS 빠르게 시작하는 방법

`pip install ragas`를 설치하고, 질문 10개와 각 질문에 대한 검색 컨텍스트, 정답, 실제 LLM 답변을 준비한다. RAGAS의 `evaluate()` 함수에 이를 넣으면 자동으로 네 가지 지표를 계산해준다. 처음 결과를 보면서 어느 지표가 낮은지 확인하고, 낮은 지표가 있는 케이스를 직접 살펴보면 문제를 빠르게 파악할 수 있다.

## 운영 체크리스트

- [ ] 검색 단계와 생성 단계를 분리해서 평가하는가
- [ ] 검색 품질에 Recall@K 또는 MRR을 사용하는가
- [ ] Faithfulness 점수로 할루시네이션을 모니터링하는가
- [ ] Answer Relevance로 생성 품질을 측정하는가
- [ ] 컨텍스트 길이가 성능에 미치는 영향을 테스트했는가

## 처음 질문으로 돌아가기

- **검색/생성 분리 평가가 중요한 이유?** 문제의 원인을 특정해야 개선이 가능하다. 모두를 한 번에 보면 어디를 고쳐야 하는지 알 수 없다.
- **Faithfulness 계산 방법은?** 답변의 각 주장이 검색된 문서에서 지지되는지 LLM으로 확인하고, 지지되는 주장의 비율을 계산한다.
- **RAGAS vs 자체 구현?** 시작은 RAGAS. 팀 특화 요구사항이 생기면 자체 구현으로 이동한다.

## 정리

RAG 시스템 평가는 "답변이 좋은가"를 넘어서, "올바른 정보를 찾았는가"와 "찾은 정보를 올바르게 활용했는가"를 분리해서 봐야 한다. 이 두 단계를 구분하는 순간 개선이 빨라진다.
