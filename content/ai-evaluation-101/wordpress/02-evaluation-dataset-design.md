# 바이브코딩을 위한 AI 평가 (2/10): 평가 데이터셋 설계하기

> 이 글은 **바이브코딩을 위한 AI 평가** 시리즈 2편입니다. LLM 앱의 품질을 측정하는 가장 중요한 자산인 평가 데이터셋을 어떻게 설계하는지 다룹니다.

바이브코딩으로 AI 앱을 만들다 보면 평가 데이터셋이 가장 먼저 건너뛰는 단계가 된다. "나중에 사용자 데이터가 쌓이면 만들지 뭐"라는 생각이 자연스럽게 든다. 하지만 그 "나중"이 왔을 때 이미 앱은 여러 번 변경됐고, 무엇을 기준으로 비교해야 하는지 알 수 없게 된다.

좋은 평가 데이터셋은 앱을 만들기 시작할 때부터 함께 자라야 한다. 처음에는 10개의 케이스로 시작해도 충분하다. 중요한 것은 이 케이스들이 실제 사용 시나리오를 반영하고, 각 케이스에 명확한 채점 기준이 붙어 있는 것이다.

골든 데이터셋이라고 부르는 이유가 있다. 잘 만들어진 평가 데이터셋은 팀 전체가 앱 품질을 이해하는 공통 언어가 된다. 새 팀원이 합류했을 때, 프롬프트를 바꿀 때, 새 모델로 업그레이드할 때 이 데이터셋이 기준점이 된다.

데이터셋 설계에서 가장 중요한 것은 라벨링 가이드라인이다. "정답"이 무엇인지 모두가 동의할 수 있어야 한다. 모호한 기준으로 만든 데이터셋은 채점 결과도 모호하고, 개선 방향도 불분명해진다. 라벨러가 바뀌어도 같은 판단을 내릴 수 있어야 좋은 가이드라인이다.

이 글에서는 바이브코더가 현실적으로 평가 데이터셋을 설계하는 방법을 단계별로 정리한다. 처음부터 완벽한 데이터셋을 만들려고 하면 시작조차 어렵다. 작게 시작하고 빠르게 이터레이션하는 방법을 배운다.

> 평가 데이터셋은 앱의 "계약서"다. 이 앱이 무엇을 잘해야 하는지 명시적으로 정의하는 문서이자, 그것을 측정하는 도구다.

## 이 글에서 다룰 문제

- 골든 데이터셋은 어떤 케이스로 구성해야 할까요?
- 라벨링 가이드라인을 어떻게 작성해야 일관성을 높일 수 있을까요?
- 데이터 누수(data leakage)를 어떻게 방지할 수 있을까요?
- LLM으로 평가 데이터를 보강할 때 주의할 점은 무엇일까요?
- 데이터셋이 현실을 반영하는지 어떻게 검증할 수 있을까요?

## Before / After: 평가 데이터셋 유무 차이

| 상황 | 데이터셋 없이 | 골든 데이터셋 적용 후 |
|------|--------------|---------------------|
| 품질 기준 | "써보니 괜찮은 것 같아요" | 94개 케이스 중 89개 통과 기준 명확 |
| 모델 교체 판단 | "느낌상 더 나은 것 같아요" | A 모델 88%, B 모델 93%, B 선택 |
| 팀 기준 공유 | 개인마다 다른 품질 인식 | 같은 채점 기준으로 통일 |
| 신기능 영향 | "혹시 뭔가 망가졌나요?" 불안 | 회귀 케이스 자동 탐지 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 테스트셋과 학습셋 혼용 | 낙관적 점수, 실제 성능 과대평가 | 엄격히 분리된 데이터셋 유지 |
| 채점 기준 없이 데이터만 수집 | 라벨러마다 다른 판단 | 라벨링 가이드라인 먼저 작성 |
| 쉬운 케이스만 포함 | 경계 조건과 엣지 케이스 누락 | 정상/경계/실패 케이스 균형 있게 |
| 한 번 만들고 고정 | 현실과 괴리 증가 | 주기적 데이터셋 리뷰와 갱신 |

## AI 팁: 데이터셋 빠르게 시작하는 방법

실제 사용 로그에서 케이스를 수집하는 것이 가장 현실적이다. 로그가 없다면 Claude나 GPT-4에 "이 앱의 전형적인 사용 시나리오 20개를 생성해줘"라고 요청해 시작점을 만들 수 있다. 단, 생성된 케이스는 팀원이 반드시 검토해야 하고, 경계 케이스와 실패 케이스를 의도적으로 추가해야 한다. AI가 생성한 케이스만으로는 너무 "깔끔한" 데이터셋이 되는 경향이 있다.

## 운영 체크리스트

- [ ] 평가 데이터셋이 학습/파인튜닝 데이터와 완전히 분리되어 있는가
- [ ] 각 케이스에 라벨링 기준이 명확하게 정의되어 있는가
- [ ] 정상 케이스 외에 경계 케이스와 실패 케이스가 포함되어 있는가
- [ ] 새 케이스 추가 절차와 주기가 정해져 있는가
- [ ] 라벨러 간 일치도(Inter-Annotator Agreement)를 측정하는가

## 처음 질문으로 돌아가기

- **골든 데이터셋 구성 케이스는?** 정상 케이스 60%, 경계 케이스 30%, 의도적 실패 케이스 10%. 이 비율이 현실적인 분포와 가깝다.
- **라벨링 가이드라인을 어떻게 쓸까요?** "이것은 좋은 답변이다"의 기준을 구체적 예시와 함께 서술한다. 추상적 기준보다 예시 기반 기준이 일관성이 높다.
- **데이터 누수 방지 방법은?** 평가셋 데이터를 프롬프트 엔지니어링에 활용하지 않는다. 절대 규칙이다.

## 정리

평가 데이터셋은 LLM 앱의 품질 기준을 코드와 데이터로 명문화하는 작업이다. 처음에는 10개의 케이스로 시작해도 충분하다. 중요한 것은 지금 당장 시작하는 것이다.

라벨링 가이드라인이 있어야 팀 전체가 같은 기준으로 품질을 이야기할 수 있다. 앱이 커질수록 이 공통 언어의 가치는 더 커진다.
