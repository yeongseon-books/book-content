# 바이브코딩을 위한 AI 평가 (10/10): 운영 환경에서의 지속적 평가

> 이 글은 **바이브코딩을 위한 AI 평가** 시리즈 마지막 편입니다. 프로덕션 환경에서 LLM 앱 품질을 지속적으로 모니터링하고 개선하는 방법을 다룹니다.

바이브코딩으로 AI 앱을 배포했다. 그런데 배포 순간이 끝이 아니다. 실제 사용자가 사용하면서 앱의 품질은 계속 변화한다. 모델 프로바이더가 모델을 조용히 업데이트했을 수도 있고, 사용자의 질문 패턴이 바뀌었을 수도 있고, 외부 데이터 소스가 변했을 수도 있다. 이를 데이터 드리프트(drift)라고 한다.

프로덕션 평가는 개발 단계 평가와 다르다. 개발 단계에서는 미리 준비한 테스트셋으로 평가했다면, 프로덕션에서는 실제 사용자의 요청을 모니터링해야 한다. 모든 요청을 평가할 수는 없으므로 샘플링 전략이 필요하다.

자동화된 품질 신호가 핵심이다. LLM-as-Judge를 사용해 실시간으로 답변 품질을 점수화하고, 사용자 피드백(thumbs up/down, 세션 이탈, 재질의)을 암묵적 신호로 활용한다. 이 두 가지를 결합하면 배포된 앱의 품질 상태를 실시간으로 파악할 수 있다.

드리프트 감지 알림 시스템도 필요하다. 일주일 평균 점수가 기준보다 5% 이상 떨어지면 알림을 보내는 규칙을 만들면, 조용히 품질이 저하되는 상황을 빠르게 포착할 수 있다.

사람 검토 루프도 빠뜨릴 수 없다. 자동 채점 점수가 낮은 케이스를 큐에 쌓아 두고, 팀원이 주기적으로 검토해서 패턴을 파악한다. 이 패턴이 새로운 평가 케이스로 이어지고, 앱 개선으로 이어지는 선순환이 만들어진다.

> 프로덕션 평가가 없으면 앱은 서서히 나빠진다. 사용자는 알고 있지만 팀은 마지막에야 알게 된다. 지속적인 모니터링은 그 간격을 최소화한다.

## 이 글에서 다룰 문제

- 프로덕션 환경의 품질 모니터링이 개발 단계 평가와 어떻게 다른가요?
- 실시간 품질 신호를 어떻게 수집하고 활용할 수 있나요?
- 드리프트를 자동으로 감지하는 시스템은 어떻게 구축하나요?
- 사람 검토 루프를 효율적으로 운영하는 방법은 무엇인가요?
- 시리즈 전체를 통해 어떤 평가 스택을 만들었는가요?

## Before / After: 지속적 평가 전후

| 상황 | 도입 전 | 도입 후 |
|------|---------|---------|
| 품질 저하 감지 | 사용자 불만 쌓인 뒤 인지 | 자동 알림으로 48시간 내 감지 |
| 모델 변경 영향 | 우연히 발견 | 드리프트 감지 시스템이 즉시 탐지 |
| 개선 우선순위 | 팀원 직관 | 낮은 점수 케이스 데이터 기반 판단 |
| 사용자 피드백 활용 | 정성적 메시지만 | thumbs down이 자동 검토 큐에 추가 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 배포 후 평가 종료 | 조용한 품질 저하 | 지속적 모니터링 파이프라인 구축 |
| 전량 자동 채점만 | 사람 판단 없어 편향 누적 | 자동+사람 검토 혼합 |
| 드리프트 기준 없음 | 언제 대응해야 할지 모름 | 명확한 기준치와 알림 규칙 설정 |
| 사용자 피드백 미수집 | 실제 품질 신호 누락 | 간단한 thumbs up/down 기능 추가 |

## AI 팁: 간단한 모니터링 시작하는 방법

Langsmith나 자체 로깅으로 모든 LLM 호출을 기록하는 것부터 시작한다. 그런 다음 매일 자정에 전날 요청 중 10%를 샘플링해서 자동으로 LLM-as-Judge 채점을 돌리는 스크립트를 만든다. 결과를 Slack에 보내는 것만으로도 기본 모니터링이 완성된다. 거창하게 시작할 필요 없다.

## 운영 체크리스트

- [ ] 프로덕션 요청의 샘플을 자동으로 평가하는 파이프라인이 있는가
- [ ] 사용자 피드백 신호를 수집하고 품질 지표와 연결하는가
- [ ] 드리프트 감지 알림이 설정되어 있는가
- [ ] 낮은 점수 케이스를 사람이 검토하는 프로세스가 있는가
- [ ] 검토 결과가 평가 데이터셋 업데이트로 이어지는가

## 처음 질문으로 돌아가기

- **프로덕션 평가가 개발 단계 평가와 다른 이유는?** 실제 사용자 요청은 테스트셋보다 훨씬 다양하고 예측 불가능하다. 샘플링과 실시간 모니터링이 필요하다.
- **드리프트 감지 방법은?** 주간 평균 점수를 기준선과 비교하고, 통계적으로 유의미한 하락 시 알림.
- **사람 검토 루프 효율화는?** 자동 채점 낮은 케이스만 큐에 쌓아 우선순위 검토.

## 정리: 시리즈를 마치며

이 시리즈를 통해 바이브코딩으로 AI 앱을 만드는 개발자가 갖춰야 할 평가 역량을 단계별로 살펴봤다.

1편: 왜 평가가 필요한가 — 측정 없는 개선은 없다
2편: 데이터셋 설계 — 무엇을 평가할지 정의
3편: 결정적 지표 — 빠르고 재현 가능한 측정
4편: LLM-as-Judge — 확장 가능한 품질 채점
5편: Rubric 설계 — 여러 차원을 동시에 측정
6편: RAG 평가 — 검색과 생성을 분리해서 봐야
7편: 에이전트 평가 — 과정이 결과만큼 중요
8편: 회귀 테스트 — 어제 잘 된 게 오늘도 잘 되게
9편: A/B 테스팅 — 통계로 결정하기
10편: 지속적 평가 — 배포 후에도 계속

이 스택을 모두 갖추면, 바이브코딩의 속도를 유지하면서도 품질을 측정하고 개선할 수 있는 안정적인 AI 앱 개발이 가능해진다.
