# 바이브코딩을 위한 AI 평가 (3/10): 결정적 지표 — Exact Match, BLEU, ROUGE, Token F1

> 이 글은 **바이브코딩을 위한 AI 평가** 시리즈 3편입니다. 사람 판단 없이 코드로만 채점할 수 있는 결정적(deterministic) 평가 지표를 다룹니다.

바이브코딩으로 LLM 앱을 만들 때 평가 지표를 선택하는 순간이 온다. "내 앱이 올바른 답을 내고 있는가"를 코드로 측정하고 싶은데, 어떤 수를 써야 할지 막막하다. LLM 출력은 사람마다 다르게 쓰고, 같은 의미라도 표현이 다를 수 있어서 단순히 문자열이 같은지 비교하면 놓치는 케이스가 너무 많다.

결정적 지표는 사람 판단 없이 수식으로 계산되는 점수다. 빠르고, 재현 가능하고, CI 파이프라인에 바로 넣을 수 있다는 장점이 있다. 단점은 의미적 유사성을 완전히 포착하지 못한다는 것이다.

Exact Match는 가장 단순하다. 정답과 완전히 일치하면 1, 아니면 0. 분류 태스크나 단답형 QA에 쓰기 좋다. BLEU는 n-gram 겹침을 기반으로 점수를 내는데, 번역 품질 평가에서 유래했다. ROUGE는 요약 품질 평가에서 많이 쓰이며 재현율(recall) 중심이다. Token F1은 두 텍스트 간 토큰 수준의 정밀도와 재현율을 결합한다.

중요한 것은 이 지표들이 서로 보완 관계라는 사실이다. 하나의 지표로는 LLM 출력의 다양한 면을 다 포착할 수 없다. 태스크 특성에 맞게 지표를 선택하고, 여러 지표를 함께 보는 것이 좋다.

바이브코더에게 실용적인 조언은 이렇다. 분류 태스크면 Exact Match부터, 텍스트 생성 태스크면 ROUGE-L을 시작점으로, 추출형 QA면 Token F1을 써라. 그리고 LLM-as-Judge(4편)와 함께 쓰면 결정적 지표의 한계를 보완할 수 있다.

> 결정적 지표는 빠른 신호등이다. 코드 변경이 품질에 영향을 줬는지 1초 안에 알려주지만, 최종 품질 판단은 항상 여러 신호를 함께 봐야 한다.

## 이 글에서 다룰 문제

- Exact Match, BLEU, ROUGE, Token F1은 각각 어떤 태스크에 적합할까요?
- 같은 의미지만 다른 표현의 출력을 어떻게 공정하게 채점할 수 있을까요?
- 결정적 지표의 한계는 무엇이고, 어떻게 보완할 수 있을까요?
- Python 코드로 각 지표를 어떻게 구현하나요?
- CI에서 결정적 지표를 어떻게 실행할 수 있을까요?

## Before / After: 결정적 지표 도입 전후

| 상황 | 도입 전 | 도입 후 |
|------|---------|---------|
| 프롬프트 변경 후 | 수동으로 몇 개 확인 | ROUGE-L 점수 자동 계산, 변화량 파악 |
| 모델 A vs B 비교 | "B가 좀 더 자연스러운 것 같아요" | Token F1 A: 0.73, B: 0.81, B 선택 |
| CI 통과 기준 | 없음 | ROUGE-L >= 0.65 기준 자동 체크 |
| 회귀 탐지 | 배포 후 사용자 불만 | 기준 미달 시 PR 블락 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 생성 태스크에 Exact Match 사용 | 정답인데 0점, 지표 무의미 | ROUGE-L 또는 Token F1 사용 |
| BLEU를 긴 텍스트 평가에 사용 | brevity penalty로 점수 왜곡 | 짧은 출력 번역 태스크에만 적용 |
| 단일 지표로만 판단 | 지표 과적합, 실제 품질 놓침 | 여러 지표 + LLM-as-Judge 병행 |
| 정규화 없이 비교 | 대소문자/공백 차이로 틀린 판정 | 전처리 파이프라인 표준화 |

## AI 팁: 어떤 지표를 쓸지 모를 때

태스크를 세 가지로 분류해보자. (1) 정확히 맞아야 하는 답(분류, 단답): Exact Match. (2) 정보 포함 여부가 중요한 답(요약, 추출): ROUGE 계열. (3) 정밀도와 재현율 균형이 필요한 답(QA, 정보 추출): Token F1. 여기서 시작해서 실제 평가 결과와 사람 판단이 얼마나 일치하는지 확인하며 조정한다.

## 운영 체크리스트

- [ ] 태스크 특성에 맞는 기본 지표를 선택했는가
- [ ] 전처리 파이프라인(소문자화, 토큰화)을 표준화했는가
- [ ] CI에서 지표 기준치(threshold)를 설정하고 자동 체크하는가
- [ ] 결정적 지표와 LLM-as-Judge를 함께 쓰는 계획이 있는가
- [ ] 지표 점수와 실제 사용자 만족도의 상관관계를 주기적으로 검증하는가

## 처음 질문으로 돌아가기

- **각 지표는 어떤 태스크에 적합한가?** Exact Match → 분류/단답, ROUGE → 요약, Token F1 → QA/정보 추출, BLEU → 번역.
- **같은 의미 다른 표현 문제는?** Token F1이 가장 관대하게 처리한다. 의미 수준까지 보려면 임베딩 기반 BERTScore도 고려한다.
- **결정적 지표의 한계 보완은?** 4편의 LLM-as-Judge와 함께 쓰는 것이 현재 가장 실용적인 조합이다.

## 정리

결정적 지표는 LLM 앱 평가의 첫 번째 방어선이다. 빠르고, 재현 가능하고, CI에 바로 통합할 수 있다. 한계가 있지만, 그 한계를 알고 쓰면 충분히 가치 있다.

태스크에 맞는 지표를 선택하고, 전처리를 표준화하고, 기준치를 정해서 CI에 넣는 것. 이 세 단계가 결정적 지표를 실제로 활용하는 방법이다.
