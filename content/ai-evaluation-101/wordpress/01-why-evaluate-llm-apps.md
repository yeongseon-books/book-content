# 바이브코딩을 위한 AI 평가 (1/10): 왜 LLM 애플리케이션을 평가해야 하는가

> 이 글은 **바이브코딩을 위한 AI 평가** 시리즈 1편입니다. LLM 앱을 만들 때 "그냥 해보니까 잘 됐어요"에서 벗어나, 측정 가능한 품질 기준을 세우는 법을 다룹니다.

바이브코딩으로 AI 앱을 빠르게 만들다 보면 어느 순간 같은 질문이 온다. "내 앱이 실제로 잘 동작하는 걸 어떻게 아는가?" 처음에는 직접 몇 번 테스트해 보고 "잘 되네"라고 넘어가지만, 사용자가 늘고 프롬프트를 바꿀 때마다 불안해진다. 지난번 잘 됐던 기능이 오늘 갑자기 이상하게 동작하기 시작한다. 무엇이 달라졌는지 알 수 없다.

LLM 앱 평가는 그 불안을 없애는 도구다. 처음에는 번거롭게 느껴지지만, 한 번 자리를 잡으면 프롬프트 변경, 모델 업그레이드, 기능 추가 때마다 오히려 빨라진다. 변경이 기존 기능을 망가뜨리는지 CI 단계에서 알 수 있기 때문이다.

평가 파이프라인의 핵심은 네 단계다. 입력을 정의하고, 기대 출력을 정하고, 모델 응답을 채점하고, 결과를 기록한다. 이 루프가 반복될수록 앱의 품질이 숫자로 보이기 시작한다. "잘 됐다"가 "87%의 케이스에서 정확도 기준을 충족한다"로 바뀐다.

이 시리즈는 바이브코딩으로 AI 앱을 만드는 개발자가 평가 역량을 자연스럽게 내재화하도록 설계됐다. 1편에서는 왜 평가가 필요한지, 최소한의 평가 파이프라인을 어떻게 세우는지 정리한다. 프로덕션에 내보내기 전에 "이 앱은 테스트를 통과한다"고 말할 수 있는 기준을 만드는 것이 목표다.

평가는 완벽을 요구하지 않는다. 지금보다 조금 더 측정 가능한 상태로 만드는 것에서 시작한다.

> 평가를 나중에 붙이면 붙일수록 더 어렵고 비용이 크다. 앱을 만드는 순간부터 평가 루프를 함께 설계하는 것이 바이브코딩의 올바른 리듬이다.

## 이 글에서 다룰 문제

- LLM 앱을 수동으로 확인하는 방식은 왜 프로덕션 규모에서 실패할까요?
- 최소한의 평가 파이프라인은 어떤 구성 요소로 이루어져야 할까요?
- 평가 데이터셋은 몇 개 케이스에서 시작하는 것이 현실적일까요?
- CI 파이프라인에 평가를 어떻게 연결할 수 있을까요?
- 이 주제에서 바이브코더가 가장 자주 놓치는 함정은 무엇일까요?

## Before / After: 평가 루프 도입 전후

| 상황 | 평가 없이 | 평가 루프 적용 후 |
|------|-----------|------------------|
| 프롬프트 변경 후 | "느낌상 더 좋아진 것 같아요" | "케이스 92개 중 88개 통과, 이전 대비 +4%" |
| 모델 업그레이드 | 배포 후 사용자 불만으로 발견 | CI 단계에서 회귀 케이스 사전 탐지 |
| 기능 추가 | 기존 기능 망가진 것 모름 | 전체 평가셋 통과 여부 자동 확인 |
| 팀 온보딩 | "직접 써보세요"가 유일한 기준 | 정량 기준으로 품질 공유 가능 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 수동 테스트만 의존 | 규모가 커질수록 빠진 케이스 증가 | 최소 10개 골든 케이스로 자동화 시작 |
| 평가 데이터를 학습 데이터와 혼용 | 낙관적 점수, 실제 품질 측정 불가 | 분리된 평가셋 유지 |
| CI 없이 평가 수동 실행 | 바쁠수록 평가 건너뜀 | PR마다 자동 실행 |
| 모든 케이스에 완벽한 정답 요구 | 평가셋 만들기 너무 어려워 포기 | "틀렸다/맞다"보다 채점 기준 먼저 |

## AI 팁: 평가 데이터 빠르게 만드는 법

바이브코딩 환경에서 평가셋을 만들 때 LLM을 활용할 수 있다. 실제 사용 케이스 5개를 AI에게 주고 "유사한 입력/출력 쌍 10개를 더 생성해 줘"라고 요청하면 시작점을 빠르게 만들 수 있다. 단, 생성된 케이스는 반드시 사람이 검토해야 한다. AI가 만든 평가 데이터에 AI가 좋은 점수를 받는 함정이 생길 수 있기 때문이다.

## 운영 체크리스트

- [ ] 최소 10개의 골든 입력-출력 쌍을 정의했는가
- [ ] 평가셋이 학습/파인튜닝 데이터와 분리되어 있는가
- [ ] 채점 함수 또는 기준이 코드로 정의되어 있는가
- [ ] PR/커밋마다 평가가 자동 실행되는 CI 훅이 있는가
- [ ] 점수 변화를 추적하는 결과 로그가 있는가

## 처음 질문으로 돌아가기

- **LLM 앱을 수동으로 확인하는 방식은 왜 실패할까요?** 사람이 직접 보는 속도와 커버리지는 자동화를 이길 수 없다. 앱이 커질수록 수동 확인은 가장 빠르게 포기하는 단계가 된다.
- **최소 파이프라인 구성 요소는?** 입력 정의, 기대 출력, 채점 함수, 결과 기록. 이 네 가지가 있으면 시작할 수 있다.
- **몇 개에서 시작해야 할까요?** 10개로 시작한다. 완벽한 100개보다 지금 당장 돌아가는 10개가 낫다.

## 정리

LLM 앱 평가는 선택이 아니다. 프롬프트를 바꾸고, 모델을 업그레이드하고, 기능을 추가할 때마다 무언가가 달라진다. 그 달라짐이 좋은 방향인지 나쁜 방향인지를 알아야 안전하게 앱을 발전시킬 수 있다.

10개의 골든 케이스, 하나의 채점 함수, CI 연결. 이 세 가지로 시작하면 오늘 당장 평가 루프를 만들 수 있다. 완벽한 평가 시스템은 이 작은 시작에서 자란다.
