# 바이브코딩을 위한 AI 평가 (8/10): 회귀 테스트 — 어제 잘 되던 게 오늘 망가지지 않게

> 이 글은 **바이브코딩을 위한 AI 평가** 시리즈 8편입니다. 프롬프트 변경, 모델 업그레이드, 기능 추가 시 기존 품질이 유지되는지 자동으로 확인하는 회귀 테스트를 다룹니다.

바이브코딩의 속도감은 매력적이지만, 빠르게 변경할수록 망가질 위험도 커진다. 특히 AI 앱에서는 프롬프트를 조금 바꿨을 뿐인데 이전에 잘 되던 케이스가 갑자기 틀리는 현상이 자주 발생한다. 이를 회귀(regression)라고 부르며, 소프트웨어 개발에서 회귀 테스트가 필수인 것처럼 AI 앱에서도 반드시 필요하다.

AI 앱 회귀 테스트의 핵심은 골든 데이터셋과 기준 점수(baseline)의 조합이다. 처음 앱이 잘 동작할 때의 점수를 기준으로 저장해 두고, 변경이 있을 때마다 이 기준과 비교한다. 기준보다 낮아지면 변경을 블락하거나 경고를 보낸다.

GitHub Actions를 사용하면 PR마다 자동으로 회귀 테스트를 실행할 수 있다. 개발자가 프롬프트를 변경하고 PR을 열면, 자동으로 평가 파이프라인이 돌아서 기존 케이스들의 점수가 얼마나 변했는지 PR 코멘트에 표시된다.

회귀 테스트 설계의 핵심은 임계값 설정이다. "점수가 2% 이상 떨어지면 실패"처럼 너무 엄격하면 정상적인 개선도 블락된다. "10% 이상 떨어지면 실패"처럼 너무 관대하면 품질 저하를 놓친다. 앱의 특성과 팀의 리스크 허용 수준에 따라 적절한 임계값을 설정해야 한다.

바이브코딩 워크플로에서 회귀 테스트는 특히 가치 있다. 빠르게 실험하고 변경하는 과정에서 자동 안전망이 있으면 더 과감하게 시도할 수 있기 때문이다. "이 변경이 기존 기능을 망가뜨릴까?"라는 불안 없이 실험할 수 있다.

> 회귀 테스트가 없는 AI 앱 개발은 안전망 없이 줄타기를 하는 것과 같다. 한 번 떨어지면 다시 올라가기 어렵고, 사용자는 이미 나쁜 경험을 했다.

## 이 글에서 다룰 문제

- AI 앱에서 회귀가 발생하는 주요 원인은 무엇인가요?
- 회귀 테스트를 GitHub Actions에 어떻게 통합할 수 있나요?
- 기준 점수(baseline)는 어떻게 설정하고 관리해야 할까요?
- 회귀 감지 임계값을 어떻게 결정해야 할까요?
- 모델 업그레이드 시 회귀 테스트 전략은 어떻게 달라지나요?

## Before / After: 회귀 테스트 전후

| 상황 | 도입 전 | 도입 후 |
|------|---------|---------|
| 프롬프트 변경 후 | 몇 가지 수동 확인 후 배포 | CI에서 자동 평가, 기준 대비 변화 표시 |
| 모델 업그레이드 | 배포 후 사용자 불만 접수 | PR 단계에서 회귀 케이스 사전 탐지 |
| 기능 추가 영향 | "혹시 다른 기능이 망가졌나?" 불안 | 전체 골든셋 자동 검증 |
| 팀 협업 | 누가 무엇을 망가뜨렸는지 모름 | PR별 점수 변화 추적 |

## 흔한 실수

| 실수 | 결과 | 올바른 접근 |
|------|------|------------|
| 기준 점수 없이 회귀 테스트 | 비교 대상이 없어 무의미 | 첫 안정 버전에서 baseline 측정 후 저장 |
| 너무 엄격한 임계값 | 정상 변경도 블락 | 점수 분포 분석 후 합리적 임계값 설정 |
| 전체 데이터셋에만 의존 | 특정 카테고리 회귀 놓침 | 카테고리별 회귀 지표 분리 |
| CI 실패 시 무시 | 회귀 테스트 의미 없어짐 | 실패 시 머지 블락 정책 수립 |

## AI 팁: 회귀 테스트 빠르게 설정하는 방법

GitHub Actions YAML 파일에 평가 스크립트를 호출하는 워크플로를 추가하는 것이 가장 빠른 시작이다. Claude나 GPT-4에 "Python으로 LLM 평가 스크립트를 GitHub Actions에 통합하는 YAML 파일을 작성해줘"라고 요청하면 기본 템플릿을 얻을 수 있다. 처음에는 5개 케이스로 시작해서 CI 실행 시간을 2분 이내로 유지하는 것이 좋다.

## 운영 체크리스트

- [ ] 기준 점수가 코드 저장소에 버전 관리되고 있는가
- [ ] PR마다 자동으로 회귀 테스트가 실행되는가
- [ ] 회귀 감지 임계값이 명확하게 정의되어 있는가
- [ ] 카테고리별 회귀를 분리해서 추적하는가
- [ ] 회귀 테스트 실패 시 머지가 블락되는가

## 처음 질문으로 돌아가기

- **AI 앱 회귀의 주요 원인은?** 프롬프트 변경, 모델 업그레이드, 외부 의존성 변경, 데이터 드리프트.
- **GitHub Actions 통합 방법은?** push/PR 이벤트에 평가 스크립트 실행 워크플로 추가. 결과를 PR 코멘트로 게시.
- **임계값 설정 방법은?** 과거 점수 분포를 보고, 자연스러운 변동 폭보다 크면 실패로 처리.

## 정리

회귀 테스트는 바이브코딩의 속도를 유지하면서도 품질을 지키는 안전망이다. 빠르게 실험하고, 자동으로 검증하고, 확신을 갖고 배포하는 사이클이 가능해진다.

처음에는 작은 골든셋과 간단한 CI 워크플로로 시작하고, 경험이 쌓이면서 점점 더 정교하게 만들어 나가면 된다.
